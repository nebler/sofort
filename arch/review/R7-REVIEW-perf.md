# R7 performance and memory review

Whole-RAM reset needlessly destroys immutable translations: a scratch-only writable-range reset removed 165 KVM fault events per steady tiny run and cut mean direct integrated-fixture CPU from 49.44 to 37.07 ms, nested.
Per-run codec/adapters expand a 35-byte one-tool body to 3,677 bytes, add about 172 KiB private dirty per slot, and account for an observed 9.55-ms nested CPU gap that includes parsing and adapter execution.
Owners run one guest until WAIT, FINISH or its deadline; a tiny job queued behind a 300-ms busy lease took 319 ms, so the 2-ms target also needs scheduling isolation.
The policy path needs fewer conversions and handoffs: the replay used 1.330 Node CPU-ms/run, while transport-only ping was 45.8/138.3 µs p50/p99; IPC alone does not explain the reported 817/3,994 µs policy round trip.
The short-fixture 0.48–0.55 MiB ledger remains useful, but does not certify the larger integrated body, Node state or native input/output retention; no metal latency or service-CPU target is established.

The Rust service was built from the reviewed source. The existing R7-IPC prepared QuickJS snapshot and Node runtime were copied into the scratch root. All 16 checked source-map entries in the reused executor bundles match current source byte-for-byte ([receipt](raw-perf/bundle-source-check.json)); hashes are in [environment.txt](raw-perf/environment.txt). ### P01 — Preserve immutable mappings across reset

`arch/jitk/shard/src/real_kvm.rs:310` calls `madvise(self.ram.ptr.cast(), RAM, 4)` across **32 MiB**. Yet `arch/jitk/shard/src/arena.rs:55` defines five stable regions with only the arena and 80-KiB transport writable, and `arch/jitk/shard/src/real_kvm.rs:216` / `:224` enforce KVM read-only plus host `mprotect` on the others. Discarding immutable pages gains no tenant-state reset. It removes their host mappings and invokes KVM's invalidation path; their translations must be rebuilt during execution.

The scratch prototype changes only that discard to the class arena and transport extents: 1,392,640 B for glue-2m, **4.15%** of RAM. Registers, MMIO drain, generation/RNG binding and guest code stay the same. All 50 runs in each of four fixture conditions return the expected result.

| Condition | Reset p50/p99 ms | RUN p50 ms | Mean reset+bind+run CPU ms |
|---|---:|---:|---:|
| Raw one-tool, full discard | 2.544 / 2.823 | 37.094 | 39.887 |
| Raw one-tool, writable discard | 1.117 / 1.219 | 28.376 | 30.024 |
| Integrated body, full discard | 3.076 / 4.296 | 45.581 | 49.437 |
| Integrated body, writable discard | 1.524 / 1.695 | 35.473 | 37.071 |

Fault evidence is stronger than a timing-only comparison: 55 return2 entries including warmups emit **20,460→11,550 `kvm_guest_fault` events**, with 55 MMIO events in both and zero major faults. A separate 15-run exit capture has **5,580→3,270 synchronous traps**. With full reset every run has 155 instruction-abort + 217 data-abort events; writable reset has the same first cold run, then **5 + 202** per run. Thus it avoids **165 events per steady run**, rather than merely shifting their timing. Counts include the doorbell fault. See [full-faults.csv](raw-perf/full-faults.csv), [writable-faults.csv](raw-perf/writable-faults.csv), [exit-counts.json](raw-perf/exit-counts.json), [writable-exit-counts.json](raw-perf/writable-exit-counts.json).

This separates two facts: **the code causes repeated translation work**, while **the cost per event in nested HVF→KVM is not a metal prediction**. The original reset metric also excludes first-touch costs incurred later inside KVM_RUN. Optimizing only its reported 2.6 ms misses much of this effect. Even this prototype remains far above 2 CPU-ms; the residual is not proven to be entirely a nesting artifact.

Keep both writable extents covered, including control/seed/rings and class-specific arena size. Do not replace the bounded extent reset with a guest-supplied dirty list. Before landing, run the existing full pristine comparisons, hostile all-writes, RNG, native-profile and lease/race suites, and measure on metal. The prototype is evidence for a change, not production certification.

### P02 — Prepare the trusted JS helpers once

`arch/jitk/executor/code.ts:12` inserts the complete codec, `installBase64`, proxy declarations and preludes into every body. `arch/jitk/executor/shard-backend.ts:15` adds another carrier/console/promise wrapper; `:24` embeds its JSON-escaped source inside another AsyncFunction. `arch/jitk/kernel/ring-bootstrap.js:49` compiles that wire wrapper, which then compiles the embedded body. The post-checkpoint path also allocates/formats repair objects at `ring-bootstrap.js:42`. Prepared QuickJS does not mean these helpers have been prepared.

[source-sizes.jsonl](raw-perf/source-sizes.jsonl) records **35 B raw → 2,340 B executionBody → 3,677 B wire** for one-tool, and 9→2,315→3,652 B for return2. Direct one-tool CPU averages **39.887 vs 49.437 ms**, with no Node policy in either measurement. The difference includes adapter execution, extra encoding, parsing and allocation; it is not all compiler time.

The two repeated private-dirty slopes are **288.000/288.063 KiB per raw slot** versus **460.000/460.000 KiB per integrated-body slot**: about **172 KiB extra per slot**. See [memory-repeat-0.jsonl](raw-perf/memory-repeat-0.jsonl) and [memory-repeat-1.jsonl](raw-perf/memory-repeat-1.jsonl). No Node per-run objects or KVM kernel charges are in those private-dirty figures. Adding the separately measured roughly 232-KiB KVM/host-kernel slope would already put this body near **0.676 MiB/slot** before Node: an **estimate**, not a new combined ledger. Therefore the R7 short-body 0.504-MiB one-tool row cannot certify this path's ≤0.6-MiB gate.

Compile immutable codec/carrier helpers before CHECKPOINT, then bind names/descriptors and compile tenant source once. Keep credentials/policy out of the guest. Providers with varying trusted preludes need explicit prepared-profile identity or a measured fallback. Re-run full byte/Unicode/error semantics and the all-in integrated ledger. The measured 172 KiB is an opportunity bound; necessary per-run codec work will remain.

### P03 — Make owners yield to queued work and cancellation

`arch/jitk/shard/src/owner.rs:421` drives a slot in an inner loop. On interruption, `:430` only sweeps expiries, then continues that same slot. `Command::Cancel` is handled only at `:382`, outside the loop. `Mailbox::send` at `:84` writes an eventfd; that wakes a sleeping owner but does not itself interrupt a KVM_RUN. The watchdog's expiry signal is the current preemption mechanism. Static `slot % owners` routing is at `owner.rs:148`.

The warmed two-slot/one-owner probe submits a busy generation with a 300-ms deadline, then a tiny return2 after **31.66 ms**. The tiny call completes in **319.28 ms**, versus the ordinary ~47-ms nested path. See [hol.jsonl](raw-perf/hol.jsonl). Deadlines can be admitted up to 60 s (`arch/jitk/shard/src/ipc_service.rs:45`), so one occupied execution lane can block its other slots for that order of time. This is code-level head-of-line blocking, independent of how much faster a tiny run becomes on metal. Four simultaneous busy slots can occupy all four owners.

Use an owner-local runnable queue, a host-controlled kick when another slot/cancel becomes runnable, and a bounded scheduling quantum when there is contention. On EINTR, yield to the queue instead of immediately redriving the same slot. Preserve lease/generation fencing and MMIO completion. A timer only needed under contention can avoid taxing the uncontended tiny path. Prompt per-slot cancellation must use the same mechanism.

### P04 — Remove internal wire-format round trips in Node

The shard CALL becomes a string wrapper and `parseFrame` at `arch/jitk/executor/shard-backend.ts:153`, then an object, then `feed(encode(frame))` at `:137`. `arch/jitk/protocol/dispatcher.ts:133` parses during encode; `:179` parses the fed bytes again. Sending a host frame calls encode/parse and then parses again at `dispatcher.ts:214`. The shard backend discards that encoded wire and constructs its own carrier at `shard-backend.ts:213`. `arch/jitk/executor/executor.ts:86`, `:88` and `:102` add codec conversions and a clone; policy adds another clone at `arch/jitk/executor/policy/policy.mjs:59`.

Counting wrappers around the builtins during ten warmed, successful real one-tool generations, including retirement, observe **13 JSON.stringify, 50 JSON.parse and two structuredClone calls per run**, with about 6,180 stringify-result bytes/run ([counts.jsonl](raw-perf/counts.jsonl)). **The parse count includes the strict parser decoding individual key tokens; it is not 50 whole-message parses.** Instrumented counts are not used for timing. The ordinary replay consumes 1.330 Node CPU-ms/run; the original run consumed 2.130 ms, both above the architecture's 100-µs broker trigger. These CPU totals include other Node work, so they are not an isolated conversion-cost estimate.

Expose a canonical object-frame validation/state-transition API and use it for internally constructed frames, preserving byte limits, duplicate-key rejection at hostile text ingress, scalar/codec semantics, IDs, pending credit and policy authority. Validate each trust crossing; eliminate encode→scan→decode chains inside one trust domain. Snapshotting helpers (P02) and this change should precede a broker rewrite decision. A metal uninstrumented phase profile is still needed to assign the saved CPU and re-evaluate the trigger.

### P05 — Publish all ready replies before resuming a slot

Each `Command::Reply` at `arch/jitk/shard/src/owner.rs:395` writes one reply, then falls into `s.drive` at `:427`. If other promises remain pending, the guest returns WAIT. `owner.rs:261` treats even WAIT with an empty request list as a Calls event, drains MMIO at `:275`, and notifies the reactor. Already queued sibling replies wait behind this entire cycle.

[batch-trace.txt](raw-perf/batch-trace.txt) contains two real executor jobs: one call, then Promise.all(10). It records **26 KVM_RUNs: 13 successful exits and 13 EINTR drains**. The one-call path requires two exits/drains; the ten-call path uses eleven of each. Direct synthetic batching in [probe.rs](raw-perf/probe.rs) applies every request reply before re-entering and needs two guest exits for a batch. Each carrier call still has its own ID and reply validation.

Drain ready commands into bounded per-slot reply batches; publish those replies and enter each runnable slot once. Do not delay an isolated reply waiting for a future batch. This avoids nine extra WAIT/drain cycles for ten replies already ready together, plus empty reactor events and repeated guest pending-map scans. It preserves asynchronous overlap rather than requiring providers to complete in order.

### P06 — Account and release native inputs/capture separately from the arena

`arch/jitk/shard/src/native.rs:95` creates a separately allocated sealed input memfd and binds it as a read-only KVM slot. `NativeVm.input` retains it (`:79`); successful completion at `:147` drains MMIO and returns without unbinding input or resetting RAM. The old input is removed only at the next run of that same profile (`:90`). The worker permits 16 retained profile VMs (`:183`). Archive size can approach 4 MiB (`arch/jitk/shard/src/inputs.rs:3`, `:133`).

Read-only means shareable **if content/backing actually is shared**. These memfds are built independently per request, so distinct inputs are distinct charged pages. Arithmetic: a near-4-MiB archive alone exceeds the 2-MiB class reservation before guest private pages/KVM state. Sixteen used profiles can keep nearly **64 MiB of old input extents** until reused or process exit, even though no run is active. Completed guest private pages remain as well. This does not invalidate the measured small native cases; the integrated ledger explicitly used only a **176-KiB** rounded input per VM (`arch/jitk/shard/RESULTS-R7-integrate.md`, memory-method section).

Host output capture permits another 1 MiB (`arch/jitk/shard/src/streams.rs:5`), then serializes a second output buffer (`native.rs:154`), while Node accumulates a response (`arch/jitk/mcp/native.mjs:82`). Arena identity and admission class do not bound these host allocations. Charge rounded input extents, capture and staging separately, and include all cached profiles in worker capacity. After successful delivery, schedule stopped reset/input removal and release their memory charge only after teardown. Cache an input extent only under an explicit bounded content-identity policy. The current native path has no equivalent of the JS scheduler's per-slot admission accounting.

### P07 — Coalesce IPC notifications and copy only bounded live bytes

`arch/jitk/shard/src/ipc.rs:151` copies **16,416 B** for every received record, then `:82` allocates/copies the live payload. `arch/jitk/executor/ipc/bridge.c:78` does the corresponding full slot copy and `:82` creates another Buffer copy. Node's outbound `record` adds a zeroed buffer plus payload copy (`arch/jitk/executor/shard-ipc.ts:15`). The fixed mapping is **2,105,344 B per channel**: about 32.1 KiB amortized over 64 slots, or a fixed ~2 MiB for a one-slot shard, not 2 MiB per VM.

A normal one-tool lifecycle carries START, REPLY, CANCEL in one direction and CALL, STATS, DONE, RELEASED in the other. Thus receive-side full-slot copying alone is **7 × 16,416 = 114,912 B/run**, before payload copies. Every send signals (`ipc.rs:199`, `bridge.c:66`); Rust additionally returns credit with a syscall per received record (`ipc.rs:163`); Node returns credit per drained batch (`bridge.c:85`). Owner mailboxes/events and arm/complete add further eventfd writes (`owner.rs:85`, `:501`; `lease.rs:156`, `:184`).

A 1,000-ping, 32-byte, no-KVM/no-policy probe measures **45.792/138.334 µs p50/p99**, Node CPU **41.392 µs/iteration** ([ping.jsonl](raw-perf/ping.jsonl)). CPU covers all 1,005 iterations; latency excludes five warmups. A separate service-style MMIO-drain probe observes WAIT-drain p50 **22.250/26.042 µs** for raw/integrated bodies, n=50 each; tails reach 259/148 µs. These are separate distributions, not an additive waterfall. They show transport and drain consume some budget, but cannot by themselves assign the original 817/3,994-µs owner round trip. Node processing, owner/reactor scheduling and per-reply resumption remain in that span.

Copy a fixed header privately, validate its private bounded length, copy only that bounded payload, then validate/use only private data. Preserve seals, private cursor shadows, generation fencing and all hostile-schema checks. Batch messages/credits and use an explicit race-safe sleeping/notification handshake; a naïve empty→nonempty check can lose wakes. Measure the same end-to-end owner span after each change.

### P08 — Make availability mean a physical slot is ready

`arch/jitk/shard/src/ipc_service.rs:97` sends READY after spawning owners. Their `slots` array initially contains only None (`arch/jitk/shard/src/owner.rs:343`). `Slot::new` runs lazily on the first command at `:365`. Node `park` creates a logical ShardSandbox at `arch/jitk/executor/shard-backend.ts:89`; it sends no physical preparation request. Thus `pool.warm()` alone does not warm KVM slots. The report already correctly says warm parking is uncertified; this finding identifies the concrete missing work.

`arch/jitk/shard/src/real_kvm.rs:205` performs VM create, five memslot registrations, vCPU create, preferred target and init: **nine KVM setup ioctls**, plus RAM/kvm_run mappings and three read-only mprotects. `Slot::new` at `:255` then restores **257 registers** before `Managed::begin` resets/restores again. The batch trace confirms one creation, five memslots and 1,285 register writes for the first two complete lifecycles: **257 initial + 2 × 2 × 257**. First admission therefore has **266 KVM ioctls beyond the ordinary begin path**, even on a quiet host.

Construct the requested reserve on its owners and acknowledge each physical slot's prepared/stopped state. Do not require tenant execution or fill every configured slot unnecessarily. Distinguish process READY from physical capacity ready, and measure the first run on every slot as well as repeated slot-zero runs.

### P09 — Reset once, then reuse the proven pristine state

The Node executor retires a successful sandbox (`arch/jitk/executor/executor.ts:132`), which sends CANCEL (`arch/jitk/executor/shard-backend.ts:223`); the reactor sends `pool.cancel` (`arch/jitk/shard/src/ipc_service.rs:174`), and the owner resets (`arch/jitk/shard/src/owner.rs:383`). Next admission calls `self.reset()` again at `owner.rs:222`. Each invokes the 257-entry loop at `arch/jitk/shard/src/real_kvm.rs:287`, regardless of whether the slot ran since the last reset.

The operation count is **514 KVM_SET_ONE_REG + two MADV_DONTNEED calls per steady generation**. The reset-only probe, with no guest mappings populated, measures **69.66 µs mean registers + 1.38 µs discard**, n=200. Reading all host RAM pages first changes discard to 83.39 µs mean; that probe still does not populate guest stage 2. These distinguish a clean duplicate restore from the dirty ~2.6-ms reset. Removing this redundancy does **not** save two dirty resets per run.

Carry an owner-private pristine/stopped flag through successful reset acknowledgement; admission binds directly from that state. Error/deadline paths must reset if necessary, exactly once before reuse. Keep completing pending MMIO before any discard/register restore. Do not omit registers merely because a tiny fixture did not modify them: the real guest uses system and SIMD state, unlike the older 34-register assembly stub at `arch/jitk/shard/src/kvm.rs:157`.

### P10 — Make native byte aggregation linear with reusable scratch

`arch/jitk/shard/src/native.rs:136` reads each ring byte through `read_volatile`; **one MiB output entails at least 1,048,576 volatile payload loads**, plus headers/padding. `arch/jitk/shard/src/streams.rs:86` allocates/zeros a record Vec and `:109` copies into a growing stream Vec. `native.rs:154` copies streams again into the worker response. The JS ring helpers also express wrapping copies bytewise at `arch/jitk/shard/src/real_kvm.rs:397`, `:551` and `arch/jitk/kernel/src/ring.rs:35`, `:79`.

Node's receiver performs `active.bytes = Buffer.concat([active.bytes, data])` on **every** pipe chunk (`arch/jitk/mcp/native.mjs:59`). For a one-MiB response delivered in sixteen equal 64-KiB chunks, copied prefixes total **64 KiB × (1+…+16) = 8.5 MiB**. This is an input-shape arithmetic example, not a claim that libuv always emits that chunk size. Smaller fragments amplify it further. The final base64 conversion also allocates output text and is required by the current MCP interface.

Use a fixed private scratch record per worker/owner and two bounded copies at ring wrap, retaining validation-before-use. Stream into a capacity-bounded output collector; use a bounded chunk list with one final concatenation or an announced-length buffer on Node. Avoid reserving a full one-MiB buffer for every idle slot. This is a native/bulk optimization, not an explanation of tiny one-tool's 56 CPU-ms.

### P11 — Optimize allocation writes/flushes conservatively

`arch/jitk/kernel/src/syscalls/mmap.rs:19` scans PTEs for first fit, `:40` maps pages, `:41` zeroes the entire rounded region and `:42` globally flushes. `arch/jitk/kernel/src/syscalls/brk.rs:11` accepts `brk(current_break)`, then flushes at `:14`; the flush is `dsb; tlbi vmalle1; dsb; isb` (`arch/jitk/kernel/src/arch/aarch64/page_tables.rs:164`). There is no new-page check for the flush. This concerns valid no-change requests, not the usual `brk(0)` query, which skips that branch. A no-change request need not alter any translation.

The merged native memory trace reports MicroPython's **2,101,248-B allocation = 513 × 4 KiB pages** (`arch/jitk/shard/RESULTS-R7-integrate.md`, root-cause section). mmap explicitly writes every byte even when backing is fresh zero snapshot data. That is a real write/CoW cost, but skipping zero-fill indiscriminately would reveal data after munmap/remap. The earlier guest-memory census found only **16 KiB** potential tiny-JS saving from an intentionally unsafe nozero experiment (`arch/research/perf/guest-memory/RESULTS.md`, §findings); do not rank memset removal ahead of P01/P02.

First avoid truly unchanged brk flushes and flush only when mappings change. Consider allocator/PTE bitmaps or a next-fit hint only if native traces justify the scan cost: current glue-2m scans at most 206 mmap pages; final glue-4m has 589. Correct lazy/known-clean zeroing requires tracking page initialization/reuse and testing partial unmaps, stale aliases and zero semantics. Compacting static page-table reservations is not automatically a private-memory saving: the ring tables include **16 × 4 KiB USER tables**, largely shared until modified (`page_tables.rs:44`).

### P12 — Scale lease work with changes rather than configured capacity

`arch/jitk/shard/src/owner.rs:347` / `:349` sweep all owned slots on wake and before each command; `:471` scans the whole array, even when almost every slot waits on a long tool. A separated Start/Reply/Cancel lifecycle has three wakes plus three command sweeps: at 64 slots/four owners that is **6 × 16 = 96 slot visits**, versus **1,536** at the 1,024-slot offline configuration. Coalesced wakes reduce this count; interrupts can add more.

`arch/jitk/shard/src/lease.rs:342` scans the entire lease board on each change wake. Arm and completion notify it at `:156` and `:184`; wakes may coalesce. Lease arm also calls gettid per run (`:153`) although the owner TID is fixed. `Pool::try_recv` calls watchdog check (`arch/jitk/shard/src/owner.rs:161`) and hence child.try_wait (`lease.rs:259`) each time the reactor probes events, including empty probes. These are concrete O(N)/syscall costs, not evidence they dominate the current 64-slot run.

Cache owner TIDs, maintain bounded active/expired queues, and use a deadline heap or change queue for the independent watchdog. Fold its pidfd into reactor polling rather than repeated try_wait. Retain the independent process and generation-CAS escalation; do not trade the Node-blocked deadline guarantee for fewer syscalls. At 64 slots, this ranks behind the measured guest/reset/adapter costs. The watchdog itself already blocks indefinitely when no lease changes/deadlines exist; the reactor's separate 100-ms liveness poll (`arch/jitk/shard/src/ipc.rs:210`) is deliberate bounded idle work.

## What is already good

- Stable VM/vCPU ownership, shared MAP_PRIVATE snapshots, MADV_NOHUGEPAGE and five immutable/writable memslots avoid per-run VM construction, bulk RAM copies and huge-page CoW. The authoritative R7 cgroup slopes include KVM charges: roughly **232 KiB kernel/slot**, 0.485/0.504/0.552 MiB total for the short fixtures (`arch/jitk/shard/RESULTS-R7-shard.md`). Optimizing a few hundred bytes of Rust Slot metadata cannot erase that kernel floor; do not mislabel 32 MiB configured RAM as resident private memory.
- WAIT releases owner stacks. The existing 1,024-waiter receipt shows five shard tasks plus one watchdog and zero process CPU ticks during its measured idle second. There is no per-waiter thread, per-tool helper process or JSON payload pipe on the JS policy path.
- MMIO completion is explicitly drained before register restore, all captured real-guest register state is restored, and generation-fenced independent deadlines do not depend on Node making progress. Those properties must survive optimization.
- Ring publication uses acquire/release cursors, bounded IDs/payloads and private copies; native byte streams avoid UTF-8/JSON expansion. Native code-cache cleaning is offline (`arch/jitk/kernel/src/ring.rs:295`), rather than CoWing the loader range after restore.
- Archive lookup uses binary search (`arch/jitk/kernel/src/fs.rs:88`); read/pread copy directly from immutable archive bytes into checked user ranges (`fs.rs:127`, `arch/jitk/kernel/src/syscalls/pread64.rs:20`). There is no eager whole-file guest copy to remove. Ring stage 1 uses block mappings for immutable RAM (`arch/jitk/kernel/src/arch/aarch64/page_tables.rs:84`), much smaller than the older identity-map table array. The generated syscall dispatcher is a Rust match (`arch/jitk/kernel/build.rs:56`); no evidence here supports replacing dispatch or stripping correct SIMD saves ahead of the ranked work.
