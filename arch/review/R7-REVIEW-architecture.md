# R7 architecture review

The core VM primitives are appropriate: retain file-backed CoW reset, bounded rings, fixed owners, and stage-2 writable arenas.\
The largest long-term costs are incomplete process isolation, shard-controlled watchdog authority, and three diverging execution lifecycles.\
The current code does not bind every admission reservation to its loaded snapshot class, and guest-controlled protocol errors can terminate a whole shard.\
Build/test entrypoints still depend on explicit environment configuration and private VM artifacts; they do not enforce the planned backend parity matrix.\
Consolidate contracts and lifecycle ownership before Linux cutover; the evidence supports targeted simplification, not a transport or VMM rewrite.

Reviewed commit: `bb95bf2c3960128a794a76355b6258daec4199e0`, 2026-10-26. Paths below are relative to the repository root. Read-only product review; only this report was added. Findings are ordered by expected long-term cost, including security boundaries, future ABI changes, and recurring integration work. **P1** means a cutover blocker or a boundary that must be resolved before relying on its advertised guarantee; **P2** means material correctness/maintenance work. Effort is an engineering estimate: **S** = roughly 1–2 days, **M** = several days, **L** = one or more weeks, including meaningful validation.

Read the goal/scope in `arch/V1.md`, intended architecture in `arch/architecture/ARCHITECTURE.md`, and `arch/work/CUTOVER-PLAN.md`; also inspected the R7 RNG, bytes, shard, IPC, integration, grow, and nested-suite reports. Those reports describe historical experiments, not measurements repeated by this review. The shard remains explicitly experimental (`arch/jitk/executor/select-backend.ts:28`); several findings are acknowledged implementation gaps, not undisclosed changes to the shipping default.

## Details

### A01 — Process boundaries must enforce the stated trust model

**Code verified; no exploit attempted.** The JS shard gets only `PATH` and selected IPC fds, which is good, but environment stripping does not prevent host file/network/process access after a VMM compromise. Startup performs parent-death handling, maps IPC, opens KVM, loads snapshots and starts owners without applying a sandbox (`arch/jitk/shard/src/ipc_service.rs:77`; `arch/jitk/shard/src/real_kvm.rs:102`). Native spawning supplies neither confinement nor an environment allowlist (`arch/jitk/mcp/native.mjs:45`). A normal guest has KVM isolation; this finding concerns the explicitly **untrusted host shard**, not evidence that guest code directly accesses host credentials.

The shipping VMM already has fail-closed confinement preparation/application and an acknowledgement after Linux setup (`arch/jitk/vmm/src/main.rs:96`, `:109`; `arch/jitk/vmm/src/confinement.rs:12`). Extract the useful launcher contract and build shard-specific rules around its actual fd/ioctl/thread needs; do not blindly copy libkrun allowlists. Restrict filesystem and network access, process signalling/inspection, inheritance and resources. Otherwise the “Node alone has usable authority” property is only a programming convention. Add hostile host-shard probes, independently of hostile-guest ring tests.

### A02 — Keep independent enforcement outside the failure domain

**Code verified; compromise scenario is an architectural inference.** `Board::map` maps shared state read/write in the shard (`arch/jitk/shard/src/lease.rs:62`). `Lease::arm`, `complete` and `acknowledge_reset` update the same state that tells the watchdog whether to act (`:145`, `:171`, `:188`). The watchdog scans only ARMED entries and trusts the supplied deadline (`:342`). A compromised shard can clear or postpone a lease; no watchdog wakeup algorithm can recover an authoritative deadline it never owned. Even without compromise, the shard reactor is responsible for noticing watchdog exit (`arch/jitk/shard/src/owner.rs:160`), so enforcement lacks a trusted liveness owner if that reactor also stalls.

Have the trusted supervisor create/register `(shard, slot, generation, deadline)` with the watchdog before dispatch. Keep that registration inaccessible to shard writes. Shard reset acknowledgements must not cancel the supervisor's whole-shard safety deadline without the defined validation/liveness protocol; same-user unrestricted signalling must also be addressed by A01. Generational CAS and pidfds should survive this change. Separately, the configured escalation grace is 100 ms after firing (`arch/jitk/shard/src/owner.rs:113`; `arch/jitk/shard/src/lease.rs:365`), so it cannot substantiate a universal ≤50-ms deadline-stop claim. Responsive-owner timings in the R7 report are a narrower claim. Specify and test both owner stop and escalation budgets.

### A03 — A writable bound and an admission charge must identify the same class

**Code-path verified; not a KVM measurement.** The finite class catalogue is a good fail-closed layout check. However, the IPC START accepts only a 2-MiB reservation (`arch/jitk/shard/src/ipc_service.rs:44`), and `ShardBackend` advertises 2 MiB and writes that reservation (`arch/jitk/executor/shard-backend.ts:31`, `:208`). The service independently loads any recognized snapshot (`arch/jitk/shard/src/ipc_service.rs:88`; `arch/jitk/shard/src/real_kvm.rs:124`). Glue4m is recognized and has 2,883,584 arena bytes plus 81,920 transport bytes (`arch/jitk/shard/src/arena.rs:16`, `:55`), already more than the reservation before KVM/host overhead.

A valid **QuickJS** glue4m snapshot can be built with the existing class selector (`arch/jitk/kernel/build-ring.sh:17`); this is not an attempt to execute a native snapshot as JS or a claim that the guest can negotiate its own class. It is a trusted configuration mismatch the service should reject. The immediate fix is a startup Glue2m assertion returned as a configuration error before READY. General admission should select a verified runtime/profile/class artifact and derive its charge from trusted metadata. The control page and an untrusted shard READY claim must not determine the charge.

### A04 — Native is a second shard implementation, not just another profile

**Code verified.** `createJitk` creates a separate native runner next to its selected executor backend (`arch/jitk/mcp/jitk.mjs:52`, `:56`). Native directly issues KVM_RUN and decodes MMIO in its own loop (`arch/jitk/shard/src/native.rs:112`), bypassing `Managed`, its owner scheduler and leases. It maintains one slot per tool and admits one request at a time (`:180`; `arch/jitk/mcp/native.mjs:75`). Its only timeout is Node's timer (`arch/jitk/mcp/native.mjs:81`): a blocked Node event loop delays enforcement, and cancellation permanently stops all native service until MCP restart (`:73`).

The binary length-prefixed native payload is not itself a wrong primitive; raw bytes are appropriate. The duplication is lifetime, admission, watchdog, reset, cancellation and recovery. Introduce a job-kind boundary under the common owner pool: JS emits policy calls, native emits bounded byte output, both share slot/class/generation/deadline/release handling. Keep per-profile preparation and the RO archive adapter. This avoids maintaining two security and recovery models as each gains concurrency.

### A05 — Fail closed at the smallest boundary that owns the failure

**Host reproduction plus code verification.** In `echo`, `next++` happens before the encoded-size check (`arch/jitk/kernel/ring-bootstrap.js:20`). A 2,000-character argument rejected and caught by JS consumes ID 1 without writing a request. The next small call attempts fd130, physical ID 2. The kernel permits that fd range but expects NEXT=1 and returns EINVAL (`arch/jitk/kernel/src/ring.rs:249`); the Promise executor consequently rejects after its pending entry has been installed (`arch/jitk/kernel/ring-bootstrap.js:24`). A caught local-limit error therefore poisons subsequent call sequencing and leaves stale bootstrap pending state. The host probe reproduced the fd130 attempt with mocked `os.write`; the intervening kernel rejection is verified from code, not from an end-to-end KVM run.

Independently, a hostile guest's bad record cursor/header/kind is handled by `assert!`, UTF-8 `unwrap`, or panic in the production JS Slot decoder (`arch/jitk/shard/src/real_kvm.rs:473`, `:487`, `:504`, `:515`), with `panic="abort"` (`arch/jitk/shard/Cargo.toml:12`). That terminates the entire shard and all its unrelated runs. The reactor also promotes guest call-schema/sequence errors to process exit (`arch/jitk/shard/src/ipc_service.rs:200`, `:292`). Native's `streams::Receiver` already demonstrates the better bounded `Result` style (`arch/jitk/shard/src/streams.rs:46`).

Validate/encode before advancing IDs or registering pending callbacks; handle failed writes by removing pending state. Convert guest failures into `RunError::GuestProtocol`, drain/reset the stopped slot and report it through the ordinary completion path. Keep shard-wide termination for a corrupt Node↔shard peer or broken host invariant. A malformed guest is expected input to this product, not an assertion failure in the host.

### A06 — Own the wire definitions once; version the actual connection

**Code verified.** The kernel's CTRL address, sizes and record fields (`arch/jitk/kernel/src/ring.rs:6`, `:67`) are reproduced in the host (`arch/jitk/shard/src/real_kvm.rs:26`, `:479`) and native decoder (`arch/jitk/shard/src/streams.rs:2`, `:62`). The nine-word layout is independently authored in kernel stage 1 and the shard catalogue (`arch/jitk/kernel/src/arch/aarch64/page_tables.rs:24`; `arch/jitk/shard/src/arena.rs:31`). Node IPC has yet another geometry in C, Rust and TS (`arch/jitk/executor/ipc/bridge.c:16`; `arch/jitk/shard/src/ipc.rs:15`; `arch/jitk/executor/shard-ipc.ts:3`). Comments and ABI Markdown cannot make these declarations mechanically agree.

Guest wire major/minor, `JTKREGS2` and layout version 2 **do exist**; the problem is uneven ownership/versioning. Policy IPC has size/seal validation but no control magic/version or capability negotiation, and READY contains no version/profile/geometry (`arch/jitk/shard/src/ipc.rs:116`; `arch/jitk/shard/src/ipc_service.rs:97`). A stale addon and newer shard with unchanged geometry can get past startup and disagree only after admission. A small schema or `no_std` crate should own offsets, bounds, class layouts and enums, with generated foreign-language constants, compile-time size/offset assertions and common golden records. Keep guest ring ABI, policy IPC and snapshot format as separately versioned contracts, not one accidental release number.

### A07 — A fresh clone cannot reproduce the current certification contract

**Code verified; one prerequisite failure reproduced.** Top-level build never builds the ring image, shard, prepared snapshots or Linux addon; top-level test never invokes `shard/Makefile` (`arch/jitk/Makefile:9`, `:16`). Executor testing adds the focused shard suite only under explicit SSH/snapshot environment settings (`arch/jitk/executor/run.sh:25`). MCP's test target does not run its real native Linux test (`arch/jitk/mcp/Makefile:11`). There is no aggregate runner executing and diffing the same corpus on both backends, as required by `arch/work/CUTOVER-PLAN.md:31`.

Running `env -u JITK_NODE python3 arch/jitk/docs/delegate.py executor/policy test` exits 1 with the instruction to set an absolute Node path, even though Node is installed. This is an explicit requirement in `arch/jitk/docs/delegate.py:13`, not an inferred `/tmp` failure. The focused shard SSH runner defaults to an already installed Node and already prepared snapshot inside `/home/dev/r7-ipc/` (`arch/jitk/executor/ipc/run-ssh.py:25`). The native preparation gate hardcodes `/home/dev/r6-census/raw` and follows binary paths from those metadata files (`arch/jitk/shard/harness/prepare-native-r7.py:10`, `:37`). The replacement nested suite defaults to an existing VM wrapper (`arch/jitk/linux/run.sh:8`; `arch/jitk/linux/nested/run-ssh.py:19`). These are reproducible lab workflows only when that private state exists.

Toolchain selection also forks: default kernel builds pin Rust 1.95.0 and a Homebrew objcopy path (`arch/jitk/kernel/build.sh:9`), ring builds use ambient cargo/objcopy (`arch/jitk/kernel/build-ring.sh:24`), and shard tests use moving `+stable` (`arch/jitk/shard/Makefile:3`). The ring payload source recipe does pin and verify upstream archives (`arch/jitk/kernel/payload/ring-rng/build.sh:14`), so this is not a claim that all inputs are unpinned.

Provide one documented setup/toolchain manifest, discover and validate installed Node by version, bootstrap reproducible artifacts into a checkout/cache directory, and define Linux-local and documented nested test entrypoints. Keep optional external comparison harnesses separate from product parity. Run the shared corpus through both selectable backends and include arena/IPC/native conformance in the supported Linux `make test`. Do not flip the default based on the present aggregate green result. A complete fresh-clone build was not attempted in this review.

### A08 — Prepared files need one verified identity, not more signatures

**Code verified.** `Snapshot::load` accepts a RAM-length check, a recognized layout also found in the first 512 KiB of memory, register magic and a minimum register count (`arch/jitk/shard/src/real_kvm.rs:124`). These are valuable structure checks but do not tie memory and registers to the same preparation or bind the artifact to QuickJS versus a native profile. The native harness writes hashes to a receipt, but runtime loading does not consume it (`arch/jitk/shard/harness/prepare-native-r7.py:49`; `arch/jitk/shard/src/native.rs:193`). Preparation publishes `.mem`, `.regs`, then `.layout` separately with create-new writes, and finally chmods them 0444 (`arch/jitk/shard/src/real_kvm.rs:627`). A failed preparation can leave partial files, and mode 0444 is not immutability against an owner able to change permissions or another writer.

Use an atomically published manifest that binds every component hash, runtime/profile, guest ABI, layout class and relevant machine-local KVM compatibility. Select that artifact by the architecture's prepared key. Verify once in trusted setup and give confined shards read-only handles to immutable content; a fully sealed shared backing object is an option for local snapshots. Do not build cross-host migration or mandatory public-key signing for v1. The immediate problem is stale/mixed local components and unconstrained runtime/profile selection, not an unproven remote cache attacker.

### A09 — Ownership is correct; it is not a scheduling policy

**Code verified; latency impact inferred, not timed here.** Commands are consumed serially by an owner. For the selected slot, `drive` loops through guest exits and the worker continues the same slot after interruptions (`arch/jitk/shard/src/owner.rs:244`, `:348`, `:421`). The watchdog supplies expiry kicks, not a time slice. A long CPU job can therefore monopolize the owner shared by other slots; slot placement is fixed modulo owner count (`:146`). START deadlines do not become watchdog leases until `begin` runs (`:220`).

Node cancellation only queues CANCEL (`arch/jitk/executor/shard-backend.ts:218`), and the owner cannot dequeue it while stuck in that job's KVM_RUN. This is distinct from releasing threads at WAIT, which is implemented correctly. Keep fixed ownership but add a bounded runnable queue, a host quantum, cancellation kicks and admission-time tracking of queued deadlines. A quantum interruption must return to owner scheduling, not immediately rerun the same slot. Test a spinner, a tiny job and a cancelled parked job on the same owner; standalone density and responsive-owner expiry tests do not establish fairness.

### A10 — The custom parser adds another accepted language to maintain

**Reproduced with the actual Rust parser and Node `parseFrame`.** This 82-byte request passes `ipc_json::request`:

```text
["call","ns","fn", <31 '[' characters> 0 <31 ']' characters> ]
```

Node wraps it as `{"args":REQUEST}` (`arch/jitk/executor/shard-backend.ts:153`), then rejects it with `DEPTH`. Rust starts recursion at depth zero and permits depth 32 (`arch/jitk/shard/src/ipc_json.rs:92`, `:221`); Node counts its extra envelope container in its 32-level structural budget (`arch/jitk/protocol/dispatcher.ts:61`). The input is within the 1,024-byte call budget and contains no unusual numbers or Unicode. This is not a policy bypass; it is proof that validators advertised as one contract drift, and that drift can turn a bounded guest request into a shard-wide connection failure.

Because the shard is untrusted and Node already validates every CALL, bounded opaque forwarding removes more complexity than replacing one full parser with another. Retain transport length/state/identity checks. If Rust must validate semantics, use maintained grammar decoding, explicitly reject duplicate keys, and differential-test strings, surrogate pairs, numbers, depth and structural budgets on exactly the envelopes used in production. The small native LOG escape recognizer is a finite canonical format (`arch/jitk/shard/src/streams.rs:128`), not a reason to retain a general bespoke JSON parser.

### A11 — A unified descriptor model would remove feature-driven syscall branches

**Reproduced by compiling the actual ring `fs.rs`, close and fstat handlers with mock user-memory helpers.** Allocate a regular fd, duplicate it to stdin, close the original, then close stdin. Both `fstat(0)` and another `close(0)` return 0, rather than EBADF. The descriptor table correctly removes fd0, but its absence is reinterpreted as an implicit console (`arch/jitk/kernel/src/syscalls/fstat.rs:5`; `arch/jitk/kernel/src/syscalls/close.rs:3`). The same distinction is repeated in read/readv, pread64 and fcntl (`arch/jitk/kernel/src/syscalls/read.rs:5`; `arch/jitk/kernel/src/syscalls/readv.rs:8`; `arch/jitk/kernel/src/syscalls/pread64.rs:6`; `arch/jitk/kernel/src/syscalls/fcntl.rs:4`). `poll_fd` separately decides availability by numeric fd (`arch/jitk/kernel/src/syscalls.rs:23`).

Use explicit initialized console descriptors, closed state, and shared open descriptions in one small table for both transports. No general VFS is needed. Let the console implementation determine byte transport; it should not determine whether a Linux descriptor exists. This also removes a substantial part of `transport-ring` branching from syscall handlers.

The same boundary problem appears beyond fds: `console` names both a byte console and ring checkpoint/native-lifecycle/syscall dispatch (`arch/jitk/kernel/src/main.rs:8`; `arch/jitk/kernel/src/ring.rs:179`, `:295`). `user::access` returns a physical address on one backend and a virtual address on the other, relying on a PAN change in the trap path (`arch/jitk/kernel/src/user.rs:97`, `:162`). A checked `UserRange`/copy API with defined address semantics, and explicit runtime/transport/platform operations, would prevent callers named `pa` from needing transport knowledge. Keep compile-time backend selection at those few boundaries; two platforms do not require dynamic trait objects everywhere.

### A12 — Removing timer devices should not remove time semantics

**Code verified; timed-WAIT behavior is a control-flow inference, not a KVM reproduction.** The ring clock is just control+0x220 and explicitly freezes during CPU work (`arch/jitk/kernel/src/arch/aarch64/wait.rs:1`). Host entry refreshes it (`arch/jitk/shard/src/real_kvm.rs:425`), so `clock_gettime` sees progress only after another host interaction (`arch/jitk/kernel/src/syscalls/clock_gettime.rs:6`). A guest loop waiting for clock advancement without a doorbell therefore cannot terminate normally through clock progress. The real-clock cutover requirement is explicit (`arch/work/CUTOVER-PLAN.md:27`).

WAIT writes its deadline at control+0x230 (`arch/jitk/kernel/src/arch/aarch64/wait.rs:9`), but the JS owner parks on WAIT, even with no pending calls (`arch/jitk/shard/src/owner.rs:261`), and its command protocol has no timer-ready event (`:70`). The overall lease is a run-kill deadline, not successful `ppoll` timeout delivery. Implement a live monotonic clock using a reference-host-validated ARM virtual-counter delta from a fresh restore baseline, and schedule timed WAIT on a host deadline queue/event source. This can retain the device-free guest and the fixed-owner design. Do not conflate the watchdog with the guest's timer service.

### A13 — Promote the implementation from experiment binaries to a library

**Code verified.** Cargo auto-discovers `src/main.rs` and `src/bin/real.rs`; there is no library target. The default binary still creates a synthetic snapshot and runs fixture ABI v0 (`arch/jitk/shard/src/main.rs:494`), while `real` imports modules with `#[path]`, routes through an alias named `kvm`, contains fixture source strings, and dispatches offline modes alongside production IPC/native modes (`arch/jitk/shard/src/bin/real.rs:1`, `:16`, `:41`, `:67`). `kvm.rs` and `real_kvm.rs` duplicate mapping, ioctl, KVM construction and reset machinery (`arch/jitk/shard/src/kvm.rs:23`; `arch/jitk/shard/src/real_kvm.rs:31`). `native.rs` is a child of `real_kvm` and imports all of its parent's internals (`arch/jitk/shard/src/native.rs:1`).

This makes private fields and module nesting carry lifecycle contracts; it also means every normal shard build assembles synthetic and attack guest code and requires the corresponding tools (`arch/jitk/shard/build.rs:18`). Some test modules correctly use `#[cfg(test)]`; the finding concerns ungated fixture/attack/measurement runtime code, not ordinary Rust unit tests.

Create `lib.rs` with explicit protocol/layout, snapshot, Linux platform, VM lifecycle, owner and reactor interfaces. Move synthetic fixture v0 to a clearly named example/harness and eventually retire duplicate platform code after preserving its useful tests. Keep production CLI parsing small; make preparation/bench/attack targets explicit. As a concrete testability benefit, this review compiled the existing `arena`, `ipc_json`, `inputs` and `streams` modules together on macOS and passed all 11 unit tests without KVM. Their portability is currently hidden behind a build script that asserts Linux arm64 (`arch/jitk/shard/build.rs:9`).

### A14 — Preserve the grow gate while reducing incidental coupling

**Code verified.** The grow transaction is genuinely stronger than repeated discovery: profiles require semantic/error/state cases, compilation failure does not count as a killed mutant, complete trace evidence is required, and SQLite integration is mandatory for its handlers (`arch/jitk/grow/loop.py:92`, `:123`, `:142`). Keep those safeguards.

However, pread mutants assert exact source substrings and replace exact return expressions (`arch/jitk/grow/profiles.py:45`). A semantics-preserving refactor can make the acceptance machinery fail or cease to apply its intended mutation. Candidate builds always use `qjs,grow-trace` and the canonical libkrun VMM (`arch/jitk/grow/runtime.py:90`, `:109`); acceptance is not automatically proof for the relocated ring memory and descriptor paths. The live prompt also prescribes console-by-number assumptions now conditional in the actual implementation (`arch/jitk/grow/agent.py:22`).

At the build boundary, `slots.json` is parsed once by Python for manifest data and again by Rust using quoted fragments of lines (`arch/jitk/kernel/build.rs:27`, `:36`). Reformatting valid JSON onto one line would not preserve that second parser's behavior. Parse the registry once with a standard JSON parser and emit both dispatch and manifest from that object. Supply mutants as explicit profile implementations or well-defined mutation operations with applicability assertions, and run backend-neutral behavioral cases against both kernels. Preserve recorded-versus-live authorship labels and isolated transactions rather than inventing a second controller.

## What is already good

- The hardware-enforced writable extents and sealed, separate RO input archive address hostile guests at the right layer (`arch/jitk/shard/src/real_kvm.rs:213`; `arch/jitk/shard/src/native.rs:21`).
- Private cursor shadows, bounded copies, fixed queues and native byte-stream totals are real fail-closed mechanisms, not documentation-only promises (`arch/jitk/shard/src/ipc.rs:143`, `:166`; `arch/jitk/shard/src/streams.rs:46`).
- Reset owns the stopped MMIO barrier, register restoration and host state; the Node slot remains charged until RELEASED (`arch/jitk/shard/src/real_kvm.rs:306`; `arch/jitk/executor/shard-backend.ts:145`).
- Fixed owners correctly release threads at WAIT. Generation fencing and pidfd-based escalation are worth preserving when authority is moved (`arch/jitk/shard/src/owner.rs:261`; `arch/jitk/shard/src/lease.rs:353`).
- Canonical Node policy remains on the actual tool-call path, and the default remains libkrun while shard parity is incomplete (`arch/jitk/mcp/jitk.mjs:69`; `arch/jitk/executor/select-backend.ts:23`). Keeping macOS libkrun is consistent with v1 scope; an enforced, finite Linux shadow period is preferable to prematurely unifying hypervisors.
- R7 evidence distinguishes nested from metal, unsupported profiles from full Linux ABI, and replay from live growth. Keep that discipline while replacing private lab prerequisites with repeatable product gates.
