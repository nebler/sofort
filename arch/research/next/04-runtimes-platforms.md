# Runtime images and competing execution platforms

Research date: **2026-10-25**. Scope: runtime memory, startup, useful CPU throughput, snapshotting, and the commercial alternatives to jitk. Research only; no builds, benchmark runs, cloud resources, or source changes were made.

## 1. Decision and evidence boundaries

**Ship separate Bellard QuickJS and PUC Lua snapshot templates first. Do not initialize every language in one image.** Keep quickjs-ng as a measured alternative; investigate an embedded V8 jitless snapshot before rejecting it on startup grounds. Offer CPython separately with a larger memory class. WAMR AOT is the most plausible small optional Wasm guest; Wasmtime is the stronger components/ecosystem option. Static Hermes and Porffor belong in an offline compilation experiment for reusable programs, not the default execution path for fresh agent code. These are recommendations, not measured outcomes.

The defensible positioning is **small, locally embedded, hardware-isolated execution of a restricted static Linux ABI, with asynchronous host capabilities**. It is not “faster JavaScript than isolates,” “arbitrary Linux,” or a demonstrated two-MiB Python computer. Two updates weaken the earlier [landscape](../landscape.md): Dynamic Workers now document Python, and OpenAI documents a fresh V8 runtime for programmatic tool calling. Conversely, Cloudflare's unique-worker creation fee is now active. Sources appear in §5–6.

Evidence notation: **L** = existing local measurement, not rerun; **P** = primary publication/source; **V** = vendor claim; **I** = inference/estimate. **NR** means no defensible number verified. Startup can mean runtime construction, process launch, VM restore, or remote API-to-first-command; those are different measurements. RSS, allocator peak, private dirty pages, provisioned RAM, and account concurrency limits are also different. Unless stated otherwise, vendor CPU model, per-host density, and physical incremental memory are **NR**. Prices are USD public list prices retrieved on the research date, excluding discounts, taxes, network/storage, and model tokens unless specified.

Local baseline: quiet Apple M4 Pro/macOS/HVF, one VMM process per VM, raw parked one-tool **0.285 ms**, raw cold approximately **6 ms**, executor cold **9.2 ms**, **4.8 CPU-ms/VM**, reported **10.7 MiB** footprint versus Hyperlight **1.8 MiB**. The footprint excludes some HVF accounting and is not an all-in density measurement. Planned ≤2 MiB/VM, ≤1 ms restore and ≤1 CPU-ms/run are **targets**. R5 also records a direct-loader change saving **2.8 MiB/VM**; do not combine that revision with the older baseline without remeasurement. [Brief](BRIEF.md), [final results](../../FINAL.md), [R5](../../PLAN-R5.md), [memory attribution caveat](../quickjs-verdict.md).

**Bellard versus ng.** NG documents opcode fusion, polymorphic inline caches, allocator/parser work, CMake, and test262 on each change. Those are engineering advantages, not proof of lower runtime cost on our workload. Bellard wins most existing local cells; ng wins the single-string JSON case and promise loop. Keep identical optimization flags, allocator/libc, features and heap caps in the next comparison. Security maintenance must be assessed by fixes and pinned builds, not CVE counts: NG explicitly excludes adversarial bytecode hardening and no longer accepts private reports/issues CVEs. Treat snapshots and precompiled bytecode as trusted build artifacts. [NG differences](https://quickjs-ng.github.io/quickjs/diff/), [security policy](https://github.com/quickjs-ng/quickjs/blob/master/SECURITY.md).

**Hermes is three different proposals.** Ordinary Hermes precompiles to bytecode and interprets it, saving source parsing for known applications. Static Hermes emits C and invokes a native compiler; typed code can optimize much better than untyped dynamic code. The evolving `static_h` branch also has a JIT: Meta's June 2025 chart explicitly measures **hv32+jit** and separately **hv32+interpreter**. Do not credit its JIT chart to AOT or interpreter execution. HV32 compresses values/pointers and boxes doubles. No verified comparable snapshot-private-memory result was found. Its C++ runtime/GC/platform port is substantial relative to running the already-working static qjs. [Original architecture](https://engineering.fb.com/2019/07/12/android/hermes/), [compiler explanation by maintainers](https://github.com/facebook/hermes/discussions/1685), [configuration-labelled update](https://github.com/facebook/hermes/blob/static_h/doc/blog/2025-07-15-static-h-performance-june-2025.md).

**V8 jitless is a real candidate, not Node-in-a-VM.** It executes JS with Ignition and native builtins without allocating executable memory at runtime. It does not intrinsically require a JIT. Its snapshot system has shared read-only heap regions and deserialized mutable startup/context state. A stripped embedder can omit Node, ICU and unnecessary facilities; the prior “42 MiB Node cannot fit, therefore V8 cannot fit” conclusion is unsupported. However, jitless does not automatically make V8 tiny, as the historical 1.7% heap reduction illustrates. [Jitless](https://v8.dev/blog/jitless), [snapshot internals](https://github.com/v8/v8/blob/main/docs/snapshot/architecture.md), [embedding/build knobs](https://v8.dev/docs/cross-compile-ios).

**JSC deserves a throughput comparison, not a promise of an easy port.** `useJIT=false` leaves LLInt; it is not equivalent to disabling only its optimizing tiers. Current source exposes heap/stack and concurrent-GC settings, which signal integration work for our threadless, restricted syscall profile. Existing local JSON performance is attractive, but native system-framework RSS does not predict a static musl guest. [JSC tiers](https://docs.webkit.org/Deep%20Dive/JSC/JavaScriptCore.html), [options/source](https://github.com/WebKit/WebKit/blob/main/Source/JavaScriptCore/runtime/OptionsList.h).

**Porffor changes the deployment model.** It compiles JS/TS through C to native code, with a Wasm target too. It is alpha; its page reports **238/394 npm packages** compiling with matching output. Compile latency and semantic coverage must be included for unique snippets. Shipping a compiler inside the snapshot would undermine the footprint argument; compile offline and cache by program/runtime hash. Its density claim is promising but cannot establish a jitk advantage before measuring the same compiled program under our ABI. [Project](https://porffor.dev/), [source](https://github.com/CanadaHonk/porffor).

## 3. Snapshotting changes the QuickJS verdict

Model the invocation as:

`T = admission + restore + first-touch/COW + parse(fresh code) + execute + host calls + cleanup`.

A runtime-ready snapshot removes initialization and trusted-library/prelude loading. It does **not** remove parsing fresh code, JSON allocation, interpretation, per-invocation binding setup, page faults, or host executor work. `qjsc` packages bytecode plus an interpreter; it is not native AOT. [QuickJS compiler/runtime documentation](https://bellard.org/quickjs/quickjs.html).

V8 published context construction falling from **40 ms to <2 ms** on an unspecified desktop and **270→10 ms** on a mobile device; custom snapshots eliminated **100 ms** of TypeScript-compiler loading. Historical numbers, not current arm64 projections. Whole-VM restoration can skip even that deserialization, provided the runtime's complete state remains valid. [V8 snapshot experiment](https://v8.dev/blog/custom-startup-snapshots).

SEUSS is direct systems precedent: pre-initialized Node/Rumprun snapshot stacks, **270 ms** initialization moved off-path, **7.67 ms** uncached NOP invocation and **>52,000** blocked runtime instances through CoW. Microbenchmarks used an **88 GB, 16-vCPU** VM; physical hosts had dual eight-core **Xeon E5-2660 2.2 GHz**, 132 GB. This shows that large runtimes can become dense after snapshotting, not that V8 costs two MiB here. [Cadden et al., SEUSS, EuroSys 2020; preprint §§7–8](https://arxiv.org/html/1910.01558).

**Revised verdict:** retain QuickJS on evidence of low active working memory, portability and adequate glue throughput; retire process-startup comparisons as the deciding criterion. Bellard's **47 µs** context creation alone cannot explain or recover the **4.8 CPU-ms** VM budget. Compare snapshot-restored engines using marginal private pages and end-to-end CPU. QuickJS reference counting writes metadata even when application code mostly reads objects; that can dirty shared snapshot pages. This is an **I** to measure, not an established regression. [Refcount/GC design](https://bellard.org/quickjs/quickjs.html), [local baseline](../quickjs-verdict.md).

The current [bootstrap](../../jitk/protocol/bootstrap.js) already parks after trusted initialization and sends `ready`; this is a plausible template cut point. Its `AsyncFunction` parses submitted code after `run`. The [executor wrapper](../../jitk/executor/code.ts) still injects codecs/preludes per request, so only fixed, authority-free work can move into a common snapshot. Parameterize capabilities after restore. Capture a quiescent kernel/transport boundary, including vCPU state, event-loop callbacks and buffers; a Linux process `fork` experiment is only a dirty-page proxy, not proof that the VM restore works.

**Restore uniqueness is runtime-specific.** Bellard HEAD seeds `JSContext.random_state` from `gettimeofday` during intrinsic initialization; `Math.random` then mutates that saved state. Updating the kernel's seed after restore does not reseed an existing context. Use a reviewed after-restore hook or trusted bootstrap replacement, plus fresh clock, getrandom state, IDs and cleared transport queues. Never snapshot credentials or pending external operations. [Inspected source, 7d1c13c](https://github.com/bellard/quickjs/blob/7d1c13c5d8f8c6b32893786ed35cdcebd88194d2/quickjs.c), [current boot-time injection](../../jitk/vmm/src/main.rs). The shipped June binary's exact source correspondence remains unverified in the earlier verdict.

### Wasm: runtime size is not language-runtime size

| Runtime / primary publication | Numbers and conditions | Consequence for jitk |
|---|---|---|
| WAMR current README | Cortex-M4F core text: fast interpreter **58.9K**, classic **56.3K**, AOT runtime **29.4K**, WASI libc **21.4K** | Code size, not host RSS. AOT compiler runs elsewhere. [P](https://github.com/wasm-micro-runtime/wasm-micro-runtime) |
| WAMR performance, 2020 | CoreMark Massif peaks: classic **365 KB**, fast **485 KB**, wasm3 **514 KB**; memory subsection does not independently specify target. On i7-7700/Ubuntu 18.04/GCC 7.5 -O3, AOT CoreMark **8.79×** wasm3, **0.79×** native GCC score | Allocator peaks are not RSS; old results and no modern cold-start distribution. | wasm3 historical benchmark | i5-8250U: CoreMark **1627.9**, Wasmtime 0.8 **6453.5**, native 64-bit GCC 7.4 **19144.9** | 2019–20 versions; proves interpreter tradeoff, not current ranking. [P](https://github.com/wasm3/wasm3/blob/main/docs/Performance.md) |
| Wasmtime minimal embedding | Documented Linux x64 size exercise: release C library **19 MB**, no defaults **2.1 MB**, further trimming **700 KB**; custom-platform example approximately **400 KB** | A minimal runtime without compiler/WASI differs radically from the CLI; sizes are not RSS. [P](https://docs.wasmtime.dev/examples-minimal.html) |
| Wizer original benchmarks | Regex instantiate+initialize **248.85→183.99 µs**; UAP **98.297→16.385 ms** | Hardware unspecified; benefit depends on initialization avoided. Development moved into Wasmtime. [P](https://github.com/bytecodealliance/wizer) |

Wasmtime explicitly combines **pooling**, **CoW heap images**, and **InstancePre** import resolution. These are the relevant comparison, not invoking the CLI/compiler for every request. Minimal no_std embedding can disable signal-based traps and compiler features, at a performance cost; default WASI is not turnkey on custom targets. WAMR offers an easier small-C port, configurable interpreter/AOT and AArch64. wasm3 advertises approximately **64 KB code/10 KB RAM** minimum useful requirements, excluding the application; its README retains a minimal-maintenance notice. [Wasmtime instantiation](https://docs.wasmtime.dev/examples-fast-instantiation.html), [minimal platform](https://docs.wasmtime.dev/examples-minimal.html), [wasm3](https://github.com/wasm3/wasm3).

Wizer records initialized globals/nonzero linear memory into a new module; it is not an arbitrary running-machine checkpoint. Its documented restrictions include imported state, host calls and reference types. Preinitializing QuickJS or Python in Wasm still carries that interpreter and its application heap. Avoid double interpretation for the default JS path: WAMR/wasm3 interpreting Wasm containing a JS interpreter cannot inherit native QuickJS throughput. Prefer AOT Wasm where performance matters. [Mechanism/caveats](https://github.com/bytecodealliance/wizer).

A useful modern throughput warning: DeCl's OSDI'25 evaluation on AWS **c7a.metal EPYC/c8g.metal Graviton4, 192 cores**, reports x64 Groth16 verification **0.313 s native**, **0.745 s Wasmtime with fuel**, **10.5 s wasm3**. Separate empty-program tests used **M2:15 µs**, **7950X:2 µs** for preallocated native SFI sandboxes. These are not VM results; they show why both startup and useful CPU must be measured. [Yedidia et al., §§7.2.1–7.2.3](https://www.usenix.org/system/files/osdi25-yedidia.pdf).

### CPython: snapshot-friendly startup, difficult small private footprint

Published native startup: PyOxidizer's macOS CPython 3.7 experiment measured **22.7±2.0 ms** normally versus **12.7±1.1 ms** with `-S`, 500 runs; CPU unspecified. Its indexed in-memory importer avoids repeated module discovery I/O. This is evidence for freezing/importing once, not a current Python 3.14 benchmark. [Author's measurements](https://gregoryszorc.com/docs/pyoxidizer/0.20.0/pyoxidizer_packaging_performance.html).

Published loaded memory: Benchmarks Game Python 3.13 n-body uses **12,198 KB peak memory**, **372.412 s** for 50 million steps, on **i5-3330 3 GHz/15.8 GiB/Ubuntu 24.04**. That is cgroup process-group memory, not idle RSS or incremental snapshot cost. No current like-for-like bare CPython/QuickJS snapshot-RSS benchmark was verified. [Results](https://benchmarksgame-team.pages.debian.net/benchmarksgame/measurements/python3.html), [measurement definition](https://benchmarksgame-team.pages.debian.net/benchmarksgame/how-programs-are-measured.html).

Lambda SnapStart supports **Python 3.12+**, snapshotting initialized Firecracker memory/disk and offering startup as low as subsecond; this does not establish a one-ms Python restore. Python has before-snapshot/after-restore hooks. Dependencies, runtime and application initialization can move off-path; connections, IDs and expired credentials must be repaired. [Current AWS documentation](https://docs.aws.amazon.com/lambda/latest/dg/snapstart.html), [Python hook announcement](https://aws.amazon.com/blogs/aws/aws-lambda-snapstart-for-python-and-net-functions-is-now-generally-available/).

Pyodide makes CPython available inside isolates, removing “Python” as an exclusive jitk advantage. Cloudflare's 2024 baseline was **6.4 MB** Pyodide download and approximately **2 s** browser initialization, half network/half CPU; deployed snapshots reduced a basic Worker below one second. Its 2025 implementation additionally restores function-pointer tables and JS references, not just linear memory. [2024 design](https://blog.cloudflare.com/python-workers/), [2025 design](https://blog.cloudflare.com/python-workers-advancements/).

The Python Language Summit 2026 reports Pyodide hello **1.406→0.353 s** with snapshots, hardware unspecified, and highlights duplicated hash randomization. Simply replacing Python's hash seed after restore invalidates the assumptions of existing dictionaries; this needs a runtime design, not just a new kernel RNG. Refcounts/GC can also erode CoW. For jitk, use a statically linked, restricted import set, read-only stdlib resources and a single initialized thread; expect syscall/extension work beyond today's qjs/Lua profile. A **32–64 MiB experimental provisioned class** is a starting experiment, not a measured requirement or two-MiB claim. [Summit report](https://blog.python.org/2026/09/language-summit-2026-memory-snapshots/), [current kernel contracts](../../jitk/docs/ARCHITECTURE.md).

### Lua / LuaJIT

PUC Lua is already demonstrated by jitk; preserve it as a separate small native template. Current upstream reports a **293K** full interpreter on 64-bit Linux, a binary-size number. LuaJIT 2.1 supports ARM64, but implements Lua 5.1 compatibility rather than being a drop-in Lua 5.4/5.5 replacement. Its JIT needs executable-memory/cache-maintenance support; compiling reusable traces before a generic snapshot cannot optimize unknown future scripts. [Lua](https://www.lua.org/about.html), [LuaJIT status](https://luajit.org/status.html), [compatibility](https://luajit.org/extensions.html).

Klehm et al., **IEEE ICCE 2024, DOI 10.1109/ICCE59016.2024.10444429**, tested Lua 5.4.4/LuaJIT 2.1, 500 executions/cell, **i7-7700 3.6 GHz/32 GB/Ubuntu 22.04**. Linux hello CPU time was **1.036/1.000 ms**, reported memory **13,712/13,935 kB**; n-body **1.153/0.08208 s**, memory **14,082/14,084 kB**. Their harness memory is not a portable idle-RSS floor, and CPU time is not API latency. Lua-in-Wasm n-body was **3.183 s/31,601 kB**, including V8. Native LuaJIT wins this CPU workload; nesting an interpreter in Wasm costs real resources. [Authors' paper, Tables I/III](https://www.researchgate.net/publication/378568763_A_comparative_analysis_between_Lua_interpreter_variants_compiled_to_WASM_JavaScript_and_native).

## 7. Honest positioning and the image portfolio

The following is **I**, derived from the cited capabilities and limits in §§2–6, compared with [current jitk contracts](../../jitk/docs/ARCHITECTURE.md) and [planned VMM](../third-option.md). “Target advantage” means conditional on meeting ≤2 MiB and ≤1 ms restore; it is not a shipping benchmark win.

| Against | jitk's credible target advantage | Where jitk loses / unsuitable workload |
|---|---|---|
| Workers isolates | Hardware boundary; locally owned static ELF/runtime profile | V8 CPU throughput, existing shared runtime, global placement and managed operations; no established memory win |
| Dynamic Workers | Same boundary plus no per-unique-program hosted creation tariff when self-hosted | Same-thread host RPC, web APIs, managed scale; Python/Wasm already supported; reusable JS is exceptionally cheap |
| Cloudflare Code Mode | Can supply a hardware-isolated alternative executor and non-JS static tools | Code Mode is a pattern we implement, not a runtime to out-benchmark; discovery/types/durability remain product gaps |
| Anthropic code execution/PTC | Local embedding, fresh state per run, lower intended memory/startup for tiny glue | Python packages/files/REPL and model integration; free execution bundles; no cold-start distribution to claim beating |
| OpenAI containers | Fresh minimal machine for short tool glue, avoiding large provisioned sessions | Data-science libraries, files, persistent workspaces and built-in model workflow |
| OpenAI V8 PTC | Hardware protection and restricted non-JS ELF, deployment/provider independence | Already offers the same stateless tool-composition pattern; startup/memory advantage unproven |
| E2B | Potentially much lower overhead for single small programs | Full Linux, toolchains, desktops, snapshots/forks, SDK/operations maturity; cannot run its general workloads |
| Daytona | Target hardware-VM latency below its published container-start class | Broad Linux and separate VM/GPU environments; do not compare container security to a VM without specifying deployment |
| Modal | Small per-call machine and local host calls | Huge fleet scale, GPUs, packages and memory snapshots; no evidence we match creation throughput/reliability |
| Vercel Sandbox | Low private memory, runtime-ready snapshots and no default 4 GB/minute minimum when self-hosted | Full root Linux, dev servers, drives/SDKs/deployment ecosystem; memory minimum is a tariff, not their physical footprint |
| Deno Sandbox | Restricted native ELF at much smaller intended footprint | Full Linux, secret substitution, storage and Deploy integration; Deno Sandbox already has hardware isolation |
| Fly Machines | Single-use pristine runtime with tiny hostcall ABI, aimed below its Linux footprint | Long-running apps, regional networking, volumes and low shared-CPU prices; no new-instance versus suspend apples-to-apples test |
| Rivet agentOS | Hardware boundary and existing stock static qjs/Lua binaries | Durable virtual filesystem, process/network abstractions and integrated agents; existing 22 MB is broader functionality |
| Hyperlight-JS | Restricted Linux ABI and demonstrated async tool fan-out | Closest direct rival; already beats current jitk cold CPU/memory. Must match reset/isolation contracts and engine versions |
| hyperlight-wasm | Stock static ELF avoids Wasm rebuilds and component plumbing | Standard Wasm components/host interfaces and reusable no_std runtime; polyglot alone is not differentiation |

**Where isolates retain a structural advantage.** They share a host runtime, avoid per-VM vCPU/stage-2 state, and can call colocated native host capabilities without VM exits or our ASCII JSON channel. V8 can JIT hot code while our default interpreter cannot. Cloudflare already reports millisecond creation with a few MB; its 128 MB cap is not its cost. Hardware isolation is a different failure boundary, not a guarantee that jitk is safer in practice than a hardened managed fleet. Browser-engine bugs, VMM bugs, reset defects and operational maturity all matter. [Cloudflare mechanism](https://blog.cloudflare.com/dynamic-workers/), [our transport/source](../../jitk/protocol/bootstrap.js), [our exposure criteria](../../jitk/docs/KILL-CRITERIA.md).

**Recommended artifact set:** `qjs-min` with initialized intrinsic objects, fixed codec/bootstrap and empty capability map; `lua-min` with its equivalent tool bridge; `python-core` later with frozen selected imports and its own larger quota. Keep ng as a switchable qjs build. Add `wasm-aot` only for an actual workload: WAMR for a tiny core-Wasm runner, Wasmtime when components justify the extra integration. Cache templates by kernel/runtime/library/resource hashes. Loading unused runtimes would add pages and reset obligations without helping a JS request. These are proposed designs; current jitk does not have this snapshot portfolio.

AOT should be opt-in for repeated code. Break-even invocation count is approximately `compile CPU / (interpreter CPU − native CPU)`, plus storage/validation costs. For a fresh one-off script, compilation often consumes the latency it saves; none of the checked Porffor/Static-Hermes execution-only tables establishes a sub-ms compile-and-run path. Do not put a C compiler/LLVM into the default image.

The memory target must be a **slope**, not one process's RSS: `M(N)=shared template+shared supervisor+N×(private guest pages+vCPU/stage-2+queues+host request state)`. At 2 MiB, the memory-only ceiling is **512 instances/GiB**, before shared overhead/reserve. At 1 CPU-ms, CPU-only capacity is **1000 runs/core-second**, before scheduling/replenishment. Neither ceiling is a benchmark. A 1 MiB structured JSON run already requiring 8 MiB heap cannot belong to the same two-MiB loaded class. Define the target against named tiny-code fixtures and publish larger-data classes separately. [Observed heap expansion](../quickjs-verdict.md).

## Top 5 gaps/blockers

1. **No all-in marginal memory attribution.** Today's 10.7 MiB excludes HVF costs; R5 loader changes and multi-VM sharing are not a measured replacement baseline. Without guest-private, hypervisor, host queues and supervisor attribution, ≤2 MiB is undecided. [Local evidence](../quickjs-verdict.md), [R5](../../PLAN-R5.md).
2. **Post-restore dirty working set may defeat density.** QuickJS/Python refcounts, allocator metadata, GC and realistic JSON mutate pages after a pristine snapshot. Sharing image bytes cannot bound active heaps. No engine's published idle size decides this. [QuickJS internals](https://bellard.org/quickjs/quickjs.html), [local JSON results](../quickjs-verdict.md).
3. **Snapshot correctness crosses runtime and kernel state.** Cloned RNGs/hash secrets, clocks, event-loop buffers and resource handles need explicit repair. Fresh boot seed injection is insufficient for a saved QuickJS context; Python hash tables make arbitrary reseeding harder. [QuickJS source](https://github.com/bellard/quickjs/blob/7d1c13c5d8f8c6b32893786ed35cdcebd88194d2/quickjs.c), [Python summit](https://blog.python.org/2026/09/language-summit-2026-memory-snapshots/).
4. **One-ms restore does not establish one-ms useful CPU.** Current raw 4.8 CPU-ms includes more than 47 µs engine creation; executor wrappers still add work, and 21 ms structured JSON alone exceeds the target. Linux metal, concurrency and replenish-inclusive CPU remain unverified. [Final](../../FINAL.md), [wrapper](../../jitk/executor/code.ts).
5. **Compatibility and competition narrow the niche.** Larger engines/CPython need a syscall/platform census; hardware VM per call is not full Linux. Cloudflare Python, OpenAI V8 PTC and Hyperlight/Wasm already cover much of “polyglot code mode.” Their latency/density gaps cannot be assumed from older landscape notes. [Loader](https://developers.cloudflare.com/dynamic-workers/getting-started/), [OpenAI](https://developers.openai.com/api/docs/guides/tools-programmatic-tool-calling), [Hyperlight Wasm](https://github.com/hyperlight-dev/hyperlight-wasm).

## Top 5 recommendations

All impacts below are **I / experiment budgets**, not promised performance. Each experiment is bounded to less than one engineer-day and needs no cloud provisioning; Linux/KVM experiments require an already-available host, otherwise remain unmeasured.

1. **Measure and prototype runtime-ready Bellard/Lua snapshots before changing engines.** Expected potential: current 5.9 ms raw cold toward **≤1 ms restore**,4.8 CPU-ms toward **1–2 CPU-ms** for tiny fixtures; memory toward **1–2 MiB marginal** only if the VMM/process/image costs amortize. In one day, instrument checkpoints before/after runtime/bootstrap initialization and restore 1000 times; staircase N=1/16/64/256 with empty, one-tool and held-tool cases. Count total process-tree PSS/private dirty plus KVM allocations where available, page faults and replenish CPU. **Kill the assumption** if total marginal memory exceeds2 MiB or p99 restore exceeds1 ms; identify which component consumes the budget before expanding scope.
2. **Make restore repair a prerequisite to sharing initialized heaps.** Expected benefit: correctness; expected latency/dirty-page cost small but **unmeasured**, budget **<0.1 ms** and record it. In one day, restore cloned templates with distinct seeds/times; compare first 100 random values, time, IDs, request counters, error paths, pending promises and canary buffers. Verify deterministic replay mode separately. **Fail closed** on duplicated supposedly unique state or post-failure leakage; do not “fix” Python by changing hash secrets under existing dictionaries.
3. **Run a snapshot-aware engine shootout with a stop rule.** Bellard versus ng using identical static build flags first; add embedded V8 jitless, Hermes and JSC only where a working build exists. A native fork/CoW harness can rank private-page growth cheaply, but label it a proxy. In one day, measure empty restore, representative 1–8 KiB snippets, promises, strings and structured 64 KiB / 1 MiB JSON; include parse time and peak/private memory. Expected upside from the existing local table: **approximately2.5–5× JSON CPU reduction** with Hermes/JSC/V8-class builtins; possible memory regression. **Promote only** an engine that fits the measured per-run memory budget and improves end-to-end CPU by≥20%; otherwise retain Bellard.
4. **Reduce materialized JSON and move fixed wrapper work off-path.** Expected impact: avoiding one 1 MiB structured parse can avoid roughly **8 MiB required heap capacity** and **~21 ms native Bellard parse/stringify work** for that fixture; not every call realizes that saving. In one day, compare 64 KiB versus 1 MiB structured results, host-side projection/limits and read-only resource/blob handles; separately measure fixed codec/prelude initialization before versus after the snapshot. **Reject** any optimization that moves authority or unbounded allocation into the common image; require byte-identical bounded outputs and explicit large-result handling.
5. **Validate the second image and the market claim with bounded prototypes.** Spend half a day on a static minimal CPython syscall census and dirty-page measurement after `json`/selected imports; reject the 2 MiB Python claim unless measured. Spend the other half on one WAMR AOT or Static-Hermes/Porffor reusable transform, including compilation/porting costs and semantic checks. Expected outcome: quantified separate resource classes, possibly much lower CPU for repeated transforms; **no assumed universal memory win**. Position only against matched contracts, include Cloudflare's unique-code fee versus cached-code case, and retain the existing Hyperlight baseline as the immediate competitive gate. [Investment criterion](../../jitk/docs/KILL-CRITERIA.md).
