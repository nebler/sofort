# Host–guest data, capabilities, and image caches

Research date: 2026-10-25. Scope: jitk's data path and the memory/CPU cost of making tools, files, and capability objects available inside single-use VMs. **[L]** denotes existing local evidence, **[P]** published/source evidence, and **[D]** a proposed design, estimate, or experiment; estimates are not measurements. No runtime changes or new performance measurements were made.

**Recommendation:** retain the packed filesystem for immutable bytes; introduce tool-backed files as a bounded RPC view; use one shared-memory transport with batched notifications; cache prepared execution state independently of live grants. Cap'n Web is valuable for dependency graphs and object capabilities, but its default awaited call sends more messages than jitk v1. Installing it alone does not make individual calls cheaper.

## 2. File-shaped interfaces: borrow Plan 9's namespace, count the RPCs

Plan 9's three ideas are hierarchical resource names, a common access protocol, and private composed namespaces. The useful precedent is a **per-run view of granted resources**, not a universal host filesystem. Its local kernel devices implement file operations as procedure calls; making something a file does not intrinsically require a wire protocol. [P: Pike et al., *Plan 9 from Bell Labs*](https://9p.io/sys/doc/9.html), [device manual](https://9p.io/magic/man2html/3/intro).

9P supplies request tags and fids, offset-based I/O, and resource teardown with `clunk`. It can multiplex outstanding requests. Modern `Twalk` carries **up to 16 path components**; claiming an unavoidable RTT for every component would be wrong. But uncached walk/open/read/clunk remain separate operations, and Linux POSIX emulation adds attributes, permissions, coherence and fd state. [P: 9P introduction](https://9p.io/magic/man2html/5/0intro), [walk specification](https://9p.io/magic/man2html/5/walk), [Linux v9fs](https://docs.kernel.org/filesystems/9p.html).

[Paper](https://www.usenix.org/system/files/conference/fast17/fast17-vangoor.pdf), Table 4 and §5. |

[Paper](https://www.usenix.org/system/files/atc21-huai.pdf), §§3.1, 4.1. |
| **virtio-9p versus early virtio-fs**, Goyal's 2018 RFC | Fedora 28, 32 GB, dual sockets/6 cores each/SMT, PCIe SSD; guest 16 vCPUs/6 GB, DAX window 2 GB. Host cache warm, guest cache dropped, three runs, 4 GB files: one-thread mmap read **28 MB/s 9p**, **126 MB/s virtio-fs cache-none+DAX**, **235 MB/s virtio-fs cache-always**; four-thread figures 140/501/858 MB/s. Historical prototype throughput, **not operation latency**; CPU model unspecified. [Original RFC](https://lkml.iu.edu/hypermail/linux/kernel/1812.1/01577.html). |

FUSE's expensive path is request construction, user/kernel scheduling, data movement, and another filesystem operation in a passthrough daemon. Metadata-heavy workloads multiply those exchanges. The FAST'17 study shows this amplification directly; read-ahead and write batching can hide it. Conversely, XFUSE demonstrates that “userspace filesystem” does not imply hundreds of microseconds. [P: papers above; interpretation D]

virtio-fs transports FUSE requests over virtqueues, avoiding a network stack. With DAX, file data can map the host page cache directly; warm data accesses avoid a daemon round trip and duplicate guest data cache. Metadata, first mappings, window eviction and coherence still cost work. Without DAX, data access again needs communication. A small DAX window trades reserved address space for mapping churn. **Do not group all virtio-fs reads with uncached 9P/FUSE RPCs.** [P: virtio-fs design](https://virtio-fs.gitlab.io/design.html), [kernel documentation](https://kernel.org/doc/html/v6.10/filesystems/virtiofs.html).

**jitk implication [D]:** retain file *names* and fd semantics where they aid unmodified binaries. Avoid porting a general 9P/FUSE client, POSIX coherence engine, or per-VM daemon merely to connect tools. Immutable per-run metadata eliminates most invalidation work. A tool-backed `stat` should inspect a local descriptor, not call a remote tool to discover its length.

## 3. Transport: vsock is convenient; shared memory must also remove wake-ups

virtio-vsock is already a shared-memory virtqueue transport underneath a socket API. Comparing it with “shared memory” really compares socket/credit/workqueue machinery with a specialized ring and scheduler. A custom ring that still sends every message through separate VMM and Node pipes retains those host wake-ups. [P: [vsock driver optimization](https://lkml.iu.edu/hypermail/linux/kernel/2407.3/07547.html); L: current VMM/backend]

| Published transport result | What it establishes |
|---|---|
| Leonardi/Pinna 2024 vsock patch | i7-10700KF 3.8 GHz, QEMU/KVM/vhost, host/guest processes and vCPUs pinned; fio SOCK_STREAM host→guest→host pingpong, 50×50 s. **64 B: 16.78→13.57 µs overall**, p99 42.24→39.17 µs; **4 KiB: 19.87→14.96 µs**. Fast path bypasses the intermediate queue/work item. [Primary patch and method](https://lkml.iu.edu/hypermail/linux/kernel/2407.3/07547.html). |
| 2022 inter-VM SMC/ivshmem RFC | Xeon Platinum, 8 cores/32 GiB, Mellanox CX4 VFs, sockperf single connection. Pingpong: **6.3 µs ivshmem**, **19.3 µs virtio TCP**, **13.2 µs SR-IOV**. Prototype explicitly unstable; exact CPU model omitted; latency used two copies. This is not a head-to-head vsock comparison. [Primary RFC discussion](https://lists.openwall.net/netdev/2022/08/03/186). |
| Hyperlight's current transport | Two non-discoverable packed virtqueues, defaults 64/32 descriptors, 12/8 pool pages, **21×4 KiB = 84 KiB** arena. Requests may reserve response buffers in the same chain. Host copies control and external bytes before invoking callbacks. Useful implementation precedent, not a portable latency result. [Transport design/source](https://raw.githubusercontent.com/hyperlight-dev/hyperlight/main/docs/virtio-host-guest-communication.md). |

These measurements make a **10–30 µs small-call transport goal plausible on tuned systems**, but do not establish it on HVF/M-series, with Node or under fleet contention. A dedicated polling thread per VM would defeat scale. [D]

### Current jitk's frames, copies, exits

`console.rs` has **1,024-byte payload buffers**, copying each outgoing chunk and notifying MMIO offset `0x50`; TX waits for its used descriptor. RX copies from its queue to the caller and reposts. `service()` also reads interrupt status through MMIO and may acknowledge it. Therefore notification count alone undercounts exits. `SVC` from EL0 to EL1 is a guest exception, **not** a host VM exit. [L: [console](../../jitk/kernel/src/console.rs), [user write](../../jitk/kernel/src/user.rs), [read](../../jitk/kernel/src/syscalls/read.rs)]

For a small v1 call/response there are two logical frames, at least **two queue-notification MMIO writes**—TX and RX repost—plus status accesses, wait/wake, interrupts and any library fragmentation. For request/reply wire lengths A/R, ideal notification lower bound is `ceil(A/1024)+ceil(R/1024)`, excluding run/done/control traffic. No total exit count was instrumented. A 64 KiB payload already needs approximately 64 notifications in its direction. [L/D: source-derived counts]

The minimum visible byte-copy path is roughly **three per direction**: guest user buffer→console queue→host pipe→Node buffer, and the reverse. libkrun's `write_volatile`/`read_volatile` operate on guest slices, so a mandatory extra VMM heap copy must not be invented. JSON strings, stdio buffering, dispatcher accumulation and parsing add allocations/copies beyond these six transport copies. [P: pinned libkrun [TX](https://github.com/containers/libkrun/blob/a1d8616/src/devices/src/virtio/console/process_tx.rs), [RX](https://github.com/containers/libkrun/blob/a1d8616/src/devices/src/virtio/console/process_rx.rs); L: [backend](../../jitk/executor/backend.ts), [dispatcher](../../jitk/protocol/dispatcher.ts)]

**Third-option proposal [D]:** two 32 KiB directional byte rings plus one 16 KiB control region: **80 KiB/VM**, 3.9% of a 2 MiB budget, compatible with the observed host's 16 KiB pages. Length-prefixed records carry kind, correlation ID, generation, capability slot, method and payload length. Use release/acquire publication, bounded offsets and credits; reset all cursors/generations on restore. Share the lane among JS calls, FS calls, responses and logs, with independent admission counters. This is a proposed ABI change, not v1-compatible framing.

Publish multiple requests before one `submit-and-wait` trap. For an immediate synchronous callback, host services the request while handling that exit and re-enters with the response: **one exit/resume pair per batch**. If the guest continues after notification and later blocks, expect a notification exit **plus a wait exit**. Async tools should release the worker to other VMs while waiting. Race-free wait must check the producer generation under the host's wait registration; a naked WFI with no interrupt source is insufficient. [D; relevant platform caveats: [third-option research](../third-option.md)]

Baseline copy target is **two per direction**: guest buffer→ring, ring→trusted host-owned request; encoded host response→ring, ring→guest buffer. The host copy prevents mutable guest memory changing between validation and use. Parsing directly from guest-writable Cap'n Proto memory is not safe merely because the format permits zero-copy access. Single-vCPU pause may support narrower borrowing optimizations, but any callback retained across await must own its data. [D; P: Hyperlight copying contract above, [Cap'n Proto pointer/traversal validation](https://capnproto.org/encoding.html)]

## 4. Capabilities and pipelining: separate authority from serialization

**E / ocaps.** E's vats isolate event-loop turns; eventual sends return promises that can themselves receive messages. Promise pipelining forwards those messages when the result resolves. Passing an object reference conveys the ability to invoke it; this supports resource-specific interfaces instead of repeatedly consulting global path/name authority. Failures still leave ambiguity between “not delivered” and “delivered, reply lost.” [P: Miller, *Robust Composition*, chapters 15–16](https://erights.org/talks/thesis/markm-thesis.pdf), [E introduction](https://www.erights.org/elang/intro/quickE.html).

**Fuchsia handles.** A handle is a process-local 32-bit table entry carrying object reference, rights and owner. Duplication/replacement can reduce rights; channel messages transfer handles into the receiver's table. Copying an integer to another process does not grant authority. For jitk, the analogous number is only an index into a **host-owned per-run binding table**, scoped by run generation—not a guest-selected global object ID. [P: [handles](https://fuchsia.dev/fuchsia-src/concepts/kernel/handles), [rights](https://fuchsia.dev/fuchsia-src/concepts/kernel/rights); mapping D]

**Capsicum as API design.** Reuse descriptors and familiar `openat`/read/write APIs, attenuate allowed operations, and remove dependence on the global namespace. The original paper's capabilities wrap existing descriptors with rights masks; relative traversal needs confinement against `..`/absolute escape. This is an argument for preopened grant roots and narrow operations, not for a second security-policy language or reproducing Capsicum's hardening results. [P: Watson et al., USENIX Security'10, §§3.1–3.2](https://www.cl.cam.ac.uk/research/security/capsicum/papers/2010usenix-security-capsicum-website.pdf).

**Cap'n Proto RPC** combines object references with promised-answer targets: the client sends dependent calls before results return. An N-call dependency chain at the same endpoint can pay one network waiting round instead of N, while the server still executes all N operations/dependencies. It does not parallelize inherently dependent work or make client-side branching on unseen data possible. Its binary format supports direct field access, but does not automatically remove transport copies or JS object construction. [P: [RPC design](https://capnproto.org/rpc.html), [encoding](https://capnproto.org/encoding.html)].

### Cap'n Web source audit

The pinned implementation uses JSON expressions, session-local import/export tables and implicit positive IDs for pushed results; ID zero denotes the main interface. A custom transport needs `send`/`receive`; it need not use HTTP or WebSocket inside a VM. `encodingLevel` can omit final JSON stringify or preserve byte arrays, but an actual VM still requires serialized bytes or a defined shared-memory ABI. It cannot transfer a JS object graph as MessagePort does. [P: pinned [rpc.ts](https://github.com/cloudflare/capnweb/blob/766655329fe4fe2dada67c8b4e82e3a81e38b194/src/rpc.ts), local [custom transport docs](../repos/capnweb/packages/docs/src/content/docs/transports/custom.mdx)]

| Operation | Cap'n Web protocol messages | VM-boundary consequence [D] |
|---|---|---|
| Ordinary awaited call, scalar result | `push`, `pull`, `resolve`/`reject`, `release`: **4** | Sending each through today's flushing stdio path adds notifications versus v1's 2 frames. Coalesce push+pull, defer/piggyback releases; one waiting RTT remains possible. |
| N-call pipeline, only final result pulled | N pushes + pull + final resolve, plus reference releases | One waiting RTT, **not one frame**. Exact releases depend on ownership/disposal. Batch publication can make notification cost largely independent of N. |
| `list().map(x => api.get(x.id))` | Push/remap instructions represent remote fan-out | Avoid returning the list to the guest merely to send its IDs back. Count each expanded host invocation against quotas. |
| `stream` message | Implicit pull and release, then response: **2** | Current `sendStream()` exposes `Promise<void>` and disposes result payload. This is designed for streaming writes; it is not a drop-in two-frame arbitrary-result RPC API. |

Protocol counts come from [wire documentation](../repos/capnweb/packages/docs/src/content/docs/reference/protocol.mdx) and `sendCall`/`sendStream`/`sendPull`/`sendRelease` in the pinned source. A ring record may contain several logical messages; distinguish message count, descriptors, doorbells, VM exits and waiting RTTs.

`.map()` records a restricted synchronous callback as instructions/captured references; it does not ship arbitrary JS source for host execution. Its input is an opaque promise: arithmetic/branching on it does not work. Passing stubs as captures conveys their authority to the peer. Thus the executor must wrap all exported capabilities and validate each eventual resolved invocation. Nested maps multiply work, and the library has no global outstanding-call/export-table bound. Keep jitk's 64 outstanding/4096 total and byte limits at **invocation**, not frame, level. [P: [map docs](../repos/capnweb/packages/docs/src/content/docs/concepts/map.mdx), [security docs](../repos/capnweb/packages/docs/src/content/docs/guides/security.mdx)]

Explicit disposal matters: remote objects can hold resources invisible to local GC; connection teardown releases a session but does not undo side effects. A single-use VM can bulk-close its run bindings, with idempotent host cleanup. [P: [disposal](../repos/capnweb/packages/docs/src/content/docs/concepts/disposal.mdx); design D]

The prior local study measured 46,404 B minified core+RPC and 59,613 B full bundle, and needed Web-platform globals/polyfills for QuickJS. Its test connected **two in-memory sessions inside one guest**: compatibility evidence, not a measured VM-crossing Cap'n Web implementation. Parsing/evaluating this per run would undermine the latency budget; preinitialize it in a shared snapshot and measure private dirty heap. Bundle bytes are not resident heap bytes. [L: [cloudflare-deep](../cloudflare-deep.md), §1.3]

Pipelining remains useful even when the executor's upstream is plain MCP: it saves guest↔host waits by resolving dependencies at the executor. It **does not collapse upstream MCP dependencies** into one network round trip unless the remote understands a batch/dependency graph or offers a composite tool. This corrects the tendency to equate guest pipelining with remote service batching. [D from the protocols]

For `list(); Promise.all(items.map(get))`, v1 already needs **two waiting rounds**, not 1+N: one for the list and one for parallel gets. Remote `.map()` saves one local round plus intermediate bytes; a genuinely sequential N-call chain can save N−1. The older Cloudflare report's 1+N-round-trip phrasing should not be carried into the merged recommendations. [L: async dispatch/bootstrap; D: dependency accounting]

## 5. MCP and `/mcp/` / `/cap/` files

MCP tools are named operations with JSON Schemas, invoked through `tools/call`. Results can contain text/media/resource links and optional `structuredContent`; schemas/annotations are not grants, and tool annotations are untrusted unless their source is trusted. Retain host policy around every adapter. [P: [2025-11-25 tools specification](https://modelcontextprotocol.io/specification/2025-11-25/server/tools)]

Resources have URI identities, `resources/list`/`resources/read`, text or base64 contents, templates and optional update subscriptions. The protocol does not specify POSIX offset reads, inode coherence, fd lifetime, or file writes. A mounted resource is therefore an adapter with explicit freshness and error semantics. `lastModified` is metadata, not a cryptographic version. [P: [resources specification](https://modelcontextprotocol.io/specification/2025-11-25/server/resources)]

Streamable HTTP uses a POST for each client JSON-RPC message, with JSON or SSE responses and optional GET SSE streams. Stream resumption is transport delivery recovery, not exactly-once execution. Neither SSE nor multiplexed outstanding requests supplies promised-result arguments. Keep MCP at the external boundary; reuse initialized connections and HTTP connections rather than negotiating MCP for each inner tool call. [P: [transport specification](https://modelcontextprotocol.io/specification/2025-11-25/basic/transports); recommendation D]

Code mode moves loops, filtering and intermediate data out of model turns into execution. Anthropic's worked example reduces **150,000 to 2,000 tokens (98.7%)**; it is not a latency, density, or general workload guarantee. jitk already provides the one-execute/many-inner-calls shape. [P: [Anthropic engineering example](https://www.anthropic.com/research/code-execution-with-mcp), [Cloudflare pattern](https://developers.cloudflare.com/agents/tools/codemode/); L: MCP server]

**Proposed filesystem contract [D]:**

| Namespace | Behavior and crossing cost |
|---|---|
| `/skills/...`, `/images/<hash>/...` | Existing immutable archive/read-only extent. Local metadata, zero host calls. |
| `/mcp/<binding>/resources/<encoded-uri>` | Local manifest of granted URIs. First open/materialization performs one `resources/read`; later reads/seek use that per-run immutable result. URI encoding must be injective; paths are aliases, never authority. |
| `/mcp/<binding>/tools/<method>.json`, `.d.ts` | Locally cached schemas/docs. Reading docs never invokes the tool. |
| `/cap/<slot>/...` | Locally resolves a prebound capability descriptor. A duplex call fd accepts exactly one bounded, complete request record and returns its response; a native generated JS stub addresses the same binding directly. |

For call fds, open/stat/readdir/close are local. Writes accumulate a request until its complete delimiter/length validates; **that explicit submission commits the call**, rather than `stat`, `open`, or reading documentation causing effects. Partial writes must not invoke; duplicate submission fails; response reads/EOF do not re-invoke. Errors map to a structured response or a documented errno. Once submitted, close/cancel does not promise rollback. Use correlation IDs and host per-run state to prevent resubmission. A seekable regular-file fiction is inappropriate for an invocation endpoint.

For resources, choose stable bytes **per open/run**; refresh is explicit. Cache authorization by binding/principal/version, not URI alone. Host CAS can deduplicate equal bytes across principals, but cache lookup must first establish current access. Large results should remain host blobs addressed by hash with bounded chunk reads; default `resources/read` may still require fetching the whole upstream object once. Chunking is a local adapter optimization, not an MCP range-read feature.

**Implementation blocker:** QuickJS bootstrap currently owns stdin and processes replies from its event loop. A synchronous `read()` on a tool fd traps into the kernel and prevents that JS loop from running. Adding a kernel call that waits for the JS bootstrap to dispatch its reply deadlocks. Implement kernel-side tagged reply demultiplexing in the common transport, or an explicitly separate endpoint. This requires a protocol/ABI revision and adapted differential tests; Linux's ordinary ext4 oracle alone cannot define synthetic RPC side effects. [L: [bootstrap](../../jitk/protocol/bootstrap.js), [read handler](../../jitk/kernel/src/syscalls/read.rs); consequence D]

## 6. Record/replay: log external decisions, not just call arguments

Cloudflare codemode's durable runtime records calls, aborts at an approval, then reruns code while supplying already recorded results. Its documented constraint is deterministic call order/arguments; nondeterministic work belongs in `codemode.step()`, and approval paths should issue connector calls sequentially. This is a useful design precedent, but jitk v1 explicitly specifies **no execution replay**, and successful completion requires no outstanding calls. Any replay facility must be a new host contract operating a fresh single-use VM. [P: [runtime documentation](https://developers.cloudflare.com/agents/tools/codemode/how-it-works/); L: [local source docs](../repos/agents/docs/codemode/runtime.md), [v1](../../jitk/protocol/PROTOCOL-v1.md)]

Temporal likewise replays workflow decisions from history and separates external Activities; Activities may retry and should be idempotent. rr demonstrates a different scope: exact process replay includes register state, syscall data and scheduling, not merely application RPC results. Neither system's guarantees can be obtained by saving only tool return JSON. [P: [Temporal determinism](https://docs.temporal.io/workflow-definition), [Activity retry/idempotency lesson](https://learn.temporal.io/assets/files/temporal-102-with-java-replay2025-468b8109d5a9ce33b36c2910c48433d9.pdf), [rr](https://rr-project.org/)]

**Minimum jitk journal [D]:** run code/recipe/ABI digests; ordered call issuance and completion delivery; capability provenance; method/argument hash; exact normalized result/error bytes or immutable result-blob hash; virtual clock/random/timer events; approval/commit decisions; external operation ID. Keep logging in host memory/append buffers for diagnostic replay, with explicit durability policy for resumable approvals.

Replay must preserve completion order for `Promise.race` and timer interactions. Same initial seed/epoch is insufficient: current `clock_gettime` reads an advancing counter, and async host tools can complete differently. Either implement logical time and controlled delivery, or restrict replay to a deterministic subset and fail on divergence. Assign IDs at guest issuance, rather than nondeterministic server arrival; parallel fan-out can then be replayable if completion delivery is also recorded. [L: [clock](../../jitk/kernel/src/syscalls/clock_gettime.rs), [wait](../../jitk/kernel/src/wait.rs); proposal D]

A crash between remote side effect and durable completion record creates an **unknown outcome**. Local logging cannot prove exactly-once execution at an arbitrary MCP server. Require remote idempotency keys/status lookup, an effect-specific transaction, or stop for reconciliation. Never blindly retry a mutating tool because its reply was lost. Content hashes deduplicate records, not business effects. E's partition ambiguity is directly relevant here. [D; P: E reference above]

## 7. Images: distinguish recipe identity, bytes, and prepared state

Nix's useful model is immutable closures with all build inputs declared. Classic input-addressed derivations hash the recipe/inputs; this is **not** the same as hashing produced bytes. Fixed-output content addressing is established; floating content-addressed derivations remain marked experimental in the inspected manual. jitk should preserve both keys instead of using “content hash” for everything. [P: [Dolstra thesis/research](https://nixos.org/research/), [Nix output-addressing specification](https://github.com/NixOS/nix/blob/master/doc/manual/source/store/derivation/outputs/content-address.md)]

Bazel separates **ActionCache: action digest→result metadata** from **CAS: content digest→bytes**. Remote Execution explicitly models command, input directory digest and execution platform, with canonical ordering requirements. This is the closest fit to recipe→artifact caching; neither API guarantees an arbitrary nonhermetic builder is deterministic. [P: [Bazel caching](https://bazel.build/versions/7.1.0/remote/caching?hl=en), [Remote Execution v2 schema](https://github.com/bazelbuild/remote-apis/blob/main/build/bazel/remote/execution/v2/remote_execution.proto)]

**Cheapest cache architecture [D]:**

1. **Grant admission once per run:** resolve principal, bindings, rights, policy generation, method schema versions and resource versions. Compile validators/types once per schema shape; continue effect-sensitive checks per invocation. Credentials remain host-only.
2. **Recipe key:** canonical encoding of architecture/ABI, kernel syscall manifest/source, trusted compiler/build inputs, static ELF, bootstrap/optional RPC bundle, resource tree digests, memory layout and relevant configuration. Hash existing digests rather than rereading all blob bytes. No credentials, live connections, wall time or run seed.
3. **Action cache:** `recipeHash → {imageHash, manifestHash}`. A hit avoids the builder; a miss builds/validates once, hashes output bytes, atomically publishes immutable CAS entries and coalesces concurrent identical builds.
4. **Prepared snapshot cache:** key image hash **plus** VMM/snapshot format, CPU features, engine/prelude ABI and initialization profile. Snapshot after initialization but **before** live caps, credentials, timers or run code. A new snapshot is its own artifact with a digest, not another name for the rootfs.
5. **Restore then bind:** initialize private ring state, fresh run generation, entropy/time and host binding table; submit code. A method call uses a small integer table lookup, schema/policy checks and dispatch—**no recipe hashing, build, snapshot lookup or grant negotiation per call**.

Keep grant *shape* separate from grant *instance*. Otherwise every tenant, approval epoch or credential rotation creates a new snapshot and destroys sharing. Conversely, omitting tool ABI/resource versions can revive incompatible state. A snapshot shared across principals must contain only shareable data; tenant resources require separate authorization domains even when their bytes deduplicate. Revocation is checked through live host binding state, not a stale image manifest.

### What lazy pulling actually demonstrated

Slacker FAST'16 studied 57 Docker workloads: pulling consumed **76% of startup**, while startup read only **6.4% of transferred data**. Storage-backed clones and demand fetch improved median deployment **5.3×** and development cycle **20×**. Measurements used a VM with 4 cores/8 GB on Dell R720, Xeon E5-2620 2 GHz, Tintri T620 storage. This is seconds-scale Docker/image-distribution evidence, not a prediction of jitk microsecond gains. [P: [Harter et al.](https://www.usenix.org/system/files/conference/fast16/fast16-papers-harter.pdf), §§4, 6]

eStargz adds seekable gzip chunks, a TOC with chunk digests, and prioritized startup files before a prefetch landmark. Its optimizer profiles accesses; the startup prefix can be fetched in one HTTP Range request. Verify trusted manifest→TOC digest→chunk digest before serving lazy bytes. This gives a usable design for a host blob cache; it does not require a FUSE daemon inside jitk. [P: [eStargz specification](https://raw.githubusercontent.com/containerd/stargz-snapshotter/main/docs/estargz.md)]

Firecracker separately supports sharing read-only disks and restoring memory files with `MAP_PRIVATE`, on-demand page loading and anonymous CoW writes. A shared squashfs lower rootfs plus per-VM writable overlay shares disk contents; **virtio-blk alone does not merge guest page caches**. Sharing memory snapshots is the mechanism that additionally shares initialized RAM. Clone entropy/userspace identifiers need post-restore handling; fresh kernel entropy alone does not repair arbitrary application state captured in a snapshot. [P: [snapshot support](https://raw.githubusercontent.com/firecracker-microvm/firecracker/main/docs/snapshotting/snapshot-support.md), [rootfs sharing example](https://github.com/firecracker-microvm/firecracker/discussions/3061), [clone-state warning](https://raw.githubusercontent.com/firecracker-microvm/firecracker/main/docs/snapshotting/random-for-clones.md)]

REAP, ASPLOS'21, found snapshot-started execution **95% slower** than memory-resident execution on average, and cut cold-start delay **3.7×** by recording/prefetching stable memory working sets. Platform: dual Xeon E5-2680 v3, 256 GB, 200 GB SATA3 SSD, fixed 2.5 GHz, Ubuntu 18.04/kernel 4.15; memory sharing disabled. Its page-working-set trace is distinct from tool-call record/replay. [P: [paper](https://arxiv.org/pdf/2101.09355), §6]

**For today's approximately 2.8 MiB jitk image, local warm-cache direct mapping is the first experiment; remote demand paging is not automatically a win.** Cache kernel/engine and small resource sets eagerly. Introduce chunk-level lazy resource fetch only when working-set/size measurements justify it; never put a remote fetch on the first instruction's critical path merely to advertise lazy loading. [D]

### Packed FS versus EROFS and squashfs

| Format | Useful property / cost |
|---|---|
| **jitk JITKFS01** | 16-byte header + **24 B/node** + names + raw data; sorted child ranges enable binary search per path component, no boot parsing. Fixed metadata and only regular files/directories make deterministic packing simple. Reads perform one checked copy into EL0. **64 fd slots**, no file mmap or general writes. [L: packer/fs.rs/README above] |
| **EROFS** | Read-only image format with **32/64 B inode cores**, compact metadata, inline/shared attributes and compression options; supports DAX for appropriate uncompressed mappings. More complete format/reader than jitk needs today. Compression still requires producing decompressed bytes; DAX is not direct access to compressed plaintext. [P: [kernel EROFS](https://docs.kernel.org/filesystems/erofs.html), [DAX](https://docs.kernel.org/filesystems/dax.html)] |
| **squashfs** | Read-only compressed data/metadata, tail fragments, directory indexes; default **128 KiB blocks**, maximum **1 MiB**. A small cold random read can require decompressing its containing block. Strong Linux/container interoperability, additional decoder/cache state for jitk. [P: [kernel documentation](https://docs.kernel.org/filesystems/squashfs.html)] |

The existing filesystem benchmark is more decision-relevant than format fashion: direct-load resources add **1 MiB physical footprint per MiB per VM**, approximately **0.15 ms/MiB boot**, and a 1 MiB guest read takes **194 µs p50** (four 256 KiB reads). The stock loader retained another image copy on macOS; the direct-load patch saved **about 2.8 MiB/VM**, but still copies bytes into each guest. With 8 MiB resources the mmap arena shrinks to **14.2 MiB**, below the configured 16 MiB QuickJS heap cap. These are contended developer-Mac/HVF observations, not quiet boot results. [L: [FS measurements](../../jitk/kernel/RESULTS-fs.md), [loader patch](../../jitk/vmm/patches/raw-direct-load.diff)]

**First improve physical sharing [D].** Put immutable resource extents into host-file-backed shared read-only mappings; keep mutable snapshot pages private/CoW. Compression reduces disk/network bytes, but decompression into each VM can still duplicate plaintext and consume CPU. If needed, decompress/verify once into a host immutable cache before mapping. Preserve the current packer initially, align shared extents to host granularity, and measure PSS/physical footprint plus hypervisor/kernel memory. Neither a smaller archive nor a 32 MiB guest configuration proves ≤2 MiB physical cost.

## 8. Explicit overhead budget and sub-day experiments

Let `T = Trestore + Tguest-fixed + N×Tcall + Ttool-critical-path + Touter-MCP`; parallel operations use the dependency critical path rather than sum of tool durations. Track CPU separately: parked pools hide restore/boot work from latency but still pay it during refill. [D model; L baselines §1]

|---|---:|---|
| 10 µs | 3.5% | Reasonable transport optimization unit. |
| 30 µs | 10.5% | Proposed upper small-call budget, excluding actual tool execution. |
| 100 µs | 35.1% | Approximately today's indicative incremental tool cost. |
| 400–500 µs | 140–175% | Outer MCP overhead can dominate a tiny execution; amortize once. |

**Proposed ≤30 µs small-call target [D]:** 5 µs encoding/decoding, 5 µs bounded copy/validation, 10 µs exit/re-entry, 5 µs host dispatch/binding checks, 5 µs slack; ≤60 µs p99 under a stated load. These allocations are hypotheses, especially for QuickJS/Node/HVF, not published component measurements. At 30 µs/call, ten sequential calls consume 300 µs locally; 64 consume 1.92 ms. The ≤1 ms CPU/run target cannot cover arbitrary call counts, large JSON, or expensive tools; define the workload envelope.

An 80 KiB ring leaves roughly 1.92 MiB of the 2 MiB target for everything else. A 1 MiB structured JSON result already required approximately **8 MiB JS heap** in the local engine study; retaining v1's maximal payloads while claiming a universal ≤2 MiB VM is untenable. Prefer small control messages and opaque blob/capability handles. Even hashing the whole 2.8 MiB image at an illustrative **1 GiB/s** would cost about 2.7 ms; this is arithmetic, not measured hashing performance. Hash on ingest/build, not per call. [L: [QuickJS study](../quickjs-verdict.md); D budget]

## Top 5 gaps/blockers

1. **No measured per-call exit/copy/CPU attribution.** 285 µs is whole execution; “two frames” is not “two exits.” Existing 1 KiB chunks and status MMIO may dominate, but their contribution remains unmeasured.
2. **Physical sharing is missing.** Direct load removes one loader copy, not per-VM image/resource residency. Eight MiB resources already squeeze guest heap space; general JSON workloads can independently exceed the ≤2 MiB target.
3. **Synthetic files lack a transport contract.** Kernel-blocking calls need reply demultiplexing outside QuickJS, local metadata, precise commit/EOF/cancel semantics, and bounded per-open state. Ordinary Linux-file differentials do not define RPC effects.
4. **Capabilities and prepared state have no clean lifecycle yet.** Baking grant instances into snapshots destroys reuse and risks stale authority; host tables, resource versions, revocation and cleanup must be separate from immutable bytes.
5. **Pipelining/replay can amplify work or repeat effects.** Cap'n Web does not bound live exports/calls; MCP has no promised-result graph or exactly-once execution; time/completion order and crash ambiguity prevent naive deterministic replay.

## Top 5 recommendations

1. **Prioritize immutable image/resource sharing and prepared bootstrap snapshots.** Largest density gain: remove the measured ~1 MiB/VM per MiB resource slope. Preserve the small packed format; evaluate compression/lazy remote reads only after working-set measurements.
2. **Build one bounded ring transport with batch submit/wait and a native host bridge.** Target 80 KiB/VM and ≤30 µs small-call local overhead, both experimental. Instrument every exit/wake/copy and total CPU; preserve asynchronous fan-out and idle parking.
3. **Use an action-cache/CAS/snapshot-cache split with late grant binding.** Recipe hashes identify construction, content hashes identify bytes, prepared-state keys identify compatibility. Cache schemas/types by shape; dispatch through live per-run capability slots without hashing/building on each call.
4. **Add `/mcp/` and `/cap/` as adapters over that same capability dispatcher.** Keep metadata and immutable reads local, materialize resources once, and make effect submission explicit. Use generated native stubs for JS, file endpoints for unmodified binaries, and opaque blob handles for large data.
5. **Gate Cap'n Web and replay behind measured workloads and explicit new contracts.** Preinitialize the bundle, batch control messages, enforce quotas after map expansion, and use pipelining for demonstrated dependent chains. Journal deterministic inputs/delivery; require remote idempotency or reconciliation for unknown side effects.
