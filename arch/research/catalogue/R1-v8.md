## Round 1 — V8/Wasm capsules — `v8/`
The question: should Sofort build a V8/WebAssembly sibling of jitk, with agent JavaScript running in QuickJS compiled to wasm32 inside V8 (Node, browser, Cloudflare Workers/workerd, Deno/Bun), so that a program parked on an awaited tool call can be snapshotted as one linear-memory file, then forked, moved between browser/server/edge, and replayed from a journal of its imports? Six angles looked at it: architecture, landscape, roadblocks, tech stack, demo and public signal. All six returned **go-with-changes**. The core mechanism reproduces (M: parked-promise restore across Node/Chromium/workerd/Dynamic Worker, divergent forks), but it is prior art (Vercel quickjs-wasi and Workflow snapshots, LangChain quickjs-rs, XS Sandbox, Golem fork). The remaining gap is a provider-neutral, versioned capsule contract with correct pending-tool, authority and effect semantics and cross-host conformance. Release blockers: resource enforcement (the Bellard port's 16 MiB cap accepted 31 MiB, while quickjs-ng honoured it), an independent kill path, a tenant boundary, and snapshot sizes far above the 100 KB demo figure. Recommended stack: a quickjs-ng wasm32 reactor that returns control at await boundaries. Recommended public story: lead with a labelled browser-to-server handoff demo, backed by jitk as the hardware tier.

### 01-architecture: Architecture feasibility: portable QuickJS/Wasm capsules
Lens: whether a fixed QuickJS-on-wasm32 interpreter, with its linear memory and a durable host-side execution record, is a sound architecture for pausing, forking and moving agent JS between Node, browser Workers and Cloudflare Workers/DO. Headline finding: a fresh rerun of the Oct 25 spike reproduced the core mechanism. A Wasmtime capsule parked on a tool promise resumed in fresh Node instances into divergent forks (42 / 100), with zero new tool emissions and an image byte-identical to Oct 25. A durable executor still needs a quiescent checkpoint protocol, persisted host and policy state, qualified resource limits and a Node-free executor core. The one bet is a four-import `capsule-abi/1` reactor, checkpointed only after control returns to the host, behind a journaled durable coordinator. Verdict: **GO-WITH-CHANGES**. Effort is **E** 43–73 engineer-days.

#### Capsule = fixed QuickJS wasm32 interpreter + linear memory + host execution record
- **What:** The portable object is a fixed QuickJS interpreter compiled to wasm32, its linear memory and the rest of its module state, plus a durable host-side execution record. Guest JS runs in QuickJS and V8 runs the Wasm interpreter.
- **How it would work:** The design captures the engine's memory instead of serializing user objects. Promise continuations, closures and cycles therefore stay as engine objects. It is not an ordinary V8 isolate snapshot.
- **Evidence / numbers:** **I**: "sound for a restricted, versioned computer with explicit host-return checkpoints."
- **Prior art / who has it:** QuickJS (Bellard), V8, Wasmtime. No product prior art named in this report.
- **Verdict:** KEPT. This is the core design, conditional on the four required changes.

#### Central mechanism reproduced (park → copy memory → resume elsewhere)
- **What:** A newly created QuickJS instance in Wasmtime parked on a pending tool promise. Its memory was copied, and fresh Node instances resumed it with different replies.
- **How it would work:** Memory and globals are copied while the instance waits on a tool call. A fresh instance of the same module is overlaid with them, and a different reply is delivered to each fork.
- **Evidence / numbers:** **M**: outputs 42 and 100; zero new tool emissions on either restore; the fresh memory image was byte-identical to the Oct 25 image.
- **Prior art / who has it:** Oct 25 spike (`portability/02-wasm.md`).
- **Verdict:** KEPT (finding). It strongly supports exact-build, quiescent memory portability between two local runtimes.

#### Four required changes before "end-to-end durable executor"
- **What:** (1) A quiescent checkpoint protocol; seeing a tool import does not by itself prove quiescence. (2) Persist the dispatcher, policy state, pending-call ledger, journal cursor and ownership alongside guest memory, and recreate trusted capabilities from host configuration. (3) Qualified allocation accounting, deterministic compute budgets and deployment-specific termination. (4) Split the portable executor core from Node dependencies, and split durable execution lifetime from the one-shot `execute()` lifetime.
- **How it would work:** Sections 4–9 of the report specify each change.
- **Evidence / numbers:** **I**. Same-thread JS timers cannot stop synchronous Wasm.
- **Prior art / who has it:** None named in the report.
- **Verdict:** KEPT. These four changes are the conditions on the GO-WITH-CHANGES verdict.

#### Integration seam exists in jitk executor, durable lifecycle does not
- **What:** `Backend.park(signal?, deadline?)` and `Sandbox.read/send/kill/exited/armDeadline` already exist. `pool.ts` owns admission and single-use sandboxes, and `executor.ts` keeps tools, policy, credentials, approval and provenance on the host.
- **How it would work:** The executor's `finally` marks the policy run dead, clears approvals, retires the sandbox and aborts tools. An execution that waits three days for approval therefore needs a durable coordinator above this layer.
- **Evidence / numbers:** **F, repository**: `arch/jitk/executor/backend.ts`, `pool.ts`, `executor.ts`.
- **Prior art / who has it:** Sofort jitk executor.
- **Verdict:** NARROWED. The seam is usable, but none of the required changes are implemented.

#### Isolation remains a tier choice (software Wasm tier vs jitk hardware tier)
- **What:** This is software isolation. The Wasm runtime, import wrappers and policy dispatcher are in the TCB. jitk stays the tier for hardware isolation and native binaries.
- **How it would work:** A native jitk memory image cannot be copied into wasm32, so replay or an explicit application checkpoint has to bridge the two tiers. Running the same Wasm capsule inside jitk could align the formats, but that is additional, unproven integration.
- **Evidence / numbers:** **I**.
- **Prior art / who has it:** jitk (Sofort).
- **Verdict:** NARROWED. No raw-memory migration between jitk and Wasm.

#### Oct 25 spike rerun: method and environment
- **What:** The read-only evidence directory was hash-verified and its existing `qjs.wasm` was reused, without rebuilding QuickJS. Paths were changed to a scratch directory; algorithms and workload were not. A fresh reactor was snapshotted in Wasmtime and then restored in fresh Node instances, so this was not just a reload of the old image.
- **How it would work:** Python `snapshot.py` initializes and runs the async workload, checks one emitted call and no output, captures memory and globals, and restores two Wasmtime forks. `restore.mjs` then loads the new image into two fresh Node instances. The workload keeps `{n:7}` with a self-cycle, a closure, a `Uint8Array([2,3,5])` and a `Map([['x',11]])` across an `await tool({value:7})`.
- **Evidence / numbers:** **M**: Darwin 25.6.0 arm64; Node 24.22.1 / V8 13.6.233.17-node.58; Python 3.15.0, Wasmtime Python 50.0.1. Reactor 966,584 bytes from Bellard QuickJS 2026-06-04, SHA-256 `d239715d…59df5`. All spike files matched `SHA256SUMS.json`.
- **Prior art / who has it:** Oct 25 spike.
- **Verdict:** KEPT (method). The compiler toolchain was not independently reproduced.

- **Evidence / numbers:** **M**: reproduced.
- **Prior art / who has it:** Oct 25 spike.

#### No duplicate tool emission on restore
- **What:** Restored instances did not re-emit the pending tool call.
- **How it would work:** The call is already recorded in the restored heap, so delivering a reply settles it without a new request.
- **Evidence / numbers:** **M**: 0 new tool emissions in all four restored instances. These were stub calls, not a crash test of external side effects.
- **Prior art / who has it:** Oct 25 spike.
- **Verdict:** NARROWED. Valid for stubs. It says nothing about crash-safe effect delivery.

#### Snapshot size (and what "~100 KB" does not cover)
- **What:** Raw and compressed sizes of the linear-memory image.
- **How it would work:** The image was gzip-compressed with the original script's `gzip.compress(memory)` defaults, and also with explicit level 9.
- **Evidence / numbers:** **M**: raw 2,097,152 bytes (32 Wasm pages, exactly 2 MiB); 99,854 bytes with defaults; 99,755 bytes at gzip level 9. Compression settings must accompany any size claim.
- **Prior art / who has it:** Oct 25 spike.
- **Verdict:** NARROWED (claim to avoid). These sizes cover linear memory only; the reactor module, metadata, host checkpoint, journal and storage envelopes come on top. "~100 KB" is not the total size of an independently runnable capsule package. Larger live heaps, source text and retained tool outputs also make the image bigger.

- **Evidence / numbers:** **M**: SHA-256 `eb468b13256f00ba8d4637340ff8ef53ecf2a3ae095bb7690518f54fbac3e3d2`.
- **Prior art / who has it:** Oct 25 spike.

#### Spike's actual import ABI and embedding
- **What:** The spike is a small embedding, not the QuickJS shell. It imports `sofort.emit(ptr,len)` and four WASI functions: `clock_time_get`, `fd_close`, `fd_seek`, `fd_write`.
- **How it would work:** It compiles the engine C files plus `bridge.c` and excludes `quickjs-libc.c`. `__EMSCRIPTEN__` branches disable atomics and native stack checks and select switch dispatch. The WASI stubs give a constant clock and no file access. There is no `random_get`: `Math.random()` is seeded from `gettimeofday()`, with xorshift state kept in the QuickJS context.
- **Evidence / numbers:** **M** (import list); **F, local source** (`build.py`, `bridge.c`, `quickjs.c`: `js_random_init`, `js_def_malloc_usable_size`).
- **Prior art / who has it:** QuickJS 2026-06-04 (Bellard).
- **Verdict:** NARROWED. This is the measured build, distinct from the proposed production profile.

#### Proposed production profile: single audited reactor, no general WASI
- **What:** Compile QuickJS, its allocator/libc support and a small bridge to wasm32, with libc clock/error/diagnostic shims inside the module.
- **How it would work:** Exclude shell modules, filesystem, sockets, dynamic native loading, threads, shared memory, externally backed buffers, externrefs and Wasm-GC state. Use an explicit feature profile: core wasm32 plus mutable globals, sign-extension, non-trapping float-to-int and bulk memory copy/fill. A build-time binary audit rejects passive-segment mutation, mutable tables and unexpected features. A fixed function table is allowed but must be recreated identically.
- **Evidence / numbers:** **I**. This is a profile to qualify; the existing spike has not passed such an audit.
- **Prior art / who has it:** None named.
- **Verdict:** KEPT. This is the proposed build.
- **Kill test / first proof:** The build-time binary audit of features, globals and tables; the effort row "Audited QuickJS reactor/build/import manifest" is **E** 3–5 days.

#### `capsule-abi/1`: four synchronous imports
- **What:** `sofort.tool_call(ptr,len)`, `sofort.clock(kind,out_u64_ptr)`, `sofort.random_fill(ptr,len)` and `sofort.log(ptr,len)`, each returning an i32 status. All are synchronous; none returns a host Promise or calls an export reentrantly.
- **How it would work:**
  - `tool_call` copies a protocol-v1 `call` frame into a bounded host outbox, without performing the tool or settling the promise inline. `log` copies a v1 `log` frame.
  - `clock` kinds 0/1 are guest virtual wall/monotonic time and are journaled. Kind 2 is operational monotonic time for trusted interruption checks only. On workerd, kind 2 cannot advance continuously.
  - `random_fill` bytes are journaled. QuickJS init is patched to use it, so `Math.random` advances a pinned PRNG deterministically. That PRNG must not be called cryptographic.
  - Status 0 means complete acceptance only. Range, kind, outbox or quota failures end the turn. Pointer/length ranges are validated without overflow against the current memory buffer, and views are reacquired after growth.
- **Evidence / numbers:** **I**.
- **Prior art / who has it:** Protocol v1 frames (Sofort).
- **Verdict:** KEPT. Host schema, state and budget checks stay authoritative even if the guest engine is compromised.

#### Bridge exports and trusted bootstrap
- **What:** Exports are `abi_version`, `init`, bounded input buffer/length accessors, `run`, `deliver_reply`, `pump(max_jobs)`, `status`, bounded result accessors, `memory`, and every mutable numeric global needed for restore, including the C stack pointer and any metering globals.
- **How it would work:** Replies are parsed as data and delivered through QuickJS APIs. The spike's numeric `JS_Eval("settle(...)")` path must not be extended into interpolating arbitrary reply code. The bootstrap keeps the existing codec, namespace proxy and protocol rules, and replaces `std/os` I/O and timers with bridge functions and explicit host scheduling.
- **Evidence / numbers:** **I**.
- **Prior art / who has it:** None named.
- **Verdict:** KEPT. The effort row "Bridge + bootstrap + codec/protocol parity" is **E** 4–7 days.

#### Resource profile starting values
- **What:** 2 MiB initial / 32 MiB max linear memory and a 512 KiB C stack, with a properly enforced inner heap cap.
- **How it would work:** These are compatibility starting values from the spike. The whole resulting module is hashed; the ABI-cleaned build will have a different identity from the Oct 25 binary.
- **Evidence / numbers:** **I**. They are not demonstrated to be enough for arbitrary code.
- **Prior art / who has it:** Oct 25 spike parameters.
- **Verdict:** NARROWED. These values must be qualified.

#### One-shot `wasm-qjs` backend on the existing seam
- **What:** Add `wasm-qjs` to `Backend.kind` and `select-backend.ts`. `WasmBackend.park()` acquires a fresh initialized instance and returns a `WasmSandbox`.
- **How it would work:** `send(run)` loads validated source and namespaces, enters the bridge and pumps bounded jobs. `send(ret)` settles one recorded resolver and pumps again. `read()` drains bounded, validated ready/call/log/done frames. `kill()` marks the instance dead. `exited` resolves only once the instance is idle and no queue retains it, so pool capacity is not released early.
- **Evidence / numbers:** **I**.
- **Prior art / who has it:** jitk Backend/Sandbox seam.
- **Verdict:** KEPT. This is next step #1. A narrow Node backend proof is **E** 3–5 days.

#### Dispatcher holds more state than `snapshot()` exposes
- **What:** `dispatcher.ts` tracks pending IDs and their byte charges, next ID, protocol phase, partial input, wire/frame/log budgets and inflight bytes. Its `snapshot()` returns statistics, not restorable state.
- **How it would work:** The executor also keeps `nextId`, pending dispatch Promises, log accumulation and provenance. Restoring only the QuickJS promise map would reset host budgets and lose ownership of outstanding calls.
- **Evidence / numbers:** **F, repository** (`arch/jitk/protocol/dispatcher.ts`).
- **Prior art / who has it:** Sofort protocol dispatcher.
- **Verdict:** NARROWED. Restorable host state has to be added.

#### Durable coordinator (not just a `snapshot()` method)
- **What:** Keep the ephemeral `execute()` behavior for codemode, and add durable `start/resume/checkpoint/fork/cancel` operations that return an execution handle and status.
- **How it would work:** A `CheckpointableSandbox` capability exposes quiescence and capture, and the backend exposes restore. The coordinator owns the matching host checkpoint. A checkpoint pointer must not go into the JSON tool protocol as if the guest could authorize it.
- **Evidence / numbers:** **I**.
- **Prior art / who has it:** None named.
- **Verdict:** KEPT. The effort row "Journal/coordinator/replay/effect and fork semantics" is **E** 7–12 days.

#### Host checkpoint requirements
- **What:** Serialize:
  - validated dispatcher state;
  - pending call IDs, requests and byte charges;
  - delivery and outbox state, and counters;
  - policy run identity, sticky private/untrusted labels and approval records;
  - tool registry and schema version;
  - journal position and remaining resource grants.
- **How it would work:** Awaiting host Promises become logical work records. Closures, credential issuers, AbortControllers and transport handles are recreated from trusted configuration. The canonical checkpoint has no partially decoded frame and no reentrant import in progress.
- **Evidence / numbers:** **I**.
- **Prior art / who has it:** None named.
- **Verdict:** KEPT.

#### Policy hazard: per-run random UUID, idempotency key and `WeakSet` grants
- **What:** `policy.mjs` gives each new run a random UUID and sends `${run.id}:${call.id}` as the tool idempotency key. It tracks granted call objects in a process-local `WeakSet`, which cannot be snapshotted.
- **How it would work:** A restore must keep the logical run identity for retries, restore taint and counters, and rebuild authorization from host policy and approval records. Starting a new policy run and resetting taint is wrong. Forks get new branch identities for new effects; approvals are re-bound or explicitly reissued per branch, not copied as ambient authority.
- **Evidence / numbers:** **F, repository** (`arch/jitk/executor/policy/policy.mjs`); **I** (fix).
- **Prior art / who has it:** Sofort policy module.
- **Verdict:** KEPT (fix required).

#### Portable executor core: source split from Node
- **What:** `backend.ts` imports child process, fs and OS utilities at module load. `executor.ts` uses `node:perf_hooks` and `setImmediate`, `code.ts` reads the codec via `node:fs`, and policy uses `node:crypto`, Buffer and a file-URL loader.
- **How it would work:** Extract a pure protocol/codec/policy state machine. Clock, digest, scheduling, artifact loading, transport and termination become injected adapters, and the bootstrap/codec is prebundled as strings.
- **Evidence / numbers:** **F, repository**; **I**.
- **Prior art / who has it:** None named.
- **Verdict:** KEPT. Adding a backend class alone does not make the package importable in a browser Worker. The effort row "Node Backend and portable executor-core split" is **E** 3–5 days.

#### `wasm-quiescent/1` checkpoint format: manifest + content-addressed blobs
- **What:** An immutable `CheckpointManifest` plus content-addressed blobs.
  - The manifest holds the module, ABI, bootstrap, source, profile, codec and tool-schema identities; the parent checkpoint; a memory map with 4096-byte chunks, a base and changed chunks; globals with exact bits; and a boundary phase (ready/waiting/done, `noActiveFrames: true`). It also holds the host-state hash, `appliedInputSeq`, `journalPrefixHash` and `resourceGrantHash`.
  - A separate `HostCheckpoint` and a `BranchHead {generation, checkpointHash, journalHead, ownerEpoch, leaseExpiry}` sit alongside it.
- **How it would work:** Hash a canonical encoding: restricted canonical JSON with sorted keys and integers or decimal strings. Use SHA-256 over domain-separated, uncompressed bytes. The compression codec lives in the blob envelope, outside logical identity, and full images are distinguished unambiguously from page-diffs.
- **Evidence / numbers:** **I**.
- **Prior art / who has it:** None named.
- **Verdict:** KEPT.

#### Exact numeric bits and what counts as runtime state
- **What:** Encode i64 values as bit strings or decimal strings, not JS numbers, and float globals by their bits. Record the table shape and fingerprint and verify its immutable initializer.
- **How it would work:** Reject unexported mutable globals, mutable imported state, external references and unrepresented data/element-segment drop state. The C heap, C statics and QuickJS job queue live in linear memory. Wasm locals, operand stack and control frames do not.
- **Evidence / numbers:** **I**. Follows the [Wasm runtime-state model](https://webassembly.github.io/spec/core/exec/runtime.html) (checked 2026-10-27).
- **Prior art / who has it:** WebAssembly core spec.
- **Verdict:** KEPT.

#### Page-diff forks (4 KiB storage chunks, not OS copy-on-write)
- **What:** Forks share the parent checkpoint and store only changed chunks.
- **How it would work:** 64 KiB Wasm growth pages are distinct from 4 KiB storage chunks. The root manifest maps the full address range with a well-known zero-chunk hash. A child references its immutable parent and replaces only changed chunks, including chunks zeroed since the parent and newly grown ones. A fork first creates only a branch record, then persists its divergent chunks and events. At capture, every chunk is compared or hash-scanned, because portable JS has no dirty-page notification for Wasm.
- **Evidence / numbers:** **I**. Capture work is O(memory size).
- **Prior art / who has it:** None named.
- **Verdict:** NARROWED (claim to avoid). This is storage deduplication, **not** OS copy-on-write RAM sharing; each runnable fork still needs its own restored memory.

#### Bounded restoration cost; no sparse physical restore
- **What:** Cap delta depth (for example 8), periodically materialize a full page map, and pack chunks to avoid thousands of object-store requests.
- **How it would work:** Garbage-collect only blobs unreachable from retained branch heads, journals and snapshot roots. The depth and packing thresholds are initial engineering choices to benchmark.
- **Evidence / numbers:** **I**.
- **Prior art / who has it:** None named.
- **Verdict:** NARROWED (claim to avoid). Plain browser/Node Wasm cannot memory-map an S3 parent and fault pages in on demand, so do not claim sparse physical restoration from a Merkle manifest.

#### Capture/commit protocol
- **What:** Fence the owner, stop reply delivery, return from every export and import, and drain runnable jobs. Then stage guest memory, globals and host state at the same applied-input cursor.
- **How it would work:** Upload blobs, journal blocks and the manifest and verify their hashes. Then advance the branch head atomically against the expected generation and owner epoch. Only after that commit may the owner release the instance or report it durably parked. A storage failure leaves the prior head authoritative. An interrupted upload leaves reclaimable unreachable blobs, never a half-published checkpoint.
- **Evidence / numbers:** **I**.
- **Prior art / who has it:** None named.
- **Verdict:** KEPT. The effort row "Checkpoint/CAS/page-diff capture/restore" is **E** 4–7 days.
- **Kill test / first proof:** Kill the process between every intent, effect, result, delivery and head-publication transition.

#### Restore procedure
- **What:** Load the committed branch head and verify tenant authorization, hashes, module/ABI/profile and resource bounds. Resolve parent chunks and instantiate the exact approved module.
- **How it would work:** Run only the specified reactor initialization, grow to the saved page count, and overlay memory. Restore mutable globals and the host checkpoint, replay committed inputs after `appliedInputSeq`, then deliver the next input once. Do **not** initialize QuickJS again after copying the heap. A grown Wasm memory cannot shrink, so use a correctly sized fresh instance or reject an unsuitable pooled one.
- **Evidence / numbers:** **I**.
- **Prior art / who has it:** None named.
- **Verdict:** KEPT.
- **Kill test / first proof:** Restore grown memories, and reject missing parents and wrong builds.

#### Storage and authority plans: S3, R2 + Durable Object, IndexedDB
- **What:**
  - **S3:** immutable module/chunk/manifest/journal objects stored under their hashes. Immutable keys use conditional create; branch heads use a conditional generation update or a transactional coordinator. ETags are concurrency tokens, not the capsule SHA-256.
  - **R2 + DO:** R2 holds bulk immutable objects. DO SQLite holds heads, journal sequencing, call ledger, leases and approval references, and a short transaction publishes pointers after the R2 uploads finish.
  - **IndexedDB:** separate object stores. Hash and compress outside the transaction, then publish in one readwrite transaction with strict durability where supported.
- **How it would work:** Upload, then publish. There is no cross-product R2+DO transaction.
- **Evidence / numbers:** **F**: S3 `If-None-Match`/`If-Match` conditional writes ([AWS](https://docs.aws.amazon.com/AmazonS3/latest/userguide/conditional-writes.html)). R2 is strongly consistent but last-writer-wins without fencing ([R2 consistency](https://developers.cloudflare.com/r2/reference/consistency/)). DO SQLite has transactional updates ([DO storage API](https://developers.cloudflare.com/durable-objects/api/sqlite-storage-api/)).
- **Prior art / who has it:** AWS S3, Cloudflare R2/Durable Objects, IndexedDB.
- **Verdict:** KEPT. These properties support pointer publication; they do not make a remote tool call and a blob upload one transaction.

#### Browser persistence has weaker failure coverage
- **What:** IndexedDB `strict` durability is a hint, not an unconditional power-loss guarantee. Quotas and eviction need handling.
- **How it would work:** Request persistent storage with `navigator.storage.persist()`. Do not assume a killed tab gets a final checkpoint opportunity. Sync committed state to a remote checkpoint and journal for server-side and device-loss recovery.
- **Evidence / numbers:** **F/I**: [IndexedDB 3.0](https://w3c.github.io/IndexedDB/#transaction-durability) (draft 2025-08-13); [WHATWG Storage](https://storage.spec.whatwg.org/) (updated 2026-10-19).
- **Prior art / who has it:** W3C/WHATWG specs.
- **Verdict:** NARROWED. The browser is a cache or replica, not the durable authority.

#### Confidentiality and authenticity of heaps/journals
- **What:** Encrypt and access-control heaps and journals, since tool outputs and source can be sensitive. Content addressing is not authorization.
- **How it would work:** Deduplicate only inside an allowed trust scope, and sign or authenticate committed manifests and resource grants. A browser can mutate its working memory, so a browser-uploaded heap does not prove the approved program ran. Server tools authorize every effect independently, and replay or validate on a trusted executor if workflow-state integrity is required.
- **Evidence / numbers:** **I**.
- **Prior art / who has it:** None named.
- **Verdict:** KEPT.

#### Journal is authoritative; snapshots only accelerate
- **What:** An ordered, hash-chained record of committed interaction history.
- **How it would work:** Each record carries the branch/logical run, sequence, prior hash, event kind, request digest, bounded input/output bytes or blob hashes, policy/schema version and call identity. Events recorded:
  - source and init inputs;
  - guest clock and entropy results;
  - call intents and normalized authorized arguments;
  - approvals and denials;
  - validated replies and errors, and delivery order;
  - timer firings, cancellation and lifecycle changes.
- **Evidence / numbers:** **I**. `Promise.race` makes delivery order observable, so an unordered list of results is not enough.
- **Prior art / who has it:** None named.
- **Verdict:** KEPT.

#### Commit barriers (because imports are synchronous)
- **What:** Import wrappers append clock, random, log and call data to a bounded in-memory turn buffer. They cannot await S3/R2 while a Wasm activation is live.
- **How it would work:** Before any external dispatch, publication of logs or results, or checkpoint acknowledgement, the host returns from Wasm and durably commits the turn's journal and outbox. An uncommitted turn that crashes is recomputed from the prior boundary, and no effect from it can have escaped. A deterministic persisted creation seed and virtual time reduce retry variation.
- **Evidence / numbers:** **I**. "Exact replay" refers to committed history only.
- **Prior art / who has it:** None named.
- **Verdict:** KEPT.

#### Reply ordering: journal before delivery
- **What:** Persist a tool's validated, redacted result and its chosen delivery sequence **before** calling the reply export.
- **How it would work:** A snapshot records which input sequence its bytes include. On failure between journal commit and delivery, restore or replay from that cursor. "Input durably selected" is not the same as "already applied to this heap." Timers follow the same model as logical host records, never serialized `setTimeout` handles.
- **Evidence / numbers:** **I**.
- **Prior art / who has it:** None named.
- **Verdict:** KEPT.

#### Replay algorithm
- **What:** Start from the pinned build at creation, or from the latest compatible checkpoint, and replay the recorded inputs and scheduling decisions.
- **How it would work:** Intercept every tool request, compare its canonical digest with the journal, and return the recorded reply without calling the tool. Clock and entropy reads consume their matching records. A missing or mismatched record stops replay as a divergence and never falls through to live dispatch. Policy history is replayed into host taint and counters, new effects are reauthorized against current policy, and committed logs are not printed twice.
- **Evidence / numbers:** **I**. The Oct 25 tiny replay record is cited as prior evidence and was not rerun.
- **Prior art / who has it:** None named.
- **Verdict:** KEPT.

#### Determinism profile beyond clock/random
- **What:** Pin timezone, locale, source/module resolution, the QuickJS build, codec, event order and allocation/resource semantics. Omit `Intl`, host environment access and GC-observable APIs until they are qualified.
- **How it would work:** Disable relaxed SIMD. Audit QuickJS/Wasm NaN behavior, especially float and typed-array bit observations, and normalize where needed; browsers lack Wasmtime's NaN canonicalization. A `memory.grow` failure under host pressure, or a forced deadline termination, is an execution failure, not portable evidence of the same logical outcome.
- **Evidence / numbers:** **F/I**: [Wasmtime deterministic execution guide](https://docs.wasmtime.dev/examples-deterministic-wasm-execution.html) names NaN payloads, relaxed SIMD and imports as sources of variation.
- **Prior art / who has it:** Wasmtime.
- **Verdict:** NARROWED. Cross-runtime replay is a qualification target, not something this rerun proved.

#### Effects and crashes: unknown outcomes, no manufactured exactly-once
- **What:** Write the call intent durably before dispatch. Use a stable idempotency key, logical branch + call ID, that survives retries.
- **How it would work:** A crash after the remote effect but before its result is journaled leaves an **unknown outcome**. Auto-retry only if the tool supports idempotency or outcome lookup; otherwise require reconciliation or an explicit at-least-once contract. The tool gateway must also check a fencing token, because a new lease cannot cancel an effect already running remotely.
- **Evidence / numbers:** **I**.
- **Prior art / who has it:** None named.
- **Verdict:** KEPT (claim to avoid: an operation log cannot create exactly-once behavior in an unrelated external system).
- **Kill test / first proof:** Next step #2. Crash at every boundary using an idempotent write tool and an explicitly non-idempotent tool, to expose unknown outcomes.

#### Fork rules
- **What:** Share completed history and checkpoint bytes. Each child gets a branch ID and a newly authorized future budget, and past resource consumption is preserved in history.
- **How it would work:** Pending calls carry an explicit mode:
  - share the original eventual result;
  - inject a hypothetical result for an effect-disabled simulation;
  - dispatch a newly approved child operation under a new key.

  Never silently multiply an in-flight payment or write by the number of forks. The PRNG stream either stays identical (the simpler default for deterministic exploration) or is explicitly reseeded in a journal event.
- **Evidence / numbers:** **I**.
- **Prior art / who has it:** None named.
- **Verdict:** KEPT. Default demonstrations should fork at an unissued/read-only tool or approval boundary, with external writes disabled in simulated branches.

#### Pause requires no live Wasm activation (not merely `await`)
- **What:** Capture is valid only when no Wasm frame is active. Core Wasm execution frames sit outside linear memory.
- **How it would work:** `tool()` builds a QuickJS promise and emits the request synchronously. The async continuation is heap state, and evaluation/job execution must return to the host before memory is copied. Capturing *inside* `sofort.tool_call` would miss the still-active C/Wasm continuation.
- **Evidence / numbers:** **F/I**: [Wasm runtime state](https://webassembly.github.io/spec/core/exec/runtime.html).
- **Prior art / who has it:** WebAssembly core spec.
- **Verdict:** KEPT.

#### V1 checkpoint policy: READY, WAITING (drained), DONE
- **What:** Supported boundaries are initialized READY, terminal DONE, and WAITING.
- **How it would work:** WAITING means every export has returned, runnable jobs are drained, no reply is being applied, and every wake source is a registered host call or timer. Multiple unresolved tools are allowed if the full pending set and order are represented. `await Promise.resolve()` only schedules runnable jobs and is not a durable wait. An unresolved promise with no registered wake source is a deadlock, not movable work.
- **Evidence / numbers:** **I**.
- **Prior art / who has it:** None named.
- **Verdict:** KEPT.

#### Job-boundary checkpoints (runnable job queue) — later option
- **What:** Empty-stack snapshots could also capture a runnable QuickJS job queue after an export returns, because the queue is in memory.
- **How it would work:** This would allow checkpoints at job boundaries, but not a portable pause halfway through a synchronous job. `pump(max_jobs)` must return periodically and enforce cumulative job/compute budgets, so a self-rescheduling microtask cannot starve the host.
- **Evidence / numbers:** **I**.
- **Prior art / who has it:** None named.
- **Verdict:** RUNNER-UP. V1 deliberately chooses drained waiting boundaries for a smaller scheduling contract.

#### Return to host after QuickJS async yield (default pause mechanism)
- **What:** This preserves the QuickJS heap continuation, memory and globals, with no active Wasm stack.
- **How it would work:** Tools are async. The guest yields, control returns to the host, and the host copies memory at an explicit safe boundary.
- **Evidence / numbers:** **I/M**: the minimal migration and fork path was reproduced.
- **Prior art / who has it:** Oct 25 spike.
- **Verdict:** KEPT (#1 mechanism). JSPI is unnecessary.

#### JSPI as the capsule mechanism
- **What:** JSPI is engine-owned suspended Wasm execution plus a link to a host Promise.
- **How it would work:** It is useful for async host APIs behind synchronous C, but the API has no continuation export or serialization operation. Copying linear memory does not move the suspended execution.
- **Evidence / numbers:** **F/I**: [JSPI proposal](https://github.com/WebAssembly/js-promise-integration/blob/main/proposals/js-promise-integration/Overview.md); [V8 JSPI intro](https://v8.dev/blog/jspi) (2024-07-01).
- **Prior art / who has it:** V8/WebAssembly CG JSPI.
- **Verdict:** KILLED as the capsule mechanism, because it cannot serialize the suspension.

#### Asyncify as an optional separate format
- **What:** Asyncify transforms code so logical Wasm stack state is spilled to and reconstructed from memory.
- **How it would work:** It needs transformed code, unwind data, entry/argument and pending-import state, an exact rewind protocol and reentrancy rules. It does not provide pause at an arbitrary instruction.
- **Evidence / numbers:** **F, prior evidence**: Oct 25 measured +57% raw module size and showed a separate unwind/rewind clone; not rerun. [Emscripten Asyncify/JSPI docs](https://emscripten.org/docs/porting/asyncify.html).

- **Verdict:** RUNNER-UP. An optional separate format/ABI for synchronous libraries, not needed for the default design.

#### Programming model for capsule guests
- **What:** Ordinary JS locals, closures, Maps and cycles survive an awaited tool. All external I/O, sleeps, approvals and entropy go through supported bridge APIs.
- **How it would work:** There is no native filesystem, socket, DOM or Node module access inside QuickJS. A long compute loop that should make durable progress must reach an explicit async checkpoint/yield tool. Otherwise it can only finish, or be terminated and replayed from the previous checkpoint.
- **Evidence / numbers:** **I**.
- **Prior art / who has it:** None named.
- **Verdict:** KEPT. Cancellation is not a successful pause.

#### QuickJS engine hooks (memory/stack/interrupt)
- **What:** QuickJS documents `JS_NewRuntime2`, `JS_SetMemoryLimit`, `JS_SetMaxStackSize` and `JS_SetInterruptHandler`.
- **How it would work:** The interrupt handler throws an uncatchable interrupted exception and does not preserve the computation for later resumption. Its periodic poll count is not an exact JS bytecode count and does not price all C builtins uniformly.
- **Evidence / numbers:** **F**: [QuickJS manual](https://bellard.org/quickjs/quickjs.html) (version 2026-06-04), plus the pinned local source.
- **Prior art / who has it:** QuickJS (Bellard).

#### Control 1: deterministic cumulative compute grant (metering)
- **What:** Meter the fixed Wasm module, or fully qualify engine-level metering, under a versioned cost model.
- **How it would work:** Charge loops and basic blocks, size-dependent bulk operations, and parser/regexp/BigInt work. Exhausting the meter traps or terminates; it does not checkpoint. Authoritative fuel lives in protected Wasm globals or host state, not only in guest-writable memory. Every added global is captured and restored, and grants are reconciled with trusted host records.
- **Evidence / numbers:** **I**.
- **Prior art / who has it:** None named.

#### Control 2: host execution deadline
- **What:** Check the deadline before each turn, tool dispatch, reply delivery and checkpoint publication. Also interrupt periodically wherever a real advancing monotonic clock exists.
- **How it would work:** Persist the remaining grant and consumption so that migrating does not reset the budget for free. Guest virtual time stays separate from enforcement time.
- **Evidence / numbers:** **I**.
- **Prior art / who has it:** None named.

#### Control 3: independent termination boundary
- **What:** In Node, run guest execution off the tool/supervisor event loop in a terminable worker or process. Keep an independent supervisor/process watchdog to preserve the current watchdog-strength guarantee.
- **How it would work:** A shard can hold many idle instances but only one active turn. Killing a shard loses its uncaptured neighbors, so keep their checkpoints or baselines, or use smaller failure domains. The owning page can terminate browser Workers, subject to browser scheduling. Termination discards execution state, and recovery starts from the last committed boundary.

#### Cloudflare Workers: no strict per-capsule millisecond watchdog

#### Explicit lifetime semantics (ephemeral vs durable)

#### Module cache + pristine initialized runtime pools

#### Account five distinct memory quantities
- **What:** (1) live QuickJS allocations; (2) current/max linear memory, including C heap, stack and statics; (3) host protocol/journal/tool buffers; (4) checkpoint materialization, compression and staging copies; (5) shared engine code/runtime plus worker/process overhead.

#### Version/portability compatibility matrix
- **What:** Which changes keep a raw image compatible:
  - Same module hash, different Node/browser/workerd version: the intended portable case. Rebuild native code and table objects from the module; never store native frames or compiled caches.
  - Same hash, arm64 ↔ x86: strong expectation for this profile but **not tested**.
  - New QuickJS release, Bellard ↔ quickjs-ng, or wasm32 ↔ wasm64/native: incompatible by default.
  - Same QuickJS but a different compiler, options, bootstrap, allocator, metering or Wizer output: also incompatible. A semantic version or release date is not enough.
  - Different clock/random/locale/codec/scheduler/tool schema: memory may copy but meaning differs. Reject, migrate explicitly, or keep the old adapter.
  - Different CPU or memory budget, or an unsupported Wasm feature: may fail to run. Reject before acquisition.
  - Native jitk ↔ Wasm: no raw migration.
- **How it would work:** Require an exact module hash and a bundle/profile match.
- **Evidence / numbers:** **I**; **F/I**: QuickJS bytecode is version-bound ([manual](https://bellard.org/quickjs/quickjs.html)), and a whole heap has stricter dependencies.
- **Prior art / who has it:** QuickJS, quickjs-ng.
- **Verdict:** NARROWED. Portability holds only for the exact build.
- **Kill test / first proof:** Run both migration directions, with replay, floating-point and resource cases, on x86 and arm64 before certifying.

### 02-landscape: Who is building portable, durable, forkable execution?
A competitive-landscape survey (2026-10-27, no new measurements) of who already snapshots, forks and moves running programs: interpreter-in-Wasm libraries, durable-execution engines, edge platforms, VM sandboxes and academic work. Headline finding: the basic mechanism is taken, sometimes by very close implementations. Vercel's quickjs-wasi and Workflow (experimental VM-memory snapshots merged Oct 1, 2026), LangChain's quickjs-rs/Deep Agents, XS Sandbox (~85 kB empty image, browser+Node), Golem's fork(), dquickts and TimeTravelJS all exist. The one bet is a provider-neutral, versioned capsule contract with browser/server/edge conformance and correct pending-tool, authority and effect semantics, not the memory-copy trick. Verdict: **GO-WITH-CHANGES**.

#### Finding: the basic mechanism is already occupied
- **What:** Snapshotting a JS interpreter in Wasm, keeping promises across a snapshot, cloning a paused computation and shipping a small heap between machines all already exist in public code. Sofort must not position any of them as its invention.
- **How it would work:** Six counterexamples. quickjs-wasi does whole-VM snapshots with pending promises and host-callback rebinding. Vercel Workflow merged VM-memory snapshots. quickjs-rs snapshots whole heaps, and Deep Agents adds checkpoint deltas. xs-sandbox exports a `Uint8Array` heap that restores on another machine. Golem journals host calls and has `fork()`. dquickts and TimeTravelJS capture synchronous frames or offer browser history forks.
- **Evidence / numbers:** F: quickjs-wasi source version 3.6.3. F: Vercel Workflow snapshot storage merged 2026-10-01, with local, Postgres and Vercel World stores. F: xs-sandbox advertises a ~85 kB empty snapshot. Sources: https://github.com/vercel-labs/quickjs-wasi, https://github.com/vercel/workflow/pull/3250, https://github.com/coder-mike/xs-sandbox/blob/main/readme.md
- **Prior art / who has it:** Vercel Labs quickjs-wasi, Vercel Workflow, LangChain quickjs-rs / Deep Agents, coder-mike/xs-sandbox, Golem, Stencil dquickts, NDevTK TimeTravelJS.
- **Verdict:** KILLED as a novelty claim (I). The mechanism is occupied, so it must not be the positioning.

#### Finding: the remaining opportunity is a product and interoperability contract
- **What:** An independently usable, versioned capsule. It carries a parked program, pending tool identities, authority requirements and a replay position. It works through tested adapters in browser Workers, server runtimes and real edge deployments, with correct fork and effect-ownership semantics.
- **How it would work:** Package and specify what the libraries already make mechanically possible: format, adapters, broker semantics and conformance.
- **Evidence / numbers:** I: the survey found no mature product publicly demonstrating the whole contract as one supported feature. The report calls this a bounded finding, not proof that nobody has it privately.
- **Prior art / who has it:** Pieces are spread across Vercel, LangChain, Golem and Cloudflare (see below).
- **Verdict:** KEPT (the report's bet). It is the only open space found, and existing players could close it quickly.

#### Claim to avoid: "~100 KB" as a moat or size guarantee
- **What:** The ~100 KB gzip snapshot from the Oct 25 spike is a useful demo property, not a differentiator.
- **How it would work:** Heap size depends on the program, retained data, engine and shared base. The engine module, host adapters, tools and stored external data are extra artifacts.
- **Evidence / numbers:** F: xs-sandbox advertises a ~85 kB empty heap. Other projects compress or delta-encode snapshots.
- **Prior art / who has it:** xs-sandbox, Deep Agents deltas, Vercel compressed snapshots.
- **Verdict:** KILLED as a claim (I). Any universal fixed-size promise would be false for growing heaps.

#### Taxonomy: five kinds of "the same capability"
- **What:** Five capture classes that keep comparisons honest. (1) Journal recovery: rerun the code and feed it recorded results (Golem, Temporal, Restate, Inngest, DBOS). (2) Application checkpoint: explicit serialized data plus a recovery handler (Cloudflare fiber `stash()`). (3) Interpreter image: heap and continuations at a quiescent Wasm stack, the closest capsule comparison. (4) Machine/process image: E2B, Daytona, Modal, Morph, Blaxel. (5) Initialization image: Wizer, JS preinit, engine startup snapshots.
- **How it would work:** Classify each competitor by what it actually captures, not by what it calls a "snapshot".
- **Evidence / numbers:** I: the report's framing. ND means "no documented capability found", which is deliberately weaker than "impossible".
- **Prior art / who has it:** As listed per class.
- **Verdict:** Adopted as the report's comparison framework (I).

#### Taxonomy: three meanings of "fork"
- **What:** Starting another task with the same input is not a fork. Copying a journal prefix is an execution-history fork. Restoring one heap image into two instances is a memory fork.
- **How it would work:** History forks and memory forks are both useful. Neither one safely duplicates an external payment, TCP peer, browser DOM or database transaction by itself.
- **Evidence / numbers:** I.
- **Prior art / who has it:** Golem and DBOS (history fork). E2B, Daytona and Modal (machine-memory fork). Interpreter libraries ("I: clone").
- **Verdict:** Adopted as framework (I). Fork safety for effects is the hard part.

#### Vercel Labs quickjs-wasi
- **What:** Sandboxed JS in QuickJS-NG on Wasm. It captures a linear-memory image plus VM pointers and stack metadata, pending promises, binary persistence and rebinding of host callbacks.
- **How it would work:** Fork means restoring one image twice (I: clone). No transactional tool-fork contract was established.
- **Evidence / numbers:** F: hosts are browser, Node, Deno and Bun. F: no supported all-host edge migration matrix was found. F: MIT, source version 3.6.3. https://github.com/vercel-labs/quickjs-wasi
- **Prior art / who has it:** Vercel Labs.
- **Verdict:** Direct overlap. A public, fast-moving library and the closest JS/Wasm engine wrapper.

#### Vercel Workflow SDK
- **What:** A durable workflow event log. The QuickJS engine can save compressed, encrypted memory snapshots at suspension and then consume only the events that follow.
- **How it would work:** A snapshot plus an event cursor replaces full replay. Without snapshots it replays the whole history.
- **Evidence / numbers:** F: the memory snapshot interface and threshold are explicitly experimental, merged Oct 1. F: Apache-2.0 SDK, hosted World is separate. F: ND for live heap branching. https://github.com/vercel/workflow/releases, https://github.com/vercel/workflow/blob/main/packages/world/src/interfaces.ts
- **Prior art / who has it:** Vercel.
- **Verdict:** Direct overlap. Do not infer browser heap migration from its portable engine dependency.

#### Vercel durable-harness
- **What:** Makes coding-agent harness sessions, turns and model/tool calls durable over Workflow Worlds, with recovery from the event log.
- **How it would work:** Session and history durability. No documented fork of an arbitrary interpreter heap.
- **Evidence / numbers:** F: announced Oct 19. F: experimental package, 0.0.x, Apache-2.0. F: the source includes IndexedDB/browser storage work, but no whole-heap browser/server transfer contract. https://vercel.com/blog/making-every-harness-durable
- **Prior art / who has it:** Vercel.
- **Verdict:** Adjacent overlap at the protocol/session level.

#### Vercel Sandbox
- **What:** Firecracker-backed execution with persistent sandboxes, filesystem snapshots and disk-based continuation across sessions.
- **How it would work:** Filesystem branching and fork are supported. The inspected docs show no live memory fork.
- **Evidence / numbers:** F: commercial hosted service; filesystem persistence has shipped. https://vercel.com/kb/guide/vercel-sandbox-duration-and-persistence
- **Prior art / who has it:** Vercel.
- **Verdict:** A substitute at the filesystem tier, not a memory capsule.

#### Golem Cloud / self-hosted runtime
- **What:** A Wasm VM that logs every host interaction in an oplog. Re-execution rebuilds locals, closures and files. Optional application-state snapshots plus a filesystem baseline.
- **How it would work:** SDK `fork()` and history-prefix forks copy history and files, then recover the child.
- **Evidence / numbers:** F: server is BSL 1.1, becoming Apache-2.0 after four years. F: the managed Cloud is a Developer Preview. F: no browser executor for its full durable host ABI. https://learn.golem.cloud/v1.6/concepts/durable-execution, https://github.com/golemcloud/golem/blob/main/LICENSE
- **Prior art / who has it:** Golem.
- **Verdict:** Established durable runtime and the strongest semantic competitor (see the Golem finding below).

#### Cloudflare Workers
- **What:** JS/Wasm execution in V8 isolates. Ordinary isolate memory is transient.
- **How it would work:** ND for exporting or forking a live isolate heap. A Wasm guest can be portable on its own.
- **Evidence / numbers:** F: workerd is Apache-2.0; the managed platform is proprietary. https://developers.cloudflare.com/workers/runtime-apis/webassembly/
- **Prior art / who has it:** Cloudflare.

#### Cloudflare Dynamic Workers

- **How it would work:** Creates new child instances. They are not documented copies of an existing heap.
- **Evidence / numbers:** F: the loader is in Apache-2.0 workerd; there is no browser Dynamic Worker host. https://developers.cloudflare.com/dynamic-workers/
- **Prior art / who has it:** Cloudflare.

#### Cloudflare Durable Objects
- **What:** Addressed actors with durable storage. Hibernation discards in-memory state, and reactivation reruns the constructor.
- **How it would work:** You can create a new object or copy application data. ND for a live heap fork.

- **Prior art / who has it:** Cloudflare.

#### Cloudflare Code Mode

- **How it would work:** Only user-defined state can be cloned. ND for forking a heap continuation.

#### Temporal
- **What:** Durable workflows built from deterministic code plus an event history of activities, timers and signals. Replay rebuilds state.
- **How it would work:** Reset copies the history to a new run and terminates the original. There are never two concurrent live memory branches.

#### DBOS

- **Prior art / who has it:** DBOS.

#### Finding: Vercel is already implementing the underlying idea
- **What:** The 2026-03-07 Workflow RFC proposed running workflows in QuickJS-Wasm, saving the VM at suspension, restoring pending resolvers and applying only later events. The October implementation keeps replay as the correctness baseline.
- **How it would work:** `experimental_snapshots` is optional. Snapshot bytes and their event cursor are stored atomically. The threshold runtime saves compressed, encrypted images and normally requires an encryption key.
- **Evidence / numbers:** F (RFC author's figures, not measured here): fresh image ~256 KB; compression cuts it by ~60–70%. https://github.com/vercel/workflow/discussions/1298, https://github.com/vercel/workflow/pull/3251
- **Prior art / who has it:** Vercel.
- **Verdict:** KILLED for Sofort's narrow claim (I). "Save a JS await continuation in a Wasm image to avoid replay" is directly occupied. Vercel can assemble a broader offering, though its public pieces do not snapshot an entire native harness process.

#### Finding: fork by restoring twice is a small extension, not a barrier
- **What:** Restoring one image twice is an easy engine-level extension. The hard part of a production fork is deciding which branch may perform which external effect, and handling a tool that completed before its result was committed.
- **How it would work:** In quickjs-wasi, host callbacks must be rebound, and the host has to rebuild pending tool delivery separately.
- **Evidence / numbers:** I.
- **Prior art / who has it:** quickjs-wasi.
- **Verdict:** I. Cheap memory copying is not the moat; effect-ownership semantics are.

#### Finding / design: wrap the quickjs-wasi serializer with module identity
- **What:** quickjs-wasi format v2 stores linear memory, stack/runtime/context pointers and extension-loading metadata. Its header is versioned but carries no hash of the engine module.
- **How it would work:** Restore reinstantiates extensions at their recorded memory/table offsets before copying memory. Per the report, a transferable capsule should wrap this with module identity and broker metadata.
- **Evidence / numbers:** F: serializer inspected directly. https://github.com/vercel-labs/quickjs-wasi/blob/main/src/index.ts
- **Prior art / who has it:** Vercel Labs.
- **Verdict:** KEPT as a design requirement (I). Versioned serialization alone does not guarantee interoperability across versions.

#### Finding: LangChain occupies the agent-framework route
- **What:** quickjs-rs only snapshots at a quiescent point: no in-flight `eval_async` and no pending async host calls. Restore checks the guest build identity, and images are treated as trusted producer output. Deep Agents keeps full images with binary-patch deltas and periodic anchors, plus snapshot authentication bound to thread identity.
- **How it would work:** A pending guest promise is different from an active host coroutine or callback crossing the embedding boundary. That matters for Sofort's "parked on a tool promise" API.
- **Evidence / numbers:** F (upstream figures, not head-to-head): full heap images ~1.4 MB in its use case; successive patches ~200 B–1 KB. https://github.com/langchain-ai/quickjs-rs, https://github.com/langchain-ai/deepagents/blob/main/libs/partners/quickjs/langchain_quickjs/_snapshot.py
- **Prior art / who has it:** LangChain.
- **Verdict:** I. Without a better embedding/API story, a capsule library could become replaceable plumbing under LangGraph. LangChain is also a plausible adopter if Sofort supplies a supported JS/browser/edge host layer.

#### Finding: XS, Stencil and TimeTravelJS remove most novelty claims
- **What:** XS Sandbox drains runnable promise jobs synchronously before returning. It rejects `snapshot()` while active, copies the snapshot bytes out, and restores into a new sandbox. dquickts serializes semantically (native-function registry, indexes instead of pointers, synchronous frames after a safepoint unwind). TimeTravelJS makes QuickJS stackless, giving instruction/line-level snapshots and branches in the browser.
- **How it would work:** XS uses a quiescent image API. dquickts is a substantial QuickJS fork with broad serializer coverage. TimeTravelJS applies a more general suspension transform than the spike's empty-Wasm-stack boundary, and captures an embedded DOM model, not the real browser DOM.
- **Evidence / numbers:** F: README, wrapper and source inspected. F: dquickts limits are the same build/word size, no host resources without custom hooks, and trusted input only. https://github.com/coder-mike/xs-sandbox/blob/main/src/index.mts, https://github.com/stencil-hq/dquickts/blob/master/quickjs-snapshot.c, https://github.com/NDevTK/TimeTravelJS
- **Prior art / who has it:** coder-mike, Stencil, NDevTK.
- **Verdict:** I. XS's size is an empty-heap example, not proof of pending-tool/fork/edge correctness. dquickts may be more expressive than an await-only capsule but is a different maintenance bet. Do not read a new repo's README as production-ready.

#### Finding: pi-world is close to the "branchable worlds" demo
- **What:** pi-world uses quickjs-wasi images and checks proposed program changes against checkpoints. Durable pauses, forks and replay are labelled designed or spiked.
- **How it would work:** An agent modifies a persistent heap; snapshots are its revision history.
- **Evidence / numbers:** F: current README. https://github.com/igouss/pi-world
- **Prior art / who has it:** igouss/pi-world.
- **Verdict:** NARROWED (I). Compete on a completed execution/migration contract, not on the idea of an agent modifying a persistent heap.

#### Finding: Golem is the strongest semantic competitor
- **What:** Golem records external interactions at the Wasm-host boundary, including clock, random and concurrent completion order. Normal recovery reruns against the oplog, with `fork()` of history and files and optional user snapshots.
- **How it would work:** "Resumes mid-function with memory/call stack/files" is a real substitute even though recovery is not a flat heap restore, because the user may not care whether the heap was copied or rebuilt. ### 03-roadblocks: Early roadblocks: QuickJS/Wasm capsules in the first 2–6 weeks
Lens: what stops a bounded, portable QuickJS-in-Wasm capsule backend from becoming a product in its first 2–6 weeks. The report ranks eight roadblocks by severity, using local measurements (M4 Pro, Node 24.22.1, Chromium 152, local workerd) and sourced platform facts. Headline: the portable continuation already works. The release blockers are resource enforcement (the spike's 16 MiB QuickJS cap accepted 31 MiB), the lack of an independent kill path, and an undefined tenant failure boundary. Snapshots also grow far past the 100 KB demo figure. The one bet: build the portable software tier with hard resource enforcement, explicit guest compatibility, checkpoint-size budgets and a documented tenant boundary. Verdict: **GO-WITH-CHANGES**.

#### Priority order: de-risk resource enforcement first
- **What:** The report's overall ranking of eight roadblocks: (1) memory/stack/runaway execution, (2) tenant fault containment versus density, (3) real heaps and snapshot growth, (4) replay semantics and build compatibility, (5) interpreter throughput, (6) npm/Node expectations, (7) Cloudflare restrictions, (8) JSPI/Asyncify dependence.

#### Claims to avoid / rejected in this report

- **"Dynamic Wasm is impossible on Cloudflare"** — wrong; Dynamic Workers accept `{wasm: ArrayBuffer}`.
- **Old 3/10 MB compressed Worker bundle limits** — outdated; the current limit is 64 MiB uncompressed.
- **Blanket JSPI support claims (e.g. the V8 explainer's Firefox statement)** — conflict with current compat data; probe behavior instead.
- **"Exact replay" across versions/engines** — needs a pinned, restricted deterministic profile.
- **Hardware-grade isolation for the Wasm tier** — no protection from V8 escapes or side channels; workerd and Node permissions are not hardened sandboxes.

### 04-techstack: The right tech stack for portable capsules
Lens: pick each layer of the capsule stack (guest engine, build toolchain, module format, suspension mechanism, TS host/scriptc packaging, snapshot encoding/storage, differential testing), backed by a small local Bellard-vs-ng benchmark on an Apple M4 Pro. Headline finding: quickjs-ng honoured the 16 MiB engine allocation limit that the existing Bellard port silently missed, which outweighs ng's ~90 KB size and ~5% tool-path cost. A controlled Node startup snapshot also showed that "V8 cannot snapshot mid-await" is wrong as a blanket claim. What V8 lacks is a supported, portable checkpoint interface. The bet: qualify quickjs-ng 0.17.0 as a single-memory wasm32 core reactor built with wasi-sdk/clang, driven by a TS host that gets control back at guest `await` boundaries (no JSPI or Asyncify on the normal path). Checkpoints are versioned and content-addressed, zstd-3 for server storage and gzip for exchange. Verdict: **GO-WITH-CHANGES**. ng cross-host checkpoint qualification, hard resource enforcement and host entrypoint separation come first. scriptc stays the Mac tool compiler, but its Wasm translator is not the isolation boundary.

#### Checkpoint execution contract (freeze before choosing wrappers)
- **What:** Fix a strict execution contract before adopting any convenient wrapper. One instance owns one QuickJS runtime/context. Durable state holds no native FS/network APIs, shared memory, threads, mutable function table, externally owned ArrayBuffers, host object references or `externref` values.
- **How it would work:** The interpreter and bridge are compiled once and guest JS is evaluated inside them. The Promise resolver and continuation stay in linear memory. A synchronous `emit(ptr,len)` import copies bounded bytes into a host queue and returns, and the host runs tools only after the outer Wasm call returns. A bounded `pump` drains jobs until completion, a resource yield or a wait for input. Checkpoints are taken only when all Wasm frames have returned and the job queue is quiescent.
- **Evidence / numbers:** F: the Oct 25 spike (Bellard 2026-06-04) parked on a tool Promise in Wasmtime and restored into Node, Chromium, local workerd and a local Dynamic Worker. Closures, cycles, Map and typed arrays survived, and forks diverged without re-emitting the pending request. Reactor 966,584 B; parked 2 MiB image ~100 KB gzip; Asyncify build 1,517,095 B. Sources: `portability/02-wasm.md`, `~/sofort-local-evidence/portability-wasm-2026-10-25/`.
- **Prior art / who has it:** Sofort's own Oct 25 portability spike.
- **Verdict:** KEPT. This is the foundational design every later layer assumes. The full migration matrix was not re-run for ng.
- **Kill test / first proof:** Port the canonical tool/bootstrap protocol to ng's minimal reactor and run the directed Node–Chromium–workerd restore/fork matrix, with Bellard as a pinned regression control.

#### Memory alone is not the whole checkpoint
- **What:** Finding: Wasm memories, globals and tables are separate state, and JSPI continuations are not exposed as memory bytes. A memory dump alone is not a complete checkpoint in general.
- **How it would work:** The checkpoint records memory length and contents, every supported mutable global (including `__stack_pointer`), stable host protocol state and the journal cursor. The immutable table is rebuilt from the exact module. Unsupported state is rejected, not silently dropped.
- **Evidence / numbers:** F: [Wasm JS interface 2026-10-27 draft](https://www.w3.org/TR/2026/CRD-wasm-js-api-2-20261027/), [V8 JSPI blog](https://v8.dev/blog/jspi).
- **Prior art / who has it:** W3C Wasm JS API spec; V8 JSPI.
- **Verdict:** KEPT as a format requirement. It feeds the v1 manifest.

#### Positioning constraint: no memory-superiority claims
- **What:** Claim to avoid. The Wasm spike's Mac RSS does not show memory superiority over jitk or Hyperlight. This tier is a software-isolated portable tier, not portable native jitk RAM.
- **How it would work:** Present capsules as a separate software-isolated tier that supports demo.md §§9–10's "file-like computers" without borrowing the hardware tier's guarantees.
- **Evidence / numbers:** F: Linux same-host results (Oct 27) put jitk shard and Hyperlight at about the same marginal memory, ~0.5 MiB per VM for small workloads (`jitk/bench/RESULTS-LINUX-MEMORY-2026-10-27.md`). The usermode and hardware-reach reports describe different isolation/ISA constraints.
- **Prior art / who has it:** Hyperlight (comparison point).
- **Verdict:** CLAIM TO AVOID. No memory win follows from the evidence.

- **What:** Finding: under the same 16 MiB `JS_SetMemoryLimit`, the selected Bellard port's engine limit is ineffective while ng's works.

#### Plain V8 awaited-closure startup snapshot (counterexample)
- **What:** Finding and claim to avoid: "V8 cannot snapshot mid-await" is inaccurate as a categorical claim.
- **How it would work:** `v8-await.cjs` leaves a Promise unresolved, then is built with `node --build-snapshot`. `startupSnapshot.setDeserializeMainFunction` resolves it with `35` in the restored process.
- **Evidence / numbers:** M: on Node 24.22.1 the restored process prints `resumed 42` and the captured object survives. This is a startup-snapshot construction experiment, not a checkpoint of an ordinary running Node worker.
- **Prior art / who has it:** Node `node:v8` startupSnapshot API.
- **Verdict:** CLAIM TO AVOID ("V8 can't snapshot mid-await"). The correct claim is that V8 lacks a supported, portable cross-host checkpoint interface.

#### V8 public interfaces do not give a portable checkpoint
- **What:** Finding: none of V8's public snapshot/serialization interfaces captures a running native JS stack, OS/tool operations, host scheduling or browser APIs as a portable blob.
- **How it would work:** `v8.serialize` is structured-clone-like and does not handle functions or closures. DevTools heap snapshots are diagnostic JSON. Node startup APIs work only during snapshot building, with callbacks to reacquire resources. C++ `SnapshotCreator` makes startup blobs, and the context serializer expects an empty microtask queue. Snapshots are trusted and build/version dependent. A purpose-built native V8 embedder could serialize selected quiescent contexts server-side, but web JS cannot call `SnapshotCreator` and browsers/workerd expose no equivalent.
- **Evidence / numbers:** F: [Node V8 APIs](https://nodejs.org/api/v8.html), [SnapshotCreator](https://v8.github.io/api/head/classv8_1_1SnapshotCreator.html), [context serializer](https://github.com/v8/v8/blob/main/src/snapshot/context-serializer.cc).
- **Prior art / who has it:** V8, Node.
- **Verdict:** NARROWED. A native V8 embedder is a meaningful server-only alternative. A guest engine in Wasm buys control of the durable heap and ABI independent of the host's V8 build. Checkpoint only at supported guest boundaries, never "at any instruction".

#### Build toolchain: wasi-sdk/clang core reactor
- **What:** Build the guest with pinned wasi-sdk/clang as a reactor with `_initialize`, bridge exports, one exported memory and explicitly listed mutable globals.
- **How it would work:** Ship a core module with minimal imports. WASI Preview 1 is a libc convenience, not the capability model. Unneeded `fd_*` imports are replaced with explicit failures or removed. Time, entropy and logging go through journaled capsule imports. Interpreter, bridge and bootstrap are reproducible artifacts with recorded source/toolchain hashes.

#### Metering that survives a compromised guest engine

#### Uniform instruction budget (block metering)
- **What:** Instrument basic blocks/loop backedges in the final module with a private fuel counter or trusted host decrement import, for a budget that does not rely on QuickJS.

- **Verdict:** NARROWED. Qualify block metering for hostile-engine fuel, and do not adopt wasm-metering as a security dependency. Wasmtime fuel/epochs/store limits are the RUNNER-UP: strongest convenience for a native host, but not portable.

#### Minimal handoff protocol for the demo
- **What:** A deliberately narrow, reviewable five-step supervised move.
- **How it would work:** (1) The source evaluates the entry once, reaches exactly one pending call and is pumped to quiescence. - **Verdict:** NARROWED. It proves a supervised move, not a fault-tolerant distributed ownership protocol. Real crash recovery needs lease/fencing semantics, crash-window tests and pending-effect ownership.
