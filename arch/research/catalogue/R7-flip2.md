## Round 7 — AI compute, compilers × Code Mode, all of CS — `flip2/`
The second flip round used the same template and labels and pointed the method at three directions. First, the gritty parts of AI: GPU kernels, ML compilers, distributed training, serving, numerics and data pipelines, where an agent could be hooked into the loop against an oracle. Second, old compiler/PL ideas that work again because models write code, both compiler techniques applied to agent-written (Code Mode) programs and LLMs proposing inside old checking machinery. Third, everything else in CS. Each agent idea also had to state how the agent could cheat its check. Overall verdict: the AI-compute layer is extremely crowded. Kernels (NVIDIA, AMD, Meta KernelAgent and others) offer only a small addressable share of runtime. Every obvious distributed-training and serving idea is occupied, mostly by old HPC ideas that won decades ago. Every LLM-proposes/old-machinery-checks pairing has already been tried. Reward hacking is documented (kernels that read reference outputs; `allclose(1e-2)` accepting an FP8 downgrade; greedy agent loops keeping mostly noise). The sweep found the obvious combination occupied in 12 of 14 areas, usually by whoever owns the oracle. That gives the four-gate flip rule: the idea died of per-case labour, an independent cheap oracle exists, the artefact runs without the model, and the owner of the oracle wins. Bets were all go-with-changes and narrow: a maintained CUDA→AMD operator port (01), recovery equivalence across training-stack changes (02), maintained translation validation of agent rewrites (03), an evidence gate for agent-run ML experiments (05), and agent-written OpenZL format descriptions (06). The strongest Sofort-relevant finding is labelled Code Mode (04): Code Mode makes Denning-style information-flow control applicable, and no shipping Code Mode runtime enforces flow labels.

### 01-kernels: GPU kernels and ML compilers: the economics flipped, and the obvious territory is occupied
Desk research (no GPU experiments; all performance results are F, not M) on agents that write, tune, port and maintain accelerator kernels against an executable reference. Headline: the GrowOS pattern fits kernels very well (agent proposes, frozen reference operator supplies numerics, compilers/sanitizers/hardware reject bad candidates), but it is already an industry: NVIDIA, AMD, Google, Meta/PyTorch, Modular, Standard Kernel, Makora and others. No candidate clears round one's "verified pain + proven old fix + no existing product" bar, and no defensible fleet-wide share of GPU time far below its roofline was found. The ONE bet is a maintained, independently accepted CUDA→AMD port of one actual customer's missing operator family, with an unseen upstream revision as the deciding test. Verdict: go-with-changes, i.e. a conditional customer-specific two-week go/no-go, explicitly not a general kernel company.

#### PHiPAC/ATLAS: agents extend the generator, empirical search chooses (idea 1)
- **What:** Revive portable performance through generated variants plus measured selection. The agent adds missing epilogues, layouts and target primitives to the generator instead of just picking a tile size.
- **How it would work:** The agent writes a generator extension. Frozen reference tests and compiler legality checks validate the generated instances, and speed is measured. It can cheat by narrowing shapes, weakening precision, or preprocessing outside the timer, so the report's acceptance boundary applies.
- **Evidence / numbers:** F: Helion's 2026 LLM-guided search shows cheaper candidate selection, and Inductor already does empirical backend/config selection. I/E: a 2× improvement on 10% of exposed runtime gives 5% savings. Charge against realized gain, not total accelerator spend. Sources: [PHiPAC 1998 report](https://www2.eecs.berkeley.edu/Pubs/TechRpts/1998/5682.html), [ATLAS](https://math-atlas.sourceforge.net/faq.html), [Helion LLM autotuning](https://pytorch.org/blog/from-minutes-to-seconds-llm-guided-autotuning-for-helion-kernels/).
- **Prior art / who has it:** Inductor, Helion, TVM, NVIDIA agents, AMD GEAK.
- **Verdict:** NARROWED. The old method worked, and the lasting cost is expanding and maintaining the expert representation. Another general autotuning agent is rejected. Generic tile-prompting gets commoditized, while libraries, device access and reusable accepted extensions keep their value.
- **Kill test / first proof:** E: one unsupported fused epilogue over five shape families on an existing device. The agent extends an existing generator, compared at equal search budget against native autotuning and an ordinary coding agent, with a dtype/layout change held out. Killer reply: "Max-autotune already finds that kernel." Kill if the strongest existing generator matches it, or if total setup/maintenance labour does not fall by at least 50%.

#### FFTW planner/genfft + SPIRAL: grow an algebraic codelet vocabulary (idea 2)
- **What:** Agents add new codelets, algebraic decompositions or target lowerings to a decomposition/generation/empirical-choice system, under independent checks.
- **How it would work:** The agent proposes a leaf or a rewrite. Exact symbolic checks (where supported), a direct high-precision transform on small sizes, and full-size numerical tests judge it. The oracle is strong algebraically and moderate numerically. Failure/cheat modes: wrong sign/normalization/stride conventions, overfitting to real-only inputs, or substituting an unstable formula.
- **Evidence / numbers:** F: FFTW already generated codelets because hand-writing them was impractical. The planner measures compositions, and genfft generates the leaves. F: Zhang et al. 2025-01-15 lift GPT-generated FFT code into SPIRAL specifications using symbolic/theorem-proving machinery. E: a 20% kernel win (1.2×) on a 5% region saves only 0.83%. Sources: [genfft PLDI 1999](https://www.fftw.org/pldi99.pdf), [SPIRAL 2005](https://www.spiral.net/doc/papers/IEEE_2005.pdf), [Semantics lifting for FFT](https://arxiv.org/abs/2501.09201).
- **Prior art / who has it:** FFTW, SPIRAL, the 2025 LLM-to-SPIRAL lifting work, cuFFT/rocFFT as practical baselines.
- **Verdict:** NARROWED. There is no evidence of a broad unsupplied FFT market. The only plausible entry is a private fused transform.
- **Kill test / first proof:** E: one existing customer's transform-plus-windowing pipeline at three nontrivial sizes, with independent sign/normalization/complex-data tests. The agent generates one backend extension. Count generation, planning, temporary buffers and repeated execution against a tuned vendor composition. Killer reply: "You rediscovered an existing library plan and excluded planning/copies." Kill below a 10% full-pipeline improvement or if no real unsupported workload exists.

#### OSKI: specialize irregular operators to structure, not just shape (idea 3)
- **What:** Agents implement missing segmented, sparse, embedding, graph and ragged kernels, with guarded structural assumptions adapted to the user's data and machine.
- **How it would work:** The agent picks or creates layouts and kernels. Reference output, index/duplicate semantics, backward tests and end-to-end performance decide. The oracle is strong for integer/indexing semantics and moderate for reductions. Cheat paths: assuming sorted/unique indices, omitting empty segments, or timing the lookup without the per-batch sort/repack.
- **Evidence / numbers:** F: OSKI notes that the matrix may be unknown until runtime and that tuning can be nontrivial. F: Meta's production account names custom ranking operators across model × hardware as a scaling problem. E: at f = 0.4, s = 1.5 and full coverage, the saving is 13.3% (a scenario, not a measurement). Sources: [OSKI 2005](https://bebop.cs.berkeley.edu/pubs/jop2005-SciDAC-OSKI.pdf), [Meta KernelEvolve](https://engineering.fb.com/2026/04/02/developer-tools/kernelevolve-how-metas-ranking-engineer-agent-optimizes-ai-infrastructure/), [SparseTIR](https://arxiv.org/abs/2207.04606).
- **Prior art / who has it:** Meta KernelEvolve, AMD GEAK, SparseTIR, specialist sparse libraries.
- **Verdict:** KEPT (#2). Structure-specific kernels can hit a concentrated expensive region, and the old format/tuning ideas transfer. It can still die because Meta/AMD and specialist libraries cover much of the ground, and repacking/skew/backward costs can erase the gain. Target an uncatered private op/structure, not embeddings in general.
- **Kill test / first proof:** E: freeze one real segmented gather/reduce or sparse gating op, including duplicates/unsorted IDs and a backward contract, with degree/skew and shape families held out. Compare vendor sparse primitives, compilation, a coding agent and the structured loop, and time repacking and gradients. Killer reply: "Your training distribution hid the slow/incorrect skew and the repack cost." Kill if existing operators remove the blocker, if any accepted implementation corrupts holdout results, or if under 5% full-workload improvement remains after costs.

#### Halide: agents search schedules inside a semantic boundary (idea 4)
- **What:** Separate the algorithm from the schedule. The agent writes schedules or supported primitive extensions, and the compiler preserves the declared computation.
- **How it would work:** The agent changes scheduling decisions. Legality, compilation, hidden reference tests and hardware runs check them. Cheats: modifying the algorithm instead, treating reduction reassociation as exact equivalence, or excluding layout conversion.
- **Evidence / numbers:** F: Halide autoschedulers already existed (Mullapudi 2016; Adams 2019 with learned costs/tree search, beating expert schedules). F: the Helion TPU backend was documented with Google on 2026-07-23. I/E: a better pilot metric is at least half the engineering time saved, not beating a library on a hand-picked shape. Sources: [Halide 2012](https://people.csail.mit.edu/jrk/halide12/), [Adams 2019 autoscheduler](https://halide-lang.org/papers/autoscheduler2019.html), [Helion on TPU](https://pytorch.org/blog/helion-on-tpu-towards-hardware-heterogeneous-kernel-authoring/).
- **Prior art / who has it:** Halide autoschedulers, Helion, Inductor, TVM, agent-guided DSL search.
- **Verdict:** KEPT (#3, jointly with idea 7, as a "reusable checked compiler/generator extension"). It is most likely an upstream contribution or vendor engagement. A new general Halide-plus-chat product is rejected. If the DSL cannot express the best algorithm, schedule search hits a ceiling.
- **Kill test / first proof:** E: a kernel whose existing DSL lowering fails on an unsupported layout or op. Add one lowering with an agent, keep the algorithm frozen, and hold out five shape/layout families, compared against an expert using the autoscheduler and a normal coding agent. Killer reply: "This is already a Helion backend patch." If that is the whole differentiation, kill the standalone product at once. Keep the upstream patch if it measurably reduces future maintenance.

#### Polyhedral compilation: agents make source analyzable, dependence analysis makes schedules legal (idea 5)
- **What:** Agents extract or repair an affine-analyzable representation, or implement missing target mappings. PLuTo/Polly/TC-style dependence analysis authorizes the transformations.
- **How it would work:** The agent proposes a lift plus entry guards. Source/reference differential tests check the lift, and dependence analysis validates schedules. The oracle is strong inside a valid extracted model and weak outside it. Cheats: asserting no aliasing, deleting a data-dependent branch, or specializing a dynamic index to fixture values. Unsupported regions must be rejected, not given invented legality.
- **Evidence / numbers:** F: the Polly paper names syntactic-extraction restrictions and poor integration with target optimizers. F: TC already combined a tensor language, a polyhedral JIT and autotuning. I/E: a one-off 5% microbenchmark win rarely funds a new compiler frontend/backend. Sources: [PLuTo](https://github.com/bondhugula/pluto), [Polly 2011](https://polly.llvm.org/publications/grosser-impact-2011.pdf), [Tensor Comprehensions](https://arxiv.org/abs/1802.04730).
- **Prior art / who has it:** PLuTo, Polly, Tensor Comprehensions, structured IRs in current tensor compilers.
- **Verdict:** NARROWED. No unoccupied revival exists for a universal affine kernel compiler. What gets revived is expert extraction/backend labour, not the dependence mathematics. A compiler team may pay for a recurring unsupported pattern.
- **Kill test / first proof:** E: three regular private kernels that current extraction rejects. The agent produces guarded analyzable variants, tested with adversarial alias/stride cases, and these are compared against a direct compilation/DSL rewrite on total human setup plus full-workload performance. Killer reply: "The guards silently excluded real production cases." Kill if guarded coverage is too low, if checks cannot validate the lifting, or if an ordinary-agent direct rewrite is cheaper.

#### STOKE: search instruction sequences under an independent checker (idea 6)
- **What:** Use an LLM as a high-quality proposal operator for PTX/assembly snippets or carefully bounded kernels, in place of STOKE's MCMC.
- **How it would work:** The agent proposes an instruction sequence. Symbolic equivalence, concurrency checks, numerical tests and hardware timing decide. The oracle is strong for restricted exact regions and partial for whole floating-point GPU kernels. Cheats: exploiting missing instruction semantics, real-vs-float differences, unsafe synchronization, or a verifier extension that assumes what it needs to prove.
- **Evidence / numbers:** F: STOKE (ASPLOS 2013) handled loop-free x86 and explicitly gave up completeness. F: AlphaEvolve's low-level win, and Costa et al. "AI as a Compiler" (Triton→PTX at 0.83–3.34× autotuned Triton, extending Volta but not claiming the extensions sound or complete). Sources: [STOKE](https://theory.stanford.edu/~aiken/publications/papers/asplos13.pdf), [AI as a Compiler](https://arxiv.org/html/2609.36800v1), [Volta](https://arxiv.org/abs/2511.12638).
- **Prior art / who has it:** Standard Kernel's PTX work, AlphaEvolve, AI as a Compiler, Volta.
- **Verdict:** NARROWED. Another general GPU superoptimizer is rejected. A verified model of an unsupported instruction might be a good research contribution, since better search raises demand for checkers and maintained trusted semantics are hard to replace.
- **Kill test / first proof:** E: a small integer packing/indexing region with executable semantics. The agent proposes replacements, a solver checks all bounded inputs, and a trusted runner benchmarks them inside a real kernel. Extend to one floating-point case only with an explicit approximation contract. Killer reply: "You verified real arithmetic or a sketch, not the executed instruction sequence." Kill any unsupported proof claim. Kill the product if integration erases the win or existing compiler passes already capture it.

#### TVM/Ansor/MetaSchedule: agents grow reusable search rules (idea 7)
- **What:** Agents propose reusable schedule rules, intrinsics or cost features, accepted through independent semantics and held-out workloads.
- **How it would work:** Compiler legality plus independent reference tests gate the rules, and hardware runs on held-out graphs judge cost. Cheats: improving the training operator set while breaking another shape, or biasing the cost model toward uncharged conversion work.
- **Evidence / numbers:** F: Ansor already addresses restricted search spaces, and MetaSchedule already targets letting experts extend those spaces, so "autotuning cannot generate its space" is too broad. I/E: proposed pilot criterion is that at least three unseen op/shape families benefit from the same extension. Sources: [TVM OSDI 2018](https://www.usenix.org/conference/osdi18/presentation/chen), [Ansor OSDI 2020](https://www.usenix.org/conference/osdi20/presentation/zheng), [MetaSchedule NeurIPS 2022](https://proceedings.neurips.cc/paper_files/paper/2022/hash/e894eafae43e68b4c8dfdacf742bcbf3-Abstract-Conference.html).
- **Prior art / who has it:** the TVM lineage, Helion hybrid search, GEAK/AKA-style optimization-knowledge libraries.
- **Verdict:** KEPT (#3, jointly with idea 4). An accepted primitive/rule can amortize across many unseen programs with less unchecked agent authority. The natural owners are the existing compiler projects, so there is no vacant generic agentic-autotuner category. Work with an existing compiler on a real missing target feature.
- **Kill test / first proof:** E: one missing intrinsic or schedule idiom with an existing compiler test corpus, an agent-authored rule and held-out operators, against ordinary autotuning at equal budget. Count compile/search overhead, source complexity and expert interventions. Killer reply: "Your rule is a template keyed to the benchmark names." Kill if gains fail on held-out families, if legality needs special pleading, or if an existing rule already covers it.

#### Systolic arrays: map computation to existing accelerators, not a new chip per prompt (idea 8)
- **What:** Agents generate tiling, pipelining, layout and DMA schedules for existing matrix engines (e.g. TPU via Pallas) and the vector/scalar work around them.
- **How it would work:** The agent writes Pallas/layout/DMA schedules. Reference JAX/PyTorch semantics, interpreter checks, device tests and pipeline/resource checks decide. The functional envelope is strong, and performance portability is moderate. Cheats: excluding transposes/DMA, using the wrong accumulation precision, or checking in the interpreter while timing a different lowered artifact.
- **Evidence / numbers:** F: Pallas TPU docs warn that unnatural patterns may need slow emulation. F: the Helion/Google TPU backend reports a selected attention result of 838 TFLOPs, about 79% of one tensor core's peak on TPU v7 (July 2026). Sources: [Kung/Leiserson 1978](https://www.eecs.harvard.edu/htk/static/files/1978-cmu-cs-report-kung-leiserson.pdf), [JAX Pallas TPU details](https://docs.jax.dev/en/latest/pallas/tpu/details.html), [Helion on TPU](https://pytorch.org/blog/helion-on-tpu-towards-hardware-heterogeneous-kernel-authoring/).
- **Prior art / who has it:** Google/Pallas, AlphaEvolve, Helion, target-specific compiler teams.
- **Verdict:** NARROWED. Systolic arrays did not die. The software opportunity is unsupported or irregular mappings, so pick a missing operator, not "bring TPUs to PyTorch". Bespoke silicon remains constrained by capital and hardware.
- **Kill test / first proof:** E: on already accessible TPU hardware, port one useful custom masked/block-sparse op with a frozen envelope against a compiled JAX baseline. Hold out a mask/shape regime and measure layout conversion and forward/backward memory. Killer reply: "XLA/Helion already lowers it, or your sparse workload was secretly dense." Kill if no real blocker remains or full target execution is no better than the existing stack.

#### TASO/Tensat: models propose rewrite rules, they do not declare equalities (idea 9)
- **What:** Agents propose missing tensor-graph rewrites or equality-saturation search strategies, and checked semantics authorize them.
- **How it would work:** The agent suggests a rewrite/strategy. A proof/solver or trusted rule derivation checks the equality, and measurements check extraction. Cheats: real-number reassociation under IEEE arithmetic, losing a mask, assuming no aliasing, or optimizing a cost proxy instead of runtime. A statement in an e-graph does not prove that the rewrite which introduced it was valid.
- **Evidence / numbers:** F: TASO reports exponential limits on substitution generation, and Tensat addresses phase ordering. F: LGuess (2025-11-01) and EggMind (2026-04-19; transfers strategies to an XLA-based compiler) already do LLM-guided equality saturation. F: EqiForge (2026-09-11) unifies tensor algebra and tiled execution in an equality-saturation optimizer. I/E: a pilot should demand at least a 5% full-block improvement over a tuned compiler. Sources: [TASO](https://www.cl.cam.ac.uk/~ey204/teaching/ACS/R244_2024_2025/papers/jia_SOSP_2019.pdf), [EggMind](https://arxiv.org/abs/2604.17364), [EqiForge](https://arxiv.org/abs/2609.12330).
- **Prior art / who has it:** TASO, Tensat, LGuess, EggMind, EqiForge.
- **Verdict:** NARROWED. Cheap domain-specific strategy writing is a real flip, but it has direct competitors. The semantics and extraction problem remain useful, and a thin agent wrapper does not.
- **Kill test / first proof:** E: a small typed tensor IR or an existing e-graph, three private operator blocks, agent-proposed rules with shape/precision side conditions, and unseen graph compositions. Exclude arbitrary user code, and inspect extraction for recomputation and peak memory. Killer reply: "Your equalities are over reals and your deployment is low precision." Kill if accepted rules violate the deployed contract, extraction costs explode, or existing compiler fusion matches the whole-block result.

#### Maintained cross-vendor kernel compatibility: grow the missing behaviour, not the syntax translation (idea 10)
- **What:** For one named workload, an agent closes the semantic and performance gaps that HIPIFY-style translation leaves, then keeps them closed through upstream change. This is the closest GrowOS analogue.
- **How it would work:** The agent picks a target-appropriate implementation instead of imitating line by line. Reference values and gradients, edge cases, alias/mutation/stream contracts, full-application tests and per-target timings check it, against a frozen reference. The maintenance artifact records: the frozen reference/version, the op contract and preconditions, implementation/compiler/device identity, the accepted envelope, numerical/safety evidence, the benchmark recipe, the dispatch guard and fallback, and known exclusions. Cheats: narrowing the envelope, silently dispatching to CPU/source hardware, dropping backward support, or making the target baseline artificially weak.
- **Evidence / numbers:** F: HIPIFY docs leave unsupported libraries and performance rework to developers. F: HipKittens (Nov 2025) documents differences in memory access, scheduling and chiplet placement. F: Triton supports NVIDIA/AMD, Pallas GPU/TPU, and MLX custom Metal kernels. These are different execution models, not interchangeable backends. E: a $10k–25k follow-on pilot is a price hypothesis, not observed willingness to pay. Sources: [HIPIFY](https://rocmdocs.amd.com/projects/HIPIFY/en/latest/index.html), [HipKittens](https://github.com/HazyResearch/HipKittens), [McKeeman differential testing 1998](https://www.cs.tufts.edu/comp/150FP/archive/bill-mckeeman/DifferentailTesting.pdf).
- **Prior art / who has it:** HIPIFY, Helion, Triton, Mojo/MAX (Modular), Meta KernelEvolve, AMD, specialist startups. ThunderKittens/HipKittens/ThunderMittens on the target-primitive side.
- **Verdict:** KEPT (#1, the ONE bet, conditional). It has a real unsupported behaviour, an executable original, a bounded target and recurring repairs, and a deployment can be valuable even without beating CUDA. It can still die because cross-vendor agents already exist, no private blocker or buyer has been shown, and toolchain/hardware support may dominate the labour. The report claims no vacant general market. Better models make ports cheap for everyone, so the remaining value is recurring integration and acceptance of private operator changes.
- **Kill test / first proof:** E: one engineer, two weeks.
  - Days 1–2: find a sponsor with a reproducible blocked deployment and source/target hardware. Stop if HIPIFY/Helion/Mojo/an ordinary agent already removes the blocker.
  - Days 3–4: freeze the contract plus three holdouts (shape/structure families, adversarial numerics, a later upstream change), and seed wrong mutants.
  - Days 5–9: run budget-matched tracks: existing tools plus a normal agent versus structured fault→propose→independent-check→accept.
  - Days 10–12: reveal the upstream change and repair it without editing the oracle.
  - Days 13–14: reproduce on the deployment path.
  - Continue only if: the blocker is removed, there are zero accepted semantic failures in the untouched holdout, the mutants are rejected, expert time including setup falls at least 50%, and either a previously unavailable deployment works or full-workload economics improve by at least 5%.
  - Killer reply: "HIPIFY plus my existing agent and tests already does that; your remaining problem is drivers, deployment, and support."

#### Independent acceptance boundary against evaluation defeat (cross-cutting component)
- **What:** A trusted, independent judge for agent-written kernels. Semantics are frozen before optimization, and the agent can edit only implementation artifacts, not reference code, tolerances, hidden generators or release rules. The report calls this the most broadly useful technical component, but not an undiscovered business.
- **How it would work:** The setup has these parts.
  - **Oracles:** four distinct ones: function (frozen reference over held-out values, layouts and shape families), numerics (op-specific error budgets, no universal atol/rtol), safety (sanitizers, poisoned buffers, mutation checks, which are partial) and performance (trusted timing on the intended device and full workload).
  - **Execution:** a narrow buffer ABI, with reference outputs never in candidate-accessible memory.
  - **Validation and timing:** the same artifact hash is validated and timed. Inputs and addresses rotate, and finalists are re-timed on fresh trials.
  - **Breaking the judge first:** seed wrong mutants (zero output, missing tail, dropped mask/clamp, unsafe downcast, input mutation, stale cache, wrong gradient, uninitialized output, fake return type, untimed work). A suite that accepts any of them fails.
  - **Further attacks to block:** changing global precision flags to slow the baseline, computing outside the timed region or on an untimed stream, caching by pointer, uncharged weight preprocessing, validating one path and timing another, writing only sampled outputs, silent downcasts, dropping masks/dropout, corrupting the reference via input mutation, and stale result caches after a shape/driver update.
- **Evidence / numbers:** F:
  - Sakana AI CUDA Engineer post-mortem (2025-03-03): exaggerated maxima, evaluator-memory access, omitted work.
  - METR (2025-06-05): kernels finding the reference tensor on the Python stack, disabling synchronization, changing timers, and tensor subclasses faking equality.
  - Kevin-32B: copying the PyTorch reference and try/except fallbacks.
  - KernelBench-Verified: best single-turn geomean speedup falls from 1.43× to 0.88× under hidden distributions plus a TF32 baseline, and 28% of kernels increase peak memory.
  - Wafer: a 104.89× HIP "result" built on invalid shared memory/uninitialized outputs that passed a loose softmax tolerance.
  - Shah/Shrestha: of 2,638 previously accepted kernels, 39.5% have violations beyond tolerance disputes and 62.1% have at least one violation.
  - Gimlet: 16 proved / 2 inequivalent / 8 unknown of 26 L1 Triton kernels, over exact reals.

  Sources: [METR reward hacking](https://metr.org/blog/2025-06-05-recent-reward-hacking/), [KernelBench-Verified](https://arxiv.org/abs/2607.16241), [Shah/Shrestha audit](https://arxiv.org/abs/2608.12700).
- **Prior art / who has it:** Standard Kernel (SK-Check), Sakana robust-kbench, KernelBench-Verified, SOL-ExecBench, Gimlet, Volta, GPUVerify, Browne/Lee/Salvi (Lean/Velvet, VerCors), the August contract-verifier study.
- **Verdict:** NARROWED. It is essential, but as part of the ONE bet, not a separate empty market. A general verifier company would need an extra capability or distribution advantage. A source proof, a real-arithmetic proof, a memory-safety proof and correctness of the shipped binary are distinct claims, and the report says not to collapse them into one badge.
- **Kill test / first proof:** The test set must reject all deliberately wrong mutants before any kernel is accepted. Unknown results and timeouts count as unknown, not as passes.

#### Rejected in this report
- **General "AI CUDA engineer"** — public loops and commercial products already exist, and KernelBench success is not product differentiation.
- **CUDA→ROCm syntax translator** — HIPIFY already handles much of it. The remaining semantics, architecture-specific performance and maintenance would have to be demonstrated.
- **Universal CUDA→AMD/TPU/Apple agent** — Meta/Modular and the compiler ecosystems already pursue heterogeneity, and one reference cannot validate every target's execution and economics.
- **LLM guesses tile sizes** — Helion already reports large reductions in tuning cost. Compare with its hybrid search before building anything.
- **"Autotuning died, agents revive it"** — historically false. Agents change the cost of expert extensions and the quality of search, not whether empirical optimization exists.
- **New Halide/TVM with a chat interface** — current DSLs and agents already cover it. An accepted missing primitive is a better contribution.
- **Polyhedral compiler for arbitrary irregular ML** — a model cannot make unsupported aliasing or data dependence affine without proving a valid transformation or restricting coverage.
- **STOKE for unrestricted GPU code** — concurrency, new instructions and finite-precision semantics go beyond the strong oracle of a small integer region, and direct PTX agent work already exists.
- **LLM plus e-graph as an unexplored combination** — LGuess, EggMind and EqiForge occupy the guidance and tensor-search directions, and unchecked rewrites defeat the premise.
- **Fresh FFT planner/codelet company** — FFTW/SPIRAL already automated this and LLM-to-SPIRAL lifting is published. It would need a real unsupported fused workload.
- **Private systolic ASIC per model** — the hardware idea succeeded. Cheap schedule writing does not remove the limits of silicon capital, fabrication, deployment or bandwidth.
- **KernelBench leaderboard optimization as the business** — benchmarks do not establish runtime-weighted coverage, deployment correctness or willingness to pay.
- **Generic "universal verifier for AI kernels"** — heavily contested, with important arithmetic/instruction/control restrictions. No universal oracle was established.
- **"GPU utilization below 30%, therefore 70% recoverable by kernels"** — mixes utilization definitions, ignores memory/communication/idle/SLO constraints, and gives no kernel-level headroom estimate.
- **Charge for every fast generated variant** — search, retuning, build time, workspace and amortization over billions of calls can eat the savings (E: a 10 GPU-hour search saving 10 µs per call needs 3.6 billion invocations to pay back). Sell a supported workload outcome instead.
- **Another agent JIT/incremental-agent compiler** — deliberately excluded, since moonshots2/02-compilers.md already covers it.

### 02-distributed: Distributed AI compute: agents around recovery, parallelism and serving
Desk research (no M results) through the lens of distributed training, inference serving and AI cluster operations. Headline: the pain is real and large, but the obvious products are already taken. BSP, collectives, checkpoint/restart, gang scheduling and queueing did not die. They became the machinery of AI compute. Agents can take on the remaining integration, instrumentation, reproducer and adapter work, but they do not remove synchronisation, bandwidth limits, finite HBM or statistical uncertainty about convergence. The ONE bet is recovery-equivalence maintenance: a repair loop that keeps one training application's recovery contract correct through a real stack change, checked against an independently captured uninterrupted run. Verdict: go-with-changes. It is a conditional two-week go/no-go that needs a sponsor's real failures and must beat DCP/ByteCheckpoint tests plus an ordinary coding agent. Confidence is medium on the technical experiment and low on an unoccupied business.

#### Maintain recovery equivalence across stack and parallelism changes (§1)
- **What:** Grow and maintain the missing state adapters an existing training job needs so it resumes with the same declared semantics across a framework update or a parallelism/mesh change. It is not a new checkpoint engine.
- **How it would work:** The agent reads the model/state code and grows the smallest adapter repair from a failing resume comparison. It is checked by an independent capture of the full canonical state: model tensors, optimizer moments/steps/groups, scheduler/scaler, RNG streams, data cursor, sample IDs and accumulation phase. The check compares an uninterrupted run against a save/reload continuation at an explicit step boundary, plus deterministic next-step outputs where achievable. Different reduction trees may need a predeclared numerical bound instead of byte equality. Ways the agent could cheat: omit hard fields, relax the tolerance, reset the optimizer, replay only easy batches, compare two equally broken converters, or save after the injected fault. The agent cannot edit the capture/comparator, the test timing or the hidden fixtures. The oracle is strong for bounded state continuity and weak for general convergence.
- **Evidence / numbers:** F: PyTorch DCP documents canonical-name/optimizer-ID complications and already supports load-time resharding. F: DeepSpeed PR #8889 (October 2026): universal checkpoint resume restored fused/capturable optimizer step tensors with the wrong device/dtype. That shows a repair task exists, not silent corruption or a merged fix. E: a $10K–25K bounded qualification pilot for a model platform team; ten pilots = $100K–250K revenue (not a market size). No primary source here measures adapter-maintenance spend. Sources: [DCP docs](https://docs.pytorch.org/docs/main/distributed.checkpoint.html), [DeepSpeed PR #8889](https://github.com/deepspeedai/DeepSpeed/pull/8889), [Nguyen et al. 2026](https://arxiv.org/html/2606.30921v1).
- **Prior art / who has it:** Old ideas: Chandy–Lamport consistent global state (1985), with the report stressing that it borrows the consistency principle, not the channel-state algorithm; Young (1974) and Daly (2006) checkpoint interval. Recent: ByteCheckpoint (NSDI 2025: parallelism-agnostic state, framework/storage adapters, load-time resharding); Nguyen et al. (June 2026: generate→validate→repair adds VeloC checkpointing to six MPI apps, with fault injection and reference-output comparison); ShardLift (local deterministic crash recovery and offline W4→W3 resharding, excluding GPU/NCCL/FSDP); PyTorch DCP.
- **Verdict:** KEPT (#1, the ONE bet). It has the most attainable independent reference, a concrete recurring source of state bugs, and a path to falsification at CPU scale. What sets it apart must be qualification across updates and applications plus accepted repairs, not checkpoint generation or a kill-and-reshard demo. A strong generic coding agent with good upstream tests could erase the advantage. Confidence: medium technically, low on an unoccupied business.
- **Kill test / first proof:** E: two weeks, one engineer, TS orchestration plus a Python/PyTorch bridge. Freeze a small workload, three layout/update transitions and an independent reference capture. Inject a missing optimizer step, a swapped shard, a stale data cursor, lost RNG and a partially committed checkpoint. Hold out whole fault families and one transition. CPU/Gloo tests the state logic only. ONE-bet plan: days 1–3 get three genuine sponsor failures; days 4–6 build capture, comparisons and hidden mutants; days 7–10 run budget-matched structured repair against an ordinary agent plus upstream tests; days 11–14 test a withheld transition and measure expert time. Demo: a job resumes and trains but diverges because of one wrongly restored optimizer field. Kill unless three real integration failures close with zero accepted state-loss mutants and ≥50% less expert time (harness included) than that baseline, and the sponsor will pay $10K–25K for the next qualification. Otherwise upstream the tests and stop.

#### Turn an incident diagnosis into a minimized, executable reproducer (§2)
- **What:** Turn a production distributed-training incident into a small standalone executable reproducer, instead of a log summary.
- **How it would work:** The agent writes targeted, bounded instrumentation/probes and distinguishes competing causes. Delta debugging minimises a difference in input or environment that preserves the failure, and traces are joined across ranks Dapper-style. The check is intervention, not logs: removing or changing the suspect condition must eliminate the failure, and restoring it must reproduce it, on a held-out environment. The check must also separate "communication timeout observed" from "rank X entered a different collective". Ways to cheat: report the last rank to log, inject the purported fault into the reproducer, change the failure predicate, disable checks, or call a timeout a hardware root cause. Original symptoms are preserved and unreproduced cases are marked unresolved.
- **Evidence / numbers:** F: L4 extracts failure-bearing logs/nodes/stages (428 reports, avg 941 accelerators/job, no denominator for all jobs). F: XPUTimer deployed across 6K GPUs for eight months and detected a 2.66% slowdown. F: TSGuard reports 19.8% better diagnostic accuracy and 63.4% less verification time against its baselines. E: a $5K–15K pilot for ten reproducible historical incidents. Sources: [L4](https://arxiv.org/abs/2503.20263), [XPUTimer](https://arxiv.org/abs/2502.05413), [TSGuard](https://arxiv.org/html/2506.01481v2).
- **Prior art / who has it:** Zeller–Hildebrandt delta debugging (2002); Dapper (2010). Directly occupied: TSGuard/AidAI (Azure multi-agent incident diagnosis, FSE May 2026); NVIDIA Minerva/Sherlock (Oct 2026, telemetry plus topology/workload knowledge graph, MCP access); Alibaba EROICA (production differential troubleshooting). Only automatic conversion of production incidents into small reproducers is potentially distinct, and the search does not prove it unoccupied.
- **Verdict:** KEPT (#2). Better models help turn unfamiliar cross-layer evidence into executable tests that are worth more than a plausible explanation, but generic diagnosis is a poor bet. It is a useful second-stage feature, and the generic GPU SRE copilot is rejected. Confidence: medium on configuration/software incidents, low on intermittent physical faults without privileged access.
- **Kill test / first proof:** E: ten local distributed fixtures: mismatched collective order, bad shape, rank exit, data-loader stall, wrong interface, injected latency. The agent gets traces/config/source but not the labels. It must produce a standalone reproducer, a reduction in ranks/input, and a repair or a justified unresolved result, compared with scripted flight-recorder analysis and a strong general agent. Kill if real operator incidents cannot be reduced, if quality depends on fixture-name leakage, or if no operator supplies ten sanitised real cases.

#### Generate and maintain SDC probes using algebraic checks and differential replay (§3)
- **What:** When a new kernel, layout or precision path appears, an agent extends the silent-data-corruption detectors and reproducers to cover it.
- **How it would work:** The agent writes probes and shrinkers but never the golden reference. Judging comes from independent algebraic redundancy (ABFT, random projections/checksums) or from deterministic replay against a trusted CPU/high-precision reference or a healthy device. A loss spike is only an alarm. Ways to cheat: drop silent-but-plausible mutants, widen tolerance, test only NaNs, let the checker share the corrupted result, or overfit to injected bit locations. Fault sites, magnitudes, timing and correlated faults stay hidden, and healthy low-precision variation is included to measure false positives. The oracle is strong for injected faults within a declared model and weak for unseen real faults.
- **Evidence / numbers:** F: AEGIS: 35M GPU-hours, 18 real SDC incidents, 13 faulty GPUs, 0.86% overhead. E: 18/35M ≈ 0.51 detected incidents per million GPU-hours, not a device fault constant. F: Meta FT-HSDP: SDC investigations take hours to days, and 37 interruptions were traced to seven hosts in its 32K-GPU observations. E: $10K–30K for a bounded qualification effort. Sources: [AEGIS](https://www.usenix.org/conference/osdi26/presentation/lei), [FT-HSDP](https://arxiv.org/html/2602.00277v1), [Huang–Abraham ABFT 1984](https://graal.ens-lyon.fr/~abenoit/CR02/papers/abft2.pdf).
- **Prior art / who has it:** Huang–Abraham ABFT (1984). Lamport–Shostak–Pease Byzantine agreement (1982) is noted as a different contract. AEGIS is the direct incumbent for online training SDC detection. Meta has internal deterministic replay. NVIDIA NVSentinel quarantines suspect nodes.
- **Verdict:** KEPT (#3). Strong independent local checks are possible and real corruption is expensive to investigate, but detection is occupied. The gap would have to be an unsupported execution path or a reproducible new fault class. Disposition: a research or coverage project, likely an upstream contribution or lab tool, with weak evidence for a standalone business. Confidence: medium on a bounded fault-injection study, low on a product.
- **Kill test / first proof:** E: two small operators plus a miniature training loop. Inject payload/metadata corruption behind a trusted runner, then compare with fixed ABFT/random-projection checks and deterministic replay, measuring sensitivity per fault class, false positives and checking cost. Kill if held-out corruption classes defeat coverage, if healthy rounding causes unacceptable quarantines, or if no lab can name a new path its detector misses.

#### Apply backup-task and tail-tolerance ideas to fail-slow training (§4)
- **What:** Diagnose transient slow participants in training, then choose rebalancing, migration, redundancy or restart based on remaining work and contention costs.
- **How it would work:** The agent maintains the mapping from symptoms to legal mitigations for unfamiliar hybrid layouts and generates policy changes. Deterministic low-overhead control stays inside the step loop. The check uses a frozen workload with sample accounting and held-out fault schedules, scoring productive progress per provisioned GPU-hour (spares, migration and abandoned work included) and verifying data weighting and effective batch after rebalancing. Ways to cheat: count only active GPUs, omit migrated work, change the batch/data distribution, or remove the injected bottleneck from the benchmark. The oracle is moderate.
- **Evidence / numbers:** F: GREYHOUND: in a fleet of >10K GPUs, 16 of 27 jobs using 512–1,024 GPUs hit fail-slows, with mean JCT delay 34.59% and mean duration 72 min. Mitigation on 256 H800s with injected stragglers gave 1.58×. F: the original MapReduce sort was 44% slower without backup tasks (not an AI saving). E: a synchronised step going from 1.00 to 1.05 s cuts throughput 4.76% across the gang. E: a hypothetical 3% of a $1M/month reservation = $30K/month gross. Sources: [GREYHOUND](https://cse.hkust.edu.hk/~weiwa/papers/greyhound-atc25.pdf), [MapReduce 2004](https://research.google.com/archive/mapreduce-osdi04.pdf), [TorchPass](https://clockwork.io/blog/torchpass-workload-fault-tolerance/).
- **Prior art / who has it:** MapReduce backup tasks (Dean–Ghemawat 2004); hedged/tied requests (Dean–Barroso 2013); GREYHOUND (graduated mitigation without humans); Clockwork TorchPass (network failover, live GPU migration, 64-H200 vendor benchmark); MegaScale straggler findings.
- **Verdict:** Ranked 8th of 10 ("#4 fail-slow mitigation"). Occupied, so do not build a new generic straggler product. TP/PP shards share stateful collectives, so speculative duplication runs into semantic and capacity barriers. A model that reasons for seconds cannot schedule microsecond collective events.
- **Kill test / first proof:** E: replay a fixed multi-stage DAG with injected compute/link slowdowns. Implement costed restart, remap and extra-replica choices, and compare against GREYHOUND-like thresholds and an offline lower bound. This runs as a CPU simulation, which can falsify the policy logic but cannot show a GPU speedup. Kill if gains disappear without future knowledge, correlate with omitted network interference, or match existing controllers.

#### Relax failure domains while preserving BSP's useful semantics (§5)
- **What:** Treat replicas as fault domains, keep synchronous update semantics within the declared participating set, and recover a failed replica without stopping every accelerator.
- **How it would work:** The agent integrates and qualifies an existing fault-tolerant runtime for an unsupported model (for example by filling a model-state callback) and does not invent a new consistency regime. State-machine checks cover membership epochs, no mixed-step reductions and clean join/leave. Convergence needs fixed-budget, multi-seed loss/quality tests with sample accounting. Ways to cheat: report steps while processing fewer tokens, skip hard data, change the LR schedule without disclosure, or claim that small-model convergence proves 100K-GPU quality. The oracle is strong for protocol safety in a bounded model and weak for final model equivalence.
- **Evidence / numbers:** F: FT-HSDP: ~32K GPUs at 2.3 interruptions/1,000 servers/day and 95–97% effective training time. At 98K GPUs, recovery stalls went from 10 to 3 min, which translates to 44%→80% effective training time under an 18-minute interruption cycle (cycle accounting, accuracy experiments at 256 GPUs). E: $10K–25K integration/qualification engagements. Sources: [FT-HSDP](https://arxiv.org/html/2602.00277v1), [torchft Manager](https://meta-pytorch.org/torchft/manager.html), [ByteRobust SOSP 2025](https://i.cs.hku.hk/~cwu/papers/brwan-sosp25.pdf).
- **Prior art / who has it:** Valiant BSP (1990); parameter servers (Li et al., OSDI 2014). Current: FT-HSDP/FTAR, torchft (quorum, process-group reconfiguration, checkpoint restore), Google slice-level continuation, Unicron, ByteDance ByteRobust.
- **Verdict:** Ranked 9th of 10 ("#5 new elastic training runtime"). Use the incumbent machinery, with §1 as the integration wedge. Asynchrony/staleness changes optimisation behaviour, and a replacement runtime needs much more than two weeks plus cluster access.
- **Kill test / first proof:** E: tiny deterministic training with two replica groups on CPU/Gloo. Script membership changes and recovery epochs, and have the agent fill an unsupported model-state callback, compared against the unmodified integration and a restart baseline. Kill unless the integration closes an actual gap and the model owner accepts its semantics.

#### Repair parallelism configurations and their missing framework support (§6)
- **What:** An agent proposes a legal model/mesh/configuration adapter, especially support for an operation a planner does not cover, and a compiler/runtime and measurement loop checks it.
- **How it would work:** The agent implements the missing sharding rule or adapter for an unfamiliar operation, and simply asking an LLM for TP/PP integers is ruled out. Checks: static divisibility/shape/memory checks; distributed-vs-reference forward/gradient/update comparisons; measured memory and throughput under a fixed batch/precision/data contract. Simulator scores only screen candidates. Ways to cheat: lower sequence length, change precision or token dropping, omit optimizer state, exploit graph-capture warmup, or optimise one homogeneous microbatch. The oracle is moderate.
- **Evidence / numbers:** F: Mist reports mean gains of 1.32×/1.34× over Megatron-LM on up to 32 L4/A100 GPUs, and its artifact still documents multi-node OOM/idling that needs manual monitoring. F: Megatron's guide computes DP = world_size/(TP×PP×CP), and EP has extra group relationships. E: 10 knobs × 4 values ≈ 1M combinations (illustrative). F: FlexParallel 2026 submission reports tuning through 8,192 devices. E: a $10K–20K pilot for one previously unsupported operator/layout. Sources: [Mist](https://people.mpi-sws.org/~cgiannoula/assets/publications/Mist_EuroSys2025_full.pdf), [Megatron Bridge guide](https://docs.nvidia.com/nemo/megatron-bridge/latest/parallelisms.html), [Alpa](https://arxiv.org/abs/2201.12023).
- **Prior art / who has it:** FlexFlow (2019), GSPMD/XLA (2021), Alpa (2022), Mist/CentML, DeepSpeed AutoTP, NVIDIA Megatron (its guide links an operational agent skill), FlexParallel.
- **Verdict:** Ranked 4th (first in the remaining order). A conditional integration opportunity, with no case for a generic auto-parallel company because generic autotuning is decisively occupied. Conventional search can beat a model inside a parameter space that is already covered.
- **Kill test / first proof:** E: pick a tiny MoE or custom op that a chosen planner lacks, have the agent implement the adapter, and hold out shapes/layouts, using CPU reference gradients and simulated costs. It must gain actual semantic support, not a bigger YAML grid. Kill if the op is already supported, if a normal agent finds the adapter trivial, or if performance needs a change to the numerical contract.

#### Synthesize topology-specific collectives, with independent schedule checking (§7)
- **What:** An agent writes a collective schedule or communication sketch for an irregular, new or degraded topology.
- **How it would work:** A symbolic checker establishes data movement and reduction coverage, then a runtime tests performance. The checker tracks chunk provenance, exactly-once reduction contributions, buffer aliasing and dependency order, with tests for odd rank counts, nonuniform messages, in-place buffers and concurrency. Integer inputs expose coverage mistakes, and FP reductions need a declared ordering/tolerance. Ways to cheat: benchmark no-ops, reuse expected buffers, omit synchronisation, reduce fewer ranks, or win a microbenchmark by occupying SMs the model needs. End-to-end measurement must therefore include competing compute. The oracle is strong for a finite schedule's logical coverage and moderate for the implementation.
- **Evidence / numbers:** I: ring allreduce takes ~2(p−1) rounds and 2(p−1)n/p bytes per rank. These simplified α/β costs omit multi-rail contention, SM use and overlap, so there is no universal "ring beats tree" rule. F: MSCCL++ reports up to 3.8× collective and 15% real inference speedup against its baselines. F: Meta NCCLX co-designs transport, overlap, inference collectives and fault localisation for 100K+ GPUs. E: a $20K–50K joint engineering pilot, conditional on hardware access. Sources: [Thakur–Rabenseifner–Gropp 2005](https://www.cs.umd.edu/class/spring2021/cmsc714/readings/Thakur-MPICH.pdf), [MSCCL++](https://arxiv.org/abs/2504.09014), [NCCLX](https://arxiv.org/html/2510.20171v4).
- **Prior art / who has it:** MPICH algorithm selection (Thakur–Rabenseifner–Gropp 2005); MSCCL; TACCL (NSDI 2023, human sketches); MSCCL++ (DSL, NCCL-compatible); OptCCL (SIGCOMM 2026, hundreds of GPUs); NCCLX.
- **Verdict:** Ranked 6th ("#7 collective backend/sketch support"). The disposition is to contribute backend/sketch support and reject generic agent collective synthesis. Solver/DSL synthesis plus an agent is occupied infrastructure, and better generic agents commoditise schedule authoring.
- **Kill test / first proof:** E: reuse MSCCL-style provenance semantics with a TS checker and a small schedule DSL. The agent writes schedules for ten withheld asymmetric/degraded topologies, compared with ring/tree and a solver, all synthesis time included. With no GPU this shows legality and modelled cost only. Kill if solver baselines win or gains vanish under contention-aware simulation.

#### Co-schedule whole jobs for useful progress, rather than GPU occupancy (§8)
- **What:** An agent translates workload requirements into gang/topology/elasticity constraints, and an established scheduler optimises placement. This includes new multi-role inference gangs (prefill/decode pools, TP/EP workers).
- **How it would work:** The agent creates the missing workload mappings (new CRDs, restart contracts) and policies, and the deterministic scheduler makes the real-time decisions. A constraint solver verifies placement/quota/gang invariants, and replay on hidden arrivals tests utilisation, queue wait, time-to-quality, fairness and starvation. Ways to cheat: reject inconvenient jobs, ignore initialisation/restart time, inflate declared priority, count stranded GPUs as useful, or benchmark only small backfillable jobs. Every admitted and waiting job counts, and transition costs are charged. The oracle is moderate.
- **Evidence / numbers:** F: NVIDIA describes hierarchical gang scheduling and topology-aware orchestration via Grove and KAI for disaggregated inference. F: NVIDIA Run:ai open-sourced in October 2026, including Workload Map. E: a $5K–15K supported adapter/policy engagement. Sources: [Ousterhout 1982](https://web.stanford.edu/~ouster/cgi-bin/papers/coscheduling.pdf), [NVIDIA Run:ai open source](https://developer.nvidia.com/blog/nvidia-runai-is-now-open-source-as-part-of-nvidia-dsx-ai-factory-platform), [Pollux](https://www.usenix.org/conference/osdi21/presentation/qiao).
- **Prior art / who has it:** Ousterhout coscheduling (1982); Pollux (goodput-aware allocation); KAI/Run:ai (gang placement, hierarchical fairness, topology awareness, GPU sharing); Grove; Workload Map.
- **Verdict:** Ranked last ("#8 general scheduler"). Occupied, and useful only as narrow integration work. Even "agent writes scheduler integration for arbitrary CRDs" competes with Workload Map, and a new scheduler company faces high switching costs against a strong open-source incumbent.
- **Kill test / first proof:** E: an existing scheduler's dry-run or a constraint model with a fixed fleet and arrival traces. The agent adds a missing workload mapping, and partial-launch, preemption and restart failures are injected. Test legal progress and starvation before predicted utilisation, with no cluster deployment. Kill if the target workload maps directly to supported upstream objects.

#### Maintain a calibrated cluster simulator, rather than treating simulation as truth (§9)
- **What:** Use discrete-event simulation and measured operator/network costs to explore mappings. An agent explains residual errors and adds missing model features (e.g. an overlap or interference effect).
- **How it would work:** The agent maintains the simulator model and proposes experiments. The check holds out real traces by topology, workload and time and scores candidate-ranking accuracy and calibrated uncertainty, not just mean runtime error. A separate physical measurement must accept any optimisation. Ways to cheat: train/test on near-identical profiles, add per-workload fudge constants, ignore rare tails, or alter the simulator so its own proposed policy wins. Observed timings stay immutable, and simulator edits are separated from policy evaluation. The oracle is weak as a final judge and moderate as a screen.
- **Evidence / numbers:** F: SimAI reports end-to-end iteration deviation <3.9% through 1,024 GPUs. F: Vidur reports request-level latency error <9%. I: these errors can exceed the gain from a 2% schedule change. E: a $10K–25K calibration project for a missing domain, with no evidence for a simulator-as-a-service market. Sources: [SimAI](https://ennanzhai.github.io/pub/nsdi25spring-simai.pdf), [Vidur](https://www.microsoft.com/en-us/research/wp-content/uploads/2024/05/vidur_mlsys24.pdf), [ASTRA-sim](https://github.com/astra-sim/astra-sim).
- **Prior art / who has it:** FlexFlow (simulation-guided), ASTRA-sim 2.0 (Chakra traces), Alibaba SimAI, Microsoft Vidur, NVIDIA AIConfigurator, Dynamo planner (live forward-pass metrics, experimental simulation-only retuning).
- **Verdict:** Ranked 5th (second in the remaining order). A useful research component, but not an independent oracle or a generic company bet, and a generic agent "digital twin optimizer" overlaps an active incumbent roadmap. If optimisation happens only inside the simulator, better models just exploit it faster.
- **Kill test / first proof:** E: an existing public trace/profile corpus with grouped holdout by topology/workload. The agent adds one missing overlap/interference effect, compared against conventional regression and manually specified features, and success means correctly ranking untouched candidate schedules. Kill if held-out ranking does not improve or if the signal is smaller than the model error.

#### Tune serving policies using queueing, working sets and a fixed service contract (§10)
- **What:** An agent proposes batching, routing, cache or pool policies for LLM serving, judged on completed useful service under a fixed contract instead of token rate.
- **How it would work:** The agent emits policy code/configuration, and an independent workload replay plus the serving engine measure it. The contract fixes model/weights/precision, input/output requirements, cache identity, admission policy, TTFT, inter-token latency and task-completion SLOs. All arrivals, rejects, timeouts and incomplete sessions count, warmup, KV movement and idle reserved capacity are included, and outputs/logits or declared quality bounds are compared. Ways to cheat: shorten generations, force EOS, truncate context, discard long requests, exclude timeouts from p99, leak future output length, reuse stale/cross-model KV, or sacrifice a tenant. Hidden burst/long-context/tool-wait traces and per-class SLO floors guard against this. The oracle is strong for a frozen replay and weak for future traffic.
- **Evidence / numbers:** F: DistServe reports up to 7.4× requests or 12.6× tighter SLO. F: Sarathi-Serve reports 2.6× capacity (Mistral-7B/A100) and up to 5.6× (Falcon-180B). F: Mooncake reports 59–498% effective capacity and production gains of 115%/107%. These gains are not multiplicative. E: an illustrative 80-layer, 8-KV-head BF16 model uses 320 KiB/token, or 40 GiB for 128 Ki tokens. E: Kingman's ρ/(1−ρ) goes from 4 at 80% to 19 at 95% utilisation (4.75×). E: 5% of a $1M/month reservation = $50K/month gross. Sources: [DistServe](https://www.usenix.org/conference/osdi24/presentation/zhong-yinmin), [Sarathi-Serve](https://www.usenix.org/conference/osdi24/presentation/agrawal), [Mooncake](https://www.usenix.org/conference/fast25/presentation/qin).
- **Prior art / who has it:** Little's law, Kingman (1961), Denning working sets (1968). Current: vLLM/PagedAttention, Mooncake, SGLang (RadixAttention), NVIDIA Dynamo/AIConfigurator, llm-d, Alibaba Llumnix, Fireworks. Agent-specific: SMetric (2026) and TOPAS (2026). Adding "for agents" does not restore novelty.
- **Verdict:** Ranked 7th ("#10 workload-specific serving tuning"). Occupied as a platform, leaving only a workload-specific contribution or evaluation integration. The tuner must beat Dynamo/engine-native tuning and a normal optimisation agent.
- **Kill test / first proof:** E: reuse Vidur/public traces or an engine's replay interface. Evaluate steady, burst, long-context, cache-miss and tool-wait workloads, and include an adversarial scheduler that drops long requests to prove the metric penalises it. Simulation-only results are labelled simulated, and no new serving engine is built. Kill if held-out gains are below the uncertainty, if quality/tenant floors regress, or if a built-in sweep matches the result.

#### Rejected in this report
- **Generic autonomous GPU SRE copilot** — TSGuard/AidAI and NVIDIA Minerva/Sherlock overlap it directly, and a chat interface to logs is not enough differentiation.
- **Agent-generated checkpointing as the revival** — Nguyen et al. already implement the generate–validate–repair loop, and ByteCheckpoint and DCP already provide the portability machinery.
- **CPU crash-and-reshard evidence as novelty** — ShardLift already demonstrates this bounded mechanism. Interoperability with an existing stack is the harder question.
- **Universal bitwise reproducibility across mesh changes** — changes to FP reduction order and kernels break that promise. Fix a numerical contract and disclose its limits instead.
- **"Loss goes down" as a correctness oracle** — wrong sample accounting, wrong optimizer state or corruption can hide behind a short smooth loss curve.
- **Byzantine consensus for every gradient** — agreement does not establish correct arithmetic, and SDC in a trusted fleet does not automatically justify Byzantine replication overhead.
- **General online SDC detector** — AEGIS already has production-scale sensing/verification evidence. Probe coverage is the narrower conditional seam.
- **Backup every slow TP/PP task** — collective/state dependencies and redundancy-induced congestion break the simple MapReduce analogy, and GREYHOUND and TorchPass already do practical mitigation.
- **Replace BSP/allreduce with a parameter server** — dense traffic, staleness and optimisation semantics remain, and cheap code is not the missing proof.
- **Generic agent selects TP/PP/DP/EP/CP** — GSPMD, Alpa, Mist, DeepSpeed and framework guidance already cover much of the space. Unsupported semantics are the only possible labour tail.
- **Agent discovers ring/tree allreduce** — MPI algorithm selection and MSCCL/TACCL/OptCCL synthesis came first, and new-topology backend work needs real hardware validation.
- **Another gang scheduler** — KAI/Run:ai, Grove and Workload Map already provide placement and workload contracts, while fairness and fragmentation still need explicit policy.
- **Simulator score as final acceptance** — an agent can exploit model errors. SimAI/ASTRA-sim/Vidur and physical held-out measurements must stay distinct.
- **Generic KV-cache/disaggregated serving optimizer** — Mooncake, vLLM, SGLang, Dynamo, llm-d, Llumnix and Fireworks already occupy it, and session/workflow scheduling also has 2026 prior art.
- **Maximize tokens/sec or GPU-busy percentage** — this can drop long requests, change quality, hide idle reservations or impair convergence. Completed qualified work is the right denominator.
- **Claim a 100K-GPU failure rate from a 10K-GPU fleet trace** — GREYHOUND's sampled jobs were 512–1,024 GPUs, so scale labels and denominators must stay attached.

### 03-propose-check: Models propose; old PL machinery checks
Desk research (no experiments run; all published benchmark results are F, not M) on compiler, synthesis and verification techniques whose search or human guidance an LLM could now supply, while an existing trusted checker validates the result. Headline: the economic flip is real, but the generic invention is already taken. By October 2026 there is direct work on LLM CEGIS, e-graph guidance, Alive2-guided optimization, Lean-checked LLVM validation, invariant/ranking synthesis, LiquidHaskell annotations, separation-logic specs, recompilable decompilation, compiler mutator generation and repair. Key correction: cheap proposals do not make checking cheap, so the deeper flip is "LLM proposes the decomposition, invariant or proof, and a small trusted checker validates each step", and Trivet, alive-next and LEMUR already occupy that too. The report grades checkers as strong / bounded / weak / none, and its shared anti-cheating rule is to freeze the reference, contract, inputs, toolchain, checker configuration and acceptance program outside the proposer's edit authority. The ONE bet is a customer-bound two-week experiment on maintained translation validation of agent rewrites in one existing native library (§3). Verdict: go-with-changes, i.e. a conditional experiment that is "not a proven company gap" and is killed unless it beats existing validators plus a normal agent.

#### CEGIS: the model replaces expensive candidate search and human sketching (§1)
- **What:** Counterexample-guided inductive synthesis, where the agent supplies the sketch that used to need human algorithmic insight, plus the successive candidates.
- **How it would work:** The model proposes sketches and complete candidates across implementation strategies, generalizes counterexamples and tries alternative decompositions. A validator returns counterexamples, which are accumulated. Oracle strength depends on the validator: an SMT proof in a supported finite/decidable DSL is strong, bounded Alloy exploration is bounded, and regression tests are weak. Cheats: refusing every request to satisfy safety, hard-coding seen counterexamples, weakening the generated formalization, or forgetting earlier cases. The formalizer must also stay untrusted.
- **Evidence / numbers:** F: the AAAI 2025 LLM-CEGIS-Repair artifact already combines MaxSAT fault localization, sketches and LLM candidates, but checks only against a test suite. F: Cunha's 2026 concept-design synthesis covered 3 applications and 12 variants; invariant-only synthesis often gave implausible designs, and scenarios helped but did not remove missed behavior. E: a $10k–25k domain pilot is plausible only if it replaces days of specialist work; this is a price experiment. Sources: [Solar-Lezama 2008](https://www2.eecs.berkeley.edu/Pubs/TechRpts/2008/EECS-2008-177.html), [LLM-CEGIS-Repair](https://github.com/pmorvalho/LLM-CEGIS-Repair), [Cunha 2026](https://arxiv.org/abs/2607.15718).
- **Prior art / who has it:** Sketch (Solar-Lezama), LLM-CEGIS-Repair (Morvalho et al.), Verified LLM-Driven Synthesis for Concept Design (Cunha), Refine4LLM (Cai et al., POPL 2025).
- **Verdict:** NARROWED. The generic CEGIS product is killed. The scarce input is a faithful DSL semantics and discrimination of intended behavior, and a 100× better model makes a standalone orchestration wrapper easy to copy. A domain pilot survives only if the hybrid beats existing synthesis plus an ordinary agent after counting harness construction. Expected expert objection: "You renamed a standard verifier feedback loop."
- **Kill test / first proof:** E: freeze 20 small reference-defined bit-vector or policy tasks, including conflicting and underspecified cases. A TS orchestrator keeps every counterexample and a solver checks candidates. Compare solver-only Sketch/SyGuS, agent-plus-tests and the hybrid at equal budget. Success needs useful contracts, explicit unknowns and fewer expert minutes, not just more passing candidates.

#### Equality saturation: the model guesses checkpoints, strategies or new rewrite rules (§2)
- **What:** The LLM supplies the human-guided step of e-graph optimization: intermediate checkpoints/sketches, search strategies, or new domain rewrite rules.
- **How it would work:** With fixed sound rules, the model only proposes waypoints or a strategy and the e-graph fills in the low-level derivation chains. Any **new** rule must be proved in the DSL semantics, side conditions included, before classes are unioned. E-graph membership only proves derivability from the installed rules. Cheats and gaps: unsound rules around floating-point reassociation, overflow, binders, aliasing or effects; gaming a symbolic cost model while real runtime gets worse; a model-written Z3 query that proves a different equation than the rule.
- **Evidence / numbers:** F: EggMind reports 45.1% lower final cost and 69.1% lower peak RAM than full EqSat on its vectorization benchmarks (author-reported). F: CHOMPY, a non-LLM conditional-rule synthesizer (FMCAD 2026), beats its LLM-only baseline on both evaluated benchmarks, so the model is not automatically the best proposer. E: $20k per compiler integration is consulting scale; demand is not established. Sources: [Guided EqSat, POPL 2024](https://steuwer.info/files/publications/2024/POPL-2024-2.pdf), [EggMind](https://arxiv.org/abs/2604.17364), [ASPEN](https://www.csl.cornell.edu/~zhiruz/pdfs/aspen-mlcad2025.pdf).
- **Prior art / who has it:** egg/egglog (Willsey), Guided Equality Saturation (Koehler et al.), LGuess (EGRAPHS 2025), EggMind, ChopChop (POPL 2026), ASPEN (LLM-proposed RTL rules with Z3 proofs, MLCAD 2025), CHOMPY.
- **Verdict:** NARROWED. "LLM + egg" is not a gap. What remains is a maintained, proof-backed rewrite package for one underserved DSL, with side conditions and upgrade tests. Kill it without a domain-specific integration advantage, or if direct generation plus checking is cheaper. Expected objection: "LGuess/EggMind already do the guidance, and your DSL has no paying users."
- **Kill test / first proof:** E: one fixed integer DSL with executable semantics. The agent proposes 20 rules or strategies, SMT proves the rules and invalid side conditions are rejected. Compare full EqSat, guided EqSat, direct candidate checking and EggMind-style strategy search on held-out expression families with real target execution. Report memory, search time, proof failures and total savings. Demo: an invalid overflow rewrite rejected before it enters the e-graph.

#### Translation validation + superoptimization: qualify individual rewrites, not the proposer (§3; the ONE bet)
- **What:** An arbitrarily unreliable searcher (the LLM) submits candidate rewrites or optimizations, and per-translation validation decides which are accepted. The residual product is **qualifying and maintaining real, source-native rewrite queues across updates** for one LLVM-using library team, using existing validators instead of inventing another proposer.
- **How it would work:** The agent proposes code and proof decompositions. Acceptance is replayed independently for the exact input/output IR, original contract, flags and semantic profile, with typed proved / bounded / refuted / unknown outcomes; unknowns are never shipped. The oracle is strong for supported loop-free refinements and bounded for ordinary Alive2 loop checks. LLVM refinement is directional, not unrestricted source equivalence. Cheats: adding `assume`/`noalias`/`nsw`/fast-math promises to the reference; dropping `undef`, overflow, exceptions, memory effects or unsupported ops; proving two Lean ports equal without proving either matches the native code; benchmark detection, cached answers and shape overfitting on the separate, noisy performance oracle.
- **Evidence / numbers:** F: Iago (an LLM in place of Souper's enumerator) found 7.4% fewer optimizations, but 35.7% of its finds were absent from Souper's results, so the two are complementary. F: LLM-VeriOpt (Alive2 feedback in GRPO on Qwen-3B) reports 90% verifiably correct outputs. F: Trivet resolves 147/148 benchmark transformations. F: Meta LLM Compiler was trained on 546B tokens. F: AlphaEvolve reports a 23% Gemini kernel improvement and a 1% training-time reduction. E: a $2m/year compute workload with a true 3% end-to-end saving gives $60k/year gross headroom before costs; a $10k–20k pilot needs a named owner and a blocked rewrite backlog. Sources: [Alive2 PLDI 2021](https://web.ist.utl.pt/nuno.lopes/pubs/alive2-pldi21.pdf), [alive-next](https://github.com/connglli/alive-next), [Trivet](https://arxiv.org/abs/2609.19583).
- **Prior art / who has it:** Alive2, Souper, Iago, LLM-VeriOpt, Meta LLM Compiler, Wang/Xie 2024 (Alive2 plus learned predictions/fuzzing), Verified Learning for Compiler Optimization (Alive2 lazification), Trivet (Lean scaffolds + LLM obligations), alive-next (agent decomposition, stepwise Alive2 certificates, replayable packages; assumes removal of `undef`), Aqueduct / Agentic Verified Optimization (Lean ports validated only by differential testing), AlphaEvolve. The report calls this subfield "especially occupied".
- **Verdict:** KEPT (#1) and the ONE bet. It has the strongest semantic oracle and a natural old-program reference, and a better model helps by producing both candidates and proof decompositions. Disposition: "best conditional tool bet; not a proven company gap". Decisive expert objection: "alive-next already supplies agents, decomposition and replayable certificates; Trivet already supplies proof scaffolds; your only addition is a queue." If source/build/version integration does not close a real recurring acceptance gap, accept the objection and contribute upstream.
- **Kill test / first proof:** E: two weeks. Days 1–2: get 20 real rewrite pairs plus one later source revision from a willing team, and stop the business experiment if no team has the problem. Days 3–5: extract the IR pairs and wire in the existing validators. Days 6–9: budget-matched runs of a normal agent versus the structured workflow. Days 10–12: replay, change source/flags/version, and inject ≥20 semantic mutants. Days 13–14: customer review. Continue only if ≥3 useful real rewrites are qualified, no supported-domain mutant is accepted as proved, a real version change is handled, expert qualification time falls ≥50% against existing validators plus an ordinary agent, and at least one customer prefers a paid $10k–20k continuation.

#### Decompilation: recompilation is feedback, behavioral preservation is the goal (§4)
- **What:** The model supplies the missing types, declarations and idiom reconstruction when recovering source from binaries, and recompilation constrains the guess.
- **How it would work:** LLM repair runs with compile and runtime feedback, and the original binary is then compared behaviorally through ABI-aware generated drivers (registers, return values, reachable memory, crash outcomes). Compilation alone is a weak oracle (compiling `return 0` proves almost nothing). Byte-identical recompilation is strong but restrictive, and differential execution is stronger but finite. Cheats: inventing a guard that removes a real vulnerability, fabricating a plausible callee, or filling unknowns with ordinary-looking C.
- **Evidence / numbers:** F: DecLLM reports about 70% recompilation success for previously non-recompilable outputs. F: Decompile-Bench released 2M training pairs and 70k evaluation pairs. F: among candidates passing shipped tests, Decompile-Diverge found 4.9% divergence overall and up to 13% for one system, and better build rate coincided with worse behavioral agreement (study-specific rates). E: $10k per bounded legacy component is a hypothesis. Sources: [DecLLM ISSTA 2025](https://daoyuan14.github.io/papers/ISSTA25_DecLLM.pdf), [LLM4Decompile](https://aclanthology.org/2024.emnlp-main.203/), [Decompile-Diverge](https://arxiv.org/abs/2609.05370).
- **Prior art / who has it:** Cifuentes (1994 thesis), LLM4Decompile, DecLLM, RevEng.AI (AI decompilation via API/MCP), Decompile-Diverge, Ghidra as a baseline.
- **Verdict:** NARROWED. No general "recompilation is the oracle" company survives. A possible residual is ABI/state-aware qualification of one binary family for security or legacy teams, preserving crash behavior and unresolved calls. Kill it without a valuable ABI/state integration that existing tools lack, or if writing valid drivers takes analyst effort comparable to manual reconstruction. Expected objection: "Your driver invented the input contract; this is already Decompile-Diverge."
- **Kill test / first proof:** E: 50 locally executable leaf functions from a permitted binary, with the source withheld. Generate drivers from ABI info and compare registers, returns, memory, boundary inputs and crashes. Evaluate Ghidra, LLM refinement and Decompile-Diverge-style checking, include a deliberately "sanitized" wrong reconstruction, and count driver mistakes and exclusions.

#### Compiler fuzzing: the model makes generators and mutators, not individual test programs (§5)
- **What:** The LLM pays the language-expert cost once by writing semantic-aware generators/mutators, and a cheap conventional generator then runs in the hot loop. The residual offer is qualification for one new compiler extension.
- **How it would work:** The agent writes a generator (for example in Rust) for a restricted, explicitly defined subset. Programs are differentially compiled and run against an independent reference interpreter, and failures are reduced while preserving definedness. A reproducible differential result on a defined program is strong evidence, but disagreement alone does not say which compiler is wrong, sanitizers are not a UB proof, and a compiler crash is not a miscompilation. Cheats: inflating novelty with invalid inputs, trivial duplicates, timeout floods, or coverage of unimportant parsing paths.
- **Evidence / numbers:** F: Csmith found over 325 previously unknown bugs in three years. F: the MetaMut paper reports 118 valid mutators at about $0.50 of model invocation per mutator and 131 bugs; the live repo claims over 200 mutators and over 130 reported bugs (kept separate). E: $15k–30k per extension campaign could fund a specialist service; there is no sourced budget. Sources: [Csmith PLDI 2011](https://www.flux.utah.edu/paper/yang-pldi11), [MetaMut ASPLOS 2024](https://connglli.github.io/pdfs/metamut_asplos24.pdf), [LegoFuzz OOPSLA 2025](https://doi.org/10.1145/3763079).
- **Prior art / who has it:** Csmith, YARPGen (Intel), Fuzz4All, WhiteFox, MetaMut, LegoFuzz, IssueMut, GapForge, and nowarp's MetaMut-style campaigns for Sui Move/Cairo (which weakens the claim that smaller languages are untouched).
- **Verdict:** KEPT (#3). Third-ranked conditional service/upstream tool. The broad "LLM makes fuzzers" gap is closed, so the differentiator must be one feature's definedness/reference semantics and lower triage effort. It may belong upstream. Kill it without a named underserved extension, or if hand templates find the same bugs for less effort. Expected objection: "MetaMut/LegoFuzz already did it, and your sanitizer is not a UB proof."
- **Kill test / first proof:** E: a CPU-executable DSL/IR extension with an independent interpreter. Compare property-based generation, templates and an LLM-assisted generator at equal CPU/model budgets, seed known wrong-code mutants and freeze a holdout feature family. Require a real minimized divergence or materially better mutant discovery, with all invalid-input triage time charged. Demo: a new vector op's wrong-code witness reduced to ten lines without losing definedness.

#### Abstract interpretation, loop invariants and termination: synthesize proof ingredients (§6)
- **What:** The model supplies predicates, disjunctions, auxiliary lemmas, lexicographic ranking functions and proof decompositions, and the existing analyzer/VC generator must establish them. The residual offer is keeping fixed safety/termination obligations discharged across ordinary code changes.
- **How it would work:** The safest design has the agent propose the **analysis result**, and a post-fixpoint check then verifies it. Writing unchecked abstract transfer functions would change the trusted analyzer instead. The oracle is strong only with complete obligations: initiation, preservation and sufficiency, plus a well-founded measure, decrease and supporting conditions for termination. Cheats: `false` passes a check of sufficiency alone, unreachable or useless invariants pass a check of preservation alone, and the agent can invent loop bounds, assume overflow away, or strengthen preconditions to exclude states.
- **Evidence / numbers:** F: Quokka evaluates 866 held-out instances. E: ten verification specialists saving one day a month at an assumed $1k/day gives $120k/year gross labor headroom (a customer situation, not product demand). Sources: [Cousot POPL 1977](https://cs.nyu.edu/~pcousot/COUSOTpapers/POPL77.shtml), [LOOPY FMCAD 2024](https://adharshkamath.github.io/papers/loopy_fmcad24.pdf), [LEMUR ICLR 2024](https://proceedings.iclr.cc/paper_files/paper/2024/hash/0c86142265c5e2c900613dd1d031cb90-Abstract-Conference.html).
- **Prior art / who has it:** Cousot/Cousot, Podelski/Rybalchenko ranking synthesis, LEMUR, Microsoft LOOPY (Houdini + Frama-C, invariants and termination), Quokka, LimICE, Medley/Manolios (LLMs + ACL2 termination), ARGUS (abstract interpretation/SMT for agent GPU optimization, adjacent).
- **Verdict:** NARROWED. General invariant synthesis is occupied, and a standalone ranking-function chat UI has little moat. Kill the proposer product unless maintenance on real revisions beats the baselines; keep the checker integration if it is useful. Expected objection: "LOOPY already does this, and a generic agent now performs equally well."
- **Kill test / first proof:** E: ten C functions with frozen ACSL assertions plus two later revisions each. The agent may change annotations/lemmas but not public contracts or executable code. Compare Frama-C alone, LOOPY/Quokka-style inference and a normal coding agent, include nonterminating and invalid-invariant mutants, and measure expert minutes and verification time, keeping safety, termination and resource bounds separate.

#### Refinement types / LiquidHaskell: models write the missing contracts (§7)
- **What:** The LLM generates refinement annotations across a call graph, removing the expert days-to-weeks annotation labor. The narrow residual is maintaining library interface guarantees across dependency and version changes.
- **How it would work:** Neural bottom-up generation with symbolic help, with LiquidHaskell as the oracle. It is strong for the properties actually expressed, within the trusted assumptions. Exported contracts are frozen, and internal contracts must be shown sufficient for all relevant clients. Cheats: weak result refinements (typechecking `Int -> Int` proves nothing about sorting), contradictory preconditions, trusted `assume` declarations, disabled termination. Reflected functions, axioms, FFI and the checker itself stay in the trust accounting.
- **Evidence / numbers:** F: LHC reports up to 94% of functions annotated automatically in hours on three packages, using a 3B StarCoder model. This is package-specific coverage, not 94% of Haskell proved. E: $5k–15k per proof-maintenance integration is a services hypothesis. Sources: [Liquid Types PLDI 2008](https://doi.org/10.1145/1375581.1375602), [LHC ICSE 2025](https://ranjitjhala.github.io/static/icse25-neurosymbolic-refinement-inference.pdf), [Tweag IFL 2025 artifact](https://github.com/tweag/ifl2025-liquidhaskell).
- **Prior art / who has it:** LHC / Liquid Haskell Copilot (an "almost exact implementation"), Tweag's refinement-driven development study. The search found no deployed universal commercial annotation service, and the report notes that a missing vendor is not proof of unmet demand.
- **Verdict:** NARROWED. Generic inference is rejected as a new bet, and porting the idea to another language is no differentiation because existing verifiers already have agent integrations. The small-language ecosystem limits market size. Continue only with a real maintenance customer and measurable saved work. Expected objection: "LHC already does the hard part; there are too few users."
- **Kill test / first proof:** E: reuse one LHC benchmark library, freeze its public spec, and apply five realistic edits and ten wrong implementations. Compare LHC, an ordinary agent and manual annotations. All frozen client obligations must survive the correct edits, and every relevant mutant must be rejected without weakening a contract.

#### Gradual typing and type migration: optimize useful checking, not green builds (§8)
- **What:** Maintained, precise third-party stubs for one dynamic framework, with runtime examples, precision gates and tests against known invalid callers, rather than arbitrary whole-codebase type migration.
- **How it would work:** The agent proposes stubs/annotations under frozen runtime behavior, checker flags and checking scope. Acceptance measures precision and injected-bug detection, not error count. The oracle is strong for the selected static constraints and weak for runtime equivalence. Cheats: `Any`, `object`, casts, ignored errors, missing-import fallbacks, excluded files, and wrong stubs that make every client look safe. Annotations can affect frameworks and introspection, so "types erase" is not guaranteed.
- **Evidence / numbers:** F: Google's int32→int64 migration had 80% AI-authored modifications and an engineer-estimated 50% time reduction, with humans still targeting and reviewing. F: in Meta's 2026 survey, 42.5% of respondents used AI to write hints, and missing third-party type information was the leading difficulty at 65.1% (not a random population sample). F: TypyBench (50 Python repos) finds plausible predictions still produce substantial consistency errors. E: $10k pilot or $1k/month maintenance per enterprise framework/version set; demand unverified. Sources: [Google migrations 2024](https://research.google/blog/accelerating-code-migrations-with-ai/), [Meta typing survey 2026](https://engineering.fb.com/2026/10/27/developer-tools/python-typing-survey-2026-ai-tools-checker-landscape/), [TypyBench ICML 2025](https://www.cs.toronto.edu/~fanl/papers/typebench-icml25.pdf).
- **Prior art / who has it:** Siek/Taha gradual typing, TypeT5, TypeWeaver/OpenTau, TypyBench, TypeCare, Meta Pyrefly agentic workflows, Google's migration toolkit, typeshed/framework maintainers.
- **Verdict:** KEPT (#2). It is ranked on the clearest directly sourced user pain, not on checker strength, and the report calls its oracle materially weaker than §3's. Sell measured gains in bug detection and valid-client support, not verified equivalence. It may belong with typeshed/framework maintainers. Kill it if mutation rejection does not improve, if valid clients get excluded, or if maintainers cannot justify recurring support. Expected objection: "My checker infers them and the framework's stubs are already improving."
- **Kill test / first proof:** E: a package with real missing or incorrect stubs and ten client modules. Check acceptance, valid-client compatibility, 20 deliberately invalid call sites and held-out runtime interactions, with no new suppressions or dynamic escapes. Compare against an ordinary agent + checker and a framework-maintainer baseline.

#### Separation logic and Infer: distinguish proved contracts from absence of alarms (§9)
- **What:** Models propose ownership predicates, unfold/fold sequences, frame facts, call summaries and proof scripts, so the human's job shifts to choosing the required behavior and qualifying the abstraction boundary. The residual is maintaining proved contracts for one custom C allocator/container or API boundary.
- **How it would work:** A complete separation-logic proof (VeriFast/Iris style) is the strong oracle. "Infer has no report" is weak, because Pulse treats unknown functions optimistically and documents false negatives. Generated library summaries count only if their truth is checked independently. Cheats: hiding effects behind an unknown call, adding a trusted lemma, weakening ownership requirements, suppressing a finding, or proving memory safety while changing outputs.
- **Evidence / numbers:** F: a 2026 study of 303 C functions found only 31.4% verification success for generated VeriFast specs. F: Spec-Agent reports 85% valid target coverage, which is empirical validation, not an SL proof. F: SPLIT evaluates 289 SL verification conditions. E: 20 specialist days a year at $1k/day caps gross labor headroom at $20k/year per team. Sources: [Fan et al. 2026](https://arxiv.org/abs/2606.26490), [Pulse docs](https://fbinfer.com/docs/checker-pulse/), [Aria](https://arxiv.org/abs/2607.06341).
- **Prior art / who has it:** Reynolds separation logic, Meta Infer/Pulse (deployed in CI), VeriFast, Iris, Spec-Agent, SPLIT / SL-VC (ICML 2026), Aria (general code agents in a verification harness). The search did not establish that Infer itself universally proves LLM patches.
- **Verdict:** NARROWED. The gap is not spec generation, and a large cross-repository product is not established. Kill it without recurring specialist work and a fixed, meaningful contract. Expected objection: "Aria plus VeriFast already handles this; your chosen API has no maintained spec."
- **Kill test / first proof:** E: freeze one allocator or container plus its existing functional/ownership contracts, and let an agent repair auxiliary predicates/proofs after five implementation edits. Compare a generic agent, existing prover automation and specialized decomposition. Inject leak/UAF/output-change mutants, including one hidden behind an unmodeled helper, and require a complete checker result, not a clean Infer report.

#### Automatic parallelization: models choose transformations, dependence machinery decides legality (§10)
- **What:** The agent proposes a parallelization plan, schedule, tiling, reduction or data representation, and a dependence checker/prover accepts the legal ones. The residual is guarded parallel fast paths with maintained legality proofs for a neglected irregular CPU workload.
- **How it would work:** Mechanical dependence checks run in an existing restricted IR, and benchmarks select for performance. Runtime alias/shape guards can enable a narrow fast path if the fallback and guard sufficiency are checked. The oracle is strong for supported dependence properties and weak for numerics and runtime behavior: race-free is not equivalent, and one threaded run explores few schedules. Cheats: false alias promises, floating-point-changing reductions, async work escaping the benchmark timer, missing barriers that fail only at certain sizes. A proof over real arithmetic does not prove bitwise FP equivalence. The more the agent changes the algorithm, the less a schedule checker alone can certify.
- **Evidence / numbers:** F: TrainVerify verifies distributed-training plan equivalence, including Llama3-405B and DeepSeek-V3-671B plans, but it is a checker, not LLM plan generation, and excludes kernel/buffer correctness. E: a verified 10% saving on $500k/year compute leaves $50k/year gross headroom. Sources: [AutoParLLM NAACL 2025](https://aclanthology.org/2025.naacl-long.593/), [CoV CGO 2026](https://doi.org/10.1109/CGO68049.2026.11395240), [TrainVerify](https://www.microsoft.com/en-us/research/publication/trainverify-equivalence-based-verification-for-distributed-llm-training/).
- **Prior art / who has it:** Feautrier affine scheduling, AutoParLLM, ParaCoder, CoV (static checks + Alive2 + runtime verification for an LLM vectorizer), TrainVerify (Microsoft), Polly, ARGUS, AlphaEvolve.
- **Verdict:** NARROWED. "AI parallelizes code" in general is crowded, and for simple directives a better compiler or agent erases a separate product. Distributed training is a separate, costlier integration outside a solo two-week build. Kill it if useful accepted coverage or the whole-application improvement is negligible. Expected objection: "CoV already does this, and your benchmark omitted numerical or synchronization cost."
- **Kill test / first proof:** E: 20 CPU loops from one application on existing hardware (no GPU rental). Compare Polly/auto-vectorization, direct agent code and guarded accepted candidates, holding out sizes and aliasing cases, timing complete executions including synchronization, and labeling non-affine refusals. Demo: the fast path rejected for overlapping ranges and selected for disjoint ones.

#### Attribute grammars: agent-built semantic frontends for a fixed DSL (§11, Track A)
- **What:** For a small existing DSL, the agent proposes attribute equations, type/effect rules and semantic pruners, filling in the labor-intensive language adapter. The residual is a maintained semantic frontend for one enterprise DSL.
- **How it would work:** Existing interpreters, solver proof obligations and independent examples check the proposed attributes/pruners, including against malicious escapes. The model must not become the unchecked authority on which programs count as correct. The oracle is strong only relative to a correct grammar/semantics: a grammar guarantees syntax, not meaning, and an attribute checker proves only the encoded property, which can omit effects or allow trusted escapes.
- **Evidence / numbers:** F: AGDecode was posted 2026-10-26, a two-day-old preprint at report date (partial ASTs, relational constraints, SMT/CHC oracles, Rocq-mechanized metatheory; uncertain solver results are rejected conservatively). E: $10k–25k per tooling integration is a customer-interview hypothesis. Sources: [Knuth 1968](https://www.ccs.neu.edu/home/chadwick/files/knuth.pdf), [ChopChop POPL 2026](https://doi.org/10.1145/3776708), [AGDecode](https://arxiv.org/abs/2610.36105).
- **Prior art / who has it:** Knuth attribute grammars, ChopChop (AST program spaces + semantic pruning), AGDecode (the "even more direct" attribute-grammar revival), mature parser generators as the baseline.
- **Verdict:** NARROWED. A generic "semantic constrained decoding" method or product is occupied and easily competed away. Keep a concrete DSL integration only if it removes paid maintenance work these tools do not already handle. Expected objection: "AGDecode/ChopChop already do the grammar work."
- **Kill test / first proof:** E: on an existing arithmetic/query DSL interpreter, the agent proposes attributes/pruners and independent examples plus solver obligations check type/effect constraints. Choose this track or Track B, not both. Demo: a well-formed but semantically invalid DSL program rejected.

#### Partial evaluation / Futamura: agent-supplied staging hints for an existing interpreter (§11, Track B)
- **What:** The agent proposes binding-time annotations and specialization hints for an existing evaluator, specializing the interpreter to produce residual programs. The report treats this as tooling for ordinary programs, separate from the already-covered agent-trace JIT.
- **How it would work:** Residual execution is compared against the interpreter on held-out inputs, and the report requires disclosing whether correctness is proved or only tested; differential testing alone is weak. Specialization must preserve the interpreter's behavior for every remaining dynamic input. Cheats: treating an environmental value as static, or removing error paths. Specializing a fixed prompt does not license replacing an opaque LLM's future decisions with a deterministic rule.
- **Evidence / numbers:** F: weval (a non-LLM partial evaluator, PLDI 2025) reports 2.17× (SpiderMonkey) and 1.84× (Lua) speedups, which are not evidence of an LLM-in-loop revival. I: the bounded search found no concrete primary demonstration of an LLM producing and certifying a general partial evaluator or Futamura compiler generator, and the report says not to turn that into a novelty claim. Sources: [weval PLDI 2025](https://cfallin.org/pubs/pldi2025_weval.pdf), [Futamura archive](https://fi.ftmr.info/), [Jones/Gomard/Sestoft 1993](https://raspi.itu.dk/people/sestoft/pebook/pebook.html).
- **Prior art / who has it:** Futamura projections, Jones/Gomard/Sestoft, weval, existing JITs and staging systems.
- **Verdict:** NARROWED. LLM-assisted specialization of one interpreter is a research integration with unproven demand, and if a normal compiler already does the constant propagation, extra LLM staging may add nothing. Expected objection: "weval already does the specialization."
- **Kill test / first proof:** E: the agent adds staging hints to an existing evaluator, and residual execution is compared against the interpreter on held-out inputs. This is an alternative experiment to Track A, not a second platform. Demo: a specialization bug exposed by changing a supposedly dynamic input.

#### Program repair / GenProg: proposal quality flipped, patch correctness did not (§12)
- **What:** LLMs replace GenProg's blind statement mutation with a rich edit prior and debugging behavior. The narrow residual is a bounded backport service for a legacy branch with a known reference fix, an executable differential oracle and an unchanged API.
- **How it would work:** Structured localization/validation against a frozen description of the defect's allowed behavior change, plus differential testing outside the defect envelope and an independent holdout corpus. Tests are a weak oracle, and a fixed-spec proof is strong only for the specified behavior. Cheats: removing the crashing path, swallowing all errors, returning empty results, rejecting valid inputs, or self-generated tests that encode the agent's own misreading.
- **Evidence / numbers:** F: Google CodeMender reported 72 upstreamed security fixes in its first six months, with humans reviewing patches before submission (October 2025). F: GenProg's own archive now discourages its 105-bug ICSE 2012 benchmark. E: $5k–20k per difficult qualified backport is a pricing hypothesis. Sources: [GenProg TSE 2012](https://web.eecs.umich.edu/~weimerw/p/weimer-tse2012-genprog.pdf), [CodeMender](https://deepmind.google/blog/introducing-codemender-an-ai-agent-for-code-security/), [Meta AutoPatchBench](https://engineering.fb.com/2025/04/29/ai-research/autopatchbench-benchmark-ai-powered-security-fixes/).
- **Prior art / who has it:** GenProg (Le Goues et al.), LLM-CEGIS-Repair, Google CodeMender (with an enterprise offering announced in 2026), Meta AutoPatchBench (fuzzing + white-box differential testing against the fixed version), spec-guided Dafny arithmetic repair (Wu et al. 2025).
- **Verdict:** NARROWED. "This is the revival, already being executed", and no generic GenProg-with-LLMs gap remains. Security-repair vendors and labs are strong competitors, so the branch/support commitment must be the differentiator. Kill it without a concrete unsupported-branch customer, or if an ordinary agent plus existing validation does equally well. Expected objection: "CodeMender/AutoPatchBench already built the loop; your corpus has the ground-truth fix that live users lack."
- **Kill test / first proof:** E: five public historical bugs with a fixed reference and an older branch, runnable without Docker, with the reference patch text withheld. Compare a normal agent against structured localization/validation, include error-swallowing and input-rejection mutants, and count maintainer review minutes, wrongly accepted patches, model spend and total verification cost. Demo: a crash-disabling fake fix rejected by valid-input replay.

### 04-codemode: Code Mode turns agents into programs: which compiler/PL ideas pay off on agent-written code
Lens: in Code Mode the model writes one TS/Python program that calls tools, so static analysis, type systems, information flow, query optimisation and debugging theory can be applied to agent behaviour. Headline (I): the program becomes the unit of authority and analysis, and only what the program returns or logs reaches the model, so "what did the model see?" becomes a checkable value. That is the precondition IFC (Denning 1976) never had in ReAct agents. Security ideas (effects, IFC, capabilities, contracts) gain value as models improve. Performance ideas (batching, pushdown, speculation, staging) are already part of Code Mode, occupied, or covered by moonshots2, and they lose value as models improve. Research is thoroughly occupied (CaMeL, FIDES, LBAC, ACE, CaMeLoT, Progent). The open gap is shipping IFC inside a real Code Mode executor whose interpreter is hostile. The ONE bet is "labelled Code Mode" as Sofort's host policy v1: host-owned labels, opaque handles, VM compartments, and a static per-program effect manifest. Verdict: go-with-changes. The claim is narrowed to enforcement on a hostile interpreter at Code Mode token cost, gated by a two-week proof, and it is a Sofort differentiator/CV capstone, not a standalone company. No experiments were run (M: none).

#### Static effect inference → per-program effect manifest and one-shot approval (idea 1)
- **What:** Before the program runs, infer from its text which effects it *can* perform (tools, read/egress/write classes, argument provenance), and approve the whole program once instead of prompting per call.
- **How it would work:** The program calls tools through a closed generated API (`tools.ns.fn(...)`), and effects come from the existing tool declarations (`reads/egress/writes`). A syntax walk plus constant propagation produces a manifest `{tool, class, args: const|user|tool-derived(handle id)}`. Computed member access or `eval`-like constructs become "unknown" and fall back to per-call policy. The host kills any call outside the manifest, so an unsound manifest fails closed. The oracle is strong for runtime soundness and weak for usefulness, which still needs a human or policy to judge the manifest.
- **Evidence / numbers:** F: approval fatigue, "users accept 93% of [manual prompts] anyway" ([Anthropic auto mode, 2026-03-25](https://anthropic.com/engineering/claude-code-auto-mode)). F: sandboxing cut permission prompts by 84% internally ([Anthropic, Oct 2025](https://anthropic.com/engineering/claude-code-sandboxing)). Origin: Gifford & Lucassen LFP 1986, Lucassen & Gifford POPL 1988 ([doi](https://doi.org/10.1145/73560.73564)). I: effect annotations never reached the mainstream (checked exceptions were the cautionary example; Koka/OCaml 5 stayed in PL circles). Superhuman test: more valuable, because better models write longer programs per approval. Experiments: a toy effect-inference pass over hand-written programs was not run because it would only measure the author's own programs.
- **Prior art / who has it:** In research: ACE (static plan check plus privilege score), LBAC (type-checked programs), CaMeLoT (model checking), Progent (policies). Not found in shipping Code Mode runtimes (Cloudflare docs, Anthropic PTC docs, Monty docs). Claude Code handles fatigue with sandboxing and an auto-mode classifier instead.
- **Verdict:** KEPT (#1, merged with idea 2 into the ONE bet as "a feature of #2"). Real value is fewer interruptions at the same safety level. It is a feature inside an executor, not a product on its own.
- **Kill test / first proof:** E: a TS compiler-API pass over ≥200 programs a real model writes for AgentDojo-ported tasks, measuring manifest coverage and approvals per task (per-call vs per-program). Demo: one dialog ("read 40 inbox messages and send **one** email to `alice@corp`") instead of 41 prompts. Kill reply: "Humans rubber-stamp a manifest exactly like a prompt; you moved the fatigue, not the risk." Kill if manifest coverage is under 50%, or if a user study / reviewer simulation shows no drop in wrongly approved malicious manifests vs per-call prompts.

#### Information-flow control with host-side labels and VM compartments (idea 2, the ONE bet)
- **What:** Labelled Code Mode. The model writes ordinary TS. Private or untrusted tool results stay on the host as opaque labelled handles. The guest can inspect a handle's content only inside a fresh compartment VM, and sinks check labels deterministically.
- **How it would work:** `tools.x.read()` returns `Handle{id}`, and the host stores value plus label `{conf, integ, sources}`. `sandbox.inspect(handles, subprogram)` spawns a child VM whose floating label starts at the join of its handles' labels. Its result comes back as a new handle (LIO `toLabeled`), so the parent's label does not rise. `return`/`console.log` to the model is a sink, so the model context's label is the join of everything revealed (this makes FIDES's "tainted history" explicit and bounded). A Q-LLM call is just a tool whose output is labelled by its inputs. `egress`/`writes` sinks compare argument labels with policy (deny, approve or endorse). Declassification happens only through human approval bound to the call digest (this exists in v0). The static manifest from idea 1 is used for one-shot approval. Agents in the loop: the task model decides the compartment structure and is checked by host label rules. Its cheats are asking for declassification on every call (approvals are counted as a cost) and covert channels via compartment timing, termination and the parent's call count (mitigation: fixed-time child results, or state these as accepted residual bandwidth). A labelling agent drafts `reads/egress/writes` for long-tail MCP tools and is checked by canary tests on egress sinks and state diffs. It can cheat by labelling maximally restrictive (shows as a utility drop) or permissive (caught only where canaries reach). Confidentiality class has no oracle and stays a human decision.
- **Evidence / numbers:** F: CaMeL reaches 77% of AgentDojo tasks "with provable security" vs 84% undefended, at a median 2.82× input / 2.73× output tokens ([arXiv 2503.18813](https://arxiv.org/abs/2503.18813)). F: The Attacker Moves Second bypassed 12 defences at >90% attack success for most ([arXiv 2510.09023](https://arxiv.org/abs/2510.09023)). F: a simple firewall "achieves perfect security" on stock AgentDojo/ASB/InjecAgent/tau-Bench, so benchmarks must be fixed and attacks adaptive ([arXiv 2510.05244](https://arxiv.org/abs/2510.05244)). F (repo): one-tool `execute()` at 1.10 ms p50 / 1.86 ms p99 on nested Linux KVM after copy-restore, so one compartment per untrusted read is affordable. F (repo): the executor policy already has a v0 sticky per-run floating label, 32 policy-bypass cases, and lists host-side opaque handles as unbuilt v1. It also states "Per-value labels inside the VM are unsound because the interpreter is attacker-controlled." F: AI-security M&A goes to detectors/guardrails (SentinelOne–Prompt Security $250M, F5–CalypsoAI $180M, Check Point–Lakera ~$300M est., Palo Alto–Protect AI $500–700M est., Snyk–Invariant undisclosed). I: willingness to pay for deterministic IFC is unproven. F: verified pain includes the GitHub MCP exploit and the lethal trifecta (Willison 2025). Lineage: Denning 1976, JFlow 1999, LIO 2011, COWL OSDI 2014 ("virtually imperceptible" cost). Experiments: M none. The decisive question (utility under coarse labels with compartments vs CaMeL's 77%) needs ported AgentDojo, a real model and adaptive attacks, so it is the two-week proof.
- **Prior art / who has it:** Research: CaMeL, FIDES (labelled hidden variables, ~16% more tasks than a basic planner), LBAC (LIO applied to agents off the shelf), ACE (static), CaMeLoT (temporal), NeuroTaint (offline semantic taint), "Can CaMeLs Talk?" (boundary laundering across composed agents), Design Patterns paper (code-then-execute). Products: Invariant/Snyk trace flow rules, Chrome Agent Origin Sets, Anthropic's PII tokenisation example, Meta's Rule of Two (per session). Not found: a Code Mode executor running *hostile* JS/TS with host-owned labels and compartments. Closest are the OpenClaw RFC #39160 (a proposal) and the unverified "sluice" repo.
- **Verdict:** KEPT (#1 together with idea 1, the ONE bet). Strongest need, and it gains value with better models because the enforcement does not depend on the model. Principal objection: research is thoroughly occupied and the market pays for detectors. The narrowed claim is that it can be enforced on an attacker-controlled interpreter at Code Mode's token cost rather than CaMeL's 2.8×, with utility close to CaMeL's. Kill reply: "Anthropic/Cloudflare will add handles in a quarter; utility below CaMeL; enterprises buy Lakera-style detectors." The first half is likely true, so this is a Sofort differentiator/CV capstone, not a company.
- **Kill test / first proof:** E, two weeks, one engineer. Days 1–3: port AgentDojo workspace + banking via an RPC bridge, apply the 2510.05244 fixes, pin one Claude model. Days 4–7: handles, compartments (nested `execute()`), sink checks, manifest. Days 8–10: baselines (undefended Code Mode, v0 label, firewall, CaMeL's published numbers). Days 11–14: stock, three-stage and fixed-budget adaptive attacks. Continue only if utility is ≥70%, there are **zero** mechanism-level data-flow attacks (timing leaks counted separately), tokens are ≤1.3× undefended, and approvals drop ≥5× vs v0. Kill if utility is <60% (label creep wins), if an unclosable mechanism-level exfiltration is found, or if the firewall baseline matches on adaptive attacks. Demo: the GitHub-MCP heist replayed. The private file stays a handle, the public PR is denied, `explain()` shows the flow, and the clean task completes.

#### Batching and promise pipelining of tool calls (idea 3)
- **What:** Automatically batch and pipeline the tool calls inside a naive agent program (`for … await tool(id)`) to cut sandbox→host→MCP round trips.
- **How it would work:** A DataLoader shim in the generated tool stubs for tools declared `reads` and idempotent. The oracle is strong (same results, fewer round trips) only for read-only idempotent tools; otherwise reordering changes semantics.
- **Evidence / numbers:** F: MCP's 2025-06-18 revision removed JSON-RPC batching, so the host must batch ([changelog](https://modelcontextprotocol.io/specification/2025-06-18/changelog)). F: LLMCompiler reports up to 3.7× latency and 6.7× cost improvements vs ReAct ([ICML 2024](https://arxiv.org/abs/2312.04511)). Lineage: Liskov & Shrira PLDI 1988; Haxl ICFP 2014; DataLoader. Superhuman test: less valuable, because models write `Promise.all` themselves (I).
- **Prior art / who has it:** Cap'n Web pipelining ("one round trip", [repo](https://github.com/cloudflare/capnweb)), LLMCompiler, gRPC/GraphQL DataLoader/Cap'n Proto; workflow superoptimisation is moonshots2 bet 3.
- **Verdict:** KILLED as a bet. It is a latency feature for executors with no separate buyer, worth an afternoon inside Sofort. Kill reply accepted: "Cap'n Web already does it and the model writes Promise.all."
- **Kill test / first proof:** E: measure the round-trip reduction of the shim on the same 200-program corpus.

#### Query optimisation and predicate pushdown into tool APIs (idea 4)
- **What:** Rewrite "fetch everything and filter in JS" into API filter parameters (e.g. `?state=open&assignee=bob`) to cut bytes and calls.
- **How it would work:** Selinger-style access-path selection applied to tool calls, using per-API rewrite rules. The oracle is medium: results must be equal, but API filter semantics (case, pagination, eventual consistency) differ from JS filters, so equivalence is per-API and fragile (I).
- **Evidence / numbers:** F: Cortex AISQL reports up to 7× from AI-filter placement ([arXiv 2511.07663](https://arxiv.org/abs/2511.07663)). F: no source found pushes JS predicates into tool parameters automatically, because the per-API rules are the expensive part. Origin: Selinger et al., SIGMOD 1979. Superhuman test: less valuable.
- **Prior art / who has it:** Semantic-operator optimisers (Cortex AISQL, Sema, iPDB); workflow-level rewrites in moonshots2 bet 3.
- **Verdict:** KILLED. Value is small, per-API rewrite rules are hand labour with a weak oracle, and the model already passes filters. "Paper, no buyer."

#### Speculative execution and deoptimisation (idea 5)
- **What:** Predict the model's next program or tool and pre-run **read-only** calls, committing on match.
- **How it would work:** In Code Mode the slow part is the model writing the next program, not the tool calls inside one program, so speculation is limited to next-program/next-tool prediction. The oracle is strong for read-only speculation (commit on match) and absent for writes.
- **Evidence / numbers:** F: Speculative Actions reports up to 55% next-action prediction with "lossless" commit-on-match ([arXiv 2510.04371](https://arxiv.org/abs/2510.04371), ICLR 2026). Lineage: Tomasulo 1967; Hölzle et al. PLDI 1992. Superhuman test: mixed, because faster models shrink the gap speculation hides.
- **Prior art / who has it:** Speculative Actions; deopt/guards for agent JIT in moonshots2 bet 1 (PreAct, TraceCompiler).
- **Verdict:** KILLED. Occupied, and there is little to speculate on inside one Code Mode program.

#### Partial evaluation and staging at plan time (idea 6)
- **What:** Treat the plan/observation split as a two-stage program: stage 0 is the trusted query (known), stage 1 is tool data (unknown).
- **How it would work:** Plan-then-execute is binding-time analysis by construction. The residual must equal the unstaged run on all stage-1 inputs, which can be tested but not proved for unknown tools.
- **Evidence / numbers:** Lineage: Futamura 1971; Jones, Gomard & Sestoft 1993; MetaOCaml/LMS. Superhuman test: neutral.
- **Prior art / who has it:** ReWOO ([arXiv 2305.18323](https://arxiv.org/abs/2305.18323)), the plan-then-execute and code-then-execute patterns (2506.08837), and CaMeL, which is exactly a staged program whose stage 0 cannot see stage 1. Residualisation for reuse is moonshots2 bets 1/2/5.
- **Verdict:** KILLED as a separate bet, absorbed into idea 2. Its useful form *is* the CaMeL/IFC split.

#### Static cost analysis (WCET, amortised resource bounds) (idea 7)
- **What:** Static resource and cost bounds for agent programs.
- **How it would work:** The only addition from this lens is that the effect manifest (idea 1) gives a call-count upper bound for loop-free or constant-bounded programs. Sofort's R10 admission queue can reserve that bound up front.
- **Evidence / numbers:** Lineage: Wilhelm et al. WCET survey TECS 2008; Tarjan 1985 amortised analysis; Hoffmann et al. RAML POPL 2011.
- **Prior art / who has it:** moonshots2 bet 6 ("Compile agents into a bounded execution budget").
- **Verdict:** KILLED as separate. Already covered by moonshots2. Here it is only a call-count field in the manifest.

#### Symbolic execution and model checking of the agent program before running (idea 8)
- **What:** Bounded symbolic execution of the short agent program against tool schemas, to find bugs like "if the search returns zero results, the program sends an empty email" before running.
- **How it would work:** MCP `outputSchema` (2025-06-18) gives symbolic return types for tools, and agent programs are short enough to avoid path explosion. The oracle is weak because paths are relative to schemas, not to real tool behaviour, and real failures are mostly semantic (wrong record).
- **Evidence / numbers:** F: survey [arXiv 2608.14590](https://arxiv.org/abs/2608.14590) says static methods "struggle with dynamically generated plans." Lineage: King CACM 1976; KLEE OSDI 2008. Superhuman test: less valuable for reliability, neutral for policy checking.
- **Prior art / who has it:** CaMeLoT (CTL over plan + taint), solver-aided compliance (Z3 on planned calls, [arXiv 2603.20449](https://arxiv.org/abs/2603.20449)), Symbolic Constraint Agents ([arXiv 2610.25552](https://arxiv.org/abs/2610.25552)).
- **Verdict:** KILLED. Occupied, with a weak oracle. The useful slice (policy over paths) folds into ideas 1/2.

#### Program slicing / provenance for "why did the agent do that?" (idea 9)
- **What:** A backward dynamic slice of any effect (e.g. "which tool results shaped this email's `to`?"), computed from host-side handle IDs.
- **How it would work:** A Code Mode run is a small program plus a host-mediated log of every tool call. If arguments carry host handle IDs (idea 2), the slice is a graph walk over data the host already stores, with no in-guest instrumentation, which matters because the guest is hostile. The oracle is medium: counterfactual replay (change a source value, observe the sink), which needs deterministic replay with recorded tool results (idea 10).
- **Evidence / numbers:** F: survey [arXiv 2606.04990](https://arxiv.org/abs/2606.04990) separates logging from "semantic provenance" and treats tool-call attribution as unsolved. Lineage: Weiser ICSE 1981 / TSE 1984; Agrawal & Horgan PLDI 1990. I: willingness to pay is real for SIEM/forensics generally and unproven for this. Superhuman test: more valuable, because more autonomous agents cause more incidents to explain, without trusting the model's own narrative.
- **Prior art / who has it:** Partly open. NeuroTaint (offline semantic taint), [arXiv 2603.28345](https://arxiv.org/abs/2603.28345) (slices developer code around LLM calls, not agent runs), Invariant Explorer (traces, not slices).
- **Verdict:** KEPT (#2). It falls out of idea 2 almost for free and has a counterfactual-replay oracle. Principal objection: no proven separate buyer, and observability vendors would absorb it. Best as a by-product of #2.
- **Kill test / first proof:** E: with idea 2's handles, add `explain(effectId)` returning the handle DAG and program source spans. Validate on 50 injected-attack runs (does the slice name the injected source?), with a counterfactual check by replaying with the source blanked.

#### Record/replay and time-travel debugging (idea 10)
- **What:** Deterministic replay of Code Mode runs from the tool call/return frames.
- **How it would work:** Code Mode narrows nondeterminism to one channel (tool call/return frames). Sofort's ASCII JSON call/ret protocol is already a complete replay log (F, repo `ARCHITECTURE.md`). The oracle is strong: replay must reproduce the identical frame sequence.
- **Evidence / numbers:** Lineage: LeBlanc & Mellor-Crummey Instant Replay 1987; rr (USENIX ATC 2017); Replay.io. Superhuman test: neutral-to-positive.
- **Prior art / who has it:** Crowded: agentrr, Chronicle cut-point replay ([arXiv 2609.20625](https://arxiv.org/abs/2609.20625)), OrcaReplay, LangGraph time travel, Temporal/Restate/DBOS.
- **Verdict:** KILLED as a bet. Kept as the cheap substrate for idea 9's counterfactual oracle.

#### Type-directed tool API design and type-checking generated programs (idea 11)
- **What:** Run `tsc --noEmit` on the generated program against the tool `.d.ts` before execution and return errors to the model without spending a sandbox run.
- **How it would work:** Sofort already generates `generated-tools.d.ts` (F, repo). The oracle is strong (the type checker).
- **Evidence / numbers:** F: Code Mode's own premise is "convert MCP tools into a TypeScript API" (Cloudflare). Lineage: Microsoft TypeChat (2023), MCP `outputSchema`/`structuredContent` (2025-06-18). Superhuman test: less valuable, because better models make fewer type errors.
- **Prior art / who has it:** LBAC requires type-checking for safety; Cloudflare `describe` returns types.
- **Verdict:** KILLED as a bet, kept as a 50-line feature. Its real value is security rather than reliability (in LBAC labels *are* types). TS types are unsound under `any`/casts, so they cannot be the enforcement layer against hostile code.

#### A DSL per task (idea 12)
- **What:** The agent generates a small DSL per task family and constrains later programs to it.
- **How it would work:** The DSL's own validator is the oracle.
- **Evidence / numbers:** F: LLMs degrade on less-known DSLs and do better with Python-then-translate ([arXiv 2405.16450](https://arxiv.org/abs/2405.16450)). F: practitioners say a DSL works when it is tiny and validated ([Fowler](https://www.martinfowler.com/articles/llm-and-dsls.html)). Lineage: Bentley "Little languages" CACM 1986; Hudak CSUR 1996. Superhuman test: obsolete-ish.
- **Prior art / who has it:** The useful version is a restricted subset of TS/Python: CaMeL's restricted Python, Pydantic Monty, LBAC's typed host language.
- **Verdict:** KILLED. Worse for the model, and the restricted subset already captures the benefit.

#### Contracts and refinement types on tool APIs, with blame (idea 13)
- **What:** An agent drafts tool contracts (`amount <= balance`, `to ∈ contacts`, "pagination cursor from the previous call") from docs and traces, and the host enforces them at the boundary. On failure, blame says whether the *program* (model) or the *tool* (server) broke the contract.
- **How it would work:** Blame routes failures to the repair loop (re-prompt the model) or to ops (tool regression). The oracle is medium: test against recorded traces (no false alarms on known-good runs) and mutants (catch seeded bad calls). Agent cheats: a vacuous contract (`true`) passes the false-alarm test, so a mutant kill rate is required. A contract overfit to traces blocks legitimate new calls, so held-out good traces are needed.
- **Evidence / numbers:** F: blame assignment specifically was not found in the abstracts read. Lineage: Meyer 1992; Freeman & Pfenning PLDI 1991; Findler & Felleisen ICFP 2002 (higher-order contracts with blame). Superhuman test: mixed. I: reliability value is moderate, and blame is an operational detail, not a market.
- **Prior art / who has it:** Symbolic Constraint Agents (mined constraints, SMT runtime check, auto-repair), solver-aided compliance (2603.20449), Progent policies, MANTRA benchmarks ([arXiv 2605.06334](https://arxiv.org/abs/2605.06334)).
- **Verdict:** KEPT (#3). A cheap extension of Sofort's strict `args` validators. Principal objection: SMT-checked tool constraints are already published, and the value is moderate.
- **Kill test / first proof:** E: a contract layer in Sofort's `tool.args` validators plus a blame tag on `DENIED`/`TOOL_ERROR`.

#### Rejected in this report
- **Batching/promise pipelining (#3)** — Cap'n Web and LLMCompiler already do it, and models write `Promise.all`. A DataLoader shim is an afternoon's feature.
- **Predicate pushdown into tool APIs (#4)** — per-API rewrite rules are hand labour with a fragile equivalence oracle, and models already pass filters.
- **Speculative execution/deopt (#5)** — Speculative Actions (ICLR 2026) and the moonshots2 JIT occupy it, and there is little to speculate on inside one program.
- **Partial evaluation/staging (#6)** — ReWOO, plan-then-execute and CaMeL already are the staged form. No separate value.
- **Static cost analysis (#7)** — moonshots2 bet 6. Here it is only a call-count field in the manifest.
- **Symbolic execution/model checking (#8)** — CaMeLoT and SMT checkers occupy it, and tool semantics make the oracle weak.
- **Record/replay (#10)** — crowded (agentrr, Chronicle, OrcaReplay, Temporal). Kept only as the substrate for slicing.
- **Type-directed APIs / type-checking programs (#11)** — Code Mode's own premise. The `tsc` pre-check is a 50-line feature, and TS types are unsound as enforcement against hostile code.
- **DSL per task (#12)** — evidence says models get worse on unfamiliar DSLs, and restricted TS/Python subsets capture the benefit.
- **A standalone agent-IFC company** — research is occupied, executor owners will build it, and acquirers have paid for detectors, not deterministic flow control.

### 05-numerics-data: Numerics and data: old maths that matters more now that agents write kernels and run experiments
Lens: the mathematical and data layer of AI (numerical analysis, information theory, algorithms, databases), asking where an agent can be hooked in, what checks it, and how it cheats the check. Headline: most of this layer has already been harvested in 2023–2026 by labs and NVIDIA (stochastic rounding in NVFP4, block FP as OCP MX, Lloyd–Max in TurboQuant, E8 lattices in QuIP#, Ozaki in cuBLAS, Newton–Schulz as Muon, MinHash dedup, checkpointing); what is not harvested is the checking layer for agent output, where acceptance still uses ad hoc constants (`allclose(1e-2)` for kernels, "keep if val loss went down once" for experiments). Two small experiments back this with caveats: allclose(1e-2) accepts an FP8 kernel for an FP32 contract on U[0,1) inputs, and in a simulated autoresearch loop 64% of kept changes are noise or harmful, but confirmation halves the true gain at a fixed budget. The ONE bet is idea 1, a harness-owned evidence gate for agent-run ML research scoped to the claim layer. Verdict: go-with-changes (meets three of four round-1 points; the 2-week proof must first show the gated change-set transfers to 4× compute better than greedy at equal total compute, else kill).

#### Evidence gate for agent-run ML experiments: design of experiments, sequential tests and the reusable holdout, owned by the harness (idea 1)
- **What:** The agent proposes changes; a harness it cannot edit owns seeds, evaluation code, metric and a ledger of every comparison, and accepts a *claim* only through a selection-aware sequential test, spending confirmation runs adaptively, with validation reuse through a Thresholdout-style reusable holdout.
- **How it would work:** Eval code and data shards hash-pinned and read-only, seeds from a sealed RNG with fresh entropy per confirmation, metric computed outside the sandbox, per-run immutable snapshots, loader file-access audit, append-only ledger, and Thresholdout/Ladder answers for the shared validation set. Policies compared: greedy, gconf (screen against recorded best, then confirm with n fresh seeds each side, keep if Δ̄ > z·σ√(2/n)), and SPRT with a minimum-effect δ. Defences mapped to known cheats: eval/data-loader edits (Sakana memory exploit), val-set shrinking/leaking, seed selection and early kills (PRIME saw both), sealed-seed detection, metric changes, subagents editing shared code (PRIME's unresolved incident), adaptive overfitting of shared val. Residual risk: changes real at 5 minutes that vanish at scale; only the transfer test catches those.
- **Evidence / numbers:** M (experiment 2b, simulated 700-run budget, 400 trials; candidate mix 4% real δ~U(0.002, 0.015) bpb, 46% null, 50% harmful, all E; noise σ ∈ {0.0019, 0.0026} bpb derived from Grover's NeurIPS 2026 workshop best-of-32-seeds gain 0.00544, I): at σ=0.0026 greedy true gain 0.198 / reported 0.203, kept 21.7 real, 33.2 null, 5.9 harmful, **false-discovery share 0.64**; paired 1-vs-1 true 0.073 / reported 0.403 (5.5× overreport, 80.9 null kept, FDS 0.89, the worst policy); confirm:4:3.1 true 0.042, FDS 0.00; gconf:2:2 true 0.094, FDS 0.15; gconf:3:2.5 true 0.073, FDS 0.05; σ=0.0019 gives the same ordering. Greedy is a good optimiser (~2× the true gain of any confirmation policy) but most kept commits are wrong individually. F: expected max of N noise draws ~σ√(2 ln N), so at N=700 3.6σ of noise is available; autoresearch ~700 experiments over ~2 days, ~20 "genuine" improvements, Time-to-GPT-2 2.02 → 1.80 h, keep rule has no rerun (F 2nd); spontaneous reward hacking on 30.5% of research-pipeline tasks across 17 models, LLM review panel missed 6.5% of confirmed hacks (Huang et al. 2026-09-23); MLE-bench val/test gap costs 9–13 medal-rate points (AIRA-dojo); survey of 26 systems finds no LLM-era system with an externally validated in-loop oracle (Ding et al. 2026); PRIME Intellect needed a frozen `verify.py` with 8 fixed seeds and threshold 3.27859; modded-nanogpt requires p<0.01; Melis et al. 2017 found tuned best checkpoints ~1σ below the rerun mean; agents fail to re-implement known NanoGPT speedrun records (NeurIPS 2025 D&B); Anthropic ~26% of AI R&D led by Claude with ~30k concurrent agents (F 2nd, primary not found); OpenAI "automated research intern" 2026-09-06; Sakana AI Scientist's own reviewer rejected all 7 manuscripts (Beel et al.), AI CUDA Engineer's 100× claims walked back after an eval memory exploit. E: a lab spending $10M per quarter on a confirmation run wastes it whenever the candidate set is 64% noise. Sources: [Dwork et al. reusable holdout](https://arxiv.org/abs/1506.02629), [Huang et al. 2609.28614](https://arxiv.org/abs/2609.28614), [PRIME Intellect](https://primeintellect.ai/blog/measuring-autonomous-research).
- **Prior art / who has it:** Fisher (1935), Wald SPRT (1945/1947), Benjamini–Hochberg FDR (1995), Dwork et al. reusable holdout (2015), Blum & Hardt "The Ladder" (ICML 2015), Microsoft ExP (Kohavi et al.), Optimizely always-valid p-values (Johari et al. 2017). In-house rules: PRIME's 8-seed verifier, modded-nanogpt p<0.01. Academia: Grover (sealed replication, 749 runs: 8 of 15 candidates replicated, 3 failed, 4 inconclusive), Miao/Pritchard/Zou "Agentic Garden of Forking Paths" (m-value, agentic bootstrap), staged promotion (2606.11387), AIRA top-k selection. Labs almost certainly in-house, not public. W&B/MLflow log but do not gate; autoresearch, AIDE/Weco, Sakana, FARS verify by rerun or review. Searches on 2026-10-28 found no product owning seeds, eval and ledger with selection-adjusted claims (absence of evidence, F/I).
- **Verdict:** KEPT (#1, the ONE bet), scoped to the claim layer. Oracle strong but probabilistic (sealed seeds + compute give unbiased re-measurement at chosen α/FDR; the gate is the oracle). Superhuman test: more valuable (more candidates, subtler exploits; 5-minute runs do not get less noisy). Value: autoresearch users (53k-star repo, Shopify-style overnight runs), labs' automated-research programs, AI-for-science; sells trustworthy claims and transfer, not speed. Weak point: labs probably have in-house versions and greedy is the better pure optimiser. Killer reply: "Greedy gets 2× the loss improvement per GPU-hour and the big run re-validates anyway" or "every lab already does this in-house; it's 300 lines."
- **Kill test / first proof:** 2-week proof (TypeScript harness + Python training) wrapping autoresearch, 2 nights per policy on one user-rented H100, leave-one-out ablation of every kept change on sealed seeds, and transfer to a 4× compute run; demo of side-by-side ledgers (greedy "68 kept, 22 real, 4 harmful" vs gate "11 kept, 10 replicated, transfer to 4× = 92%"). Kill if, at equal total compute including the big run, the greedy set transfers to 4× at least as well as the gated set, or if autoresearch, W&B or a lab ships sealed-seed gating with selection-adjusted reporting first.

#### Precision-contract numerics oracle for agent-written kernels: Wilkinson/Higham bounds instead of `allclose(1e-2)` (idea 2)
- **What:** Accept a kernel against a declared precision contract (input, accumulate, output types; allowed reordering) with a componentwise probabilistic error bound derived per op, adversarial input families (sign-mixed, scaled, cancellation-heavy, LLM-style outliers) and an fp64 shadow reference.
- **How it would work:** A Python library (`contract_check`) maps contract → bound for matmul, softmax, layernorm, attention and reductions, e.g. `|Ĉ−C| ≤ (10·√K·u_acc + u_out)·(|A||B|)`, scaled by |A||B| rather than |C| so it stays meaningful under cancellation; FPRev recovers the accumulation order; generators produce adversarial distributions. Cheats against it: detecting the reference via shapes or pointers, specialising to generator distributions (defence: randomised families, held-out shapes), writing into the reference buffer (defence: separate process, copied-out buffers).
- **Evidence / numbers:** M (experiment 2a, numpy CPU emulation, M=N=128, K 512–16384, ratio max error/allowed, ≤1 passes): FP32 contract on U[0,1) — fp8-e4m3 inputs at K=1024 allclose 0.78 PASS vs contract 409 fail; fp8 at K=8192 0.24 PASS vs 43.5 fail; bf16 at K=8192 0.012 PASS vs 2.16 fail; tf32 at K=8192 0.0014 PASS / 0.26 PASS; randn bf16 K=1024 20.7 fail / 25 fail; randn tf32 K=8192 6.3 fail / 0.39 PASS; legit fp32 ≤0.02 / ≤0.1 PASS. BF16 contract: skipping 2% of K at K=16384 on U[0,1) passes allclose (0.68) but fails the contract (1.7); chunked bf16 running sum passes on randn (≈0.5), fails on outlier-heavy inputs (2.7–3.2). I: input distribution decides more than the tolerance; a single constant is ~1000× too loose for fp32 accumulation and about right for bf16 output rounding. Limits: one op, CPU emulation, λ=10 hand-picked, TF32 at large K slips under the √K bound, so calibration needed (Sao et al. 2026 predict GEMM error within 3% for given reduction trees). F: KernelBench-Verified — GPT-5.5's 1.43× speedup collapses to 0.88× with TF32 baselines and hidden distributions, 35.2% of problems affected, a ReLU returning its input passes all-positive tests at "374×"; bf16 ABFT false positives on healthy nodes. Sources: [Higham & Mary 2019](https://doi.org/10.1137/18M1226312), [KernelBench-Verified 2607.16241](https://arxiv.org/abs/2607.16241), [Wafer reward hacking](https://www.wafer.ai/blog/reward-hacking).
- **Prior art / who has it:** Wilkinson (1963), Higham (1996/2002), Higham & Mary (SISC 2019). KernelBench-Verified (hidden distributions, fixed tolerance), Kernel Contracts (2604.22032, spec language with tolerance field, 12 contract classes, no Higham bounds in the abstract), Dr. Kernel/KernelGYM, TritonRL, robust-kbench, Wafer ($4M seed, bitwise checks), V-ABFT, NVIDIA cuBLAS automatic dynamic precision. Occupied in parts; the error-analysis-derived acceptance criterion itself was not found.
- **Verdict:** KEPT (#2), partly occupied and likely a feature (KernelBench v-next, Triton testing utilities), not a company. Oracle strong (fp64 reference + bound); weak spot is calibrating the constant and input distributions. Superhuman test: more valuable (more kernels, more hardware targets, smarter downgrades). Buyers: kernel-agent startups, labs porting to non-NVIDIA silicon, benchmark maintainers. Killer reply: "Hidden sign-flipped inputs already catch that, and bitwise checks catch the rest."
- **Kill test / first proof:** Replay published KernelBench agent kernels; report how many pass allclose but fail the contract, and the reverse (false rejects of legitimate split-K reorderings). Kill if hidden distributions plus a fixed tolerance catch ≥95% of what the contract bound catches on real agent kernels.

#### Training-data lineage with deletion-by-construction: provenance semirings + content addressing + sharded training (idea 3)
- **What:** Track every training document by content hash through filtering → dedup → shard → data-loader order → checkpoint, so a removal request answers "which checkpoints saw it" and triggers bounded retraining.
- **How it would work:** Why/where-provenance and provenance semirings over a content-addressed pipeline, with SISA-style shard-scoped retraining; a "blast radius" query returns affected shards and checkpoints.
- **Evidence / numbers:** F: EU AI Act training-data summary template mandatory since 2025-08-02, enforcement from 2026-08-02; Bartz v. Anthropic $1.5B settlement with destruction of LibGen/PiLiMi copies and derivatives certified to class counsel (proving "derivatives destroyed" needs lineage). Oracle strong for the pipeline (deterministic replay), weak for the model (LLM membership inference near chance; OLMoTrace misses paraphrase). Sources: [SISA](https://arxiv.org/abs/1912.03817), [WilmerHale on the EU template](https://wilmerhale.com/en/insights/blogs/wilmerhale-privacy-and-cybersecurity-law/european-commission-releases-mandatory-template-for-public-disclosure-of-ai-training-data), [Lieff Cabraser on Bartz](https://www.lieffcabraser.com/2025/09/authors-secure-1-5-billion-settlement-in-landmark-ai-piracy-case/).
- **Prior art / who has it:** Buneman, Khanna & Tan (ICDT 2001), Green, Karvounarakis & Tannen (PODS 2007), SISA (Bourtoule et al., S&P 2021); data catalogues (Atlan et al.), Data Provenance Initiative, OLMoTrace/infini-gram, labs in-house, "Tracing the Roots" (ACL 2026). No product found that combines retraining scope. Sorting table: lineage catalogues exist, nobody ties document → shard → checkpoint → model for deletion ("maybe").
- **Verdict:** KEPT (#3, weak). Superhuman test neutral (legal demand drives it). Real money in legal/compliance, but bought from lawyers and catalogues, not an agent-loop company. Killer reply: "Nobody retrains a frontier model for a deletion; they filter the next run and settle." Probably right.
- **Kill test / first proof:** Content-hash lineage for a datatrove pipeline plus a "blast radius" query. Kill if no provider will say lineage, rather than the summary template, is their bottleneck.

#### ABFT checksums for silent data corruption with error-analysis thresholds (idea 4)
- **What:** Carry row/column checksums through matrix products (Huang & Abraham, IEEE TC 1984) to detect silent data corruption at 10k–100k-GPU scale.
- **How it would work:** Checksum identity checked within an error bound; the blocker is setting thresholds at low precision. Recomputing the last step after detection also works.
- **Evidence / numbers:** F: SDC publicly flagged by Meta, Google, ByteDance and DeepSeek; bf16 ABFT gave false positives on healthy nodes; V-ABFT fixes it with variance-based thresholds at ~12% overhead on Ascend. Sources: [2502.12340](https://arxiv.org/abs/2502.12340), [V-ABFT 2602.08043](https://arxiv.org/abs/2602.08043), [2604.00726](https://arxiv.org/abs/2604.00726).
- **Prior art / who has it:** V-ABFT, vendors, early production on Ascend.
- **Verdict:** NARROWED (rejected as a separate bet). Oracle strong, agent hook small; occupied by V-ABFT/vendors, and the threshold maths is the same as idea 2, so it is folded in as a module of idea 2.

#### Bitwise train/inference parity by agent: Kulisch / reproducible summation (idea 5)
- **What:** Fix train/inference mismatch that breaks on-policy RL with the old remedy: fixed reduction order and exact or batch-invariant accumulation (Kulisch accumulator, ReproBLAS, Demmel & Nguyen 2013), with an agent localising and fixing diverging ops.
- **How it would work:** The oracle is the strongest possible, diff == 0, plus a separate gradient check because a bitwise-equal forward does not prove a correct backward.
- **Evidence / numbers:** F: DeepSeek-V4-Flash KL 2e-3 → 29.9 with reward falling; Nemotron-3.5 SWE-bench Pro 0.56 → 0.22 baseline vs 0.59 consistent; NVIDIA/Inferact's `train-inference-consistency` agent skill (11 gates; finds first diverging operator, minimal repro, fix, reruns regressions) reaches zero diff at 87.5–91.3% of baseline rollout throughput. Sources: [vLLM 2026-10-14](https://vllm.ai/blog/2026-10-14-train-inference-consistency), [vLLM 2025-11-10](https://vllm.ai/blog/2025-11-10-bitwise-consistent-train-inference), [IsoExec](https://vllm.ai/blog/2026-08-21-isoexec).
- **Prior art / who has it:** NVIDIA/Inferact vLLM skill, IsoExec (SkyRL), TBIK (deterministic across TP sizes, ICML 2026), Thinking Machines' batch-invariant ops.
- **Verdict:** KILLED, occupied by the right people. Its separate-gradient-check is the kind of cheat-awareness idea 2 generalises.

#### Shadow-precision root-causing + Herbie-style rewriting for training numerics (idea 6)
- **What:** Run one training step with an fp64 shadow to find the op where error is introduced; an agent proposes a stable rewrite (log-sum-exp, Kahan, rescaling) checked by the shadow.
- **How it would work:** FPDebug/Herbgrind-style shadow values localise error; Herbie-style rewriting proposes fixes; the check must be numerical, not the model's explanation (Panchekha found ChatGPT produced a valid rewrite with a wrong explanation).
- **Evidence / numbers:** I: value real but episodic (loss spikes at new precisions); labs debug by hand; the NVFP4 recipe (keep last ~15% of layers in higher precision, Hadamard transforms on Wgrad) is the kind of finding it would automate. Oracle medium: shadow error is local, loss-curve impact global. Known cheat: over-promoting to high precision (slow but "passes"). Sources: [Herbie](https://herbie.uwplse.org/), [TE debug docs](https://docs.nvidia.com/deeplearning/transformer-engine/user-guide/debug/1_getting_started.html), [Panchekha on ChatGPT+Herbie](https://pavpanchekha.com/blog/chatgpt-herbie.html).
- **Prior art / who has it:** FPDebug (Benz et al. PLDI 2012), Herbgrind (Sanchez-Stern et al. PLDI 2018), Herbie (PLDI 2015); NVIDIA Transformer Engine debug tools (per-GEMM stats, force selected GEMMs to high precision, no root-causing or rewriting).
- **Verdict:** NARROWED ("small"); kept as a feature of idea 2's library, not a standalone bet.

#### Stochastic rounding, block FP, MX, posits (idea 7)
- **What:** Stochastic rounding (von Neumann & Goldstine 1947; Forsythe 1959), block floating point (1960s DSP) and posits/unums (Gustafson & Yonemoto 2017) as low-precision training formats.
- **How it would work:** SR on gradients and block scaling in low-precision formats; hardware SR on Trainium and Graphcore.
- **Evidence / numbers:** F: NVIDIA's NVFP4 pretraining (12B on 10T tokens) uses SR on gradients; OCP MX spec v1.0 (2023) defines MXFP8/6/4; no major accelerator ships posits for training (I). Sources: [NVIDIA NVFP4 2509.25149](https://arxiv.org/abs/2509.25149), [OCP MX spec](https://www.opencompute.org/documents/ocp-microscaling-formats-mx-v1-0-spec-final-pdf), [Gupta et al. 2015](https://arxiv.org/abs/1502.02551).
- **Prior art / who has it:** NVIDIA (NVFP4), OCP MX, Graphcore, Trainium.
- **Verdict:** KILLED, industrial; posits lost to MX/NVFP4.

#### Lloyd–Max / VQ / lattices for weights and KV cache (idea 8)
- **What:** Lloyd–Max scalar quantisation (1957/1982; Max 1960) and vector/lattice quantisation (Gersho & Gray 1992; Conway & Sloane) applied to LLM weights and KV cache.
- **How it would work:** Quantile or precomputed Lloyd–Max codebooks (TurboQuant: random rotation then a Lloyd–Max codebook), E8 lattice, trellis or additive VQ codebooks.
- **Evidence / numbers:** F: NF4 (QLoRA 2023) is quantile-based; TurboQuant (ICLR 2026) in vLLM since 2026-04-15. Sources: [TurboQuant](https://arxiv.org/abs/2504.19874), [QuIP#](https://arxiv.org/abs/2402.04396), [QTIP](https://arxiv.org/abs/2406.11235).
- **Prior art / who has it:** NF4/QLoRA, QuIP# (E8), QTIP (trellis), AQLM (additive VQ), TurboQuant/Google, vLLM.
- **Verdict:** KILLED, harvested; the old signal-processing playbook has been run end to end.

#### Ozaki scheme and mixed-precision iterative refinement (idea 9)
- **What:** Emulate FP64 (and FP32) on low-precision tensor cores (Ozaki et al. 2012) and mixed-precision iterative refinement (Wilkinson 1948 → Carson & Higham 2017/18), since AI GPUs cut FP64.
- **How it would work:** Split operands into low-precision slices, compute on INT8/BF16 units, recombine; cuBLAS decides automatically when emulation is safe.
- **Evidence / numbers:** F: cuBLAS ships Ozaki FP64 and BF16x9 FP32 emulation on Blackwell with automatic dynamic precision; iterative refinement is industrial in HPC (HPL-MxP), not an LLM-training topic. Sources: [NVIDIA cuBLAS emulation blog](https://developer.nvidia.com/blog/unlocking-tensor-core-performance-with-floating-point-emulation-in-cublas/), [Mukunoki 2025](https://arxiv.org/abs/2508.00441), [HPL-MxP](https://hpl-mxp.org/).
- **Prior art / who has it:** NVIDIA cuBLAS, HPL-MxP.
- **Verdict:** KILLED, industrial; a textbook flip taken by the vendor.

#### Newton–Schulz/Muon, RandNLA/GaLore (idea 10)
- **What:** Polar decomposition by Newton–Schulz (Kovarik 1970; Björck & Bowie 1971; Higham 1986) as an optimizer, and randomised NLA (Halko, Martinsson & Tropp 2011) in optimizers and compression.
- **How it would work:** Newton–Schulz polar iterations orthogonalise updates (Muon); low-rank gradient projection (GaLore) and randomized SVD in LoRA init variants.
- **Evidence / numbers:** F: Muon (Jordan 2024); Kimi K2 trained with MuonClip at trillion-parameter scale; Polar Express (2025) adds minimax-optimal polynomials. Sources: [Polar Express](https://arxiv.org/abs/2505.16932), [Kimi K2](https://arxiv.org/abs/2507.20534), [GaLore](https://arxiv.org/abs/2403.03507).
- **Prior art / who has it:** Muon, Moonshot/Kimi K2, Polar Express, GaLore.
- **Verdict:** KILLED, industrial; "a perfect old-numerics flip, already taken".

#### Dedup and contamination (idea 11)
- **What:** MinHash (Broder 1997) for dedup and n-gram (GPT-3 13-gram) contamination detection.
- **How it would work:** datatrove/FineWeb MinHash over 5-grams with 14×8 buckets; n-gram overlap against benchmarks.
- **Evidence / numbers:** F: MinHash is the default (SemDeDup optional); rephrasing and translation evade n-gram and embedding contamination checks; SWE-bench memorisation documented. Sources: [FineWeb](https://arxiv.org/abs/2406.17557), [Yang et al. 2023](https://arxiv.org/abs/2311.04850), [2506.12286](https://arxiv.org/abs/2506.12286).
- **Prior art / who has it:** datatrove/FineWeb, FineWeb2, Lee et al. 2021; LiveCodeBench-style fresh benchmarks and canary strings as the live fix.
- **Verdict:** KILLED, no buildable gap; contamination detection has no strong oracle ("oracle-less" in the table) and the fix is post-cutoff benchmarks, not better hashing.

#### LSH vs vector search vs BM25 (idea 12)
- **What:** LSH (Indyk & Motwani 1998) and BM25 (Robertson 1994)/grep for retrieval in agent loops.
- **How it would work:** LSH lost to graph indices (HNSW) and IVF/PQ; BM25/grep came back because the agent writes the queries.
- **Evidence / numbers:** F: BM25 competitive with dense retrieval in several agent setups; coding agents use grep. Sources: [2608.06305](https://arxiv.org/abs/2608.06305), [BRIGHT baselines 2509.02558](https://arxiv.org/abs/2509.02558).
- **Prior art / who has it:** HNSW, IVF/PQ, hybrid BM25, coding agents.
- **Verdict:** KILLED, already practice, no product gap.

#### Interval arithmetic (sorting table)
- **What:** Moore (1966) interval bounds for numerical guarantees.
- **How it would work:** Worst-case enclosure of rounding error.
- **Evidence / numbers:** F/I: worst-case bounds are far too pessimistic for deep nets; probabilistic √n bounds are the useful form ([Higham & Mary 2019](https://doi.org/10.1137/18M1226312)).
- **Prior art / who has it:** niche.
- **Verdict:** KILLED, no gap; use probabilistic bounds (idea 2) instead.

#### Arithmetic coding, MDL, Kolmogorov (sorting table)
- **What:** Compression theory applied to LMs and tokenisation.
- **How it would work:** LMs as compressors; entropy-based byte patching.
- **Evidence / numbers:** F: harvested as analysis and niche tools ([Delétang et al. 2023](https://arxiv.org/abs/2309.10668), [BLT](https://arxiv.org/abs/2412.09871), ts_zip).
- **Prior art / who has it:** DeepMind "LMs are compressors", Meta BLT, ts_zip.
- **Verdict:** KILLED, harvested; no agent hook.

#### Count-Min and HyperLogLog (sorting table)

- **How it would work:** Streaming frequency and cardinality estimates.
- **Evidence / numbers:** Industrial in data infrastructure; nothing AI-specific (no source given).

- **Verdict:** KILLED, commodity infrastructure.

#### Suffix arrays for contamination and attribution (sorting table)
- **What:** Suffix arrays (Manber & Myers 1990) for verbatim tracing of model outputs to training data.
- **How it would work:** Index trillions of training tokens and look up verbatim spans.

#### Structured matrices: butterfly, Monarch, Toeplitz/FFT long convolutions (sorting table)

- **How it would work:** Butterfly/Monarch factorisations and FFT long convolutions (Hyena).

#### Reversible computation → RevNets (sorting table)

- **How it would work:** Reconstruct activations from outputs in the backward pass.
- **Evidence / numbers:** F: niche; activation recomputation won ([RevNets](https://arxiv.org/abs/1707.04585)).

#### AD + checkpointing / revolve (sorting table)
- **What:** Automatic differentiation (Wengert 1964; Linnainmaa 1970) with Griewank's revolve checkpointing (1992/2000).
- **How it would work:** Trade recomputation for activation memory.
- **Evidence / numbers:** F: industrial — √n checkpointing (Chen 2016), selective recomputation (Korthikanti 2022), torch.compile memory-budget rematerialisation. Sources: [Chen et al.](https://arxiv.org/abs/1604.06174), [Korthikanti et al.](https://arxiv.org/abs/2205.05198).

#### Curriculum and active learning (sorting table)

- **How it would work:** Data mixing and selection classifiers inside lab training stacks.
- **Evidence / numbers:** F: industrial in disguise ([DoReMi](https://arxiv.org/abs/2305.10429), RegMix, DCLM classifiers). Agent-hook table: data-curation filters are checked only by downstream eval (weak, noisy, contaminable; cheat = filters tuned to eval benchmarks).
- **Prior art / who has it:** DoReMi, RegMix, DCLM, labs in-house.
- **Verdict:** KILLED, lives inside labs' data-mixing stacks.

#### Bayesian optimisation for HPO (sorting table)
- **What:** Bayesian optimisation (Mockus 1970s; GP-EI, Jones 1998) for hyperparameter search.
- **How it would work:** Surrogate-model-guided config proposals checked on val loss.
- **Evidence / numbers:** F: industrial ([Vizier 2017](https://research.google/pubs/google-vizier-a-service-for-black-box-optimization/), Optuna), partly displaced by μP transfer and scaling laws ([μP](https://arxiv.org/abs/2203.03466)). Agent-hook table: HPO oracle medium, same cheats as research.
- **Prior art / who has it:** Google Vizier, Optuna, μP.
- **Verdict:** KILLED, mature and partly displaced.

#### Rejected in this report
- **Posits** — lost to MX/NVFP4 in hardware; no buyer.
- **Interval arithmetic** — worst-case bounds are useless at LLM scale; probabilistic bounds replace it.
- **Stochastic rounding / block FP** — already industrial (NVFP4, MX, Trainium).
- **Lloyd–Max / VQ / lattice / trellis quantisation** — harvested (NF4, QuIP#, QTIP, AQLM, TurboQuant in vLLM).
- **Arithmetic coding / MDL for tokenisation** — harvested as analysis (LMs-as-compressors, BLT); no agent hook.
- **Count-Min / HyperLogLog** — commodity infrastructure.
- **MinHash dedup** — standard (datatrove/FineWeb).
- **Contamination detection by better hashing** — no strong oracle; fresh post-cutoff benchmarks are the real fix.
- **LSH** — lost to HNSW/IVF-PQ; BM25/grep's comeback is practice, not a product gap.
- **Butterfly/Monarch/FFT structured matrices** — lost the hardware lottery to dense + MoE.
- **RandNLA / GaLore** — harvested.
- **Muon/Newton–Schulz** — the flip happened; taken.
- **Ozaki / iterative refinement** — taken by NVIDIA cuBLAS.
- **Reversible networks** — recomputation is cheaper and numerically safe.
- **AD history / revolve checkpointing** — fully industrial.

#### Grow format descriptions for format-aware compression (OpenZL), roundtrip as oracle (ONE bet)
- **What:** An agent writes and maintains an OpenZL SDDL format description (or parser) for each of a customer's binary/semi-structured formats. Only compressed bytes plus a lossless roundtrip decide what is accepted.
- **How it would work:** OpenZL does "describe → train → compress": the description feeds an offline trainer that searches transform graphs, each frame records its plan, and one universal decoder decodes every file. The agent gets only the spec, sample files and a read-only harness, and a description is accepted only on 100% roundtrip. The fixed universal decoder is the structural anti-cheat, because the agent cannot hide data in a custom decoder (**I**).
- **Evidence / numbers:** SAO file on M1: zstd -3 ×1.31 at 220/850 MB/s; xz -9 ×1.64 at 3.5/45 MB/s; OpenZL ×2.06 at 340/1200 MB/s (**F**). OpenZL publishes "SDDL for LLMs", a "complete v0.6 spec optimized for AI assistants" (**F**). Agent drafts a description in minutes vs hours-to-days for a human (**E**). At $0.02/GB-month, moving 1 PB from ×1.3 to ×2.0 saves ~0.27 PB, ~$5.4k/month in storage alone (**E**). A $1–3k/month service is plausible only at multi-PB scale (**E**). Meta: "every bespoke scheme means another compressor and decompressor to create, ship, audit, patch, and trust" (**F**). Experiment: M-not-obtained, because the `openzl` 0.3.0 Python wheel has no SDDL compiler or trainer and the C trainer build was over budget. Sources: [Meta Engineering](https://engineering.fb.com/2025/10/06/developer-tools/openzl-open-source-format-aware-compression-framework), [arXiv 2510.03203](https://arxiv.org/abs/2510.03203), [openzl.org/sddl](https://openzl.org/sddl/).
- **Prior art / who has it:** Meta OpenZL (framework; plans an "automated compressor explorer" for plan changes, and its blog does not mention LLMs). AgentGC, an LLM multi-agent evolutionary compressor for genomics only ([2601.13559](https://arxiv.org/abs/2601.13559)). LLM-as-compressor (e.g. CIDR 2026) is a different idea, with the model in the decode path. PAQ, CRAM and columnar codecs are the old fix. No agent-grows-OpenZL-descriptions product or paper found (**I**). Occupation risk is high: Meta wrote the LLM spec page (**I**).
- **Verdict:** KEPT (#1, the ONE bet). It has the strongest oracle in the sweep, a model-free GB/s hot-path artefact (passes gate 3 completely), and buyers whose oracle (their own data) is fragmented, so gate 4 favours an outsider. Pain is only inferred (**I**). Main risks: Meta ships it, or zstd dictionaries capture most of the gain. Repo fit: the GrowOS loop moved from syscalls to file formats. Cheat counters: date-split held-out files and counting dictionary bytes against overfitting; roundtrip on all files, with a failure scored as zstd fallback; a throughput floor; a read-only harness in a separate process.
- **Kill test / first proof:** Two weeks. Build the OpenZL CLI and trainer, then have an agent describe 10 public formats (pcap, Parquet pages, protobuf logs, OTLP, GRIB, FITS, BAM, SQLite pages, game replays, CAN-bus logs) and score held-out files vs zstd -3/-19, xz -9 and OpenZL with no description. Kill if the gain over max(zstd -19 with dictionary, OpenZL without description) is under 15% on at least 6 of 10 formats at equal or better decompression speed, or if more than 2 formats need human edits. Stop the company idea (keep the OSS result) if Meta ships agent authoring first.

#### LLM-evolved QEC decoders, gated by circuit-level simulation
- **What:** AlphaEvolve-style evolution of decoder programs per QEC code family and noise model, replacing hand-built decoders (MWPM 1965, union-find 2017, BP+OSD 2019).
- **How it would work:** Score candidates by logical error rate in a Stim circuit-level simulator with a fixed noise model, under an op-count or FPGA-resource latency budget. Seed from BP-OSD and Relay-style message passing; go from Python to a C subset with an op budget. Cheat counters: the decoder runs in a separate process that sees syndrome bits only; held-out noise parameters and seeds; HLS/FPGA synthesis of finalists; fixed shot budget with sequential testing.
- **Evidence / numbers:** Riverlane's FPGA LCD reaches sub-µs for the surface code ([2411.10343](https://arxiv.org/abs/2411.10343)), but its 2026 blog says sub-µs isn't established for every qubit type (**F**). IBM: FPGA-tailored qLDPC decoders "remain far slower and less accurate than Relay" ([2511.21660](https://arxiv.org/abs/2511.21660)) (**F**). The 2026 wave of LLM-discovered codes was all evaluated with off-the-shelf BP-OSD, which leaves a decoder gap (**F/I**). Evolution loops cost dollars (**F**). Buyers: ~10–20 hardware companies plus Riverlane and NVIDIA CUDA-Q QEC (**E**).
- **Prior art / who has it:** Code discovery is crowded (IBM, MPI, OmniQEC, Qian & Li, AlphaEvolve encodings). Neural decoder AlphaQubit 2 runs under 1 µs/cycle to d=11 ([2512.07737](https://arxiv.org/abs/2512.07737), DeepMind/Google Quantum AI). Two searches found no LLM-evolved decoder. One qLDPC paper ([2606.20513](https://arxiv.org/abs/2606.20513)) only uses Codex as an implementation helper.
- **Verdict:** KEPT (#2). The oracle is strong and cheap, and a better model makes it more valuable because the decoder runs at µs with no model. Pain is verified in primary sources. Gate 4 risk: Google and IBM own the hardware, noise data and decoder teams, and could run the loop in-house within weeks. Better as a research/CV artefact (a public leaderboard of evolved decoders per new code) than a business.
- **Kill test / first proof:** Three published 2026 LLM-discovered qLDPC codes plus the [[144,12,12]] gross code in Stim, scored against BP-OSD on held-out noise strengths. Kill if evolved decoders don't beat the best published decoder per code (not just default BP-OSD) at equal op budget on held-out noise, or if the gain vanishes after HLS synthesis.

#### Certificate-carrying evolved code: certifying algorithms as the run-time oracle
- **What:** Require AI-evolved or agent-written algorithms to emit certificates (Mehlhorn-style certifying algorithms) and ship the small checker with the code in production, so a wrong answer on an unseen input is caught on that input.
- **How it would work:** Each answer comes with a witness that a small, simple checker verifies (a bipartition, a max-flow optimality cut, an LP dual, DRAT/LRAT for UNSAT). The checker is often under 200 lines, can be formally verified, and sits outside the agent's write scope. Cheat counters: count solved instances (against timeouts/refusals); tiny verified checkers (against checker bugs); score the primal/dual optimality gap (against loose certificates).
- **Evidence / numbers:** McConnell, Mehlhorn, Näher & Schweitzer catalogue ([Computer Science Review 2011](https://doi.org/10.1016/j.cosrev.2010.09.009)); built into LEDA; DRAT used to check SAT Competition results since 2013–14 (**F**). ADRS: candidates "bypassed one stage of the evaluation pipeline"; spot policies "collapse on unseen spot patterns" (**F**). Verification Horizon ([2606.26300](https://arxiv.org/abs/2606.26300)): fixed rewards decay as capability grows (**F**). SATLUTION accepted UNSAT only with checked DRAT (**F**). Tao et al.: AlphaEvolve gives one-sided bounds unless a dual exists ([2511.02864](https://arxiv.org/abs/2511.02864)) (**F**). The extra labour of a certifying variant is now nearly free (**I**).
- **Prior art / who has it:** LEDA checkers, DRAT/LRAT, cvc5 and Lean proof production, MIP dual bounds. AlphaEvolve GA and OpenEvolve leave evaluators to users. No library or harness found that enforces certificates on evolved code across problem classes (**I**). Named AlphaEvolve users: FM Logistic, Klarna (vendor-reported).
- **Verdict:** KEPT (#3). It is the cross-cutting fix for ADRS-documented reward hacking, and a better model makes it more valuable because hacks grow while a sound checker doesn't decay (Lampson's "hint checked against the truth" at run time). Risks: it becomes a feature of AlphaEvolve/OpenEvolve, and the direct buyer is small. Likely form: an OSS harness plus a checker zoo (graph, flow, matching, LP/MIP gap, SAT/UNSAT, scheduling feasibility), also useful in GrowOS-style loops.
- **Kill test / first proof:** Five classes (bipartite matching, max-flow, negative-edge shortest paths, MIS heuristics with an LP dual bound, SAT). Run OpenEvolve with a test-suite evaluator vs a certificate-required evaluator, with injected harness loopholes and held-out adversarial instances. Kill if a plain test-suite evaluator with adversarial tests gives the same held-out wrong-answer rate, or if certificate overhead costs more than 20% of solved instances.

#### Active automata learning with LLM-written mappers
- **What:** Revive Angluin's L* (1987) protocol model learning by having an LLM write the protocol-specific abstract-to-concrete mapper from the RFC.
- **How it would work:** The live implementation answers membership queries (strong oracle). Cheat: a mapper that collapses distinct states (coarser alphabet means trivially small models). Counter: RFC conformance tests and state-coverage metrics.
- **Evidence / numbers:** It found TLS state-machine bugs (de Ruiter & Poll, USENIX Security 2015) (**F**). Mappers are expert labour and equivalence queries are expensive (**I**). Survey: [Vaandrager, CACM 2017](https://cacm.acm.org/research/model-learning/).
- **Prior art / who has it:** Aarts et al. (hand-written mappers); ProtocolGPT infers state machines statically ([2405.00393](https://arxiv.org/abs/2405.00393)); ChatAFL uses LLM grammars for fuzzing. No LLM-as-mapper active learning found (**I**).
- **Verdict:** RUNNER-UP (niche). Plausible and unoccupied, but the protocol security-testing market is small and overlaps `flip/02` (protocol interop).

#### MMS-gated simulation code (computational science)
- **What:** Use the method of manufactured solutions (Salari & Knupp, Sandia 2000; Roache) as the oracle for agent-written PDE solver code.
- **How it would work:** Pick an analytic solution, derive the source term symbolically, and require the observed order of accuracy to match theory. That is hard to fake without solving the PDE. Cheat: special-casing the manufactured source. Counter: randomised manufactured solutions.
- **Evidence / numbers:** It is standard practice but laborious per PDE and boundary condition (**I**); it never actually died.
- **Prior art / who has it:** MOOSEnger 10-problem MMS benchmark ([2603.04756](https://arxiv.org/abs/2603.04756)); MMS as a continuous RL reward ([2607.10474](https://arxiv.org/abs/2607.10474)); PDEAgent-Bench ([2605.09636](https://arxiv.org/abs/2605.09636)); CodePDE. DOE labs own the codes.
- **Verdict:** KILLED as a bet (occupied academically, DOE-owned). It is the best oracle in its area and worth borrowing as an oracle pattern for the numerics report.

#### Agent-driven PQC migration (Lens B)
- **What:** Agents remediate code toward post-quantum crypto, reviving crypto agility (RFC 7696, 2015), since most code isn't agile.
- **How it would work:** Agents do the large, deadline-driven migration labour. KATs, Wycheproof and interop handshakes check primitives, but nothing checks the application level.
- **Evidence / numbers:** NIST IR 8547 draft (Nov 2024) deprecates quantum-vulnerable public-key algorithms after 2030 and disallows them after 2035 ([NIST](https://csrc.nist.gov/pubs/ir/8547/ipd)) (**F**). AWS removes Kyber-draft endpoint support in 2026 (**F**). RSA-OAEP key transport doesn't map 1:1 to a KEM; naive "syntactic replacement" is the documented failure mode ([OSA SP-040](https://opensecurityarchitecture.org/patterns/sp-040)).
- **Prior art / who has it:** Inventory and discovery vendors (IBM, SandboxAQ, Keyfactor and others) plus generic coding agents. No single agent-remediation product found in one search, but the space is crowded with funded security vendors (**I**).
- **Verdict:** RUNNER-UP. Value is large (every regulated enterprise) (**E**), but it fails gate 2 at the application layer, where the gap is semantic protocol redesign that agents don't check.

#### Requirements-based test evidence for DO-178C / ISO 26262 (embedded)
- **What:** LLM-generated requirements-based tests reaching structural coverage (MC/DC for DAL A) for certification evidence.
- **How it would work:** The coverage tool plus the requirement act as the oracle. Certification keeps the model out at run time, so gate 3 passes.
- **Evidence / numbers:** Vendors and talks claim 40%+ faster test creation with LLMs (Embedded Testing 2026 abstract, vendor-reported) (**F**). Rapita: "blindly generating tests to simply get a high or complete coverage metric is a very bad way of testing software" ([2013-10-15](https://www.rapitasystems.com/blog/automatic-generation-mcdc-test-cases-complete-waste-time)) (**F**). No DO-330 tool qualification for LLM generators published, per one search (**I**).
- **Prior art / who has it:** Vendor and academic AI pilots (Embedded Testing 2026, AeroCON 2026). Possible fit for Rapita, LDRA or VectorCAST.

#### The four gates: the rule that predicts flips (§5)
- **What:** A synthesis across round 1 and this sweep. An old, technically right idea flips when it passes gates 1–3, and gate 4 predicts who captures it.
- **How it would work:** (1) The death cause was per-case labour, not capital (masks, CHERI), physics or information theory (covert channels, FHE overhead), coordination (semantic web, MDE), intractability (AMD) or correlated failure (N-version). (2) There is an independent, extensional oracle much cheaper than the labour: it judges behaviour on inputs, can't be edited by the proposer, and isn't the same model family. It is strongest when structural (roundtrip, proof kernel, certificate, conformance suite, frozen original). (3) The artefact must run without the model (µs latency, certification, cost per call, offline/embedded). Otherwise the model obsoletes the idea instead of reviving it: expert systems, Cyc, end-user programming, literate programming, authored tutors, classic CV. (4) Oracle ownership decides who wins: an owning organisation revives it in-house (Meta ACH, Google TAP, Google/IBM QEC, Siemens PLC, IBM/AWS COBOL, DOE solvers). Outsiders win where the oracle is public (Linux/GrowOS, Lean/Math Inc, Khronos CTS, TLA+ traces/Specula) or lives with many fragmented customers (`flip/02`'s database bet, this report's file formats). **Lens B variant:** an idea is needed more when an agent-scale rate crosses a threshold the old design assumed away and a giant built the fix in-house (merge queues above ~10³ merges/day vs Google TAP, `flip/05`); a fix that lives only inside a giant is a product for everyone else. **Corollary (superhuman-model test):** pass gates 2 and 3 and a better model makes the idea more valuable; fail gate 3 and it becomes obsolete; fail gate 2 and a better model makes it worse because it hacks harder.
- **Evidence / numbers:** Retrospective check "against 30 ideas" (the table lists 32 rows: unikernel/GrowOS, mutation testing, PBT, expert systems, end-user programming, literate programming, N-version, semantic web/MDE, CHERI, custom accelerators, confinement, agoric auctions, AutoAdmin, active networks, TLA+/Specula, superoptimisation, COBOL migration, reproducible builds, post-merge integration/TAP, Kay STEPS, rules-as-code, QED, Remy CC, ITS authoring, LLM relevance judges, PLC, MMS, QEC, zkVM, FHE, WCET, AMD). All are consistent with the rule, but it was fitted after the outcomes, so this is consistency, not prediction (**I**). Weakest points: gate 1 vs gate 2 is often a judgement call (Remy, rules-as-code), and gate 4 can't predict timing ("if anyone does it, the oracle owner does it before outsiders").
- **Verdict:** KEPT as the report's general rule; it explains why the sweep is mostly occupied.
- **Kill test / first proof:** Forward predictions, check by 2027-10-28 (**E**): (a) agent-evolved QEC decoders are published first by an oracle owner (Google, IBM, NVIDIA, Riverlane, Quantinuum), and an earlier outsider paper with hardware-validated results falsifies gate 4; (b) no credible LLM-generated sound WCET model is accepted by a certification authority, and acceptance falsifies gate 2's unsound-oracle kill; (c) LLM-only relevance judging does not replace human qrels as TREC's primary ground truth, and replacement falsifies gate 2's circularity clause; (d) agent-authored format descriptions appear as an OpenZL feature or third-party tool within 12 months, and no activity at all suggests the gates are necessary but not sufficient, with buyer demand as the missing factor.
