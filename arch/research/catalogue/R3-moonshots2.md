## Round 3 — superhuman models and worsening problems — `moonshots2/`
The round asked what survives if models become so good they no longer need verification, and pushed for 100–1000× ideas in or near the Cloudflare/TypeScript world that attack problems which get worse as models improve: inference compute and energy, agent traffic hitting origins, data movement, generated-code volume, and scarce evidence. A critic first re-scored the round-1 bets and found that assurance survives only when narrowed (Oracle Foundry plus Failure Seed Bank first, cross-party notarised computation second) and that no report shows a capsule or live heap is needed. The six lenses then converged on one family: amortise intelligence by turning repeated agent work into maintained programs or incremental build graphs (trace foundry, incremental agents, thought builds); move the next bounded operation to the data or origin (Origin Work Protocol, visiting compute); and issue buyer-checkable replay receipts. Every ONE bet came back **go-with-changes**, gated on beating strong conventional baselines (prompt caching, Code Mode, handwritten code, SQL pushdown, signed JSON). The repeated warning: a parked JS heap is not a parked KV cache and relieves no GPU scarcity.

### 00-critic: Round 1 critic: verification survives; the capsule thesis remains unproved

Lens: a critique, not an idea list. It re-scores the ten round-1 bets (reports 01–07) under a generously applied 100× model premise, with no new runtime measurements; scores are **model-proofness / need / scalability**, each 0–5, higher better (judgments, not additive returns). Headline finding (I): round 1 found a real family of needs (accountability, adversarial counterparties, changing world state, irreversible effects, other parties needing proof, specification ambiguity) but overgeneralized its cause, and no report shows a capsule advantage on an independently selected customer workload; "verification is the scarce resource" survives only narrowed, because the real scarcity is authoritative specifications, observations, permission to act and evidence another principal accepts. Its ONE bet: **Oracle Foundry + Failure Seed Bank restricted to one real reference-backed contract family** (go-with-changes; second choice notarised computation for a specified cross-party deliverable; counterfactual debugger as entry feature). Direct casualties: "one tab → eight branches → one file" and runtime fault-grown Node.

#### Rebuild occupied software (01)
- **What:** Controlled evolution of live tenant software and its in-flight state (migrations, version transitions) using retained-state capsules.
- **How it would work:** Run retained-state/schedule trials of each migration against checkpoints of pending work before cutover; the critic narrows it to valuable, hard-to-replay in-flight state under declared boundaries and excludes arbitrary-frame upgrades.
- **Evidence / numbers:** E: 10,000 tenant variants × 4 changes/month = 40,000 migration jobs; 20 trials/job = 800,000 checks; 10 × 3 MB checkpoints/tenant = 300 GB ≈ $4.50/month; one model attempt/job = $4,000–$40,000/month; 1% manual exceptions at 30 min = 200 h/month. F: Amazon rollback-safety account (2019-12-05) supports transition management, not opaque state. Round 1's 90%-of-30 threshold is a feasibility threshold, not a production error rate. [Amazon deployment account](https://builder.aws.com/content/3F04j2yRAAMBuPSPs50xwXZqg01/ensuring-rollback-safety-during-deployments)
- **Prior art / who has it:** Expand/contract schema migration, versioned workflow handlers, canary/rollback (the baseline a better model can write).
- **Verdict:** NARROWED (survives only narrowed) — **Scores: 3 / 4 / 3** (model-proofness / need / scalability); near-perfect agents can keep explicit schemas from the start, so capsules win only for in-flight computation conventional workflows cannot cheaply reconstruct.
- **Kill test / first proof:** Kill the capsule requirement if explicit state + versioned workflows match downtime, lost progress and total maintenance effort across several real, independently chosen changes (the 30-state upgrade clinic only proves one bounded change).

#### Executable citations (01)
- **What:** Publish claims whose underlying analysis is a forkable saved continuation that readers can challenge.
- **How it would work:** Retain a capsule per claim; a reader forks it to change assumptions or inputs. Narrowed to expensive intermediate computational analyses where exact historical inputs, assumptions and versions matter.
- **Evidence / numbers:** E: 1 million claims, 100,000 challenged forks/month; 3 MB each = 3 TB/$45/month; one full-image read per fork = 300 GB/month; 2 min manual packaging × 1 million publications = 33,333 h, so manifests must be extracted automatically from a small toolchain. [Binder documentation](https://mybinder.readthedocs.io/en/latest/introduction.html)
- **Prior art / who has it:** Binder; pinned source + input hashes + environment manifest + notebook + cached intermediates.
- **Verdict:** NARROWED (survives only narrowed) — **Scores: 3 / 2 / 4**; at 100× the reader's agent absorbs routine re-checking, and a replayable cherry-picked analysis is still misleading; keep citation/provenance independent of snapshots, a public footnote-fork demo does not justify a standalone product.
- **Kill test / first proof:** Five-reader challenge pilot on analyses selected *before* deciding to preserve a cyclic graph; must reduce time to a correct substantive challenge including author packaging and dependency maintenance, then test real author/reviewer disagreement.

#### Immune repair colonies (02)
- **What:** Integration workflows that, on failure, spawn a colony of candidate repairs selected against replayed incident state, with reusable "memory cells".
- **How it would work:** Capture the incident state, generate ~16 repair proposals, replay each against ~100 cases, keep the winner. Narrowed to executable incident capture and bounded recovery for hard-to-reconstruct state; the durable asset is the incident state and effect history, not the colony.
- **Evidence / numbers:** E: 1 million workflows, 0.1%/month incidents = 1,000; 16 proposals = 16,000 attempts = $1,600–$16,000/month; 1.6 million checks ≈ $1.60 guest CPU; 3 MB state/workflow = $45/month, 30 versions = $1,350; 10% of incidents × 2 h specialist = 200 h/month; 2–4 roles ≈ $33,000–$67,000/month. [Temporal event history](https://docs.temporal.io/workflow-execution/event)
- **Prior art / who has it:** Temporal/Workflows (event history for recovery), retries and reconciliation, JSON checkpoints, ordinary regression tests.
- **Verdict:** NARROWED (survives only narrowed) — **Scores: 2 / 3 / 3**; at 100× most schema drift needs one correct repair, so colony search is optional and likely shrinks; reuse repairs by contract/version, never move raw customer heaps across tenants.
- **Kill test / first proof:** Kill if one strong repair plus explicit state matches end-to-end results within the report's own 20% threshold; the six-fault-class ingestion proof must then survive independently sourced incidents.

#### Failure-search gate (03)
- **What:** A gate that rehearses proposed agent writes across many adversarial simulated futures before allowing them.
- **How it would work:** Narrowed to selective adversarial qualification of new, high-consequence policies/integrations with calibrated contracts, plus cheap broker enforcement (authorization, version, fencing checks) on every routine effect, rechecking current conditions at commit.
- **Evidence / numbers:** E: 1 million proposed writes/day ≈ 30 million/month; rehearse only 0.1% = 30,000 jobs × 1,000 suffixes = 30 million replays ≈ $30 guest CPU; model attempts $3,000–$30,000. Rehearsing every write = 30 billion suffixes, $30,000 CPU, and a $0.10 model call per suffix = $3 billion, so selectivity is fundamental. [Antithesis docs](https://antithesis.com/docs/setup/overview/), [FoundationDB paper](https://www.foundationdb.org/files/fdb-paper.pdf)
- **Prior art / who has it:** FoundationDB deterministic simulation, Antithesis (fault control, multiverse debugging), IAM/transactional effect brokers, policy-as-code, property-based fault testing.
- **Verdict:** NARROWED (survives only narrowed) — **Scores: 3 / 4 / 3**; a universal per-write multiverse gate dies; the most model-proof part is the broker's authority boundary, a familiar function, and a simulator from the same mistaken spec is no independent defense.
- **Kill test / first proof:** One owned configuration connector proves a bounded effect protocol and finds a seeded race; then test guided search against the strongest baseline at equal total budget, and show testing verdicts predict real deployment behavior.

#### Counterfactual debugger (03)
- **What:** Exact replay of a captured agent incident, with bounded interventions to explore what would have happened.
- **How it would work:** Capture execution evidence (rare schedules, private observed data, historical versions) as an incident artifact; replay exactly, and allow explicitly modeled interventions that stop at the knowledge boundary where recorded replies are invalidated.
- **Evidence / numbers:** E: 10,000 incidents/month × 20 interventions = 200,000 replays; 200 CPU-ms each ≈ $0.80/month; 10 MB/incident = 100 GB/month, rolling year ≈ 1.2 TB/$18/month; model investigation $1,000–$10,000/month; two roles ≈ $33,000/month; instrumentation, retention rights and data handling decide adoption.
- **Prior art / who has it:** Structured traces + source/version hashes + recorded tool responses + ordinary reproducers; existing record/replay tooling.
- **Verdict:** NARROWED (survives only narrowed; highest-scored bet) — **Scores: 4 / 4 / 4**; starts from observed evidence rather than claiming to know future reality; preferred technical entry feature for the Foundry; predictive counterfactuals remain optional and domain-bound.
- **Kill test / first proof:** After the toy order-coordinator replay, one opt-in production workflow with measured capture overhead and a blinded diagnosis task; measure correct conclusion and total elapsed work, not branches explored.

#### Notarised computation (04)
- **What:** Deliverables that carry signed, independently replayable evidence of what was computed, from which inputs, under what authorization.
- **How it would work:** Signed envelope (input/output manifest, source/tool receipts) per deliverable; optional capsule for executable replay by a buyer-selected verifier. Narrowed to cross-party evidence for specific, consequential deliverables, capsules optional.
- **Evidence / numbers:** E: 10 million receipts/month; 10 KB envelope = 100 GB/$1.50/month vs mandatory 3 MB capsule = 30 TB/$450; 1% replay sample (100,000 × 500 CPU-ms) ≈ $1 CPU; 0.01% human review × 20 min = 333 h/month (1% review > 33,000 h); 2–5 roles ≈ $33,000–$83,000/month. I: signatures prove attribution/integrity, not truth, completeness or legal notarial status; a seller can replay a fabricated input honestly. [Sigstore docs](https://docs.sigstore.dev/)
- **Prior art / who has it:** Sigstore (artifact identity, signatures, transparency); signed transcripts, hashes, audit logs; PCAOB AS 1105 evidence principles.
- **Verdict:** NARROWED (survives only narrowed; second choice) — **Scores: 4 / 3 / 4**; independence and historical evidence are among the most model-proof needs, but the extra need for *executable* notarisation over a signed transcript is unproved.
- **Kill test / first proof:** An actual buyer/verifier resolves a realistic dispute with less total work than the baseline and rejects an internally consistent package that used an unauthorized or missing input; if no external verifier values the runnable package, keep ordinary receipts and stop.

#### One tab → eight branches → one file (05)
- **What:** Fork one running agent/tab into eight parallel branches (copies of the JS heap) and join the result into one file, with cross-device handoff.
- **How it would work:** Suspend a capsule, fork it to eight branches each doing a model attempt, then join; the critic would only keep fork/join and handoff as capabilities inside another product.
- **Evidence / numbers:** E: 1 million jobs/day; 8 branches = 240 million attempts/month vs 30 million; at $0.10–$1 per attempt, $24M–$240M vs $3M–$30M, so the extra $21M–$210M must buy outcomes or latency; 3 MB base per branch = 720 TB/month moved; 7-day retention = 21 TB/$315/month; guest CPU only $240/month. F: Anthropic multi-agent research (2025-06-13) ≈ 15× chat token use, gains tied to token budget and parallelism. [Anthropic multi-agent account](https://www.anthropic.com/engineering/multi-agent-research-system)
- **Prior art / who has it:** One strong agent + `Promise.all`/task queues; provider-internal parallel search; Anthropic multi-agent research system.
- **Verdict:** KILLED (dies as the top product bet) — **Scores: 1 / 2 / 4**; at 100× one agent does most of the work correctly, and saving a heap copy does not save weights, prompt processing or reasoning state; plausible as an SDK feature, not a company.
- **Kill test / first proof:** Choose workloads before the fan-out, same strongest model at equal total budget, scheduler allowed to choose one; only if independently selected workloads hit +10 points success or 2× latency, sell that workload benefit.

#### Fault-grown Node (06)
- **What:** A runtime that grows missing Node APIs on demand when a program faults on them, via a colony of synthesized implementation attempts checked against an oracle.
- **How it would work:** A fault on a missing capability triggers synthesis attempts, qualified against real Node, then reused. The critic's replacement (already in 06): offline qualification/distribution of a narrowly supported compatibility profile, scored as part of Oracle Foundry.
- **Evidence / numbers:** F/local: report 06 attributes most newly passing GrowOS corpus programs to one mmap handler, with helper work, environment overfitting and held-out limits documented (leverage at one gap, not scalable semantics). E: 1,000 package/version combos/month × 20 attempts = 20,000 attempts/$2,000–$20,000; reference fleet $1,000–$10,000; two maintainers ≈ $33,000; floor ≈ $36,000–$63,000/month. [Workers Node support](https://developers.cloudflare.com/workers/runtime-apis/nodejs/), [unenv](https://github.com/unjs/unenv)
- **Prior art / who has it:** Cloudflare Workers built-in Node compatibility, `unenv`, polyfill bundling, CI against Node, Node/container tools.
- **Verdict:** KILLED (dies as a durable runtime-growth product) — **Scores: 1 / 2 / 2**; at 100× the compatibility layer is built ahead of execution, missing host primitives are not missing code, and a universal Node shim is a finite shared asset whose synthesis cost collapses.
- **Kill test / first proof:** Grown StringDecoder plus unseen-package reuse proves one mechanism; before generalizing, census the packages users actually need, separate shimmable code from absent host semantics, and show incremental supported applications.

#### Oracle Foundry (07)
- **What:** A qualification operator that accepts or rejects generated implementations against maintained, independently grounded references.
- **How it would work:** Versioned reference/candidate runners execute stateful test sequences per release; narrowed to one difficult contract family where acceptance depends on a private customer contract, current target environment, compatibility requirement, independent counterparty or newly observed failure; value comes from access, evidence ownership and adjudication.
- **Evidence / numbers:** E: 100 customers × 10 releases/month = 1,000 jobs × 10,000 sequences = 10 million sequences ≈ $10 CPU; 10,000 model attempts = $1,000–$10,000; three roles ≈ $50,000; reference infra $1,000–$10,000; total ≈ $52,000–$70,000/month before sales/support/margin. F: OpenAI (2026-02-23) found material test/task problems in 59.4% of an audited 138-task hard subset of SWE-bench Verified (graders can be wrong). [SWE-bench Verified reassessment](https://openai.com/index/why-we-no-longer-evaluate-swe-bench-verified/)
- **Prior art / who has it:** Reference-backed CI, property/differential testing, mutation testing, better coding agents.
- **Verdict:** NARROWED (survives only narrowed; first choice with Seed Bank) — **Scores: 3 / 4 / 3**; round 1's 5/5 model-resilience was too high; best builder fit and most credible accumulation loop, but needs customer data rights and a trusted reference, and if each customer needs a new semantics expert it scales as consulting; capsules optional.
- **Kill test / first proof:** Beyond the 20-attempt/three-contract proof, test genuinely unseen model outputs and at least one customer-owned contract; must reduce wrong acceptance at equal false-rejection and total human/oracle budget, or materially shorten a release/dispute.

#### Failure Seed Bank (07)
- **What:** An ever-growing archive of minimized captured incidents replayed against new releases and models.
- **How it would work:** Capture, minimize and version incident packages (journal + fixtures); release campaigns select relevant cases by tenant, contract and failure mechanism; retire or reclassify cases with their contract versions. Narrowed to a fresh, versioned incident corpus inside the Foundry or debugger.
- **Evidence / numbers:** E: 1 million packages × 10 MB = 10 TB/$150/month; 10,000 new cases/month; 10 campaigns × 100,000 cases = 1 million replays ≈ $4 CPU; mutating 10,000 cases = $1,000–$10,000; 0.5% adjudication × 30 min = 25 h; 1–2 roles ≈ $17,000–$33,000/month.
- **Prior art / who has it:** Minimized regression corpora (source, input, expected outcome, event schedule) in existing CI/observability.
- **Verdict:** NARROWED (survives only narrowed) — **Scores: 3 / 4 / 4**; frozen model-error cases go trivial at 100× and public cases leak into training; an accumulation loop and release feature, not an independent moonshot business; the bank can survive while the capsule disappears.
- **Kill test / first proof:** Collect an opt-in stream, freeze a temporal split, and test whether bank-guided qualification predicts *later* failures better than an ordinary regression suite (invalid/unminimizable captures stay in the denominator); failure kills the learning claim but leaves regression coverage.

#### Round-1 thesis: "verification is the scarce resource"
- **What:** The round-1 umbrella claim that as generation becomes free, verification/acceptance becomes the scarce, growing market.
- **How it would work:** The critic splits it into three tests: does assurance remain necessary, does an independent supplier earn payment for it, does retaining a live heap improve it; and replaces the slogan with `value of added checking = N × p_bad × loss_if_bad × fraction_prevented + evidence/recovery value − total checking cost`.
- **Evidence / numbers:** I: 100× volume with 100× lower error probability at fixed stakes leaves expected loss unchanged. F: NIST 2010 summary of 2002 study (testing 50% of dev budgets, $59.5B/year US flaw cost); Datadog revenue $2.68B 2024 (+26%), $3.43B 2025 (+28%); PCAOB opex $370.5M 2024 vs $332.2M 2023; LangChain surveys offline eval 39.8% → 52.4%, online 32.5% → 37.3%; no comparable 2024–2026 dollar series for AI eval/guardrail spend exists. [CompCert manual](https://compcert.org/man/manual001.html), [PCAOB AS 1105](https://pcaobus.org/oversight/standards/auditing-standards/details/AS1105), [DORA 2024](https://dora.dev/research/2024/dora-report/)
- **Prior art / who has it:** CompCert, PCAOB auditing standards, FAA AC 20-115D / DO-178C, FoundationDB simulation, Anthropic and NIST eval/monitoring work.
- **Verdict:** NARROWED (survives only narrowed) — assurance persists and changes form, but the persistent scarcity is authoritative specs, observations of changing systems, permission to act and evidence accepted by another principal; "its spend must outgrow generation" is unproved, and capsule/heap necessity is unshown in every report.
- **Kill test / first proof:** Round 2 must answer eight questions before promoting a bet: which failure survives 100×, who holds the authoritative answer, which buyer pays for which changed decision, whether need grows faster than unit cost falls, why a capsule, what is checked once vs per release vs per effect, whether the acceptance procedure is falsifiable, and what makes the two-week result predict a scalable product.

#### First choice: Oracle Foundry + Failure Seed Bank on one reference-backed contract family
- **What:** The critic's combined pick: a narrow Oracle Foundry with the Failure Seed Bank as its feedback loop, restricted to a real reference-backed contract family, with the counterfactual debugger (exact replay) as the entry interface.
- **How it would work:** One reference-backed API family → maintained CI acceptance integration → fresh incident ingestion → more families only where reference reuse is economical; broker mechanisms (conserved budgets, stable operation IDs, stale-owner rejection, reconciliation) are credited to the broker, not the capsule.
- **Evidence / numbers:** Same as the Foundry and Seed Bank entries (E: ≈ $52,000–$70,000/month Foundry floor). I: zero failures in 30 trials gives only an approximate 95% upper bound near 10%, so pilots cannot show the reliability tail; prior capsule measurements (1.5–6.4 MB images, 5–11× glue overhead) were not rerun.
- **Prior art / who has it:** Reference-backed CI, differential/mutation testing, regression corpora.
- **Verdict:** KEPT (#1, go-with-changes) — best builder fit and plausible two-week falsification; if it works without capsules, the product has succeeded and the capsule thesis has failed, and that result must be accepted.
- **Kill test / first proof:** An acceptance improvement on actual unseen work with affordable reference maintenance, compared against a baseline that gets the same stronger model, data, budget and tools.

### 01-compute: The compute crunch: stop paying a GPU to rediscover a program
Lens: the compute crunch. Agent demand is rising on several independent axes (Google tokens ~330× in two years, agents 4×/15× chat tokens, IEA 485→950 TWh), and that growth outpaces falling token prices. The report finds no measured global fraction of reusable agent compute, so a 100× saving only holds for very repetitive workloads with cheap hits. Its ONE bet is the **trace foundry**: an agent discovers a recurring API procedure once, then fresh inputs run as versioned TypeScript/Wasm on CPUs, backed by a small dependency-aware artifact store. Verdict: **go-with-changes**. The first proof has to report full economics against prompt caching, Code Mode and handwritten code, and publish how much repetition 100× actually needs.

#### Trace foundry: turn repeated agent behavior into a residual program
- **What:** Watch an agent solve a recurring task, parameterize the stable procedure, and ship ordinary TypeScript/Wasm with explicit fallback points. This is "program distillation", not model distillation. 100×: one expensive discovery serves a million changing inputs, and models run only on novelty.
- **How it would work:** Collect a tool-boundary trace and a candidate task family. Infer typed parameters, branches and read dependencies, then emit a restricted effect-aware program that guards schema, connector version, pagination and freshness and falls back when they change. Start with structured APIs rather than browser macros. Run on Workers/Wasm, with scriptc only if CPU profiling justifies it.
- **Evidence / numbers:** F: Anthropic agents use ~4× chat tokens, multi-agent ~15×. F: Agentic Plan Caching saves 50.31% cost and 27.28% latency. E: a 1M-invocation scenario drops from $5,640 to $40.64 (~139×), but only ~9.4× at 10% fallback and ~16× if model tariffs fall 10×. E: reuse ceiling `new/old = (1-h) + h*r + a` gives 9.81× at 90% reuse, 83.40× at 99% and 333.44× at 99.9%. Links: [APC v2](https://arxiv.org/abs/2506.14852v2), [ReUseIt](https://arxiv.org/abs/2510.14308v2), [Futamura 1971](https://fi.ftmr.info/PE-Museum/PE-Original-English1971.pdf).
- **Prior art / who has it:** Futamura partial evaluation (lineage), ReUseIt (guarded reusable web workflows), Agent Workflow Memory (AWM, ICML 2025), APC, Cloudflare Code Mode. The claim "we invented learning workflows from traces" is not available.
- **Verdict:** KEPT (#1, the ONE bet). It is the strongest path to a discontinuous drop in recurring model execution and produces an inspectable artifact. Its toughest baselines are a handwritten function and an agent that writes and remembers that function itself.
- **Kill test / first proof:** First proof: 3 recurring API workflows, 30 discovery cases and 300 later cases (unseen params, empty pages, retries, a schema change), compared against fresh agent, prompt-cached agent, APC templates, Code Mode and handwritten code. Targets are 100× fewer model calls on admitted stable cases and 10× lower total pilot cost. Kill if families need ongoing human rewriting, unseen-input success drops more than 1 pp, or break-even repeat volume exceeds the buyer's stable volume.

#### A reasoning CDN: distribute reusable procedures, not universal cached answers
- **What:** A network where agents fetch compatible public reasoning artifacts and tool-plan programs before generating their own. 100×: the thousandth organization configuring the same public API reuses a maintained procedure at the edge.
- **How it would work:** Artifacts carry a typed plan, executable subroutines, connector/schema versions, required capabilities, dependency manifests and provenance. R2 holds content-addressed packages, Workers cache and match them, and a Durable Object coordinates one build per key. Semantic retrieval proposes a candidate and a deterministic compatibility check admits it or misses. Private inputs stay tenant-local and namespaced.
- **Evidence / numbers:** F: Google tokens grew ~330× (May 2024 to May 2026), and APC shows plan reuse. I: no measured cross-company duplicate fraction exists. E: the 2030 design point is 1M public artifacts consumed by 10,000 organizations. Links: [Michie memo functions 1968](https://www.nature.com/articles/218019a0), [RFC 9111](https://www.rfc-editor.org/rfc/rfc9111.html).
- **Prior art / who has it:** Michie memoization, HTTP caching (RFC 9111), APC. A plain package registry is a serious substitute.
- **Verdict:** KEPT (#3). It is the largest distribution moonshot and closest to Cloudflare's economics, but its key premise (cross-tenant admissible reuse) is unproven. Start as distribution for trace-foundry outputs, not a standalone "thought cache".
- **Kill test / first proof:** First proof: 20 public read-only API procedures in a Worker/R2 registry, 200 independent held-out requests, compared against local skills, docs search, APC and fresh generation, with a target of 5× lower first-task planning cost. Demote to a registry feature if under 20% of requests admit artifacts or if refresh cost eats the savings. Any cross-tenant disclosure kills it.

#### Agent make: content-addressed, incremental execution of agent work
- **What:** Turn agent work into a dependency graph whose unchanged nodes do not rerun. 100×: continuously updated analyses or reconciliations compute only the affected frontier.
- **How it would work:** A node key covers canonical inputs, program/model version, tool schema, tenant/auth scope, environment and dependency digests. Tool adapters expose ETags, commits or snapshot IDs, and undeclared dependencies make a node non-cacheable. Clock and randomness are explicit inputs. Effects go to a separate intent/receipt ledger: a past payment is never a reusable instruction to pay again. R2 stores values and DO/SQLite stores graph and invalidation state.
- **Evidence / numbers:** F: PEEK is 1.7–5.8× cheaper than ACE. F: OpenRouter prompts grew ~1.5K→6K+ tokens. E: the 2030 shape is 100M reusable nodes per organization. Links: [Acar 2005 thesis](https://www.cs.cmu.edu/~rwh/students/acar.pdf), [Build Systems à la Carte](https://www.microsoft.com/en-us/research/publication/build-systems-la-carte/), [PEEK](https://arxiv.org/abs/2605.19932v1).
- **Prior art / who has it:** Self-adjusting computation (Acar), Build Systems à la Carte, existing build/data/workflow systems.
- **Verdict:** KEPT (#2). It builds the strongest accumulating systems asset and cuts the cost of new questions without needing identical text. Risks: incomplete dependency tracking, graph overhead, and substitution by ordinary workflow tools.
- **Kill test / first proof:** First proof: a TS engine over 100 versioned docs plus a fixture repo running 100 related tasks with mutations, permission revocation and a new doc that changes an empty search result. Target is 100× fewer expensive node evaluations when 99% of the frontier is unchanged. Kill on any silent stale answer, or if savings fall below 2× over conventional workflow caching.

#### Context once: maintain an executable map of a recurring world
- **What:** A versioned index of what agents learned about a repo or corpus, exposed as small query functions instead of reloading the world. 100×: thousands of agents share orientation on one evolving codebase.
- **How it would work:** Three layers with separate accounting: (1) immutable source objects, (2) maintained maps/indexes/query programs with source spans, dependency digests and invalidation rules, and (3) provider-specific prompt-prefix caching. CPU code runs search, filter and join, and raw source is fetched when the map can't answer. There is no claim of portable KV tensors.
- **Evidence / numbers:** F: prompts grew ~1.5K→6K+ tokens (OpenRouter). F: Cursor cut cold cache misses 20% and total token cost 7%. F: PEEK shows 1.7–5.8× savings. E: a 50-turn run with a 10K fixed prefix sends 1,725,000 input-token appearances. E: targets are 10× lower orientation cost and 100× on map-answerable lookups. Links: [Cursor token efficiency](https://cursor.com/blog/improved-token-efficiency), [Gupta & Mumick 1995](https://homepages.inf.ed.ac.uk/wenfei/qsx/reading/gupta95maintenance.pdf).
- **Prior art / who has it:** Materialized views (Gupta/Mumick), PEEK (which already occupies learned orientation caching), Cursor, native agent memory, prompt caching.
- **Verdict:** RUNNER-UP (rank 5 of 8). Better models may orient in one cheap query, and a summary prompt is easily absorbed. The durable part is maintaining queries across many consumers.
- **Kill test / first proof:** First proof: 50 questions on a real TS repo plus a changed revision, compared against rg/symbol search, native memory, prefix caching and a PEEK-style map. Reject if map maintenance costs more than the exploration it saves, if stale-map errors exceed the full-source baseline, or if the best search-plus-memory baseline comes within 20%.

#### Yield the accelerator: park orchestration and lease KV residency separately
- **What:** Agents explicitly yield while tools run: the app continuation is parked cheaply, and a cooperating inference host is told whether KV residency is worth keeping. 100×: millions of pending agents exist as stored state while HBM serves only runnable work.
- **How it would work:** A tool-only guest reaches a quiescent boundary and snapshots QuickJS/Wasm state (or explicit state), journaling pending operation IDs outside the image. A `yield(expected_wait, deadline, resume_key)` call at the model gateway lets the host choose retain/offload/evict/re-prefill. On completion the broker wakes one owner and rebinds current grants. A capsule does not hold remote KV or hidden chain-of-thought.
- **Evidence / numbers:** F: TokenCake shows up to 47.06% lower latency and +16.9 pp GPU utilization vs vLLM. F: Continuum shows over 8× better job completion time. F: Sonnet 4.5 kept focus for 30+ hours, and Cursor ran 10M tool calls in a week. E: 10M dormant agents at 0.1% runnable is 10K active continuations. Links: [TokenCake](https://arxiv.org/abs/2510.18586v5), [Continuum](https://arxiv.org/abs/2511.02230v7), [Scheduler Activations](https://homes.cs.washington.edu/~tom/pubs/sched_act.html).
- **Prior art / who has it:** Scheduler Activations (lineage). Vercel quickjs-wasi/Workflow snapshots, LangChain quickjs-rs, Golem, VM hibernation. Snapshotting an await is occupied territory.
- **Verdict:** RUNNER-UP (rank 6 of 8). Strong systems evidence, but GPU savings need an inference-host buyer and adapter. A JS image cannot back an accelerator-savings claim.
- **Kill test / first proof:** First proof: a Worker/DO/R2 broker with 1,000 synthetic waiting sessions, plus a yield hint on a local serving adapter if hardware exists. Targets are 100× lower resident app memory for long sleepers and 2× serving improvement. Drop the capsule part if explicit JSON plus replay wins. Drop the accelerator product if lease hints add less than 20% useful throughput.

#### The agent query compiler: put loops and data near tools, collapse round-trips
- **What:** Compile one model-produced tool plan into a typed DAG with CPU-side loops, joins and reductions executed near the data. 100×: a million-record task needs a bounded number of model decisions.
- **How it would work:** The runtime resolves dependencies, runs independent reads concurrently, pushes filters and reductions to the data owner, and returns only decision-relevant results. Workers do glue and Wasm/scriptc handles CPU-heavy transforms. Regional placement and server-side queries are compared explicitly. Typed bulk APIs cut origin calls; concurrency alone does not.
- **Evidence / numbers:** F: Anthropic's tool context fell 150K→2K (98.7%). F: LLMCompiler is up to 3.7× lower latency and 6.7× cheaper than ReAct. E: 100 serial 100 ms round-trips fused into one is 10 s→0.1 s, i.e. 100× less control RTT, not 100× faster total work. Links: [Code Mode](https://blog.cloudflare.com/code-mode/), [LLMCompiler](https://proceedings.mlr.press/v235/kim24y.html), [Selinger 1979](https://people.eecs.berkeley.edu/~brewer/cs262/3-selinger79.pdf).
- **Prior art / who has it:** System R access-path selection (lineage), Cloudflare Code Mode (which already offers the central mechanism), LLMCompiler, Anthropic code execution with MCP.
- **Verdict:** RUNNER-UP (rank 4 of 8). It needs cost-based placement, bulk connectors and cross-run reuse beyond Code Mode. "Replace an LLM loop with `for`" is not a platform.
- **Kill test / first proof:** First proof: a cross-service inventory report over 100 jobs with real traces, compared across tool loop, Code Mode, a regional Worker and a data-side query. Targets are 100× fewer control transitions on a mechanical loop and at least 2× over Code Mode. Demote if optimized Code Mode plus server-side queries comes within 20%.

#### Deadline-aware agent capacity: buy flexibility, not just cheap electricity
- **What:** Separate an agent's "must finish by" from "run now" and dispatch work when compute and energy are available. 100× is a capacity ambition: many more dormant logical agents per fixed power allocation. 100× cheaper inference from energy arbitrage is not credible.
- **How it would work:** Jobs declare deadline, pause/resume boundaries, regions, residency, model compatibility and max restart cost. A scheduler uses capacity bids, tariffs and carbon forecasts, queues work in DOs and keeps artifacts in R2. Inference must run on a controllable fleet or a flexible-price product. Workers cannot choose the electricity source of a remote model API.
- **Evidence / numbers:** F: IEA 485 TWh (2025) → 950 TWh (2030 central). F: Germany had 573 negative-price hours in 2025 vs 457 in 2024, with a €89.32/MWh average (E: ~6.5% of the year). F: Google has ML demand-response agreements (2025-08-04). E: if electricity is 10% of job cost and is cut 50%, total savings are 5%. Links: [IEA](https://www.iea.org/reports/key-questions-on-energy-and-ai/executive-summary), [Bundesnetzagentur](https://www.bundesnetzagentur.de/SharedDocs/Pressemitteilungen/DE/2026/20260105_Smard.html), [Google flexibility](https://blog.google/inside-google/infrastructure/how-were-making-data-centers-more-flexible-to-benefit-power-grids/).
- **Prior art / who has it:** Liu & Layland deadline scheduling (lineage), Google demand-response agreements, hyperscaler capabilities generally.
- **Verdict:** NARROWED (rank 8 of 8). Rank stays low until an operator supplies real economics, because a small TS team cannot get energy-price exposure or grid contracts. The best buyer is a capacity-constrained operator.
- **Kill test / first proof:** First proof: replay one month of price/carbon traces against 1,000 checkpointable TS jobs, comparing immediate, cheapest-window and deadline-aware dispatch, with a target of 20% modeled energy reduction and zero deadline misses. No standalone business if customers lack slack, the host exposes no lever, or value is under 10% with no capacity payment.

#### Speculate on reads: start likely tools before the model asks
- **What:** Use recurring plans and in-flight intent to prefetch likely read-only observations, accepting a result only if the committed request and its dependencies match. This is a latency bet that can increase compute and origin load.
- **How it would work:** A stored plan proposes likely reads, run as bounded lookahead on Workers or an isolated capsule branch and keyed by canonical request, version and auth scope. Results are held until the real call matches and discarded otherwise. No speculative payments, messages or writes. Connector-specific budgets apply because reads can cost fees and rate limits.
- **Evidence / numbers:** F: PASTE gives 43.5% lower average task time. F: TomasuLLM gives 1.31× on SWE-bench and 1.35× on Terminal-Bench. E: if tool stalls are 80% of latency, the maximum speedup is 5×, and 100× needs over 99% removable latency. Links: [PASTE](https://arxiv.org/abs/2603.18897v3), [TomasuLLM](https://arxiv.org/abs/2609.38201v2), [Tomasulo 1967](https://courses.grainger.illinois.edu/ece511/fa2005/papers/Tomasulo.1967.IBMJRD.pdf).
- **Prior art / who has it:** Tomasulo (lineage). PASTE and TomasuLLM already occupy much of this terrain.
- **Verdict:** RUNNER-UP (rank 7 of 8). It is a weaker standalone compute-saving product than eliminating repeated reasoning, so it fits better as a feature in the plan/CDN runtime.
- **Kill test / first proof:** First proof: 200 held-out read-only workflows with a 2-read speculation budget, targeting 2× better p95 latency within 10% added spend. Stop if it can't beat ordinary batching/prefetch, if it worsens origin throttling, or if any stale observation is accepted.

#### Instrumented tool gateway with a per-job cost ledger (shared first artifact)
- **What:** A tool gateway that records dependency and receipt IDs plus a per-job cost ledger, used to find where a real buyer repeats work before building any compiler or cache.
- **How it would work:** One structured recurring integration family runs through the gateway. Its traces separate compilation (#1), cross-user distribution (#2), incremental reuse (#3), context amortization (#4), waiting (#5), placement (#6) and speculation (#8). The smallest necessary compiler/cache is added afterward.
- **Evidence / numbers:** I: no source measures the soundly reusable fraction of worldwide agent compute, so this is the diligence gap. Open questions in priority order: how much paid work repeats, how long preconditions stay stable, whether cross-tenant reuse works, what irreducible tool/data cost remains, the break-even against cheaper models or handwritten code, and buyer willingness to integrate.
- **Prior art / who has it:** None named specifically.
- **Verdict:** KEPT as a prerequisite ("avoid building eight services"). Snapshots are a separate decision from the product: use them only when the retained state saves real reconstruction.
- **Kill test / first proof:** If the recurrence study fails, kill the global 100× thesis while keeping any useful generated programs.

#### Rejected in this report
- **Universal "thought cache" / global repository of private chain-of-thought** — arbitrary thoughts lack a sound global cache key. The cached object must be a typed program/plan with preconditions, not raw reasoning or a similar question.
- **100× cheaper inference from energy arbitrage** — not credible. Electricity is a fraction of all-in cost, and negative wholesale prices are not free delivered power.
- **Parked JS capsule as GPU savings** — a capsule does not free remote KV. Lower app RAM is not higher GPU utilization.
- **Capsule novelty ("small file", "await survives", "fork it twice")** — insufficient differentiation given Vercel quickjs-wasi, Golem, LangChain and others.
- **"We invented learning workflows from traces"** — unavailable given ReUseIt, AWM and APC.

### 02-compilers: Compile away repeated thinking: compiler theory applied to agents
Lens: compiler theory applied to agents. The report covers Futamura projections, supercompilation, staging, tracing JITs, deoptimization, superoptimization, e-graphs, Halide, MLIR and incremental computation. Its headline finding is that "a JIT for agents" is already occupied: Muscle-Mem, PreAct, Agent JIT Compilation, SKILL-DISCO, TraceCompiler, A-JIT and FlyMy.AI cover guarded replay, fallback and prompt-to-program. A local scriptc probe confirmed the guarded state-machine mechanism (88.75% of simulated decisions removed with identical tool traces) but learned nothing automatically. The ONE bet is an **agent runtime that turns one recurring task into an incrementally maintained program**. Verdict: **go-with-changes**, gated at day 14 on ≥100× fewer processed records, ≥10× lower total cost vs full saved-TS reruns, zero stale answers or duplicate effects, and a disclosed gap to hand-incremental code.

#### A tracing JIT that calls the model only on a side exit
- **What:** Record recurring typed agent paths, specialize data handling and control flow into TS, and call the model only when an explicit assumption fails. 100×: remove 99–99.9% of inference turns on stable task families.
- **How it would work:** A TS tool wrapper emits dataflow, not log strings, and frequently reused graph segments are compiled. Novel judgment stays as explicit residual model calls. Deoptimization records carry versions, a logical PC, live values with provenance, observations, completed and unresolved effect IDs, and budgets. A fallback is fed the recorded context and forbidden to replay completed effects. Writes re-guard at the remote end with conditional versions and idempotency keys; a timeout after dispatch is an unknown outcome to reconcile.
- **Evidence / numbers:** M (local probe, 1,000 invoice jobs, hand-written fast path, deterministic model stand-in, zero real model calls): decisions fell 4,000 → 450 (88.75% removed, 8.89×) with identical tool traces. Removing policy guards caused 150 wrong jobs (150 forbidden payments, 1,000 charge attempts vs 850). The Node and scriptc native results were byte-identical, and the native binary is 300,016 bytes. E: 1M jobs/day × 20 turns, 99% eliminated = 19.8M turns/day removed. E: break-even needs `(K-D)*c > g` and `N > C/((K-D)*c - g)`. F: Agent JIT Compilation reports 10.4× planner and 2.4× scheduler speedups, and PreAct reports 8.5–13× on repeat runs. Links: [PreAct](https://arxiv.org/abs/2606.17929), [Agent JIT Compilation](https://arxiv.org/abs/2605.21470), [Muscle-Mem](https://github.com/pig-dot-dev/muscle-mem).
- **Prior art / who has it:** Lineage is Dynamo, TraceMonkey, SELF/HotSpot deopt and PyPy meta-tracing. Current work: Muscle-Mem (replay with Checks), PreAct (state machines with fallback), Agent JIT Compilation, TraceCompiler, FlyMy.AI, Cloudflare Code Mode.
- **Verdict:** KEPT (#2). It is the best acquisition path into #5 and the local mechanism works, but it is heavily occupied and saved TS already captures much of the value. Pursue only if automatic bindings, effect-aware resumption, invalidation and measured end-to-end savings beat those alternatives.
- **Kill test / first proof:** First proof: 3 structured API workflows with ≥100 untouched variants each, a pinned real model and 20 drift/failure cases, compared against ReAct, Code Mode, saved TS and Muscle-Mem/PreAct. It requires ≥10× fewer inference tokens and ≥2× lower total cost, plus reconciling one unknown write outcome. Kill if under 80% of repeat traffic avoids per-step inference, if savings vanish against saved TS, or if a side exit duplicates a write.

#### A forge for model-free agent capsules
- **What:** Compile an explicitly bounded task into a deployable program plus state and contracts, with no model endpoint or key. 100×: one reasoning session manufactures a capability usable a billion times, including offline.
- **How it would work:** Use synthesis at the front, then MetaOCaml/LMS-style staging (a genuine first Futamura projection) once the task is a typed DSL program. Require no residual model nodes, bounded loops, a defined input domain and explicit "unsupported" outputs. Package generated TS, tool bindings, contract versions and optionally an interpreter image. Network tools may remain. scriptc native is not browser/Wasm portability.
- **Evidence / numbers:** F: Google/IEA demand growth. M: the local probe shows native execution works for one restricted TS policy. E: one compilation amortized across 1M invocations moves generation cost off the execution path but does not remove API/data costs.
- **Prior art / who has it:** Code as Policies, ordinary generated applications, Vercel QuickJS-Wasm snapshots, LangChain checkpoints, XS, Golem.
- **Verdict:** KEPT (#3). It is the strongest deployment test of the compiler (disconnect inference and run). The capsule is justified only for valuable occupied state, and a plain bundle plus explicit state is the benchmark to beat.
- **Kill test / first proof:** First proof: compile one reconciliation rule to browser/Worker JS, Node TS and scriptc native, then run 1,000 valid and 100 out-of-domain inputs with inference disconnected, comparing JSON state against a QuickJS/Wasm capsule. Kill if model-free coverage needs so much hand coding that an SDK is cheaper, or if JS plus JSON matches the capsule. In that case keep the program and drop the capsule product.

#### A superoptimizer for agent workflows
- **What:** Search equivalent tool/dataflow programs for the lowest measured inference, API, byte and latency cost. 100×: continuously reduce a fleet's bill after every model or tool release.
- **How it would work:** Start with an algebra of pure transforms and snapshot reads: map/filter fusion, projection pushdown, shared reads at one version, batch APIs and permitted aggregation, with equivalent forms held in an e-graph. Effectful operations stay ordered. Rate limits, auth checks, errors and freshness count as observable semantics.
- **Evidence / numbers:** F: Anthropic's 150K→2K tool-context reduction. E: 10M workflows × 100 per-record reads = 1B reads, and a lawful server-side aggregate could approach a 100× request reduction. Links: [Massalin 1987](https://web.stanford.edu/class/cs343/resources/superoptimizer.pdf), [STOKE](https://github.com/StanfordPL/stoke), [egg POPL 2021](https://homes.cs.washington.edu/~cnandi/docs/popl21-cr.pdf).
- **Prior art / who has it:** Massalin, STOKE, Souper, egg (equality saturation). Hand-optimized Code Mode is the baseline.
- **Verdict:** RUNNER-UP (rank 5 of 8). Real external-operation savings are measurable, but it needs trusted semantics, gains saturate on a finite workload, and strong code generation competes.
- **Kill test / first proof:** First proof: 10 pure/read-only workflows over a versioned fixture API with a small rewrite grammar, seeking ≥10× fewer external operations on at least two batchable tasks, search cost included. Kill if an engineer asking the model for optimized TS matches it, or if rewrites alter freshness, errors or effects. In that case keep it as an optimizer pass.

#### Halide for agents: separate the task from its execution schedule
- **What:** Express the task once and compile where and when it runs (browser, Worker near data, Node, native), so thousands of dependent operations happen locally instead of across the WAN.
- **How it would work:** Preserve algorithm and effect dependencies, then pick placement, fusion, batching, parallelism and checkpoint frequency from measured profiles. Code deploys to explicit cooperating hosts with brokered grants and bounded return values. This is not arbitrary Durable Object migration.
- **Evidence / numbers:** E: 1,000 dependent 50 ms WAN calls give a 50 s serial floor, versus ~150 ms with one transfer and local ops, about 333× for that constructed component. This requires owner-side access. Links: [Halide 2012](https://people.csail.mit.edu/jrk/halide12/), [Agent JIT Compilation](https://arxiv.org/abs/2605.21470).
- **Prior art / who has it:** Halide, Agent JIT Compilation (which already separates planning and scheduling), Cloudflare placement tools, conventional query pushdown.
- **Verdict:** RUNNER-UP (rank 4 of 8). Data movement and serial WAN latency survive superhuman planning, but existing batch/query/placement APIs overlap heavily.
- **Kill test / first proof:** First proof: two regional endpoints and three dataflow tasks, comparing per-record calls, batch APIs, fixed placement and compiler-chosen placement, requiring ≥10× fewer measured WAN bytes or crossings plus a real latency win. Kill if batching or SQL pushdown plus existing placement matches it, or if customers won't host the fragment.

#### Incremental agents: maintain the answer instead of rethinking the world
- **What:** Compile a recurring agent task into a dependency graph that reacts to changed facts and recomputes only the affected slice. 100–1000×: millions of always-on agents become sparse dataflow updates.
- **How it would work:** Stage the task, record complete dynamic dependencies, and use webhooks, change feeds or versioned snapshots. Memoize pure subgraphs and invalidate transitive consumers. Track version read, collection membership, deletions, permission changes and negative queries, because digests alone don't establish freshness. Model nodes stay explicit and versioned, and revoked authority does not persist. Workers run pure slices, DOs track graph/effect epochs, and R2 stores versions.
- **Evidence / numbers:** E: 10,000 records with 10 changed per update gives an ideal 1,000× reduction in per-record work, which vanishes if a change invalidates a global judgment. E: the 2030 shape is 1M continuous graphs over 10B tracked facts. Links: [Acar/Blelloch/Harper POPL 2002](https://www.cs.cmu.edu/~rwh/papers/afp/popl02.pdf), [Build Systems à la Carte](https://www.microsoft.com/en-us/research/publication/build-systems-la-carte/).
- **Prior art / who has it:** Incremental computation (Acar et al.), build systems (Mokhov/Mitchell/Peyton Jones). Conventional hand-written incremental software is the formidable baseline.
- **Verdict:** KEPT (#1, the ONE bet, with tracing/staging to build the first graph). It removes repeated world-reading even when the plan is perfect. The open risk is whether customers have trustworthy change feeds.
- **Kill test / first proof:** First proof: one inventory/reconciliation report, 3 versioned fixture tools, 10,000 records and 100 change batches including inserts, deletes, membership and auth changes, compared against full agent reruns, full saved-TS reruns and hand-incremental code. It requires ≥100× fewer processed records, ≥10× lower total cost and exact answers. Kill if connectors can't invalidate without full scans, global changes dirty everything, or it loses to ordinary incremental code after maintenance.

#### Compile agents into a bounded execution budget
- **What:** Compile supported tasks into programs with enforceable upper bounds on inference calls, tool attempts, output bytes and local work, so agent fleets can be admitted and scheduled like services.
- **How it would work:** A restricted TS/IR subset with ranked loops and conservative effect/count analysis (abstract interpretation), plus runtime meters at the broker. Unknown loops yield unknown static cost and are capped at runtime. CPU, tokens and remote attempts have separate limits. Remote latency is not provable.
- **Evidence / numbers:** E: 1M event jobs × an accidental 1,000-iteration loop = 1B attempts, while a 10-call contract bounds it to 10M, a 100× reduction in exposure. This is a constructed capacity argument. Link: [Cousot/Cousot POPL 1977](https://cs.nyu.edu/~pcousot/COUSOTpapers/POPL77.shtml).
- **Prior art / who has it:** Abstract interpretation (Cousot), simple workflow DSLs, runtime metering.
- **Verdict:** RUNNER-UP (rank 7 of 8). Capacity and quotas still matter with perfect models, but this is more naturally a runtime feature than a company.
- **Kill test / first proof:** First proof: 10 bounded TS workflows plus 3 unbounded variants over 1,000 inputs, comparing predicted and actual counts with a Worker broker enforcing the limits. Kill if the restrictions exclude paying workloads or metering alone gives equal value. In that case keep the meter and drop the compiler.

#### A supercompiler that turns experience into algorithms
- **What:** Infer parameterized loops and branches from multiple traces, then synthesize a compact algorithm that handles new sizes and combinations without replaying the original exploration.
- **How it would work:** Turchin-style unfold/generalize/fold plus synthesis over a bounded trace language. Recover explicit bindings and use multiple traces and counterexample simulator probes to tell "repeat until empty" from "exactly three". Unknown predicates stay as model nodes or cause refusal.
- **Evidence / numbers:** E: a 1,000-record task needing one decision per record becomes one loop with zero per-record inference, a 1,000× reduction in that component. F: TraceCompiler took one intent from 34→11 tool calls and passed 15/21 state tests, using a hand-transcribed skeleton. Links: [SKILL-DISCO](https://arxiv.org/abs/2606.26669), [TraceCompiler](https://arxiv.org/html/2608.02680v1), [Turchin 1986](https://doi.org/10.1145/5956.5957).
- **Prior art / who has it:** Turchin supercompilation, WebRobot (PLDI 2022), Gulwani FlashFill-style synthesis, AWM, SKILL-DISCO (direct overlap), TraceCompiler.
- **Verdict:** RUNNER-UP (rank 6 of 8). It is the largest leap from experience to software, but branches are underidentified, and stronger models may infer the algorithm from the prompt alone.
- **Kill test / first proof:** First proof: 3 simulator families trained on sizes 1–5 and tested on hidden sizes 0, 17 and 100 plus an unseen branch, compared against a prompt-only coding model and SKILL-DISCO-like reuse. Kill if direct prompt-to-code does as well or guard failures dominate. In that case keep trace-guided debugging.

#### A multi-level intermediate representation for agent programs
- **What:** A portable IR that preserves task, dependency, effect and cost semantics and progressively lowers into different runtimes, so one procedure deploys across frameworks without rebuilding its meaning.
- **How it would work:** Three levels (intent/model, effectful workflow, executable code) that preserve residual inference, guards, versioned reads, authority scopes and resumable state. It uses dialect-like tool extensions and explicit refusal. Imitate MLIR's architecture in a small TS IR rather than using MLIR itself. The concrete first IR: a typed JSON graph (pure ops, versioned reads, residual model decisions, guarded branches, bounded loops, writes, suspension) with a TS interpreter.
- **Evidence / numbers:** E: 1,000 workflows × 10 connectors × 10 configurations = 100,000 qualification relationships. That arithmetic does not show the matrix factorizes, and no primary measure of framework churn was found. Link: [MLIR](https://research.google/pubs/mlir-scaling-compiler-infrastructure-for-domain-specific-computation/).
- **Prior art / who has it:** MLIR (lineage). Heterogeneous agent frameworks and tool interfaces.
- **Verdict:** RUNNER-UP (rank 8 of 8). It enables the other bets, but standardization without consumers is infrastructure looking for demand. Keep it internal.
- **Kill test / first proof:** First proof: represent 5 workflows from two harnesses, lower them into a TS interpreter and scriptc source, and force a schema mismatch. Identical effects and a useful refusal are required. Kill if no second consumer needs the format or ordinary source translation suffices.

#### Rejected in this report
- **"First agent JIT" / "a JIT for agents" as the story** — already occupied by Muscle-Mem, PreAct, Agent JIT Compilation, SKILL-DISCO, TraceCompiler, A-JIT and FlyMy.AI.
- **"The first Futamura projection of an LLM"** — fixing tools, weights and prompt doesn't make inference model-free. The honest routes are a staged DSL with explicit model nodes, or synthesis/distillation with a restricted validity domain.
- **Compiling to TypeScript/native as differentiation** — an implementation choice, not a product. A smaller capsule or native binary alone does not establish a compiler product.
- **Snapshotting/capsules as the novelty** — the capsule landscape (Vercel, LangChain, XS, Golem) already covers it. Source plus JSON state is the default.
- **Tracing HTTP calls inside the inference client** — the PyPy lesson: this doesn't compile reasoning. Trace a typed workflow machine instead.
- **Treating similar-scoring prompts as equal (e-graph rewrites)** — not an equality. Rewrites must be valid under effect and freshness semantics.
- **Building everything at once (e-graph optimizer + new language + distributed scheduler + standards consortium)** — explicitly ruled out for the two-week prototype.

### 03-classiccs: Classic computer science becomes central again
Lens: classic CS (memoisation, incremental computation, query optimisation, dataflow, paging, scheduling, transactions, consensus, GC, MDL) applied to a world where the expensive function is a model call or a whole agent run. Headline finding: even a perfect model cannot make yesterday's data current, remove round trips, or stop a million agents recomputing the same thing, so build-system and database machinery for cognition becomes worthwhile; a local surrogate showed 100× fewer warm node evaluations on sparse edits and exactly 1.00× on dense edits, so dependency sparsity is the deciding unknown. Two cross-cutting rules: end-to-end (the application owns reuse/freshness/effect contracts) and worse-is-better (small `observe/derive/subscribe/commit/release` API). The ONE bet: Thought Builds for a continuously changing operational dossier, with code compilation as its second optimisation, inside one organisation first; verdict **go-with-changes** (continue only at ≥2× total recurring cost saving on a real workflow with a plausible route to 100×).

#### Thought builds (Salsa/Adapton for agent work)
- **What:** Build and maintain expensive reasoning as a dependency graph so that an input change rebuilds only the demanded affected artifacts; the 100× version is a shared computation fabric where thousands of agents consume one maintained industry map, repo analysis or supplier assessment.
- **How it would work:** A TS `derive/read/observe` API keys each request by code/prompt/schema identity, model/deployment identity, sampling contract, tenant/authority scope and versioned dependency observations, stores the response as an immutable artifact, and dirties/recomputes downstream nodes on demand with early cutoff on equal canonical output (Bazel action-hash vs content-addressed output split). Effects go through the transaction manager (#7), outside memoisation; Workers serve, sharded DOs coordinate per-graph revisions and single-flight work, R2 holds artifacts; no global graph or automatic cross-tenant cache.
- **Evidence / numbers:** E: 1,000 agents × 200-artifact dossier = 200,000 evaluations vs 200 shared (1,000× ceiling, needs exact shared inputs). M: local surrogate (200 extraction + 20 dossier + 1 portfolio nodes), 100 sparse edits: 22,321 vs 441 node evaluations; warm-only 22,100 vs 220 = **100.45×**, ~**50.61×** incl. cold start; dense edits **1.00×** (memo strictly more CPU). E: speedup ≈ `C/(f*C + H)`; 100× needs `f + H/C ≤ 0.01`; 100× cheaper inference makes overhead's share 100× larger. F: Google >1.3 quadrillion monthly tokens, >20× YoY (2025-10-29). Sources: [Acar thesis 2005](https://www.cs.cmu.edu/~rwh/students/acar.pdf), [Adapton PLDI 2014](https://www.cs.umd.edu/projects/PL/adapton/), [Build systems à la carte 2018](https://www.microsoft.com/en-us/research/publication/build-systems-la-carte/).
- **Prior art / who has it:** Michie memo functions (1968), Acar self-adjusting computation, Adapton, Salsa, Build systems à la carte, Bazel remote cache, Nix content addressing.
- **Verdict:** KEPT (#1, the ONE bet) — most directly attacks the bill that grows as agents maintain overlapping work; sparse, stable dependency boundaries are the decisive unknown.
- **Kill test / first proof:** Repo-impact and supplier dossiers over ≥30 held-out revisions vs fresh, whole-run cache and hand-incremental code; stop the platform pitch if it cannot halve recurring cost vs the best simple incremental baseline, if most changes invalidate nearly everything, or on any silent reuse across an undeclared dependency.

#### System R for intelligence: materialised views over model calls
- **What:** Accept a declarative task and plan its execution across exact code, indexes, model calls, tools and maintained model-derived relations; the 100× version is an intelligence database whose optimiser amortises semantic operations across queries, tenants (where authorised), revisions and providers.
- **How it would work:** Cost-based planner with `EXPLAIN` showing measured cardinalities, provenance of model-derived columns, freshness, expected expense and shared in-flight work; materialise a relation by expected future use vs refresh/storage cost, prioritising cross-query/cross-revision reuse and origin budgets over prompt routing. Only semantics-preserving transformations (moving a model call past a filter can change answers); ordinary SQL engine plus a TS controller.
- **Evidence / numbers:** E: 1M documents with a 1% selective exact predicate cuts model extraction 1M → 10,000 calls (100× for that stage only, not end-to-end). F: IEA data-centre demand 485 TWh (2025) → ~950 TWh (2030). Sources: [Selinger System R 1979](https://web.eecs.umich.edu/~michjc/eecs584/Papers/selinger_1979.pdf), [Palimpzest 2024](https://arxiv.org/abs/2405.14696), [LOTUS 2024/2025](https://arxiv.org/abs/2407.11418).
- **Prior art / who has it:** System R, Gupta & Mumick view maintenance (1995), Palimpzest (cost/time/quality optimisation of AI workloads), LOTUS (semantic relational operators) — "SQL plus LLMs" is occupied.
- **Verdict:** RUNNER-UP (rank 4) — excellent mechanism and buyer economics, but Palimpzest/LOTUS occupy the obvious pitch; integrate before competing.
- **Kill test / first proof:** 10,000 supplier records, 20 overlapping queries, predicate pushdown + one materialised extraction column + one cross-query reuse rule + adaptive replanning vs hand-tuned and Palimpzest/LOTUS; demote to a feature if net savings <20% vs a well-tuned existing engine at equal outcomes/latency.

#### A living spreadsheet of shared agent observations
- **What:** Replace repeated agent rereading and status meetings with continuously maintained, provenance-bearing facts and derivations; the 100× version is an organisation whose agents subscribe to changes in a common operational model, calling models only at unstructured-data boundaries.
- **How it would work:** Distinguish `observed(source, version, value)` from `model_claim(model, input_hash, value)`; model calls extract structured notes once per document version, and positive finite-domain Datalog / SQL maintains declared consequences and notifications. Monotone evidence accumulation can be coordination-free (CALM); "resolved", "no blocker" or final allocations cannot, and go to a DO owner.
- **Evidence / numbers:** E: 1,000 agents polling 100 inputs hourly = 2.4M reads/day vs 2,400 for one shared observer (1,000× ceiling given same lawful view and freshness). F: Cloudflare crawl growth 24% YoY June 2025 slowing to 4% July; Anthropic crawl-to-referral ~38,000:1. Sources: [Excel recalculation](https://learn.microsoft.com/en-us/office/client-developer/excel/excel-recalculation), [Differential dataflow 2013](https://www.microsoft.com/en-us/research/publication/differential-dataflow/), [CALM 2020](https://doi.org/10.1145/3369736).
- **Prior art / who has it:** Dennis dataflow (1974/75), Excel dependency trees, Datalog/deductive databases (Ceri/Gottlob/Tanca 1989), differential dataflow, ordinary databases with CDC/event subscriptions.
- **Verdict:** RUNNER-UP (rank 5) — strong origin/API savings but likely a vertical application of #1 plus ordinary databases.
- **Kill test / first proof:** Release-readiness sheet for 20 services / 10 consumers vs independent agents and shared SQL+events (incl. deletion, duplicate delivery, contradictory claims); require ≥10× fewer origin reads or model extractions with bounded freshness, kill standalone platform if SQL/events match it with less integration.

#### Demand paging for context, backed by a computation CDN
- **What:** Give long-lived agents addressable external memory and a cost-aware working set, with fetched/derived pages cached near consumers; the 100× version is a context hierarchy spanning device, edge, regional storage and inference service.
- **How it would work:** Content-addressed pages, stable IDs, explicit fetch tools (the model/controller must request a page; API models cannot fault transparently), versioned summaries and a cheap index of what lives outside the window. Eviction scored by avoided cost × reuse probability per byte, adjusted for freshness/authorisation and measured against LRU; Belady used only as an offline bound; semantic paging, KV/prefix reuse, result caching and source revalidation kept separate.
- **Evidence / numbers:** E: 100 turns × 500,000 tokens = 50M input tokens vs 2.5M with a 25,000-token working set (20× presentation reduction, before faults/summaries and provider discounts). E: 2030, 10M resumable sessions × 10 MB = 100 TB. Sources: [Denning working sets 1968](https://denninginstitute.com/pjd/PUBS/WSModel_1968.pdf), [MemGPT 2023](https://arxiv.org/abs/2310.08560), [PagedAttention/vLLM 2023](https://doi.org/10.1145/3600006.3613165).
- **Prior art / who has it:** Belady (1966), Denning, Akamai, RFC 9111 HTTP caching, MemGPT (virtual context management), vLLM PagedAttention, SGLang prefix reuse; provider prompt caching.
- **Verdict:** RUNNER-UP (rank 7) — real resource problem but considerable prior art and high provider-internalisation risk; must beat modern caching/retrieval.
- **Kill test / first proof:** 20 long tasks vs full context + provider caching, structured retrieval, MemGPT-style paging and cost-aware eviction, incl. a late question needing an evicted fact; stop if it cannot halve actual recurring spend at comparable outcomes or fault churn destroys latency.

#### A scheduler for cognition, with solvers instead of agent meetings
- **What:** Schedule agent jobs over token budgets, deadlines, tool quotas and shared reservations while exact solvers pick feasible combinations of proposed actions; the 100× version is a multi-resource OS for millions of intermittent agent jobs with metered bounded search.
- **How it would work:** Models propose jobs/actions in a typed schema; constraints encode budgets, capacities, deadlines, precedence, geography; SAT/SMT for feasibility, a fair/DRF-style policy for online admission; budgets reserved atomically via #7/#8; scheduling at call/tool boundaries (no assumed preemption). Levin/Solomonoff used honestly: finite candidate library, computable prior, measured yields, bounded quanta, only for tasks with cheap completion checks.
- **Evidence / numbers:** E: 1,000 agents × 100 speculative branches = 100,000 competing branches; 100 agents × 10 plans = 10^100 joint combinations (search-space count, not runtime). Sources: [Dominant Resource Fairness 2011](https://www.usenix.org/conference/nsdi11/dominant-resource-fairness-fair-allocation-multiple-resource-types), [Z3 2008](https://www.microsoft.com/en-us/research/publication/z3-an-efficient-smt-solver/), [Levin 1973](https://www.mathnet.ru/eng/ppi914).
- **Prior art / who has it:** Bellman DP, CTSS time-sharing (1962), DPLL, Z3, DRF, Levin universal search, Solomonoff induction.
- **Verdict:** NARROWED (rank 6) — scarce-resource allocation survives, universal-search rhetoric does not; platform distribution is the obstacle; keep basic admission and budget accounting.
- **Kill test / first proof:** TS queue with 1,000 replayable synthetic jobs + small real API cohort, FIFO vs fair vs DRF vs solver-assisted; kill the sophisticated policy if it cannot improve useful completed work per dollar or deadline misses by 20% vs a simple scheduler.

#### Compression is executable understanding: compile recurring thought into code
- **What:** Detect a repeated model-mediated operation and replace it with a small executable procedure plus explicit fallback; the 100× version is a reasoning compiler that continuously converts stable portions of an organisation's agent traffic into ordinary cheap software.
- **How it would work:** Mine traces for bounded transformations (identifier normalisation, log parsing, schema mapping, routing, repeated calculations), propose a parameterised TS program or decision table with a declared input domain, fall back to a model outside it; compile to Wasm/native (scriptc for its supported subset) or run in QuickJS. Operational MDL charges program, libraries, exceptions and residuals, plus runtime and maintenance; shared parameterised implementations, not a microservice per example.
- **Evidence / numbers:** E (hypothetical unit costs): $100 generation, $0.01/model op, $0.00001/execution → break-even ~10,010 executions; at 1M executions ~1,000× operating-cost ratio, ~91× incl. the $100. F: GitHub 1M+ coding-agent PRs May–Sep 2025. Sources: [Kolmogorov 1965](https://www.mathnet.ru/eng/ppi68), [Rissanen MDL 1978](https://research.ibm.com/publications/modeling-by-shortest-data-description), [Solomonoff 1964](https://www.raysolomonoff.com/publications/1964pt1.pdf).
- **Prior art / who has it:** Kolmogorov complexity, Rissanen MDL, Solomonoff prior; expert systems and program synthesis (struggled with spec, coverage, drift).
- **Verdict:** KEPT (#2) — largest direct inference-elimination upside and better models improve the compiler; volume and drift decide break-even; use as the optimisation backend of #1, not a separate launch.
- **Kill test / first proof:** Three recurring transformations with authoritative specs, temporal holdout, malformed/new-version inputs and one simulated format migration vs strong cached/batched model and handwritten code; kill if best candidate is below 10× total-cost improvement, drift keeps resetting break-even, or a few handwritten functions capture it all.

#### A transaction manager for long-running agent work
- **What:** Put effect identities, budgets, reservations and compensation outside agent runs so restarts and forks do not repeat commitments; the 100× version is a transaction fabric across participating agent-operated services with explicit partial completion.
- **How it would work:** A DO-backed ledger records stable business-operation identity, parent budget, intent, result and workflow state, using local transactions/outbox, downstream idempotency where supported, and resource-owner-checked fencing. Forked branches get new proposal identities, retries keep the same operation identity; uncertain non-idempotent outcomes surface as `unknown`; no locks held during long model calls (read versions, propose, reserve briefly, commit).
- **Evidence / numbers:** E: 10,000 workflows/day × 20 actions × assumed 0.1% ambiguous rate = 200 uncertain outcomes/day. F: GitHub 1M+ coding-agent PRs (says nothing about duplicate effects). Sources: [Gray 1981](https://www.cs.utexas.edu/~witchel/380L/papers/gray81vldb-transaction.pdf), [Sagas 1987](https://www.cs.princeton.edu/research/techreps/598).
- **Prior art / who has it:** Gray transactions, Garcia-Molina & Salem Sagas; durable-workflow engines and payments/integration providers already own much of the surface.
- **Verdict:** NARROWED (rank 8) — strictly survives perfect reasoning, but mature workflow/connector competition makes it an integration wedge; "exactly-once agents" is occupied and too broad.
- **Kill test / first proof:** Idempotent + non-idempotent mock connectors, crashes in each window, stale capsule restore, failed compensation, vs an existing workflow engine; any duplicate within the idempotent contract falsifies it; kill the platform thesis if an existing engine plus small adapter serves equally.

#### Consensus for ownership, CRDTs for shared work
- **What:** Separate what agents can accumulate concurrently (evidence, annotations, compatible edits) from the few decisions that need one authoritative order (budgets, ownership, commits); the 100× version is an agent society sharing evidence asynchronously and serialising only where required.
- **How it would work:** Existing CRDT libraries for evidence/documents; an authoritative resource owner/log (DO or established store) for ownership and spending, with monotonic fencing tokens enforced by the target resource; no agent-implemented Paxos, no arbitrary heap merge, crash-fault assumptions only; a copied capsule does not copy a lease.
- **Evidence / numbers:** E: 1,000 fully connected agents = 999,000 directed pairs; 10,000 = 99,990,000 (topology warning); at 100 ms RTT, 20 serial rounds ≥2 s. Sources: [Paxos Made Simple 2001](https://lamport.azurewebsites.net/pubs/paxos-simple.pdf), [Raft 2014](https://raft.github.io/raft.pdf), [Shapiro et al. CRDTs 2011](https://www.lip6.fr/Marc.Shapiro/papers/2011/Comprehensive-CRDTs-RR7506-2011-01.pdf).
- **Prior art / who has it:** Paxos, Raft, CRDTs, central event logs, pub/sub, platform coordination primitives.
- **Verdict:** NARROWED (rank 9) — essential infrastructure, weak standalone product; consume established consensus/CRDT implementations.
- **Kill test / first proof:** 100 simulated + 2 real browser clients editing evidence offline with a separate quota ledger (duplicate delivery, reconnect, stale ownership, concurrent allocation) vs central log and pub/sub; kill if central events plus existing libraries match latency/availability with less complexity; reject any design treating heap merge or a model's ownership assertion as protocol.

#### A garbage collector for agent-generated software
- **What:** Make generated apps, tasks, dependencies, credentials and cloud resources collectible through explicit ownership, roots, leases and references; the 100× version lets organisations create millions of temporary software objects without millions of permanent obligations.
- **How it would work:** Every generated deployment gets a manifest (owner, entrypoints, resource IDs, deps, scheduled jobs, external consumers, retention, rollback pins); roots are production routes, user pins, active tasks, pending effects/compensations and retention policies; mark a consistent generation, quarantine unreferenced objects, grace period, idempotent sweep, write barrier for new references. Only for resources created through one managed runtime/tool broker (jitk/QuickJS guests register via the tool channel); no inferring deadness from access logs.
- **Evidence / numbers:** F: GitHub 43.2M merged PRs/month, +23%. E: 1M generated resources × $0.10/month idle = $100,000/month; ×1 MB = 1 TB per version; 2030 scenario of 10M temporary apps. Sources: [McCarthy Lisp 1960](https://www-formal.stanford.edu/jmc/recursive/node4.html), [Kubernetes GC](https://kubernetes.io/docs/concepts/architecture/garbage-collection/), [Crossplane managed resources](https://docs.crossplane.io/v1.20/concepts/managed-resources/).
- **Prior art / who has it:** McCarthy GC, Nix store GC with profile generations, Kubernetes owner references/finalizers, Crossplane external-resource deletion.
- **Verdict:** KEPT (#3) — strongest bet on the stock of obligations growing with software abundance; restrict to a mediated resource population; may be just a small adapter to an existing controller.
- **Kill test / first proof:** 1,000 local manifests + small Cloudflare test cohort (shared deps, cycles, delayed effect reply, reference during marking, rollback pin, external root) vs TTL, IaC destroy and owner-reference/Crossplane controller, reversible quarantine first; kill if creation cannot be mediated, unknown roots dominate, or TTL/IaC/existing controllers give the same savings; one collected rooted object invalidates safety.

### 04-worsening: The problems that get worse as models get better
Lens: second-order costs of capable, cheap, abundant agents — a ranked map of 12 worsening problems (origin/API load, generated-software lifecycle, accumulated state, delegated authority, sequential latency, power/HBM, dependency churn, swarm contention, data movement, human attention, reproducibility, recycled evidence) turned into eight candidate products A–H. Headline finding: perfect workers still compete for a finite world (origins, speed of light, shared budgets, retained state), so allocation, locality, conservation and reclamation are model-proof, whereas human approvals and model-collapse insurance are weaker; much of the obvious surface (Pay Per Crawl, Signed Agents, Code Mode, Cap'n Web, Dynamic Workers) is already Cloudflare's. The ONE bet: A, an Origin Work Protocol that makes one origin compute shared agent work once per data epoch and permission class; verdict **go-with-changes** (continue only at ≥2× backend-work win over tuned cache/coalescing/change-feed on a held-out mixed workload with a willing origin, else switch to B).

#### A. Origin Work Protocol: let the scarce server schedule the agents
- **What:** An origin publishes bounded query jobs, freshness contracts and capacity reservations so agents request useful results instead of independently crawling and polling; the 100× version is a network where millions of consumers subscribe to owner-defined computations, with shared work done once per authorised equivalence class.
- **How it would work:** Jobs carry code/query hash, data epoch, freshness bound, authorisation scope, output cap, price/budget and cancellation lease; a DO scheduler and owner-approved query executor share results only within entitlement classes, so origin work grows with distinct authorised queries and data changes rather than consumer count. Start with owner-published templates, not arbitrary visitor code; D's quota conservation and B's leases are components.
- **Evidence / numbers:** F: Cloudflare 2025 review >15× (body text >21×) growth in user-action crawling; AI bots 4.2% of HTML requests plus Googlebot 4.5%; AI-training share of classified crawls 22% → 52% (spring 2025 → June 2026). E: 2030, 100,000 origins, 1B logical queries/day; DO soft limit ~1,000 req/s per object (F). Sources: [Cloudflare Radar 2025](https://blog.cloudflare.com/radar-2025-year-in-review/), [Cloudflare agentic-internet report 2026](https://blog.cloudflare.com/agentic-internet-bot-report/), [Active Cache 1998](https://pages.cs.wisc.edu/~cao/papers/active-cache.html).
- **Prior art / who has it:** Active Cache (Middleware 1998), CDNs/edge compute, HTTP caching/ETags/request coalescing, change feeds; Cloudflare Pay Per Crawl (closed beta), dynamic crawl pricing, and Cloudflare's freshness/discovery roadmap (major bundling threat).
- **Verdict:** KEPT (#1, the ONE bet) — strong observed demand, real resource boundary, best Cloudflare fit; a caller cannot dedupe across competitors, an owner can; distribution (one willing origin) is the solo-builder risk.
- **Kill test / first proof:** One catalog/search origin, 3 templates, 2 auth classes, 1,000 replayed consumers vs tuned caching + ETags + coalescing, batching and change feed; target ≥10× fewer backend executions on repeated cohort, ≥2× on held-out mixed trace, zero wrong-scope sharing; stop if queries rarely share, subscriptions win, overhead erases savings, or no owner provides an epoch contract.

#### B. Lease OS: garbage collection for generated computers
- **What:** Every generated app/task gets an owner, renewable lifetime, retained roots and a reclamation plan for its state and external resources; the 100× version makes creation and retirement equally automatic across billions of temporary computers (memories, files, deployments, timers, credentials, evidence).
- **How it would work:** A root/lease graph across heaps, files, sessions, schedules and authority, enumerable because resources are allocated through the tool channel; retiring authority precedes stopping wakes precedes deleting data; content-addressed shared base images; tasks can be frozen as receipts, kept, or retired; coarse leases rather than per-file heartbeats; audit evidence has its own root.
- **Evidence / numbers:** F: GitHub 986M pushes (+25%), 43.2M merged PRs/month (+23%), 2.42M repos with notebooks (+75%), 1.9M with Dockerfiles (+120%) — proxies, orphan state unsized. E: 1M tasks/day × 30-day retention = 30M roots; ×1 MB = 30 TB ≈ $450/month at R2 $0.015/GB-month (F), vs checkpoint/minute for 1M tasks = 43.2B writes/month ≈ $194,400 — bookkeeping can exceed savings. Sources: [Gray/Cheriton leases 1989](https://web.stanford.edu/class/cs240/readings/leases.pdf), [Nix LISA 2004](https://static.usenix.org/events/lisa04/tech/full_papers/dolstra/dolstra_html/index.html), [Code Mode how it works](https://developers.cloudflare.com/agents/tools/codemode/how-it-works/).
- **Prior art / who has it:** Leases, Nix closures/GC, native object-store TTL, Cloudflare Code Mode's replay, connector disposal, retention limits and `expirePaused()`.
- **Verdict:** KEPT (#2) — strongest builder-owned mechanism and the fallback if no origin participates; must prove cross-resource completeness under crashes beyond existing expiry hooks.
- **Kill test / first proof:** Five adapters (R2 images, DO state, scheduled wakeups, simulated browser, broker grants), 10,000 task trees with crashes at every boundary vs native TTL + Code Mode disposal; target zero retained-root deletion, zero authorised wake after expiry, ≥95% reclamation within two sweeps; kill if native TTL/workflow cleanup covers meaningful spend or adapters cannot enumerate costly resources; kill the capsule story if JSON task roots suffice.

#### C. Round-trip compiler: move the next hundred instructions to the data
- **What:** Lower discovered deterministic stretches of agent work into bounded programs placed beside the tool/data owner, returning to the model only at real reasoning or authority boundaries; the 100× version optimises a task's distributed critical path across cooperating domains.
- **How it would work:** Agent tool loops become dependency graphs; deterministic subplans run in owner-approved Workers/Wasm environments with promise pipelining, an external broker authorises writes, capsules park only where reconstruction is costly; scriptc optional native backend on a compatible host (not Worker Wasm).
- **Evidence / numbers:** F/E: speed of light 299,792,458 m/s → ≥~40 ms request/reply at 6,000 km in vacuum, 100 sequential exchanges ≥~4 s; at 80 ms RTT, 100 round trips = 8 s. F: METR ~7-month doubling of task horizon (difficulty, not chain length). F: Anthropic MCP code-execution example 150,000 → 2,000 tokens (98.7%). Sources: [Cap'n Web 2025](https://blog.cloudflare.com/capnweb-javascript-rpc-library/), [Cap'n Proto pipelining 2013](https://capnproto.org/news/2013-12-12-capnproto-0.4-time-travel.html), [METR 2025](https://metr.org/blog/2025-03-19-measuring-ai-ability-to-complete-long-tasks/).
- **Prior art / who has it:** Cap'n Proto promise pipelining, Active Names (USITS 1999), Cloudflare Code Mode, Dynamic Workers, Cap'n Web, ordinary query pushdown.
- **Verdict:** RUNNER-UP (rank 4) — physical limit and clear trace demo, but Code Mode/Cap'n Web/ordinary placement sharply narrow novelty; Cloudflare is better placed to integrate it.
- **Kill test / first proof:** 30 held-out read-only tasks at 20/80/160 ms RTT vs plain tool calls, hand Code Mode and Cap'n Web; go only at ≥2× p95 over the best baseline on one real workload with equal outputs and no added authority; stop if existing tools suffice, the owner won't execute subplans, or each step needs central inference.

#### D. Conserved mandates: cloning a worker cannot clone its rights
- **What:** A tool broker gives descendants attenuated rights against one externally conserved task budget, with revocation and fenced ownership across copies; the 100× version is a "resource constitution" where millions of descendants act but their combined money, quotas and effect rights stay within the principal's grant.
- **How it would work:** Per-root DO brokers reserve sub-budgets into bounded child escrows (no global sequencer); signed requests name operator, principal/root, descendant, resource, amount, expiry and operation ID; rights live in the broker, not the snapshot, so stale restores cannot spend; uncertain external operations stay unresolved; humans set a bounded policy once.
- **Evidence / numbers:** F: Okta vendor estimate of 50 non-human identities per human (April 2025, not an agent growth rate); Anthropic multi-agent ~15× chat tokens. Sources: [Macaroons NDSS 2014](https://research.google/pubs/macaroons-cookies-with-contextual-caveats-for-decentralized-authorization-in-the-cloud/), [Okta NHI datasheet](https://www.okta.com/sites/default/files/2025-06/Securing-Non-Human-Identities-with-Okta.pdf), [Cloudflare Signed Agents](https://blog.cloudflare.com/signed-agents/).
- **Prior art / who has it:** Macaroons, OAuth scopes, IAM/payment platforms, Cloudflare Signed Agents / Web Bot Auth, Visa/Mastercard agentic-commerce integrations.
- **Verdict:** KEPT (#3) — needed even for honest perfect agents and a required component of A and B; crowded IAM/accounting space, so must win on descendants, portability and revocation.
- **Kill test / first proof:** One root with 1,000 credits forked into 100 descendants across two adapters with retries, stale restores, cancellation and crashes; require aggregate spend ≤1,000, no post-revocation reservation, no stale-owner dispatch, vs OAuth + transactional balance; demote to a library if IAM + a budget table suffices; never claim global exactly-once without external idempotency.

#### E. Inference refinery: spend intelligence once, run the routine many times
- **What:** Convert repeated, stable agent work into versioned deterministic programs, keeping inference only for novelty; the 100× version is a fleet-wide repertoire of executable skills whose repeated execution costs ordinary compute.
- **How it would work:** Content-addressed skills declare input domain, policy, dependencies and version; sharing uses explicit semantics and permission scope (no fuzzy answer caching); Workers JS/Wasm first, scriptc for its supported native subset; changed contracts/input classes fall back to a model. Break-even requires more than C/s reuses, reported per skill class.
- **Evidence / numbers:** F: IEA 2025 data-centre electricity +17%, AI-focused +50%; 485 → 950 TWh by 2030 (E: ~14.4% CAGR all-centre, ~24.6% AI-focused); Stanford AI Index >280× price drop for fixed GPT-3.5-level MMLU (Nov 2022–Oct 2024). E: 2030, 10B routine invocations/day. Sources: [IEA 2026](https://www.iea.org/reports/key-questions-on-energy-and-ai/executive-summary), [Futamura 1971](https://fi.ftmr.info/PE-Museum/PE-Original-English1971.pdf), [AI Index 2025](https://hai.stanford.edu/ai-index/2025-ai-index-report/research-and-development).
- **Prior art / who has it:** Futamura partial evaluation; prompt caching, batching, cheap adequate models, hand-written templates.
- **Verdict:** RUNNER-UP (rank 5) — better models improve synthesis and economics are measurable, but cheap models, caching and low reuse may erase savings.
- **Kill test / first proof:** 20 repeated workloads × 1,000 held-out inputs vs prompt caching, batching, cheap model, templates, generated JS; target ≥10× net cost reduction on ≥5 workloads vs the best model-price baseline; kill if caching/cheap models win, reuse is low or templates dominate.

#### F. Runtime closure commons: patch the shared substrate, retire the copies
- **What:** Package generated apps as explicit immutable dependency/runtime closures, deduplicate them and propagate supported substrate updates across the dependent fleet; the 100× version lets a billion bespoke programs share a small maintained compatibility layer.
- **How it would work:** Apps bind to a small number of maintained closure families; a new base revision migrates eligible tasks, pins incompatible ones and retires unreferenced bases; GrowOS grows missing non-trusted APIs demand-driven while the tiny trusted jitk host stays fixed.
- **Evidence / numbers:** F: Sonatype 9.8T package downloads in 2025, +67% YoY; 86% of Maven Central traffic from cloud providers; 454,600+ new malicious packages in 2025, cumulative >1.233M. E: 2030, 100M app revisions over 10,000 closure families. Sources: [Sonatype 2026](https://www.sonatype.com/press-releases/sonatype-research-reveals-open-malware-grows-75-percent), [Exokernel 1995](https://pdos.csail.mit.edu/6.828/2006/readings/engler95exokernel.pdf), [Nix 2004](https://static.usenix.org/events/lisa04/tech/full_papers/dolstra/dolstra_html/index.html).
- **Prior art / who has it:** Exokernel, Nix, package mirrors, lockfiles, bundlers, platform base images.
- **Verdict:** RUNNER-UP (rank 6) — most direct GrowOS/scriptc extension to software proliferation, but fragmentation, compatibility and existing deployment tools may dominate; better models also remove dependencies.
- **Kill test / first proof:** 20 constrained TS programs, 3 dependency families, one compatible substrate fix vs bundled deps + warm cache; require ≥5× fleet byte reduction or ≥2× rebuild reduction with rollback; stop if caches win, families fragment ~one per app, or migrations become per-tenant services; never grow the trusted host to chase npm.

#### G. Observation capsules: preserve the world a correct program actually saw
- **What:** Package a constrained execution with pinned code/engine, tool observations, data identities and explicitly absent secrets so another host can reproduce its recorded result; the 100× version is a portable interchange for computational history that outlives the original provider/orchestrator.
- **How it would work:** Tool-only ABI journals nondeterminism (clock, random, responses); offline replay in a browser Worker or Node host makes no network calls and issues no real effects; a live fork gets fresh authority and is labelled a new run; receipts can attest body hashes without retaining bodies.
- **Evidence / numbers:** F: GitHub 11.5B Actions minutes, +35% in 2025 (execution volume, not irreproducibility). E: 2030, 100M run manifests/day. Sources: [ReVirt OSDI 2002](https://www.usenix.org/conference/osdi-02/revirt-enabling-intrusion-analysis-through-virtual-machine-logging-and-replay), [GitHub Actions 2025](https://github.blog/news-insights/octoverse/what-986-million-code-pushes-say-about-the-developer-workflow-in-2025/), [quickjs-wasi](https://github.com/vercel-labs/quickjs-wasi).
- **Prior art / who has it:** ReVirt, workflow-engine journals, Code Mode logs/replay, Vercel quickjs-wasi snapshots, LangChain/XS/Golem capsule alternatives.
- **Verdict:** RUNNER-UP (rank 7) — exact past observations survive perfect reasoning, but much of the value may be source + journal and distribution is weak.
- **Kill test / first proof:** 30 read-only workflows with clock/random and a changed upstream response replayed offline on two hosts vs signed source+inputs+journal and Code Mode logs; require 100% covered-output reproduction, zero live calls, ≥2× lower reconstruction time on costly-prefix cases; kill the capsule requirement if journals suffice.

#### H. Fresh evidence exchange: buy an observation rather than another paraphrase
- **What:** Data owners publish signed, time/version-scoped observations and derived query results with explicit reuse terms so agents can tell original evidence from chains of copies; the 100× version is a market for fresh facts and licensed computations whose provenance survives composition.
- **How it would work:** Each response carries owner identity, source version/time, query hash, output digest and a machine-readable licence reference; derived artifacts keep source links; payment via existing rails (Pay Per Crawl etc.). A signature asserts origin and bytes only, not truth, human authorship or permission.
- **Evidence / numbers:** F: Nature 2024 recursive synthetic-data collapse; Gerstgrasser et al. 2024 show accumulation with original data avoids it; Cloudflare crawl-to-referral ~38,066:1 (Anthropic, July 2025) vs 286,930 in January, OpenAI ~1,091:1. E: 2030, 10,000 owners, 100M observations/day. Sources: [Shumailov et al. 2024](https://www.nature.com/articles/s41586-024-07566-y), [Gerstgrasser et al. 2024](https://arxiv.org/abs/2404.01413), [W3C PROV 2013](https://www.w3.org/TR/prov-overview/).
- **Prior art / who has it:** W3C PROV, Cloudflare Pay Per Crawl and payment integrations, plain signed JSON + billing.
- **Verdict:** RUNNER-UP (rank 8, explicitly "least compelling independent bet") — freshness remains scarce, but provenance/payment bundling and participation are hard and "prevent model collapse" is not a business premise.
- **Kill test / first proof:** One consenting/synthetic owner via a Worker, two clients, tests for stale versions, replayed receipts, forbidden redistribution and correctly signed false data; require zero entitlement bypass, vs plain signed JSON + billing; stop if owners/clients won't preserve provenance or signed JSON suffices.

#### Rejected in this report
- **Pay-per-crawl / charging crawlers for access** — Cloudflare Pay Per Crawl already exists (launched 2025-07-01, still closed beta).
- **AI congestion pricing at the edge** — already too close to Cloudflare's 2026-06-16 dynamic crawl pricing (URI exceptions, Worker-controlled prices).
- **Freshness hints for crawlers** — collides with Cloudflare's stated freshness-signal/discovery roadmap.
- **Agent identity by signing traffic alone** — Signed Agents / Web Bot Auth exist and identify operators, not a user's full mandate; folded into D.
- **Approval-summary chatbot / human-attention queue as a top-level product** — worsening not guaranteed (100× actions with 1,000× lower escalation gives 0.1× decisions) and vulnerable to better models; belongs inside D's mandates (Horvitz 1999 mixed-initiative).
- **General decentralised multi-agent marketplace for coordination** — adds identity, pricing, clearing and strategy before proving useful work; start with cooperative scheduling and reserved quotas inside A/D.
- **Universal AI-content detector / "prevent model collapse" product** — model collapse is not an inevitable result of better models and signatures cannot prove truth.
- **New portable heap/snapshot format as the moat** — Vercel, LangChain, XS, Golem and VM alternatives exist; reuse an engine and compare source+JSON+journal baselines.

### 05-systems: Systems, hardware, and the physics of compute
Lens: systems, hardware and the physical limits of compute (memory wall, roofline, Horowitz energy table, Amdahl, light-speed RTT, tail amplification, GPU/Workers/R2 prices). Headline: better models do not repeal memory bandwidth, network distance, HBM capacity, queueing or power, but "model-proof does not mean demand-proof" (a 100× better model may make fewer calls), so the durable wedge is work needing fresh external data, memory, movement, deadlines or power; GPU wait/KV scheduling is already occupied by strong 2026 prior art. ONE bet: visiting compute (#1) powered by the tool-traffic compiler (#5) for a concrete two-owner data workflow, "your agent runs its next bounded data program where the data already lives". Verdict: go-with-changes, gated at day 14 on ≥100× fewer cross-boundary bytes and ≥2× completion time/paid work versus the strongest pushdown/Placement baseline; if SQL plus a normal queue wins, ship that or stop.

#### Visiting compute: bring the agent's next operation to the data
- **What:** Data owners accept bounded TypeScript/Wasm continuations and return small answers instead of exporting bulk datasets to remote agents. 100× version: executable queries become the standard inter-company agent interface, removing 100–1000× cross-boundary bytes on selective workloads.
- **How it would work:** A continuation (plus its next needed data and capabilities) is moved to an owner-controlled endpoint, runs ordinary transformations against local data through owner-controlled tools (jitk/capsule limits its I/O), and sends back a small result; it can visit several owner domains while retaining unfinished algorithm state. Migration pays only when checkpoint + transfer + handoff + restore < the critical-path transfer/RTT/rebuild it removes.
- **Evidence / numbers:** E: 10,000 → 1M daily jobs reading 1 GiB centrally = ~10 TiB → 1 PiB/day; a 0.5 MiB continuation + 0.5 MiB result moves 1024× fewer WAN bytes than a 1 GiB export (removes up to 8.59 s at 1 Gbit/s). E: break-even example, 10 ms handoff + 1 MiB at 1 Gbit/s ≈ 18.4 ms, plausible against several avoided 20 ms crossings, unattractive against one 1 ms regional call. F: Biscuit's >15× TPC-H speedup came from hardware filtering; software in-storage scans did not reproduce earlier gains on faster SSDs. F: IEA 2026, data-centre demand +17% in 2025, 485 → 950 TWh by 2030. I: R2's zero egress means saved bytes are not automatically saved dollars. Sources: [Active Disks, VLDB 1998](https://pdl.cmu.edu/ftp/Active/VLDB98.pdf), [Biscuit, ISCA 2016](https://class.ece.iastate.edu/tyagi/cpre581/papers/ISCA16Biscuit.pdf), [Cloudflare Placement](https://developers.cloudflare.com/workers/configuration/placement/).
- **Prior art / who has it:** Active Disks (Riedel et al.), Biscuit (Gu et al.), SQL/query pushdown; Cloudflare Placement already places Workers near upstreams with region/host hints ("near the database" alone is occupied); capsule landscape (Vercel quickjs-wasi/Workflow, LangChain quickjs-rs, XS Sandbox, Golem).
- **Verdict:** KEPT (#1) — best physical wedge ("fresh private bytes must be processed somewhere"); must beat pushdown and Placement, otherwise the useful result may just be a good executable-query SDK. The ONE bet, with #5 as its engine.
- **Kill test / first proof:** Kill the capsule pitch if query pushdown or source + small JSON state gets within 10% of its latency/cost; kill mobility when retained state approaches data avoided, scan CPU dominates, or owners won't host foreign code. First proof: two owner datasets, a stateful multi-stage analysis on a streamed 1 GiB fixture, compared across central download, SQL pushdown + stateless service, Cloudflare Placement, and moving the continuation.

#### Accelerator valet: suspend the agent, lease its KV, admit ready work
- **What:** Expose tool waits and expected resumptions to inference serving so GPU compute slots are reused at once and KV state is retained, offloaded or recomputed under an explicit cost policy. 100× version: 100× more tool-waiting sessions per scarce hot allocation on a 1%-duty-cycle workload (a concurrency ambition, not 100× FLOPs).
- **How it would work:** The agent's single tool channel gives a precise WAIT/READY boundary; a framework-neutral lifecycle adapter passes context identity, cache handle, wait class, deadline and budget to the serving engine; ready continuations join model/prefix-compatible queues; agent continuation and KV are tiered separately.
- **Evidence / numbers:** E: illustrative GQA model at 128 KiB/token = 1 GiB KV at 8K tokens, 4 GiB at 32K; 10,000 waiting sessions ≈ 10 TiB of 8K KV. E: 0.1 s inference + 10 s tool wait = 0.99% useful occupancy. E: copying 1 GiB KV out and back at an assumed 32 GiB/s/direction ≥ 62.5 ms, so short waits lose. E: forming a fresh batch of 32 at 1,000 arrivals/s takes ~31 ms. F: H100 SXM 80 GB HBM, 3.35 TB/s; Lambda $4.29/GPU-hour (E: 10 s = $0.0119, but not saved if the GPU was already shared). Sources: [Continuum v7](https://arxiv.org/abs/2511.02230v7), [TokenCake v5](https://arxiv.org/abs/2510.18586v5), [NVIDIA Dynamo KV offloading](https://docs.dynamo.nvidia.com/dynamo/v1.4.1/kubernetes/kv-cache-offloading/overview).
- **Prior art / who has it:** Orca (iteration-level scheduling), vLLM/PagedAttention, Continuum (tool-aware KV TTL, Sept 2026), TokenCake (proactive idle-agent KV offload), EfficientAgent, NVIDIA Dynamo (CPU/disk offload, agent-lifecycle cache management), Workers AI session affinity/prompt caching.
- **Verdict:** KEPT (#3) — largest adjacent budget, but an occupied field; only a partner/integration play with direct provider access or a self-hosted buyer. "Do not build a GPU scheduler behind an API that conceals the GPU."
- **Kill test / first proof:** Kill the adapter business if an ordinary async service with existing engine policies gets within 10% of goodput and cost. First proof: instrument WAIT/READY in TS agents with a self-hosted vLLM/Dynamo adapter (or trace-driven simulator with no GPU claim); compare continuous batching/prefix caching, fixed retention, TTL and offload/recompute across tool durations 1 ms–30 s.

#### Inference-adjacent tool appliances: make local tool loops actually local
- **What:** A small isolated tool execution plane beside inference, with scriptc-native fast paths and capsule parking when work leaves the machine. 100× version: cut the local orchestration/transport part of a tool cycle from milliseconds to tens of microseconds, while showing remote calls as remote.
- **How it would work:** Inference racks expose tenant-isolated CPU tool slots (local read-only indexes, parsers, domain runtimes) reached over one tool channel instead of the full POSIX/network surface; the host keeps GPU drivers and sockets; a session uses the slot for milliseconds, parks its capsule, and reacquires a slot when external results return.
- **Evidence / numbers:** E: 100 serial crossings × 20 ms = 2 s; at a proposed 50 µs same-host path = 5 ms, a 400× cut in that transport term only. F: Unikraft ~1 MB images, <10 MB RAM, ~1 ms guest boot, 3–40 ms total boots; Shenango reallocates cores every 5 µs. M-prior: jitk parked one-tool p50 1.133 ms, p99 127 ms (not evidence of a sub-ms production tail). Sources: [Unikraft EuroSys 2021 artifact](https://github.com/unikraft/eurosys21-artifacts), [Attack of the Killer Microseconds](https://research.google/pubs/attack-of-the-killer-microseconds/), [Workers AI embedded function calling](https://developers.cloudflare.com/workers-ai/features/function-calling/embedded/).
- **Prior art / who has it:** Exokernels (Engler et al.), MirageOS, Unikraft, Shenango; Cloudflare's embedded function calling in the same execution environment.
- **Verdict:** RUNNER-UP (#5) — credible host partnership, but no edge API lets a small builder promise universal same-host tools; a model that collapses 100 calls into one erases much of the gain.
- **Kill test / first proof:** Stop if optimized warm processes match useful latency/density or if model/tool time dominates (count idle CPU burned by busy polling). First proof: a TS harness comparing warm Node, workerd/Wasm, scriptc-native and jitk on real local tools (indexed lookup, parsing, stateful chain) at 64 B–1 MiB payloads, measuring queue/tool/entry-exit time and p99 under open-loop arrivals.

#### A tail budget for agent chains: hedge, prefetch, and cancel at continuations
- **What:** A tool broker spends a bounded redundancy budget on the critical path: delayed hedges for equivalent reads, speculative prefetch for predictable future reads. 100× version: a 100× reduction in avoidable outlier exposure on workloads with independent replica stalls (not a universal 100× latency guarantee).
- **How it would work:** A forkable continuation plus one broker that knows branch identity, remaining deadline, cancellation and effect class; endpoints declare cancellability, consistency, cost and shared failure domain; reads are admitted under a global budget, writes need a single authoritative owner or idempotency. Prefetch continues only if `pL` is worth `C`.
- **Evidence / numbers:** F: Tail at Scale, Bigtable p99.9 1,800 ms → 74 ms with a 10 ms hedge delay and 2% extra requests. E: independent 1% tail, 100 calls → 63.4% chance of a slow call, 1,000 calls → 99.996%. E: prefetch at p = 0.8 on a 200 ms read = 160 ms ideal expected benefit. I: the delayed-hedge tail is `P(X>t)P(Y>t−h)`, not `P(X>t)^2`; shared congestion breaks the multiplication. Sources: [Dean & Barroso, The Tail at Scale, 2013](https://barroso.org/publications/TheTailAtScale.pdf).
- **Prior art / who has it:** Delayed hedging, tied requests, CPU speculation, storage prefetch; commodity HTTP proxies.
- **Verdict:** RUNNER-UP (#4) — strong measurable feature; watch correlated overload and commodity proxies. Duplicating a whole agent and picking a plausible answer is not a correctness-preserving hedge.
- **Kill test / first proof:** Kill default-on hedging if extra traffic worsens origin queues or can't be cancelled/billed; kill capsule investment if a standard HTTP proxy captures the benefit. First proof: TS broker + forkable Wasm guest + controlled replicas at 50/80/95% utilization, independent vs shared stalls; target ≥3× p99 improvement at ≤5% extra upstream work, zero speculative writes, replay/JSON baseline included.

#### A compiler for tool traffic: fuse the bytes before they become model context
- **What:** Compile generated TS tool pipelines into streamed, fused native/Wasm operators that keep intermediates local and send only decision-relevant outputs through the tool channel. 100× version: a "read, filter, join, summarize" program uses 100× fewer materialized/interchange bytes, with a per-job traffic budget enforced by the runtime.
- **How it would work:** scriptc lowers hot, well-understood TS operations; typed byte/record handles replace re-serializing the same values between tools; the tool-only ABI makes output boundaries inspectable; a capsule can keep incremental indexes and join state across waits. It can ship inside visiting compute (#1).
- **Evidence / numbers:** E: 20 boundaries × 100 MB intermediate = 4 GB materialization traffic; 10M such jobs/day = 40 PB/day; 4 GB on a 50 GB/s path = 80 ms before parsing/GC. E: cutting an uncached 100K-token input to 1K saves $0.004455/job at Workers AI's $0.045/M input tokens (llama-3.1-8b fp8-fast) = $4,455 per million jobs. I: copying FlashAttention's principle doesn't copy its speedup. Sources: [FlashAttention, 2022](https://arxiv.org/abs/2205.14135), [Kung, Why Systolic Architectures, 1982](https://www.eecs.harvard.edu/~htk/publication/1982-kung-why-systolic-architecture.pdf), [Workers AI pricing](https://developers.cloudflare.com/workers-ai/platform/pricing/).
- **Prior art / who has it:** Dennis/Misunas dataflow machines, Kung's systolic arrays, FlashAttention; classic fusion, databases, vector engines and generated tool-composition code already remove much of this work. Report notes scriptc does not yet do this fusion.
- **Verdict:** KEPT (#2) — best builder-controlled implementation, compatible with perfect generated code, likely the engine of #1; threat is that databases, streamed JS or native libraries already do the valuable work.
- **Kill test / first proof:** Stop if ordinary streaming/query pushdown gets within 10% with less complexity. First proof: three TS pipelines (log selection, incremental reconciliation, join/aggregation) through scriptc and Wasm versus JSON tool chaining, hand-streamed JS and optimized SQL; target ≥100× interchange-byte cut plus a separate cost/latency win over the strongest baseline; force a mid-pipeline wait to test preserved state.

#### A single-address-space internet of capsules, explicitly non-coherent
- **What:** Give parked program state and immutable data blocks stable global identities, with local access inside a host and explicit async fetch across hosts. 100× version: one addressable namespace with 100× less replicated state/restore traffic for read-mostly fork populations; a billion mostly dormant agents stored as shared bases plus deltas.
- **How it would work:** Versioned handles name engine, base blocks, delta, pending operations and ownership epoch; immutable blocks are shared, mutable state belongs to a branch; a missing block at the single tool channel triggers explicit park/fetch/resume rather than a hidden blocking pointer load. No cross-tenant dedup assumed.
- **Evidence / numbers:** E: 1M × 1 MiB states = 1.05 TB ≈ $15.73/month on R2; 1B = 1.05 PB ≈ $15,729/month; 1B park+load pairs ≈ $4,860 in R2 operations even after a 100× byte cut. E: 100 uncached remote faults at 20 ms RTT = 2 s. F: FaRM 160M lookups/s across 20 machines at 31 µs. Sources: [Opal](https://homes.cs.washington.edu/~levy/opal/), [FaRM, NSDI 2014](https://www.microsoft.com/en-us/research/publication/farm-fast-remote-memory/), [Infiniswap, NSDI 2017](https://www.usenix.org/conference/nsdi17/technical-sessions/presentation/gu).
- **Prior art / who has it:** Opal, Singularity, FaRM, Infiniswap; capsule landscape already shows delta implementations (format export alone is occupied).
- **Verdict:** NARROWED / ranked #8 — useful substrate, but the coherent global RAM / transparent Internet dereference pitch fails and the product buyer is the weakest; keep the namespace, drop the coherence. Compact source+state from better models directly threatens it.
- **Kill test / first proof:** Kill the 100× claim when dirty entropy/base size prevents that ratio or hashing/tiny-object ops cost more than full snapshots. First proof: TS manifest service + R2-compatible store + two Wasm hosts; fork one populated state into 1,000 branches, vary dirty fraction, compare full compressed images, delta checkpoints, JSON and replay; test old-owner resumes and engine-version mismatch.

#### Power-following continuations: defer flexible agents, not their users
- **What:** Park deadline-flexible agent work and admit its next compute burst when power, capacity and data locality make execution cheapest. 100× version: a large agent population becomes a controllable load that can shed 99% of its flexible instantaneous demand in a grid/capacity event (time shifting, not 100× less energy).
- **How it would work:** A provider pools millions of background tasks with minute-to-day deadlines, keeps model weights warm at a few sites, moves only small continuations when worthwhile, and packs runnable bursts into already powered capacity.
- **Evidence / numbers:** E: 1,000 accelerators × 700 W = 700 kWh/hour; shifting that hour from $0.20 to $0.05/kWh saves $105 of device electricity, versus $4,290 of GPU rent for the same 1,000 GPU-hours, so renters who run longer lose. F: Zeus 15.3–75.8% training energy-efficiency gain (not an inference promise). E: 16 GB of weights over 100 Gbit/s ≥ 1.28 s. Sources: [Google carbon-intelligent compute, 2021/2023](https://arxiv.org/abs/2106.11750), [Zeus, NSDI 2023](https://www.usenix.org/conference/nsdi23/presentation/you), [IEA 2026](https://www.iea.org/reports/key-questions-on-energy-and-ai/executive-summary).
- **Prior art / who has it:** Google Carbon-Intelligent Compute Management, Zeus; ordinary queues/checkpoints often suffice.
- **Verdict:** RUNNER-UP (#7) — valuable only for owners of power-constrained capacity; queueing often beats migration; Workers/Workers AI give no control over facility power or GPU clocks.
- **Kill test / first proof:** Kill migration when transfer/recompute exceeds benefit; kill power capping when runtime grows enough to raise joules or rented GPU-hours. First proof: TS scheduler + resumable Wasm jobs on supplied price/carbon traces (simulation); target ≥20% modeled energy-cost cut at ≥99% deadline completion.

#### A precision and placement ladder: device → edge → central, by work class
- **What:** Keep task state portable while choosing the smallest suitable resident model and site under explicit quality, memory, power and latency budgets. 100× version: cut central GPU/API demand 99% for qualified narrow workload classes via local exact code, compact models and batching.
- **How it would work:** SaaS apps/browsers keep the unfinished task local, run deterministic transforms and narrow inference nearby, and escalate only hard subtasks centrally; weights stay resident, continuations and allowed summaries move; task classes have explicit acceptance targets and prequalified variants (no weak model judging a stronger one).
- **Evidence / numbers:** F/E: 2,000 in / 200 out tokens on Workers AI = $0.0001668/job (8B) vs $0.0010366 (70B), $166,800 vs $1,036,600 per billion jobs, only ~6.2×. F: EnerJ corrected energy savings to 7–38%. E: 3B params at 4 bits ≈ 1.5 GB; at 50 GB/s a per-token scan takes 30 ms vs H100's 4.78 ms floor for a 16 GB model, so a nearby small model can be slower. F: Apple ~3B on-device model with 2-bit QAT (2025). Sources: [EnerJ + correction](https://sampa.cs.washington.edu/research/approximation/enerj.html), [AWQ](https://arxiv.org/abs/2306.00978), [Apple Foundation Models 2025](https://machinelearning.apple.com/research/apple-foundation-models-tech-report-2025).
- **Prior art / who has it:** Approximate computing (EnerJ), AWQ quantization, Apple on-device models; routing and device integration are crowded.
- **Verdict:** RUNNER-UP (#6) — better compact models help, but routing/device integration is crowded and quantization alone is a few-fold, not 100×.
- **Kill test / first proof:** Stop if cold loads, throttling, retries or quality loss dominate, or a single static policy performs as well. First proof: 1,000 held-out extraction/classification tasks with a fixed quality target, comparing exact rules, one strong model, one compact model and a fixed routing policy; target ≥90% fewer central calls at equal quality.

#### Rejected in this report
- **A tiny kernel or forkable file as the product** — it is an enabling mechanism; Vercel quickjs-wasi, LangChain quickjs-rs, XS, Golem and VM providers already cover pause/fork/recovery.
- **A new GPU scheduler / GPU OS behind a public token API** — the API hides the GPU and eviction control; jitk need not become a GPU OS; a small OS cannot raise HBM bandwidth.
- **Coherent global mutable RAM / transparent Internet pointer dereference** — pointer identity, coherence, failures and reclamation break it; no public Workers RDMA API.
- **Microsecond global tool channels** — 2,000 km already has a 20 ms RTT floor; only same-host microseconds are plausible.
- **Free speculation / duplicate-the-whole-agent hedging** — redundancy costs upstream capacity and duplicating an agent is not a correctness-preserving hedge.
- **Invoicing energy savings from the Horowitz pJ table or TDP × time** — not a joules-per-byte/token figure; power claims need measured system boundaries.

### 06-theory: Theory of computation: what remains scarce when intelligence is abundant
Lens: theory of computation, with a theorem ledger (P vs NP, IP = PSPACE, GKR, PCP, SNARKs/STARKs, PCC, Rice, Wolfram irreducibility, Kolmogorov, Landauer/Bennett, Yao/Razborov, FLP/CAP, Myerson–Satterthwaite, Armstrong–Mindermann, Goodhart) stating exactly what each does and does not imply. Headline: the round-1 thesis "generation becomes free so verification becomes scarce" is too broad, since perfect models remove self-checking; what lasts is making computation acceptable across boundaries of information, authority, incentives and time (remote facts, shared intent, conserved authority, evidence another party accepts). 2026 proofs can cost cents (Ethproofs), but prover overhead, setup, fixed latency, input truth and specification stay separate costs. ONE bet: a buyer-selected replay receipt for deterministic invoice reconciliation, then proof-carrying write authority. Verdict: go-with-changes. Start with cheap replay against a signed-JSON+source baseline, not a zkVM, and kill the standalone business if real buyers accept ordinary signed output just as readily.

#### Counterparty receipts: computation that a stranger can accept
- **What:** Return an output with everything a buyer needs to independently check its agreed relation. 100× version: a network carrying a billion accepted work receipts/day between companies and agents, with receiver-selected replay or succinct proof verification.
- **How it would work:** Deterministic TS runs in the QuickJS/Wasm tool-only ABI; the receipt binds program/module and engine digests, accepted genesis/input commitments, ordered host-call journal, output root, policy/checker version, evidence mode and nonce. Receivers replay it in Node/browser/Wasm or check an optional zk proof. Workers route/version receipts, R2 serves artifacts, heavy proving goes to external CPU/GPU services.
- **Evidence / numbers:** E: 1M deliveries/day × 10 recipients × 100 ms of redundant checking = 1M CPU-seconds/day. I: break-even, proof wins on compute only if `k > (P − C)/(C − V)`; a 250× prover needs roughly hundreds of replayers. F: Ethproofs rows at $0.0031–$0.0063 per block proof (ZisK, OpenVM, zkDTVM); SP1 Groth16 ~260 bytes, ~6 s Groth16 / 70 s PLONK wrapping overhead. F/E: 1B × 2 KiB receipts ≈ $31/month storage, but $4,500 writes + $360 reads on R2. Sources: [GGP 2010](https://www.iacr.org/archive/crypto2010/62230459/62230459.pdf), [Ethproofs](https://ethproofs.org/), [SP1 network FAQ](https://docs.succinct.xyz/docs/sp1/prover-network/faq).
- **Prior art / who has it:** GGP, GKR, Pinocchio, Groth16, STARKs; SP1/Succinct, RISC Zero, Boundless; durable replay/reproducible computation; round 1's notarised computation (this adds a receiver-selected evidence contract and explicit economics).
- **Verdict:** KEPT (#1) — the ONE bet, because the receiver's need does not depend on the producer's intelligence. Key risk: a buyer may not need more than a normal signature and journal; don't build the network before that's answered.
- **Kill test / first proof:** Kill the standalone product if three target buyers accept ordinary signed outputs just as readily, total checking exceeds recomputation without compensating value, or the capsule adds nothing over a signed journal. First proof (10 days): reconcile one committed invoice/ledger batch, replay independently in Node and browser, reject altered input/output, omitted call, wrong program, arbitrary seller checkpoint and reused nonce; price an optional zkVM proof on one small reducer only.

#### Proof-carrying actions: a small gate for an enormous agent
- **What:** Each effectful tool call carries a checkable authorization derivation. 100× version: a cross-vendor mandate protocol letting millions of agents delegate, subdivide and spend precisely bounded authority without human approval of every step.
- **How it would work:** Portable mandates name principal, target, action, aggregate budget, expiry and revocation/ownership epoch; a small total checker in a restricted policy DSL validates grant ancestry, amount, expected state version and unique op ID; a per-account DO or destination authority conserves reservations. Unreachable authority means effects wait; forked capsules cannot clone spending authority.
- **Evidence / numbers:** E: 10,000 agents × 100 writes/day at 1 s manual review = 278 person-hours/day. F: anchor B, Anthropic 2026-02-18, long-session tail of autonomous Claude Code work rose from <25 to >45 minutes in three months (not a measure of unauthorized actions). F/I: FLP/CAP mean a cloned capsule must not clone exclusive authority. Sources: [Necula–Lee PCC, OSDI 1996](https://static.usenix.org/publications/library/proceedings/osdi96/full_papers/necula/html/node2.html), [Macaroons, NDSS 2014](https://research.google/pubs/macaroons-cookies-with-contextual-caveats-for-decentralized-authorization-in-the-cloud/), [Anthropic agent autonomy](https://www.anthropic.com/research/measuring-agent-autonomy).
- **Prior art / who has it:** Proof-carrying code (Necula–Lee), macaroons; adjacent to IAM, OAuth and policy-as-code, which it must beat on cross-agent delegation.
- **Verdict:** KEPT (#2) — exclusive authority and current state remain real constraints as intelligence improves; small checker, clear fork/retry demo; main competitor is good destination-side authorization. Must be narrower than "we verified intent".
- **Kill test / first proof:** Kill if destination OAuth scope + conditional write + budget table does the same with less work, policy authors can't explain rejections, or any fork/retry spends outside the global bound. First proof: TS policy DSL + checker; fork a capsule 100 ways with a bounded write grant, exhaust the shared budget, transfer ownership, reject stale copies, crash between dispatch and ack and reconcile against an idempotent toy destination. No zkVM.

#### A common computation store: cache the progress, not the prose
- **What:** Address deterministic subcomputations and parked states by their exact dependencies, keeping common bases and changes. 100× version: huge agent fleets pay once for shared parsing, initialization, reference data and repeated analysis, then pay only for their differences.
- **How it would work:** Tenant-scoped R2 stores share approved engine/code/data chunks; a Worker resolves dependency graphs and materializes state deltas near demand; keys cover code, runtime/ABI, input roots, seed and freshness context; a model release creates new program identities and invalidates results; side effects are replayed, never cached as permission.
- **Evidence / numbers:** E: 1M branches × 10 MiB = ~9.54 TiB; 9 MiB shared base + 1 MiB/branch ≈ 0.954 TiB, roughly 10×, not 100×. F: Kolmogorov counting argument limits generic compression; exact K is uncomputable. Sources: [rsync report, 1996](https://download.samba.org/pub/unpacked/rsyncweb/tech_report/tech_report.html), [Adaptive functional programming, POPL 2002](https://www.cs.cmu.edu/~blelloch/papers/popl02.pdf), [Adapton](https://matthewhammer.org/adapton/).
- **Prior art / who has it:** rsync, adaptive functional programming, Adapton; existing capsule competitors already implement deltas; build/data caches and ordinary memoization.
- **Verdict:** KEPT (#3) — the cleanest bet on growing compute/data pressure rather than lasting model error; established techniques, so it must beat compression, caching and checkpoints.
- **Kill test / first proof:** Kill if object compression + ordinary memoization land within 20%, the dependency graph costs more than recomputation, or correct invalidation needs undisclosed global knowledge. First proof: 100 real snapshots/workflows plus a high-entropy control; compare chunk dedup, page deltas, source+state replay and memoized pure calls; target ≥5× fewer transferred bytes and ≥2× lower p95 completion cost, <20% regression on unrelated runs.

#### Data-local proof capsules: send a question instead of a database
- **What:** Ship a bounded, policy-checked computation to a data owner's runtime and return a small authenticated result, optionally with a succinct proof. 100× version: a federated analysis fabric where agents work across thousands of owners without centralizing datasets.
- **How it would work:** Owners run a small Wasm execution gateway next to their stores; a portable query artifact names a restricted input schema and export policy; the owner runs it, enforces a fixed small output schema/budget, caches permitted outputs and returns evidence bound to a data version; Cloudflare handles control, identity and serving.
- **Evidence / numbers:** E: 10,000 queries × 100 MB exported = 1 TB vs 10 KB returned each = 100 MB, a 10,000× traffic cut if the query admits that result and data already sits at the owner. F: Yao/Razborov communication lower bounds (Ω(n) for set disjointness) mean missing data is a real constraint; code-to-data changes placement, not the bound. Sources: [Yao, STOC 1979](https://doi.org/10.1145/800135.804414), [Razborov 1992](https://doi.org/10.1016/0304-3975(92)90260-M), [Necula papers incl. mobile agents](https://people.eecs.berkeley.edu/~necula/papers.html).
- **Prior art / who has it:** PCC/mobile agents lineage; prior capsule landscape and round 1's visiting-agent idea already hold the mechanism; conventional SQL pushdown/APIs.
- **Verdict:** RUNNER-UP (#6) — mechanism already occupied; communication complexity is a design constraint, not a differentiator against SQL; needs willing hosts, and "runs on your data" is not a privacy proof.
- **Kill test / first proof:** Kill if no three owners will host it, pushdown matches the gain, or a useful answer can't fit a defensible export policy. First proof: two Node/Wasm owner gateways + a Worker coordinator run a deterministic reconciliation query on versioned tables, compared with indexed SQL and a normal API; deliberately try exfiltration via output values, timing, exceptions and oversized artifacts.

#### Specification escrow: agree on acceptance before buying the answer
- **What:** Turn an outsourced agent job into a signed acceptance relation with input commitments, examples, exclusions and a dispute path before work starts. 100× version: a marketplace of composable executable work contracts that don't require a shared model vendor or vague NL score.
- **How it would work:** Reusable contract modules: canonical input set, feasible-output predicate, max price, deadline, evidence mode, adjudicator, remedy; a preview with positive/negative examples surfaces ambiguities (e.g. rounding) before execution. Workers expose the protocol, DOs manage reservations/status, R2 holds signed versions; payments stay on existing rails (test credits in prototype).
- **Evidence / numbers:** E: 10,000 jobs/day × 1% unresolved acceptance × 20 min/dispute = 33.3 person-hours/day. No source quantifies the specification backlog. F: Myerson–Satterthwaite impossibility under stated assumptions; Armstrong–Mindermann, a policy doesn't identify its reward without normative assumptions. Sources: [Myerson–Satterthwaite 1983](https://www.cs.princeton.edu/courses/archive/spr06/cos444/reading/MS83/MS83.pdf), [Armstrong–Mindermann](https://arxiv.org/abs/1712.05812).
- **Prior art / who has it:** Mechanism design literature; computable contracts; closely related to round 1's executable work orders.
- **Verdict:** RUNNER-UP (#5) — survives perfect models (different preferences and private information remain), but computable contracts cover only part of commerce, and templates may suffice.
- **Kill test / first proof:** Kill if writing the contract consumes the job's value, reviewers routinely reject formally accepted outputs, or an ordinary schema/template resolves the same cases. First proof: one reconciliation service with a tiny contract schema, run on 30 designed ambiguous cases against a plain-language brief baseline with consenting reviewers; no real escrow or legal-enforceability claim.

#### Fresh-observation clearinghouse: buy the missing fact once
- **What:** Agents buy a fresh, nonce-bound observation from an authenticated source and reuse it within an explicit validity window. 100× version: a clearinghouse for scarce origin queries, instrument slots, inventory observations and experiments, with provenance and disclosed measurement assumptions.
- **How it would work:** Sources issue signed observations (subject, units, time basis, challenge nonce, calibration/source identity, expiry); DOs coalesce permitted requests and reserve scarce measurement slots; buyers pick trusted sources; R2 keeps raw evidence; stale observations are explicitly rejected.
- **Evidence / numbers:** E: 100,000 agents polling one fact every 10 s = 10,000 origin requests/s, collapsible to one 1 Hz stream if all buyers accept 1 s freshness. F: Cloudflare 2025, user-action crawler traffic grew over 21× January–December. F: C2PA warns provenance does not establish factual accuracy. Sources: [C2PA 2.4 explainer](https://spec.c2pa.org/specifications/specifications/2.4/explainer/Explainer.html), [Succinct ZCAM, 2026-04-23](https://blog.succinct.xyz/introducing-zcam/), [Cloudflare Radar 2025](https://blog.cloudflare.com/radar-2025-year-in-review/).
- **Prior art / who has it:** Shannon (information vs messages), C2PA signed provenance, Succinct ZCAM capture attestation; HTTP caching/ETags, subscription feeds, websockets.
- **Verdict:** RUNNER-UP (#4) — a perfect model with the same old data still can't tell two new external outcomes apart; but the scarce asset is the source relationship, not "truth tokens", and a signature authenticates the report, not reality.
- **Kill test / first proof:** Kill if feeds/caches already solve the workload, freshness/privacy needs are incompatible, sources won't sign, or source reliability can't be evaluated independently. First proof: a test inventory endpoint with three changing versions; authenticated responses, challenge/expiry, coalescing and explicit "stale"; compare with ETags and a websocket feed; no camera hardware.

#### A market for accepted computational progress, with irreducibility treated honestly
- **What:** Buy resumable expensive computation as checked progress toward a customer objective, routing execution and evidence generation to suitable capacity. 100× version: coordinate large pools of independent simulation, search and proving workers, with portable checkpoints so unfinished useful work isn't discarded.
- **How it would work:** Customers submit deterministic simulation/search subjobs with checkpoint format, input commitments, acceptance predicate, evidence mode, deadline and max cost; Cloudflare is the control plane, outside native/GPU workers execute; progress and witnesses return through the receipt protocol; owner epochs prevent duplicate settlement. Rewards go to accepted results, not cycle counts.
- **Evidence / numbers:** E: 1M useful 60 s jobs/day = 16,667 CPU-hours/day before replication/proving. F: Wolfram's irreducibility is an author thesis, not a proven universal lower bound; time hierarchy gives rigorous separations; VDF sequentiality rests on hardness assumptions. F: Succinct and Boundless (reverse Dutch auction, collateral) already run prover markets. Sources: [Wolfram NKS p.738](https://www.wolframscience.com/nks/p738--computational-irreducibility/), [VDFs, 2018](https://eprint.iacr.org/2018/601), [Boundless auction](https://docs.boundless.network/developers/tutorials/auction).
- **Prior art / who has it:** Succinct prover network, Boundless; managed batch/spot execution; GKR/modern proofs.
- **Verdict:** RUNNER-UP (#7) — ambitious, but incumbents exist and the workload premise (substantial cost left after strong-model algorithm choice and caching) is unproven; generic marketplaces are already built.
- **Kill test / first proof:** Kill if a better algorithm removes most work, managed batch/spot wins after verification, input transfer dominates, no easy acceptance relation exists, or customers need optimality proofs. First proof: a deterministic integer scheduling/packing search with easy feasibility checks; compare domain solver + model-generated algorithm against three native workers resuming checkpoints and a simple queue; target ≥2× accepted progress per dollar or ≥3× recovery improvement.

#### Metric-pressure lab: find when a score stops buying the outcome
- **What:** Continuously attack a customer's acceptance metric with increasingly strong optimizers and track divergence from independently observed outcomes. 100× version: an evaluation-maintenance service for large agent ecosystems, with reproducible counterexamples and renewed outcome data instead of a fixed leaderboard.
- **How it would work:** Acceptance modules plus versioned adversarial examples, hidden outcome cohorts and bounded optimization budgets; Workers orchestrate tests, R2 stores reproducible failure capsules and outcome evidence; ground-truth collection stays outside the optimizer being evaluated; includes an exact-spec control where the proxy has no gap.
- **Evidence / numbers:** E: 100,000 independent candidates each with 10^-4 chance of exploiting a gap → ~99.995% chance at least one succeeds (independence is an artificial assumption). F: Gao–Schulman–Hilton measured reward-model overoptimization in a synthetic setup; Manheim–Garrabrant separate regressional, extremal, causal and adversarial Goodhart. Sources: [Manheim–Garrabrant](https://arxiv.org/abs/1803.04585), [Gao et al., ICML 2023](https://proceedings.mlr.press/v202/gao23h/gao23h.pdf).
- **Prior art / who has it:** Goodhart/Campbell lineage, reward-overoptimization research; round 1's Oracle Foundry and failure-search gate are direct predecessors; property-based testing.
- **Verdict:** RUNNER-UP (#8, last) — useful but most exposed to better judges; depends most on a lasting model/judge gap; a static exploit corpus is a feature a stronger model can absorb.
- **Kill test / first proof:** Kill if there's no affordable independent outcome signal, attack search only finds known toy tricks, a maintained judge catches every relevant case more cheaply, or repair keeps overfitting the same failures. First proof: CSV reconciliation scored by shallow schema/total checks; search against the proxy at increasing budgets, hold out a final outcome cohort, compare with property-based testing and a strong model checking outputs directly.

#### Rejected in this report
- **Blanket "generation is free, so verification is scarce" thesis** — too broad; a product whose only job is catching today's model mistakes can disappear.
- **Proving every JavaScript instruction / all of QuickJS or the native kernel in a zkVM first** — explicitly "do not start" there; Wasm is not a zkVM and SP1 proves RISC-V; prove one small reducer.
- **An undifferentiated "marketplace for verifiable compute"** — Succinct and Boundless already run one; not missing infrastructure.
- **"Sample a few steps" of a raw trace sold as PCP security** — 64 of 1M steps catches a single bad transition with 0.0064% probability; PCP depends on the encoding.
- **Reversible-chip moonshot / claiming Landauer savings from snapshots** — not justified for a TS team; snapshotting isn't reversible hardware.
- **Selling "truth tokens" or verified intent** — signatures authenticate reports, not reality; transcripts can't reveal hidden goals.
- **Cycle-count / VDF busywork rewards or "irreducible" as a commercial warranty** — they invite bloated traces and subsidy farming; there's no proven lower bound for useful simulations.
- **A second-model "safety score", or replacing a protocol checker with a persuasive model** — this throws away the interactive-proof guarantee; charge for accepted operations instead.
