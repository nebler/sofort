# Computing archaeology: the computer as a living, forkable artifact

Research date: **2026-10-27**. Lens: great old ideas that were right too early. Scope: the [moonshots brief](BRIEF.md), including every named historical lineage. This report proposes **nine** bets; it does not propose another snapshot library, durable workflow engine, or sandbox.

**Labels:** **F** = sourced fact; **M** = measured result, explicitly attributed to earlier project research; **I** = inference, design proposal, or judgment; **E** = estimate or proposed experimental threshold. There are **no new runtime measurements** here. All web sources were searched or inspected on **2026-10-27**; publication dates and retrieval limitations appear in the source notes. All 100× outcomes are **I/E ambition**, not demonstrated speedups or forecasts. All tweets are drafts for use **only after the described proof works**, with actual measurements replacing targets.

## The thesis

**I — The interesting resurrection is a computer you can own, cite, visit, change, and disagree with.** Smalltalk made the running environment the thing you worked on. Persistent systems tried to abolish the save/load translation. Mobile-object systems tried to make location a choice. Engelbart and Nelson tried to make knowledge navigable through its structure and origins. A portable capsule could join these ideas: a piece of ongoing work becomes an addressable artifact, with forks as alternative futures and explicit authority deciding which future can act.

**I — Strong models change the labor economics, rather than repeal distributed systems.** They could maintain millions of individual live programs, translate their evolving state, construct counterexamples, and negotiate protocols. Edge distribution and browser Wasm give those programs places to execute without installing a special workstation. Small images make retaining unfinished work plausible. None of this automatically resolves code evolution, secret leakage, malicious hosts, global agreement, or external side effects.

**I — My bet is #2: software that can be rebuilt while people are using it.** The product is an upgrade submitted as an inspectable set of running futures: original state, proposed migration, counterexamples, and a controlled promotion. That is substantially more useful than “Git for heaps.” #1, executable citations, is the best complementary public demo. #3, visiting agents, has the largest institutional ambition and the hardest deployment boundary.

## What the capsule really buys, and what it does not

**F — Read before generating these bets:** [landscape](../v8/02-landscape.md), [roadblocks](../v8/03-roadblocks.md), [signal](../v8/06-signal.md), [demo §0/§9/§10](../../../demo.md), [Wasm portability](../portability/02-wasm.md), and [GrowOS](../../jitk/grow/README.md). The landscape already identifies Vercel `quickjs-wasi`, LangChain `quickjs-rs`, XS Sandbox, Golem, TimeTravelJS, and `pi-world`. In particular, an agent modifying a persistent heap is already explored by `pi-world`. None of the proposals below claims that mechanism or product direction as an invention.

**M — Prior project measurements, not reproduced:** the minimal portability example produced a **99,854-byte gzip** checkpoint and resumed in Node, Chromium, local workerd, and a local Dynamic Worker. More representative library/data examples reached approximately **1.5–6.4 MB compressed**. Warm glue workloads used about **5–11×** direct V8 CPU; a numeric loop was worse. Freed buffers could remain in the raw image, and Wasm memory did not shrink. The allocator cap was not reliable. These observations come from the [portability](../portability/02-wasm.md) and [roadblocks](../v8/03-roadblocks.md) reports, not production Cloudflare measurements.

**I — Common design contract for all nine ideas:**

1. **An image is a dependency-bearing artifact.** Keep the exact interpreter/module hash, bootstrap/ABI identity, memory/globals, pending-call identities, journal position, branch parent, and policy references. A 3 MB state file is not its separately distributed engine, blob collection, model weights, or tool infrastructure.
2. **Pause at a supported boundary.** Return all Wasm frames to the host after a guest `await tool()`. Do not promise arbitrary instruction-level preemption or native jitk RAM restoration into a browser. Busy execution needs enforced budgets and a kill path; the current spike needs hardening before public hostile tenancy.
3. **Fork state; explicitly allocate effects.** A branch starts with recorded/read-only tools. A trusted broker owns credentials, operation IDs, budgets, and writer epochs. A pending real effect has one owner; changing branch IDs must not mint another permission to spend. Unknown outcomes require reconciliation or remote idempotency, rather than blind retry.
4. **Publish state before advertising it.** Write an immutable R2 image, then transactionally advance a DO's manifest/journal pointer and ownership epoch. A crash can leave an orphan image to collect. There is no assumed atomic transaction spanning R2, the DO, and an arbitrary external API.
5. **Keep giant data and bulk compute outside the heap.** Use immutable blobs and narrow tools. Schedule forks in bounded batches through Queues; hundreds of logical branches do not require hundreds of simultaneously resident memories. Workflows can organize the experiment, rather than become a rival platform to rebuild.
6. **Treat the destination honestly.** Browser execution is useful for inspection and local data, but the browser owner can alter the capsule. A signed checkpoint proves provenance, not faithful execution by an untrusted host. Wasm is software isolation, not confidentiality from that host.

**F — “Any Cloudflare city” is an architectural reach goal, not a city-pinning API guarantee.** Workers normally execute near request ingress, with placement controls for upstream locality. DO location hints are best effort; existing DOs do not currently relocate. R2 buckets have location/jurisdiction choices; storing an image there does not place a hot replica in every city. [Workers placement][placement], [DO location][do-location], [R2 location][r2-location]. **I:** move the capsule between eligible executors; leave the authoritative broker explicit. Record observed execution locations in a real hosted demo.

**E — A useful scale correction:** at an assumed 3 MB each, one million independent full checkpoints contain **3 TB**; 100 million contain **300 TB**, before history and replicas. One hundred active 3 MB images already contain **300 MB** before engine/host overhead. “100×” must come from work people can accomplish, not an assertion that copies, checkpoints, or model calls are free.

## The excavation: what each old idea becomes

These are constraints relevant to revival, not complete causal histories. Several systems succeeded and their ideas remain in use; “right too early” must not erase that.

[Language Reference, October 1995][telescript], [White, March 1996][white]. **I:** a network of willing hosts and meaningful services is a harder product than mobility alone. | **I:** a buyer's unfinished task visits sellers' or data owners' execution places with a budget and narrow tools. **100×:** cross-organization services negotiate and compute without a bespoke central integration for every pair. **→ #3, #5.** |

[Douglis/Ousterhout, 1991][sprite], [author retrospective][sprite-retro]. | **I:** intentionally discard POSIX transparency and make every dependency a named tool. **100×:** unfinished agent search can be evicted, resumed, and placed across a heterogeneous pool without migrating a Unix kernel. **→ #8.** |
| **MOSIX** | **F:** its Linux design split migrated execution from a home-node deputy handling location-dependent work. [Barak, La'adan, Shiloh, 1999][mosix]. **I:** moving CPU while retaining a home dependency does not make the program independent of that home. | **I:** make the deputy an explicit, replaceable authority service; expose its availability and cost. **100×:** move continuation work among sites without pretending its tool dependencies moved too. **→ #8, #3.** |
| **Condor / HTCondor checkpointing** | **F:** historical standard-universe checkpointing required suitable linked programs; other jobs needed their own checkpoint strategy. [HTCondor historical guide][condor]. **I:** saving a runtime with a tiny tool ABI avoids many compatibility obligations but deliberately supports fewer programs. | **I:** pool paused, explicitly compatible Wasm continuations rather than arbitrary jobs. **100×:** a market in verified search progress, with revocable leases and replayable results. Generic CPU sharing is the weak version. **→ #8.** |
| **Erlang / OTP supervision, hot loading, “let it crash”** | **F:** supervisors restart children; Erlang supports current/old module code, with rules for switching and purging. | **Plan 9: files, private namespaces, 9P** | **F:** resources use hierarchical file-like interfaces, 9P, and per-process namespace composition. [Pike et al., 1995][plan9]. **I:** representation does not erase the distinction between reading data and issuing an irreversible command. | **I:** each capsule carries a declarative namespace such as `/customer`, `/calendar`, `/proposal`, rebound to authorized host tools. **100×:** generated agents program against a stable personal world despite changing service providers. 9P can be an adapter; it is not mandatory overhead for every tool. **→ #3, #6.** |
| **Tandem NonStop process pairs** | **F:** Gray describes process pairs and transactions as complementary fault-tolerance mechanisms. [Gray, June/revised November 1985][tandem]. **I:** redundant copies do not repair a deterministic defect shared by both. | **I:** retain a conservative active continuation and an independently checked recovery candidate, with only one authorized writer. **100×:** controlled semantic repair in addition to failover; no availability claim follows from making two copies. **→ #4.** |
| **Xanadu** | **F:** versioned documents refer to persistent content identities, with visible origins and transclusion. [Nelson's model, 1999/revised 2001][xanadu]. **I:** requiring an entire new publishing model creates coordination costs; the source does not establish one simple explanation for its adoption history. | **I:** transclude a computation and its evidence dependencies, not only a passage. **100×:** an argument can be challenged by forking the exact computational state that produced it. Start with ordinary links and explicit source versions. **→ #1.** |
| **Engelbart's NLS** | **F:** the 1968 demonstration joined structured editing, links, views, and collaboration; the 1962 framework treats tools, methods, and people as one augmentation system. [1968 demo][nls], [1962 report][engelbart]. **I:** expert interaction methods and dedicated infrastructure implied substantial adoption/training work. | **I:** people and agents navigate a shared graph of claims, programs, evidence, and alternative futures. **100×:** a small group can investigate problems previously requiring an institution, while keeping disagreements inspectable. **→ #1, #7.** |
| **HyperCard** | **F:** stacks, cards, fields, buttons, and scripts formed an end-user programming environment. [Dan Allen, Apple HyperCard team, 1988][hypercard]. **I:** distributing a stack did not automatically give it modern cross-host execution or a shared live authority model. | **I:** every card can hold a durable computation, and an agent can modify its behavior. **100×:** user-created applications can keep working, await people, fork, and move after their original tab closes. Ordinary AI-generated forms alone do not justify capsules. **→ #1, #2.** |
| **Mainframe CICS transactions** | **F:** units of work commit recoverable resources at syncpoints; nonrecoverable resources are not backed out. [IBM CICS synchronization points, current][cics]. **I:** CICS's success proves the value of a defined transaction boundary, not atomicity over today's arbitrary SaaS APIs. | **I:** branch proposals freely, then commit through explicit participating resources and reconciliation. **100×:** institutions can negotiate executable contingencies without granting every speculative agent write access. **→ #5.** |
| **Linda tuple spaces** | **F:** independently existing tuples decouple senders/receivers in space and time; the original paper includes continuation passing among its consequences. [Gelernter, January 1985][linda]. **I:** a global associative space still needs placement, failure, and access semantics. | **I:** tuples can name unfinished work: image hash, requested capability, result contract, lease. **100×:** a population of agents discovers and advances a shared frontier of problems without one brittle hand-coded workflow graph. **→ #8, #5.** |
| **JavaSpaces** | **F:** entries can be written, read, taken, matched, leased, and included in transactions. [JavaSpaces specification][javaspaces]. **I:** the JVM/RMI/serialization ecosystem was part of the deployment contract; taking an entry is not proof an external job completed. | **I:** lease and atomically claim capsule work, with fenced result publication and independent verification. **100×:** dynamically assembled organizations of agents exchange tasks and conditional offers. **→ #8, #5.** |
| **CAP capability machine** | **F:** CAP used protected capability mechanisms and protected procedure access. [Wilkes/Needham, 1979][cap]. **I:** specialized hardware/OS adoption was a large surface; this is not evidence capabilities themselves failed. | **I:** put authority in the trusted host's references and checks, not editable guest strings. **100×:** each agent-created collaborator gets a separately limited computer without inheriting a person's entire account. **→ #3, #5, #9.** |
| **E / object-capability security** | **F:** Miller presents E as a distributed, persistent language joining access and concurrency control. Budget conservation matters as much as sandboxing. **→ #3, #5.** |

## Nine 100× bets

### 1. Executable citations: a link into the computation behind a claim

**I — One sentence:** attach a forkable continuation, source-version links, and an input journal to an analytical claim, so another person can resume the exact analysis with one assumption changed.

**I/E — The 100× version:** the unit of technical and institutional discussion becomes a disputable computation. Agents produce and maintain **100× more individually inspectable claims per analyst**, while other agents search for counterexamples and compose claims into larger arguments. An engineering incident report, benchmark, or procurement recommendation carries a button labeled “disagree here.” A changed source marks dependent claims stale; it does not silently overwrite the historical claim.

**F — Lineage:** Xanadu supplies stable source/version identity; NLS supplies structured collaborative argument; HyperCard supplies approachable executable documents. [Nelson][xanadu], [Engelbart demo][nls], [Allen][hypercard]. **I — Then versus now:** a browser link removes the need to adopt an entire replacement publishing environment; models can build adapters and explicit tests for objections. The hard new work is linking an observed answer to executable provenance, rather than decorating an LLM answer with citations.

**I — Why stronger models help / value:** stronger agents create more consequential analyses and can formulate more discriminating challenges. Engineering teams, research-tool vendors, and audit/review teams could pay for inspecting and updating a large estate of claims. The stored computation becomes more valuable as the supply of plausible prose explodes. A deterministic result is still not proof its inputs or model of reality are true.

**I/E — First proof, 10 working days:** build one TypeScript application that analyzes a public incident/event dataset. Give its claim an explicit scope, such as “all schedules in this declared timeout envelope satisfy the target.” Park it after it has constructed a cyclic index, closures, and several recorded tool results, immediately before a disputed tool input. Store a versioned image and journal in R2. A browser Worker restores it and forks two alternative replies; an edge executor restores the same parent. Show the exact point of divergence, source hashes, a counterexample generated by an agent within the declared envelope, and zero live writes. In week two, give five unfamiliar engineers the artifact and compare time-to-challenge against a source/input notebook baseline. Use bounded public fixtures, not private incident exports; distinguish a counterexample to the model's claim from a new observation about the real incident.

**F/I — Substitute pressure:** Binder already turns repositories into shareable executable environments. [Binder introduction][binder]. The capsule must preserve useful expensive or irregular intermediate work and make a precise disagreement easier; “an executable document” is occupied ground. If source+inputs replay is as easy, use it.

**I — Demo, 60 seconds:** a confident sentence sits above its evidence; a reviewer clicks “disagree,” changes a timeout assumption, and the same saved analysis produces a counterexample. Close the source tab, open the artifact elsewhere, and repeat. Label recorded inputs and actual hosts; do not stage an answer unrelated to the computation.

**I — Draft tweet:** “A footnote you can fork. This analysis link carries a paused computation and its recorded inputs. Change one assumption in your browser and inspect the different result. Inspired by Xanadu, NLS, and executable notebooks.”

**E — Single kill test:** in the five-person comparison, the capsule fails to reduce median time to a correct, inspectable challenge by **at least 2×** over the notebook/source+inputs baseline. That kills this product wedge even if the artifact demo looks good.

### 2. Software that can be rebuilt while people are using it

**I — One sentence:** make an upgrade a reviewable family of migrated running programs, tested against actual old states and pending work before one future receives production authority.

**I/E — The 100× version:** millions of businesses have individually adapted live software, and stronger agents continuously improve it without requiring those businesses to become software-maintenance teams. Aim for **100× more safely maintained application variants per engineer**. Users keep their work while agents split a schema, replace a connector, or change a business rule. A proposed upgrade includes counterexamples and evidence across the affected states, much as a pull request includes code.

**F — Lineage:** Squeak and Genera make development part of an occupied environment; PJama identifies evolution of persistent classes as a central barrier; Erlang demonstrates that live replacement needs explicit version rules. [Squeak][squeak], [Genera][genera], [PJama][pjama], [Erlang code loading][erlang-code]. **I — Then versus now:** agents may supply the enormous volume of migration labor that bespoke persistent worlds require. They do not supply correctness automatically. Prior `pi-world` work makes “an agent edits a heap” inadequate differentiation; the proposed leap is verified evolution across many living variants.

**I — Why stronger models help / value:** more capable agents create more software diversity and propose harder state transformations. That increases demand for an independent evolution boundary. Vertical-software vendors, agencies maintaining bespoke tools, and agent-application platforms could pay to upgrade customer-specific systems without throwing away in-flight work. The asset is the corpus of compatibility contracts, migration evidence, and operational history.

**I/E — First proof, two weeks:** provide visible development examples and seed **30 held-out** small workflow worlds with different object-graph shapes and pending order-processing tasks. Keep the engine fixed. Use a stable dispatcher/object-root contract; an agent proposes a migration and new handlers for an address/schema change. Test aliases, cycles, missing fields, already-applied effects, and delayed replies against independently authored invariants. Old continuations retain old code until a declared boundary; versioned reply adapters handle old pending calls. Shadow the same recorded suffix through old/new worlds, then promote one under a fenced DO writer epoch. Keep the held-out graph variants from the proposing agent. Include a deliberately invalid migration that the gate rejects. Run the same change through a source+input replay or explicit-state baseline with the same agent and budget; compare human fixes, lost progress, and interruption, rather than awarding capsules a win merely for passing their own tests.

**I — Crucial limit:** this experiment does **not** rewrite arbitrary suspended stack frames or transplant a new engine into incompatible heap bytes. More general upgrades may need semantic export/reconstruction or replay. If every useful upgrade requires that escape hatch, the value of the live image must be re-evaluated.

**I — Demo, 75 seconds:** show several customers midway through work. Ask an agent to add a rule and migrate a field. One proposed future breaks an old pending task and turns red; another passes the hidden variants. Promote it, deliver the delayed reply, and show the original task continuing with one authorized external write. Display which migration code the agent actually wrote.

**I — Draft tweet:** “Smalltalk's live image, with an upgrade review. An agent migrates occupied applications; old pending work becomes the compatibility test. Forks expose a broken future before one candidate gets write authority. Fixed engine, explicit upgrade boundaries.”

**E — Single kill test:** the proposal-and-gate process cannot complete **90% of the 30 held-out variant cases** for this bounded change without hand-written per-case fixes, while preserving all declared invariants. That result would show the migration labor still scales with the number of worlds, undermining the 100× thesis.

### 3. Visiting agents: send the unfinished question to the data

**I — One sentence:** a data owner hosts an incoming capsule under a locally chosen namespace and output policy, allowing the question's computation to visit data that is not copied into a central agent service.

**I/E — The 100× version:** a network of institutions offers execution places rather than bulk data exports. One problem branches into visiting programs at **100 independent owners**, each supplies locally approved answers, and the parent combines those answers. Users carry a continuing task between their browser, organization, and service providers. The ambition is to make cross-institution work feasible without a new centralized data lake or a custom integration project for each question.

**F — Lineage:** this deliberately revives Telescript's agents, places, authorities, and permits; Emerald's explicit mobility; Plan 9's private namespaces; and E's controlled composition. [Telescript][telescript], [Emerald][emerald], [Plan 9][plan9], [Miller][e]. **I — Then versus now:** compatible browsers/Wasm and one edge platform reduce runtime-distribution work; agents may negotiate application adapters. The host still must willingly expose meaningful tools. Wasm does not force a supplier, hospital, or bank to participate.

**I — Why stronger models help / value:** stronger agents can construct a useful visiting computation from a high-level question, adapt to each owner's vocabulary, and minimize requested authority. Data platforms, enterprise collaboration vendors, and organizations doing cross-company analysis could pay for useful answers with controlled disclosure. Start with suppliers or engineering datasets, where approvals and outputs can be defined concretely.

**I/E — First proof, 1–2 weeks:** run three separately configured TypeScript hosts: a browser with a local inventory fixture and two Workers with different private fixtures/tool schemas. A paused supply-allocation analysis visits each host, with logical capabilities rebound locally. Each owner permits bounded aggregates and rejects row export, arbitrary egress, and overspending. An agent adapts a tool schema and the host validates the adapter. Publish network traces, output bytes, restore identity, and a rejected malicious query. Compare against a normal remote-query/connector implementation; image movement must retain a meaningful iterative local plan, not merely replace an RPC request with a bigger blob.

**I — The privacy trap that could invalidate the whole pitch:** an outgoing raw heap can contain private input, including freed bytes. After reading confidential data, the continuation **stays at that owner** unless the owner authorizes the entire image export. Otherwise only approved outputs leave, and a fresh public-state capsule continues elsewhere. This sacrifices unrestricted same-image mobility. Even permitted aggregates can leak through repeated queries; output-policy enforcement needs budgets and a real data owner's rules. No confidentiality from the execution host, cryptographic computation proof, or universal privacy claim is made.

**I — Demo, 60 seconds:** move a paused question through three visibly separate execution places. Each place shows its granted namespace and a different local answer. Try exporting a row and then the post-query heap; both fail. The parent continues from approved outputs. Show this restriction as part of the actual behavior.

**I — Draft tweet:** “Telescript's visiting agents, using a Wasm capsule. The question travels to three data owners; each grants its own tools and export rules. Private heaps stay put. Approved answers continue the task. Mobility is useful only with explicit authority.”

**E — Single kill test:** two of three representative data owners cannot offer a useful result without granting outputs or heap exports they would refuse in their normal workflow. That kills the institutional federation wedge, regardless of successful migration.

### 4. NonStop repair: a failure becomes a farm of proposed recoveries

**I — One sentence:** a supervisor turns a failed capsule into isolated candidate repairs, tests them against the failure and unaffected histories, and promotes one without giving speculative children production write access.

**I/E — The 100× version:** every failure becomes an improvement opportunity for a fleet of continuing services. Rather than retry the same broken program 100 times, explore **100 materially different recoveries** and retain reusable counterexamples. Aim for **100× more localized incidents resolved per operator**, with explicit escalation for cases the gate cannot judge. The ambition is a continuously repairing integration fabric, not an “AI SRE” chat window.

**F — Lineage:** OTP separates supervisors from workers; Tandem process pairs and transactions preserve service under failures. Neither implies a copied program fixes its own deterministic bug. [Armstrong][armstrong], [OTP][supervision], [Gray][tandem]. **I — Then versus now:** capable models can propose semantic repairs; portable failures can be sent to independent analysis hosts. The model must remain outside the trusted acceptance decision. Stronger models also produce subtler incorrect fixes, so independent contracts become more valuable.

**I — Why stronger models help / value:** better models can propose harder repairs and more discriminating counterexamples; a gate that accepts only observed compatible behavior becomes more valuable as proposals multiply. Automation vendors and platform teams could pay to recover connector breaks, parser changes, and bounded application failures while preserving pending work. Start with repairable adapter failures. A debugger plus a normal deployment pipeline is a strong substitute; the capsule must preserve information those tools lose.

**I/E — First proof, 10 days:** use three tiny TypeScript services with **10 predeclared connector-change failures** and an independent unaffected trace corpus. Snapshot at the last good boundary; retain the failure journal separately. Generate up to five actual candidates per failure, with a fixed model/spend budget. Run a patch only through a declared replaceable handler boundary, replay the failing input, then replay unaffected suffixes. Check business invariants and operation-ledger identities. A DO supervisor bounds restart intensity, fences the old writer, and dispatches one tested continuation. Inject crashes before/after promotion and show explicit unresolved outcomes.

**I — Demo, 60 seconds:** a connector changes its response schema. Restarting fails again. Five repair branches appear; one overfits and fails an unrelated case. A passing candidate continues the original task and the service remains inspectable. Label the injected failure, prerecorded histories, actual model calls, and elapsed time.

**I — Draft tweet:** “Let it crash—then inspect several repairs. This supervisor forks a failed continuation, checks agent-written fixes against recorded histories, and grants one candidate write authority. Inspired by Erlang and Tandem; narrow connector failures so far.”

**E — Single kill test:** on the fixed 10-failure set, capsule-assisted repair reduces neither human intervention nor recovery time compared with restart-from-source plus the same agent, traces, tests, and budget. That kills the capsule-specific product, even if automated repair itself works.

### 5. Executable agreements: many proposals, one authorized commitment

**I — One sentence:** represent a multi-party negotiation as forkable continuations whose proposed effects become real only through an explicitly participating transaction/commit broker.

**I/E — The 100× version:** people delegate goals and spending limits, then agents explore **100 contingent plans** across suppliers, calendars, and resources before any plan commits. The durable artifact contains the ongoing agreement, accepted evidence, remaining contingencies, and disputes. An organization could express “buy this combination only if these conditions are still true” rather than manually coordinate every application. This is a computational protocol, not a claim about legal enforceability.

**F — Lineage:** CICS makes the unit of recovery explicit; JavaSpaces supports transactions and leased entries; Telescript and E make authority part of interaction. [CICS][cics], [JavaSpaces][javaspaces], [White][white], [Miller][e]. **I — Then versus now:** models could turn fuzzy goals into conditional proposals, but resource participation remains decisive. A calendar invitation, message, or nonparticipating payment API cannot be rolled back by restoring a heap.

**I — Why stronger models help / value:** better agents produce more alternatives and can negotiate richer constraints; they need a reliable boundary between proposing and committing. Procurement/operations platforms and marketplaces could pay for bounded delegations that survive waiting, disagreement, and partial failure. The broker must conserve a parent's budget across forks; cloned authority cannot clone funds.

**I/E — First proof, two weeks:** build one DO-backed broker with transactional fictional stock and budget records, plus two separately running offer-producing Workers. The offers are real messages; the economic resources are explicitly a simulation. A guest explores 20 order combinations, pauses for a human selection, and commits one against versioned reservations. The broker transaction records the winner, resource changes, and one outbox intent atomically. An idempotent mock downstream consumes it. Test duplicate winners, expiry, stale reservations, restored old writers, and crash after downstream application/before acknowledgment. For a non-idempotent mock, surface “outcome unknown” instead of retrying. This proves local transaction semantics and honest external uncertainty, not global SaaS atomicity.

**I — Demo, 75 seconds:** twenty branching offers compete for a deliberately scarce last unit; two copies try to win. Show one authoritative commitment, conserved stock/budget, and a stale branch rejection. Kill the executor at the awkward acknowledgment window. The ledger explains what is known and what requires reconciliation.

**I — Draft tweet:** “Twenty possible deals, one authorized commitment. Agents fork the negotiation; a transaction broker owns stock and budget. Killing a worker cannot mint another purchase. CICS and capability security meet portable continuations. Demo uses simulated inventory.”

**E — Single kill test:** one adversarial execution in the specified crash/expiry/fork schedule produces two committed winners for the same reservation or exceeds the parent's budget. Stop the agreement product until that invariant holds; attractive negotiation output is irrelevant.

### 6. A personal mainframe that outlives its providers

**I — One sentence:** give a person or small organization an exportable federation of continuing services whose identity and progress survive changing hosting, software vendors, and model providers.

**I/E — The 100× version:** a household, research group, or small business owns a computational estate as durable as its documents: thousands of dormant duties, specialist tools, and institutional memories, maintained by agents. Aim for **100× more useful long-lived automations per nontechnical owner** without 100× administration. The computer is a collection of portable manifests and bounded images, with bulk data separately owned; no single heap must contain someone's whole life. This becomes especially consequential when the original software supplier disappears.

**F — Lineage:** Multics's utility, System/38's high-level objects, EROS's consistent persistence, and Grasshopper's storage/execution/protection split all question the customary separation between a program and its saved data. [Multics][multics], [System/38][s38], [EROS][eros], [Grasshopper][grasshopper]. **I — Then versus now:** existing hosts can cache the running part and object storage can retain the rest. Agents might maintain the dependency graph and upgrade paths. This does not inherit the old systems' internal consistency guarantees merely by naming the same abstractions.

**I — Why stronger models help / value:** capable agents create personalized services and maintain provider adapters, increasing the cost of losing those services. User-owned execution state is complementary to better models. Personal-cloud vendors, membership organizations, and small-business software providers could sell hosting, backups, capability brokers, and migration support. Willingness to pay for continuity is unproven; cheap parked bytes alone do not create demand.

**I/E — First proof, 1–2 weeks:** create three interdependent duties—renew an item, reconcile a public ledger fixture, and wait for an approval—with nontrivial guest-local state. Save their images, engine artifacts, manifest, journal, and blob references. Shut down the original Node host and make its endpoint return an error. Import into a second host and a browser inspector, renew authority explicitly, and complete the tasks without consulting the original service. Revoke one grant before import; it must stay revoked. Demonstrate one engine/application upgrade through a specified migration or qualified replay, not blind restoration into a new memory layout. Validate that the export lists every dependency.

**I — Hard limit:** a durable artifact cannot guarantee that a future engine remains safe, an upstream API remains available, or a supplier will accept an old credential. “Forever” is a maintenance commitment. Preserve inspectable source, qualified migrations, and open formats, rather than shipping an eternally runnable vulnerable engine. Capsule provenance also does not establish that imported guest state is safe or truthful.

**I — Demo, 60 seconds:** turn off the original service, move its active duties as an artifact, and finish one after rebinding tools. Show the intentionally revoked duty failing correctly. A user exports an occupied computer, not merely a chat transcript or static database backup.

**I — Draft tweet:** “The service is gone. The work isn't. This export includes three paused programs, their history, and an explicit dependency manifest. A new host rebinds authorized tools and continues them. Revoked access stays revoked. A small personal-mainframe experiment.”

**E — Single kill test:** **any** required program/engine/data dependency in the defined three-duty export can only be retrieved from the disabled original service. That falsifies the ownership claim for the proof. A later demand test must separately establish that customers value occupied-state export over ordinary data portability.

### 7. Shared computational rooms that people and agents can fork together

**I — One sentence:** synchronize people and agents around a deterministic running model, with branches that preserve the group's exact computational context and make alternative decisions directly comparable.

**I/E — The 100× version:** replace a meeting's slide deck and disconnected chats with a room containing the executable system being discussed. An incident team, factory planner, or standards group can explore **100 alternatives from one shared state**, let agents search consequences, then bring back inspectable proposals. The room may sleep in R2 and later reopen in browsers or at an edge host. The ambition is much better collective reasoning; a hypothetical simulation remains a model, not a prediction of reality certified by the runtime.

**F — Lineage:** Croquet/TeaTime treats collaboration as replicated computation with coordinated messages, while NLS treats a group and its working methods as an augmentation system. [Croquet][croquet], [Reed][teatime], [Engelbart][engelbart]. **I — Then versus now:** familiar browser interfaces can replace specialized 3D clients, and agents can populate alternative models or search branches. External nondeterminism remains the key constraint. Do not invoke an LLM independently on every replica and expect identical behavior.

**I — Why stronger models help / value:** stronger agents become active participants that propose executable changes and investigate side effects. The durable shared state coordinates their work. Operations/reliability teams and collaborative simulation vendors could pay for replayable exercises and decision records. A CRDT document, normal multiplayer app, or shared notebook is a strong substitute whenever only document state matters.

**I/E — First proof, 10 days:** build a small incident-response simulation in TypeScript with three browser replicas, a fixed QuickJS/Wasm model, and a DO ordering events. Model calls and tool replies happen once at the broker and enter the ordered input journal. Each replica executes the same model and reports semantic state/output digests at declared boundaries; host-specific heap bytes need not hash identically. Fork after one failure, let an agent propose a response, reconnect a dropped participant from an R2 checkpoint, and compare outcomes. Promote a selected action as a new event after validating its preconditions against current authoritative state; do not merge heaps or commit a stale simulated world.

**I — Demo, 60 seconds:** three cursors share the same running incident. One person forks, an agent explores a repair, and another participant disconnects. Rejoin from the saved state, compare the branch, and adopt one still-valid proposal. A visible event counter shows that a model/tool result was consumed once, rather than regenerated by each viewer.

**I — Draft tweet:** “A shared room made of computation, not screen sharing. Three browsers resume one saved model, fork a decision, and compare the consequences. An agent joins through the same ordered event stream. Inspired by Croquet/TeaTime; external inputs are journaled once.”

**E — Single kill test:** within a **10,000-event** reconnect/reorder/duplicate-delivery trial under the declared deterministic profile, replicas disagree at a committed boundary without detecting and stopping before action publication. That kills the trustworthy-room claim until corrected.

### 8. A planetary exchange for unfinished computation

**I — One sentence:** make a leased, verifiable continuation the transferable unit of a distributed search market, so workers trade actual progress instead of repeatedly reconstructing tasks from prompts.

**I/E — The 100× version:** a difficult planning, program-repair, or counterexample-search problem leaves a frontier of a million dormant continuations. Compatible browsers and edge/server workers claim slices, advance promising branches, and publish independently checkable results. Aim for **100× more useful search frontier retained and revisited per coordinator**, with scheduling adapted by agents. A marketplace for meaningful progress is the ambition; merely renting idle browser CPU is a low-value version.

**F — Lineage:** Sprite demonstrated useful migration and painful host-state coupling; MOSIX exposed the persistent home deputy; Condor checkpointing depended on a supported program contract. Linda and JavaSpaces supply decoupled matching and leases. [Sprite][sprite], [MOSIX][mosix], [HTCondor][condor], [Linda][linda], [JavaSpaces][javaspaces]. **I — Then versus now:** a fixed Wasm interpreter and explicit tools narrow compatibility requirements, and agents can propose task decomposition. Inference cost, verification cost, and valuable local work still dominate the economics.

**I — Why stronger models help / value:** more capable agents generate harder search programs and better admissible heuristics; an inspectable frontier can preserve valuable intermediate work across model changes. Verification/search platforms might depend on it. However, if the frontier is only a set of prompts or compact ordinary data structures, existing queues and batch runners are simpler. This is deliberately ranked low.

**I/E — First proof, two weeks:** choose one bounded repair-search workload whose partial state contains a cyclic constraint graph and a captured continuation, with a cheap independent checker. Use a DO per bounded work partition for lease epochs and claims, R2 for images, and Queues as at-least-once wakeups. Run **100 logical branches** across a few Node workers, controlled browser workers, and one hosted Worker where available. Evict 30% of assignments; accept only current-epoch outputs. Compare completed verified candidates per total CPU/byte/model budget against a source+input checkpoint representation. Predeclare a cost model for CPU and transferred bytes so the kill test has one comparable denominator. Do not call it a global deployment unless remote hosts actually ran.

**I — Malicious-worker boundary:** a browser can fabricate a “completed” capsule. Only publish a result after a cheap independent checker, or replay the authoritative work on a trusted host. Do not hand it production secrets or raw private snapshots. If verification costs as much as recomputing, the public exchange loses its central advantage. Leases conserve assignment rights; they do not prove honest execution.

**I — Demo, 60 seconds:** a visible search frontier lives as sleeping artifacts. Close a worker tab; its lease expires and another host advances the same branch. A fabricated solution fails the checker. Show accepted progress, transferred bytes, and model calls alongside elapsed time, so duplication is visible.

**I — Draft tweet:** “Condor-style progress sharing for a constrained Wasm search. Workers claim paused branches, survive eviction, and submit results to an independent checker. A closed tab loses its lease, not the work. No claim of trustworthy volunteer execution.”

**E — Single kill test:** at equal total model-call budget and the defined eviction rate, capsule transfer fails to improve **verified useful progress per total CPU-and-transfer cost by 2×** over source+input/semantic-checkpoint scheduling. Drop this application; heap movement is then expensive packaging.

### 9. A computer foundry that grows the smallest environment a program needs

**I — One sentence:** let agents synthesize a program family's minimal host environment and adapters from executable contracts, while keeping protection, credentials, and acceptance tests outside that generated environment.

**I/E — The 100× version:** the world can afford **100× more specialized computational habitats**: a legacy-data instrument, a transient protocol interpreter, a policy searcher, or a self-contained business tool each gets only the runtime services it needs. Agents maintain compatibility “species” and propose new services against independent oracles. The large ambition is preserving and extending executable software ecosystems without porting an entire operating system for every family.

**F — Lineage:** Mirage compiles a purpose-built stack; exokernels separate protection from application resource policy; CAP separates protected authority; GrowOS already grows a narrow syscall subset against Linux with independent and held-out gates. [Mirage][mirage], [Engler et al.][exo], [CAP][cap], [local GrowOS](../../jitk/grow/README.md). **I — Then versus now:** agents might lower the integration labor that specialization imposes. Merely showing another agent-written syscall repeats existing GrowOS work. The proposed extension is a maintained family of portable, minimally sufficient environments with the same behavior across hosts.

**I — Why stronger models help / value:** better models can infer and implement more complicated compatibility contracts and identify missing assumptions. Legacy-software tool vendors and agent-platform teams could pay for verified narrow adapters. Better code generation also creates dangerous overfitting. The independent oracle, mutation checks, resource budgets, and host-policy boundary remain the asset; the model cannot grade its own work or expand its own grants.

**I/E — First proof, 1–2 weeks:** keep the QuickJS/Wasm engine and trusted broker fixed. Select three small generated programs that require different clock, encoding, file-view, or query-tool conventions. An agent synthesizes guest-side adapters from a visible behavioral contract. Run the same family in Node, browser, and workerd against held-out host fixtures and known-bad mutants. Add one new behavior and regenerate the adapters without changing the broker allowlist. Report the declared supported subset and failures. This is a TypeScript/Wasm habitat proof, not a new kernel, formal equivalence proof, automatic npm compatibility, or an x86 jitk port.

**I — Demo, 45 seconds:** a program meets a missing tool convention. The agent supplies a small adapter; the independent gate rejects one superficially passing proposal, accepts another, and the program resumes on two hosts. Show that requesting a new privilege still fails. Public code and exact tests accompany the video.

**I — Draft tweet:** “A tiny environment grown around a program. An agent builds an adapter; independent host fixtures and bad-implementation tests decide whether it works. The same capsule resumes in two runtimes. Inspired by exokernels, Mirage, and GrowOS; authority stays fixed.”

**E — Single kill test:** adding the selected new behavior requires expanding the trusted protection/broker core rather than adding a bounded untrusted adapter. That would show this proposed portable specialization boundary is wrong; defer the foundry instead of turning it into a general OS project.

## Ruthless evaluation before building

**I — These are alternative experiments, not nine simultaneous two-week commitments.** Each proof assumes reuse of the existing interpreter spike and a small TypeScript host/broker, uses controlled fixtures, and measures the whole path. A public hostile-tenant service is additional work. If enforcing the fixed resource limits or obtaining a real hosted deployment consumes the budget, record that result and narrow the claim; do not substitute a UI animation or call local workerd an edge city.

**I — The recurring possibility of failure is that ordinary representations win.** A workflow journal, source+inputs, JSON application state, or a notebook may be smaller, more inspectable, easier to migrate, and equally useful. The image earns its place only when it preserves consequential intermediate computation that is awkward or expensive to reconstruct. Models becoming better at reconstruction could eat the capsule advantage. Every top bet therefore needs a matched baseline with the same model, tools, history, and budget.

**I — Stronger models increase the value of the acceptance boundary, but also its burden.** A hundred model-written variants judged by the same model are not a hundred independent checks. Preserve independent invariants, unseen fixtures, a fixed effect policy, and explicit failure results. Borrow GrowOS's evaluation discipline; do not present a held-out pass as a proof of arbitrary future behavior.

**I — Do not merge bytes.** Two heap branches may share a prefix, but their pointer layouts and external actions do not admit a general useful Git merge. Merge a supported application operation, proposal, or journal event after conflict/precondition checks. Similarly, rolling a heap back does not roll the world back. These two limitations should be visible in every demo where a branch becomes authoritative.

**I — Demotions:** #4 is useful but easily becomes ordinary automated incident repair; #5 is powerful but depends on participating resource systems; #6 has the strongest ownership philosophy but weak immediate proof of demand; #7 risks becoming a multiplayer simulation demo; #8 risks losing to queues and cheap recomputation; #9 risks recreating an entire systems-research agenda. Keep them as sources of requirements, rather than launching nine products.

## Primary sources, dates, and evidence limits

**F — Source policy:** original authors' papers, original vendor documentation, and project-maintainer specifications are preferred below. A mirror of an original paper remains primary content; its upload/crawl date is not its publication date. Dynamic documentation has an access date rather than an invented release date. No historical failure cause is inferred from a source merely being old.

- **Squeak:** Ingalls, Kaehler, Maloney, Wallace, Kay, [“Back to the Future: The Story of Squeak”][squeak], **OOPSLA 1997**, author paper in the Computer History Museum collection. Immediate modification, portability, image representation, compactness motivations.
- **Lisp machines:** Symbolics, [“Genera Concepts”][genera], **copyright 1990**, original manual text mirrored with permission. Extensible integrated environment and saved worlds; no claim of universal external-device capture.
- **Multics:** Corbató, Saltzer, Clingen, [“Multics—The First Seven Years”][multics], **1972**, author-hosted paper. Utility goals and one-level-memory architecture.
- **KeyKOS/EROS:** Shapiro and Adams, [“Design Evolution of the EROS Single-Level Store”][eros], **USENIX ATC, June 2002**, especially §§2–3 and the account of KeyKOS inheritance. The linked original Landau KeyKOS checkpoint page returned **404** during this research; this report relies on the designers' accessible later account, rather than pretending to have retrieved that page. [CapROS's maintainer checkpoint notes][capros] independently document the lineage and differences.
- **System/38:** Dahlby, Henry, Reynolds, Taylor, [“The IBM System/38: A High-Level Machine”][s38], **System/38 design published 1978**, reproduced in *Computer Structures: Principles and Examples*. **IBM i:** [“Storage Structures”][ibmi], current IBM documentation, accessed **2026-10-27**. These establish an enduring design, not transparent process-checkpoint equivalence with EROS.
- **PJama:** Jordan and Atkinson, [“Orthogonal Persistence for Java—A Mid-term Report”][pjama], **1998**, original paper text indexed at CiteSeerX. Its indexed abstract, introduction, and conclusion explicitly identify evolution/external-state issues; direct PDF retrieval returned **403**. Claims are restricted to that readable indexed material.
- **Grasshopper:** Dearle et al., [“Grasshopper: An Orthogonally Persistent Operating System”][grasshopper], **Summer 1994**, author-hosted paper, publication pp. 289–312. Abstractions and persistence/integration challenges.
- **Telescript:** General Magic, [*Telescript Language Reference*][telescript], **October 1995**, especially the introduction and agent/place/permit concepts; Jim White, [“A Common Agent Platform”][white], **1996-03-11**, W3C/OMG workshop submission. The latter documents an interoperability ambition, not a retrospective explanation of General Magic's business history.
- **Emerald:** Jul, Levy, Hutchinson, Black, [“Fine-Grained Mobility in the Emerald System”][emerald], **ACM TOCS, February 1988**, author-hosted paper. Some OCR copies incorrectly render 1988 as 1966; the publication is 1988.
- **Sprite:** Douglis and Ousterhout, [“Transparent Process Migration: Design Alternatives and the Sprite Implementation”][sprite], **Software—Practice & Experience, August 1991**, author-hosted paper; Ousterhout, [“Sprite Retrospective”][sprite-retro], author-hosted retrospective, undated page accessed **2026-10-27**.
- **MOSIX:** Barak, La'adan, Shiloh, [“Scalable Cluster Computing with MOSIX for Linux”][mosix], **Linux Expo 1999**, author-hosted paper. Initial direct retrieval returned **503**; a subsequent retrieval made the original deputy/migration sections readable. No current MOSIX product-status claim is made.
- **Condor:** [HTCondor “How To Checkpoint”][condor], historical project-maintainer guide; [8.8 checkpoint-server documentation][condor-server], historical versioned manual. These describe historical standard-universe behavior; they are not claims that every current HTCondor job supports transparent checkpointing.
- **Erlang:** Armstrong, [*Making Reliable Distributed Systems in the Presence of Software Errors*][armstrong], **December 2003**, corrected **2003-11-20**; official [supervision][supervision] and [code-loading][erlang-code] documentation, current pages accessed **2026-10-27**. Historical philosophy and specific live-loading limits are kept distinct.
- **Plan 9:** Pike, Presotto, Dorward, Flandrena, Thompson, Trickey, Winterbottom, [“Plan 9 from Bell Labs”][plan9], **Computing Systems, Summer 1995**, original paper hosted by USENIX.
- **Tandem:** Gray, [“Why Do Computers Stop and What Can Be Done About It?”][tandem], **Tandem TR 85.7, June 1985, revised November 1985**, original paper mirrored by UW. Process pairs and transaction scope, rather than an inferred modern availability promise.
- **Xanadu:** Nelson, [“The Xanadu Model: A Pictorial View of Referential Documents and Content Linking”][xanadu], page dated **1999-11-30**, revision marker **2001-05-23**. The main `xanadu.com` route failed; the project-hosted `xanadu.net` copy was readable. Content identity/version/transclusion only; no endorsement of every architectural or economic claim.
- **NLS:** Engelbart, [*Augmenting Human Intellect: A Conceptual Framework*][engelbart], **October 1962**; [original 1968 demonstration and institute's chaptered guide][nls], **1968-12-09**. Claims concern the demonstrated collaboration/structure and the original augmentation thesis.
- **HyperCard:** Dan Allen, Apple HyperCard team, [“An Introduction to HyperCard Programming”][hypercard], **Dr. Dobb's, 1988**, original developer article mirrored in its archive. Apple's [1987 user guide][hypercard-manual] was located, but browser retrieval rejected its approximately 28 MB content length; no claims depend on unread manual pages.
- **CICS:** IBM, [“Synchronization points”][cics] and [“Unit of work recovery”][cics-recovery], current CICS TS documentation, accessed **2026-10-27**. Recoverable/nonrecoverable distinction and in-doubt failure handling are material to the proposed agreement broker.
- **Linda:** Gelernter, [“Generative Communication in Linda”][linda], **ACM TOPLAS 7(1), January 1985**, original paper indexed/mirrored by UCSD. Direct retrieval timed out; readable indexed original excerpts support temporal/spatial decoupling and continuation passing. No measured modern scalability claim relies on it.
- **JavaSpaces:** Sun/Apache River, [*JavaSpaces Service Specification*, version 2.2][javaspaces], maintainer-hosted specification accessed **2026-10-27**; the original [Sun specification][javaspaces98] dates to **1998**. Entry/lease/transaction semantics are taken from the readable v2.2 text, not retroactively assigned to every earlier version.
- **CAP:** Wilkes and Needham, [*The Cambridge CAP Computer and Its Operating System*][cap], **1979**, original book hosted by Cambridge. Hardware/OS capabilities and protected procedures.
- **E:** Miller, [*Robust Composition: Towards a Unified Approach to Access Control and Concurrency Control*][e], **May 2006**, author's dissertation page and readable indexed original abstract; [JHU thesis PDF][e-pdf]. The author's page intermittently returned **502**, and direct JHU PDF retrieval returned **403**. No detailed E persistence/revocation mechanism is asserted from the indexed abstract alone.
- **Mirage:** Madhavapeddy et al., [“Unikernels: Library Operating Systems for the Cloud”][mirage], **ASPLOS, March 2013**, original author paper. Specialization, compatibility tradeoffs, and library/integration work.
- **Exokernel:** Engler, Kaashoek, O'Toole, [“Exokernel: An Operating System Architecture for Application-Level Resource Management”][exo], **SOSP 1995**; Engler's [MIT dissertation][exo-thesis], **1999**, describes the protection/management split. The guessed MIT direct paper route failed; use the publisher record and institutional thesis, not that failed URL.
- **Croquet:** Smith, Kay, Raab, Reed, [“Croquet—A Collaboration System Architecture”][croquet], **2003**, VPRI original report; Reed, [TeaTime architectural-framework slides][teatime], author slides dated **2005-10-19**, with readable indexed original passages on replicated message histories. Direct slide retrieval rejected the server's `application/octet-stream` content type. Replication is a semantic lineage, not evidence of present Wasm cross-host determinism.
- **Modern substitute:** [Binder introduction][binder], current project documentation accessed **2026-10-27**. Shareable executable environments pre-exist the proposed executable-citation product.
- **Deployment constraints:** official Cloudflare [Workers placement][placement], [DO location][do-location], and [R2 location][r2-location], current documentation accessed **2026-10-27**. Runtime resource/security constraints and exact earlier measurements are separately attributed to this repository's research above.

### Ranked shortlist: top three

**1 — #2, rebuild occupied software. I:** this goes straight at the problem persistent systems made unavoidable: how does a world improve after it already contains valuable state? Strong agents make both the opportunity and the failure mode larger by creating many more bespoke applications and migrations. A fleet of old states, delayed replies, and independently checked candidate futures is a concrete engineering artifact. The 30-case upgrade trial can falsify the premise quickly. Success would justify a much larger maintenance/evolution system; a heap-editing demo alone would not. The public hook is an old task visibly surviving a meaningful upgrade, with a rejected bad migration beside it.

**2 — #1, executable citations. I:** the 100× ambition is a knowledge ecosystem in which computational claims can be interrogated and composed without returning to their original author or cloud. Xanadu/NLS supply a richer direction than a familiar Git metaphor. It is also the easiest idea to distribute: a stranger can open one link and challenge it in a browser. The weakness is substantial prior art in notebooks, reproducible research, and source replay. The five-engineer baseline test makes that objection productive. The headline should be the easier disagreement, with exact provenance and measurement, not the invention of executable documents.

**3 — #3, visiting agents. I:** Telescript becomes much more consequential when the visiting program can understand a host's tools and carry a nontrivial unfinished task. Federation could unlock work blocked by integration labor or unnecessary bulk data centralization. But the MB file does not solve trust: private heaps cannot freely leave, malicious owners can inspect visiting programs, and useful output policies require willing participants. Three separate owners rejecting forbidden exports while still answering a real joint question would be a meaningful result. Without that useful answer, global mobility is an impressive transport demo searching for a reason to exist.

### The ONE I would bet on

**I — #2: software that can be rebuilt while people are using it.** Build the small upgrade clinic: one concrete business change, 30 unseen occupied states, a pending call, an agent-written migration, independent invariants, one deliberately rejected future, and a fenced promotion. Reuse an existing snapshot engine. Measure whether retained execution state makes the upgrade materially easier and safer than source+input replay. If it does, the 100× version is individually evolving software without individually scaling maintenance labor. If it does not, stop before building a platform. The experiment confronts an old unsolved adoption problem and gets more consequential as models create more software.

### Five-line TL;DR

1. **I:** Revive living, owned, shareable computation; heap snapshots, durable execution, and forks already have substantial prior art.
2. **I:** Best bet: agents submit upgrades as independently checked futures of occupied software, tackling PJama's evolution problem directly.
3. **I:** Best public companion: executable citations that let a reader fork the exact analysis behind a claim and expose a counterexample.
4. **I:** Biggest institutional moonshot: Telescript-style visiting computation, constrained by each data owner's tools and export policy.
5. **I:** Kill every idea that loses to source replay or ordinary state; copied heaps cannot copy spending authority, guarantee privacy, or undo the world.
