# Lens A: the networking, database, and distributed-systems graveyard

Research date: **2026-10-28**. Scope: networking, servers, distributed systems, databases, storage, and compatibility-led legacy migration. Written against BRIEF.md. Primary sources are linked beside claims; undated project documentation was checked on the research date. Paper dates below are publication/submission dates, not search-engine crawl dates.

**Labels:** **F** = sourced fact, including an explicitly attributed author/vendor result; **M** = measured in this investigation; **I** = inference; **E** = estimate, proposed price, or experimental target. **There are no M claims:** this was desk research; no experiments, accounts, deployments, or infrastructure changes were performed. All demos and two-week results below are proposals.

## Finding

**I — The best revival is to grow the missing behavioral surface of an existing compatibility layer for a particular application, using the incumbent database as an executable oracle.** Sell an application that can migrate, backed by replayable evidence. The attractive work is errors, types, metadata, session state, and transaction behavior that migration tools leave to experts. Writing another general database, network stack, or S3 service has a much worse starting position.

**I — This is a conditional bet, not an uncovered category.** AWS DMS already applies generative AI to migration leftovers; Doltgres already uses PostgreSQL differential tests; IBM already checks translated COBOL against original executions. Agentic formal verification and storage tuning also have remarkably direct 2025–2026 prior art. The experiment must beat these alternatives, including an engineer using an ordinary coding agent.

## What has actually flipped, and what has not

- **F — Inference became cheaper; complete systems engineering has no established universal multiplier.** Stanford's 2025 AI Index reports the price of GPT-3.5-equivalent MMLU performance falling from $20 to $0.07 per million tokens between November 2022 and October 2024, over 280-fold. This is a benchmark-specific inference price comparison, not a measured reduction in migration or verification cost. [Stanford HAI, AI Index 2025](https://hai.stanford.edu/ai-index/2025-ai-index-report/research-and-development).
- **F — Human review can erase generation savings.** METR's early-2025 randomized study used 16 developers and 246 real tasks and found 19% longer completion times with AI. Its February 24, 2026 update says newer speedups seem likely but its follow-up estimates are unreliable because of selection and measurement problems. Neither result establishes the economics of an unattended oracle-driven loop. [2025 paper](https://arxiv.org/abs/2507.09089), [2026 update](https://metr.org/blog/2026-02-24-uplift-update/).
- **F — There is now directly relevant positive evidence, with limits.** Tobias Philipp's July 15, 2026 Ada/SPARK experience report describes 49,280 discharged obligations and approximately 20–40-fold lower supervision cost against the author's comparison with hand verification. Some properties are functional proofs; others only absence of run-time errors. This is an author-reported comparison, not a controlled productivity trial. Independent peers caught defects the proofs missed. [The Prover Is the Judge, §§III, V, VII–IX](https://arxiv.org/html/2607.14340v1).
- **I — The plausible change is the price of repeated implementation, adapter construction, failure reduction, and proof maintenance.** Customer access, defining the intended behavior, production-equivalent performance tests, data movement, and deployment authority do not become free. Each candidate below identifies which of those remains binding.

**I — Oracle discipline:** “strong” means a useful independent automatic acceptance signal for the stated scope, not a proof of all behavior. Separate functional equivalence, standards conformance, performance, crash durability, and security. A peer that accepts a handshake is a weak security oracle. A model checker strongly checks a model and its specified properties, not automatically the implementation or the adequacy of those properties. Two peers can share a bug. Never let the patching agent silently change the comparator, excluded cases, or acceptance contract.

## 1. Active networks: revive operator-controlled functions, reject arbitrary code in Internet packets

1. **Idea / origin — F.** Tennenhouse and Wetherall proposed user-injected computation in network nodes, including packets carrying executable capsules, to let services evolve independently of router hardware and slow standardization. The proposal included application-specific multicast and information fusion, not simply programmable forwarding. [Towards an Active Network Architecture, 1996](https://people.eecs.berkeley.edu/~sylvia/papers/active.pdf).
2. **Did manual effort kill it? — Mostly no, I.** The authors' 2019 retrospective attributes stalled adoption to the absence of a driving use case, and distinguishes packet-carried programs from the more practical operator-injected variant. Their story is evolution through PlanetLab, SDN, and P4, rather than a good implementation abandoned solely because coding cost too much. Security, resource control, and who gets to run code in whose network remain separate barriers. [Wetherall and Tennenhouse, October 2019](https://ccronline.sigcomm.org/wp-content/uploads/2019/10/acmdl19-340.pdf).
3. **What flipped — I.** Agents can cheaply implement bounded middlebox functions and their tests. They do not create permission to execute them on third-party routers or an incentive for Internet-wide deployment. **F:** the P4 consortium's February 2026 review lists Cisco, Oxide, and Xsight joining in 2025: evidence of an active operator-programmability ecosystem, not of capsule demand. **No sourced 2024–2026 labor-cost or adoption number establishes a capsule revival.** [P4 review, February 19, 2026](https://p4.org/2025-at-a-glance/).
4. **Oracle — Weak for a new in-network service; strong for replacing a specified existing function, I.** Mirror packet inputs against an existing proxy/firewall and compare outputs and state effects. Termination/resource verifiers do not establish policy correctness. The bounded replacement has effectively become candidate 2 or 10.
5. **100× better model — I.** Makes specialized middleboxes easier; does not solve trust, ownership, or the absence of a compelling distributed execution use case. Generic capsule hosting remains low value.
6. **2025–2026 prior art — F/I.** Operator programmability is already represented by P4 and its evolving control interface; the retrospective explicitly recognizes this lineage. Calling that agent-built active networks would mostly rename an existing market. No evidence found that the extreme capsule form has acquired a missing killer application.
7. **Value — E.** An enterprise might pay $25k/year for a managed, application-specific network function; 40 deployments imply a $1m/year beachhead. This estimates bounded middleboxes, not demand for an active Internet.
8. **Two-week proof — E.** Days 1–3: choose a preexisting packet transformation and immutable replay corpus. Days 4–9: agent implements the function in a local Rust packet processor or Wasm sandbox. Days 10–14: differential replay, resource limits, held-out malformed packets, and comparison with a conventional proxy plugin. No router deployment required.
9. **Demo / tweet / kill — E/I.** Demo an operator adding one bounded function and seeing independent replay agree. Tweet: “A packet-processing function grows from a failing trace, checked against the old appliance.” Expert killer: “This is an ordinary programmable middlebox; capsules add nothing.” Kill if the benefit requires network-wide adoption or an existing plugin is equally cheap. **Disposition: reject as a standalone revival.**

## 2. P4 and programmable dataplanes: expert porting can flip; hardware limits cannot

1. **Idea / origin — F.** Bosshart et al.'s 2014 P4 proposal sought field reconfigurability, protocol independence, and target independence: describe parsing and packet processing at a higher level, then compile to a switch target. [P4, CCR July 2014](https://www.cs.princeton.edu/~jrex/papers/P4-ccr14.pdf).
2. **Did manual effort kill it? — Partly constrained it; it did not die, I.** The original paper describes difficult chip-specific interfaces. Modern tooling still models target architectures, externs, and extensions separately. **F:** P4Testgen instantiated those semantics for V1model, eBPF, PNA, and Tofino, with extension effort depending on target complexity. This supports an expert-scarcity bottleneck, not a claim that P4 failed. [Ruffy et al., SIGCOMM 2023](https://natefoster.org/papers/p4testgen.pdf).
3. **What flipped — F/I.** A November 2025 paper already generated P4 using fine-tuned LLMs and released a 50-test compilation benchmark; it also assessed semantic behavior on tutorial tasks. Agent loops can absorb compiler diagnostics and target-porting work. Compilation success remains insufficient evidence of correct forwarding. [Dumitru et al., Generating P4 data planes using LLMs, 2025](https://www.sciencedirect.com/science/article/pii/S1389128625006759). **F:** open-p4studio supports Tofino simulation, but essential real-board software has separate access requirements; its README says Intel stopped granting those requests January 1, 2026. Cheap code does not remove hardware/vendor constraints. [Project README, checked 2026-10-28](https://github.com/p4lang/open-p4studio).
4. **Oracle — Strong for a bounded port, I.** Existing forwarding behavior plus independent packet/state traces; P4Testgen for implementation semantics; compiler/resource reports for feasibility. BMv2 agreement alone does not establish ASIC timing, line rate, target fit, or correct control-plane updates.
5. **100× better model — I.** Makes more functions and target ports economical. The remaining durable product is target-specific acceptance evidence and integration, not an English-to-P4 text box.
6. **Prior art — F.** P4Testgen; the 2025 LLM paper; open-p4studio; and current P4-Spectec semantic work. P4Runtime 1.5.0 and new ML-networking group behaviors appear in the consortium's February 2026 review. Generic generation is occupied; trustworthy target adaptation is the narrower possibility. [2025 review](https://p4.org/2025-at-a-glance/).
7. **Value — E.** Network appliance vendors/operators pay to avoid specialist porting: $50k–200k per port or supported function; 20 ports/year at $100k is a $2m services beachhead. No sourced TAM or willingness-to-pay evidence was found.
8. **Two-week proof — E.** Port an existing stateful ACL/telemetry function between two available software targets, using a frozen Rust reference and generated PTF tests. Spend week one on compilation/state mapping, week two on minimized counterexamples and held-out packet sequences. Demonstrate the software boundary; do not claim hardware readiness.
9. **Demo / tweet / kill — E/I.** Tweet: “An agent ports a stateful dataplane function and repairs it until independently generated packet traces agree.” Expert killer: “Show it fitting the real chip and surviving table updates, not just BMv2.” Kill if it saves under 50% of expert time against existing templates, or no buyer supplies a supported target. **Disposition: useful niche, hardware-heavy sales.**

## 3. User-space network stacks: compatibility labor is real, but reuse is the formidable baseline

1. **Idea / origin — F.** Jeong et al.'s mTCP combined packet and socket batching, connection locality, and user-level TCP to remove kernel overhead on multicore servers. Its 2014 benchmark reported up to 25× more small transactions than its Linux baseline; this is historical hardware/software evidence, not a current speedup. [mTCP, NSDI April 2014](https://www.usenix.org/conference/nsdi14/technical-sessions/presentation/jeong).
2. **Did manual effort kill it? — Partly, I.** Applications need porting and missing OS services must be supplied. mTCP's paper documents application/API changes and prototype limitations. Microsoft's Demikernel position paper explains that kernel bypass otherwise forces developers to understand each device and rebuild missing OS functionality. Polling CPU cost, NIC access, sharing, and operational integration are additional obstacles. [mTCP paper](https://www.usenix.org/system/files/conference/nsdi14/nsdi14-paper-jeong.pdf), [Demikernel motivation, HotOS 2019](https://www.microsoft.com/en-us/research/wp-content/uploads/2019/04/demikernel-hotos19.pdf).
3. **What flipped — F/I.** Agents can port socket APIs and repair missing options. A 2026 peer-reviewed edge study reports 3.09× throughput and 62% lower p99 for one DPDK/Seastar memcached condition versus its POSIX mode, demonstrating a workload-specific opportunity, not universal superiority. [Achieving Low Serving Latency in DPDK-Applied Systems, 2026](https://globals.ieice.org/en_transactions/information/10.1587/transinf.2025EDP7023/_f). Verification must compare equally tuned modern Linux and include all polling cores.
4. **Oracle — Strong for scoped socket behavior; weak for identical packet timing, I.** Linux/FreeBSD, packetdrill scripts, independent TCP peers, and socket-operation transcripts. ACK timing, congestion behavior, segmentation, and valid implementation choices must be compared through allowed behaviors rather than byte-identical captures.
5. **100× better model — I.** Helps absorb socket and application tails, increasing specialization value. It also makes deploying an existing stack easier, reducing the value of a fresh TCP implementation.
6. **Prior art — F.** F-Stack already reuses FreeBSD over DPDK, integrates applications, and shipped v1.25 in November 2025. Seastar already offers native and POSIX stacks. Demikernel exposes a common API but labels its code a prototype. [F-Stack releases](https://github.com/F-Stack/f-stack/releases), [Seastar documentation](https://docs.seastar.io/master/split/18.html), [Demikernel](https://github.com/microsoft/demikernel). **I:** start with porting/closure of an existing stack, not a new TCP core.
7. **Value — E.** A fleet spending $1m/year on network-bound CPU could justify $20k–50k/year if measured savings exceed 15%. Thirty $30k deployments give a $0.9m/year narrow market. Many fleets will fail the network-bound prerequisite.
8. **Two-week proof — E.** Choose one small server and an existing stack. Build a Rust socket-call trace harness; have the agent repair three bounded API gaps; reserve half the traces and run real peers. Benchmark on a supplied Linux test host only if available, otherwise report functional results and withhold performance claims.
9. **Demo / tweet / kill — E/I.** Tweet: “This server grows the socket behaviors it needs, checked against Linux and real TCP peers.” Expert killer: “You won by pinning idle cores or ignoring offloads and deployment cost.” Kill if tuning/reusing F-Stack or Linux delivers within 10% of the benefit with less effort. **Disposition: credible labor wedge, difficult standalone company.**

## 4. RFC to verified implementation: a real flip, already being demonstrated

1. **Idea / origin — F.** Project Everest, started in 2016 and described in 2017, aimed for deployable verified replacements across the HTTPS ecosystem, building on the earlier miTLS work. Its approach was specifications, proofs, and executable components rather than treating an RFC parser as a complete protocol generator. [Everest retrospective, 2025, §§1–2](https://project-everest.github.io/assets/everest-perspectives-2025.pdf).
2. **Did manual effort kill it? — Strong evidence for an expensive unfinished part, not whole-project death, F/I.** The retrospective describes substantial deployed component successes but an incomplete miTLS-fstar handshake proof; shifting team priorities were among the causes. A 2025 OpenSSL conference presentation estimates many PhD-student-years per verified component and substantial memory-safety proof effort. [Everest retrospective, §2](https://project-everest.github.io/assets/everest-perspectives-2025.pdf), [Bhargavan, OpenSSL Conference 2025](https://archive.openssl-conference.org/2025/presentations/Karthik_Bharg_OpenSSL__High-Assurance_Post-Quantum_Cryptography.pdf).
3. **What flipped — F/I.** The July 2026 SPARK report is unusually close to the proposed loop: agent writes code/contracts, machine checks them, independent peer failures drive repair. Its SSH key-derivation defect passed proof obligations but failed against OpenSSH. This demonstrates both labor reduction potential and why peer testing cannot be omitted. **F:** PSMBench's 2025 evaluation covers 14 protocols; its models reached state F1 up to 0.82 but transition F1 at most 0.38. RFC prose-to-machine extraction remains a serious semantic bottleneck. [SPARK report, §§III, VII](https://arxiv.org/html/2607.14340v1), [PSMBench, NeurIPS 2025](https://proceedings.neurips.cc/paper_files/paper/2025/hash/521bd9583b3a39e92f662ee57e81e5ce-Abstract-Datasets_and_Benchmarks_Track.html).
4. **Oracle — Strong only as a stack of independent checks, I.** Proof checker against reviewed contracts; official vectors; interoperation with multiple peers; malformed-state tests; explicit security and side-channel properties. A peer verifies compatibility on exercised paths, not confidentiality or certificate policy. RFC ambiguity and omitted properties remain human/specification work.
5. **100× better model — I.** Increases the feasible number of verified extensions, parsers, and niche protocol implementations. It commoditizes generic “we generate proofs” services; audited specifications, repeatable acceptance, and maintenance matter more.
6. **Prior art — F.** Everest/EverParse; Cryspen's Bert13/Bertie with hax and proof backends in the 2025 Rust protocol-verification paper; and the 2026 agentic SPARK work. Bert13 deliberately delegates PKI certificate validation to the application, illustrating a concrete proof boundary. [Bhargavan et al., CCS 2025, §4](https://eprint.iacr.org/2025/980.pdf), [Bertie documentation](https://cryspen.com/bertie/bertie/index.html). **I:** generic verified TLS generation has direct prior art; consider an unsupported industrial protocol extension only with a paying maintainer.
7. **Value — E.** Appliance/embedded vendors pay $30k–150k per supported verified extension; 20 engagements at $75k give $1.5m/year. Certification, liability, and secure integration could dominate delivery; no market size is established here.
8. **Two-week proof — E.** Implement one bounded binary parser/state transition from a specified RFC section in Rust with Verus or an existing verification toolchain. Freeze contracts and vectors independently. Use an existing complete implementation as peer/reference; reserve negative states and fragmented inputs. No fresh cryptographic primitives or full TLS stack.
9. **Demo / tweet / kill — E/I.** Tweet: “From RFC clause to checked parser: proofs catch memory mistakes; an independent peer catches a mistaken reading.” Expert killer: “You proved a weak model, not the protocol.” Kill if success requires weakening a contract, if held-out peer failures remain, or if an existing verified library already covers the buyer's need. **Disposition: top-three technical revival, generic version already occupied.**

## 5. Protocol compatibility and interop testing: automate the human around the matrix

1. **Idea / origin — F.** McKeeman's 1998 differential testing fed comparable systems mechanically generated cases and reduced differences for investigation. Cardwell et al.'s packetdrill in 2013 joined socket and packet events in replayable tests. Seemann and Iyengar's 2020 QUIC Interop Runner automated cross-implementation testing under network conditions. [McKeeman, 1998](https://www.cs.tufts.edu/comp/150FP/archive/bill-mckeeman/DifferentailTesting.pdf), [packetdrill, ATC 2013](https://research.google/pubs/packetdrill-scriptable-network-stack-testing-from-sockets-to-packets/), [QUIC interop, 2020](https://research.protocol.ai/publications/automating-quic-interoperability-testing/).
2. **Did manual effort kill it? — No; it limited coverage and maintenance, I.** Interop automation already worked. The labor is endpoint adapters, stateful test scenarios, adjudicating differences, and maintaining standards-to-tests mappings. **F:** TLS-Anvil identifies the difficulty of constructing an oracle across interacting parameters; its 2022 evaluation found 15 interop issues among other defects in 13 implementations. [TLS-Anvil, USENIX Security 2022](https://www.usenix.org/conference/usenixsecurity22/presentation/maehren).
3. **What flipped — F/I.** Agents can write adapters and failure-reducing scenarios. Current QUIC Interop Runner supports QUIC and WebTransport, so a generic hosted matrix is not missing. The September 14, 2026 rustls advisory documents a TLS encryption-boundary issue rejected by five other tested libraries: independent peers still expose meaningful mistakes in mature code. [Runner, checked 2026-10-28](https://github.com/quic-interop/quic-interop-runner), [rustls advisory](https://github.com/rustls/rustls/security/advisories/GHSA-2mjx-qc3c-rqvc).
4. **Oracle — Strong for a minimized compatibility discrepancy; weaker for blame, I.** Compare several independent peers, assert a specific standards obligation, and retain packet/application transcripts. Majority voting does not determine the correct implementation. Capabilities advertised as unsupported need explicit treatment.
5. **100× better model — I.** More valuable as a repair/adapter factory for obscure protocols and extensions; less defensible as a dashboard or generic test generator, which protocol maintainers can run themselves.
6. **Prior art — F.** QUIC interop, packetdrill, TLS-Anvil, 2025 Spec2Code mapping RFC requirements to code functions, and 2025 LLM-facilitated RFC-update differential analysis. These are neighboring pieces of a standards-change-to-reproduction workflow. [Spec2Code, ASE 2025](https://doi.org/10.1109/ase63991.2025.00174), [Wu et al., October 28, 2025 preprint](https://arxiv.org/abs/2510.24408). Mokav already uses execution feedback for LLM differential test generation on general program pairs; it is not a protocol implementation product. [Mokav, December 2025](https://www.sciencedirect.com/science/article/pii/S0164121225002407).
7. **Value — E.** SDK/protocol vendors might pay $10k–40k/year for maintained adapters and reproducible issue reports; 100 at $20k gives $2m/year. Standards communities' ability to pay is weaker than vendors'.
8. **Two-week proof — E.** Pick one HTTP/2 or QUIC extension already implemented by three peers. Write a Rust/TypeScript runner launching native local processes, a fixed set of standards-derived assertions, and an agent that adds one adapter and minimizes failures. Existing upstream suites are baselines; no Docker is needed for this proposed reduced harness.
9. **Demo / tweet / kill — E/I.** Tweet: “A standards change becomes a three-peer interop test, a minimal failing exchange, and a candidate patch.” Expert killer: “This is existing CI plus a coding agent, and your failures are permitted differences.” Kill if there are no actionable new cases beyond the upstream suites or adapters need continual expert handholding. **Disposition: valuable component, weaker independent bet.**

## 6. Database personalities and wire compatibility: the strongest bounded GrowOS analogue

1. **Idea / origin — F.** Brian Bruns began FreeTDS in early 1997 to make existing DB-Library software work on free systems through experimentally reconstructed TDS behavior. This was a client compatibility layer, not a complete database substitute. AWS's Babelfish proposal in December 2020 applied the server-personality idea to PostgreSQL: preserve TDS clients and much T-SQL while changing the underlying database. [FreeTDS history](https://www.freetds.org/userguide/FreeTDShistory.html), [AWS proposal, December 1, 2020](https://aws.amazon.com/blogs/opensource/want-more-postgresql-you-just-might-like-babelfish/).
2. **Did manual effort kill it? — It constrained completeness, not survival, F/I.** Babelfish's architecture needs hooks for transaction, trigger, and other SQL Server semantics. Its interoperability guidance documents interference between its PostgreSQL and TDS endpoints. Wire parsing alone is a small part of application compatibility. [Architecture](https://babelfishpg.org/docs/internals/software-architecture/), [interoperability guidance](https://babelfishpg.org/docs/usage/interoperability/). **I:** the expensive tail is exactly where repeated differential repair could help: catalog queries, casts, error behavior, collations, session settings, and rollback effects.
3. **What flipped — F/I.** There is concrete ongoing tail work: Babelfish 5.4.2, July 20, 2026, fixed a TVP issue that repeated the last row; 5.4.1 fixed skipped rows with concurrent UPDATE/OUTPUT. Doltgres reported 99% on its SQL Logic Test suite July 10, 2026, after baselining against PostgreSQL and correcting its runner. These are behavioral closure problems, but 99% of that suite is not 99% of PostgreSQL or customer applications. [Babelfish release notes](https://docs.aws.amazon.com/AmazonRDS/latest/AuroraPostgreSQLReleaseNotes/AuroraBabelfish.Updates.html), [Doltgres report](https://www.dolthub.com/blog/2026-07-10-doltgres-99-percent-sql-logic-tests/).
4. **Oracle — Strong within a pinned application/version envelope, I.** Run source and target against identical snapshots and operation sequences. Compare typed values, row ordering where specified, SQLSTATE/vendor errors, update counts, catalog results, transaction outcomes, and final state. For concurrency compare permitted histories, not a single observed interleaving. A live SQL Server/PostgreSQL/MySQL endpoint is much stronger than syntax conversion success.
5. **100× better model — I.** Makes broader personalities feasible and this old idea more valuable. It also makes patching cheap for incumbents. Durable value must be the customer's executable behavioral contract and reduced migration labor, not ownership of a wire parser.
6. **Prior art — F.** Babelfish; Dolt/MySQL and Doltgres/PostgreSQL; and AWS DMS generative schema conversion, launched December 1, 2024 with an “up to 90%” schema-conversion claim. That is vendor-reported schema coverage, not application equivalence. Current DMS documentation explicitly requires validation and excludes several constructs from generative conversion. [Dolt/MySQL and Doltgres background, April 16, 2025](https://www.dolthub.com/blog/2025-04-16-doltgres-goes-beta/), [DMS launch](https://aws.amazon.com/about-aws/whats-new/2024/12/aws-dms-schema-conversion-generative-ai/), [current scope/limitations](https://docs.aws.amazon.com/dms/latest/userguide/schema-conversion-convert.databaseobjects.html). Doltgres also runs PostgreSQL's own regression suite. [July 8, 2025](https://www.dolthub.com/blog/2025-07-08-doltgres-correctness-testing/). **I:** generic SQL translation is occupied; evidence-driven repair of one application's missing semantics remains a hypothesis to test against those products.
7. **Value — E.** Payor: an ISV/platform owner blocked on SQL Server→PostgreSQL migration, or a compatibility database vendor. Price a $10k–25k bounded pilot, then $50k–150k per completed migration/support envelope. Fifty $75k projects/year imply $3.75m/year, mostly services initially. Savings must exceed continued license/hosting cost and a conventional migration engagement; no sourced universal savings estimate is claimed.
8. **Two-week proof — E.** Obtain authorized dev endpoints for one source/target pair and one modest application. Days 1–3: Rust capture/replay and resets. Days 4–5: classify 20 reproducible mismatches. Days 6–10: agent patches three independent semantic gaps in the existing layer or compatibility functions. Days 11–14: hold out half the transactions, cross-feature tests, and post-write-state comparisons; measure human minutes and agent spend against a plain coding-agent baseline. Existing endpoints are a prerequisite; a local PostgreSQL/Doltgres substitute can test mechanics but cannot establish SQL Server migration success.
9. **Demo / tweet / kill — E/I.** Tweet: “This application failed on the replacement database. An agent grew three missing behaviors, checked against the original server and unseen transactions.” Expert killer: “Babelfish/DMS plus a normal agent already does this; you measured expressions, not application correctness.” Kill if fewer than 3 of 5 real migration blockers are representable by stable differential tests, if any accepted patch corrupts held-out final state, or if expert time falls by less than 50% versus that baseline. **Disposition: ONE bet, conditional on endpoint access and an actual blocked buyer.**

## 7. Learned/self-tuning databases and automatic indexing: do not put AutoAdmin in the graveyard

1. **Idea / origin — F.** AutoAdmin began at Microsoft in 1996; Chaudhuri and Narasayya's 1997 index-selection work used optimizer cost estimates and hypothetical designs to reduce expert physical-design work. Neo in 2019 learned plan construction from an existing optimizer and execution feedback. These are distinct proposals: automate configuration/indexing versus learn the optimizer itself. [AutoAdmin history/publications](https://www.microsoft.com/en-us/research/project/autoadmin/), [Neo, VLDB 2019](https://people.csail.mit.edu/tatbul/publications/neo_vldb19.pdf).
2. **Did manual effort kill it? — Mixed, I.** **F:** AutoAdmin technology shipped in SQL Server 7.0 in 1998; automatic indexing is commercially alive. **F:** a 2024 reproducibility study found PostgreSQL beating evaluated learned optimizers in almost all its experiments depending on splits; it documents training/encoding/integration problems. This supports engineering burden and brittle generalization, not “an otherwise solved optimizer lacked coders.” OtterTune's own site confirms its 2020–2024 death but does not establish manual effort as the cause. [AutoAdmin](https://www.microsoft.com/en-us/research/project/autoadmin/), [Lehmann et al., VLDB 2024](https://digitalcollection.zhaw.ch/bitstream/11475/30586/3/2024_Lehmann-etal_Learned-query-optimizers_VLDB.pdf), [OtterTune](https://ottertune.com/).
3. **What flipped — F/I.** Agents can run the monitor→diagnose→experiment→rollback workflow and adapt integrations. They cannot cheaply fabricate representative production data or eliminate expensive query executions. **F:** 2025 LLM4IA reports 5–10% improvement over its Extend advisor baseline on TPC-H/TPC-DS; a 2025 learned-optimizer paper applies conformal prediction to bound latency estimates and handle shifts. These are research results under their evaluations, not production guarantees. [LLM4IA, CIKM 2025](https://xmudm.github.io/files/Lyu25LLM4IA.pdf), [Liu et al., VLDB 2025](https://nexdig.usc.edu/project/reliable_LQO/).
4. **Oracle — Strong for result equivalence, weak/noisy for future cost, I.** Actual execution on representative snapshots checks candidates; existing plans are a fallback, not an optimal-plan oracle. Include writes, index-build time/space, cache effects, concurrency, and changing parameters. EXPLAIN's estimated cost cannot independently certify a tuning decision built from that same cost model.
5. **100× better model — I.** Improves search and diagnosis, but recurring optimizer integration likely absorbs it. A proprietary generic “database brain” is less defensible; representative evaluation and conservative rollback become more valuable.
6. **Prior art — F.** Bao's 2021 hint selection; Google's Kepler, which executes candidate plans and falls back on low confidence; Azure automatic tuning, which creates/verifies indexes; Supabase index_advisor; LLM4IA. [Bao](https://people.csail.mit.edu/tatbul/publications/bao_sigmod21.pdf), [Kepler](https://github.com/google/kepler), [Azure docs, checked 2026-10-28](https://learn.microsoft.com/en-us/azure/azure-sql/database/automatic-tuning-overview?view=azuresql), [Supabase docs](https://supabase.com/docs/guides/database/extensions/index_advisor).
7. **Value — E.** Teams with $20k/month database bills might pay $1k/month for independently demonstrated $3k/month savings. One hundred such accounts imply $1.2m ARR; a provider's included feature is the pricing ceiling. No evidence that this segment is underserved was found.
8. **Two-week proof — E.** On PostgreSQL, restrict changes to indexes and a small existing hint/configuration space. Use HypoPG/advisor output as candidates, materialize on a native local clone, then run mixed reads/writes under a fixed compute budget. Split by query template and time, compare existing advisors and budget-matched search, and include build/retraining amortization.
9. **Demo / tweet / kill — E/I.** Tweet: “The database proposes an index, tests tomorrow's workload slice, and rejects it when write amplification erases the read win.” Expert killer: “Your baseline was untuned and your holdout leaked templates.” Kill if existing advisors plus bounded search capture 80% of savings or the benefit disappears after build/inference cost and distribution shift. **Disposition: reject generic autonomous DBA; AutoAdmin was a success.**

## 8. Log-structured and workload-specialized storage: maintenance may flip; physics does not

1. **Idea / origin — F.** O'Neil, Cheng, Gawlick, and O'Neil's 1996 LSM-tree batched index changes to trade cheap sustained inserts for other access costs. Idreos et al.'s 2019 design continuums proposed unifying layouts to support stores that choose/transition designs according to workload and hardware. This is specialization through a design space, not an all-purpose faster store. [LSM paper, 1996](https://db.cs.berkeley.edu/cs286/papers/lsm-acta1996.pdf), [CIDR 2019 design continuums](https://vldb.org/cidrdb/2019/design-continuums-and-the-path-toward-self-designing-key-value-stores-that-know-and-learn.html).
2. **Did manual effort kill it? — LSM no; arbitrary per-workload engines partly, I.** **F:** RUM explicitly treats workload/hardware variation as a source of redesign and read/update/memory trade-offs. It is a conjecture, not a universal theorem with practical constants. **F:** RocksDB's tuning guide documents intertwined write-stall, flushing, compaction, and memory choices. [Athanassoulis et al., EDBT March 2016](https://research.ibm.com/publications/designing-access-methods-the-rum-conjecture), [RocksDB tuning guide](https://github.com/facebook/rocksdb/wiki/RocksDB-Tuning-Guide). **I:** maintaining many recovery paths and formats makes bespoke stores expensive; there is no sourced evidence that this is the only reason broad synthesis remained limited.
3. **What flipped — F/I.** ELMo-Tune-V2, February 24, 2025, already uses LLMs for workload synthesis, configuration, and dynamic tuning; it reports up to roughly 14× YCSB gains over defaults, but end-to-end gains of 34% for NebulaGraph and 26% for Kvrocks. StorageXTuner, October 28, 2025, already adds an agentic executor/search/reflection loop across four engines. These make the generic tuning pitch prior art. [ELMo-Tune-V2](https://arxiv.org/abs/2502.17606), [StorageXTuner](https://arxiv.org/abs/2510.25017).
4. **Oracle — Strong for a scoped logical API and declared durability contract; weak for optimal layout, I.** A map/SQLite/RocksDB reference, operation logs, permitted acknowledged-write prefixes, crash/restart tests, and corruption detection. A no-crash key/value match says nothing about fsync correctness. Benchmark speed is an objective, not a ground-truth design oracle.
5. **100× better model — I.** Makes niche codecs/layouts and their maintenance feasible; more valuable when a workload has stable unusual structure. Does not abolish read/write/space trade-offs, workload drift, or migration cost. Existing engine tuning is likely to absorb many wins.
6. **Prior art — F.** Dostoevsky adapted compaction across an LSM design space in 2018; design continuums anticipated self-designing stores; ELMo-Tune-V2 and StorageXTuner directly occupy agentic tuning. [Dostoevsky, SIGMOD 2018](https://nivdayan.github.io/dostoevsky.pdf). **I:** a new bet must change an engine's structure for a specific paid workload and outperform tuned existing engines, not defaults.
7. **Value — E.** A graph/logging vendor spending $2m/year on storage could pay $50k–150k/year for at least 20% all-in savings; 20 at $100k is $2m/year. Format migration and recovery support are part of the price.
8. **Two-week proof — E.** Implement one Rust append-only store for a fixed TTL/log workload, initially using existing durable components. Agent grows an index or codec against a logical reference. Week two: crash-boundary simulation, held-out skew/expiry mixes, and comparisons with tuned RocksDB/SQLite including compaction, disk bytes, and peak memory. This validates a narrow prototype, not production durability.
9. **Demo / tweet / kill — E/I.** Tweet: “A store grows around one workload, while every logical operation and crash outcome is checked independently.” Expert killer: “You benchmarked before compaction and omitted recovery.” Kill below 2× a relevant resource-efficiency gain against the tuned baseline or at any acknowledged-write-loss counterexample. **Disposition: reserve for a distinctive workload; reject generic agentic RocksDB tuning.**

## 9. Distributed-system verification: a genuine labor barrier with unusually direct 2026 competition

1. **Idea / origin — F.** Lamport's 1994 Temporal Logic of Actions represents concurrent behavior through state transitions and temporal properties. AWS's 2015 account describes practical TLA+ specification/model checking; Jepsen, operating since 2013, instead drives real systems through faults and checks operation histories. These are complementary design and implementation checks. [Lamport, May 1994](https://www.microsoft.com/en-us/research/publication/the-temporal-logic-of-actions/), [AWS, CACM April 2015](https://www.amazon.science/publications/how-amazon-web-services-uses-formal-methods), [Jepsen analyses/method](https://jepsen.io/analyses).
2. **Did manual effort kill it? — It limited spread, not usefulness, F/I.** AWS reports seven teams finding value in 2015, while emphasizing the skill of choosing a faithful model. The code/model correspondence gap was explicit. Specula's authors say their earlier real-system specifications took months of expert work. [AWS full paper](https://assets.amazon.science/67/f9/92733d574c11ba1a11bd08bfb8ae/how-amazon-web-services-uses-formal-methods.pdf), [Specula, §1, August 3, 2026 revision](https://arxiv.org/html/2607.25333v2).
3. **What flipped — F/I.** Specula already generates TLA+ models/invariants, instruments code, validates traces, and reproduces violations; its authors report 249 bugs across 48 systems and runs taking 1.43–9.86 hours. These are preprint-author results, not independently reproduced here. **F:** Jepsen's October 16, 2026 release fixed a safety bug in a workload/checking dependency, a useful reminder that the oracle itself needs checking. [Specula, §§3–5](https://arxiv.org/html/2607.25333v2), [Jepsen news](https://jepsen.io/).
4. **Oracle — Strong for a formal property inside a model; weak unless tied to implementation, I.** TLC plus independently reviewed invariants; trace conformance; linearizability/serializability checkers; deterministic fault execution. A reference server can also violate the promised consistency contract, so “match the old server” cannot be the sole distributed-correctness criterion. Test passing does not establish all executions.
5. **100× better model — I.** Makes extracting and maintaining models much more useful. It makes “LLM writes TLA+” a commodity. Independent invariants, adversarial traces, reproduction, and process integration retain value.
6. **Prior art — F.** Specula is direct prior art for the whole agentic model/check/reproduce concept. Antithesis already supplies deterministic whole-system fault testing; its December 3, 2025 announcement reports a $105m Series A and customers including Jane Street and MongoDB. FoundationDB's 2021 paper explains its simulation practice; AWS's P tool is used across flagship services. [Antithesis announcement](https://tools.prnewswire.com/en-us/live/20823/release/20251203EN37581), [FoundationDB, SIGMOD 2021, §6.2](https://www.foundationdb.org/files/fdb-paper.pdf), [P project](https://p-org.github.io/P/). Funding is evidence of established competition, not market size or proof of effectiveness.
7. **Value — E.** Infrastructure vendors might pay $30k–100k/year for maintained models and regression traces; 50 at $60k is $3m/year. Jepsen already sells analysis/training, and platform vendors already bundle correctness tools. A new entrant needs a specific underserved integration.
8. **Two-week proof — E.** On one small open-source lease/queue service, freeze externally reviewed safety properties and seeded historical bugs. Use existing TLC/Jepsen or a local Rust history checker; let an agent build the model and trace adapter. Compare with Specula and a plain agent under equal cost. Reproduce failures in unmodified logic, beyond harness instrumentation.
9. **Demo / tweet / kill — E/I.** Tweet: “A passing service gets a model, a failing execution, and a replayable real-code counterexample.” Expert killer: “Specula and Antithesis already cover this, and your agent can weaken invariants.” Kill if it needs substantive invariant relaxation, cannot reproduce failures, or offers no deployment/coverage advantage over existing tools. **Disposition: reject generic autonomous TLA+/Jepsen product.**

## 10. Server specialization per application: an old good idea with strong ordinary alternatives

1. **Idea / origin — F.** Pu, Massalin, and Ioannidis's Synthesis kernel generated specialized routines for known situations, factoring invariants and collapsing layers. MIT's 1990s Cheetah/XIO work applied application-specific abstractions to high-performance servers. This is eliminating unnecessary generality using known context, not merely deploying a smaller VM. [Synthesis, Winter 1988](https://www.usenix.org/legacy/publications/compsystems/1988/win_pu.pdf), [Ganger's Cheetah project account, 1996-era](https://pdos.csail.mit.edu/~ganger/servers.html).
2. **Did manual effort kill it? — Plausible contributor, causal evidence incomplete, I.** Creating/maintaining specialized runtimes and integrating extensions is costly. **F:** Katana's 2006 server-framework paper explicitly calls writing OS extensions difficult. This supports the burden, but does not prove why Cheetah/Synthesis did not become a universal server-building model. Compiler improvements, protocol changes, and operational tooling are competing explanations. [Katana, Berkeley technical report, 2006, §7](https://www2.eecs.berkeley.edu/Pubs/TechRpts/2006/EECS-2006-34.pdf).
3. **What flipped — F/I.** Agents can construct application-specific fast paths and fill compatibility gaps. But a compiler may already capture much of the win: weval's June 2025 paper specializes existing interpreters with lightweight annotations; its repository reports 3–5× JavaScript speedups over the generic interpreter. This is not a comparison with V8 JIT or a whole-server improvement. [Fallin and Bernstein, PLDI 2025](https://c1f.net/pubs/pldi2025_weval.pdf), [weval](https://github.com/bytecodealliance/weval).
4. **Oracle — Strong for pinned application semantics, incomplete for operations/security, I.** Original server responses, side effects, error paths, restart behavior, and application test suites. Replaying only successful requests would encourage deleting authorization, rate limiting, or rare error behavior. Compiler equivalence and production telemetry add independent signals.
5. **100× better model — I.** Makes per-application implementations more plausible, especially if enough CPU/memory is wasted on stable generality. A generic compiler/runtime can also exploit the stronger model; maintenance differentiation must survive that comparison.
6. **Prior art — F.** weval/Bytecode Alliance, mature partial-evaluation/JIT approaches discussed in its paper, and Unikraft's app-specific OS/cloud. Unikraft's December 2025 Prisma customer story claims over 100k isolated databases/server and image size falling from 280MB to 61MB; this is vendor/customer-reported density and sizing, not independent evidence that rewriting an application's server logic is worthwhile. [Prisma story, December 8, 2025](https://unikraft.com/customer-stories/prisma-postgres).
7. **Value — E.** A hosting company with $5m/year of applicable compute could fund $100k/year for verified 10% savings. Ten such customers imply $1m/year. Small applications rarely justify a maintained bespoke server.
8. **Two-week proof — E.** Choose one stable, CPU-bound service; keep existing HTTP/TLS/authentication libraries. Agent specializes routing/serialization or a measured expensive adapter in Rust. Compare the original implementation, PGO/LTO, and any applicable specialization framework on held-out request/error sequences and equal load-generator capacity.
9. **Demo / tweet / kill — E/I.** Tweet: “The service sheds general-purpose work while a replay harness checks every response and state change against the original.” Expert killer: “PGO or a serializer swap gets the same gain without maintaining a second server.” Kill below 30% all-in CPU/memory savings, or if ordinary optimization recovers 80% of it. **Disposition: conditional technical niche, weak evidence of an economy-wide labor flip.**

## 11. Mainframe/COBOL/CICS migration: strong oracle economics, already an incumbent battleground

1. **Idea / origin — F.** Fowler's June 29, 2004 Strangler Fig essay proposed replacing a critical system incrementally and preserving required old behavior, sometimes even bugs. The networking/storage form is to replace one transaction or batch slice while the incumbent remains executable. This is one documented lineage, not a claim to originate all mainframe migration. [Original Strangler Fig Application](https://martinfowler.com/bliki/OriginalStranglerFigApplication.html).
2. **Did manual effort kill it? — Strong labor burden, but no death, F/I.** IBM's FSE 2025 paper explicitly identifies manual validation of COBOL→Java translation as time-consuming and labor-intensive, and automates functional-equivalence tests from symbolic execution. AWS's December 2025 launch says testing typically consumes over 50% of modernization project duration; that number is a vendor claim. Neither proves that language translation alone was the historic bottleneck. [IBM, July 28, 2025](https://research.ibm.com/publications/automated-testing-of-cobol-to-java-transformation), [AWS testing automation, December 1, 2025](https://aws.amazon.com/about-aws/whats-new/2025/12/transform-mainframe-testing-automation/).
3. **What flipped — F/I.** Generating adapters, translation candidates, test inputs, and discrepancy repairs can move into unattended loops. IBM already supports original COBOL execution followed by Java equivalence checking and exported JUnit tests. **I:** the attractive residual burden is capturing CICS/DB2/VSAM and external side effects, not generating attractive Java. No independently established 2026 full-system migration cost multiplier was found. [IBM Validation Assistant workflow, checked 2026-10-28](https://www.ibm.com/docs/en/watsonx/watsonx-code-assistant-4z/1.1?topic=validate-using-z-validation-assistant).
4. **Oracle — Strong if the actual environment is runnable and observable, I.** Capture transaction inputs plus before/after DB and file state, CICS commit/rollback boundaries, emitted messages, return codes, decimal/encoding semantics, and batch-order dependencies. A paragraph-level mock is insufficient for whole-transaction equivalence. The old program is an oracle for existing behavior, not for deciding which behavior the business wants to change. A GnuCOBOL run cannot certify IBM Enterprise COBOL or CICS semantics.
5. **100× better model — I.** Makes progressively larger replacements economical. It increases demand for the remaining execution evidence, environment access, and cutover process. Generic translation software becomes less defensible.
6. **Prior art — F.** IBM watsonx Code Assistant for Z combines understand/refactor/transform/validate; AWS Transform for mainframe adds automated test planning, collection scripts, and functional-test environments. These directly occupy broad agentic migration and validation. IBM also reuses recorded integration tests for transformed services. [IBM current overview](https://www.ibm.com/docs/en/watsonx/watsonx-code-assistant-4z/2.x?topic=welcome-overview-watsonx-code-assistant-z), [IBM recorded-test demonstration](https://mediacenter.ibm.com/media/Modernize%2BApplications%3A%2BAccelerate%2BCOBOL%2Btransformation%2Bto%2BJava%2Bwith%2BWCA4Z/1_vigw5fvh). **I:** an independent vendor would need a specific missing CICS/VSAM evidence-capture capability or channel partnership.
7. **Value — E.** Banks, insurers, public agencies, and systems integrators pay $25k–100k for a bounded transaction pilot; $100k–500k/year for a supported capture/validation pipeline. Twenty $150k deployments imply $3m/year. Procurement, mainframe specialist time, and fixture access will constrain a single engineer more than code generation.
8. **Two-week proof — E.** With an existing customer's authorized captured transaction slice, build a Rust fixture runner and a translated candidate. Compare packed decimals, files, DB writes, and rollback effects; agent repairs discrepancies against frozen outputs. If no mainframe access exists, use a native GnuCOBOL batch fixture to test the mechanism and label the result accordingly. Do not present a laptop unit demo as CICS migration evidence.
9. **Demo / tweet / kill — E/I.** Tweet: “The old transaction stays the judge: migrated code must reproduce outputs, writes, messages, and rollback behavior on unseen fixtures.” Expert killer: “IBM/AWS already do this, and your mocks hide the behavior that makes mainframes hard.” Kill if real side effects cannot be captured by day 3, or incumbent tools cover the same transaction with comparable specialist time. **Disposition: top-three economics, crowded and access-constrained.**

## 12. S3 and API/SDK compatibility: a live ecosystem with a costly moving tail

1. **Idea / origin — F.** Eucalyptus's Walrus was already an S3-interface-compatible store in the late-2000s private-cloud work; Rich Wolski's LISA 2009 presentation shows Walrus as the S3 component. The intent was reusing cloud clients/tooling against another implementation. [Wolski, LISA 2009](https://www.usenix.org/legacy/events/lisa09/tech/slides/wolski.pdf), [Eucalyptus architecture documentation](https://docs.eucalyptuscloud.org/eucalyptus/5/admin_guide/managing_system/system_concepts/).
2. **Did manual effort kill it? — No; the ecosystem succeeded, I.** Compatibility still has an expensive tail. **F:** Cloudflare's October 14, 2026 R2 matrix lists operation/feature differences, including checksum combinations and unsupported versioning/IAM-style bucket operations. Ceph's unofficial s3-tests even marks cases that fail on AWS itself. This is evidence that API-name compatibility is not behavioral identity. Some gaps are deliberate product choices, not missing engineering. [R2 matrix](https://developers.cloudflare.com/r2/api/s3/api/), [s3-tests](https://github.com/ceph/s3-tests).
3. **What flipped — F/I.** Agents can add header/error/SDK corner cases more cheaply; the installed ecosystem makes preserving clients valuable. AWS's 2026 twenty-year S3 account reports over 500 trillion objects and over 200m requests/sec. These establish scale, not the obtainable revenue of a clone. [AWS, March 2026](https://aws.amazon.com/blogs/aws/twenty-years-of-amazon-s3-and-building-whats-next/). **I:** compatibility costs can fall while durability engineering, storage economics, and regional operations remain expensive.
4. **Oracle — Strong for bounded API semantics, weak for durability/availability, I.** A real, authorized AWS test endpoint plus pinned SDK versions, Ceph tests, and a declared source region/storage class. Compare status/error codes, signed request handling, pagination, multipart state, checksums, conditions, and post-operation object state. Normalize request IDs, timestamps, and other deliberately variable fields. A local clone is a secondary comparison, not a substitute AWS oracle.
5. **100× better model — I.** Makes exact subsets easier to implement; reduces differentiation of the API frontend. Increases the value of a maintained SDK/behavior corpus as AWS and clients evolve. It does not make a storage backend durable by imitation.
6. **Prior art — F.** Ceph's s3-tests, MinIO's compatibility work, Cloudflare R2, and SeaweedFS's integration with the Ceph tests already cover implementation and conformance workflows. [MinIO compatibility product account](https://min.io/product/s3-compatibility), [SeaweedFS compatibility harness](https://github.com/seaweedfs/seaweedfs/blob/master/test/s3/compatibility/README.md). MinIO's broad vendor claims are not adopted here as independent completeness measurements. **I:** generic S3 clones and generic test dashboards are already well supplied.
7. **Value — E.** Store vendors might pay $20k–80k/year for supported SDK compatibility closure; 30 at $40k gives $1.2m/year. Alternatively an on-prem customer pays for its needed storage constraints, where compatibility is a purchase prerequisite rather than a separately priced product.
8. **Two-week proof — E.** Select one existing store and one SDK-driven workload, such as multipart/checksum interaction. Build a native Rust or TypeScript stateful comparator, run public/local fixtures, and use an already authorized AWS endpoint only when supplied. Agent repairs a gap in the existing frontend. Without the AWS endpoint, explicitly downgrade the oracle and withhold a claim of AWS equivalence.
9. **Demo / tweet / kill — E/I.** Tweet: “One S3 workload grows the compatibility it needs, checked against pinned SDK behavior and the source API.” Expert killer: “The gap was intentional or already covered by Ceph tests; the hard part is durable storage.” Kill if unmodified mature stores already pass the workload, or repair requires promising durability/availability not established by the harness. **Disposition: reject another general S3-compatible store; possible vendor feature.**

## Ranked top three

**I — Ranking criterion:** a documented manual tail, an independent executable oracle, attainable buyer value, and a two-week discriminating experiment. This ranks experiments worth running, not demonstrated companies. All three have serious incumbent competition.

1. **#6 — Workload-specific database personality closure.** Best alignment with GrowOS: the old server runs; a concrete application exposes the required surface; many faults can be reduced to bounded semantic work. Start on an existing compatibility layer. **Confidence: medium on technical fit, low-to-medium on an unoccupied business wedge.** A blocked migration sponsor and a baseline comparison are mandatory.
2. **#4 — Verified implementation of an underserved protocol extension.** Strongest direct 2026 evidence that proof/interop loops can lower expert supervision. Generic TLS is occupied; a small neglected extension with independent peers and a maintainer willing to pay is the plausible wedge. **Confidence: medium on labor flip, low on generic novelty.**
3. **#11 — Mainframe transaction equivalence and side-effect capture.** Largest plausible value per deployment, strong original-system oracle when accessible, and documented validation labor. IBM and AWS are direct competitors; access and integration could make it a consulting business. **Confidence: medium on value, low on a solo entrant's access and differentiation.**

**I — Remaining order:** #2 P4 target adaptation; #8 genuinely workload-specific storage; #5 protocol interop/repair adapters; #3 user-space stack compatibility; #10 server specialization; #9 generic distributed verification; #7 generic tuning/indexing; #12 general S3 replacement; #1 active-network capsules. Low placement can reflect existing success and competition, not technical inferiority.

## The ONE bet

**I — Grow an application's missing database personality, with the incumbent database as judge.** Start with one repeatable SQL Server→PostgreSQL/Babelfish migration blocker, not a promise to emulate every SQL dialect. The deliverable is a maintained behavioral envelope for a named application/version: replayable source/target evidence, accepted patches in a supportable layer, held-out transactions, and explicit unresolved differences. Prefer upstreamable fixes over a private database fork.

**I — Why this survives a much better model:** generating compatibility code becomes easier for everyone, but acceptance still requires the customer's actual semantics, state resets, representative transactions, and a reliable comparator. This does not establish a moat: if a standard coding agent plus existing tools reproduces the result, the machinery should be abandoned or shipped as an open-source integration.

**E — Two-week decision protocol, one engineer:**

- **Days 1–3:** sponsor supplies existing dev endpoints and a small application. Freeze versions, fixtures, allowed normalizations, and final-state comparisons. Identify five genuinely blocked behaviors. If access or reproducibility fails, stop this experiment; a synthetic corpus is not equivalent evidence.
- **Days 4–5:** build capture/replay and shrinking. Hold out whole transactions/templates and edge-case families, not random near-duplicates. Record all exclusions. Start two budget-matched tracks from the same clean code: ordinary coding-agent-assisted repair versus the structured fault→repair→differential-accept loop. Keep each track's patches and diagnosis out of the other's context; charge all additional harness construction to the structured approach.
- **Days 6–10:** repair three independent gaps. The agent can edit implementation code; the acceptance suite and final-state comparator stay outside its write authority. Record human diagnosis/review minutes, model spend, build/test time, and subsequent regressions.
- **Days 11–14:** run unseen operations, rollback and session interactions, typed-result comparisons, and realistic performance sanity checks. Include an erroneous-result mutation test so a comparator that ignores types/errors/writes cannot look successful.
- **Continue only if:** at least three real blockers are closed; zero accepted state-corruption cases occur in holdout; expert time drops by at least 50% including harness work; and the sponsor prefers a paid bounded pilot to the incumbent workflow. These are E decision thresholds, not observed outcomes. A zero-failure holdout remains finite evidence.

**E — Commercial gate:** quote the sponsor $10k–25k for the next bounded pilot and ask which existing migration expense it replaces. Do not infer willingness to pay from a large database bill or from praise of the demo. Fifty hypothetical projects are a sizing scenario, not a sourced market count.

**I — The expert reply that should end this bet:** “Run DMS/Babelfish plus my existing tests and a normal agent on the same blockers. Your special loop saves no additional expert time, or the remaining failures are environmental and organizational.” The experiment above is designed to make that reply decisive.

## Five-line TL;DR

1. **I:** The useful graveyard is the long tail of compatibility, not an inventory of technically interesting old systems.
2. **F/I:** Active networks lacked a driving use case; AutoAdmin, LSMs, interop automation, and S3 compatibility largely succeeded rather than died.
3. **F:** 2025–2026 prior art already includes agentic protocol verification, TLA+ modeling, storage tuning, and original-versus-translated COBOL testing.
4. **I:** The best experiment grows one application's database compatibility against its original server, checking typed results, errors, and state effects.
5. **E:** Kill it unless three real blockers close with zero holdout state corruption and at least 50% less expert time than existing tools plus a normal agent.

## Rejected ideas and why

- **#1 Arbitrary active-network capsules:** no labor-only death or convincing new deployment incentive; operator-controlled successors already exist.
- **#2 Generic English→P4 generation:** direct 2025 prior art; target-porting remains interesting only with hardware/vendor access and a buyer.
- **#3 Fresh general-purpose user-space TCP:** mature reusable stacks and Linux are formidable; polling, sharing, and operations survive cheap code.
- **#4 Generic verified TLS generator:** Everest, Bert13, and 2026 agentic SPARK are direct prior art; retain only a paid, unsupported extension.
- **#5 Generic protocol interop dashboard:** existing runners already automate matrices; adapter maintenance and actionable repair are the residual work.
- **#6 Universal PostgreSQL/MySQL/SQL Server replacement:** the compatibility surface is too broad; retain only application-scoped closure on an existing engine/layer.
- **#7 Autonomous DBA/learned optimizer/automatic indexing:** AutoAdmin was not dead, current products and papers already automate much of it, and performance oracles remain costly/noisy.
- **#8 Generic agentic RocksDB tuner or bespoke engine for every app:** direct 2025 tuning prior art and recovery/format obligations; require structural advantage over a tuned engine.
- **#9 Generic autonomous TLA+/Jepsen service:** Specula already models, trace-checks, and reproduces; Antithesis and Jepsen already sell adjacent acceptance infrastructure.
- **#10 Per-app server rewrite without a measured hotspot:** compilers, PGO, serializers, and specialized deployment can erase the benefit with much less maintenance.
- **#11 Generic COBOL→Java conversion:** IBM/AWS already offer transformation plus validation; retain only a demonstrably missing transaction-evidence capability.
- **#12 Another general S3-compatible store:** compatibility ecosystem already exists; cheap frontend implementation does not supply durable storage or operational differentiation.
