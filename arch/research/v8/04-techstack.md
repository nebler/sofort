# The right tech stack for portable capsules

Research date: **2026-10-27**. Scope: research only; this report is the only repository file written. **F** = sourced fact, including repository evidence; **M** = measured in this investigation; **I** = inference or proposed design; **E** = estimate. External sources were checked on 2026-10-27; release/publication dates are stated where relevant. Decimal bytes and binary KiB/MiB are distinguished.

**I — Recommendation: qualify quickjs-ng 0.17.0 as a single-memory wasm32 core reactor, built with wasi-sdk/clang, driven by a TypeScript host that returns from Wasm at guest `await` boundaries.** Keep Bellard QuickJS 2026-06-04 as the reproducible baseline and runner-up. Use neither JSPI nor Asyncify on the normal tool path. Store versioned, content-addressed checkpoints; use zstd-3 for server storage and gzip for the universal exchange path. Keep the native Mac controllers in TypeScript compiled with scriptc; initially let them own a Node/V8 execution process, rather than making scriptc's Wasm translator the isolation boundary.

**I — Two qualifications change the decision.** First, the local benchmark finds an allocation-accounting advantage for ng that matters more than its modest size/latency penalty. Second, “V8 cannot snapshot mid-await” is an inaccurate categorical claim: a controlled Node startup snapshot preserved and resumed an awaited closure here. The missing V8 capability is a supported, portable checkpoint interface across independently managed hosts, including browsers and workerd.

## 1. Starting evidence and the checkpoint contract

**F — Repository evidence, not new measurements:** [the Oct 25 Wasm report](../portability/02-wasm.md) and its read-only evidence at `~/sofort-local-evidence/portability-wasm-2026-10-25/` demonstrate Bellard 2026-06-04 parked on a tool Promise in Wasmtime, then restored into Node, Chromium, local workerd and a local Dynamic Worker. Closures, cycles, Map and typed arrays survived; forks diverged without re-emitting the pending request. Its reactor was 966,584 bytes, its parked 2 MiB image about 100 KB gzip, and its Asyncify version 1,517,095 bytes. This research does not repeat that full migration matrix for ng.

**I — Freeze the execution contract before choosing convenient wrappers:** one instance owns one QuickJS runtime/context; no native filesystem/network APIs, shared memory, threads, mutable function table, externally owned ArrayBuffers, host object references or `externref` values in durable state. Compile the interpreter and bridge once; evaluate guest JS inside it. The guest Promise resolver and continuation remain in linear memory. The synchronous `emit(ptr,len)` import copies bounded bytes into a host queue and returns; the host executes tools after the outer Wasm call returns. A bounded `pump` drains guest jobs until completion, a resource yield, or waiting for input. Only checkpoint after all Wasm frames have returned and the relevant job queue is quiescent.

**F/I — Memory alone is insufficient in general.** Wasm memories, globals and tables are distinct state, and JSPI continuations are not exposed as memory bytes. The checkpoint must include the memory length and contents, every supported mutable global (including `__stack_pointer`), stable host protocol state and journal cursor. The module's immutable table is reconstructed from the exact module. Reject unsupported state rather than silently omitting it. See [Wasm JS interface, 2026-10-27 draft](https://www.w3.org/TR/2026/CRD-wasm-js-api-2-20261027/) and [JSPI's mechanism](https://v8.dev/blog/jspi).

**F — Positioning constraint:** [Linux same-host memory results, Oct 27](../../jitk/bench/RESULTS-LINUX-MEMORY-2026-10-27.md) put jitk shard and Hyperlight around the same marginal memory, about 0.5 MiB for these small workloads. No memory superiority over either follows from the Wasm spike's Mac RSS. [The usermode](../portability/01-usermode.md) and [hardware-reach](../portability/03-hardware-reach.md) reports describe different isolation/ISA constraints. This recommendation adds a software-isolated portable tier; it does not make native jitk RAM portable. It supports [demo.md §§9–10](../../../demo.md)'s file-like computers without borrowing the hardware tier's guarantees.

## 3. Small local benchmark: what actually decided the engine

**M — Environment and procedure:** Apple M4 Pro, arm64, Darwin 25.6.0; Node **24.22.1**, V8 **13.6.233.17-node.58**; wasi-sdk **34.0** (clang 23.1.0-wasi-sdk). Scratch: `/tmp/v8-research-techstack/`. No Docker, Linux VM, network tool execution, production deployment or full executor was used. Six final processes ran sequentially in order Bellard/ng, ng/Bellard, Bellard/ng. Each instance warmed for 2,000 return-plus-tool pairs, then seven batches per case: 2,000 return executions, 2,000 tool round trips, or four integer-loop executions. The table gives the median of three process medians; brackets give those three medians' range. Host contention was not controlled, and these are not tail-latency/SLO measurements.

**M — Build comparability:** reused the earlier spike's `bridge.c` unchanged, identical `-O2 -fwrapv -funsigned-char`, assertions retained, 512 KiB C stack, 2 MiB initial/32 MiB maximum memory, 16 MiB QuickJS limit, and stripped symbols. Both use switch dispatch: Bellard's `__EMSCRIPTEN__` branch and ng's `EMSCRIPTEN` branch. Bellard compiles `quickjs.c,dtoa.c,libregexp.c,libunicode.c,cutils.c`; ng compiles the first four (cutils is header-based). Bellard's unused `setjmp.h` include was removed in the scratch copy, as in the old spike; ng already comments it out. This is a matched bridge comparison, not a contest between each project's maximally optimized release recipe. No LTO, `wasm-opt` or Wizer applied.

**M — Work included:** the return case parses/evaluates an async function and drains jobs. Tool execution emits JSON, copies/decodes/parses it in Node, obtains the request ID, calls a reply export that evaluates `settle(id,1)`, pumps jobs and produces `2`. There is no I/O wait, full policy dispatcher, storage, worker messaging or network. Final results are checked per case; CPU result is `-220441792`. The harness does not retain every frame as the old benchmark did. Do not present the lower timings as an improvement to the production system or substitute them for the Oct 25 host comparisons.

**M — The deciding additional probe:** with the same 16 MiB `JS_SetMemoryLimit`, retain 22,000 `new Uint8Array(1024)` values. Bellard returned normally with all 22,000 retained, **25,923,476 B reported JS heap** and **29,032,448 B linear memory**. ng threw **`InternalError: out of memory`**, reporting **15,515,171 B heap**, **17,760,256 B linear memory**. The selected ng WASI allocator calls `malloc_usable_size`; the selected Bellard branch returns zero usable size. This is evidence that the existing Bellard port's stated engine limit is ineffective, not proof that upstream Bellard cannot be fixed or that ng has complete resource containment. JS-accounted heap and total linear memory differ, so ng exceeding 16 MiB linear memory is not itself a limit violation. [ng allocator source](https://github.com/quickjs-ng/quickjs/blob/v0.17.0/cutils.h), [prior port caveat](../portability/02-wasm.md).

**I — Interpretation:** trivial return performance is effectively tied; Bellard is ~5% faster on this bridge's tool path and ~20% lower wall time on this one integer loop. ng costs ~9.3% more raw code and ~15 KB more compressed parked state. Prefer ng's stronger maintenance/testing and currently working accounting, then qualify stack, interruptions, OOM cleanup and cross-host snapshots. Do not generalize this integer result to all JS workloads or count the microbenchmark as an engine security audit.

**M — Identity/reproducibility:** Bellard module SHA-256 `e04a49a7b6e06d41ff838514fb3eae394029a992b745fe583a2b9fc03c3b5ccb`; ng `5c99a4584265826493e937604b082973c57eb67d8501e89f6629f297e74a4571`. Small retained scratch includes `build.ts`, `bridge.c`, `bench.ts`, `final-{bellard,ng}-{1,2,3}.json`, `limits.ts`, `limits.json`, `compress.ts`, `compression.json`, `v8-await.cjs`, and `scriptc-coverage.log`. `build.ts` uses the read-only old evidence's SDK and Bellard source and the ng v0.17.0 tarball; its per-engine JSON records exact compiler arguments. Recreate ng source with `curl -L https://api.github.com/repos/quickjs-ng/quickjs/tarball/v0.17.0` and extract to scratch `ng/`; run `node build.ts`, then `node bench.ts bellard` / `node bench.ts ng`. Large scratch sources, binaries and memory images were removed at the end; all decision numbers and identities are retained here.

## 4. Plain V8: a real awaited-closure snapshot, but not the required API

**M — Counterexample to “V8 cannot snapshot mid-await”:** on Node 24.22.1 this build script succeeds. The first process leaves a Promise unresolved; the restored process supplies `35` and prints **`resumed 42`**. The captured object survives. This is a startup-snapshot construction experiment, not an ordinary running Node worker checkpoint.

```js
// v8-await.cjs
const { startupSnapshot } = require('node:v8');
(async () => {
  const retained = { x: 7 };
  const reply = await new Promise(r => globalThis.resume = r);
  console.log('resumed', retained.x + reply);
})();
startupSnapshot.setDeserializeMainFunction(() => globalThis.resume(35));
```

```sh
node --snapshot-blob=/tmp/v8-research-techstack/v8-await.blob \
  --build-snapshot /tmp/v8-research-techstack/v8-await.cjs
node --snapshot-blob=/tmp/v8-research-techstack/v8-await.blob
```

**F — What the public interfaces actually provide:** `v8.serialize` follows structured-clone-like value serialization, not arbitrary functions/closures. DevTools heap snapshots are diagnostic JSON, not executable restores. Node startup APIs operate during snapshot building and register serialization/deserialization callbacks to reacquire resources. V8 C++ `SnapshotCreator` creates a **startup** blob for an isolate prepared for serialization, with embedder callbacks/external references; current context serializer checks expect an empty microtask queue. Snapshots are trusted, build/version dependent. None of these interfaces promises to capture a currently executing native JS stack, OS/tool operations, host scheduling or browser APIs. [Node V8 APIs, current docs](https://nodejs.org/api/v8.html), [SnapshotCreator](https://v8.github.io/api/head/classv8_1_1SnapshotCreator.html), [context serializer](https://github.com/v8/v8/blob/main/src/snapshot/context-serializer.cc), [snapshot format architecture](https://github.com/v8/v8/blob/main/docs/snapshot/architecture.md).

**I — Correct 2026 conclusion:** an `await` continuation can live on the V8 heap too. A deliberately designed native V8 embedder may serialize selected quiescent contexts, rebind tool handles and constrain versions. That is a meaningful server-only alternative, not a physical impossibility. However, ordinary web JavaScript cannot call `SnapshotCreator`; no supported equivalent exposes an arbitrary browser/workerd isolate as a portable blob. Node's startup test does not establish arbitrary live snapshotting, cross-version compatibility or portability to those embedders. Guest-engine-in-Wasm buys control of the durable heap and ABI independent of the host's V8 build. Checkpoint only at supported guest boundaries, not “at any instruction.”

## 5. Build toolchain and module format

**I — Main build:** use pinned **wasi-sdk/clang** to build a reactor with `_initialize`, bridge exports, a single exported memory and explicitly listed mutable globals. Ship a core module with minimal imports; WASI Preview 1 is a build/libc convenience, not the application capability model. Replace unnecessary `fd_*` imports with explicit failures or eliminate the dependency. Route time, entropy and logging through journaled capsule imports. Keep the interpreter, bridge and generated bootstrap as reproducible artifacts with recorded source/toolchain hashes. [wasi-sdk](https://github.com/bytecodealliance/wasi-sdk) supplies clang/lld and a WASI sysroot; it does not supply a browser's system calls.

**I/F — Emscripten is the runner-up:** its established QuickJS TS bindings, packaging, debug variants and Asyncify integration reduce ordinary embedding work. But host-side handles, Promise resolvers and loader objects created by wrappers are additional state; copying their heap is not part of a Wasm memory checkpoint. A snapshot-oriented bridge must use stable integer IDs and rebuild host wrappers. The default synchronous variant already supports ordinary guest async functions; “sync” does not mean the guest cannot `await`. [quickjs-emscripten packaging and variants](https://github.com/justjake/quickjs-emscripten). Avoid default filesystem/network glue and avoid assuming an arbitrary `.wasm` package is already checkpointable.

**F/I — Binaryen:** `wasm-opt` can reduce/optimize the module and perform Asyncify. Benchmark `-O2` versus `-Oz` after building the production bridge; interpreter dispatch can trade speed for size. Freeze and hash **the final transformed bytes** as the checkpoint executable identity: optimizations may change data layout, table indices or globals. Do not restore old memory into a separately optimized build. [Binaryen](https://github.com/WebAssembly/binaryen) is actively maintained, Apache-2.0; LLVM uses Apache-2.0 WITH LLVM-exception, and Emscripten has MIT/University of Illinois licensing plus dependencies. Retain an artifact-level dependency/notice manifest, not a single licence string for the whole SDK. [LLVM licence](https://llvm.org/LICENSE.txt), [Emscripten licensing](https://emscripten.org/docs/introducing_emscripten/emscripten_license.html).

**F/I — Wizer pre-initialization:** use **`wasmtime wizer`**, where development has moved from the standalone Wizer repository. Initialize only a tenant-free engine/bootstrap with deterministic inputs; Wizer runs initialization and rewrites memory/global initial state into a module. It is a cold-start optimization, not a generic external-resource or active-stack serializer. Never bake live credentials, guest state, time or random seeds into the shared template. The Oct 25 spike measured cold compile+instantiate+init+first-return medians of **36.37 ms →21.47 ms**, excluding Node process startup and file/network reads, but module gzip grew **332,133→372,412 B**. Test the network/startup trade-off; cache compiled modules and initialized templates independently. [Wizer's upstream move and caveats](https://github.com/bytecodealliance/wizer), [local evidence](../portability/02-wasm.md).

**F/I — Core module now; component wrapper later:** components/WIT improve typed interfaces, composition and WASI ecosystem interoperability. They do not define portable snapshots of external resource handles or scheduler state. JS hosts can run transpiled components through jco and shims; this introduces generated core modules, adapters and JS-managed resources that also need accounting. Keep the capsule's durable execution unit one core module, optionally describe/wrap the tool ABI in WIT for Wasmtime consumers. Do not make Fetch/Streams/WASI HTTP resources part of the durable capsule. [jco's transpilation and shims](https://github.com/bytecodealliance/jco), [StarlingMonkey's component orientation](https://github.com/bytecodealliance/StarlingMonkey).

### Metering must survive a compromised guest engine

**F/I — QuickJS interrupt hooks and job limits are necessary but insufficient.** Bound instructions/jobs, allocation and recursion; the previous Bellard port disabled its native stack check, so test the Wasm stack separately. A compromised guest interpreter could bypass its own checks. Browser/Node timers on the same thread cannot interrupt a synchronous infinite Wasm loop. Use a terminable worker/process and an independently scheduled watchdog, keeping pool capacity charged until termination is confirmed. On workerd rely additionally on the platform's enforced CPU budget; do not assume a same-isolate JS timer provides preemption.

**I — For a uniform instruction budget beyond QuickJS:** instrument basic blocks/loop backedges in the final module with a private fuel counter or trusted host decrement import, rejecting/failing on exhaustion. Handle indirect calls, growing memory, bulk-memory costs and counter overflow; fuzz and validate transformed binaries. Fuel must live outside guest-writable linear memory (or be enforced by the trusted runtime), and host authority must not accept a restored guest's claimed remaining budget. Metering traps terminate the instance; they do not yield a portable mid-C checkpoint. **F:** the often-mentioned npm `ewasm/wasm-metering` repository explicitly labels itself **ORPHANED**; do not adopt it as a maintained security dependency. Wasmtime fuel/epoch interruption is a useful native adapter feature but not a WebAssembly JS API portable feature. [wasm-metering status](https://github.com/ewasm/wasm-metering), [Wasmtime interruption](https://docs.wasmtime.dev/examples-interrupting-wasm.html).

## 6. Suspension: three mechanisms, three different promises

| Mechanism | What suspends / where state lives | Portability and overhead | Use here |
| --- | --- | --- | --- |
| **Guest Promise + return to host** | **F/I:** JS continuation in QuickJS heap; all native Wasm frames return. Host queues requests, sends replies, pumps jobs. | **M:** both engines restored in Node here; Bellard already crossed the four host families in the old spike. No suspension transform. | **I:** default. Support concurrent guest tools with IDs/Promises rather than serializing all tools through a synchronous import. Prebundle modules to avoid synchronous module-loader I/O. |
| **JSPI** | **F:** host engine retains a suspended Wasm execution stack and returns a Promise to JS. | **F/I:** low-transform-cost async interoperability, but no supported API exports that continuation as checkpoint bytes. Current V8 documentation reports shipping Chrome/Firefox support; exact deployed-host availability needs feature tests. A newer V8 does not make the stack part of linear memory. | **I:** optional for a nonportable synchronous C API path; finish/unwind it before checkpointing. Not a dependency of baseline capsules. |
| **Asyncify** | **F:** compiler instrumentation unwinds/rewinds frames using linear-memory state plus runtime metadata. | **F/M:** extra code/runtime cost; old spike grew raw module ~57%, gzip ~50%, and successfully restored a carefully controlled Asyncify suspension Node→Wasmtime. That proves feasibility for that bridge, not arbitrary Emscripten Promise/glue state. | **I:** runner-up for a required synchronous guest call, loader or deep-C yield. Include Asyncify stack/control metadata and a stable resume entry in the format; qualify reentrancy. |

**F — Sources:** [Emscripten Asyncify vs JSPI](https://emscripten.org/docs/porting/asyncify.html) explains instrumentation and indirect-call analysis; [V8 JSPI](https://v8.dev/blog/jspi) explains engine-held stacks; [Oct 25 report/raw evidence](../portability/02-wasm.md) contains the measured transformation and restore. **I:** do not turn either a JSPI feature check or an Asyncify flag into a claim that arbitrary imported host state is serializable.

## 7. TypeScript host, scriptc and host packaging

**F — Existing seam:** [backend.ts](../../jitk/executor/backend.ts) defines `Backend.park()` and `Sandbox.read/send/kill/exited/armDeadline`; [pool.ts](../../jitk/executor/pool.ts) charges capacity through disposal and never reuses completed sandboxes; [executor.ts](../../jitk/executor/executor.ts) owns policy, approval, provenance and tool dispatch. [select-backend.ts](../../jitk/executor/select-backend.ts) is Node-specific. The backend currently imports process/filesystem APIs, and executor imports `node:perf_hooks` and re-exports Node launchers. A browser-ready package needs source entrypoint separation, not simply another backend constructor.

**I — Keep the core in TS:** protocol parsing/encoding, bounds and state transitions, policy, checkpoint manifest, replay and tool journal should share a dependency-light TS library. Compile/bundle to ESM with browser/workerd entrypoints that cannot import Node launch code; inject module loading, clock, entropy, persistence, scheduling and termination. The C bridge contains engine/byte-buffer operations, not policy or orchestration. Retain the canonical dispatcher, frame budgets and codec; the benchmark bridge is not its implementation.

| Host | Packaging / execution choice — **I** unless noted | Qualification required |
| --- | --- | --- |
| Node | ESM package with explicit module/bytes loader, `worker_threads` or process owner, shared compiled module per owner, fresh instance per capsule; no dependency on complete `node:wasi`. | Snapshot restore, cancellation, owner exit/reap, memory slope and end-to-end executor latency. |
| Browser / Chromium | Same reactor in dedicated Web Worker; `compileStreaming(fetch(...))` with correct Wasm MIME or bytes fallback; message-based tool broker; IndexedDB/remote storage. | Restore across Worker lifetimes; termination during a synchronous infinite loop; device memory and offline codecs. |
| workerd / Cloudflare Workers | Import a precompiled `.wasm` module as a deployment artifact; instantiate using minimal imports. Keep durable bytes in object storage/DO-owned state, not isolate lifetime. **F:** Workers instantiate only precompiled modules. | Pin workerd binary and compatibility date. ### scriptc is relevant in three different roles

**F/M — Mac tools:** keep the existing **scriptc 0.4.5** pin from [tools/package.json](../../jitk/tools/package.json) and [scriptc.mk](../../jitk/tools/scriptc.mk). It compiles the Mac build/benchmark/test controllers and supervisors from TypeScript, preserving the project rule. Node in this research is the runtime under measurement, not a replacement implementation of those project controllers. The existing [SCRIPTC-HANG.md](../../jitk/SCRIPTC-HANG.md) identifies a lost child-exit wakeup with far-future timers; use [tslib/process.ts](../../jitk/tslib/process.ts)'s `track`/`spawnCapture` (50 ms keepalive while children run, deadline, process-group cleanup). Do not recreate raw spawn/wait helpers.

**F — Native Wasm host:** pinned scriptc 0.4.5 can translate known Wasm modules to native code **at build time**, select them by bytes' SHA-256 at runtime, and expose the WebAssembly API. This is not a V8 embedding. The pinned documentation explicitly records unreclaimed instances, non-detaching memory growth, possible removal of unused out-of-bounds loads, NaN/scheduling differences and a restricted feature set. **M:** `scriptc coverage scriptc-host.ts --wasm bellard.wasm` accepted this 966,552-byte reactor (1,125 functions, 5 imports, 14 exports; mutable globals, sign-extension, nontrapping float conversion, bulk memory). Coverage acceptance is not compilation, restore or containment validation. [Pinned source/docs](https://github.com/vercel-labs/scriptc/blob/v0.4.5/docs/content/limitations/webassembly-modules.mdx).

**I — Native-host recommendation:** compile the Mac TS supervisor with scriptc and let it own a bounded Node/V8 execution process first. Share TS protocol/policy code as compilation coverage permits. If a Node-free native host is required, a scriptc TS controller can call a thin **Wasmtime C API** bridge through supported FFI, while policy and formats remain TS. Qualify that adapter against the same snapshots. Do not select scriptc's built-in Wasm translator as the untrusted production boundary merely because coverage accepts the module: its documented lifetime/trap differences and an additional translator TCB need independent testing. It may become a useful optional adapter after those gates; process recycling addresses the leak only, not all semantic issues. [scriptc FFI](https://github.com/vercel-labs/scriptc/blob/v0.4.5/docs/content/docs/ffi.mdx).

**F/I — Guest compilation:** scriptc also emits **wasm32-wasi** executables/reactors from supported TS; that can serve fixed trusted helpers. It does not compile the C QuickJS engine, and a WASI library-mode reactor excludes async functions/Promises/timers in the pinned contract. AOT-compiling arbitrary agent source changes the language/admission model and may put continuations on native Wasm frames. It is not a transparent replacement for a persistent QuickJS heap. [Pinned Wasm module docs](https://github.com/vercel-labs/scriptc/blob/v0.4.5/docs/content/docs/wasm.mdx), [library restrictions](https://github.com/vercel-labs/scriptc/blob/v0.4.5/docs/content/limitations/browser-embedding.mdx), [platforms](https://github.com/vercel-labs/scriptc/blob/v0.4.5/docs/content/docs/platforms.mdx). Native FFI is unavailable in the WASI target, so compiling the host to Wasm does not recursively supply a Wasm runtime. **F:** scriptc itself is [Apache-2.0 licensed](https://github.com/vercel-labs/scriptc/blob/v0.4.5/LICENSE).

**F/I — Carry over the observed gaps:** [docs/SCRIPTC-GAPS.md](../../jitk/docs/SCRIPTC-GAPS.md) covers literal stdio branches and controlled environment construction; [bench/SCRIPTC-GAPS.md](../../jitk/bench/SCRIPTC-GAPS.md) covers dynamic-record arrays, iterator spreads and numeric formatting; [kernel/SCRIPTC-GAPS.md](../../jitk/kernel/SCRIPTC-GAPS.md) warns about equality across parsed optional-field layouts. Use typed arrays/records, canonical byte/frame comparisons and native API shims already established there. [scriptc-corpus/SCRIPTC-GAPS.md](../../jitk/scriptc-corpus/SCRIPTC-GAPS.md) distinguishes compiler errors from timezone, libc and missing-command environment differences. No local workaround in those notes implies an upstream fix; pin and test actual compiler behavior.

## 8. Snapshot encoding and storage: separate identity from compression

**M — Compression experiment:** the existing Oct 25 `snapshot.bin` is **2,097,152 B**, SHA-256 `eb468b13256f00ba8d4637340ff8ef53ecf2a3ae095bb7690518f54fbac3e3d2`. Node 24.22.1, zstd 1.5.7, Brotli 1.2.0; five sequential synchronous encode/decode pairs per configuration, medians, exact byte equality checked. Timings include Node output allocation. This is one sparse, low-entropy small heap, not a corpus of large/secret/compressed guest data. gzip-9 yields 100,796 B with this Node encoder versus the earlier Python report's 99,854 B; codec implementation/settings matter, so neither compressed blob is the logical identity.

**I — Choice:** zstd-3 for server-side parking; gzip-1 when cheap encoding/ubiquitous decoding matters most, gzip-6 when byte size matters more. gzip-9 saves only 156 B over level 6 here and is a poor live-checkpoint default. Brotli-11 belongs in offline artifact distribution, if anywhere; Brotli-6 is a possible bandwidth-oriented export. None improves checkpoint correctness. Prefer asynchronous codec execution/off-thread work on the live host; these synchronous benchmark calls are measurement tools.

**F/I — Cross-host codec reality:** native Node exposes gzip/Brotli/zstd APIs, but the web Compression Streams standard specifies deflate/deflate-raw/gzip, not a portable application-level Brotli/zstd decoder. HTTP `Content-Encoding: br/zstd` support is separate from decoding an opaque stored checkpoint. Include a tested decoder artifact or transcode server-side before browser/edge delivery. Make gzip a required exchange encoding and zstd optional, negotiated by capabilities. Native Node codec availability does not establish workerd or Bun parity. [Compression standard, updated Oct 19 2026](https://compression.spec.whatwg.org/), [Node zlib](https://nodejs.org/api/zlib.html), [zstd format/project](https://github.com/facebook/zstd).

### Proposed format, content addressing and dedupe

**I — v1 format:** a bounded binary envelope with magic/version/header length, a canonical UTF-8 JSON manifest and a compressed raw memory payload. This avoids Base64 memory and avoids adding a CBOR dependency before one is needed. The manifest records exact module SHA-256, bridge/bootstrap ABI versions, memory byte/page length and maximum, supported scalar mutable globals, checkpoint boundary kind, pending tool requests, applied-reply/journal cursor, ancestry/fork identity and uncompressed payload digest/length. Stable-width encodings are required for i64/float globals; use decimal strings or tagged bit encodings rather than lossy JSON numbers. Replay metadata and resource budgets remain host-authoritative.

**I — Identity:** hash domain-separated, canonical **uncompressed logical bytes** plus the semantic manifest; store compression algorithm/version/length in a transport envelope. Use SHA-256, already present in Node/Web Crypto and project receipts. Do not content-address host-native compiled code as the portable executable: the Wasm module hash is the compatibility key. Keep old executable versions available; upgrades use replay/migration rather than assuming raw heap layout compatibility. An object-store key alone is not authorization or integrity against a party able to replace both manifest and payload; bind checkpoints to a tenant/execution and authenticate the envelope through trusted storage/signature mechanisms. Bound decompression and allocate only after lengths, module identity and format have been validated.

**M — Page scan of this same image:** at 4 KiB, **512 pages / 69 unique / 68 nonzero**, with a naïve 32-byte-hash index of **16,384 B**. At 64 KiB, **32 pages / 9 unique / 8 nonzero**, index **1,024 B**. Individually gzip-6-compressing nonzero pages totals **100,602 B** at 4 KiB and **97,765 B** at 64 KiB, excluding indexes/metadata. These numbers are not a fork-delta or restore-speed measurement. Empty pages explain much of the apparent saving; whole-image compression already removes most of them.

**I — Dedupe plan:** ship whole-image v1 first. Add a v2 page map of independently addressed **64 KiB Wasm pages**, with a distinguished zero page and shared tenant-free base image, when real fork histories show savings. Compare 4 KiB subpages for small dirty deltas, balancing index/storage-request/hash costs. Scan and compare hashes at a quiescent boundary; ordinary JS hosts expose no portable dirty-page bitmap or page-remap CoW API. Reconstructing memory is still a copy, not hardware CoW. Prefer flat page manifests or periodically flattened ancestry to unbounded delta chains. Tenant-scoped/private-state dedupe avoids turning hash lookup into cross-tenant existence disclosure. Fixed-page maps are a simpler first implementation than content-defined chunking for a pointer-addressed heap; the latter may help shifted large buffers but needs corpus evidence.

## 9. Differential testing: reuse jitk's experimental discipline

**F — Existing model:** [scriptc-corpus/README.md](../../jitk/scriptc-corpus/README.md) and [RESULTS.md](../../jitk/scriptc-corpus/RESULTS.md) pin source/toolchain/reference environments, compare bytes and exits, resume from manifests only when pins match, retain per-case receipts, distinguish reference errors/infrastructure failures from semantic mismatches, and separate visible and held-out gates. The growth loop uses controlled counterfactuals rather than assigning every absent syscall causal blame. Reuse those properties for capsule imports and host behavior.

**I — Build a TS conformance runner with scriptc-compiled Mac controllers and three primary execution legs: Node worker, Chromium Web Worker, and pinned local workerd.** Browser interactions can be driven by the documented project browser harness; the tested program/protocol stays TS/JS. Add Wasmtime as an independent engine/implementation oracle, then Deno/Bun after the initial gate. Native Bellard/ng runs are useful language oracles; Node running guest source directly is an oracle only for the declared shared JS subset, not error text or all engine extensions.

**I — Per case, execute these comparisons:**

1. **Continuous vs restored:** same module/source/import journal, run uninterrupted, then checkpoint at each eligible boundary and restore to the same host. Compare ordered tool requests/replies, log bytes, terminal result/error category and resource outcomes. Detect duplicate tools, missing completions and unexpected imports.
2. **Every directed host pair:** Node↔Chromium, Node↔workerd, Chromium↔workerd, plus same-host controls. At every move use the **identical executable bytes**, same snapshot schema and journal cursor. Validate module/global/memory reconstruction before executing a reply.
3. **Fork:** restore one image twice, supply different responses, require two expected results with independent heaps and pending-call tables. Test `Promise.all`, replies arriving in different orders, rejection/catch/finally, nested async closures, cycles, Map/Set, BigInt, Unicode, typed arrays, memory growth and module-local state.
4. **Crash and replay:** cut before enqueue, after durable intent but before dispatch, after external completion but before journaling, after journaling but before reply, and after reply but before checkpoint. Tool side effects need idempotency/transaction rules; heap snapshots alone do not create exactly-once external effects.
5. **Hostile/limit cases:** pointer-length wraparound, malformed/oversized frames, duplicate/reordered IDs, detached/grown views, snapshot truncation/hash mismatch, wrong module/schema, zip bombs, memory/stack/job/fuel exhaustion, endless synchronous loops, import exceptions, cancellation and owner cleanup. Require no host tool effect after denial and no capacity leak after kill.

**I — Determinism rules:** record clock/random/tool/log import results and scheduling decisions; define reply order explicitly rather than inherit network arrival order. For replay, substitute journal results and verify the requested call digest before delivering each result. Do not silently normalize frame ordering or broad exception output to make hosts agree. Compare semantic wire results first; raw memory equality is diagnostic because stale C stack bytes, allocation behavior and NaN payloads may differ without changing the program. Disable or journal all remaining nondeterministic engine facilities. Error stacks/messages are version-specific; only normalize fields explicitly excluded from the public contract.

**I — Receipts and acceptance:** each result includes guest/module/bootstrap/runner SHA-256, host version and flags, workerd compatibility date, seed, fixture hash, source/destination checkpoint IDs, journal digest, output hashes, cleanup result and failure classification. A changed pin starts a new run identity. Retain bounded failing evidence; regenerate reports from receipts. Run standard language tests separately from hostile protocol and resource tests. Keep visible development fixtures and trusted held-out fixture families distinct when an agent is modifying the runtime. Start with a small pairwise/fork suite on every change, and a pinned complete matrix before promoting a new engine/compiler/optimizer. Do not claim support for unexecuted Deno/Bun/edge deployments.

### Five-line TL;DR

1. **I:** Qualify quickjs-ng's small core reactor; keep Bellard as the measured, smaller fallback.
2. **M/I:** ng costs ~90 KB more raw code but honored the engine allocation limit that the selected Bellard port missed.
3. **I:** Park at guest `await` with an empty Wasm stack; JSPI is not a checkpoint-export interface.
4. **M/I:** zstd-3 is the server-storage choice here; gzip remains the universal exchange encoding.
5. **M/I:** V8 can preserve an awaited closure in a startup snapshot, but cross-host capsule portability still requires a controlled durable ABI.

**Verdict — GO-WITH-CHANGES for this angle.** **I:** the stack is practical, but ng cross-host checkpoint qualification, hard resource enforcement and host entrypoint separation are required before exposing it as a supported backend. scriptc remains the Mac tool compiler; its native Wasm translator is not yet the recommended isolation boundary.

**The three things I would do next:**

1. **I:** Port the canonical tool/bootstrap protocol to ng's minimal reactor, then run the directed Node–Chromium–workerd restore/fork matrix, with Bellard as a pinned regression control.
2. **I:** Qualify allocation, stack, job/fuel, hostile-frame and cancellation limits under owner teardown; compile the Mac TS controller with scriptc using existing tslib helpers.
3. **I:** Implement bounded whole-image checkpoint v1 and an idempotent tool journal, then measure real checkpoint/restore workloads with zstd/gzip before adding page dedupe or component wrappers.
