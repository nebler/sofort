# Hardware-isolated jitk: reach, porting effort, and performance

Research date: **2026-10-25**. Researcher: **hw**. Read `BRIEF.md` before investigation. No product sources were changed and no services were purchased or contacted. Experiments live under `/tmp/portability-hw/` on the Mac and `~/portability/hw/` in the shared Linux VM.

Labels: **F** = source/code fact; **M** = measured here or in the cited repository benchmark; **I** = inference; **E** = engineering/performance estimate. Prices are advertised prices checked on this date, before tax unless specified; USD and EUR remain separate. “Month” means 730 hours for hourly estimates, unless a provider publishes a monthly subscription/cap. Storage, public IPs, traffic, setup fees, and reservations can change the bill. A documented platform capability is not a completed jitk certification.

## Findings that change the decision

1. **I: Port x86-64 first for deployment reach.** It unlocks nested KVM on AWS, GCP, Azure, OCI, Vultr VX1, OVH Public Cloud, and inexpensive specialist VPSes. The missing work is mostly jitk's guest architecture and host confinement, not a new x86 VMM. Budget **31–50 engineer-days**, or roughly **6–10 engineer-weeks**, for a reviewed QuickJS/Lua port and its security regressions. A narrow boot-to-QuickJS prototype is plausibly 10–15 days, without production validation.
2. **F: AWS is no longer “bare metal only.”** February 16, 2026 added nesting on C8i/M8i/R8i; June 18 expanded it to seventh-generation Intel and additional eighth-generation families. This does **not** make virtual Graviton instances suitable. Sources: [February launch](https://aws.amazon.com/about-aws/whats-new/2026/02/amazon-ec2-nested-virtualization-on-virtual/), [June expansion](https://aws.amazon.com/about-aws/whats-new/2026/06/nested-virtualization-intel-us-gov-cloud/).
3. **F: Pi 4/5 require a small guest GICv2 port, not a new libkrun interrupt controller.** The pinned libkrun already tries GICv3 and falls back to GICv2. Jitk's `fdt.rs` and `wait.rs` still require GICv3. Estimate **3–5 days**, including actual-board tests.
4. **M: The available HVF→KVM system is a very slow nested path under contention.** It must not be used to promise “5 ms plus 10%.” The raw exit microbenchmark measured approximately **1 ms per nested KVM MMIO exit**, versus **1.5–1.7 µs** through direct HVF on the same Mac. Full protocol results and limitations are below.
5. **F/I: A $5 hardware-isolated deployment is plausible after the x86 port, but provider selection matters.** RamNode documents nested KVM and lists a $5/1 GB plan; its passthrough guide describes free activation by support. Cloudzy's low-price sales claim conflicts with its 8 GB minimum setup guide. Hetzner Cloud, including dedicated-vCPU and CAX products, is explicitly unsuitable.
6. **F: Hetzner's historical RX170/RX220 ARM dedicated prices are not current purchase options.** Its live RX page says no RX servers are currently offered. Ordinary Ampere bare metal remains viable elsewhere, but is hundreds of dollars per month rather than $5. [RX availability](https://www.hetzner.com/dedicated-rootserver/matrix-rx/).

## 1. What the current implementation actually assumes

**F, repository audit:** Read `arch/jitk/kernel/src/{boot.S,vectors.S,mmu.rs,user.rs,main.rs,wait.rs,fdt.rs,console.rs,syscalls.rs,syscalls/*.rs,trace.rs,fs.rs}`, the build/packer/slot files, and VMM launcher, confinement/watchdog, patches and nested tests. The ten main kernel implementation files total approximately 1,120 lines before the syscall modules. Small size helps, but the code crosses several security-critical architecture boundaries.

- `boot.S`: masks ARM exceptions, accepts the DTB in x0, handles an EL2→EL1 drop, enables FP/SIMD, clears BSS and enters Rust.
- `vectors.S` / `user.rs`: a 2 KiB-aligned VBAR table, an 800-byte saved frame, `ESR_EL1`/`FAR_EL1`, SVC64 decoding, syscall number x8, arguments x0–x5, result x0, EL0 entry by ERET. It saves all NEON registers and FP status.
- `mmu.rs`: ARM 4 KiB stage-1 tables, hard-coded RAM at `0x80000000`, payload physical alias `0x80080000`, AP/PXN/UXN bits, PAN on user entry, guard page, read-only kernel aliases and TLB maintenance. `user.rs` also explicitly performs ARM instruction-cache maintenance.
- `fdt.rs`: accepts a DTB only inside the initial RAM window; recognizes `virtio,mmio` and **only** `arm,gic-v3`; asserts distributor and redistributor addresses are present. Parses seed, epoch and virtual-counter baseline from bootargs.
- `wait.rs`: reads CNTVCT/CNTFRQ; initializes GICD/GICR and ICC system registers; uses CNTV timer plus masked-interrupt WFI parking. The optional tick fallback skips GIC operations but does not remove the FDT assertions or libkrun's IRQ-controller creation.
- `console.rs`: modern virtio-MMIO console, four queues including multiport control, explicit ARM loads/stores/barriers; queue descriptor logic otherwise largely portable. Its **1024-byte TX chunks each notify and wait for completion**. Large external frames can consequently be exit-heavy even though the canonical `json1m` case returns only a short length.
- `slots.json`: 24 numeric slots, with both exit numbers mapped to one handler. Most handlers share portable semantics, but numbers, constants and structures are Linux/AArch64 ABI. `newfstatat.rs` explicitly writes a 128-byte ARM `stat`; `openat.rs` embeds ARM flag values. `readv.rs` dispatches console reads with literal syscall **63**, and `trace.rs` recognizes literal **29/63/64/73**.
- `vmm/src/main.rs`: Linux `counter()` contains AArch64 assembly; Unix fd APIs and `/dev/urandom` are assumed. One vCPU, 32/64 MiB RAM, console-only device policy, external **Raw** image, nested virtualization **disabled inside jitk**, host sandbox acknowledgement before RUN. The latter setting does not prevent running this VMM inside an L1 VM whose provider exposes virtualization.
- `vmm/sandbox/mod.rs`: the seccomp audit architecture, host syscall numbers and pthread `clone` argument assumptions are **AArch64-specific**. This is a separate x86 port from guest syscall translation. Landlock, rlimits, the external watchdog and the strict thread roles remain useful.

**F: Pinned libkrun is already substantially portable.** Revision `a1d8616765da03980f3be1bb8714bfdd3842f33c` has Linux x86-64 register/MSR/APIC setup and ELF/PVH loading. `src/libkrun/src/vmm/device_manager/kvm/mmio.rs` publishes x86 virtio-MMIO devices in `virtio_mmio.device=<size>@<base>:<irq>` command-line parameters. **PCI is optional, not required for an x86 port.** However, jitk's exact `Payload::load_external(..., KernelFormat::Raw, ...)` path is not an x86 loader: the external-kernel Raw match arm is unreachable there. Use an ELF entry compatible with the existing Linux-style direct boot, or add a deliberately small direct-load contract.

The same checkout has `src/whp`, Windows register/device-manager code and GICv2 support. Its README calls Windows **“upcoming”**, and `choose_payload()` still makes an external Windows kernel unreachable. These source files are evidence of reusable work, not proof that jitk runs on Windows. Permanent reference: [pinned libkrun tree](https://github.com/libkrun/libkrun/tree/a1d8616765da03980f3be1bb8714bfdd3842f33c).

## 2. Concrete x86-64 port

### Proposed minimal target

**I:** Keep one vCPU, one virtio-MMIO console, the JSON-lines protocol and the existing syscall semantics. Start with Linux KVM on x86-64 and an ELF kernel entered in long mode with a Linux-style boot-parameter pointer. The existing libkrun non-PVH path already sets registers and bootstrap page tables; no BIOS, UEFI, disk boot, ACPI parser or PCI enumeration is necessary for this fixed topology. PVH is possible but starts in a different execution mode and is needless extra scope for the first port.

**I:** Separate architecture primitives behind a small module interface: entry/trap frame, page permissions/TLB, user entry, clock/park, boot metadata and MMIO barriers. Preserve strict pointer validation and W^X. Guest Linux syscall dispatch should normalize architecture numbers into named handlers, avoiding another layer of literal numbers in `readv` and tracing.

**I:** Rebase the kernel/payload **physical** layout for libkrun's x86 RAM map; blindly retaining ARM's `0x80000000` RAM base in a 32 MiB x86 VM will fail. The user ELF's low virtual-address contract can remain separate from physical backing. Specify the memory map once and derive the linker, packer and VMM boot metadata from it.

**I: SYSCALL details are essential, not optional glue.** Set EFER.SCE, STAR, LSTAR and FMASK. Map Linux x86 numbers from RAX and arguments RDI/RSI/RDX/R10/R8/R9; return RAX. SYSCALL saves RIP/RFLAGS in RCX/R11 and **does not switch RSP**: entry must switch to a protected kernel stack before writing a frame. Set up a kernel GS/per-CPU strategy if using SWAPGS, with careful fault/NMI ordering. Start with validated IRETQ returns; only adopt SYSRET after canonical-address/RFLAGS checks. Use baseline SSE2 or correctly preserve all advertised extended state; do not advertise AVX and save only legacy XMM state. This is the sort of code where a one-day demonstration and a reviewed port have very different costs.

**F/I: More than number renaming.** Linux x86-64 `stat` is 144 bytes with different offsets; O_DIRECTORY is `0x10000`, versus the current ARM `0x4000`. At minimum trace `arch_prctl`, `fstat`, `getrandom`, robust-list/rseq fallback and signal initialization for the exact libc build. A required syscall must be implemented; an optional ENOSYS fallback should be explicit and tested. Linux UAPI sources: [x86 stat](https://github.com/torvalds/linux/blob/master/arch/x86/include/uapi/asm/stat.h), [x86 syscall table](https://github.com/torvalds/linux/blob/master/arch/x86/entry/syscalls/syscall_64.tbl), [generic fcntl flags](https://github.com/torvalds/linux/blob/master/include/uapi/asm-generic/fcntl.h).

**E: Performance goal after port:** single-digit to low-tens of milliseconds cold, sub-millisecond raw parked tool calls on a quiet fast non-nested x86 host. This is a target, not a measurement; CPU generation, libc/QuickJS code generation, process creation, mitigations and page initialization all change the result. AArch64 binaries cannot execute directly in an x86 hardware VM.

### What nesting costs, and which operations pay

**F:** A Linux syscall inside jitk is **EL0→EL1**, or **ring 3→ring 0 after the x86 port**, not automatically an L2→L1 VM exit. Pure `brk`, archive lookup and many pointer-copy operations stay inside the guest. Tool I/O pays console notifications, MMIO/status accesses, wakeups, pipe scheduling and re-entry. Boot also programs page tables, virtual interrupt/timer state and virtio queues. Thus neither “multiply every syscall by VMEXIT cost” nor “multiply the entire cold start by 1.1” is a useful model.

**I:** A useful model is:

`T = host process/setup + guest compute + exits × exit_roundtrip + wakeups/scheduling + executor/tool time`.

Ordinary CPU virtualization can be close to native on the **same CPU and interpreter build**; page faults, nested translation and exit-heavy I/O can dominate instead. Different CPUs and JS engines are not virtualization overhead. Planned cold snapshots remove much of guest initialization but cannot remove the outer provider's exit cost.

**F: Published evidence does not establish one universal 2026 percentage.** Google warns of **10% or greater** degradation for CPU-bound nested workloads and potentially greater degradation for I/O. The OSDI 2010 Turtles paper measured 7.8% SPECjbb and 14.5% kernbench degradation relative to a single-level guest; its worst-case CPUID loop cost roughly **2,600 cycles single-level versus 58,000 nested** before optimizations. Non-trapping VMCS access reduced that large cost substantially. These old microbenchmark numbers explain sensitivity; they are not forecasts for Xeon 6/Nitro or M4 HVF. Sources: [GCP performance note](https://docs.cloud.google.com/compute/docs/instances/nested-virtualization/overview), [Turtles §4 and §4.3, pp. 8–12](https://www.usenix.org/legacy/event/osdi10/tech/full_papers/Ben-Yehuda.pdf).

**F:** Modern KVM documentation highlights EPT, shadow VMCS and APIC virtualization as important nesting accelerators. A September 2026 kernel selftest proposal specifically measures reflected CPUID and intercepted MSR transitions; the proposal is methodology, not a published fleet-wide latency result. [KVM tuning](https://docs.kernel.org/virt/kvm/x86/running-nested-guests.html), [transition benchmark patch](https://www.mail-archive.com/linux-kernel%40vger.kernel.org/msg2658052.html).

**E: For planning only**, reserve **10–30% extra CPU time for compute-heavy nested x86 execution**, and test **10–50 ms cold / 0.3–3 ms raw parked one-tool** as an initial acceptance envelope on a quiet mainstream nested x86 host. These are deliberately unvalidated ranges, not provider measurements or SLOs; an oversold one-vCPU VPS or a slow exit path can be much worse. The measured HVF→KVM path below is worse by orders of magnitude.

## 4. Measurements in kvm-dev and direct macOS

### Environment and method

**M:** The brief describes Debian 13/4 vCPU/8 GiB, but the running shared machine reported **Ubuntu 26.04.1 LTS, kernel `7.0.0-38-generic`, aarch64, six online vCPUs, about 8.7 GiB visible RAM and 4 KiB host-kernel pages**. The Mac is an **Apple M4 Pro**, macOS 26.6.1 in the saved benchmark. `kvm-dev/start.sh` uses QEMU `virt,virtualization=on,gic-version=3`, HVF, CPU host. The VM was already up; it was neither restarted nor stopped. The physical Mac was heavily contended: load1 was around 61 when checked, and **73.1–76.0 during the direct-HVF comparison**. Other researchers ran work inside the VM concurrently. The Linux guest's load does not describe physical-host contention.

**M:** Copied the current kernel and the already-built patched Linux VMM into the hw directory, with no edits. The VMM build metadata reports the exact libkrun revision and all five repository patches, sandbox enabled. SHA-256:

```
Linux jitk-vmm: e8d7bc8dc294b522926ad2ff6c6b43d967bdd52a618470311b50310a854a0125
kernel.bin:    6c00a278cff95058241967655810dcf0cc9cfa1158a38630d818f26c3b07cbc6
```

Used copies of canonical `bench/run.py`, `processes.py`, `cases.json` and `watchdog.py`; a small `measure.py` imports its `Worker`, validates READY **and host sandbox acknowledgement**, sends identical RUN/RET frames, validates exact done values and tool counts, and kills/reaps only its own worker. Cold = process spawn→validated done; parked = RUN→validated done after READY and 5 ms idle. Three randomized blocks of ten samples per case, for **30 samples per row**, single-use VM. No load-based cherry-picking. The harness's zero-delay echo tool is used, so times exclude a real external tool/service. No MCP/TS-executor timing was collected here.

An initial exploratory run attempted `/proc/PID/smaps_rollup`; Linux's non-dumpable confinement correctly denied it. Those rows were saved separately and excluded from the final run by **run identity**, not latency. The final run reads accessible `/proc/PID/status` VmRSS instead. Temporary evidence and reproducible scripts: `~/portability/hw/{measure.py,raw-hw.json,raw-hw-initial-memory-failed.json,exit.c}`; Mac copies and comparison data under `/tmp/portability-hw/` and `/tmp/portability-hw/native/`. The current compiled kernel differs from the saved quiet-run image, so the old/new comparison is contextual, not an exact-build causal experiment.

**M: Final results, milliseconds.** Each new environment has 30 successful samples per row, **0 failures across 180 samples**. Nested run: 08:27:11–08:34:56 UTC; direct HVF comparison: 08:27:18–08:27:25 UTC. Linux load1 ranged 2.14–13.74; that does not make any sample a quiet-physical-host result. The saved quiet values come from `arch/jitk/bench/RESULTS-quiet-2026-10-24.md`.

## 5. Other hypervisor APIs and host-layer reuse

The normal TCB for protecting the **host from untrusted guest code** includes CPU/firmware, host hypervisor/kernel, VMM/device code and its confinement, jitk kernel, and trusted executor/policy. The numeric API-port ranges are **engineering envelopes, not benchmark evidence**, and exclude external/network tool RTT. Per-syscall work remains guest-local unless a handler reaches an emulated device. For new APIs, measure entry/exit, clock and interrupt behavior before setting an SLO. A minimal shared-memory ring with one doorbell per batch can reduce transport cost relative to a full virtio console, at the price of a new device ABI and fresh hostile-input validation.

**E, per-syscall/compute budget across APIs:** For a tiny non-I/O handler with no allocation, use **0.1–2 µs on a modern fast CPU** and **0.5–5 µs on a Pi-class core** only as provisional engineering budgets. No syscall microbenchmark was performed here. Buffer copies and directory walks scale with input size; a console syscall includes the device path and can cost much more. KVM/HVF/WHP/MSHV/bhyve do not intrinsically add a host transition to each guest syscall. For the same interpreter on the same CPU, use **0–10% non-nested compute overhead** as a hypothesis to test, not a portable measured factor; use the nested caveats in §3 instead on L2. Android Microdroid additionally includes its guest Linux/Android runtime. These budgets describe small local operations and do not imply that a Python or JS syscall benchmark isolates trap-entry cost.

**M, end-to-end context:** The brief's saved macOS results are roughly **9 ms cold via the executor and 2.1 ms warm via MCP**, versus approximately 5.9 ms/0.29 ms raw. The executor/IPC layers and any real tool RTT remain additive after a hypervisor port; none of the raw estimates in this report is an MCP latency promise. See repository `arch/FINAL.md` and `arch/jitk/bench/RESULTS*.md` for the measured scope.

### Does adopting Hyperlight give KVM + MSHV + WHP “for free”?

**F:** Hyperlight already implements those backends. More strongly, a fresh source checkout inspected here at commit **`8a7e6b8794fea050ce287eed614088f0beb6b973`** includes ARM64 KVM, Windows ARM64 WHP and HVF code as well. The ARM64 MSHV file is a placeholder whose detection returns false and constructor is unimplemented. Its VM abstraction and backend modules are largely **`pub(crate)`**, not an independent stable general-VMM library. [Exact VM abstraction](https://github.com/hyperlight-dev/hyperlight/blob/8a7e6b8794fea050ce287eed614088f0beb6b973/src/hyperlight_host/src/hypervisor/virtual_machine/mod.rs), [ARM MSHV stub](https://github.com/hyperlight-dev/hyperlight/blob/8a7e6b8794fea050ce287eed614088f0beb6b973/src/hyperlight_host/src/hypervisor/virtual_machine/mshv/aarch64.rs).

**I:** We get tested backend **code and design**, not a drop-in replacement for libkrun. Hyperlight expects its guest layout, entry/call ABI, virtqueue transport, MSR policy and snapshot contract. Jitk expects a Linux-style boot, its own stage-1 tables and EL0 execution, FDT, GIC/virtio-console/PSCI, and process confinement. Neither “hand it the current Raw kernel” nor “link hyperlight-host” reconciles those contracts.

Two sensible implementations are **E:** (a) extract/generalize the private VM layer and retain jitk's kernel, adding a small console/boot/IRQ layer: roughly **2–4 engineer-weeks** beyond the common guest work; or (b) move QuickJS/Lua to Hyperlight's guest runtime and implement the selected Linux/libc surface there: a **different backend/ABI project**, with useful reuse of existing Hyperlight JS experiments. Both need the Sofort executor, capability policy and teardown/isolation tests. Snapshot “restore a logical sandbox in a retained HW VM” also differs from “each fork gets its own simultaneously isolated HW VM.” Hyperlight's own docs state pre-1.0 API instability and describe retained MSR reset differences across KVM/MSHV/WHP. [Project contract](https://github.com/hyperlight-dev/hyperlight), [MSR restore design](https://github.com/hyperlight-dev/hyperlight/blob/main/docs/msr.md).

## 6. Raspberry Pi, other ARM boards and Asahi

**F:** Pi 5's BCM2712 and Pi 4's BCM2711 describe **GIC-400 / GICv2**, despite Pi 5's newer Cortex-A76 CPU. Do not infer a GICv3 from CPU generation. The Pi 5 kernel configuration has `CONFIG_KVM=y` and uses 16 KiB host pages; Arm's own Multipass instructions demonstrate usable KVM on Pi 5. [Pi 5 DT](https://github.com/raspberrypi/linux/blob/rpi-6.18.y/arch/arm64/boot/dts/broadcom/bcm2712.dtsi), [Pi 4 DT](https://github.com/torvalds/linux/blob/master/arch/arm/boot/dts/broadcom/bcm2711.dtsi), [Pi kernel config](https://github.com/raspberrypi/linux/blob/rpi-6.18.y/arch/arm64/configs/bcm2712_defconfig), [Arm's tested KVM setup](https://learn.arm.com/install-guides/multipass/).

**F/I:** With a 64-bit Linux kernel, EL2 made available by firmware and KVM enabled, `/dev/kvm` can work on Pi 4 and 5. That is first-level virtualization; nested virtualization is not required to run jitk directly on the board. Neither board should be treated as a general nested-ARM host just because it can run KVM. The current Linux nested mode has newer CPU/FEAT_NV2 prerequisites. [Kernel parameters](https://www.kernel.org/doc/html/latest/admin-guide/kernel-parameters.html).

**F:** At the pinned libkrun revision, `vmm/builder.rs` lines near 1258–1272 explicitly mention Raspberry Pi, try `KvmGicV3::new`, and fall back to `KvmGicV2::new`. `devices/legacy/kvmgicv2.rs` already exposes a compatible GICv2 FDT node and MMIO CPU interface. **The blocker is in jitk:** `fdt.rs` ignores that node, and `wait.rs` uses GICR/ICC registers that do not exist in GICv2.

**I/E: Pi implementation, 3–5 days total:**

1. Add GIC version and CPU-interface address to boot config; recognize the libkrun GICv2 compatibility string and validate each version's required fields.
2. Implement distributor/CPU-interface setup, priority mask, acknowledge/EOI and target routing using GICv2 MMIO; retain GICv3 path. Existing low MMIO mappings cover libkrun's controller vicinity, but verify both frames and attributes.
3. Validate CNTV timer PPI and console SPI wakeups, masked IRQ/WFI race handling, idle CPU consumption and watchdog behavior on **both boards**. A timer-polling workaround might get a demonstration running, but is not a substitute for low-CPU event-driven parking.
4. Build current libkrun natively, verify host page-size alignment (16 KiB on many Pi 5 images), confinement kernel support, all hostile console tests, 32 MiB RAM and FD policy. Guest 4 KiB stage-1 pages and host 16 KiB pages are different layers; the latter does not inherently force a 16 KiB guest ABI.

**E:** On Pi 5, plan **20–80 ms cold / 0.3–3 ms raw short parked tool call**; Pi 4 **40–150 ms / 0.5–5 ms**. No board was available to measure. Cortex performance, SD-card/cache state, power/thermal throttling, GICv2 MMIO and kernel mitigations can dominate. Compute should run at approximately the native speed of the **same board/QuickJS build** between exits, not at M4 speed. Resident memory is plausibly around 10–20 MiB per tiny VM, plus host/VMM allocations, with the same 32 MiB guest address-space reservation. Preserve conservative tails until measured.

**F/I: Other inexpensive boards:** RK3588 boards (e.g. Rock 5/Orange Pi 5 families) describe GICv3, so they avoid the Pi-specific guest interrupt rewrite. Their host firmware must still enter Linux with usable EL2; choose an actively supported 64-bit kernel with KVM and confinement features. RK3399 and other ARMv8 boards vary in controller/kernel/firmware support; check each actual board instead of equating “ARM64” with KVM. Older 32-bit-only boards are outside this ABI. [RK3588 device tree](https://android.googlesource.com/kernel/common.git/+/bd58782995a2e6a07fd07255f3cc319f40b131c9/arch/arm64/boot/dts/rockchip/rk3588-base.dtsi). **E:** 1–3 days to certify a supported GICv3 board; 10–100 ms cold and 0.3–3 ms tool path is a test envelope, not a measured claim.

**F/I: Asahi Linux on M1/M2:** First-level KVM works; libkrun is already used by Asahi's `muvm` to run 4 KiB-page guests on 16 KiB-page hosts. This directly rebuts “M1/M2 cannot run KVM” and “host 16K prevents a 4K guest.” [muvm](https://github.com/AsahiLinux/muvm), [Asahi page-size notes](https://github.com/AsahiLinux/docs/blob/main/docs/sw/broken-software.md). Use the supported Asahi kernel and libkrun virtual interrupt model, not the physical Apple AIC as a guest driver. **E:** 1–3 days for native build/strict sandbox/clock/wakeup certification, with **5–20 ms cold / 0.2–1 ms parked** as an initial target. Not measured here. M1/M2's lack of Apple's newer **nested** macOS facility does not prevent first-level Asahi KVM; Apple says that nested facility requires M3 or later. [Apple nesting limit](https://developer.apple.com/documentation/virtualization/vzgenericplatformconfiguration/isnestedvirtualizationsupported).

## 9. Isolation, pause, snapshots and fork across these targets

**F/I:** The hardware boundary's strength is largely independent of whether the host is cheap: untrusted EL0 compromise first needs a jitk kernel escape and then a VMM/hypervisor escape to reach host authority. But device exposure, host permissions and API correctness matter. Porting x86 without its seccomp audit, or running the guest via a permissive generic crosvm/bhyve command, would drop an existing defense. A larger host API wrapper can have the same CPU isolation while increasing the software TCB.

**I:** Single-vCPU quiescence at a pending tool call is an excellent common checkpoint. Stop execution, drain/record console and host pipe buffers, record outstanding call IDs and responses, save CPU/FP/system/timer/interrupt state, and snapshot guest RAM plus virtqueue/device state. Recreate host VM/IRQ/event objects on restore. Mere `SIGSTOP`, process RAM copying, Unix `fork`, or “the VM is in WFI” is not sufficient for a durable portable snapshot.

**F/I:** The present launcher finishes with `vm.run()` and provides no application snapshot/fork API. The table below describes what the underlying APIs make possible; implementing it requires extending the VMM/lifecycle interface as well as a state format. It is additional work beyond the x86 boot/syscall-port total, and the planned 1 MiB marginal-memory outcome is not obtained by these ports alone.

| Backend family | Pause | Snapshot/fork feasibility | Important boundary |
|---|---|---|---|
| KVM bare/nested | Stop vCPU using supported kick/immediate-exit handling | Good basis: register/state ioctls + RAM backing + explicit virtual-device serialization. New hardware VM per simultaneous fork. | Kernel-resident VGIC/APIC/timers, FP/XSAVE, in-flight I/O and virtual clock all need explicit handling. L1 host loss still loses unsaved L2 state. |
| HVF | Request vCPU exit and synchronize owning thread | Good basis; recreate new process/VM object and map copied/CoW RAM for forks. | One VM per process, VM state not inherited as a usable clone by `fork()`. |
| WHP/MSHV | Cancel/kick run and save state through their API | Feasible; Hyperlight has useful reset/state code, but not automatic jitk device serialization. | Hyper-V state/MSR coverage, mappings/handles and backend-supported state versions differ. |
| crosvm/bhyve | VMM lifecycle controls or a purpose-built adapter | Possible for compatible topology; general VMM snapshot commands are not a jitk continuation/fork contract. | More VMM/device state; bhyve's handbook still warns of experimental support. |
| Protected Android pVM | Platform-controlled pause may be possible | **Do not assume host-readable RAM snapshots or free cloning.** | Confidential/protected RAM, verified firmware and key/identity policy conflict with naive host CoW export. Microdroid persistence is not a saved CPU continuation. |

**I:** Cross-host migration requires a stable snapshot schema, matching ISA/features and compatible guest/device/time semantics. AArch64 machine state cannot simply resume on x86-64. Replay or application-level state transfer can bridge ISAs, but is a different mechanism. Forking at a pending external tool also needs executor semantics: idempotency/deduplication or explicit branch ownership, so a cloned guest does not repeat a paid/destructive host action accidentally. None of the researched hypervisor APIs provides that policy.

## 10. Ranked recommendation

1. **Ship/certify x86 Linux KVM next (E 6–10 engineer-weeks).** It gives the largest real reach increase without abandoning static unmodified engines or hardware isolation. Start on controlled x86 metal, then RamNode and Vultr VX1, then AWS/GCP/Azure/OCI. Keep virtio-MMIO initially and preserve confinement. A real $5 plan is a deployment target after this port, not a capability the ARM-only product already has.
2. **Add GICv2 and test Pi 5/4 (E 3–5 days).** This is the cheapest physical ARM experiment and the best small independent improvement. Include idle/wakeup/timer and 16K-host-page tests, not just a boot screenshot.
3. **Certify Asahi and one generic GICv3 ARM Linux host (E 1–3 days each).** Reuse existing ARM implementation; use owned hardware before paying hundreds per month for Ampere metal. Treat unavailable Hetzner RX offers as unavailable.
4. **Benchmark a real nested x86 cloud/VPS before promising latency.** The local nested-HVF stack is functional evidence and a performance warning. Capture exit counts, cold process/setup, parked calls, big-frame console behavior and tails under contention; retain direct-metal baseline on the same CPU family where possible.
5. **For Windows, first choose deliberately between libkrun WHP completion and Hyperlight's runtime/backend layer (E 2–4 additional weeks).** Hyperlight offers substantial tested backend work and increasingly broad architecture support, but no drop-in jitk ABI. MSHV is useful for specialized Microsoft-root hosts, not a universal Azure VM fallback.
6. **Keep AVF, privileged ChromeOS and bhyve as demand-driven ports.** They have real hardware isolation, but host access restrictions or adapter cost yield much less immediate reach. Protected AVF also complicates the desired snapshot/fork primitive.

**I:** Hardware isolation can reach inexpensive hosts, PCs, boards and major x86 clouds, but it cannot be the single universal local backend. The irreducible requirement is usable virtualization exposed by the OS/provider. For browsers and non-nesting VPSes, choose a separate portable backend or explicitly remote hardware execution.
