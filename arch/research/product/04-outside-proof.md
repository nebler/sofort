# 04 — Outside evidence and per-shard host confinement

Research date: **2026-10-28**. Covers the **Proof from outside** and **Shard containment** rows in [PRODUCT-GAPS](../../PRODUCT-GAPS.md), principally order items **2 and 3**. Research only: no builds, VM access, Docker, purchases, registrations, outreach, commits or publication. Only this report was written. All external links below were checked on this date; a date beside a source is its publication date when available, otherwise it is living documentation accessed today. Prices are list prices before tax unless stated, in the currency shown; estimates are not vendor quotations.

**Labels:** **F** = fact from a cited primary source, including repository inspection; **M** = an existing project measurement, attributed to its receipt, not rerun here; **I** = inference, recommendation or proposed design; **E** = estimated money, effort or proposed acceptance threshold. A source reporting a vendor capability is F about that statement, not an independent test of the service. “Unverified” means no architecture-specific guarantee or test was established in this investigation.

## Decision

**I — Spend the next small budget on a second physical machine and a reproducible evidence bundle, then move deadline authority out of the shard and confine the process.** A useful initial result costs **E €0 with already-owned spare hardware, or about €3–10 for a short dedicated-Mac rental**, plus **2–4 engineer-days** to make the real Linux shard and macOS backend runnable from a clean checkout. This establishes portability and gives outsiders something concrete to inspect. It is not yet an independent security review.

**I — Do not buy a managed ARM CI runner merely because its jobs run inside Firecracker or KVM.** That describes the provider's isolation boundary. jitk needs another virtualization boundary *inside the job*, or direct execution on a dedicated host. Many cheap ARM runners do not provide it. Stock GitHub Apple Silicon runners also cannot run the required Hypervisor.framework integration tests. [GitHub macOS limitations](https://docs.github.com/en/actions/reference/runners/github-hosted-runners#limitations-for-arm64-macos-runners), [GitHub ARM KVM discussion, January 2025](https://github.com/orgs/community/discussions/148648#discussioncomment-11863547).

**I — A credible near-term security claim is:** “This revision runs these bounded hostile-input and process-confinement tests on named ARM hardware; its supervisor enforces termination independently; here are the failures, source, raw receipts and reproduction instructions.” A test count, an audit logo and a green badge each answer narrower questions than “safe for arbitrary tenants.”

### 2.4 Minimum useful CI design

**I/E — In 2–4 days, produce these three distinct checks:**

1. **Every change, hosted free runner:** pinned native ARM build, pure shard/kernel-core tests where available, protocol differential corpus, sanitizer/fuzz smoke, formatting. Cross-build Mac artifacts on hosted Mac if needed. Name this check `build-and-core`, not `KVM passed`.
2. **Reviewed revision, dedicated Linux ARM:** build from source, prepare helpers from hashes, run shard unit + ignored KVM tests, executor/shard IPC checks, timeout/reset/recovery cases, and a tiny native-worker smoke. Nightly plus maintainer-triggered pre-release initially is enough; a permanently running agent is optional.
3. **Reviewed revision, dedicated Mac:** actual `hv_vm_create`/guest execution, libkrun backend checks, Seatbelt negative controls, watchdog and executor smoke. Keep its console backend separate from Linux ring parity results.

**F/I — There is already a useful entry point, not a finished CI product:** [shard-host.sh](../../jitk/executor/ipc/shard-host.sh) prepares deps/snapshots and runs shard/executor checks; [Makefile `test-kvm`](../../jitk/shard/Makefile) runs ignored hardware tests. It still defaults to `/home/dev/bench.lock`; pass a machine-local lock path. The Oct 28 receipt records a bare-`node` install-script dependency: put the pinned Node on `PATH`, not only in `JITK_NODE`. Record which native census fixtures were imported and make required native tests fail when absent. Do not call “Mac `make test` green” Linux shard certification.

**I — The job receipt should contain:** exact commit and dirty-state flag; binary/kernel/helper hashes; CPU model; OS/kernel; host page size; hypervisor backend and nested/metal status; Rust/Node/compiler versions; enabled Landlock/seccomp policy hashes; named tests with PASS/FAIL/SKIP; run link, elapsed time and artifacts. Log open/API/create/run results, not just `ls /dev/kvm`. On macOS check entitlement/signing plus actual VM execution, not only `kern.hv_support`. A hardware job that cannot run the hypervisor must not produce a green hardware badge.

**I — Runner containment is distinct from guest containment.** A workflow can execute host shell commands before jitk starts. For the cheap direct-host lane, allow only owner-reviewed trusted commits, no personal/cloud credentials on the box, minimal token permissions, and disposable workspaces; no automatic fork PR execution or `pull_request_target` checkout of foreign code. JIT runner deregistration alone does not wipe a compromised OS. This follows GitHub's explicit [self-hosted-runner threat model](https://docs.github.com/en/actions/reference/security/secure-use#hardening-for-self-hosted-runners). A public log can still show a trusted-commit test. Fully disposable ARM nested runners can follow after the hardware support is demonstrated.

## 3. Confinement: copy mature mechanisms at the shard boundary

### 3.1 What mature projects actually confine

| System | Mechanism and present limitation | Minimal lesson for jitk |
| --- | --- | --- |
| Firecracker | **F:** jailer clears environment, closes unexpected FDs, creates a restricted root/mount namespace, supports network/PID namespace and cgroup/resource configuration, drops UID/GID, then executes Firecracker. Production builds apply per-thread seccomp filters with syscall-argument checks. Debug/experimental GNU targets do not get the default filters. The jailer explicitly says it is designed for its matching Firecracker binary, not arbitrary executables. [jailer](https://github.com/firecracker-microvm/firecracker/blob/main/docs/jailer.md), [seccomp](https://github.com/firecracker-microvm/firecracker/blob/main/docs/seccomp.md). | **I:** one constrained *shard process*, explicit inherited resources and role-specific filtering. | Cloud Hypervisor | **F:** seccomp plus optional Landlock filesystem restrictions; Landlock support shipped in v41, Aug 16, 2024. The Oct 2026 v54 notes add filtering to the main thread, which had remained unfiltered after workers started. [Landlock release](https://github.com/cloud-hypervisor/cloud-hypervisor/discussions/6667), [threat model](https://github.com/cloud-hypervisor/cloud-hypervisor/blob/main/docs/threat-model.md), [v54 notes](https://github.com/cloud-hypervisor/cloud-hypervisor/discussions/9079). | **I:** enumerate **all threads**, including reactor/main and native workers. ### 3.3 Minimal implementation sequence and acceptance gates

**I/E — Budget 5–10 focused engineer-days total, not all independent estimates added together.** Existing VMM sandbox code saves policy work, but its libkrun thread hook, low FD limit and process-per-VM assumptions are not the shard contract.

1. **Launcher and resources, 1–2 days.** The supervisor chooses slot/owner counts and opens immutable snapshot/entropy/IPC resources. Validate hashes on those same FDs; stop reopening checked paths. Read-only path permissions do not prevent another host process from replacing or truncating a snapshot, so use supervisor-owned immutable assets or sealed backing where appropriate. Strip **both** JS and native environments; close every unneeded FD. Drop capabilities and use a dedicated identity distinct from trusted Node/watchdog. Set core dumps off, no-new-privileges, non-dumpable, resource bounds and a parent-death policy. Recheck PDEATHSIG after any credential transition that can clear it.
2. **External deadlines, 1–3 days**, described below. Remove the shard's child-watchdog authority before trying to forbid exec/signaling. Make JS and native admissions use the same outer contract.
3. **Filesystem and syscall lockdown, 2–3 days.** Apply Landlock before owner threads, with runtime ABI detection and an explicit minimum guaranteed policy; allow only the few remaining named resources. New kernel Landlock features do not exist on every CI kernel, and previously opened FDs retain authority. Use an empty network namespace when supplied by a privileged launcher; still deny socket creation. Initialize lazy entropy/pagemap and owner setup before a barrier, then install per-role seccomp or a verified union using TSYNC for all threads. Report successful enforcement before accepting any tenant input. If the required controls are unavailable, fail the hardened mode closed; a clearly named development mode is a different support tier. [Landlock semantics and ABI negotiation](https://docs.kernel.org/userspace-api/landlock.html).
4. **Compromise probes and regression, 1–2 days overlapping the above.** Run a test-only host-code probe *inside the confined shard*, with an unconfined positive control. Try reading an out-of-scope sentinel, writing a file, creating a socket, executing a helper, signaling the supervisor, and a disallowed ioctl. Assert denial or SIGSYS, sentinel integrity, bounded shard recovery and no unexpected FD/env exposure. Separately test hostile guest payloads, malformed rings and clean reuse; guest-only failures do not exercise a compromised host process.

**I/E — Put process resource ceilings above the current observed working set and validate them under worst-case inputs.** For a 64-slot JS shard, **512 FDs, 16 tasks and a 256 MiB shard-only memory ceiling** are initial test values, not measured requirements; the nominal 2 MiB guest class is not the total host charge. Native classes/input archives need separate sizing. A supervisor-owned cgroup supplies memory/pids/CPU ceilings and `cgroup.kill`; it does not provide millisecond wall deadlines. Avoid copying the old VMM's `RLIMIT_NOFILE=64` into a process holding 64 VM/vCPU pairs, or `RLIMIT_FSIZE=0` into native code that still creates input memfds. Keep watchdog/Node outside the killable shard cgroup.

**I — macOS:** keep the existing precompiled deny-default Seatbelt profile on the libkrun process, with real host-process negative controls on the rented Mac. Linux seccomp/Landlock are not portable to macOS. A future HVF shard needs a separately reviewed process profile, FD/entitlement handling and supervisor deadline design. It is not covered merely because today's libkrun process is sandboxed.

### 3.4 Deadlines belong to the supervisor, including the non-cooperative case

**I — Extend the existing Node-spawned [jitk-vmm watchdog](../../jitk/vmm/src/watchdog.rs), following R9 N14, instead of growing a fourth watchdog.** Trusted Node/supervisor owns admission and the monotonic deadline. A small native watchdog remains responsive when the Node event loop is blocked. The shard receives an immutable lease identity `(process identity, slot, generation, deadline)`; it cannot extend or disarm the watchdog's authoritative timer. Keep any writable shard acknowledgement area separate from the supervisor-owned deadline data; a read-only map is not sufficient if the shard retains a writable FD to the same authority.

**I — Normal expiry:** watchdog wakes/signals the validated owner to leave `KVM_RUN`; owner stops, resets/quarantines, and reports the matching generation. If the shard does not respond by a bounded grace, watchdog sends SIGKILL through its pidfd and the supervisor reaps/restarts the shard. A pidfd prevents PID confusion; it does not bypass signaling permissions. The launcher must establish the watchdog's ability to signal its target after any shard UID/namespace change, while preventing the reverse. On macOS use the existing process-event/kqueue approach. Test signal races, blocked reactor, busy owner, event-loop stalls, IPC saturation, stale generation/TID and PID reuse, Node death, watchdog death and native runs. Watchdog failure must retire affected shards. The monitored process must not be able to signal/ptrace the watchdog or starve it inside its own cgroup.

**I — There is a crucial claim boundary:** a compromised shard can **forge STOPPED/RESET acknowledgements**. An external watchdog cannot prove a single VM stopped by trusting another message from that process. For an enforcement claim against *host-process compromise*, retain a supervisor-owned non-cancellable **process lifetime/retirement bound**, and always kill the process when that hard bound expires. Treat per-slot kick/reset acknowledgements as normal-operation recovery, not a cryptographic proof of stopped execution. If expiry is a security event, retire the shard rather than letting its ack cancel the hard kill. You cannot externally SIGKILL one VM in a shared address space while trusting the rest of a compromised process.

**I — Record three times separately:** requested deadline → actual vCPU stop, → process death/reap if escalated, → API settlement. A stopped VM does not interrupt synchronous trusted host JavaScript or undo an external tool effect. Tools need their own bounded cancellation/process isolation where appropriate. Set the hard grace from measured scheduler behavior; **E 10–100 ms** is a test range, not a promise. The current code's 100 ms grace and millisecond polling resolution belong in the baseline receipt.

**F/I — Supervisors already use this separation at a coarser scale:** systemd provides externally enforced service lifetime/stop timeouts and watchdog-triggered recovery. `WatchdogSec=` is heartbeat liveness, not a hostile process's per-request deadline: a compromised service can continue sending heartbeats. Borrow process identity, external timers, escalation and reaping; retain jitk's explicit per-admission contract. [systemd service semantics](https://www.freedesktop.org/software/systemd/man/latest/systemd.service.html), [pidfd signaling](https://man7.org/linux/man-pages/man2/pidfd_send_signal.2.html).

## 6. Benchmarks an outsider can rerun

**I/E — Deliver a small versioned reproduction kit in 1–2 days after clean-host CI:** one command for dependency validation/build, one for correctness, one for benchmarks; declared input/output schema and expected functional results; a manifest binding source, binaries, images, helper snapshots and raw results. Use the existing benchmark runners and memory-ledger method, not a second implementation built for the post. A third party should be able to build locally rather than execute only an opaque owner binary.

**I — Separate four experiments:**

1. **Correctness and isolation regression:** JS one-tool/fan-out, small native tool, hostile input, timeout and post-failure reuse. Output is a test matrix, not a speed score. Required tests cannot silently skip.
2. **Latency/CPU:** raw RUN→DONE, `execute()` admission→settlement, and MCP request→response separately. Include fresh-process build/preparation as its own interval; distinguish prewarmed restored slots. Use no-op local tools for mechanism tests and a recorded real workload for application value. Count supervisor/watchdog/Node/shard CPU through cleanup.
3. **Memory:** sweep N with fitted fixed + marginal slope, shared snapshot/page-cache ownership, cgroup kernel charges and peak/OOM events stated. Publish total deployable memory as well as marginal slope. Native versus JS, READY versus executed, and hot versus trimmed are different rows.
4. **Recovery:** requested deadline→stop/death/reap/API settlement, other-slot failures when a shard is retired, restart time and next successful job. Normal cancellation and non-cooperative process termination are separate cases.

**I/E — Suggested reproducibility controls:** a quick CI smoke of a few hundred runs; a release benchmark with **5 independent repetitions and ≥10,000 operations per principal latency cell**, pinned workload seed, warmup recorded, all observations retained, failures included. Interleave baseline/candidate or rotate ordering; declare governor/thermal/load/NUMA/page-size/KSM/THP settings and avoid concurrent bench jobs. Shared hosted runner p99 is diagnostic, not a production SLO. Do not promote a noisy nightly performance delta into a required failure until reproducibility warrants it.

**I — Comparisons:** rerun Hyperlight with its shared-snapshot layout on the same host and matched code/tool semantics; keep current roughly equal memory as the expectation to investigate. Native Linux direct execution is a useful lower-bound control with a different isolation contract. Firecracker only belongs where the same useful task/runtime/lifecycle can be compared; its configured RAM or full boot time is not the shard's marginal RAM or `execute()` time. Benchmarking an HTTP service includes network/queueing; do not subtract those away to imply user latency.

**I — Request one outside reproduction before a larger launch.** Ask a peer with another ARM host to follow the manifest without private instructions, keep their build log and raw JSON, and report the first failed step. **E:** **1–2 owner-days** asynchronous support and **1–3 hours** peer time, plus **€0–10** host rental if needed. Publish the peer's identity/report only with consent. A second owner-operated CI host and a third-party-built result should have different labels.

### Rejected or deferred ideas

- **Buy larger GitHub ARM/Mac runners to obtain virtualization:** more resources are not an architecture-specific nesting guarantee; Mac limitation is explicit.
- **Choose Actuated merely because it uses Firecracker:** documented ARM jobs do not get the nested KVM jitk needs; software fee also precedes hardware cost.
- **Start a new Cirrus CI setup:** shutdown and no-new-customer policy make historical offers inapplicable.
- **Treat KVM-backed Ubicloud/BuildJet/Namespace marketing as a passed jitk job:** provider isolation and guest access are different capabilities.
- **Assume a Pi or 16 KiB Asahi host reproduces the fast reset result unchanged:** current copy-restore explicitly selects 4 KiB hosts; board/backend compatibility must be exercised.
- **Copy the existing libkrun seccomp filter verbatim:** direct shard creation/reset/native memfd operations need a different syscall/FD contract.
- **Let the watched shard own the authoritative lease board or cancel hard kill with an ack:** a compromised process can change those values or forge the message.
- **Launch a public open-ended hostile-program endpoint now:** containment/deadline/runner failure domains remain open; a local preset board already demonstrates the work.
- **Spend €/$50k+ on a broad audit before closing known missing controls:** money buys more useful review after a stable boundary and reproducer exist.
- **Apply immediately to Sovereign Tech Fund or the old NGI0 calls:** prototype/maturity minimums or closed calls block the assumed route; current NLnet scope/AI policy adds material conflicts.
- **Use an OSS-Fuzz acceptance badge as the first objective:** eligibility is not established; local/ClusterFuzzLite harnesses produce useful findings immediately.
- **Count reviewers, meetup attendees or stars as first users:** adoption evidence requires an external engineer running their own workload and returning to it.
- **Publish “no escapes observed” as a security guarantee:** finite tests, one architecture and one reviewed revision support only their stated properties and conditions.
