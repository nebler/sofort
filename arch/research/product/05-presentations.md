## 1. The story to tell now

**I — Lead with an engineer making a difficult boundary inspectable:** “I built a small Rust kernel for disposable tool programs, then measured where the whole system actually spends memory and CPU.” For KL platform hiring, the useful signal is ownership across guest code, host scheduling, integration, measurement, failure handling and documentation. Winning a sandbox benchmark is unnecessary. Explaining why an apparent win disappeared is valuable.

**I — Use two related narratives, selected by audience:**

- **Runtime/platform:** a short untrusted program gets a fresh execution state inside a hardware VM; tools and credentials belong to the host. Show the job, boundary, lifecycle and operational gaps.
- **Systems/research:** models propose restricted Linux-ABI handlers; independently controlled tests and a Linux oracle reject bad behavior. Show one accepted change, one rejection, held-out results and the limits of the oracle. This is an engineering workflow, not a claim that generating kernels makes them secure.

**F/M — Evidence hierarchy and corrections to earlier pitch material:** [PRODUCT-GAPS](../../PRODUCT-GAPS.md) and the dated Oct 27–28 artifacts supersede the Oct 25 synthesis where they conflict. The requested `review/R9-ARCH-QUALITY.md` is actually [arch/review/R9-ARCH-QUALITY.md](../../review/R9-ARCH-QUALITY.md).

**I — Sequence the communication by completed evidence:** publish the measurement boundary now; a successful clean-clone reproduction earns the launch; metal earns the capacity post; parity and containment earn a pilot; a real user's repeated workload earns the operator case study. Each update should answer “what can another engineer now do?” One gap closing is usually a short engineering update, not another Show HN.

**I — Value versus appearance:** clean setup, known API limits, honest measurements and recovery behavior directly affect a user's ability to try/adopt Sofort. External evidence affects trust. Tenancy and full operations become blocking when another person runs it as a service. x86 is not blocking a talk or an ARM-local pilot. A logo, elaborate animation, sponsorship booth, billing page and million-tile wall are presentation choices, not product readiness.

2. **A ten-second result:** a real tool-program output and lifecycle receipt. State if data and external tools are fixtures.
3. **The boundary:** QuickJS at EL0 → restricted Rust kernel → KVM/HVF → trusted host policy/tools; include VMM/host kernel/runtime dependencies, not just guest LOC.
4. **The deliberately narrow contract:** static ARM payloads, allowed I/O, source/reply/timeout limits, no promise of npm/full Linux.

6. **The change:** dirty-page copy/restore, cache maintenance, clean state and fallback policy. Explain hostile reset correctness and the cost of retaining mappings.
7. **The experiment:** workload, host/topology, image/commit hashes, warm/cold boundary, counts, failure rate, repetitions, distributions and total CPU. Nested results carry the word “nested” on the chart itself.
8. **The correction:** matched Hyperlight memory is parity; earlier cross-platform comparison was not a fair density comparison. Explain fixed versus marginal memory and shared cache charges.
9. **The other experiment:** one handler accepted, one rejected/overfit; held-out corpus denominator and the read-only filesystem mismatch. No “81% of Linux works.”
10. **Limits and invitation:** absent parity/hardening/operations, where not to use it, reproducible commands and two useful feedback questions. Link follow-up corrections from the top.
