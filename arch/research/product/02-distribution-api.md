# Distribution and public API: make the narrow runtime easy to try

Research date: **2026-10-28**. Scope: the **Distribution** and **User API** rows, order item **4**, in [PRODUCT-GAPS](../../PRODUCT-GAPS.md). Research and proposals only. All external links below were accessed **2026-10-28**; publication/update dates are given when material. Prices are USD list prices observed on that date, excluding tax. No accounts, deployments, purchases, posts, Docker runs, VM operations, benchmarks, or implementation changes were made.

Labels: **F** = sourced fact, including a repository observation; **M** = an existing repository measurement, not a new measurement by this researcher; **I** = inference or proposed design; **E** = estimate. In comparison tables, factual cells are **F** unless explicitly marked **I/E**. A numbered package release is not, by itself, a compatibility commitment.

## 1. Decision and the cheapest credible route

**I — Ship an installable, local TypeScript execution component, with an MCP entry point, before considering a hosted service.** Its initial job is running short JavaScript tool programs with a fresh hardware VM execution state and trusted host callbacks. Make the existing Cloudflare and TanStack adapters convenient to use. A hosted account system, billing, general shell, persistent workspace, or broad Linux personality would turn order item 4 into several other product gaps.

**I/E — The smallest credible release is one versioned artifact set, one npm wrapper, four CLI entry points (`doctor`, `eval`, `demo`, `mcp`), a small documented API, and three runnable examples.** Start with Apple Silicon macOS for individual evaluators; offer the Linux arm64 shard as an explicitly experimental profile until parity and containment gates pass. Budget **6–10 focused engineer-days** for API, packaging, docs and acceptance, after order items 2–3 supply usable builds and their required safety work. Allow **$0 incremental service spend** within existing public registry/release/static-hosting allowances; **$99/year, region-adjusted**, if buying Apple Developer Program membership for Developer ID distribution. This is an effort estimate, not evidence that an installer already works. [Apple membership pricing](https://developer.apple.com/programs/enroll/).

**I — Scope the release honestly.** Installing the macOS backend does not reproduce Linux shard density or its 1.1 ms result. An experimental Linux package can be useful for local engineering evaluation without being a multi-tenant service. Keep packaging work behind the brief's existing priority order; do not count fixing all parity/containment issues as a two-day installer task.

**I — The useful patterns are consistent.** Hosted products remove host requirements but insert account/key/plan steps. Local products succeed when the prebuilt runtime and useful guest are ready together. Infrastructure projects expose machine or container lifecycle; interpreter products expose a compact code/result operation. Sofort should copy microsandbox/`hluk`'s artifact convenience and Riza's small initial code example, while keeping its own explicit host-tool model.

**F — Firecracker supplies a notably concrete support policy:** critical/security patches for each minor for at least six months, the last two minor lines for up to one year, and the latest minor of each major for one year from release. Developer-preview features have explicit exceptions. Kata instead ships monthly snapshots without stable branches/backports; these are very different maintenance products despite similar version numbers. [Firecracker policy](https://github.com/firecracker-microvm/firecracker/blob/main/docs/RELEASE_POLICY.md), [Kata process](https://github.com/kata-containers/kata-containers/blob/main/docs/Release-Process.md).

**F/I — Do not confuse Cloudflare's two sandbox families.** Dynamic Workers/Code Mode are isolate execution. Cloudflare Sandbox is a separate Linux/container-backed SDK with commands and files; its docs now distinguish SDK 0.x from 1.0. It is relevant to workspace adapters, but cannot be assumed to supply KVM to a Sofort process. [SDK migration notice and example](https://developers.cloudflare.com/sandbox/sdk/tutorials/ai-code-executor/). Likewise, a Python guest does not imply a Python host SDK, and `Sandbox.create()` does not imply a new VM for every subsequent execution.

## 4. Packaging a KVM/HVF aarch64 runtime

### 4.1 Choose one release payload, then several delivery channels

**F — Today's install is not just a VMM executable.** [executor/package.json](../../jitk/executor/package.json) is private, targets a built ESM entry, and carries benchmark-related dependencies alongside the framework dependencies. [build.mjs](../../jitk/executor/build.mjs) leaves packages external and copies helper files; it is not a published closed bundle. [select-backend.ts](../../jitk/executor/select-backend.ts) discovers sibling kernel/VMM files, reads readiness/parking receipts and writes an integration-selection receipt. The MCP package imports the sibling executor build and provider/resource files. Merely clearing `private:true` would publish broken assumptions.

**F/I — Create a production entry module rather than bundling the entire current export graph.** [executor.ts](../../jitk/executor/executor.ts) re-exports the Hyperlight benchmark backend from `../bench/hyperlight/backend.js`. Keep that comparison dependency and the unsafe local backend out of the public runtime's dependency graph; retain them in development/benchmark entry points. The production package should import canonical execution/policy code and only the selected supported host backend.

**F — Linux has an additional native addon and preparation dependency.** [ipc/build.sh](../../jitk/executor/ipc/build.sh) currently compiles `shard-ipc.node` using a C compiler and Node headers. [snapshot.ts](../../jitk/shard/snapshot.ts) compiles a helper-injected ring kernel and then calls the prebuilt shard's `prepare` command. Distributing the kernel containing those helpers removes the customer-side Rust/scriptc build; preparation can still happen on the destination host. Snapshot register coverage and identity checks mean “one snapshot works on every arm64 host” is not established. [Snapshot loader](../../jitk/shard/src/snapshot.rs).

**I — Define a release manifest before an installer.** Include release/API version, target OS/architecture, minimum tested OS/runtime, backend/profile, exact host/kernel/helper/addon hashes, ABI/feature versions, dependency notices and source provenance. Ship the files needed by that profile together. Resolve paths relative to the installed package, write caches/diagnostics to user-writable application directories, and keep installed artifacts immutable. Fail on incompatible/missing pieces; never download a moving `main` or choose `local-qjs` as a fallback.

### 4.2 macOS signing, entitlements and notarization

**F — Hypervisor.framework permission belongs to the process using it.** Apple requires `com.apple.security.hypervisor` for any process using Hypervisor APIs. It is different from the Virtualization.framework entitlement. Current [hypervisor.entitlements](../../jitk/vmm/hypervisor.entitlements) has that key, and [build.ts](../../jitk/vmm/build.ts) strips then ad-hoc signs the VMM. This is suitable local build behavior, not evidence of Developer ID signing or notarization. [Apple entitlement reference](https://developer.apple.com/documentation/BundleResources/Entitlements/com.apple.security.hypervisor).

**F — For a new public notarized distribution, Apple's requirements include Developer ID signing, hardened runtime, secure timestamps, valid XML entitlements, an appropriate SDK, and no enabled `get-task-allow`.** Use `notarytool`, inspect the acceptance log and validate the distributed artifacts; notarization is an automated scan, not an external security audit. Shared libraries inherit executable entitlements, so a child VMM lets Node keep its normal signature. Do not add host JIT entitlements merely because QuickJS executes guest JavaScript; determine actual host executable-memory needs from the build. [Requirements](https://developer.apple.com/documentation/security/notarizing-macos-software-before-distribution), [hardened runtime](https://developer.apple.com/documentation/Security/hardened-runtime).

**F — Notarization accepts ZIP, DMG and signed flat installer packages.** A standalone command-line binary can have a notarization ticket, but neither a raw binary nor a ZIP can be stapled directly. A stapled PKG/DMG is a useful offline distribution path; a notarized CLI extracted from npm/ZIP relies on the online ticket when assessed. A Homebrew bottle or npm tarball is not itself a notary submission container. Do not claim that packaging alone bypasses Gatekeeper. [Custom workflow and stapling limitations](https://developer.apple.com/documentation/Security/customizing-the-notarization-workflow), [Apple's notarization action](https://github.com/Apple-Actions/notarize).

**I/E — Release workflow:** finish all relocation/fixups → sign nested native code and VMM with only required entitlements → sign a Developer ID distribution → notarize and require acceptance → publish exact hashes → test a quarantined download on another Mac. Never ad-hoc re-sign the released VMM during install, which would replace the distributor identity. Budget **1–2 days engineering** and **$99/year membership**, with enrollment/issuance delay outside that estimate. Linux-only private evaluation does not require this spend; public Apple Silicon onboarding benefits directly from it. [Membership terms](https://developer.apple.com/programs/enroll/).

### 4.3 Linux KVM permissions and failure messages

**F — The host needs working KVM and read/write access to `/dev/kvm`.** Firecracker's official guide documents distribution-specific `kvm` group and ACL approaches. Being arm64 does not establish usable KVM, and a guest cloud VM needs supported nested virtualization if it is not bare metal. [KVM prerequisites](https://github.com/firecracker-microvm/firecracker/blob/main/docs/getting-started.md).

**I — `doctor` should check:** native OS/architecture; running Node architecture; device existence and read/write access; a bounded KVM API/create-VM probe; required KVM/CPU features; host page size; addon load; artifact identity; writable cache; and one tiny completed/reaped guest. On macOS check entitlement/signature and a bounded HVF operation instead. Return actionable distinct reasons: unsupported target, virtualization absent, permissions denied, incompatible CPU/snapshot, missing addon, stale artifact, timeout. Diagnostic logs go to stderr; `--json` has a schema version.

**I — Document administrator actions, never execute them silently.** Where `/dev/kvm` is owned by group `kvm`, an administrator can add the user with `sudo usermod -aG kvm "$USER"`; the user must establish a new login/group session. Where ACLs are used, document a narrowly scoped ACL and whether it survives reboot. Do not recommend world-writable `/dev/kvm` or making the whole Node process root. In containers the numeric host group and device cgroup access must both line up. These are deployment instructions grounded in the cited host documentation, not changes made by this research.

**F/I — Page size is part of the experience.** The new copy-restore optimization falls back to discard on non-4-KiB hosts. A 16-KiB arm64 host can therefore have a valid execution path with a different latency profile; `doctor` must not advertise the 4-KiB nested measurement as its expected speed. [Copy-restore policy and limits](../../jitk/bench/RESULTS-copy-restore-2026-10-28.md).

### 6.2 Proposed surface

**I — Proposal, not existing exports.** Keep the documented root surface to `open`, `defineTool` and the following runtime operations; publish framework adapters at `/cloudflare`, `/tanstack` and `/ai`, and the MCP executable separately. Use JS/TS initially. Native bindings, custom backend implementation, snapshot format, policy engine internals and diagnostics stay outside the stable root contract.

**I — Make Linux shard opt-in explicit during this release.** The initial qualified root entry can support macOS arm64, while a separately marked `/experimental` entry selects the Linux shard and returns the same result shape with its actual limits. Add it to the qualified default matrix only after parity/containment acceptance; package installation, API-shape stability and backend maturity are separate claims.

```ts
type Json = null | boolean | number | string | Json[] | { [key: string]: Json };
type ErrorCode =
  | 'TIMEOUT' | 'CANCELLED' | 'POLICY' | 'LIMIT'
  | 'OVERLOADED' | 'SANDBOX' | 'GUEST_ERROR' | 'UNSUPPORTED';

type RunResult =
  | { ok: true; result: Json; logs: string[] }
  | { ok: false; error: { code: ErrorCode; message: string }; logs: string[] };

interface RuntimeOptions {
  profile?: 'javascript';
  timeoutMs?: number;
  maxConcurrent?: number;
  maxQueued?: number;
  tools?: Record<string, Record<string, HostTool>>;
}

interface Runtime {
  readonly info: RuntimeInfo;
  execute(input: {
    code: string;              // async function body, e.g. "return 2"
    timeoutMs?: number;
    signal?: AbortSignal;
  }): Promise<RunResult>;
  close(): Promise<void>;
}

declare function open(options?: RuntimeOptions): Promise<Runtime>;
```

**I — `HostTool` is produced by `defineTool`, not an unchecked raw callback.** Its documented definition takes description, input/output JSON schemas with actual trusted validation, required effects `{reads: 'none'|'public'|'private', egress: boolean, writes: boolean}`, and an async host implementation accepting **one JSON input object** plus `{signal, idempotencyKey}`. Adapt that object into the existing canonical argument array internally. The implementation may close over host credentials; no credential, function object, provider path or approval callback is serialized into guest arguments. Reuse current canonical validators/policy; do not add an independent security engine to the wrapper. A schema describes permitted values only when it is actually enforced.

**I — Start without public approval suspension.** Calls requiring approval fail `POLICY`; a later explicit host approval extension can be designed around existing call-bound approval. This preserves current fail-closed MCP behavior and avoids pretending an execution can durably pause. Effect declarations remain mandatory even when the application supplies no approver. Schema-generation/type libraries can be adapters around the public schema contract rather than a promise that every consumer must import the repo's exact Zod internals.

**I — `RuntimeInfo` is deliberately small:** package version, resolved host/backend/profile identity, supported feature flags and effective numeric limits. Expose feature flags for JS, native profiles, timers and state persistence only if verified. Artifact hashes/ABI identity can be included for reproduction; PIDs, absolute cache paths, queue implementation, timing-hook enums and kernel register formats are diagnostics. Memory fields must distinguish configured guest/heap limits from measured marginal physical memory.

**I — Initial example, after implementation:**

```ts
import { open } from '@sofort/runtime';

const runtime = await open();
try {
  const out = await runtime.execute({ code: 'return { answer: 6 * 7 }' });
  if (!out.ok) throw new Error(`${out.error.code}: ${out.error.message}`);

} finally {

}
```

### 6.3 Contracts to freeze and limits to make visible

1. **I — Execution unit:** each call gets clean guest execution state. Implementation may allocate a fresh VM or reset a consumed slot from pre-tenant state; do not promise a new KVM file descriptor/PID for every call on the shard. No user globals, writable guest state or ungranted capability carries between calls. A runtime handle is a host-side owner, not a persistent user computer.
2. **I — Source:** standard supported JavaScript async function body; explicit `return` for values; no imports, Node globals or package installation. Default result for no return is JSON null, consistent with existing API checks. Framework wrappers may accept upstream arrow syntax and strip types where the upstream actually does so.
3. **I — Values:** JSON domain only, with finite numbers, well-formed strings and documented byte/depth limits; reject unsupported values predictably. Do not promise Buffer/Date/Map/BigInt transport because a private codec handles some richer cases. Schemas/types for host tools are not proof that model-written guest code returns a particular application type; validate at the application boundary.
4. **I — Deadlines and queues:** `timeoutMs` includes admission waiting and host-tool round trips; per-call timeout may tighten the runtime maximum, never enlarge it. Bounded FIFO; full queue reports `OVERLOADED`. Abort produces `CANCELLED`, deadline produces `TIMEOUT`; preserve cause at the core, not by parsing English strings. Positive finite integer configuration is validated before allocation.
5. **F/I — Cancellation limits:** host tool signals are cooperative. A synchronous callback blocking Node delays the returned Promise even if an independent watchdog kills guest execution. Cancellation cannot undo a completed external write. The existing idempotency key is a per-run call identity, not cross-retry exactly-once delivery. **No automatic retry** after guest/tool effects. [Executor cancellation documentation](../../jitk/executor/README.md).
6. **I — Failures:** operational execution outcomes resolve `RunResult`; bad `open` configuration/artifact/host support can reject a documented typed initialization error. `message` is diagnostic and unstable; callers branch on code. A caught tool failure can still yield an overall successful guest result, as current [api-check.ts](../../jitk/executor/api-check.ts) demonstrates. Never convert an unknown sandbox failure into a successful null result.
7. **I — Close:** idempotent; refuses new admissions, cancels queued/running work and awaits owned child teardown/reset/disposal. Successful execute may resolve before deferred cleanup; only close/drain-level lifecycle evidence establishes cleanup completion. This keeps the existing resolve-before-reap behavior explicit.
8. **I — Tool registration:** immutable trusted-host registry per runtime; exact tool identity/effects and bounded calls. No model-selected provider modules, host paths or credentials. Adapters must reconcile their tool bindings with this registry instead of bypassing policy for convenience.
9. **I — Scope:** local execution, no hosted endpoint or tenant abstraction. No promised user snapshot/resume/fork, shell, writable workspace, Python guest or arbitrary native executable upload. Existing experimental native profiles can be documented separately with their actual lifecycle and byte I/O.

**F/I — Do not hide backend parity behind a uniform function signature.** Current ring code bounds source at **8,192 bytes including wrappers**, tool call/reply payloads at **1,024 bytes**, and the shard launch encodes **32 calls** and a **60,000 ms maximum deadline**. macOS's process path has wider protocol budgets and different clock/timer behavior. A 2-KiB JSON object can therefore be a real application blocker on Linux even if a small hello-world passes. [Shard adapter](../../jitk/executor/shard-backend.ts), [ring bootstrap](../../jitk/kernel/ring-bootstrap.js), [protocol limits](../../jitk/protocol/dispatcher.ts).

**I — Release one common advertised JavaScript contract only after the same corpus passes both backends.** Until then, stable API shape and backend feature maturity are separate: the Linux profile is experimental and `info` reports its lower limits. Preflight encoded source/argument/result sizes before handing them to a guest wherever possible. Do not advertise “8 KiB of user code” while trusted wrappers also consume the budget; report available encoded budget and a precise limit failure. Timers should be excluded from the initial common contract until parity work supplies them. Features absent on a backend fail explicitly rather than emulate an unsafe host capability.

### 6.4 Version and stability policy for one maintainer

**I — Adopt an explicit supported subset of SemVer rather than “anything may change because 0.x.”**

- **0.1.x:** preserve documented root exports, input/result/error schemas, CLI options and MCP `execute` contract. Patch releases fix bugs/security issues; new optional capabilities normally use a minor. Never replace the pinned native artifact under the same package version.
- **0.2.0 and later pre-1.0 minors:** may contain announced breaking changes, with a migration note, exact old/new examples and an explicit list of affected profiles/adapters. Where feasible keep a deprecated shim for **one minor and at least 30 days**; this is a proposed maintenance policy, not a commitment already made by the owner. Security fixes may tighten rejected inputs immediately, with release notes.
- **1.0 gate:** external clean installs, an independent reproduction, backend contract corpus and at least two real consuming applications without undocumented internal imports. After 1.0, documented breaking changes require a major version; security enforcement exceptions stay explicit.
- **Adapter compatibility:** publish tested peer ranges separately from core version. Begin with the repo's pinned Cloudflare **0.5.5**, TanStack **1.0.0** and AI SDK **7.0.152** baseline; add supported current versions only after executing their generated-code tests. Do not claim compatibility merely because TypeScript structural assignment passes.
- **Three identities:** SDK/package SemVer, MCP protocol negotiation version, and private kernel/shard/snapshot ABI version are different. Keep API/CLI/MCP package versions aligned initially for maintenance convenience, while checking internal ABI compatibility explicitly. No public snapshot format guarantee in v0.
- **Support scope:** one tested Node major, two arm64 targets and the current release line. Publish known limitations and a changelog; avoid an enterprise SLA or multi-year backport promise. Save upstream test fixtures and original failing application inputs so version upgrades test behavior, not just types.

**I — Required qualification work is proportionate:** extracted-package smoke on both target machines; no compilers/cache/repo siblings; addon and entitlement verification; two concurrent tools finishing out of order; timeout/cancel while queued and running; close/reap; stale artifacts; unsupported host; empty versus omitted result; schema/effect denial; source/reply boundaries; and generated Cloudflare/TanStack wrappers. Reuse the existing conformance suites. Packaging cannot be accepted from a demo on the machine whose cache accidentally supplies missing files.

## Rejected ideas

- **I — Hosted SaaS as the initial distribution fix:** adds tenancy, authorization, quotas, operations and support before a narrow user has asked for them.
- **I — Publish the current private executor package unchanged:** sibling paths, external dependencies, receipts, addon compilation and snapshots still depend on the checkout.
- **I — Single-static-binary rewrite now:** replacing the canonical Node executor/policy is much larger than distributing the existing runner plus its files.
- **I — Every framework gets a full sandbox provider:** shell, writable state, packages and process semantics are absent; interface names cannot supply them.
- **I — Claim to replace Anthropic hosted code execution or Monty Python:** neither is a generic interchangeable JS backend contract.
- **I — Homebrew core, OCI, Nix and five host SDKs at launch:** a solo maintainer would multiply release/support surfaces before validating the common payload.
- **I — Postinstall downloads/builds and unsigned fallback execution:** make installation network/toolchain-dependent and conceal artifact or boundary failures.
- **I — One raw KVM register snapshot for every arm64 machine:** cross-host CPU/KVM/page-size compatibility is not established; prepare and bind it locally.
- **I — Public MCP HTTP as an instant hosted tier:** current loopback transport does not implement service authentication, tenant control or operational ownership.
- **I — A universal sub-minute onboarding headline now:** no clean-machine install was measured; use a visible target until actual recordings support a number.
- **I — Another broad market pitch or more benchmark-only clips:** prior reports cover positioning; this gap needs an executable path from interest to useful work.
