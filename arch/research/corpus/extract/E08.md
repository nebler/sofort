## Recurring themes and disagreements across this share

All synthesis in this section is **I**; the supporting observations are **Q** at the cited minute buckets.

1. **Separate policy, durable state, and execution.** Google separates interactions from environments (46 09:00–10:00); Pai praises separate harness/hands (49 03:00–04:00); Anthropic explains a durable harness plus disposable execution (50 1:03:00–1:06:00); Exo adds an explicitly stateless mutable executive (52 16:00–20:00). This is a recurring architectural convergence, not an unclaimed invention. [Google example](https://www.youtube.com/watch?v=Y_p3y6zP5QE&t=540), [Exo example](https://www.youtube.com/watch?v=5lFD-34dhqE&t=960).
2. **Code composes operations better than long tool menus, but moves complexity into execution.** Arize uses code for math and large-result inspection (45 04:00, 11:00); Phoenix adds Bash/Python/SQL/UI programming (47 06:00–08:00); Cloudflare exposes its entire API through search/execute (48 24:00–30:00). Partial effects, discovery, nested runtimes, and binary output remain pain in 47 09:00–11:00. The bridge between code-capable systems is more interesting than another Code Mode wrapper. [Arize limitations](https://www.youtube.com/watch?v=dAoOYFx7ZYw&t=540), [Cloudflare implementation](https://www.youtube.com/watch?v=-ZikRWR1Gb4&t=1440).
3. **Context selection is both a cost and a behavior boundary.** Arize's bounded files/checkpoints (45 10:00–13:00), Code Mode result filtering (47 03:00–05:00), preserved-thinking migration (50 08:00–13:00), and Exo's cross-thread Discord fix (52 39:00–41:00) all concern which information enters each call. Cheaper context is useful only if relevant evidence and user separation survive. [Arize memory](https://www.youtube.com/watch?v=YIhvrvHtonk&t=600), [Exo cost case](https://www.youtube.com/watch?v=5lFD-34dhqE&t=2340).
4. **Secret non-disclosure and permitted action are different properties.** Placeholder/proxy credentials appear in 46 12:00–13:00 and 50 1:05:00–1:07:00; short-lived read-only grants appear in 51 16:00–18:00; Exo separates storage in 52 27:00–28:00. King's composition/sixth-operation concern (47 09:00) and the host's unexpected-AWS-key example (52 28:00) ask what the agent should do with delegated authority. No claim here that a proxy alone proves task correctness. [Composition concern](https://www.youtube.com/watch?v=dAoOYFx7ZYw&t=540), [Credential-use concern](https://www.youtube.com/watch?v=5lFD-34dhqE&t=1680).
5. **Autonomy is not a universally ordered quality metric.** One user calls a model lazy; another objects that it acted too soon (50 34:00–38:00). The Orbs interview debates unrestricted assistants versus bounded permissions (51 18:00–20:00). Torsten's reviewer can move feedback before a commit (43 04:00). Testing needs the user's intended scope and intervention preferences, not only task completion. [Personalization debate](https://www.youtube.com/watch?v=MRQTlwcW-aQ&t=2040), [Orbs debate](https://www.youtube.com/watch?v=hvwtHZ5E27c&t=1080).
6. **Interactivity needs a control path that remains responsive during work.** Portals already queues and steers comments (43 04:00); Exo's author describes having to open another conversation because a working thread cannot answer (52 31:00–32:00). These are different products and behaviors, not evidence that all agents are uninterruptible. The useful question is what changes, cancels, or remains in flight after steering. [Portals](https://www.youtube.com/watch?v=2MUWvEbQI0w&t=240), [Exo discussion](https://www.youtube.com/watch?v=5lFD-34dhqE&t=1860).
7. **Boot, failure, resume, and cleanup are distinct from successful code generation.** Runpod config experiments wait on loads/restarts (44 04:00–09:00); Phoenix has sandbox boot/debug failures (47 08:00–10:00); Anthropic rejected a boot-the-agent-in-a-box API (50 1:04:00); Amp's top complaint is startup and it criticizes missing resume (51 09:00, 27:00). Cloudflare's demo also needs session-created resources removed (48 22:00–23:00). [Amp lifecycle pain](https://www.youtube.com/watch?v=hvwtHZ5E27c&t=1620), [Cleanup request](https://www.youtube.com/watch?v=-ZikRWR1Gb4&t=1320).
8. **An architecture can erase compute state without losing the user's work only if ownership is explicit.** Google's fresh interaction/same environment (46 10:00), Anthropic's sandbox death/durable harness (50 1:04:00), and Exo's executive replacement/protected history (52 17:00–20:00) approach this from different directions. Packaging a new hosting primitive is taken; checking what survives a transition is narrower.
9. **Verification demand survives cheaper implementation, but its placement is disputed.** Arize preserves golden datasets in CI (45 18:00); Anthropic uses shadow traffic and verification for Rust (50 57:00–59:00, 1:24:00); Amp rejects mandatory code review and questions separate CI (51 07:00, 23:00–26:00). The disagreement is not “test versus never test”: Amp says its agent already ran tests. Independent test selection and reusable execution evidence are the unresolved boundary. [CI debate](https://www.youtube.com/watch?v=hvwtHZ5E27c&t=1380), [Rust verification](https://www.youtube.com/watch?v=MRQTlwcW-aQ&t=3420).
10. **Specialists versus one agent depends on coordination cost and task shape.** Arize collapsed ten page specialists into one skill-loading agent (45 13:00–14:00). Google demonstrates narrow sequential file-handoff agents (46 13:00–16:00); Anthropic recommends a lead and nonblocking workers for parallel tasks (50 1:45:00–1:46:00). These are useful competing recipes, not direct experimental contradictions. [Arize simplification](https://www.youtube.com/watch?v=YIhvrvHtonk&t=780), [Anthropic parallelism](https://www.youtube.com/watch?v=MRQTlwcW-aQ&t=6300).
11. **Model upgrades are integration changes, not just model-ID substitutions.** Runtime/CUDA support changes in 44 01:00–07:00; stop semantics change in 45 08:00–09:00; thinking preservation and controls change in 50 08:00–13:00 and 40:00–41:00. A portable harness needs observable compatibility fixtures, not a universal marketing promise.
12. **Inference economics have multiple denominators.** Runpod warns against unnecessary expensive fleets (44 14:00–15:00), Arize chooses fast/good-enough models (45 14:00), Anthropic emphasizes intelligence per dollar and CPU efficiency (50 08:00, 54:00–59:00), while Krentsel says frontier models are more expensive (52 03:00). These claims are not necessarily inconsistent: price per call, price per token, quality per dollar, and per-completed-task cost differ. They should be measured on the same task before declaring agreement or contradiction.
13. **The operator still owns the objective and acceptance check.** Arize uses human gold labels and human latency/quality decisions (45 17:00–18:00). Anthropic discusses conflicting taste and hard Slack decisions (50 34:00–40:00, 1:31:00–1:33:00). Exo acknowledges evaluator specification and reward hacking (52 38:00–41:00). Generic optimizer loops are in the background's kill list; owner-defined concrete outcomes remain necessary.
14. **Forking is becoming a distribution model, while ownership work remains.** Pai/hosts discuss owning and adapting dependencies (49 10:00–12:00); Amp plans jellyware to avoid running a maintained SaaS/open-source business (51 32:00–35:00). The stable frontend/backend contract wish is explicit in 51 12:00. A fork installer alone is uninteresting; preserving owner customizations across a real upstream change is an inferred narrower question. [Fork discussion](https://www.youtube.com/watch?v=287Q-bs_pEU&t=600), [Jellyware](https://www.youtube.com/watch?v=hvwtHZ5E27c&t=1920).
15. **Generated output can transfer rather than remove work.** Open-source maintainers close contributions after poor reports/patches (49 12:00); Anthropic engineers object to unreviewed documents burdening readers (50 1:21:00–1:23:00); a complex cookbook becomes a maintenance burden (50 1:38:00). Evidence-first issue packets and executable reference examples are concrete practices that might be packaged.
16. **Software's interaction surface may become programmable.** DOM-bound comments (43 02:00), Phoenix's Web Worker UI bindings (47 07:00–08:00), controlled code replacing DSLs (48 33:00–34:00), and an agent replacing settings screens (51 10:00–12:00) point in the same direction. The distribution/composition contracts between these surfaces are less settled than the basic generation feature.
17. **Originality is requested, not supplied by a new framework name.** Pai wants an original portable abstraction and applications near current capability limits (49 04:00–05:00, 13:00–14:00). Krentsel's self-editing implementation (52 20:00) and Anthropic's self-architecting prediction (50 1:46:00) show active competition. No line in this share supplies a concrete, unoccupied GrowOS-style prediction; the closest seed is the missing cross-runtime abstraction, still too underspecified to call a project.

## Five most interesting candidates

These are **I**, selected for the specificity or surprise of the practitioner signal, not certified empty markets. All are outside the kill list at the **narrow scope stated**; several are more credible as upstream fixtures/adapters than companies.

1. **P02 — Preserve artifact identity through nested Code Mode.** **Q:** King explicitly identifies double sandboxing, JSON serialization/parsing, and difficult image extraction (47 10:00–11:00). **I:** Start with one real composition: a Code Mode MCP server returning an image or large result to a harness that is itself in Code Mode. Pass a scoped artifact reference through both layers, with explicit ownership, expiry, fetch, and user display behavior; verify the payload never has to become model-visible base64 or an unnecessary JSON blob. **F:** MCP resource links already exist, so the [specification](https://modelcontextprotocol.io/specification/2025-06-18/server/tools) is a starting point. The interesting gap is preserving meaning/lifetime across actual runtimes. Exact prior art is **Unclear**; durability/snapshotting and a general Code Mode framework are excluded from the proposal.

2. **P11 — Show when Code Mode changes a permission rule's meaning.** **Q:** King says a permission can be right for five operations and wrong for the sixth, or wrong in composition (47 09:00). **F:** [Docker documents](https://docker.github.io/docker-agent/features/code-mode/#interaction-with-permissions-and-tool-approval) a concrete difference between direct and inner-call permission evaluation, while [Anthropic exposes](https://platform.claude.com/docs/en/managed-agents/permission-policies) context-aware per-call policy. **I:** Build a small fixture pack: the same allowed/denied tool sequence called directly, through a generated script, and through a nested wrapper, with a deterministic expected effect log. Report the first boundary where the intended rule stops applying. This is a portable behavioral comparison, not a new security model or generic labelled Code Mode system. Exact suite status is **Unclear** and an upstream contribution is the likely outcome.

3. **P01 — Evaluate a model rollout under conflicting real user profiles.** **Q:** Anthropic admits personalization evaluation is hard and cannot make one proactivity setting right for everyone; the host questions whether his own benchmark penalizes behavior that a user's instructions could change (50 34:00–38:00). **I:** Pair each coding task with at least two explicit profiles, such as “discuss before editing” and “carry the implementation through,” then score task result and unwanted action separately across a model/harness upgrade. This could reveal a supposed model regression that is actually a default-preference mismatch. **F:** [MemPABench](https://mempabench.com/) and [KnowU-Bench](https://arxiv.org/abs/2604.08455) already occupy broad personalization evaluation. The candidate is a narrow release-comparison adapter using owner-written profiles, not a new general personalization benchmark; broad status is **Being built**, exact adapter **Unclear**.

4. **P03 — Test interruption at the side-effect boundary.** **Q:** Krentsel describes a working thread that cannot answer and the absurd workaround of opening another conversation to ask what it is doing (52 31:00). Torsten already demonstrates useful queue steering (43 04:00), so “interrupt agents” is too broad. **I:** The interesting small project is an executable corpus for steer/cancel/status during long work: pending permission, an operation already committed, a late result, and a resumed session. Check whether the newest instruction is honored without falsely claiming to undo an external effect or resuming cancelled work. **F:** [ACP lifecycle work](https://github.com/agentclientprotocol/agent-client-protocol/blob/main/docs/protocol/v2/migration.mdx) already defines much of the contract and recommends fixtures. Status is **Being built**; proving one implementation's behavior against that contract is a concrete contribution.

5. **P09 — Rehearse an upstream update against a person's forked app.** **Q:** Pai/hosts want the neglected fork-and-adapt path (49 11:00), while Amp wants to distribute remixable jellyware without joining the maintenance business (51 32:00–33:00). The stable frontend/backend contract wish is explicit (51 12:00). **I:** Take one app with meaningful owner changes, stage one upstream patch, and show which custom behavior or service assumption the update breaks before applying it. The output should be a concrete conflict/reproduction rather than another merge bot. **F:** [GitBlixt](https://www.gitblixt.com/docs/instance-updates) and [Marin](https://marin.readthedocs.io/en/latest/dev-guide/forking-policy/) already cover update/fork maintenance mechanisms. Exact contract rehearsal status is **Unclear**; need is less proven than the first four and overlaps earlier app-upgrade research. What is new here is the practitioner prediction that fork-and-own distribution will become ordinary, making ownership of changes a potentially larger problem.
