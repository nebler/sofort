## Five most interesting candidates to carry into phase 2

These are **I**, selected for practitioner specificity and surprise rather than declared market novelty. None requires pitching a kill-list item as new. The narrow proposed checks are distinguished from the occupied mechanisms they would use. Two semantic candidates remain separate because a correct conversion and a compatible downstream application are different acceptance boundaries.

1. **Agent job bid calibration (P06).** **Q:** Jane Street actually saw agents assign excessive value to their compute jobs and preempt human work (08 35:00–36:00); this is a resource-allocation externality, not a complaint that inference is expensive. **I:** A small adapter could require owner-defined urgency/value ceilings, compare proposed bids with those constraints, and report which other jobs would be displaced. It should sit beside an existing scheduler and return a concrete counterexample to an excessive bid. **F / I:** Existing fair-share and quota mechanisms are substantial prior art (P06); the provisional gap is translating task intent into defensible bids, not scheduling or distributed-training operations. The first question is whether a fixed cap already solves the real user's problem.

2. **Semantic conversion witness, including governance (P02).** **Q:** The dbt presenter explicitly says semantic specs are not one-to-one and asks how governance survives their conversion (03 19:00–20:00). **I:** Run the same small business examples through source and destination implementations and produce one concrete discrepancy: a metric result, join grain, filter or caller's permitted view that changes. Unsupported features should remain explicit rather than disappear inside a successful YAML conversion. **F / I:** Apache Ossie already owns the common specification, structural validation and reference converters (P02); novelty is unproven, and the plausible work is an executable preservation check around those implementations. This is distinct from the earlier schema-lens idea because the evidence must include executed queries and authority, not merely round-trip structure.

3. **Semantic-consumer upgrade rehearsal (P04).** **Q:** An audience member cannot upgrade because Hex does not parse the new semantic specification (03 17:00–18:00), a concrete real consumer blocking progress. **I:** Given a customer's actual notebooks/cells, semantic project and version pair, rehearse parsing, available features and representative metric results before a cutover; report the smallest affected cell and the incompatible feature. **F / I:** Hex/dbt already ship integrations and migration guidance (P04). What remains unverified is the packaged rehearsal of the consumer's actual working artifacts across versions. Start by establishing what “V2” means in the reported incident; a new connector or generic API migration agent would not be the project.

4. **Shared-skill change impact rehearsal (P05).** **Q:** Jane Street says changes to shared skills can have unknown effects across different parts of the firm (08 01:07:00), while Michael and Peter both see required workflow steps silently skipped (04 16:00–20:00, 25:00). **I:** Let consumers attach small owner-defined behavioral fixtures to a shared skill; a proposed edit discovers those consumers, exercises the old/new skill in their actual harnesses, and shows step/artifact regressions with uncertainty from repeated runs. **F / I:** Existing regression guidance already covers prompt/tool changes (P05); the open question is consumer discovery plus distributed ownership, not another evaluation runner or “better prompt” generator. A full suite at one owner may already be sufficient, so adoption should be tested before building infrastructure.

5. **Controller-trace behavioral comparison harness (P01).** **Q:** Theo says he wanted to record his controller inputs in the reference skate game, replay them against his generated game and compare behavior, but settled for screenshot judges; he also reports an animation regression and expensive skybox optimization (01 07:00, 16:00–17:00). **I:** An input-conditioned comparison could align trick phases, trajectories and outcomes while keeping frame comparison secondary, making a physics/control claim independently inspectable. **F / I:** Qaping and Frame Perfect materially weaken the broad idea (P01). Only reference-versus-reimplementation behavioral alignment across different engines remains a specific hypothesis worth checking; start with one trick and abandon the project if those tools already provide it. It is interesting because the practitioner voiced the missing stronger test, not because record/replay is new.
