## Recurring themes and genuine disagreements across the share

1. **I — The durable asset can be an implementation grown against an existing semantic reference.** Simulation files plus SMT in Lakeroad (g2-02, 32:00–34:00), rendering equations in Olano's fitting workflow (g2-03, 33:00–47:00), the UET spec/simulator (g2-06, 08:00–09:00, 18:00–19:00), and LRM/VPI/sv-tests in Verilator (g2-08, 03:00–04:00, 10:00–14:00) are concrete **Oracle** signals. The growth mechanism itself is established prior art; the possible opening is a missing substantive implementation, not a new proposer/checker loop.
2. **I — Oracle quality and scope are the limiting factor.** Vendor simulation models may contain bugs (g2-02, 33:00–34:00); an unconstrained fit misses exact endpoints (g2-03, 45:00); tests miss visible game failure (g2-09, 1:02:00); model classifications hallucinate (g2-10, 12:00). Passing a reference says nothing about behavior outside its model/domain. A human-owned contract must remain separate from the generator's convenience.
3. **I — Effort plus oracle appears repeatedly, but usually inside occupied projects.** Two years understanding a DSP sheet (g2-02, 12:00–13:00), difficult e-graph export (26:00), repeated manual derivatives (g2-03, 54:00–57:00), manual policy/version maintenance (g2-07, 27:00), and weeks bringing four-state simulation to an actual core (g2-08, 09:00) are unusually good seeds. Lakeroad/Churchroad, Slang and Antmicro already work on most of them.
4. **I — Iteration delay is a material practitioner pain across domains.** Lakeroad's tiny compile/demo/CLI latency (g2-02, 07:00–08:00, 16:00), specialized shader compilation (g2-07, 35:00), Verilator's cache-invalidating generated output (g2-08, 14:00–15:00), and Blow's flow-breaking builds/asset processing (g2-09, 31:00–34:00, 41:00–44:00) are not merely preferences about syntax. They suggest measuring end-to-end edit-to-result time.
5. **I — More parallelism or more information can make a system worse when composed incorrectly.** Thirty-one conventional workers lose to eight in Gustafsson's solver (g2-04, 18:00–21:00); richer HPCC signals lose to an older controller under packet spraying (g2-06, 1:13:00–1:15:00). Neither supports a universal claim that more threads or more telemetry are bad. The interaction is the engineering problem.
6. **I — Explicit disagreement: build caching versus full rebuild simplicity.** A UVM user urgently wants ccache reuse (g2-08, 14:00–15:00), while Blow deliberately avoids incremental builds because of confusing state and bugs (g2-09, 43:00). Workload scale, generated output and current full-build cost differ. A fast clean rebuild is a reference behavior; persistent caching needs an equivalence argument.
7. **I — Explicit disagreement: should standards text plus LLMs close semantic gaps?** Weston's optimism about proof-guided AI (g2-01, 31:00, 37:00–40:00) and an audience proposal to analyze all four-state clauses (g2-08, 17:00) meet Biegański's skepticism that this finds real-world esoteric cases (18:00). This is a disagreement in emphasis, not a controlled comparison of the same task. Existing public designs should be held out from the generation loop.
8. **I — Cross-target portability hides missing semantics, not just spelling differences.** Adobe's emulation layers and least-capable-target constraints (g2-07, 21:00–22:00), difficult Metal ray-tracing lowering (52:00), API profiles/wildcard differences in UET (g2-06, 46:00–54:00), and FPGA primitive-specific mappings (g2-02, 00:00–13:00) make a generic transpiler inadequate.
9. **I — Runtime truth beats compilation or nominal conformance.** UVM compiles and quits or produces wrong results (g2-08, 01:00); Blow's tests miss invisible objects and absent author markup (g2-09, 1:02:00); a stale artifact reference is sometimes harmless until actual consumer behavior is examined (g2-10, 06:00, 10:00–13:00). A compiler success signal cannot serve as the whole oracle.
10. **I — Secure defaults and structural prevention outlast advice alone.** Weston argues for stronger boundaries (g2-01, 30:00–44:00); Steindler says documentation did not change millions of unsafe workflows (g2-05, 03:00, 11:00–17:00); Shudrak wants non-reusable/scoped ownership (g2-10, 35:00–36:00). This supports preventive implementation, not more incident-discovery tooling.
11. **I — Trust/ownership must survive lifecycle changes.** Package release authority (g2-05, 13:00–16:00), UET job/security/context lifetimes (g2-06, 48:00–50:00, 59:00–1:06:00), and deleted artifact hosts (g2-10, 03:00–04:00, 33:00–36:00) all expose a gap between a name and the authority attached to it. These are related obligations, not identical protocols.
12. **I — Better compute/code generation does not erase physical, human or institutional bottlenecks.** Light-speed/cooling/capex (g2-06, 03:00–15:00), GPU/CPU feedback latency and energy (g2-04, 25:00, 46:00–51:00), aesthetic judgment (g2-03, 14:00–15:00; g2-09, 51:00), and vendor coordination (g2-03, 1:12:00; g2-06, 26:00–27:00) remain. ## Five most interesting residual candidates — ranked, conditional

**I — Selection rule.** These are the five most interesting *implementation hypotheses* from this share outside the explicit rejected-project list. They are not five validated all-filter winners. Broad versions of each have substantial prior art, so only the residual described below is retained. No generic GPU-kernel agent, numerical revival, C-to-Rust migration, proposer/verifier framework, package-behavior atlas, browser specification, hardware-trace translation, preservation archive, OS/kernel growth or participant institution is proposed. All implementation sketches use C++, Rust, Slang, C or Lean; none requires Python for its core. A wrapper around an existing tool fails regardless of its branding.

### 1. P02 — A CPU execution backend for a substantial, bounded Slang ray-tracing subset

**I — Project and practitioner seed.** Let real Slang ray-query/ray-tracing programs execute on CPUs through a growing, checked semantic backend. In [g2-07](../transcripts/g2-07-the-khronos-group-developing-with-slang-tools-techniques-and-future-di.txt), 1:00:00–1:01:00, an audience member asks for CPU ray tracing and Yong says the work is possible but “haven't been prioritizing that work yet.” Adobe's missing cross-target emulation (21:00–22:00) supplies a production motivation. The value is concrete: run and inspect a useful class of existing shaders without RT hardware, and retain one material/geometry codebase. **F:** The current [slang-rhi matrix](https://github.com/shader-slang/slang-rhi/blob/main/docs/api.md) lacks CPU ray-pipeline/acceleration-structure support; [Embree](https://www.intel.com/content/www/us/en/developer/videos/improve-ray-tracing-on-cpu-gpu-with-embree.html) already handles traversal. **I:** The residual is semantic lowering and integration—payloads, attributes, instances, hit rules, callable behavior and declared unsupported features—not writing another traversal engine. Start with a ray-query subset, reject unsupported semantics explicitly, and extend only after tests pass. Adjacency to the active Slang team is a serious absorption/ownership risk; this has not passed an exhaustive prior-art check.

- **I — What grows / oracle / model tailwind:** Checked lowering rules and runtime implementations grow inside a versioned Slang backend with explicit capability boundaries. Oracles are public Slang/API definitions, independently constructed traversal/geometry cases, compiler regression tests and independent executions where semantics permit comparison. Better models implement more supported constructs and repair integration failures; accepted code continues to run without a model. Embree agreement alone cannot validate payload/control semantics.
- **I — One-shot test / non-code value:** A model can produce an Embree demo from one prompt. The proposed finished value is broad, maintained compatibility inside a real compiler, with independently fixed semantics, accepted implementations and held-out programs. That accumulated artifact and the human's support/acceptance design matter. Whether two better model generations could simply supply this whole residual remains **Unclear**; a small adapter does not pass.
- **I — Ambition rung and solo fit:** **Infrastructure for a field, bounded subsystem.** One ambitious C++ compiler engineer could begin without partners or new hardware; full DXR/Vulkan equivalence and every GPU feature are outside the initial promise.
- **E/I — Six-week version and demo:** A documented triangle/instance ray-query subset, several real Slang material functions and an explicit unsupported-feature diagnostic. Run identical source in a CPU executable, inspect a hit/payload in a native debugger, and compare against independently generated geometry cases. No claim of full renderer parity.
- **I — Strongest kill / cheapest test:** Slang or another project may already implement the exact subset, or a thin host wrapper may cover all useful demand. Inspect current backend code/issues and execute one nontrivial public shader locally before a substantial build. Stop the standalone proposal if the remaining work is small or already assigned; contribute upstream if useful.

### 2. P01 — Stable compilation boundaries for large generated verification models

**I — Project and practitioner seed.** Give large UVM simulations a generated implementation whose unaffected parts genuinely stay reusable after a small source edit. The audience's “one line ... all ... CPP file ... changed” in [g2-08](../transcripts/g2-08-fossi-foundation-next-big-step-for-verilator-towards-four-state-logic-.txt), 14:00–15:00, is unusually direct pain; Biegański says the team is not actively addressing it. This is not a claim to invent stable hashes or content-aware partitioning: [Verilator #2958](https://github.com/verilator/verilator/issues/2958) already proposes them, and it is closed. **F:** Present [documentation](https://verilator.org/guide/latest/simulating.html) still acknowledges widespread recompilation after minor edits; the [FAQ](https://verilator.org/guide/latest/faq.html) explains why global symbol structures help simulation speed while increasing recompilation. **I:** The residual worth investigating is whether persistent semantic identities, class/type boundaries and layout separation can remove *remaining measured* invalidation while preserving fast generated simulation. The clear value is shorter edit-to-simulate cycles on an existing large codebase. A reporting dashboard or ccache configuration helper is too small; a compiler representation change with real throughput constraints may be ambitious enough.

- **I — What grows / oracle / model tailwind:** The grown artifact is a compatible compiler/codegen architecture with increasingly covered UVM structures. Clean builds, declared SystemVerilog semantics, existing regression suites and execution checks are the correctness oracles; wall time, cache reuse, generated size and simulation throughput are separate cost checks. Better models can implement broader structural changes and maintain them across compiler evolution, within human-owned acceptance rules.
- **I — One-shot test / non-code value:** A hash-based file splitter is one-prompt code and already proposed. The only plausible durable value is a mature, measured compiler implementation preserving semantics across *type/layout/scheduling* changes and branch switches. This may still collapse to an upstream feature a stronger model writes quickly; **conditional**, not a proven moat.
- **I — Ambition rung and solo fit:** **Tool → hardware-verification infrastructure**, as a substantial upstream compiler subsystem. Public UVM/open hardware suffice for core work; private verification environments are optional validation, not prerequisites.
- **E/I — Six-week version and demo:** Identify one public class-heavy testbench with reproducible residual churn after existing build options are tuned. Change a single behavior, show which semantic dependencies truly changed, and demonstrate fewer compiled units with identical simulation observations. Report clean rebuild and runtime tradeoffs on the same machine.
- **I — Strongest kill / cheapest test:** Existing stable-splitting/hierarchical options may already solve the meaningful case, or global layout is essential to the cited simulation speed. Run a small source-edit matrix and trace invalidation causes before designing a new representation. If no large residual survives tuning, drop it.

### 3. P04 — An order-preserving CPU schedule compiler for iterative physics constraints

**I — Project and practitioner seed.** Grow implementations that overlap independent CPU constraint work while preserving an explicitly chosen solver's per-body operation order. In [g2-04](../transcripts/g2-04-better-software-conference-dennis-gustafsson-parallelizing-the-physics.txt), 55:00–56:00 and 1:02:00–1:03:00, audience members ask about overlapping iterations/per-body readiness; Gustafsson says it could be worth checking but expects complexity, atomic costs and perhaps little gain. His hand-written pool and observed 31-versus-eight-thread inversion (18:00–34:00) make the seed concrete. **F:** [enkiTS](https://github.com/dougbinks/enkiTS) already supplies efficient scheduling and [Jolt](https://github.com/jrouwe/JoltPhysics/blob/master/Docs/Architecture.md) already supplies deterministic parallel physics. **I:** Drop the generic thread pool and generic “parallel physics” pitch. The narrow residual is a solver-specific schedule implementation family with verified read/write dependencies, deterministic order and measured barrier/energy tradeoffs. The value would be more simulated objects within the same game frame budget, using public CPU workloads and existing solvers.

- **I — What grows / oracle / model tailwind:** Validated CPU schedule variants grow under a fixed constraint-operation contract. A dependency checker establishes permitted reorderings; a trusted sequential baseline checks arithmetic order/results for the supported subset; long-run settling scenes catch quality regressions; CPU measurements accept performance. Better models search/implement more of this difficult scheduling space while a small independent checker rejects illegal transformations. General LLM optimization loops are established; the useful artifact must be the substantive scheduler implementation.
- **I — One-shot test / non-code value:** A parallel-for wrapper is one-shot code. A broadly useful, order-preserving implementation with sound dependency extraction, bounded state and repeatable performance under preemption is the larger hypothesis. Accumulated valid schedules, semantic design and actual run measurements supply value. The chance that one future prompt can replace the narrow implementation remains material.
- **I — Ambition rung and solo fit:** **Product-scale systems library**, with a path into field infrastructure if it generalizes. Begin with one public solver and ordinary CPUs, not a universal engine rewrite or hardware fleet.
- **E/I — Six-week version and demo:** A C++/Rust dependency-aware executor for one small public projected-impulse solver; compare baseline coloring, scoped spinning and legal per-body overlap on identical piles. Show deterministic outputs plus end-to-end frame cost, overhead and joules where local measurement is available.
- **I — Strongest kill / cheapest test:** Gustafsson may be right that there is almost no profitable overlap. Offline critical-path analysis of a recorded public contact graph can bound the available saving before implementing a complex runtime. Also compare against existing Jolt/Box2D mechanisms; discard if gains require changing the quality contract.

### 4. P03 — A grown library of constrained rendering sampling implementations

**I — Project and practitioner seed.** Build an accumulating library of concrete Fresnel/inverse-distribution/sampling implementations whose domains, exact constraints and approximation errors are checked. The seed is Olano's repeated bespoke fitting practice in [g2-03](../transcripts/g2-03-the-khronos-group-siggraph-2026-real-time-shading-birds-of-a-feather.txt), 42:00–49:00: fit the real equation, preserve endpoint behavior, change variables to remove expensive inverse trig. **F:** [Sollya](https://sollya.org/sollya-8.0/help.php?name=fpminimax) already fits constrained approximants; [Gappa](https://gappa.gitlabpages.inria.fr/gappa/index.html) already supports arithmetic proofs. **I:** The surviving question is whether rendering contains a sufficiently large *unimplemented* family of useful inverse maps and sampling primitives that these tools do not already deliver. The result must be ready-to-use checked Slang/C++ components, each with a fixed domain and PDF/CDF or boundary obligations. Generic fitting, generic numerical synthesis, old numerical revival, automatic GPU kernels and a cross-device behavior atlas are dropped. If the proposal is only a front end around Sollya/Gappa, it fails. This is an interesting residual to investigate because its practitioner oracle is unusually clear, not because its novelty is established.

- **I — What grows / oracle / model tailwind:** Concrete rendering components and checked derivations grow. Human-written reference equations/domains, normalization/non-negativity/endpoint laws and independently checked error certificates govern promotion. Better models can derive representations, split domains and implement harder components; accepted routines remain cheap and model-free at render time. Mathematical validity does not establish perceptual quality.
- **I — One-shot test / non-code value:** One fitted Fresnel function is easy and not the project. The larger value is the accumulated implementation library, explicit domain contracts and independently checked derivations across distinct sampling problems. A future model may generate much of it at once; whether enough difficult unfinished components exist is the deciding open issue.
- **I — Ambition rung and solo fit:** **Product/library → bounded graphics infrastructure**. One expert can use public mathematics and CPU validation; target-specific benchmarks improve utility but do not require a GPU fleet for the core mathematical value.
- **E/I — Six-week version and demo:** Three useful, distinct functions: a constrained Fresnel approximation, one monotone inverse-CDF approximation and one inverse map with an expensive variable change. Ship Slang/C++ implementations and independent numerical certificates. Demo fixed constraints/error envelopes and a renderer cost improvement where measured.
- **I — Strongest kill / cheapest test:** A literature/library search may show existing implementations are already excellent, leaving only a polished wrapper. Before building infrastructure, find one practitioner-needed function where available libraries cannot meet a stated error/cost/domain contract. No such missing function was established in this extraction, so this remains below the three higher-ranked candidates.

### 5. P05 — A small verified artifact-resolution core with concrete fetch semantics

**I — Project and practitioner seed.** Implement a bounded artifact resolver that preserves authorized publisher/content identity through redirects, mirrors, cached objects and extraction/materialization decisions. Its clear value is a reusable high-consequence boundary component, even before adoption. This is the weakest of the five because existing clients may already cover the meaningful scope and the generic idea lies close to occupied proof automation.

- **I — What grows / oracle / model tailwind:** Checked implementation support grows for a deliberately small resolution contract.
