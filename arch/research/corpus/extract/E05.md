“Interesting” here follows the brief: surprising practitioner evidence and outside the supplied kill list. It does **not** mean five proven greenfield markets. Each paragraph separates the transcript signal (Q), checked overlap (F) and proposed narrow project (I).

**1. P13 — A production code witness for test-only abstractions.** **Q:** Mattis says an agent built him a check of decompiled output so an abstraction used at test time leaves only the intended instructions in production ([22, 1:28–1:29](https://www.youtube.com/watch?v=0GzwuYGvKA4&t=5280)). This is the strongest hand-rolled verification artifact in the share: a senior systems engineer wanted an independently inspectable claim about the actual compiled result. **F:** FileCheck and Rust codegen tests already provide the core mechanism; this is **Shipped**, not a new compiler-verification discovery. [LLVM](https://www.llvm.org/docs/CommandGuide/FileCheck.html), [Rust](https://rustc-dev-guide.rust-lang.org/tests/compiletest.html). **I:** A small library-facing wrapper could declare one elimination obligation, build selected targets/configurations, and attach a readable instruction/symbol witness in CI. It should check a narrow human-owned property rather than ask another model to certify performance. The first question is whether existing tooling makes the wrapper trivial; compiler/target brittleness may make this an upstream example rather than a product.

**2. P06 — Failure behavior fixtures whose business rationale can expire.** **Q:** The most distinctive example is Orosz's account of Uber changing from allowing uncertain payments during growth to rejecting them when profitability mattered, while Newman emphasizes feature- and amount-specific choices ([20, 1:23–1:25](https://www.youtube.com/watch?v=a0sZV0qIbI0&t=4980)). **F:** Executable policy testing is already available in OPA; the exact business-intent follow-through remains **Unclear**. [OPA](https://www.openpolicyagent.org/docs/policy-testing). **I:** Start with a tiny fixture format: unavailable dependency, business context, acceptable user consequence, decision, owner and reason. Run it during policy changes and prompt reconsideration when its explicit business trigger changes. The independent criterion is the product owner's concrete expectation, not a model inferring which trade-off is “safe.” This is not an all-purpose policy engine or generic chaos-testing pitch; the possible gap is preventing a technically functioning fallback from silently implementing yesterday's business strategy.

**3. P07 — Verify that the path to recovery survives the failure.** **Q:** The host's Meta door-access story illustrates a recovery action depending on the failed domain ([20, 1:30](https://www.youtube.com/watch?v=a0sZV0qIbI0&t=5400)); Mattis supplies a direct participant account of the foundation Bigtable used to break a Colossus bootstrap cycle ([22, 0:22–0:23](https://www.youtube.com/watch?v=0GzwuYGvKA4&t=1320)). The first anecdote's historical details remain uncertain; the second reinforces the general dependency problem. **F:** AWS already documents independent emergency access paths and periodic testing, so break-glass access itself is taken. [AWS](https://docs.aws.amazon.com/singlesignon/latest/userguide/emergency-access.html). **I:** Build a small declared recovery graph, remove a nominated dependency, and return the unavailable prerequisite chain for a specific recovery action. Include identity, DNS, secret retrieval, consoles and communication; physical access can be a declared manual prerequisite. Exact availability is **Unclear**. It is interesting because the normal service graph misses the steps needed to regain control, but it must demonstrate one real missing dependency before expanding into a general resilience platform.

**4. P05 — A corpus that distinguishes retry duplication from repeated intent.** **Q:** Newman describes the Danish terminal rejecting a legitimate second purchase for the same amount within minutes, and the equally legitimate loop provisioning identical EC2 instances ([20, 1:13–1:15](https://www.youtube.com/watch?v=a0sZV0qIbI0&t=4380)). The surprising requirement is not merely “deduplicate more reliably”: sometimes identical requests must execute twice. **F:** Stripe already ships key-based idempotency with payload checks; its documented API-version differences also show why a generic replay assumption is insufficient. [Stripe](https://docs.stripe.com/api/idempotent_requests). **I:** Package labeled histories for true retry, identical independent intent, changed payload under a reused key, concurrency, and expiry, then run them against a team's existing adapter. A human must supply operation identity and legitimate-repeat expectations. The exact shared corpus is **Unclear**, and it may be only a useful open test fixture collection. It avoids re-pitching idempotency middleware, payment infrastructure, or generic property-test generation.

**5. P15 — Close the loop on an architectural prediction.** **Q:** Pocock likens strategic programming to a mixing desk whose sound cannot be heard until nine months later, then asks how to demonstrate the value of fundamentals to stakeholders ([23, 1:01–1:07](https://www.youtube.com/watch?v=4DhcSPkEbwI&t=3660)). Newman independently describes brittle assumptions and targets that must evolve ([20, 1:05–1:07](https://www.youtube.com/watch?v=a0sZV0qIbI0&t=3900)). **F:** ADRs already capture rationale, consequences, confidence and reconsideration triggers; another decision document tool is not a gap. [ADR guidance](https://martinfowler.com/bliki/ArchitectureDecisionRecord.html). **I:** For one decision, record a falsifiable consequence (“changing checkout pricing will stay inside one module”), then collect the next few relevant changes and let the team compare the prediction with observed coordination, edits and incidents. Exact consequence follow-through tooling is **Unclear**. The small artifact could improve learning even if it is just a periodic review workflow; the main risks are attribution, sparse examples and teams not returning to review their own predictions.
