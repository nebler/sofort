## Recurring themes and disagreements

1. **I — Interfaces can create or remove the dominant work.** Eskildsen designs for independent, parallel object reads (g1-31, 00:31:00–00:37:00); Cloutier removes application/database round trips (g1-32, 00:20:00–00:21:00); Greef removes network-held locks (g1-36, 00:17:00–00:20:00). This supports redesigning a specific execution substrate, not assuming a faster implementation of an unchanged interface will help.
2. **I — The physical representation and convenient programming interface need not coincide.** Lugg's transient keys hide compact extra-data storage (g1-35, 00:26:00–00:30:00). Cloutier builds a fixed-width schema/transport representation for runtime reflection and cheap access (g1-32, 00:21:00–00:23:00). Pshenichkin deliberately separates his dedup tree's fanout from hardware page tables (g1-40, 00:17:00). This is a concrete family of grown executable artifacts, with no need for an institution or participant network.
3. **I — New bottlenecks appear after old layers disappear.** Object-store durability leaves metadata/listing and compaction economics (g1-31, 00:29:00–00:31:00; 00:44:00–00:45:00). Eliminating a game server leaves fanout and view invalidation (g1-32, 00:37:00–00:38:00; 00:46:00–00:47:00). Fast deterministic replay leaves snapshot memory/deletion (g1-40, 00:11:00–00:15:00). These are better seeds than duplicating the already-built parent platforms.
4. **I — Engineering effort is often integration effort.** Runtime schemas replace missing Protobuf affordances (g1-32, 00:22:00–00:23:00); Rust adoption crosses rustfmt/rustdoc/Clippy/bindgen/Kbuild (g1-34, 00:15:00–00:20:00; 00:27:00–00:30:00); composition crosses WIT, language bindings, and `wac` (g1-37, 00:12:00–00:15:00); urunc crosses OCI, VMMs, guests, and networking (g1-38, 00:09:00–00:17:00). Integration volume alone does not establish a durable project: many of these are explicit upstream roadmaps.
5. **I — Opaque state is difficult to verify or debug.** A Rust developer cannot see LLVM-inserted panic paths at source level (g1-33, 00:01:00–00:02:00; 00:07:00–00:10:00). A short-lived guest may disappear before `top` observes it (g1-38, 00:21:00–00:23:00). Antithesis can rewind and branch to inspect state (g1-40, 00:01:00; 00:08:00). The existing approaches operate at different layers and should not be treated as interchangeable.
6. **I — More realistic adverse conditions beat ordinary happy-path stress.** Actual hot keys invalidate uncontended OLTP results (g1-36, 00:08:00–00:11:00). Deliberate scheduler delays reveal the HSMP bug missed during a 24-hour run (g1-39, 00:14:00–00:16:00). Whole-system injected faults create rare interaction states (g1-40, 00:01:00–00:03:00). Broad automated chaos/fuzzing is already occupied territory; it is not a fresh agent-era Jepsen proposal.
7. **I — Memory locality and change-proportional work recur.** Zig avoids storing the largest union payload for every element (g1-35, 00:10:00–00:13:00). SpacetimeDB localizes a database to one core and sends incremental results (g1-32, 00:38:00–00:43:00). Antithesis updates snapshot accounting by the changed pages rather than all pages (g1-40, 00:14:00–00:18:00). A portable engine can accumulate specialized operations rather than merely accumulate observations.
8. **I — Centralizing state enables live changes, but boundaries remain.** Database histories enable procedure replay and planned client prediction (g1-32, 00:26:00–00:27:00; 00:58:00–00:59:00). Components can be swapped without rebuilding callers (g1-37, 00:11:00–00:12:00). Deterministic snapshots enable alternate histories (g1-40, 00:08:00–00:12:00). Each assumes a distinct state/ABI contract; none guarantees arbitrary upgrade safety.
9. **I — “Strong” and “correct” require workload-specific definitions.** Eskildsen chooses read-committed operations and current-index-plus-WAL reads (g1-31, 01:01:00). Greef insists on serializable transaction processing (g1-36, 00:22:00). Cloutier lets clients accept earlier durability stages (g1-32, 00:34:00; 00:45:00). These are tensions in product requirements, not a demonstrated logical contradiction between equivalent workloads.
10. **I — There is real disagreement over eliminating all failure paths.** Courbot wants visibility into implicit panics; other developers accept panic on an internal invariant violation and reject forcing Result everywhere (g1-33, 00:18:00–00:26:00). Greef's “correct and fast” stance (g1-36, 00:22:00–00:23:00) does not settle which failure policy is appropriate in a kernel driver. A panic detector must report facts before imposing policy.
11. **I — Data-oriented design is useful but does not solve every bottleneck.** Lugg demonstrates representation savings (g1-35, 00:06:00–00:13:00). Greef explicitly argues that those techniques cannot fix locks held over the network (g1-36, 00:30:00–00:31:00). This is a limit on applicability, not evidence that compact layouts are pointless.
12. **I — Deterministic simulation and scheduler chaos expose different classes.** Antithesis's one-core-per-VM restriction is explicit (g1-40, 00:05:00); SCX Chaos changes scheduling on real systems without changing the application (g1-39, 00:16:00–00:17:00). Neither talk establishes exhaustive weak-memory or true-parallel interleaving coverage.

### 1. P01 — A compaction engine optimized for object-store requests and dependency depth

- **I — Shape / tailwind:** What grows is the accepted implementation of compaction and layout policies inside an immutable-file/manifest architecture. No numerical improvement is promised before measurement.
- **I — Kill / cheapest test:** Add the proposed request-aware policy to an existing open engine before inventing a new one. If its current knobs match the result, or gains vanish on held-out workloads, drop the standalone project. **Verdict: strongest unresolved seed, not verified Open.**

### 4. P03 — A reusable snapshot DAG with cross-branch interning and independent reclamation

**Q — Seed:** Pshenichkin describes “inheritance upon deletion” (g1-40, `g1-40-let-s-do-a-lot-of-fuzzing-in-the-cloud-by-alex-pshenichkin-scylladb-p9.txt`, 00:12:00), then says subtree deduplication avoids “a million reference counts to update” (00:14:00). **I — Candidate:** A Rust library exposing fork/read/write/checkpoint/delete over sparse logical memory, sharing equal subtrees across independently produced branches and keeping update work proportional to changes. The value is more branchable state in a fixed memory budget for existing simulators and debuggers. **F/Q — Prior art:** Antithesis already implements the key technique and [ships multiverse debugging](https://antithesis.com/blog/multiverse_debugging/). **I — Residual:** A reusable library separated from a proprietary deterministic hypervisor, not a new algorithm or new testing platform; no unoccupied demand is established.

- **I — Shape / tailwind:** The growing artifact would be the snapshot engine's accepted data structures and specialized update/reclamation paths, under a fixed byte-memory API. A slow flat-copy store is the oracle; every branch must read the same bytes after arbitrary ancestor deletion, collision cases, and concurrent lifecycle operations. Better models can improve the engine's change-proportional behavior without changing the API.
- **I — One-shot test:** A persistent Merkle tree is plainly prompt-sized. The proposal survives only if a production-quality change-proportional engine is materially beyond ordinary persistent collections and retains verified performance improvements. Neither accumulated snapshots nor a large codebase automatically makes it durable value.
- **I/E — Ambition / solo / language:** Product → simulator/debugger infrastructure, approximately 10× solo in Rust without building a hypervisor. The hardware interface can be an adapter later; no physical partner or customer dataset is necessary for core semantics.
- **E — Six-week version / demo:** Fork many sparse memory states, create identical bytes through different histories, delete intermediate snapshots, and compare all surviving branches to a flat-copy reference. Report peak resident memory and work per changed page under sustained branching/deletion.
- **I — Kill / cheapest test:** Compare against an ordinary persistent radix tree and COW pages on that exact workload. If cross-branch sharing does not pay for hashing/accounting, stop.
