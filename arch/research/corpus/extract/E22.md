## Recurring themes across the share

1. **I — Verification, rather than code production, limits iteration.** Singh describes disproportionate DV staffing and reverification after every design change (g1-21 00:02–00:03, 01:01–01:05). Brooker says design/formal verification occupied much of a roughly three-year database project (g1-25 00:59–01:01). Adam describes thousands of library-model lines and specialist policy-writing effort (g1-29 04:00–05:00). Zhang starts from failures whose origins cannot be reconstructed from logs or dumps (g1-30 00:00–01:00). These are different bottlenecks; none establishes that an arbitrary new verifier would be useful.

2. **I — Existing checked representations are promising model-work boundaries.** Singh names temporal assertions, equivalence tools, Coq/Agda/Lean and structured circuit references (g1-21 00:09–00:10, 00:35–00:36, 00:49–00:52). Carruth names Miri and preserving C++ unit tests during migration (g1-24 29:00–30:00, 37:00). Hyperlight reused .NET tests through FFI and adopted WIT (g1-27 17:00, 22:00–27:00). Paralegal consumes marked dependency graphs (g1-29 10:00–15:00); KRR uses public LTP tests and historical reproducers (g1-30 11:00, 14:00). The model should build inside a fixed interpretation, not be allowed to replace the acceptance rule when it fails.

3. **I — An oracle may be incomplete, circular or perturbed.** Singh's “reference” network picture turns out to be his own, and HDL specifications/simulators disagree (g1-21 00:14–00:15, 00:35–00:37). Paralegal requires correct semantic markers and intentionally incomplete deletion policies (g1-29 07:00–09:00); an apparent deletion error is intended behavior (17:00). KRR makes executions repeatable partly by preventing parallel kernel execution, thereby masking one test bug (g1-30 14:00–15:00). A passing check is evidence for its stated obligation, not a guarantee of all desired behavior.

4. **I — Lifetime and invalidation cross nominally safe boundaries.** Carruth's Dawn example needs field-sensitive interior-pointer promises (g1-24 25:00–30:00). Omniglot separates allocation lifetime from the lifetime of a validated value (g1-28 11:00–14:00). Hyperlight's shared communication buffers need a different ownership discipline for concurrent calls (g1-27 34:00–35:00). Paralegal's type-only approximation loses dependencies around interior mutability (g1-29 15:00). Merely translating a function signature does not settle these temporal obligations.

5. **I — Delay work until an observation requires it, while retaining explicit invariants.** Tornow discards and reconstructs continuations after durable calls complete (g1-23 24:00–29:00). DSQL retains local writes and coordinates chiefly at commit (g1-25 20:00–30:00). LazyLog acknowledges durability before final ordering but exposes only a stable ordered prefix (g1-26 14:00–16:00, 23:00–24:00, 31:00–32:00). The implementations already exist; the reusable lesson is to identify precisely which intermediate result an application actually observes.

6. **I — Coordination costs survive faster code and hardware.** Tornow reduces coordination to waiting and recovery to retries (g1-23 06:00–08:00). Brooker emphasizes round trips and propagation limits (g1-25 35:00–38:00). Alagappan shows that black-box shards still coordinate internally even when an outer layer tries to avoid it (g1-26 26:00–29:00). Better models cannot remove causality or physical propagation; they may find valid specializations that remove unnecessary dependencies.

7. **I — Full rewrites have more dependencies than the code itself.** Carruth stresses tightly coupled APIs and staged migration (g1-24 02:00–06:00, 23:00–24:00). Hyperlight's migration duplicated every concurrent feature across two languages and glue code (g1-27 30:00). Schuermann adds domain expertise and certification as reasons to retain C libraries (g1-28 01:00–02:00). This supports concrete interop artifacts, but the broad automated-migration category is already on the kill list.

8. **I — Compositionality must include the dimensions that matter.** Singh composes behavior, layout, timing and scheduling rather than only gates (g1-21 00:25–00:31, 00:41–00:45). Tornow composes durable function executions (g1-23 14:00–19:00, 35:00). Omniglot composes scope constraints that individual valid operations otherwise violate (g1-28 11:00–14:00). DSQL composes catalog versions with ordinary transaction checks (g1-25 53:00–55:00). A generic “modular” label is insufficient without naming those dimensions.

9. **I — Simplicity has a boundary-dependent meaning.** Kladov removes extra tools and entry points but deliberately outsources real OS heterogeneity (g1-22 07:00–09:00, 19:00–23:00). Tornow concentrates recovery in functions/promises (g1-23 13:00–15:00). Carruth accepts substantially more language complexity to preserve brownfield compilation/API structure (g1-24 09:00–17:00, 31:00–32:00). This is a contextual tension, not evidence that one speaker refutes another: the relevant complexity has moved to a different owner.

10. **I — Useful evidence accrues against exact artifact versions.** TigerBeetle's release candidate accumulates passing simulation seeds before a later human decision (g1-22 42:00–43:00). Hyperlight's host/guest must agree on interface signatures (g1-27 21:00–27:00). Paralegal annotations must follow evolving source (g1-29 04:00–05:00, 09:00). DSQL validates catalog versions at read/commit (g1-25 53:00–55:00). A grown artifact needs versioned obligations, not an undifferentiated pile of “passed tests.”

11. **I — Performance comparisons require the same guarantee and workload shape.** Hyperlight explicitly warns that its rewrite comparison includes unrelated optimizations (g1-27 28:00–29:00). LazyLog shows the adverse case where read latency worsens (g1-26 36:00–37:00). DSQL distinguishes statement time, durable commit and client region (g1-25 39:00–44:00). ## Five most interesting residual candidates, ranked

These are **I — phase-2 investigation candidates**, not five projects verified to pass every filter. The ledger's strongest near-literal tailwind pitch—Lean hardware—is already being pursued. ### 1. C01 — A reconfigurable streaming circuit that carries checked transition controllers

**I — project and seed.** Build a fixed-interface FPGA streaming pipeline whose growing set of alternative implementations includes checked controllers for switching between them without losing or duplicating accepted stream items. The seed is unusually explicit: Singh says “dynamic configuration was hard to sell because it was hard to verify” and asks how many people can produce/believe the required proofs (`g1-21-acm-sigplan-icfp-25-functional-programming-for-hardware-design.txt`, 01:02–01:03). The valuable output would be usable circuit/controller combinations, not a catalog of observations about hardware. Keep scope to one FPGA family, one streaming handshake and a few state shapes. Functional circuit correctness, quiescence and state transfer are separate obligations; a digital proof does not prove the electrical assumptions. Prior work already verifies reconfigurable controllers and vendors already provide PR flows, so the precise possible gap is composable, retained transition implementations/proofs, not “verified reconfiguration” in general. This is the most interesting seed to investigate, not a claim of a new research field.

- **I — shape / what grows / oracle / tailwind:** accepted RTL blocks, transition controllers and reusable state-transfer lemmas grow inside a fixed stream semantics and region interface. Check stream refinement and controller invariants with a proof checker/equivalence tool; separately use the vendor PR model, timing/implementation checks and board tests. A better model can attempt more stateful transitions and repair more proofs while previously accepted artifacts remain executable. The specification and trusted hardware assumptions stay human-owned.
- **I — one-shot test:** a prompt may produce a toy switcher. The intended finished value is a family of independently checked, implemented transitions across multiple parameter sizes and state shapes, with proof and implementation results retained by revision. Resistance comes from successful compositional extension and physical validation, not merely the number of files. If a next-generation model can generate that whole bounded family with existing tools in one run, this fails the filter.
- **I — ambition rung / solo boundary:** **product**, with a possible path to field infrastructure. A single person building the semantics, transition mechanism and several real parameterized circuits is very ambitious; arbitrary vendor devices, arbitrary RTL and all electrical behavior are outside the proposal.
- **I — value proposition:** change the acceleration function on a running FPGA while keeping the surrounding stream's promised behavior.
- **E — six-week version:** one board, two small stream-processing personas, a deliberately unsafe swap rejected by the check, and an accepted stateful swap that continues processing under backpressure. Implement control/proof infrastructure in Rust plus Lean/Coq and RTL; use existing vendor tooling rather than rewriting placement or a kernel.
- **I — strongest kill / cheapest test:** this may already be the normal PR freeze/reset flow with a small proof bolted on, or a no-state handoff may eliminate the claimed need. Spend the initial days reproducing one vendor flow and the closest formal controller work; require a genuinely stateful transition that cannot be handled by the stock recipe. If that residual is absent, drop it before growing a library.

### 2. C02 — Checkable dependency summaries for Rust wrappers with interior mutability

**I — project and seed.** Extend an existing Rust analyzer with summaries that retain actual data dependencies through a bounded family of `Cell`/`RefCell`/lock-backed wrappers, instead of silently treating shared references as unmodified. Adam names expensive manual library models (g1-29 05:00) and explicitly acknowledges the interior-mutability exception (15:00) in `g1-29-usenix-osdi-25-paralegal-practical-static-analysis-for-privacy-bugs.txt`. The accumulated value would be soundly reusable analysis components that let existing policies inspect more real code. Keep policy vocabulary and privacy intent unchanged. **F:** Mendel already supplies a capability-based approach for clients using trusted library annotations, so the residual is checked dependency-summary derivation/integration, not inventing interior-mutability verification. [Mendel paper](https://pm.inf.ethz.ch/publications/PoliDenisMuellerSummers24.pdf)

- **I — shape / what grows / oracle / tailwind:** summaries and supporting derivations for pinned library bodies grow inside a small effect/dependency language. An independent checker verifies a summary against expanded MIR or a formally specified supported fragment; Paralegal consumes the checked result. Compiler tests and counterexamples are secondary checks, not a soundness proof. Better models help extend supported constructs and produce derivations; a summary is retained only under the same acceptance semantics.
- **I — one-shot test:** generating annotations alone is a prompt-sized task and fails. The intended non-one-shot artifact is the checker plus a versioned body-to-summary derivation chain that continues to establish dependency preservation as real wrappers change. Trusted primitives and unsupported constructs must be explicit. If the whole opportunity reduces to a few obvious `RefCell` models, it is an upstream patch and fails the ambition test.
- **I — ambition rung / solo boundary:** **product/component infrastructure** at about 10× scope if it covers a meaningful wrapper family with mechanically checked composition. Rust MIR integration and a bounded proof/checking layer are solo-plausible; full soundness for arbitrary unsafe concurrent Rust is not the proposal.
- **I — value proposition:** a privacy or access-control check should keep seeing the same relevant data when an application moves it behind shared mutable library wrappers.
- **E — six-week version:** a Rust implementation for `Cell` plus a few nested single-threaded wrappers, a real Paralegal policy that misses a dependency under type-only approximation, and the same policy correctly reporting it with the checked summary. Show rejection of a deliberately incomplete proposed summary. Leave general concurrency unsupported until its semantics is established.
- **I — strongest kill / cheapest test:** an existing Mendel/Flowistry/Paralegal feature or simply analyzing those bodies directly may solve the problem more cheaply. Construct a minimal reproducer against current Paralegal, then compare precise expansion with the proposed summary on a public wrapper. If no practical precision/performance trade-off remains, drop the standalone project.

### 3. C03 — Retained buffer-contract adapters for existing native libraries

**I — project and seed.** Build actual Rust adapters for a narrow family of native APIs whose legal aliasing and invalidation behavior cannot be read from a C signature. Carruth's concrete BoringSSL example permits input/output aliasing only under a particular relation while a tag buffer must remain separate (g1-24 20:00–23:00); his Dawn example hides which interior pointers a mutation invalidates (25:00–30:00). Schuermann shows why validating a value once is insufficient after later foreign calls (g1-28 08:00–14:00). The transcript files are the g1-24 and g1-28 files listed above. Build on Omniglot's existing soundness boundary; do not replace it with speculative alias inference. The possible residual is a set of useful, explicitly scoped API contracts and their executable adapters, not general safe FFI, not a migration agent, and not a cross-language memory-safety layer.

- **I — shape / what grows / oracle / tailwind:** checked adapters, range/overlap predicates and invalidation-state machines grow under a fixed ownership/validation core. Named API documentation, retained upstream tests and independent reference behavior supply functional obligations; compiler/compile-fail tests check lifetime promises; a small formal model checks the adapter's own state transitions. A stronger model can add more awkward API cases without changing the core boundary. Passing tests never substitutes for a missing semantic contract.
- **I — one-shot test:** a single binding, even one with clever pointer checks, is likely one-shot-sized. The larger candidate survives only if accepted adapters share enough checked structure that the accumulated executable library removes substantial repeated integration work across nontrivial APIs and revisions. The core value must be verified behavior that is used directly, not a registry or evidence atlas. This condition is currently unproven.
- **I — ambition rung / solo boundary:** **product** for one API family. Rust plus a small Lean/Coq model is plausible for a solo builder; reproducing cryptographic expertise, algorithm certification or proving arbitrary native libraries correct is outside scope.
- **I — value proposition:** use an existing high-performance native library from Rust with its unusual buffer rules made explicit and checked.
- **E — six-week version:** three concrete public APIs in one family, including the in-place/out-of-place distinction, an automatically proposed adapter rejected for allowing an illegal partial overlap, and a passing adapter exercised by unchanged upstream vectors. Include allocation and retained-reference cases so the demo is more than `bindgen` output.
- **I — strongest kill / cheapest test:** existing Omniglot scopes, crate wrappers or Carbon/Crubit may already cover the work, and library semantics may require expensive human decisions per API. Compare one difficult API's current wrapper with the proposed artifact. If the difference is a small wrapper or unverifiable model-written assertions, drop it.

### 4. C04 residual — Reusable physical transformations for one regular FPGA network family

**I — project and seed.** Grow a library of implemented, equivalence-checked layout transformations for one concrete regular circuit family, such as a parameterized switching network. Singh's Xilinx customers had enough nominal gates but designs would not place/route; his compositional layout made them fit (`g1-21-acm-sigplan-icfp-25-functional-programming-for-hardware-design.txt`, 00:24–00:25). [RapidWright](https://www.rapidwright.io/docs/Introduction), [Lakeroad/Churchroad](https://blog.yosyshq.com/p/lakeroad/). Consequently this is an investigation of a narrow physical-transformation residual, not a recommendation to build HLS, a mapper or a generic circuit proof agent.

- **I — shape / what grows / oracle / tailwind:** placement-aware transforms, valid parameter ranges and implemented network variants grow under a fixed circuit algebra. Check sequential/logical equivalence separately from device legality, timing and resource constraints; a proof of logic does not establish timing. Better models can propose folding, tiling and pipeline arrangements and their derivations, while the accepted implemented variants remain useful without a model.
- **I — one-shot test:** a generated layout script is readily eaten by a better model. Survival requires accumulated parameterized transforms that repeatedly deliver valid physical implementations where generic flows do not, with reusable proof/cost structure. Real implementation runs add value but do not by themselves make the project resistant to a stronger model; this must be demonstrated.
- **I — ambition rung / solo boundary:** **product** for a single network family and device family. A Rust/Haskell circuit algebra plus Java access to RapidWright and existing RTL tools is plausible; a new general placer/router is not.
- **I — value proposition:** make a useful regular circuit fit and meet its timing target while preserving its specified behavior.
- **E — six-week version:** reproduce a public baseline, then show a nontrivial folding/tiling transform across several network sizes, each retaining behavior and passing physical implementation. Report failures as well as successes. The compelling demo is an accepted circuit at a previously failing size, not a prettier diagram.
- **I — strongest kill / cheapest test:** this may already be a routine RapidWright pre-implemented-module exercise. Run that canonical flow before writing a new abstraction. ### 5. C05 residual — Progress-preserving admission plans for a controlled SQL workload

**I — project and seed.** Generate and retain executable client-side admission plans for a bounded transaction language, aimed at preventing a long writing transaction from being repeatedly displaced by short conflicting transactions. Nathan Bronson asks about the “starving elder” and Brooker answers that they do not presently address it (`g1-25-cmu-database-group-aurora-dsql-serverless-scalable-global-oltp-databas.txt`, 00:33–00:35). This is a precise systems gap but weaker commercial evidence: Brooker also says customer reports had not justified prioritizing it. **F:** fair database scheduling is already implemented in research such as DRFT, and CockroachDB's design addresses starvation with priorities. [DRFT](https://www.vldb.org/pvldb/vol18/p2602-cheng.pdf), [CockroachDB design](https://github.com/cockroachdb/cockroach/blob/master/docs/design.md). The only residual entertained here is a constrained client-only solution without internal database scheduling hooks; it has not been established as open.

- **I — shape / what grows / oracle / tailwind:** checked workload-specific admission plans and conflict decompositions grow inside a fixed read/write-set and bounded-duration transaction model. Check semantic equivalence, bounded exploration for counterexamples and a progress argument under explicit fair-worker/failure assumptions; benchmark on public PostgreSQL workloads. Better models might find less conservative plans as shapes become more complex. More clever scheduling cannot promise progress against uncontrolled conflicting writers.
- **I — one-shot test:** age-based retry/backoff is prompt-sized and fails. This candidate needs a genuine accumulated library of nontrivial, checked admission plans whose concurrency advantage survives realistic changes. If a FIFO gate or standard backoff gives similar progress and throughput, there is no remaining project.
- **I — ambition rung / solo boundary:** **product/component** for one cooperative client gateway. Rust plus SMT/proof-checking machinery and ordinary PostgreSQL suffice for core experiments; no AWS internals, private traces or vendor partnership may be required. Distributed all-client fairness is explicitly outside scope.
- **I — value proposition:** let a necessary large update finish under a busy controlled workload without pausing every unrelated transaction.
- **E — six-week version:** a public mixed-duration workload exhibiting repeated aborts, a naive serialized baseline, and a checked client admission plan that completes the long transaction while preserving more short-transaction concurrency. Include an uncontrolled-writer case that correctly refuses to promise progress.
- **I — strongest kill / cheapest test:** this may be existing DRFT/priority scheduling repackaged, require information a client cannot obtain, or lack a real workload benefit. Reproduce the starvation and compare ordinary FIFO/keyed gates and established approaches before using a model. Any one of those failures kills it.
