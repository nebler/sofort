### Disagreements to preserve, not average away

- **I — Laziness:** Subramaniam calls it essential to functional performance (P3-29 19:00–20:00); Volkmann shows a naive lazy-to-eager translation fails (P3-31 35:00–39:00); Feldman says purity was the more valuable Haskell lesson and pursues fast eager execution (P3-34 1:22:00–1:28:00). They discuss different scopes; none proves laziness always good or always bad.
- **I — Server authority:** Gillilan initially recognizes front- and backend-owned state (P3-34 07:00), later argues many apparent local-state problems vanish server-first (25:00–30:00, 53:00–56:00). Feldman insists private draft state and a saturated inherited database made local work correct (52:00–59:00). His requested experiment is never carried out in the episode (1:10:00).
- **I — Performance ceiling:** The JSON.parse ceiling asserted at P3-34 11:00–12:00 is qualified by selective binary access at 1:18:00–1:20:00. Different amounts of work must be compared explicitly.
- **I — Layout simplicity:** Muratori argues small explicit computations make layout transformations easy (P3-33 1:20:00–1:21:00); Gillilan stresses the difficulty of game-UI constraints (P3-34 34:00). A useful comparison must retain accessibility and the actual transformation requirements.
- **I — Architecture evidence:** Feldman treats survival and continuing features after Twitter staffing cuts as limited positive evidence; Muratori says "didn't roll over and die" proves little (P3-33 1:10:00–1:15:00). Neither has a validated universal architecture metric.
- **I — AI trajectory:** Campbell predicts tapering progress and dismisses broad AGI claims (P3-32 25:00–28:00, 40:00–41:00); the ambition brief deliberately assumes much stronger future models. This report retains his statements but does not base the finalists' value on models staying weak.

## Five most interesting candidates, after the ambition filter

All five are **I**, grounded in practitioner signals above. They are research directions with **Unclear** novelty, not five established startup openings. None is proposed as a generic agent runtime, code migration engine, proof generator, testing wrapper, agent-web component, or other item from the kill list. The distinguishing hypothesis in each case is an accumulated observation base or a participant institution. If that institution cannot be recruited, the implementation alone fails the one-shot test. The five are also related: they should not be mistaken for five independent businesses.

### 1. Runtime cost-contract commons

**I:** Muratori wants language designers to promise something dependable about what code costs (P3-33 1:02:00–1:03:00), and the two podcasts repeatedly show why intuition or a "fast" label is insufficient. Build toward a public body of real consumer workloads whose expected cost envelopes are acknowledged by runtime/library maintainers: input regimes, hardware, source constructs, generated behavior, and upgrade consequences. The large goal is to make performance an observable, negotiated part of software compatibility across an ecosystem. This goes beyond keeping one microbenchmark green. WebKit already has serious performance infrastructure; any credible project must complement it with useful outside workloads and consumers, rather than pretend the runner is new. [Existing WebKit infrastructure](https://webkit.org/blog/15249/).

**One-shot test — I:** A better model can build the runner, analysis, and suggested fixes. It cannot generate permissioned production workloads, genuine hardware observations over future releases, or commitments that outside maintainers and consumers have actually accepted. Those observations and relationships are the non-code value; absent them, reject this as another benchmark tool.

**Ambition rung — I:** **Field infrastructure.** The 100–1000× version makes resource behavior a shared compatibility language across runtimes and libraries; it is not a faster profiler.

**Smallest first step in weeks — I:** Recruit two unrelated application maintainers to contribute the real hot paths behind one surprising cost regression each. Measure them across two engine generations and two actual devices, and ask one runtime maintainer to annotate what is stable, accidental, or unsupported. The new result would be a jointly signed-off source-to-cost case with an explicit change boundary, not a synthetic object-versus-array anecdote. Such an agreement is a target, not something this extraction already obtained.

### 2. Software capability continuity commons

**I:** Muratori's "we lost functionality" in the Sketchpad comparison and both speakers' frustration with disappearing Windows workflows are unusually direct signals (P3-33 05:00–07:00, 1:15:00–1:22:00). Aim to preserve the human tasks software enables across upgrades, vendors, and eventual agent-written replacements. Users contribute the workflow, why it matters, observable completion, assistive needs, and authorized historical artifacts; maintainers can attach restoration or compatibility evidence. Cheap agents may make reconstruction feasible at ecosystem scale, but only the users can establish what was lost and which replacement counts. Software Heritage already provides an archive interface; source preservation alone does not settle this proposed task-level scope. [Existing Software Heritage archive implementation](https://github.com/SoftwareHeritage/swh-web).

**One-shot test — I:** A better model can generate adapters, demonstrations, and a compatibility shell. It cannot recover unrecorded user intent, obtain another party's artifact rights, invent original environments, or secure acceptance from people whose jobs depend on the behavior. The moat, if any, is a living user/maintainer network and its evidence.

**Ambition rung — I:** **Field infrastructure**, with a **field-changing** objective: make software replacement preserve accumulated human capability instead of repeatedly rediscovering it. A plain visual-regression suite would be only a tool and would fail the ambition filter.

**Smallest first step in weeks — I:** With one consenting user community, document three genuinely lost workflows in one application family, reproduce them in authorized old/new environments, and have the same users adjudicate a minimal restoration. Publish the task evidence and acceptance, including a failure. The new observation is whether a replacement restores the same capability, not whether it resembles an old screenshot. Confirm present product behavior before relying on the historical taskbar example.

### 3. Accessible graphics interaction commons

**I:** Feldman wants native-style, high-frame-rate tools but identifies the semantic accessibility tree as serious added scope (P3-34 30:00–34:00), and his classroom example makes accessibility an adoption condition (51:00–52:00). The large project is shared interaction knowledge and measured assistive behavior for dynamic editors, timelines, and dense visualizations across renderers. Begin with task semantics co-designed with people who use assistive technology; let agents produce renderer adapters and repairs against this externally owned evidence. AccessKit is already accessibility infrastructure and ARIA-AT already assesses screen-reader behavior. The proposed scope must therefore be developed with those communities; its claimed distinction is dynamic cross-renderer user tasks, not a new bridge. [AccessKit](https://github.com/AccessKit/accesskit/blob/main/ARCHITECTURE.md), [ARIA-AT's stated scope](https://raw.githubusercontent.com/w3c-cg/aria-at/master/README.md).

**One-shot test — I:** A better model may write an accessibility tree or adapter from a prompt. It cannot substitute for actual task observations, users' chosen interaction conventions, device-specific experience, or sustained agreements among toolkit and assistive-technology maintainers. Simulated screen-reader success alone would dissolve the proposed distinction.

**Ambition rung — I:** **Field infrastructure.** The 100–1000× outcome is that direct-rendered tools across a field inherit an evidenced accessible interaction model, rather than each app improvising it after drawing pixels.

**Smallest first step in weeks — I:** Co-design one timeline-editing task with two or three compensated assistive-technology users and compare a DOM implementation with an existing direct-rendered implementation. Record semantic/visual divergence and task completion, including disagreements about expected controls. The new artifact is participant-approved interaction evidence unavailable from a prompt, not another accessibility checklist. Compensation and participation would need to be arranged by a future project; none was requested or performed here.

### 4. Production web architecture trials network

**I:** Gillilan explicitly asks to recreate Feldman's overloaded classroom system and port it to Datastar (P3-34 1:10:00). This is a rare practitioner invitation to resolve a live architectural dispute. Expand that seed into a cooperative research network where actual teams contribute workloads and constraints, competing approaches receive the same acceptance budget, and participants publish outcomes and counterexamples. Required variables include private drafts, database writes, existing backend limits, multi-tab behavior, truthful acknowledgment, accessibility, and real networks. The 18-month redesign story supplies the cost of being wrong. An author-run Datastar/chatbot comparison already exists, so "hypermedia beats a reference app" is taken ground. [Existing comparison and caveats](https://zweiundeins.gmbh/en/blog/spa-vs-hypermedia-real-world-performance-under-load).

**One-shot test — I:** A better model can produce all competing implementations and execute load tests. It cannot fabricate real task frequencies, contractual/backend constraints, previously undisclosed user behavior, or independent teams' acceptance that the trial represents their problem. These are the value; a self-authored demo tournament fails.

**Ambition rung — I:** **Field infrastructure.** The 100–1000× goal is empirical architecture knowledge across many organizations, making longstanding disputes answerable with representative counterexamples rather than slogans.

**Smallest first step in weeks — I:** Work with one willing education-software practitioner to define a small draft/highlight/reorder workflow under a fixed database write budget. Implement both server-first and client-local versions, let the practitioner approve equivalent behavior, and publish device/network/write-load curves including where each wins. The novelty target is a mutually accepted, constraint-preserving result; a toy reconstruction without a real participant is only a preliminary demonstration.

### 5. Prospective product-decision/outcome commons

**I:** Simmons says the bottleneck is deciding what to make, then gives a concrete reversal: maintainers prefer deterministic labels to AI summaries (P3-30 07:00, 26:00–27:00). Campbell manually compares repeated promises month by month (P3-32 28:00), while Feldman's Meteor story shows how an attractive pitch omitted a crucial real user habit (P3-34 1:04:00–1:09:00). Build toward a participant-governed corpus of decisions recorded before the outcome is known: intended task, competing options, assumptions, constraints, what evidence would change the choice, and subsequent real user results. Retain misses and removals. The ambition is cumulative empirical product knowledge when implementation becomes cheap. Microsoft's ExP already supplies hypothesis-driven experimentation; this proposal lives or dies on voluntary cross-organization sharing and credible prospective history, not experiment execution. [Existing Microsoft ExP](https://www.microsoft.com/en-us/research/group/experimentation-platform-exp/).

**One-shot test — I:** A better model can create the registry, summarize discussions, and generate all UI variants. It cannot reconstruct an honestly timestamped prior belief after results arrive, create independent user behavior, compel confidential teams to share, or replace participants' trust. Those longitudinal observations and permissions are the non-code value.

**Ambition rung — I:** **Field infrastructure**, if it becomes a shared empirical record for product decisions; **product** if it remains one company's demo/decision organizer. Do not upgrade the rung merely by calling a database a commons.

**Smallest first step in weeks — I:** Recruit two unrelated teams to preregister one real choice each between generated prose and deterministic state labels. Record their own success criteria, obtain actual task feedback, and publish the original assumptions, outcome, and decision change with consent. The new result is prospective evidence including a negative outcome. A model-only taste evaluator or retrospective success story would not pass.
