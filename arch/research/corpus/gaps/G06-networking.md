# G06 — Networking and protocols

Research date: **2026-10-29**. Read `BRIEF-gaps.md`, `BRIEF-tailwind.md`, the round-13 summary and exclusions, the earlier networking revival report, and the complete 00:00–18:00 Homa transcript. Searched the prediction ledger and both transcript collections for TCP, QUIC, RDMA, network, latency and packet. This is desk research: implementations, proofs, interoperability and performance proposed below were **not** run.

**Labels:** **Q** = checked quotation; **F** = sourced fact, including an attributed research result; **I** = inference/design judgment; **E** = proposed scope, cost, threshold or experiment. Scores are **E**, not measurements. “Open” scores express uncertainty about the precise remaining scope, not proof that nobody is building it.

**I — Finding:** the useful shape is a growing **executable protocol implementation**, with independently checked semantics and a bounded deployment target. Another QUIC implementation, RFC-to-code agent, conformance dashboard, or parser generator does not pass the prior-art filter. Three narrower candidates deserve discriminating experiments; none has an established novelty moat. My pick is **HomaCore**, conditional on beating reuse of the existing userspace implementation.

## 3. Which oracles are actually available?

| Oracle | Exact useful scope | What a pass does not establish |
|---|---|---|
| **F:** [RFC 9001 Appendix A](https://www.rfc-editor.org/rfc/rfc9001.html#appendix-A); [RFC 9369 Appendix A](https://www.rfc-editor.org/rfc/rfc9369.html#appendix-A) | QUIC v1/v2 sample packet-protection bytes, derivation and packet layouts. | **I:** loss recovery, scheduling, certificate validation and implementation-wide conformance. |
| **F:** [RFC 8448](https://www.rfc-editor.org/rfc/rfc8448.html) | Reproducible TLS 1.3 handshake traces with intermediate values. | **I:** all TLS modes, malicious-message handling, authorization policy or side-channel resistance. |
| **F:** [QUIC/WebTransport Interop Runner](https://github.com/quic-interop/quic-interop-runner) | Real implementation pairs, selected scenarios, version-pinned endpoint images. | **I:** an exhaustive standards oracle, or a proof of security. Pairwise success can preserve a shared mistake. |
| **F:** [Ivy-based QUIC conformance approach](https://tquic.net/docs/further_readings/conformance/) | A formal model drives one endpoint and checks permitted responses. | **I:** correctness beyond the modeled version/features; a prose RFC still needs interpretation. |
| **F:** [h3i](https://github.com/cloudflare/quiche/blob/master/h3i/README.md), [QUIC-Fuzz](https://arxiv.org/abs/2503.19402) | Controlled malformed input and stateful exploration of local test endpoints. | **I:** no findings means neither complete coverage nor a formal guarantee. |
| **F:** [packetdrill](https://github.com/google/packetdrill) | Scripts combine socket operations, packet expectations and time for TCP/UDP stacks. | **I:** an off-the-shelf Homa or QUIC conformance suite; adding another protocol requires new semantics. |
| **F:** [P4Testgen](https://natefoster.org/papers/p4testgen.pdf) | Expected packets and control-plane configurations from P4 program/target semantics. | **I:** that the P4 program implements the intended RFC, or that a physical target meets timing. |
| **I:** fixed proof contracts + checker + separately maintained implementation peers | Particular invariants and exercised behavior, with proof scope recorded per module. | **I:** correctness of an omitted requirement or of an unmodeled adapter. |

**F/I — There is no universal “IETF RFC test-vector suite.”** The named RFC appendices and traces are narrow published examples. HTTP/3 and MASQUE require clause-based tests, peer checks and state exploration in addition to byte examples. For nondeterministic behavior, compare allowed outcomes and application deliveries—not exact packet ordering or freshly generated ciphertext. [RFC 9114](https://www.rfc-editor.org/rfc/rfc9114.html), [RFC 9297](https://www.rfc-editor.org/rfc/rfc9297.html), [RFC 9484](https://www.rfc-editor.org/rfc/rfc9484.html).

**F/I — No Python means a real design constraint.** The upstream QUIC/WebTransport runner is written in Python. Treat it as prior art and a scenario/endpoint-contract reference; the proposed project code and its acceptance driver use Rust, C/C++, Go, shell and a proof language. A Rust driver reproducing selected scenarios must calibrate against known peers and must not claim to have passed the upstream runner. The same restriction rules out adopting RecordFlux's Python tool implementation as the project's growth engine. [Runner requirements](https://github.com/quic-interop/quic-interop-runner#requirements), [RecordFlux repository](https://github.com/AdaCore/RecordFlux).

**F — The most relevant 2026 warning, explained:** Tobias Philipp's *The Prover Is the Judge* reports agents implementing verified Ada/SPARK security software with 49,280 discharged obligations. Some checks establish functional properties; others establish absence of runtime errors. An SSH key-derivation field-order defect survived the proofs and was caught by OpenSSH interoperation: the missing property had never been specified. **I:** this directly supports a layered oracle and directly defeats a generic “AI plus proofs for protocols” novelty claim. The author's productivity comparison is not an independently controlled experiment. [July 15, 2026 report, §§III, V, VII–IX](https://arxiv.org/html/2607.14340v1).

**F — Fuzzing has also moved beyond crash finding:** the NDSS 2026 MerCuriuzz paper tests QUIC implementations for incorrect protocol decisions using a black-box fuzzing framework. In plain terms, a peer can stay running while making the wrong state transition, so “no crash” is an inadequate conformance verdict. **I:** use such work as a defensive test baseline on local fixtures, rather than pitching another generic protocol fuzzer. [Authors' paper](https://www.jianjunchen.com/p/quic-logic.NDSS26.pdf).

## 4. Three candidate artifacts

### 1. HomaCore — grow a current-wire Homa engine outside a custom kernel

**I — One sentence/value:** a bounded, event-driven Homa library that grows missing message/recovery behavior against an independently running Homa peer, so an application can speak the protocol without installing a Homa module on its own host.

**Q — Seed:** Ousterhout, H 12:00–13:00: “it's message-based, not stream-based”; “Shorter messages can bypass long ones.” Greef's 0:39:00–0:40:00 buffer/I/O remarks above supply the implementation boundary. **I:** preserve those semantics in an explicit engine, rather than equating userspace placement with lower latency.

**I — What grows:** implement packet codecs, RPC identity/lifecycle, grant accounting, out-of-order assembly, resend handling, duplicate suppression, buffer return and bounded cleanup as separate modules. The human supplies `step(state, event) -> actions`, explicit time, caller-owned buffers, resource limits, a supported-wire manifest and frozen observable invariants. The growth trigger is an unsupported protocol action or an independently minimized failing exchange. Accepted modules become ordinary compiled code; no model processes live packets.

**I — Oracle/ratchet:** pin HomaModule code, wire headers and the peer binary. Check application byte delivery and RPC completion/error outcomes in both client and server roles; do not demand identical scheduling choices. A separate network driver produces held-out loss, duplication, reordering, whole-message loss, delayed replies and resource-pressure sequences. Check no double release, no delivery after local teardown, no extra delivery from duplicate packets, and bounded allocation under the declared limits. Keep the checker and approved contracts outside the coding agent's write access. A proof or bounded state check must name its actual assumptions; it cannot promise that a server executes an RPC exactly once across restarts. [Wire definitions](https://github.com/PlatformLab/HomaModule/blob/main/homa_wire.h), [API](https://github.com/PlatformLab/HomaModule/blob/main/homa.h), [implementation tests](https://github.com/PlatformLab/HomaModule/tree/main/test).

**I — Tailwind / one-shot test:** better models can tackle longer recovery histories and larger proof obligations while old accepted exchanges remain regression gates. The accumulated value is the current-wire engine, ownership discipline and independently accepted behavior across adapters. A new model can generate a plausible engine in a prompt; it cannot establish the claimed cross-peer behavior without actually running the peers, adversity schedules and host adapters. If an ordinary strong coding agent plus the old C++ code achieves the same scope with comparable effort, the special growth machinery loses its rationale.

**E — Ambition beyond the demo:** cover a complete pinned wire profile, concurrent RPC/resource lifecycles and multiple stock-host I/O adapters, with independently checked recovery and useful measured performance. That is the ambitious solo artifact; changing a packet codec or merely wrapping an existing socket is not enough.

**E — Six-week version/demo:** Rust core plus a Linux raw-IP adapter and deterministic C++/Rust impairment driver. Use one pinned 2026 Homa peer in a disposable Linux VM; the candidate host uses existing raw-socket facilities and no custom Homa module. Demonstrate a small request and a multi-packet request, then remove a required recovery capability: the exchange fails, an agent grows that capability, all frozen cases pass, and the rebuilt library repeats the exchange with the model disconnected. Include `START_MSG` if targeting the post-September wire. Raw packet access needs host permissions; “no module” does not mean “no privileges.” [Protocol number/API](https://github.com/PlatformLab/HomaModule/blob/main/homa.h), [reference installation](https://github.com/PlatformLab/HomaModule/blob/main/INSTALL.md).

**E/I — Performance boundary:** the six-week claim is interoperable behavior and explicit resource accounting, not a recreated 13× result. A later incast experiment needs real hosts, configured switch queues, comparable TCP/QUIC peers and all CPU/polling costs. A same-machine loss simulator can establish neither data-center p99 nor GPU savings. The transcript's 06:00–16:00 mechanism dictates that distinction.

**F/I — Prior art / what remains:** the inactive C++ project already has a driver-agnostic transport, while eTran implements Homa through a modified kernel. The only defensible residual is a maintained current-wire core with explicit ownership/recovery contracts and stock-host adapters, if inspection shows the old implementation cannot cheaply supply it. No search result establishes that this residual is commercially untaken. [C++ README](https://github.com/PlatformLab/Homa/blob/master/README.md), [eTran](https://github.com/eTran-NSDI25/eTran).

**E — Kill test, 3–5 days:** allocate equal effort to updating the existing C++ engine and to a minimal new core. Require each to complete one current-wire multi-packet RPC in each role and recover from a dropped message announcement/data packet. Kill the new-engine direction if reuse is comparably easy; kill the whole bet if useful deployment requires changing the kernel or inaccessible NIC features. Stop before six weeks if peer/wire churn consumes most implementation time. **I:** an unmaintained predecessor is evidence of possible deployment trouble, not free novelty.

### 2. CapsuleMachine — grow checked MASQUE/WebTransport extension state

**I — One sentence/value:** a small, carrier-independent implementation of tunnel/session extensions whose new capabilities are promoted only with state/resource contracts and independent interoperation, so the same protocol state can run behind multiple existing HTTP engines.

**Q — Seed:** Krazit, `08-jane-street-how-ai-is-changing-programming.txt`, 0:46:00–0:47:00, wants endpoint-level restrictions and describes pushing them into RPC infrastructure. **I:** the networking translation is explicit authority and lifecycle in the tunnel/session layer, rather than adding permissions to opaque byte forwarding. Greef's “bring your own IO,” 0:40:00, supports separating that layer from a runtime.

**I — What grows:** start with an existing QUIC/TLS/HTTP engine, then grow incremental capsule decoding, HTTP Datagram demultiplexing, CONNECT-IP address/route state, session drain/close and WebTransport credit updates. The human defines the adapter contract and a state model: which session owns a datagram, when a route/address is usable, how credits change, and how much incomplete input can be retained. Agent-produced extension code and proofs are separate from approved semantics. Each release declares exact RFC/draft versions and rejects or reports unsupported combinations.

**I — Oracle/ratchet:** use fixed RFC 9297/9484 clause tests, two independent implementation peers where the selected behavior exists, chunking-invariance checks, and generated state histories held outside agent edit authority. Required properties include no cross-session delivery, no routing authority invented from a payload, monotone credit where specified, cleanup after closure, and bounded retained data. Proofs establish only the written state/resource contracts; existing TLS is the cryptographic boundary. A new extension with no independent peer or mature contract remains experimental. [Capsules](https://www.rfc-editor.org/rfc/rfc9297.html), [CONNECT-IP](https://www.rfc-editor.org/rfc/rfc9484.html), [WebTransport draft](https://datatracker.ietf.org/doc/html/draft-ietf-webtrans-http3-16).

**I — Tailwind / one-shot test:** stronger models can grow more extension combinations and discharge more state obligations without reimplementing QUIC. The lasting artifact is the accepted transition system plus executable adapters and proofs—not an RFC summary or task queue. The discriminating question is whether that structure handles unseen combinations better than a normal coding agent editing an existing MASQUE library. A capsule decoder alone is small enough to fail the ambition and one-shot tests.

**E — Ambition beyond the demo:** a composable implementation of the named tunnel/session families across native and capability-limited hosts, with checked authority, ownership and resource behavior across extension combinations. It must accumulate working protocol machinery, rather than remain a wrapper around today's libraries.

**E — Six-week version/demo:** Rust with a restricted Verus-checked state/codec core and TypeScript Wasm bindings. Implement CONNECT-IP address/route capsules plus one bounded WebTransport lifecycle/credit slice; attach to a native existing HTTP/3 engine and run the same core in a Wasm event harness. Demonstrate two concurrent sessions while input is split at every byte boundary, one session drains, and the other keeps its identity and credit. An independent failing state history triggers growth; the resulting native/Wasm artifacts replay it offline without a model. Exclude full certificate policy, a new congestion controller and all-extension verification from this scope.

**F/I — Host limits:** a Wasm replay demo is not a deployed QUIC client. A Workers adapter would need a demonstrated legal carrier through its documented APIs; its TCP API does not supply a raw-datagram capability. Capsule-based fallback also changes transport behavior: the WebTransport draft explains that putting the session into one stream loses stream independence and makes carried datagrams reliable. Do not advertise the fallback as retaining Homa-like small-message latency. [Workers sockets](https://developers.cloudflare.com/workers/runtime-apis/tcp-sockets/), [draft §2.1.2](https://datatracker.ietf.org/doc/html/draft-ietf-webtrans-http3-16#section-2.1.2).

**F — Prior art / what remains:** masque-rs already implements CONNECT-UDP/IP. webtransport-go's releases already add capsule parsing, stream/data credit and draft-16 updates; a WebTransport fuzzer already exercises capsule sequences against live session state. **I:** a generic extension implementation or stateful fuzz harness is taken. The residual is checked cross-extension state/resource composition shared across carriers, and it remains uncertain whether that is a worthwhile independent project. [masque-rs](https://github.com/Kotodian/masque-rs), [WebTransport releases](https://github.com/quic-go/webtransport-go/releases), [fuzzer](https://github.com/qbitroot/webtransport-fuzzer).

**F/I — A tempting false gap:** search results still listed CONNECT-IP DNS/PREF64 issue #62 as open, but the issue page is closed and implementation PR #67 is merged. Do not pitch that extension as missing. [Issue #62](https://github.com/quic-go/connect-ip-go/issues/62), [merged PR #67](https://github.com/quic-go/connect-ip-go/pull/67).

**E — Kill test, 4 days:** implement one lifecycle slice using an existing library and one using the checked core, against the same frozen peer/state tests. Continue only if the checked core exposes a reproducible composition/resource failure or supplies an actual second-host integration that reuse cannot achieve within the same budget. Kill if all that remains is a thin wrapper, an already-fixed upstream issue, or proving a home-grown model with no independent behavior check.

### 3. PacketSeam — grow packet interpretation with a proved fast/slow boundary

**I — One sentence/value:** a packet-processing library that grows support for nested headers while proving that its fast path either agrees with a complete reference interpretation or explicitly defers the packet, preventing partial parsing from silently becoming an allow decision.

**Q — Seed:** Krazit, `08-jane-street-how-ai-is-changing-programming.txt`, 0:46:00: “only certain endpoints inside of it.” **I:** packet-layer enforcement has an analogous interpretation boundary: an address/protocol decision is meaningful only if the parser reached the right inner header. This is a narrower, defensive use of that seed; encrypted RPC names still require application termination/integration.

**F — Concrete issue:** connect-ip-go issue #13 says IPv6 extension handling is needed for correct IP-protocol filtering. The checked page displays it open, but its old timestamp/cache makes reproduction mandatory before treating it as a current missing feature. [Issue #13](https://github.com/quic-go/connect-ip-go/issues/13), [IPv6 extension rules, RFC 8200 §4](https://www.rfc-editor.org/rfc/rfc8200.html#section-4).

**I — What grows:** header-chain/option handling and corresponding extraction proofs, beginning with IPv6 and later a named overlay such as Geneve. Define a reference interpretation with explicit byte ranges and results `Complete(view)`, `NeedSlowPath(reason)` or `Malformed(reason)`. A fast-path result must agree on fields, offsets and relevant validity conditions; a deferred packet reaches a trusted slow parser that applies the same policy. The agent adds a bounded capability when real traffic hits `NeedSlowPath`. It cannot turn “unsupported” into “allow.” The artifact runs without a model.

**I — Oracle/ratchet:** an approved reference semantics, an independent existing decoder/endpoint for supported valid inputs, protocol-specific malformed cases and proof checking. Verify the relation on the supported packet domain, not just parser/serializer round trips. Keep the RFC interpretation and policy evaluator outside the agent's edits. Bytewise fuzzing and field mutations challenge the extraction relation; disagreements about permissible but unusual packets are recorded for human resolution rather than decided by majority vote. [IPv6 specification](https://www.rfc-editor.org/rfc/rfc8200.html), [Geneve, RFC 8926](https://www.rfc-editor.org/rfc/rfc8926.html).

**I — Tailwind / one-shot test:** better models extend variable-length chains and prove larger relations while previously accepted paths keep their checks. The accumulated deliverable is deployable semantic coverage and checked delegation at the boundary. A model could quickly write the usual Ethernet/IP/UDP parser; the project survives only if growing difficult compositions and preserving the forwarding relation is substantially more than that. If existing generators plus ordinary agent edits do it as well, stop.

**E — Six-week version/demo:** a Rust/Verus specification and checked fast parser, compiling the same executable Rust code as a native library and to Wasm. Start with bounded IPv6 extension chains and explicit fragment deferral; do not implement reassembly. Add one option/header family from a frozen failing case, discharge its extraction/deferral contract, and replay the same packets through both builds. Show that a policy-sensitive packet used to defer and now reaches the correct complete view; a deliberately wrong offset must fail the independent gate. An XDP adapter is later work: it must preserve the checked parser boundary and separately pass the stock kernel verifier and runtime tests. No kernel modifications and no claim that a source-level proof verifies LLVM or the BPF JIT.

**E — Ambition beyond the demo:** grow a substantial library of nested protocol/option combinations while retaining an explicit interpretation/deferral relation at every supported execution boundary. C, P4 or eBPF lowerings would each need their own semantic-preservation argument; emitting another language is not automatically covered by the Rust proof.

**F — Prior art, explained:** Leapfrog already proves equivalence between packet-parser automata, including translation validation; its artifact also documents scale/resource limits. It means equivalence machinery itself is not a new project. P4Testgen generates inputs, table settings and expected outputs for a P4 program/target; that checks the execution of the program, not whether the program captured the intended RFC. [Leapfrog artifact](https://github.com/verified-network-toolchain/leapfrog), [P4Testgen paper](https://natefoster.org/papers/p4testgen.pdf).

**F — Direct 2026 competition, explained:** Heimdall uses models to migrate C eBPF programs to Rust, repairs failures and checks program equivalence. Its August 26 revision reports 109 checked translations out of 115 programs. **I:** an agent growing verifier-accepted eBPF or preserving an old parser's behavior is therefore taken. PacketSeam's possible residual is proving a forwarding-relevant field/deferral relation against reviewed protocol semantics when adding new supported inputs; EverParse/RecordFlux and ordinary library reuse remain serious baselines. [Heimdall v2](https://arxiv.org/abs/2605.25411v2), [Everest](https://project-everest.github.io/), [RecordFlux](https://docs.adacore.com/live/wave/recordflux/html/recordflux_ug/10-introduction.html).

**E — Kill test, 3 days:** reproduce one named filtering/interpretation defect against pinned current code. Compare an existing parser generator plus conventional agent-assisted integration with the proposed relation-based growth. Kill if the issue is already fixed, the fix is routine, or proof work supplies no material guarantee beyond the incumbent tools. Also kill if bounded fast-path support requires silently dropping valid traffic instead of truthful delegation. **I:** this is the most crowded of the three candidates.

Also searched HN and X with 2026/Homa/QUIC/verified-protocol terms, arXiv, IETF drafts, project pages and issue trackers. **I:** sparse or irrelevant X/search results provide no evidence of absence. Novelty judgments above rest on the linked primary projects and exact residuals, not on a zero-result query.

**F/I — HN was useful as a lead, not a benchmark:** the [October Homa discussion](https://news.ycombinator.com/item?id=49957117) contains conflicting QUIC/Homa performance assertions and a reply under Ousterhout's name calling for matched-workload comparison. No quantitative claim here depends on those comments. The actionable experiment remains equal hardware, mixed message sizes, all CPU costs and explicit encryption/deployment conditions.

**F/I — Do not re-pitch:** generic verified TLS/QUIC, an RFC-to-implementation agent, a QUIC/WebTransport interop dashboard, an open UET provider, portable P4 generation, or a general agent-grown userspace TCP stack; the linked projects above already cover those categories. The earlier report already reached similar conclusions for general stack/verification revivals. [Earlier networking report](../../flip/02-networks.md), [round-13 exclusions](../BRIEF-tailwind.md), [kill list §11](../../RESEARCH-SUMMARY.md#11-the-kill-list). These candidates concern executable networking artifacts, not the excluded package atlas, agent-era Jepsen, UI behavior, or kernel/OS growth.

**I — Common promotion rule:** a candidate patch cannot edit the accepted contract, expected outputs, peer images, failure exclusions or resource ceilings. Pin those separately; require explicit approval to revise them. Keep `pass`, `fail`, `unsupported` and `inconclusive` distinct. A later model release enlarges the accepted artifact only when it passes the old envelope plus the new independent requirement. This is an engineering acceptance design, not a novel verification algorithm.

## 6. Ranked decision

**I — ONE pick: HomaCore's reuse-versus-new-core experiment.** It has the clearest practitioner-specific mechanism and a useful outcome even with zero users: a current-wire endpoint that can exchange real RPCs with the reference. Its most serious objection is unusually concrete—the original project already built a userspace transport—so that baseline can reject the idea cheaply. Do not start a six-week rewrite before that test. CapsuleMachine is the fallback if it produces a real cross-carrier requirement; PacketSeam ranks lower because the prior art covers so much of the machinery.

**E — Scores, 1–5, higher is better.** Tail = model tailwind; Open = how untaken the precise residual appears; Solo includes verification and host-access burden. These rank experiments, not demonstrated filter passes.
