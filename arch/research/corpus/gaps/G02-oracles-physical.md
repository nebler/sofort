# G02 — Inverse search: physical, hardware, graphics and science oracles

**Research date: 2026-10-29.** Read against [BRIEF-gaps](../BRIEF-gaps.md), [BRIEF-tailwind](../BRIEF-tailwind.md), the [round-13 exclusions](../tailwind/SUMMARY.md), and the [kill list](../../RESEARCH-SUMMARY.md#11-the-kill-list). Only this file was written. No implementation was built or benchmarked.

**Labels:** **F** = sourced observation; **Q** = quotation checked in the local transcript; **I** = inference, proposed design or search interpretation; **E** = estimate or proposed acceptance threshold. Facts in each inventory row are supported by its linked primary source; growth suggestions are **I**, not descriptions of existing features.

**I — The finding:** there is ample oracle supply. The scarce thing is a useful artifact that can grow against an oracle without merely becoming another simulator wrapper, ordinary code-generation agent, or benchmark archive. The best pairing I found is **pbrt + probability-preserving sampler construction → a growing bank of reusable rendering sampling algorithms**. A SPICE-checked bank of real-time circuit solvers is a credible runner-up. Chemical model compression has an excellent reference but much less open territory; it is developed below as a reserve with an explicit novelty kill.

## 1. What counts as an oracle here

**F/I — Four different strengths need different claims.**

| Mark | What can actually be checked | Boundary |
|---|---|---|
| **Exact** | Discrete outputs, rounding bits, instruction state; or formal equivalence under stated assumptions | A proof of the wrong specification remains the wrong result. EQY also has explicit semantics for undefined initial state and unknown values. [EQY semantics](https://yosyshq.readthedocs.io/projects/eqy/en/latest/xprop.html) |
| **Ref** | Agreement with a frozen implementation for declared inputs and configurations | Verilator supplies execution of HDL; it does not supply an independent correct design. QEMU supplies modeled machine behavior; it is not a silicon timing specification. [Verilator](https://verilator.org/guide/latest/overview.html), [QEMU](https://www.qemu.org/docs/master/system/introduction.html) |
| **Stat** | Distributional or numerical agreement, with tolerances and uncertainty | Rendering reference images are noisy estimates. Mitsuba uses distribution tests and image Z-tests rather than requiring identical noisy pixels. [Mitsuba testing](https://github.com/mitsuba-renderer/mitsuba3/blob/master/docs/src/developer_guide/testing.rst) |
| **Physical** | Agreement with specified physical measurements, models or validation cases | Agreement with a force field or a contact model does not establish agreement with nature. Physical validation is a separate layer. [Chrono validation studies](https://projectchrono.org/validation/) |

**I — Minimum growth contract:** freeze oracle versions, input generators, units, comparison rules and promotion thresholds outside the candidate's writable directory. The model submits a module plus a declared domain. An independent process checks it, stores any counterexample, reruns prior obligations, and promotes an immutable version. The accepted artifact must run with the model disconnected. New evidence can revoke a version; a ratchet is retention of accepted evidence and working versions, not a claim that an empirical test makes future failures impossible.

**I — Do not silently strengthen the result.** Finite differential testing is not equivalence over all inputs. A reference solver's tolerance is not an error bar against reality. Two engines using the same equations, constants or device models are useful implementation checks but not independent physical experiments. A closed holdout can reduce overfitting; it is not the whole oracle.

## 2. Inventory: 54 existing public oracle systems

**E — Size convention.** Source-scale bands are rough triage estimates, **not measured LOC**: **S** below about 50k lines, **M** about 50–500k, **L** about 0.5–2m, **XL** above about 2m. Generated sources, vendored dependencies, datasets and build trees can dominate disk use and are excluded from these bands. Where a meaningful published scope count is available, it is given separately. For datasets, the size describes the kind of corpus and a proposed bounded subset rather than inventing a total download size. Pin and measure the chosen subset before committing to a build.

**I — Accessibility notation.** **N** = native executable/library or non-Python implementation route; **D** = language-neutral data; **P** = normal configuration, execution or supplied verification flow materially uses Python. **B** = native runtime but Python is involved in build/support tooling. These distinctions matter: a C++ core does not automatically make the whole supplied workflow Python-free. The ideas below specify native routes and do not depend on Python-authored harnesses.

**I — U?** marks a bounded negative finding: the searches in §4 found no clear public example of an agent persistently growing a replacement/algorithm bank against that named oracle. It does **not** mean nobody uses the oracle, nobody has tried it privately, or that a wrapper is novel.

## 5. Three developed oracle → growth pairings

**I — Scope of these proposals:** their output is a new computational method or reduced physical model, rather than a copy of a dependency API. They do not propose kernel/OS growth, game reconstruction, GPU numerical atlases, driver translation from hardware traces, scientific-record archives or a general proposer/verifier framework. All three depend on a concrete held-out generalization test. Only the top pairing merits an immediate build recommendation; the chemistry pairing remains a reserve because the prior-art objection is substantial.

### 5.1 Sampler Foundry — grow better ways to follow light

**I — One sentence / value:** a rendering engine accumulates small, reusable sampling recipes for difficult light/material configurations, so an accepted recipe makes later images converge faster without calling a model.

**The seed — Q/F.** Matt Pocock, [the checked transcript](../transcripts/23-the-pragmatic-engineer-ai-skills-with-matt-pocock.txt), **0:50:00**, says: **Q:** “if you can turn” simulation interactions into text, “the agents are going to do a pretty good job.” This is a general practitioner seed, not a prediction specifically about rendering. The domain-specific seed is [Aether](https://aekul.github.io/aether/aether.pdf): its authors describe a sampling language that handles probability-density and multiple-importance-sampling bookkeeping, and demonstrate a specialized light-path construction for a scene seen through a small pinhole. In plain terms, many rendering bugs come from miscounting how likely a sampled light path was; putting that bookkeeping in the language makes more complicated sampling strategies safer to express. It gives a model a useful restricted place to work, rather than asking it to rewrite a renderer.

**What grows; what the builder owns — I.** The growing artifact is a bank of **algorithmic sampling recipes**, not rendered reference images or scene-specific caches. Start with direct-light configurations: small area lights, grazing glossy lobes, and mixtures of light and material sampling. A recipe takes a typed geometric/material situation and maps uniform random numbers to directions using a small grammar of normalized distributions, mixtures and supported invertible transforms. It exports an automatically derived density and a domain guard. Existing reference light transport, material evaluation, visibility and scene parsing remain frozen.

The builder owns that grammar, its probability semantics, support checks, compiler, domain dispatch and acceptance runner. The model may compose permitted nodes and propose parameterizations; it may not handwrite its own answer-checking density, alter the BSDF being integrated, remove difficult scenes or edit the renderer used as reference. A required baseline mixture preserves support where the candidate is weak. An accepted recipe is a native C++ module; unsupported situations continue through the baseline.

**Its oracle — F/I.** [pbrt](https://pbrt.org/users-guide-v4) provides a native spectral reference and well-developed sampling/material implementations. [Mitsuba's tests](https://github.com/mitsuba-renderer/mitsuba3/blob/master/docs/src/developer_guide/testing.rst) demonstrate the relevant distinction between checking a sampling distribution and checking rendered image expectations, but their supplied Python tests are not the proposed runtime or harness. Implement the required comparisons in C++/Rust and use pbrt as the operational reference.

**I — Promotion has separate gates:**

1. The restricted construction gives a mathematically accounted density/support contract. Candidate arithmetic still needs range/finite-value checks; structural probability accounting does not make floating-point execution exact.
2. Independent native tests compare sample frequencies, density integrals and known analytic integrals, including boundary/degenerate cases. These catch implementation mistakes; they do not prove all possible sampler programs correct.
3. Frozen pbrt configurations provide high-sample image/energy references with estimated uncertainty. Promotion uses independent random seeds, per-region checks and multiple scenes, rather than one global image score that hides a localized bias.
4. Measure **time to target error**, including sampling overhead. Equal samples per pixel is insufficient: an expensive “better” sample can lose in wall time.
5. Restrict the 6-week version to smooth non-delta distributions and direct illumination. Specular chains, arbitrary participating media and singular/discrete mixtures are expansion targets, not silently covered cases.

**Tailwind and one-shot test — I.** Better models search more useful compositions, derive stronger domain guards and explain failed cases. Existing recipes remain native, measured assets. What a later model must still earn is a bank that generalizes across unseen scenes, with correct densities/support and actual wall-time wins. A one-prompt renderer demo or a single good distribution is not that artifact. However, if a later one-prompt model can produce an equally good general recipe that passes the same frozen suite, this moat vanishes; the baseline experiment must test that possibility instead of asserting immunity.

**E — The 6-week version and demo.** Weeks 1–2: pbrt CPU integration, a small recipe grammar, analytic fixtures and an independent acceptance runner. Weeks 3–4: allow growth on about 12 training scene families; reserve about 12 families and parameter sweeps for evaluation. Weeks 5–6: keep roughly 5–10 reusable recipes and package a native viewer/CLI. Demo an unseen glossy scene with a moving small light: baseline remains noisy while the accepted bank reaches the same independently checked error sooner; disconnect the model, change the light again, and rerun. A visually impressive scene counts only alongside its error/time evidence. Budget about €300–1,000 in inference and rented CPU time, excluding an existing development machine; this is an estimate, not a measured cost.

**Prior art; precisely what remains — F/I.** [Aether](https://aekul.github.io/aether/aether.pdf) already supplies much of the probability-language idea. [Practical Path Guiding](https://github.com/Tom94/practical-path-guiding) learns where useful light paths are during rendering. [BSDF importance sampling using a diffusion model](https://doi.org/10.1145/3680528.3687684) learns sampling distributions and demonstrates integration into rendering. In plain language, it trains a neural sampler to put more work where a material reflects light, showing that learned sampling itself is not new. [Efficiency-aware MIS](https://iliyan.com/publications/EfficiencyAwareMIS/EfficiencyAwareMIS_Sig2022.pdf) also automatically allocates work among existing sampling techniques.

**I — The residual is narrow:** agents grow **reusable native sampling algorithms within checked probability semantics**, across scene families, instead of training a new neural sampler or choosing among a fixed menu for one scene. The searches did not establish that this exact residual is taken, but absence is unproven. No novelty claim attaches to the DSL, importance sampling, path guiding or automatic sample allocation individually.

**E — Kill test.** Spend three days on one smooth direct-light family and one held-out family. Compare against pbrt's existing strategy, a simple tabulated/factored sampler, an adaptive baseline, and a strong model's one-prompt recipe under the same final gate. Stop if the grammar only expresses existing strategies, if probability accounting requires candidate-owned exceptions, or if no reusable recipe delivers at least about **2× lower wall time to the same error** across held-out variations. The longer-term 10× ambition is a broad repertoire of difficult transport situations, not a promise of a universal 10× render speedup.

### 5.2 Circuit Voice — grow real-time solver methods, checked against SPICE

**I — One sentence / value:** a native audio circuit engine grows reusable numerical treatments for nonlinear circuit motifs until new circuits can run under an audio deadline while staying inside a measured SPICE-agreement envelope.

**The seed — Q/F.** Matt Pocock's same [transcript](../transcripts/23-the-pragmatic-engineer-ai-skills-with-matt-pocock.txt), **0:06:00**, describes building a voice spectrogram analyzer: **Q:** “Extremely in-depth, ran terribly.” At **0:50:00** he connects nonsoftware simulation feedback to agent work. Neither passage specifically proposes a circuit compiler; the connection to physical audio is **I**. The domain-specific seed is [Petri Nets for Automatic Wave Digital Code Generation, published 2026-09-22](https://onlinelibrary.wiley.com/doi/10.1002/jnm.70202). The paper turns a declarative circuit-model graph into explicit evaluation schedules and generated numerical code. It matters because solver scheduling and nonlinear dependencies are concrete, machine-checkable work; it also removes the simplistic claim that automatic circuit-to-code generation is untouched.

**What grows; what the builder owns — I.** Do not generate a new circuit schematic. Take a fixed, public, small audio netlist and grow **motif-level solver methods**: state parameterizations, nonlinear solve strategies, initial guesses, update order and bounded approximation formulas. A newly encountered diode/op-amp/feedback motif triggers a patch; the patch must also handle changed component values and a different circuit containing that motif. It cannot be a waveform table for one test song or a fitted black-box model that ignores parameter changes.

The builder owns a native netlist subset, component equations, units, state representation, permitted solver hooks and the audio deadline contract. Begin with R/C/diode networks and declared op-amp models; do not claim arbitrary SPICE dialect/device support. The model can change numerical implementation inside these hooks, not the physical equations, reference netlists, component parameters or acceptance stimuli. Accepted patches are Rust/C++ and run with no model or neural inference. A circuit outside its accepted parameter/input envelope is rejected for real-time use until a new patch passes; the system does not silently substitute an uncontrolled approximation.

**Its oracle — F/I.** [ngspice](https://ngspice.sourceforge.io/) is the reference implementation of the declared device/netlist model; [Xyce](https://github.com/Xyce/Xyce) can cross-check compatible cases. The reference should be rerun with tighter tolerances and smaller maximum time steps until its relevant observables stabilize. That gives a stronger computational reference, not proof that a real pedal/amplifier has identical component behavior.

**I — The gate must cover dynamics, not only a Bode plot.** Check DC operating points, small-signal response, transient sweeps, clipped/multitone signals, startup, parameter modulation and long silent tails. Compare aligned waveforms, harmonics/intermodulation, state trajectories where observable, and residuals of the fixed circuit equations. Check real-time work/allocation limits separately. Do not assert global passivity for active amplifiers; use passivity only for passive subcircuits, and require declared stability/boundedness tests for active ones. Component drift, external input spikes and stiff corners belong in the holdout generator.

**Tailwind and one-shot test — I.** Better models can invent solver decompositions and range guards for motifs the engine cannot yet handle. The bank accumulates implementation methods and cross-circuit evidence. A stronger model can certainly write an individual distortion plugin; it does not automatically supply a reusable family of methods that meets a deadline under changing component values while matching fixed physical models. If a one-prompt implementation already does so as well as the accumulated bank, drop the project. “It has a lot of tests” alone is not a moat.

**E — The 6-week version and demo.** Weeks 1–2: native ngspice runner, fixed device subset and 8–12 small training circuits. Weeks 3–4: grow approximately 3–5 solver patches and evaluate each on a structurally different held-out circuit. Weeks 5–6: a standalone native audio application, with plots of reference agreement and deadline misses. Demo changing a resistor/diode arrangement, showing the missing-method failure, growing a solver patch, then hearing and measuring the result while sweeping parameters with the model offline. Target 48 kHz processing in 64-sample blocks on one declared laptop; the precise CPU budget and tolerances must be frozen after baseline measurement. Estimate €300–1,000 in inference/compute; no physical lab is required for the computational demo.

**Prior art; precisely what remains — F/I.** [chowdsp_wdf](https://github.com/Chowdhury-DSP/chowdsp_wdf) already provides C++ wave-digital building blocks. [ATTILA](https://github.com/polimi-ispl/attila) automatically constructs and simulates wave-digital models from SPICE netlists, using MATLAB. The [2026 Petri-net paper](https://onlinelibrary.wiley.com/doi/10.1002/jnm.70202) generates scheduled numerical implementations from declarative models. These remove “netlist in, audio model out” as the novel claim. [Spice++](https://www.spicepp.com/ai-circuit-design) separately removes the general agentic circuit-design claim.

**I — What may remain:** growth is triggered by a **missing reusable numerical method**, and promotion requires deadline-compliant behavior on new circuits and parameter ranges. It is not just porting the MATLAB tool to Rust or replacing its fixed scheduler with an LLM. If existing automatic generation plus a general nonlinear solver already handles the selected motif families at the desired deadline, there is no independent project here. This is why its Open score is lower than Sampler Foundry's.

**E — Kill test.** Before building a UI, take three nonlinear motifs at escalating difficulty. Establish the best existing C++ WDF/general solver baseline. Give a model a hook to propose one method, freeze it, and evaluate it on different netlists plus parameter/input sweeps. Kill if accepted methods fail to transfer, if transient accuracy depends on tuning to the training waveform, or if existing automated methods reach the same real-time/accuracy envelope with comparable effort. Do not rescue a failure by renaming ordinary plugin generation as growth.

### 5.3 Reaction Capsules — grow compact dynamical closures for declared chemical regimes

**I — One sentence / value:** build small native chemical dynamical models that learn to cover additional operating regimes while retaining elemental conservation, stable state conversion and measured agreement with a frozen detailed mechanism.

**I — Status:** reserve, not a validated survivor. The oracle is strong for computational agreement, but the novelty and domain-expertise risks are materially higher. A generic mechanism generator/reducer is dropped; the only residual developed here is a bank of **explicit compact dynamical closures with independently checked transitions between validity regimes**.

**The seed — Q/F.** Matt Pocock, [transcript](../transcripts/23-the-pragmatic-engineer-ai-skills-with-matt-pocock.txt), **0:50:00**, asks whether other engineering professions' simulations can become text feedback for agents. This is the same checked practitioner seed applied to a different domain; it is not a chemistry-specific practitioner prediction. The concrete computational seed is [A graph neural network based chemical mechanism reduction method, submitted 2026-03-20](https://arxiv.org/abs/2603.22318). It learns dependencies among species/reactions to reduce detailed chemistry's cost. In plain terms, a full reaction system can be too expensive to solve at every point in a flow simulation; much of it can sometimes be removed while preserving the behavior of interest. The paper establishes the need and competition, not the novelty of this proposal.

**What grows; what the builder owns — I.** Fix one public detailed mechanism and a deliberately small, benign gas-phase reactor problem. The growing artifact contains reduced state equations, algebraic closures for eliminated fast species, validity guards and conservative state-conversion maps. A new temperature/composition trajectory that violates the current error budget triggers a new capsule or a more general closure. The bank must retain prior accepted regimes and work without inference.

The builder owns the species/element matrix, units, detailed mechanism identity, reactor configuration, solver tolerances and permitted closure grammar. Candidate closures cannot invent favorable rate constants or alter the reference mechanism. Conservation can be enforced algebraically through the state representation; positivity and equilibrium behavior need separate constraints/checks. A guard based only on initial temperature/pressure is inadequate: the actual evolving composition and thermal state matter. Handing over between capsules is part of the checked algorithm, not an unmeasured dispatch detail.

**Its oracle — F/I.** Native [Cantera](https://github.com/cantera/cantera) runs with tighter tolerances provide reference trajectories for the declared chemical model; native [SUNDIALS](https://computing.llnl.gov/projects/sundials) supplies an independent route to integrating candidate equations. Agreement checks include species over time, temperature, conserved elemental totals, equilibrium approach, sensitivities where relevant, and full wall time including capsule selection/state conversion. These are computational checks against a chosen mechanism. They do not establish new chemistry or improved agreement with laboratory experiments.

**I — Strength boundary:** a finite trajectory suite cannot certify an entire temperature/pressure/composition region. Initially call domains **tested envelopes**, expose the reference fallback when available, and retain failing trajectories. If claiming a rigorous envelope later, provide actual conservative error/stability bounds; neither conservation alone nor a classifier's confidence supplies them. The runtime may invoke the detailed solver outside accepted envelopes; the exported reduced capsule itself remains native and model-free.

**Tailwind and one-shot test — I.** Better models can propose more useful eliminations, closure formulas and transition maps. The enduring artifact would be the accumulated compact equations and checked regime coverage, not a pile of generated Cantera scripts. A future model producing one reduced mechanism does not automatically cover all retained regimes and transitions. But standard adaptive chemistry could make that distinction commercially and technically irrelevant; this proposal must beat those baselines before claiming value.

**E — The 6-week version and demo.** Weeks 1–2: one small public gas mechanism, native C++ oracle/harness, exact elemental bookkeeping and a fixed reactor suite. Weeks 3–4: synthesize a few low-dimensional closures over separated regimes. Weeks 5–6: demonstrate a prescribed thermal/composition trajectory crossing regimes, show a counterexample, add a capsule, and replay every older trajectory with the model disconnected. Target a clear error budget and approximately **3× end-to-end speedup** over the same detailed native solver on held-out trajectories; do not compare against an unnecessarily slow Python wrapper. Estimate €500–1,500 for inference/reference computation. A compact demo may be solo-buildable; broad chemical expertise remains a serious solo risk.

**Prior art; precisely what remains — F/I.** [pyMARS](https://niemeyer-research-group.github.io/pyMARS/index.html) already accepts operating conditions/error limits and removes reactions/species. [RMG](https://rmg.mit.edu/) already grows mechanisms, while [dynamic adaptive chemistry](https://ansyshelp.ansys.com/public/Views/Secured/corp/v251/en/forte_th/i85722.html) already changes the active chemistry locally. [AMORE v2](https://pmc.ncbi.nlm.nih.gov/articles/PMC12403060/) removes, merges and reroutes chemical graphs, so even graph rewrites are not unoccupied. In plain language, it compresses very large atmospheric reaction networks while preserving selected outputs; it is a strong reason not to mistake deleting or merging species for a new capability.

**I — The residual, if real:** explicit model-grown closure equations plus conservative inter-regime state maps, tested as one reusable native dynamical artifact. I found no conclusive direct match for that complete package in the bounded searches, but the nearby methods are strong enough that this is **not** evidence of an open field. Do not build it merely because much prior art is Python: language choice is not sufficient differentiation.

**E — Kill test.** Spend at most two days comparing against skeletal reduction, a conventional quasi-steady-state closure, and an adaptive mechanism baseline on the same small problem. If they already cover the regimes and transitions at the desired error/cost, drop this idea. Also kill if the model's useful contribution reduces to tuning existing thresholds, or if understanding its closures requires sustained chemistry consultation. A failed novelty test should end the proposal, not produce another scientific-model registry.

## 6. Choice and ranked table
