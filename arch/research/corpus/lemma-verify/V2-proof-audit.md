# V2 — proof-boundary audit

2026-10-29. Assignment: audit the proof boundary, not benchmark the spike.

**The model-to-body-byte claim holds, with substantial limits.** Lean checks a real preservation theorem for a bounded, custom Wasm-like language and connects six particular instruction lists to particular byte arrays through a custom decoder. It does not prove correctness from official Wasm semantics to Apple silicon, host isolation, or the host trap/result convention. The README now states those qualifications fairly explicitly. Describing this as an end-to-end verified Wasm compiler would overstate the artifact.

The strongest adversarial result is that changing **both** source and target right-shift semantics from modulo 32 to modulo 16 passes the generic proofs, all six certificates, and the complete existing build/test suite. A concrete Lean evaluation then disagrees with the native result. This is a specification-boundary failure, not an inconsistency in Lean.

**What the five named declarations actually establish.**

1. **`preservation`** in each generated fixture is a definition specializing `Compiler.compile_correct true program accepted`, not a proof of one concrete native invocation. The corresponding unoptimized definition selects `false`. The remaining arguments are arbitrary initial source/target states, evidence that they match, evidence that the source stack is empty, and source fuel. If the source interpreter finishes normally at that fuel, the compiled instruction-list machine has a finite execution from PC 0 to the instruction-list length, with a matching final state. If the source interpreter traps, the target model reaches a modeled trap with matching linear memory. Source `stuck` and an escaping branch are impossible under the hypotheses. Timeout yields only `True`. No bytes occur in this theorem. See CM 1473–1493 and, for example, `build/load.lean`.

2. **`Native.check_sound`** says: for any instruction list and byte list whose finite checker returns true, decoding at **every natural-number instruction PC** equals lookup in the expected instruction list. The checker requires exactly four bytes per expected instruction and equality at every body PC. Beyond the body, both sides return `none`. This is a genuine all-PC result, including instructions that happen to be unreachable. It says nothing about whether this decoder is the hardware decoder, whether a source program is valid, or whether these bytes are installed in an executable. See NB 115–132.

3. **`Native.step_eq`** says: given that same passing check, for every PC and every `Arm.State`, one byte-backed model step equals one instruction-list model step, including branch, trap, and halt outcomes. It requires no `Match`, source validity, reachability, or fuel hypothesis. Its strength is universal equality of these two model steppers. Its limit is that both use the **same `Arm.step`** for arithmetic, flags, registers, and memory; the proof unfolds those definitions after rewriting the decode equality. It does not compare two independently specified ISA semantics. See NB 134–147.

4. **`Native.compiler_to_bytes`** adds a passing check for the actual `Compiler.compileB opt f` output to the hypotheses of `Compiler.compile_correct`. It transfers finite model reachability/traps to `Native.Reach`/`Native.Traps`, whose steps decode the byte list. Normal completion reaches body PC `compileB.length`; traps end at the model's atomic trap event. The timeout/escaping-branch/stuck cases are respectively `True`/`False`/`False`. This is conditional preservation of terminating and trapping source-model executions, with no bound on target steps. See NB 172–195.

5. **`preservation_to_bytes`** in a fixture specializes the previous theorem with its concrete `program`, optimization flag, `accepted`, `bodyBytes`, and `compiled_bytes_checked`. Crucially, the fixture separately proves `compiler_eq`, so an untrusted certificate writer cannot replace the expected instruction list while keeping the same source program and compiler. The specialized declaration still needs the initial-state, matching, and fuel arguments. It does not identify a C call, Mach-O file, loaded process, or official Wasm execution inside its type. The build script supplies the connection to a file by extraction and comparison outside Lean.

For 1, 4, and 5, the important shared hypotheses are:

- The custom validator returns true: at most eight locals, at most sixteen simultaneously live operand values, valid local indices, offsets below `2^32`, and the restricted block/loop/branch stack discipline.
- The initial source operand stack is empty. Each live operand and each declared local is represented by the **zero-extended** i32 value in its assigned 64-bit register. Operand slots use X0–X15; locals use X19–X26. Scratch registers are X16/X17, memory size X27, and base X28.
- `MemRel` requires source memory size at most `2^32`, `base.toNat + size ≤ 2^64`, X27 equal to that size, and equality of **every byte inside** the linear-memory region. It does not require a page multiple or specifically 64 KiB. It assumes the required target memory exists as a total function.
- The byte theorem additionally needs `Native.check (Compiler.compileB opt f) bytes = true`. Fixture certificates discharge this condition, but not the initial-state/host-entry contract.

These are meaningful restrictions, not a hidden premise that the compiler already executes correctly. Zero extension and nonwrapping host placement are necessary for this particular bounds-check implementation. The missing work is proving that real entry/exit code establishes and preserves the contract.

**Vacuity, nontermination, and observations omitted by the statement.** I found no contradictory premise that makes all ordinary fixture cases vacuous. [BoundaryProbes.lean](/tmp/lemma-verify-v2-proof-audit/audit/BoundaryProbes.lean) constructs and proves `Match 2` for every i32 argument, with 64 KiB of zero memory at base 4096, the argument in local 0, and local 1 zero. Restricting that local relation also supplies the one-local fixtures. The proof checks with only `propext` and `Quot.sound`. This establishes inhabited model hypotheses; it does not verify the actual wrapper's entry state.

Timeout is a genuine weakness. `Wasm.exec 0` returns timeout even for trivial code, so the top theorem instantiated at fuel 0 has no target obligation. The theorem quantifies over all fuel, so this does **not** erase its obligations when a larger fuel produces a result or trap. However, a valid infinite loop, `loop [br 0]`, has no terminating/trapping result to trigger those obligations. The probe accepts that loop and evaluates it to timeout. There is no divergence-preservation theorem, timeout-prefix simulation, execution budget, interruptibility, resource bound, or safety claim for all prefixes of an indefinitely running program.

The normal postcondition relates the source operand stack, declared locals, and linear memory. It is not a scalar function-return/ABI theorem. The trap postcondition relates only memory, not preserved registers or the returned trap-status word. Neither postcondition asserts equality of all host memory, records accesses, or establishes constant-time behavior.

`MemRel` never relates bytes outside the linear-memory region. I proved two different target memories both satisfy it for the same source memory and base, while their byte at address 0 differs; the region starts at 4096. The probes and their axiom lists pass in [BoundaryProbes.log](/tmp/lemma-verify-v2-proof-audit/audit/BoundaryProbes.log). Thus the relation itself cannot distinguish arbitrary corruption outside that region. It also does not, by itself, relate the final base register to its initial value. This is a weakness of the exported contract, **not evidence that the unmodified compiler actually writes outside the region**. A separate frame/access-containment theorem could potentially prove stronger facts from its implementation. No such theorem is exported here. Final-state equality alone would also miss a temporary outside write followed by restoration.

**How much of Wasm is modeled.** This is a small, manually defined language with Wasm-inspired operations, rather than a mechanized import of the official module semantics. Its relevant scalar choices are sensible:

- `BitVec 32` addition, subtraction, and multiplication wrap modulo `2^32`; unsigned comparison uses `BitVec.ult`.
- Both shifts mask the count modulo 32; `shr_u` is logical, not arithmetic.
- Load/store effective addresses use the unsigned i32 address plus the immediate offset in natural numbers. They do **not** wrap that sum back to 32 bits. Four-byte accesses trap exactly when `address + offset + 4 > size`, before performing the access.
- Reads/writes are little endian and permit unaligned addresses. Traps retain successful preceding writes in the returned source memory.

Those memory choices agree with the official scalar load/store rules: the access-width bound uses the extended address sum, and alignment annotations do not prohibit ordinary unaligned access. [WebAssembly execution specification](https://webassembly.github.io/spec/core/exec/instructions.html#memory-instructions).

The executable probes produce wrapping addition `0xffffffff + 1 = 0`; right shifts of `0xffffffff` by 32 and 33 give `4294967295` and `2147483647`; an unaligned read from bytes 1…8 at address 1 gives `0x05040302`; a four-byte read ending exactly at size 8 succeeds and one extending past it traps; `0xffffffff + offset 1` traps rather than wrapping; a store of 170 before a later failing load remains visible at byte 0. These are useful concrete checks, not a proof of conformity for all Wasm executions.

The limits are substantive. There is no module/store/instantiation semantics, function signature, parameter binding, function-result typing, official validator equivalence, or source-binary decoding theorem. The custom `Func.validB` even accepts an empty body and a body leaving two i32 values; I proved both. Neither is a valid body for the spike's exported `(i32) -> i32` function. This is consistent with a validator for internal stack programs, but it cannot serve alone as Wasm function validation. The JavaScript frontend's initial `WebAssembly.validate` adds a real external check, without proving that its translated `program` preserves that module's meaning.

Only zero-parameter/zero-result nested block types are modeled, with conservative validation after unconditional branches; many valid Wasm programs are rejected. Calls, tables, globals, growth, `if`, result-bearing blocks, `return`, division traps, `unreachable`, floating point, SIMD, and other excluded features have no corresponding preservation guarantee. The implemented memory trap behavior is real within the model; saying “traps are proved” must retain that restricted scope. I found no concrete semantic mismatch in the unmodified supported scalar operations I inspected.

The target is similarly a custom AArch64 subset. Its memory is total, with no page permissions, faults, alignment/device-memory conditions, MMU, concurrency, or code-as-memory. Instruction PCs are list indices. W writes zero-extend, address additions wrap at 64 bits, and comparisons compute flags, but no theorem connects these definitions to an authoritative Arm model or silicon.

Native execution with argument 1 returns **1**; V8 returns **2**. D2 changes the load body's branch at PC 4 from `0x54000068` to `0x54000048`, making it branch to normal body exit instead of the handler. At address 65530 with offset 3, source execution must trap, while the corrupted native function returns normal success with result **65530**. Both wrong certificates are rejected by the baseline decoder and accepted by their mutant decoder, with clean composed axiom lists. The joint shift mutant is stronger evidence of the remaining gap. In its own complete project copy, `npm run build` and `npm test` both exit 0, including all 460 native/V8 comparisons and the decoder checks. Yet the mutated Lean source semantics evaluates `0xffffffff shr_u 16` to **4294967295**, while the native `shift(16)` returns **65535**. The compiler output and instruction bytes did not change. The tests compare real native execution with V8/Pulley, without checking that either agrees with the Lean evaluator; consequently they cannot notice this model drift. Full native/V8 regression testing would catch this wrong trap result; the body proof alone cannot.

**The trap handler and ABI are assumed, not verified.** `decodeAt` designates trap PC `body.length / 4 + 1`. The wrapper places one normal-exit branch immediately after the body and the trap handler after that. The decoder checks the conditional branch's destination, but `Arm.step (.bTrap ...)` immediately produces an abstract trap; it does not execute the handler. Normal execution likewise stops before the exit branch, register restores, stack adjustment, and `ret`.

The assembly prologue's parameter placement, zeroing of additional locals, saving/restoring X19–X28, X29/X30, stack alignment and availability, the C signature, the result/status encoding, actual memory mappings, and return control are outside the theorem. LLVM agreement checks the chosen assembly encoding, including the wrapper, but does not prove that the chosen wrapper implements the intended ABI. The ABI mutant makes this distinction observable.

**The full trust boundary has three parts.**

1. **Logical checking.** Trust Lean 4.35.0's kernel and the actual toolchain/imported library artifacts used to check the declarations, plus the reported standard axioms. Rebuilt preservation/composition declarations depend on `[propext, Classical.choice, Quot.sound]`; `check_sound`, `step_eq`, `body_checked`, and `compiler_eq` use only `[propext, Quot.sound]`. There are no local `sorry`, declared axioms, or `native_decide` uses in the audited sources/certificates. `bv_decide` occurs in the model proofs, but these checked declarations introduce no additional axiom in their dependency lists. Tactics, the SAT search, and the certificate writer do not need to be trusted to invent correct proof terms beyond what Lean checks. I did not independently rebuild/check the entire Lean toolchain and standard library.
2. **Specification adequacy.** To interpret those logical statements as Wasm-on-Arm correctness, trust the custom source syntax, validator and interpreter; `Match`/`MemRel` and the adequacy of their chosen observations; the Arm arithmetic/flag/register/memory and control semantics; the byte fetcher, opcode masks, field decoder, signed branch arithmetic, and trap/body-exit conventions; and that these definitions correspond to the intended external specifications. None of those external correspondences is a theorem here. Axiom cleanliness cannot establish them. The decoder and semantic mutants directly exercise this trust.
3. **Artifact and runtime binding.** For claims about executed files, trust the V8 validation plus JavaScript binary parser/Lean-source generation to select the right source program; the build orchestration and dependency selection; Mach-O parsing, symbol lookup, fixed 68-byte body offset, extraction, equality/hash checks, file identity and launch path; the ABI wrapper/trap handler/C harness and its native compilation; loader/OS mappings, instruction execution, and absence of interference. The entry hypotheses require real accessible memory, correct base/size/register values, and suitable stack/code placement, none of which is supplied by `Match` as a host theorem. For workerd-visible correctness, also trust its Worker/service-binding route, local server/process invocation and result serialization. V8, Pulley, LLVM and native tests are independent evidence sources, not logical proof rules.

The JavaScript **body encoder need not be trusted for correspondence of a body that passes the concrete certificate**; nor does Lean need to trust the certificate writer's proposed expected list, because of `compiler_eq`. The exporter's computed instruction list is similarly checked back against the compiler definition. These are material improvements. They do not remove the trusted source frontend, decoder-to-hardware interpretation, wrapper, or extraction/execution binding. There is no universal theorem about this JavaScript encoder and no proof that the in-memory executed bytes equal the Lean literal.

**Comparison with clifv.** [D3 §4.1](../deepdive/D3-lemma-gaps.md) describes a substantially broader backend: CLIF semantics, an LNSym-derived Arm model with conformance testing, checked allocation/proven fallback, encoder proofs, and linking/ELF-level results. This spike supplies a much smaller compiler plus translation validation of particular linked bodies against its custom ISA. Neither its frontend nor its ISA model attains the external semantic connection required to close D3's proposed Wasm-to-bytes theorem.

The current [clifv README](https://github.com/eth-act/clifv/blob/main/README.md) explicitly qualifies `E2E.backend_correct_final` by scope, callee contracts, and ABI contracts, and trusts semantic models and native proof evaluation. Its entry language is CLIF, not Wasm. The [contract document](https://github.com/eth-act/clifv/blob/main/docs/contracts/e2e.md) makes runtime/base-environment and entry-state premises explicit and documents closed-base witnesses; they must be assessed rather than hidden behind “end to end.” Its [usage documentation](https://github.com/eth-act/clifv/blob/main/docs/USAGE.md) distinguishes verified functions, compiled-but-unverified functions, and fallback to cg_clif. A successful build is therefore not a fully verified executable. I checked those primary documents, not clifv's full implementation or proofs.

The fair conclusion is that clifv already covers far more backend and binary-composition work, while retaining a qualified assurance boundary of its own. This spike's concrete byte bridge is worthwhile, but it neither establishes the missing official-Wasm frontend theorem nor independently validates its Arm semantics. Its smaller standard-axiom dependency list should not be mistaken for a stronger external specification.
