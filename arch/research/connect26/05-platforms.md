### C1. Sampling Witness — test a metric's exactness before changing its storage path

**Q — Source:** TELUS, Kevin, `[11:00]`: "Every click, every page view, every deploy went into the same D1 database"; `[12:00]`: "we weren't counting people properly anymore" and "our numbers jumped like seven times". T12-17–23. **I — Status: Open**, narrowly for an executable exactness contract plus counterexample corpus at the Analytics Engine boundary; broad analytics products and sampling-aware SQL already ship.

**I — One sentence:** a TypeScript test adapter that takes a declared metric, its event/index schema, and query, then produces a small counterexample whenever the requested exact result cannot survive the configured loss/sampling path.

**E — 30-second demo:** show two seven-event histories for the same app sampling index: one repeats user A, the other contains users A–G. A deliberately thinned fixture retains only A with weight seven in both histories. Event totals can be represented by the weight, but exact distinct users differ: one versus seven. The checker refuses `exact monthly active users` on that path, points to the lost identity information, then runs an exact `(tenant, month, canonical_user_id)` deduplication table on the full synthetic events and shows the correct result for each history. Include retries, skewed heavy users, and late events as additional fixtures. This is an illustrative simulator/counterexample, not a claimed reproduction of TELUS's unknown SQL or Cloudflare's proprietary sampler.

**F — Closest prior art:** [Analytics Engine's sampling guidance](https://developers.cloudflare.com/analytics/analytics-engine/sampling/) already explains weighting and index choice. [lazyanalytics](https://github.com/JayFarei/lazyanalytics/blob/main/README.md) already emits a `sampled` flag and calls visitor counts approximations; [its schema notes](https://github.com/JayFarei/lazyanalytics/blob/main/CLAUDE.md) use a visitor hash as the index. [Counterscale](https://github.com/benvinegar/counterscale) already packages analytics on this stack. [sqlsure](https://github.com/sqlsure/sqlsure) already checks semantic SQL errors against declared facts; its checked v0.1 rule list covers joins/additivity/policy, not this sampling contract. The [npm simulator package](https://www.npmjs.com/package/@d1testflare/analytics-engine) is adjacent local-testing prior art; registry metadata was readable even though the npm page returned 403.

**I — What remains after prior art:** the product is not an analytics dashboard, a semantic layer, a sampled-results badge, or a promise to infer exact identities from sampled events. The small opening is a reproducible witness connecting a declared exactness requirement to a concrete incompatible ingestion/index/query path, plus an integration fixture proving the selected exact lane. If an existing simulator/checker already generates these counterexamples, this candidate reduces to a contribution there.

**F/I — Beneficiary and evidence beyond the talk:** Workers platform owners moving operational events out of D1, and maintainers of WAE-based analytics packages. The public lazyanalytics and Counterscale implementations demonstrate actual consumers of this storage/query boundary; sqlsure demonstrates an existing implementation of declarative semantic checking. None establishes demand for this particular adapter. **Q:** TELUS supplies the unusually concrete silent-sevenfold-error anecdote. **I:** the metric contract must define authenticated identities and qualifying events; exactness is relative to accepted input events, not a claim to observe every human visit.

**I — Cloudflare relationship:** Cloudflare could implement a WAE-specific validator, and its error-bound roadmap reduces the room for a broad accuracy product. An independent fixture format can also run against SQLite/D1 and other analytics systems, while teams own their event identity and metric meaning. That gives Cloudflare a reason to adopt the fixtures/docs upstream, but little reason to leave a large platform feature unbuilt.

**E — 2–3-week version:** a local CLI/library with a small declared metric schema (`event count`, `weighted sum`, `exact distinct`), WAE-style index/weight fixtures, a supported SQL subset, counterexample output, and one D1/SQLite exact-dedup example. Reject unsupported syntax explicitly. Use deterministic known event histories as the oracle; do not ask an LLM whether the count is right. Keep proprietary-sampler emulation out of scope. For real ingestion, an exact-lane integration must deduplicate accepted events before sampling and define failures/late arrivals; a side write with unhandled loss cannot substantiate exactness.

**E — 1–2-day kill test:** reproduce the two-history counterexample, then run one existing WAE analytics query and one exact-ID query through the adapter. Inspect sqlsure and the simulator's actual APIs/tests for equivalent coverage. Ask three WAE/platform maintainers whether this catches a migration mistake their existing checks miss. Kill the standalone project if an existing tool already expresses the contract with the same witness, if all target users only need rough traffic trends, or if nobody will provide a metric/schema example. A successful test earns a small OSS prototype, not an inferred revenue forecast.

### C2. Worker Heap Check — reproducible retained-memory regressions for SSR bundles

**Q — Source:** Lovable, Fabian, `[16:00]`: "128 megabytes of memory budget"; `[17:00]`: "some out of memory errors" after including a compiler/highlighter in the server bundle; `[18:00]`: "keep the bundle on a diet". **I — One sentence:** a workerd/TanStack test adapter that compares retained heap and allocation evidence for a fixed SSR scenario before and after a bundle change, returning the import path and repeatable case behind a regression.

**E — 30-second demo:** a valid isomorphic app imports a server-compatible compiler unnecessarily. Its build and import-protection checks pass. Run a pinned local worker through a cold load and fixed render sequence, show the heap evidence and import chain, move that feature to the client-only path, then rerun the same workload and show the reduction. Any numbers shown would be measured by the demo; this report does not invent an MB improvement or claim every original Lovable error reproduces.

**F — Closest prior art:** [TanStack import protection](https://tanstack.com/start/latest/docs/framework/react/guide/import-protection), [Vite Bundle Analyzer](https://github.com/nonzzz/vite-bundle-analyzer), [Wrangler startup checks](https://developers.cloudflare.com/changelog/product/workers/3/), [Workers local memory snapshots](https://developers.cloudflare.com/workers/observability/dev-tools/memory-usage/), and [production CPU/heap profiles](https://developers.cloudflare.com/workers/observability/profiling-in-production/) already ship. **F/I — Beneficiary and evidence beyond the talk:** platform engineers shipping many SSR bundles and maintainers receiving worker-specific OOM reports. A [workerd stream-memory issue with a supplied reproduction](https://github.com/cloudflare/workerd/issues/5665) shows that concrete memory investigations occur outside this talk; [an independent worker-based connector](https://github.com/oomol-lab/open-connector/blob/main/docs/cloudflare.md) documents source-string retention and bundle-size effects. These are different memory mechanisms, not independent proof of the same Lovable dependency leak. Existing profilers show both technical feasibility and competitive pressure.

**I — Important limits:** compressed bundle bytes are not heap usage. Allocation profiles are not retained-heap snapshots. The loader does not guarantee that repeated remote requests hit one isolate, so a remote load sweep cannot claim controlled same-isolate concurrency. Node's heap limit is not equivalent to Workers' total memory accounting. Start with pinned local workerd fixtures and report runtime/build/scenario identity; stage remote corroboration only as observational evidence. A passing finite scenario is not a universal memory bound.

**I — Cloudflare relationship:** this is natural Wrangler/Vite-plugin/TanStack/MemLab contribution territory. Cloudflare already owns nearly all instrumentation. Independent value would lie in reusable application scenarios and import-to-retention diagnostics across many repositories, not a new profiler. Expect weak standalone defensibility.

**E — 2–3-week version:** a CLI adapter for a pinned workerd/Wrangler version, a handful of TanStack SSR fixtures, inspector snapshot capture, source-map/import-chain correlation, and a baseline-diff report. Consume existing profiler formats. Run known requests/data, separate cold initialization from post-GC retained state, and publish variability rather than one precise-looking total. Do not claim a managed-runtime hard cap from a local profile.

**E — 1–2-day kill test:** establish whether the inspector can reliably identify and snapshot the dynamically loaded child isolate. Run one compiler-bearing fixture through MemLab plus Wrangler and compare the effort to produce the same explanation. Kill or reduce to a documented recipe if isolate targeting is unavailable, if diagnostics cannot separate allocation from retention, or if existing tools already produce the required result without meaningful integration work. Do not silently substitute a top-level worker while calling it a dynamic-child test.

**I — One sentence:** a TypeScript analyzer that joins app publication/binding/rollback roots to stored bundle manifests and emits a conservative, explainable retention plan instead of aging files out blindly.

**F — Closest prior art:** [R2 lifecycles](https://developers.cloudflare.com/r2/buckets/object-lifecycles/) already expire objects by age/prefix. **I — Cloudflare relationship:** Cloudflare can supply lifecycle rules and generic storage APIs but does not automatically know an external platform's manifest/reference model. A neutral manifest/report schema may be useful upstream. A new artifact store or Git service is out of scope; existing stores remain authoritative.

**E — 2–3-week version:** JSON manifest/roots format, R2 inventory plus D1 metadata adapter, reference traversal, grace/rollback rules, stale-plan detection, and a local human-readable/JSON report. Require a publication generation or consistent snapshot; otherwise issue a keep/unknown result. Deliver read-only plans. Actual deletion, online write coordination, private backup enumeration, and recovering already deleted state are outside this version.

**E — 1–2-day kill test:** obtain an anonymized inventory from two independent dynamic-app operators and compare projected reclaimable bytes/rows with a simple last-N policy. Inject shared assets, a stale alias snapshot, a hidden reference, and publication during scan; the plan must refuse unproven retirement. Kill if existing registry/lifecycle tooling already captures their roots, if no operator has material retention debt, or if integrating its metadata costs more than maintaining a small internal SQL query.

## 5. ONE pick

**I — Pick C1: Sampling Witness, conditional on its two-day kill test.** The distinctive opening is not better counting advice: it is a runnable counterexample showing when a promised exact metric cannot be recovered from the retained information. TELUS reports an actual sevenfold discrepancy, while existing WAE analytics packages prove that developers encounter the same storage boundary. Better models can select better queries, but cannot recover arbitrary discarded identities from a sample.

**E — Start with one deliverable:** a small TypeScript fixture pack/CLI containing the two-history witness, weighted event-count checks, exact-distinct rejection, and a tested D1/SQLite deduplication example. Investigate contributing the sampling contract to sqlsure or an existing WAE simulator before creating an independent framework. If maintainers can already produce the same witness or do not need exact identities, stop; this research does not justify building another analytics platform.

**I — Why it wins the tie:** C2's missing integration may disappear once existing tools are composed, and C3's retention pain lacks urgency evidence. C1's unsound exactness claim has a small, model-independent counterexample and directly explains the strongest failure reported in these talks. That is enough to justify the bounded experiment, not a claim of a large unoccupied market.
