# Durable Objects: the runtime is taken; observing the lifecycle still has gaps

Research date: 2026-10-28. Assigned talks: **09** and **11**. Both supplied transcripts were read in full, including the Q&A. Background checked: `RESEARCH-SUMMARY.md` §0, §11, §12 and `stack/SUMMARY.md` §1.

**Labels:** **Q** = supplied transcript quotation; **F** = externally sourced fact; **I** = interpretation, candidate, or judgment; **E** = estimate or proposed acceptance target. In signal tables, the quotation column is Q and the meaning column is I. Timestamps identify the supplied one-minute caption block, not the exact second of the utterance. Brackets inside quotations mark caption corrections. Audience questions are attributed separately; employers are unknown unless identified.

**I — Finding:** the talks validate operational pain much more strongly than a new agent-hosting business. Most mechanisms are shipped or explicitly on Cloudflare's roadmap. Three narrowly scoped openings remain plausible, with substantial prior art: observing hibernation eligibility without waking the object; checking business effects across interrupted alarms; and rehearsing an application's hot shard. The strongest is an upstream test/runtime contribution, not another agent platform.

### Corrections that materially affect project selection

- **F — Memory is per isolate, not an exclusive 128 MB allocation per object.** Multiple DOs of a class and surrounding Worker code can share it. [Memory metrics documentation](https://developers.cloudflare.com/durable-objects/observability/metrics-and-analytics/). **I:** do not calculate fleet capacity by multiplying each object by a guaranteed 128 MB private budget.
- **F — SQLite DO storage is capped at 10 GB per object on Paid; a SQL string, BLOB, or whole row is capped at 2 MB.** Active CPU defaults to 30 seconds per invocation and is configurable up to five minutes; that is distinct from time waiting for I/O. [DO limits](https://developers.cloudflare.com/durable-objects/platform/limits/), [CPU explanation](https://developers.cloudflare.com/durable-objects/reference/faq/). **I:** chunked files do not remove the total storage ceiling, and a 30-second CPU limit does not establish a 30-second total agent lifetime.
- **F — About 1,000 requests/sec is a soft, workload-dependent figure.** CPU-heavy or serialization-heavy handlers may sustain less; overload returns errors after queueing. [DO FAQ](https://developers.cloudflare.com/durable-objects/reference/faq/). **I:** shard rehearsal must measure an application, not treat 1,000 as an admission entitlement.
- **F — Single-threaded does not mean only one asynchronous request at a time.** Execution can interleave across external awaits; input/output gates matter. [Design rules](https://developers.cloudflare.com/durable-objects/best-practices/rules-of-durable-objects/). **I:** a watchdog, alarm handler, and ordinary request can still race through stale business state.
- **F — Alarms persist and are at least once, with up to six automatic retries on uncaught failures.** They use millisecond Unix timestamps. Constructor scheduling can interfere with an existing alarm. [Alarm API](https://developers.cloudflare.com/durable-objects/api/alarms/). **I:** “a deploy lost my alarm” is a practitioner symptom needing a reproduction, not an established platform storage guarantee violation. Rearming before work is a pattern, not proof of correct business effects.
- **F — Abort testing and graceful eviction are different.** Current test APIs expose forced reset without draining as well as graceful eviction that drains requests. [Test APIs](https://developers.cloudflare.com/workers/testing/vitest-integration/test-apis/). **I:** selecting the wrong helper can omit the interruption window a test claims to cover.
- **F — Hibernation differs from inactive eviction; pending timers/I/O affect the lifecycle.** Profiling also affects eviction. [Lifecycle](https://developers.cloudflare.com/durable-objects/concepts/durable-object-lifecycle/). **I:** C1 must observe those transitions rather than create an extra pending request that changes them.
- **Q/I — The talk's “ACID databases… lock the table” explanation is not a general database result.** Its useful observation is shared write pressure versus per-thread partitioning; neither quadratic reads nor table-wide locking is inevitable for all implementations.
- **I — Status is date-scoped.** The recording's “not out yet” and “30 seconds” statements are preserved as Q; compatibility settings, package versions, partial rollout, and recording timing prevent using them as the current universal contract. The announced shutdown/deploy/retry features remain taken even where public docs have not caught up.

### Independent convergence and counterevidence

1. **Q — Lifecycle:** 09 at 16:00–19:00 promises fixes for exactly the disconnect/deploy/retry problems that 11 at 27:00–31:00 describes working around. **I:** this is strong convergence on pain and strong evidence against building the primitive independently.
2. **Q — Partition boundaries:** 09 at 12:00–14:00 warns about hot singletons; 11 at 20:00–25:00 uses a central accounting/Sheets coordination path. **I:** the demo is a useful workload for C3, but does not demonstrate that its coordinator is overloaded.
3. **Q — Files and memory:** 11 at 40:00–41:00 explicitly says the practitioner and Cloudflare independently arrived at chunked SQLite files. **F:** Computer now exposes that layer. [Filesystem](https://developers.cloudflare.com/agents/tools/filesystem/). **I:** convergence validates the need while killing the mechanism as an opening.
4. **Q — Telemetry:** 11's own 17:00 claim that per-thread storage solves logging is qualified by its 42:00 admission that fleet aggregation remains unresolved. **F:** Cloudflare now provides substantial tracing, and Yielded already exposes unfinished-work operations. [Tracing](https://developers.cloudflare.com/agents/runtime/operations/observability/tracing/), [Yielded operations](https://yielded.dev/agent/guide/operations/). **I:** “observability for agents” is too broad to recommend.
5. **F — Hibernation test demand extends beyond these talks:** LiveStore #1328 reports dependency timers preventing hibernation and is closed as resolved; `cloudflare-os` #338 separately reports long-lived RPC capabilities holding an idle workspace billable. [LiveStore issue](https://github.com/livestorejs/livestore/issues/1328), [Cloudflare OS issue](https://github.com/cloudflare/cloudflare-os/issues/338). **I:** runtime eligibility is a better test boundary than checking for a particular timer spelling.

## 3. Three candidates from the residual gaps

**I — Scope:** these are bounded contributions or developer tools, not claims that a new infrastructure company is justified. Generic agent hosting, idle fleet hosting, immortal Workers, durable/forkable Code Mode, basic scheduling, a filesystem, generic agent tracing, and a long-thread benchmark remain excluded. All candidate acceptance targets below are E, not measured outcomes.

### C1 — Observe hibernation eligibility without waking the Durable Object

**Q — Source:** 09, 15:00: “you need to use our APIs”; 09, 16:00: “anything held in… the properties of the class… will be wiped”; 11, 28:00: “eternally booting itself up.” **I:** these establish lifecycle-sensitive correctness and cost; the precise missing assertion comes from the external feature requests, not an invented quotation from the talks.

**I — One sentence:** add a local runtime/test observer that can assert an idle object's hibernation eligibility and observe its natural transition without calling or forcibly evicting it.

**E — 30-second demo:** start a plain hibernatable room and a room whose dependency retains a timer. A test reports the eligible control's natural transition and the blocked object's reason. Remove the timer and rerun; both pass. The demo must leave the socket functional after reconstruction. A fast eligibility assertion can be shown immediately; natural-transition verification takes the actual idle interval until a supported test-clock mechanism exists.

**F — Closest prior art:** [the existing reproduction](https://github.com/bohdanbirdie/cf-do-hibernation-repro) already uses durable boot counters and real idle waits; [Agents #1956](https://github.com/cloudflare/agents/issues/1956) requests a supported test API; [workerd #5835](https://github.com/cloudflare/workerd/issues/5835) requests passive lifecycle events; [test APIs](https://developers.cloudflare.com/workers/testing/vitest-integration/test-apis/) already provide forced eviction. **I:** none of those should be claimed as work this project invented. The residual is a supported, non-invasive eligibility/transition observation path.

**F/I — Who benefits and evidence:** maintainers of DO-backed realtime/agent frameworks and applications with long-lived sessions. [LiveStore #1328](https://github.com/livestorejs/livestore/issues/1328) is a resolved dependency-timer incident; [OS #338](https://github.com/cloudflare/cloudflare-os/issues/338) is a separate open RPC-residency report. These justify regression coverage but do not establish willingness to buy a standalone service.

**I — Why Cloudflare adopts it:** this belongs in workerd plus its test integration. Cloudflare is the natural owner; the contribution makes its scale-to-zero behavior testable by framework maintainers. There is no defensible argument that the platform would be unable to build it. The project's plausible destination is upstream.

**E — 2–3-week version:** an opt-in local observer at the actual hibernation decision point; bounded events keyed by namespace/object ID; a test helper waiting for eligibility or a lifecycle transition; cases for a pending timer, ordinary versus hibernatable sockets, completed work, and retained RPC work. Report only reasons the runtime can actually distinguish. Keep histories bounded and ensure the observer holds neither an actor capability nor an I/O task. Preserve the existing counter-based reproduction as an external control. No hosted dashboard is needed.

**E — 1–2-day kill test:** inspect the current workerd/Miniflare test plumbing for a supported passive hook or an in-flight implementation; reproduce the plain/timer distinction using the public fixture; prove a minimal observer leaves that distinction unchanged. Kill if it needs to wake the DO, bypasses eligibility like forced eviction, relies only on JavaScript timer monkey-patching, or duplicates an accepted implementation. If only the boot-counter wrapper is feasible, upstream the small test improvement rather than launch a separate project.

**I — Main limitation:** the state transition is runtime-owned, and upstream API acceptance is unverified. A local assertion does not certify production billing. The independent oracle is the runtime's real eligibility decision plus the existing black-box control, not a model grading its own explanation.

### C2 — Check the business effect across interrupted alarms

**Q — Source:** 11, 30:00: “die mid-execution”; 11, 29:00–30:00: “set the 9:15 alarm before it even executes”; 09, 19:00: “opt in some of your methods to double execute if it's [idempotent].”

**I — One sentence:** a workerd/Vitest scenario runner checks that a particular alarm-driven business operation neither disappears nor commits an unintended duplicate when its acknowledgement or execution is interrupted.

**E — 30-second demo:** an expense agent sends one approval notification. The receiver records the commit, then drops the acknowledgement. Reset the agent before its local completion write and invoke recovery. The unkeyed integration produces two receiver receipts; the keyed integration produces one and eventually records completion. Separately exhaust a failed schedule's retries and show the accepted operation remaining unresolved. Assertions use the receiver's receipts and the application's durable work record.

**F — Closest prior art:** [Cloudflare test APIs](https://developers.cloudflare.com/workers/testing/vitest-integration/test-apis/) provide lifecycle/failure ingredients; [SDK durable recovery](https://github.com/cloudflare/agents/blob/main/docs/agents/long-running-agents.md) gives checkpoint hooks; [`durability`](https://www.npmjs.com/package/durability) explicitly documents the commit/ack ambiguity and stable keys. [Resend](https://resend.com/changelog/idempotency-keys) supplies provider-side keys with a 24-hour retention contract. [celld testing](https://github.com/denoland/celld/blob/main/docs/testing.md) already uses conformance, simulation, and fleet fault injection at the runtime layer. **I:** the residual is a reusable application-effect check, not another retry library or runtime chaos framework.

**F/I — Who benefits and evidence:** developers using DO agents to send emails, submit expenses, or update external systems. Resend's own announcement identifies network/retry duplicate sends; the [TEEI practitioner report](https://theeducationalequalityinstitute.org/blog/durable-object-alarms-concurrent-updates-expiring-state-en/) describes stale alarm decisions and a fake-storage test that hid a race. The report distinguishes review/test findings from measured production loss. This supports realistic boundary testing, not a universal outage claim.

**I — Why Cloudflare adopts or leaves room:** the provider cannot infer an application's correct business receipt or the receiver's deduplication lifetime. It can supply reset helpers; the customer supplies the acceptance contract. A small package or upstream example can compose those boundaries. If the useful part is only a few fixtures, it should remain a contribution.

**E — 2–3-week version:** a thin adapter for a plain DO and one Agents-based harness; test receiver/control Worker with its own durable receipts; interruption barriers at request accepted, remote effect committed, acknowledgement delivered, and local completion persisted; deterministic restart/retry sequences; bounded schedule horizon; adapter-defined terminal statuses; machine-readable failing trace. Keep control across DO I/O contexts via explicit requests rather than shared awaited promises. Use abort for abrupt reset cases and eviction only for graceful cases. Do not contact real email recipients or mutate real customer systems.

**E — 1–2-day kill test:** run a seeded broken integration and its keyed counterpart on the real local runtime, both with lost acknowledgements. Compare directly with a handwritten test built from existing APIs. Kill the standalone-tool thesis if the package adds no reusable failing-schedule generation/diagnostic value, if the same suite already ships, or if an independent receiver cannot distinguish committed from attempted effects. A finding that application code needs idempotency is insufficient by itself.

**I — Main limitation:** effect semantics still require manual application input, and this overlaps the earlier research's replay-diff theme. No replay engine, continuation language, or unconditional exactly-once promise is proposed. Differentiation and willingness to adopt remain low-confidence.

### C3 — Rehearse the application's hottest Durable Object

**Q — Source:** 09, 12:00: “the hot singleton is the most common one”; 09, 13:00: “you get this chatty interface”; 09, 13:00: “broadcast… to all 1,000 people”; 11, 42:00: “a million users at the same time.”

**I — One sentence:** a workload-specific report compares candidate object boundaries using skewed traffic, real fan-out, and per-object latency/error data while also checking delivery/order invariants.

**E — 30-second demo:** keep total request volume constant, switch from uniform tenant traffic to one busy tenant, and watch the organization-level object develop a queue. Try channel objects, then isolate durable writes from socket fan-out. The report shows which object is hot, additional coordination hops, latency, overloads, and whether every expected recipient still got the correct ordered messages. Use a prerecorded run for the demo if the measurement window takes longer than 30 seconds.

**F — Closest prior art:** [k6 WebSockets](https://grafana.com/docs/k6/latest/using-k6/protocols/websockets/) and [thresholds](https://grafana.com/docs/k6/latest/using-k6/thresholds/) already generate load and fail SLOs; [Load Lab](https://gryczka.dev/garden/cloudflare-load-lab/) already provides global Cloudflare/k6 orchestration; [DO design rules](https://developers.cloudflare.com/durable-objects/best-practices/rules-of-durable-objects/) explain sharding; [`durability`](https://www.npmjs.com/package/durability) supplies routing/fan-out/topology; [FokosDB](https://www.lambrospetrou.com/articles/fokosdb/) already splits partitions. **I:** only reusable application-boundary comparison and invariant checking are tentatively open. Do not build another generator or router.

**F/I — Who benefits and evidence:** developers migrating a shared API or adding a central coordinator to per-thread agents. FokosDB's author reports latency spikes around partition splits and extra hops in a load test; [Cloudflare's FAQ](https://developers.cloudflare.com/durable-objects/reference/faq/) explicitly ties attainable throughput to handler work and overload queueing. Those establish that partition shape matters beyond these talks, but neither proves a market for a packaged advisor.

**I — Why Cloudflare adopts or leaves room:** safe boundaries depend on customer ordering, permissions and business transactions, which a generic router cannot guess. Cloudflare can still build this easily as a reference harness. A credible contribution would publish workload adapters and measurements rather than assert automatic optimal sharding.

**E — 2–3-week version:** reuse k6; implement Slack-like room and expense-coordinator adapters; support uniform, skewed and burst traffic; attach stable logical-operation IDs; correlate caller RTT with server execution time and available per-object metrics; record fan-out delivery receipts and coordination edges; compare user-supplied partition functions. Bound run duration and offered load. Clearly separate measured latency from estimated hidden queue time: an object cannot directly observe time spent queued before its handler starts.

**E — 1–2-day kill test:** compare an ordinary k6 script plus Cloudflare metrics against the proposed report on the same two partition schemes and a seeded delivery bug. Kill if the only extra output is a heatmap, if existing tags/thresholds express the entire useful result, or if the comparison changes semantics so that the faster scheme is not a valid replacement. Do not count successful requests as proof of ordered delivery.

**I — Main limitation:** likely consulting/reference-material value, with weak evidence for a separate product. Its survival against better models comes from measuring finite capacity and actual receipts, not from asking a model to invent a shard plan.

## 4. ONE pick

**I — Pick C1: a passive hibernation eligibility/transition assertion contributed upstream to workerd and the Workers test integration.**

**I — Why:** it has a precise missing API, a working external reproduction, demand in the runtime and framework issue trackers, and distinct dependency-timer/RPC-residency incidents. Its acceptance check is factual: does observation preserve the normal eligibility decision and transition? Better models do not remove that observer effect. The talk's “it goes idle and costs nothing” promise becomes something applications can test.

**I — Boundary:** this is not an original hibernation discovery, another idle-hosting system, a billing-cap service, or a new agent runtime. The counter-based test already exists. The contribution must remove invasive instrumentation/observation and expose the real runtime decision. Cloudflare adoption is the success path; commercial defensibility is not established.

**E — Decision:** spend at most two days on the kill test before a 2–3-week implementation. Stop if a supported passive hook or accepted implementation already resolves the request, if observation changes object liveness, or if the runtime owners reject the required test surface. This research authorizes no outreach or implementation beyond this report.

## 5. Five-line TL;DR

1. **Q/I:** both talks expose hard lifecycle and partitioning problems; neither supports reviving a general DO agent host.
2. **F:** pending-I/O keep-alive, schedules, recovery, files, tracing, profiling and load-test machinery already have implementations.
3. **Q/I:** shutdown hooks, graceful deploys and runtime retry improvements are Cloudflare-owned roadmap areas, even before full public controls.
4. **F/I:** silent hibernation blockers have reproducible prior art, while a supported non-waking eligibility assertion remains an open request.
5. **I/E:** pick C1 as an upstream contribution; use a two-day kill test, with C2 and C3 retained only as lower-confidence tools.
