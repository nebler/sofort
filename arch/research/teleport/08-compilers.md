# Warm compiler heaps, forked test worlds, and agent build loops

Research date: **2026-10-28**. **F** = sourced fact; **M** = measured in this report; **I** = inference; **E** = estimate or proposed experiment/price. External documentation without a publication date was checked on the research date. Prior local measurements are labelled **F — prior measurement**, not represented as new measurements.

**I — Main finding:** expensive developer-tool state is a real reason to snapshot and fork, but the strongest commercial implementation already does almost exactly the proposed server-side trick: BuildBuddy preserves warm Bazel state in Firecracker snapshots and ships it between executors. The most interesting remaining experiment is **isolated test branches for coding agents**, where each branch needs the same expensive initialized world but must not inherit another branch's mutations. Use the original tool's native runtime for real Node/Java applications. Treat QuickJS/Wasm as a candidate for a small, deliberately portable subset, not a faster place to run TypeScript's compiler.

**I — Scope:** researched the required lineage and five candidate workloads. No local benchmark was run: timing a small Node project would not decide whether a large compiler heap can be captured, invalidated correctly, transferred, and used faster than a persistent native compiler. This report creates no scratch artifacts, installs, accounts, deployments, or background processes. Read the two briefs and the round-one TL;DRs/verdicts; only this report is edited.

## 1. The precedent that most changes the answer

**F — BuildBuddy, January 26, 2026:** its own repository's fully cached Bazel build took about **6 minutes**, including **3.5 minutes** installing tools, checking out source, and constructing the analysis graph. It reports a **30-second median CI run** with snapshotted runners. This is a vendor's before/after report, not a controlled measurement isolating memory snapshotting. Its implementation chunks memory and disk, fetches chunks lazily, shares cached data, and uploads changed chunks. [BuildBuddy engineering report](https://www.buildbuddy.io/blog/fast-runners-at-scale/).

**F — BuildBuddy's current runner documentation:** memory-preserving Firecracker runners resume on another executor, with startup described as hundreds of milliseconds. Locality/save policies trade freshness, latency and billed traffic. A 16 GB-memory/50 GB-disk VM illustrates a **66 GB logical snapshot**, not a 66 GB download on every restore. [Remote runners](https://www.buildbuddy.io/docs/remote-runner-introduction/).

**I — Consequence:** “move an expensive warm build process to idle capacity” is a demonstrated product category. A new implementation must win on a particular integration, footprint, portability boundary, or correctness contract. Reimplementing it inside an interpreter with a smaller toy workload does not establish an advantage.

## 2. Lineage: three different kinds of reuse

**I — Distinguish:** (a) avoid executing an unchanged action by retrieving its output; (b) keep a process alive so its internal caches stay warm; (c) clone a prepared execution state so independent jobs inherit expensive initialization. Only (c) inherently supplies warm state plus branch isolation. Movement is an additional property, not a prerequisite for useful forks.

| Lineage | F: what it preserves/distributes, with primary source | I: implication for this proposal |
| --- | --- | --- |
| **distcc**, developed since 2002 | Distributes C/C++ compilation jobs; its ordinary path sends preprocessed source to installed remote compilers. [Project](https://www.distcc.org/) | Moving independent jobs is simpler than migrating a half-executed compiler. Input transfer and action granularity matter. |
| **Icecream** | Descends from distcc; schedules jobs onto free servers and can distribute packaged compiler environments. [Project README](https://github.com/icecc/icecream) | Scheduling and toolchain consistency already have solutions; an environment archive is not a live AST/checker heap. |
| **Bazel remote execution/cache** | Distributes build/test actions; remote cache holds action results and content-addressed outputs. [Execution](https://bazel.build/remote/rbe), [cache](https://bazel.build/remote/caching) | A cache hit avoids more work than restoring a compiler. Target misses and analysis/startup costs that remain after output caching. |
| **Bazel persistent workers** | Long-lived tools retain JIT work and ASTs; docs report Java compilation improvements of **2–4×**, with compiling Bazel about **2.5×** faster. [Workers](https://bazel.build/remote/persistent) | Mandatory strong baseline. If requests can safely share a daemon, exporting its heap often adds unnecessary work. |

Images do not eliminate version control or resource rebinding. |

[SBCL implementation and API documentation](https://github.com/sbcl/sbcl/blob/master/src/code/save.lisp) | Do not describe every image system as arbitrary instruction-level continuation capture. Hooks and quiescence are longstanding requirements. |
| **V8 / Node startup snapshots** | V8 explicitly demonstrated preloading TypeScript in **2015**, reporting roughly **100 ms** avoided compiler loading in that example. Node exposes snapshot build and deserialize hooks. [V8, September 25, 2015](https://v8.dev/blog/custom-startup-snapshots), [Node API](https://nodejs.org/api/v8.html#startup-snapshot-api) | Warm compiler startup is an incumbent snapshot use case. Use current Node restrictions rather than treating the 2015 limitations as current API guarantees. |
| **GraalVM native-image** | Runs selected initialization at image build time and embeds resulting objects in the image heap of a native executable. [Native Image basics](https://www.graalvm.org/latest/reference-manual/native-image/basics/) | Excellent for suitable static initialization. Not an API for moving an arbitrary already-running JVM. |
| **CRaC** | Checkpoints a warmed JVM; before/after hooks release and reacquire external resources. Its historical project benchmark reports Spring Boot time to initial operation **3898 → 38 ms** on a specified older Linux laptop/JDK setup. [Project](https://crac.org/), [project documentation](https://github.com/CRaC/docs) | A much more natural mechanism for existing Java services and JVM build tools. Do not transfer that ratio to Node tests. |
| **Firecracker in CI** | Serializes VM memory/device state; matching disk state is also needed. BuildBuddy uses this for warm CI/build runners. **F — Another direct incumbent:** E2B now documents reusable snapshots containing **filesystem and memory**, with many new sandboxes spawned from one snapshot. Pause/resume also preserves running processes. In contrast, Depot's documented custom CI images and sandbox snapshots preserve filesystem contents, **not process memory**. [E2B snapshots](https://docs.e2b.dev/sandbox/snapshots), [E2B persistence](https://docs.e2b.dev/sandbox/persistence), [Depot CI images](https://depot.dev/docs/ci/how-to-guides/custom-images), [Depot sandboxes](https://depot.dev/docs/sandboxes/overview), checked October 28, 2026.

**I — Product implication:** neither “snapshots” nor “microVMs” alone tells a buyer whether their checker, JIT, database buffer pool, or running server is retained. Ask what bytes and processes survive, where they can resume, and what must be rerun.

**F/I — Coding agents repay initialization only when their execution policy recreates it.** BuildBuddy identifies relatively cold agent runners as a target; OpenHands' October 4, 2024 evaluation article reports an example taking **10 minutes** and **300 examples taking two days** sequentially, motivating parallel evaluation. Neither source measures the share spent on compiler warmup or counts repeated build commands per task. [OpenHands evaluation](https://hub.openhands.dev/blog/evaluation-of-llms-as-coding-agents-on-swe-bench-at-30x-speed). **There is no sourced population-average “agents spend X% warming tools” in this research.**

**E — Transparent agent arithmetic:** if a task launches a fresh project service 20 times, 20 × 9.6 s is **192 s** of project-load work in the historical JS example; 20 × 1.2 s is **24 s** for the corresponding native example. Across 1,000 such launches, those are **2 h 40 min** and **20 min** respectively. These are scenario calculations, not observed agent behavior and not achievable savings forecasts. Twenty fresh whole-program checks have additional useful work that a snapshot cannot simply delete.

**I — Three distinct traces to collect:** independent agent tasks each booting one environment; one task repeatedly executing a fresh test/compiler CLI inside a persistent environment; and speculative patch branches created from the same initialized base. They have different reuse opportunities. A persistent workspace avoids repeated installs but does not automatically keep each CLI's checker alive. A persistent language server can avoid reloads, but must expose the diagnostics the agent actually needs.

## 4. The engine and transfer math are the main filter

**F — Prior local measurements, not rerun:** QuickJS-in-Wasm took **5.2×** V8 CPU for record/JSON transformations, **11.5×** for handwritten validation, and **31.1×** for one numeric loop. Those workloads are not TypeScript benchmarks. Actual retained heaps were megabytes: a Zod example was **5.51 MB raw / 1.50 MB gzip**; a 5,000-record world was **5.96 MB raw / 2.88 MB gzip**, with one **115.9 ms** gzip sample. See [engine measurements](../v8/03-roadblocks.md#7-interpreter-in-wasm-versus-v8-jit) and [heap measurements](../v8/03-roadblocks.md#5-real-snapshot-sizes-forks-and-storageegress-economics).

**I — Do not extrapolate the spike's ~0.4 ms restore into a compiler SLA.** That excludes substantial capture, compression, transfer, durable storage, runtime creation and invalidation work. Linear memory's high-water mark can stay large after GC; a small live-object count does not guarantee a small wire image. Browser Wasm memory copies are not operating-system CoW forks. One 32 MiB parent plus 100 fully resident 32 MiB children already implies **3.125 GiB** of child linear memories before hosts/staging.

**E — End-to-end break-even model:** let `W` be rebuildable initialization time on the baseline runtime, `U` useful per-branch CPU on that runtime, `k` the candidate's CPU multiplier, `A` capture/publication cost, `R` full per-child restore/transfer/rebind/invalidation cost, and `N` branches. Fresh execution costs `N(W+U)`; a once-warmed interpreted image costs approximately `kW + A + N(R+kU)`. Snapshotting wins only if:

```text
N[W - R - (k-1)U] > kW + A
```

**I — Interpretation:** even with infinitely many forks, `W` must exceed `R + (k−1)U`. Using a sensitivity assumption `W=10 s`, `R=0.2 s`, `k=5`, the suffix must cost less than **2.45 s** on V8; with `k=11`, less than **0.98 s**. With only `W=1 s`, the limits shrink to **0.20 s / 0.08 s**. These are hypothetical JS-runtime comparisons; the measured QuickJS/V8 ratios cannot be substituted for QuickJS/native-Go ratios. A persistent service costs roughly `W+NU` and is usually stronger still, if sharing/reset is correct.

**E — Transport sensitivity, decimal MB, excluding codec/RTT:** a **5 MB** image needs at least **0.4 s at 100 Mbit/s**, or **2 s at 20 Mbit/s**. A **100 MB** image needs **8 s / 40 s**. A **1 MB** delta needs **0.08 s / 0.4 s** only if the receiver already possesses the matching base. Moving a large checker to a browser can cost more than recreating it natively. Full/base/delta sizes must be measured after real edits and GC; pointer churn can dirty many pages.

### Which mechanisms fit which state?

**F/I — V8 snapshots:** Node's startup API is stable and provides rebinding hooks. Its current CLI docs require bundling user-land modules into the entry script and describe only a subset of built-ins as tested for serialization. They are a plausible baseline for a prepared pure-JS tool graph, not a documented arbitrary Node process checkpoint. `v8.writeHeapSnapshot()` is a diagnostic heap dump, not a process restore API. Existing filesystem watchers, native addons, sockets and background workers need separate treatment. [Node V8 API](https://nodejs.org/api/v8.html), [current CLI restrictions](https://nodejs.org/api/cli.html#--build-snapshot).

**F/I — Native forks/CRaC/Firecracker:** use a purpose-built prefork runtime when single-host process cloning is safe; Node's `child_process.fork()` starts a new Node process and does not expose a Zygote-style clone of the current JS heap. [Node child-process documentation](https://nodejs.org/api/child_process.html#child_processforkmodulepath-args-options). CRaC is the Java path. A whole-VM image is the natural unit for a Node server plus native modules plus local database and OS state. It retains original-runtime execution speed, at the cost of host compatibility and a much bigger state-management system. Firecracker's kernel mechanisms for lazy paging are unavailable to ordinary browser Wasm memory.

**F/I — `esbuild-wasm`:** browser execution and incremental contexts are documented; contexts retain file and parsed-AST caches. But the project warns its Wasm package can be **10× slower** than native esbuild in some cases. Running that Wasm directly avoids the QuickJS guest-JS interpreter, not the native-versus-Wasm penalty. Its JS bridge, plugins, worker messages and Go runtime state must be included or rebound; copying QuickJS memory does not snapshot an external esbuild instance. [API](https://esbuild.github.io/api/), [performance warning](https://esbuild.github.io/getting-started/).

**F/I — `swc-wasm`:** SWC publishes a browser Wasm interface. Good candidate for portable transforms, but a single-file transformation has little expensive mutable state to retain; caching its output may be better. A custom long-lived index or resolver could change that. A reusable SWC Wasm module is not evidence of an existing forkable live heap. [SWC Wasm documentation](https://swc.rs/docs/usage/wasm).

**F/I — TypeScript-Go Wasm:** Microsoft's 7.1 iteration plan lists publishing a Wasm build and bringing up the playground as work items; this is not proof of a supported snapshot API. The independent `ttsc` project documents an **experimental** TypeScript-Go browser build with an in-memory filesystem and Go's `wasm_exec.js`. This makes a bounded feasibility test credible. It does not establish native multithreaded performance, upstream browser support, or portable compiler continuations. Go distinguishes JS and WASI ports; a WASI command that exits is not automatically a resumable compiler service. [Microsoft plan, July 31, 2026](https://github.com/microsoft/TypeScript/issues/63703), [ttsc Wasm](https://ttsc.dev/docs/wasm/), [Go Wasm ports](https://go.dev/wiki/WebAssembly).

**I — Practical fit:** prefer a few MiB to a few tens of MiB of initialization-heavy, CPU-light pure-JS state, with virtual files and explicit host imports. Those are experiment admission targets, not measured compiler-heap sizes. A large native checker, Next.js/Turbopack process, jsdom environment, or Postgres server is not covered by the existing QuickJS capsule ABI.

## 5. Five candidates, each with a buyer, proof, and kill reply

### A. Warm TypeScript checker / language server per PR or agent branch

**F/I — Pain and present workaround:** large TS repositories pay seconds for project loading and more for checking, as above. They use watch mode/language services, project references, incremental `.tsbuildinfo`, CI caches and now native TypeScript. `.tsbuildinfo` is documented project-graph information on disk, not a serialized running checker. [Incremental builds](https://www.typescriptlang.org/tsconfig/incremental.html). A heap fork could preserve cyclic ASTs, symbols, resolution caches and lazily evaluated types without writing a new stable serializer.

**I — Why a live fork might win:** many independent edits against one unchanged dependency graph; one clean graph per branch, then narrowly invalidate affected nodes. Plain JSON loses functions and graph identity unless one builds a substantial serializer. Replay reruns parsing/binding and queries. But output caches already win on unchanged actions, and a persistent native service wins on serial edits. Loading an AST is not enough: lazy queries have to be exercised to warm useful checker state.

**E — Value:** a platform doing **100,000 checks/month** and saving **1 s/check** avoids only **1,667 runner-minutes**, about **$10/month** at the $0.006/min Linux reference rate below. Saving **10 s** gives about **$100/month**. Latency or parallel branch capacity, not cheap CPU savings, must support a **$500–$2,000/month** pilot. Ten such buyers would be **$60k–$240k ARR**, entirely a market hypothesis.

**E — 1–2 week proof:** small pinned TS 6 JS compiler with a virtual read-only dependency tree and one changed-file overlay; exercise diagnostics before capture. Compare fresh native TS 7, native incremental builds, a persistent language service, and bundled V8 startup snapshots. Only then try QuickJS. Include configuration/lib/dependency changes, file deletion, changed exports and transitive diagnostics; compare every result with fresh compilation. Stop the QuickJS path if the compiler API cannot be adapted or the heap exceeds the cap within two days.

**E — Demo/tweet:** show 20 isolated diagnostic branches sharing one base, actual parent-load count, image bytes and cold/warm p95. “Load a project once; fork isolated semantic checks for 20 patches. Here are the bytes and the native-daemon comparison.” **I — Killing expert reply:** “TS 7 plus a persistent service is faster; your edits invalidate the expensive cache anyway.” Accept that result if measured.

### B. Warm bundler or dev-server graph

**F/I — Pain and current tools:** large Next.js projects historically had multi-second initial-route work; esbuild contexts, Turbopack filesystem caches, HMR and persistent servers already retain or reconstruct graphs efficiently. A snapshot adds value only for isolated branches or host loss after significant graph construction, not merely keeping a dev server running.

**E — Both sides/value:** at **100,000 preview starts/month**, eliminating **5 s** is **8,333 minutes**, about **$50/month** in reference runner time; eliminating **30 s** is **$300/month**. A **50 MB** wire image costs at least **4 s** over a 100 Mbit/s link before resume work. A preview-platform buyer might pay **$1k/month** for a proven first-preview latency improvement; **100 buyers = $1.2m ARR** is a scenario, not a sourced addressable market.

**E — 1–2 week proof:** persistent `esbuild-wasm` context over virtual files, finish one build, checkpoint at a cooperative idle boundary if the runtime can be made self-contained. Compare direct native esbuild, its context rebuild API, a persistent Wasm worker, cached build outputs, and restart with existing disk caches. Pin plugin behavior. This requires a separate Wasm snapshot adapter; do not claim the QuickJS adapter captures it. For Next.js itself, benchmark current cache-enabled native restart rather than porting Turbopack in a fortnight.

**E — Demo/tweet:** compile a real small app, terminate the original worker, restore elsewhere, edit and rebuild; show complete initial and incremental timings. “A warm build graph crosses hosts, then rebuilds an edit; native rebuild is the control.” **I — Kill reply:** “Your bundler is stateless enough to cache outputs, or already restarts from disk in under 500 ms.” If so, reject heap migration for it.

### C. Isolated tests from a seeded, booted application world

**F/I — Pain and existing alternatives:** test frameworks explicitly identify repeated imports/environment creation and expensive setup as costs. Existing answers include global setup, persistent workers, transactional rollback and database templates. PostgreSQL can clone a prepared template database; that is a stronger seeded-data baseline than rerunning every migration and insert. [Vitest lifecycle](https://vitest.dev/guide/lifecycle.html), [PostgreSQL CREATE DATABASE](https://www.postgresql.org/docs/current/sql-createdatabase.html).

**I — Why live state wins specifically:** tests need a clean starting world but can mutate it independently. Snapshotting after fixtures, schema construction, dependency injection and app boot can preserve more than a database copy: initialized application objects, indexes and compiled rules. A serial daemon requires a correct reset protocol; an immutable fork removes that category of contamination. Journal replay still executes expensive setup CPU even if external responses are cached. A database on a remote service is not inside the app's heap; restore its state separately or snapshot the whole local stack consistently.

**E — Both sides/value:** assume **10 s** seed+boot, **0.2 s** complete restore, **0.05 s V8** useful suffix, and **5×** QuickJS CPU. For **100 branches**, fresh V8 costs **1005 s** of serial work; interpreted warm-fork costs **50 + 100×(0.2+0.25) = 95 s**, before capture cost. This deliberately favorable model is not a measurement. A persistent V8 app with reliable cheap reset could cost only about **15 s**, so it is a required control. At **100k branches/month**, saving **9 s** is **15k runner-minutes ≈ $90/month**. Charge **$500–$2k/month** only if the customer's latency, isolation or developer throughput gain supports it; **50 buyers = $0.3m–$1.2m ARR** is a hypothesis.

**E — 1–2 week proof:** use a real small pure-TS service/domain module that can run in both V8 and QuickJS, seeded with synthetic in-memory data and an actual derived index. Capture after boot; run independent mutation/test branches on Node and local workerd. Baselines: fresh V8, persistent V8 with explicit reset, V8 startup image, fresh and persistent QuickJS, and serialized fixture/index reload. Record integration exclusions. A genuine Postgres+Node integration suite belongs on a native/VM snapshot backend; adapting it is not an honest deliverable for the existing QuickJS mechanism in this time box.

**E — Demo/tweet:** boot and seed once, then fork 20 branches that deliberately corrupt different fixture rows; every sibling and the parent remain unchanged. “An agent tests 20 patches against the same booted world, each with clean state. We compare snapshot, reset, and fresh V8.” **I — Kill reply:** “Transactions or a warm test pool give the same isolation and run faster.” This is the central experiment, not an objection to wave away.

### D. CI resumes an entire warm job environment

**F/I — Pain/current spend:** the BuildBuddy case establishes minute-scale setup costs and a working memory-snapshot product. Namespace's cache volumes and Depot's prepared filesystems remove installs/downloads without memory images. E2B offers reusable memory-preserving sandboxes. Most general CI jobs need native tools, shell processes and filesystem state; those are outside a QuickJS heap.

**I — When live state adds value:** preserve analysis graphs, JIT state and running local services after filesystem caches have already removed download/install work. Whole-VM snapshots are the stronger mechanism; replay and JSON cannot reconstruct kernel/process state. Durable Objects hibernation is not a facility for retaining an arbitrary native build-server heap. For pure orchestration, a queue/workflow replay is usually adequate.

**E — Both sides/value:** **100k jobs/month × 210 s** is **350k runner-minutes ≈ $2,100/month** at the reference rate, an upper-bound scenario using the published setup duration rather than a promise of recoverable savings. A service capturing 20–30% of net verified savings could support **$420–$630/month** from that account. **100 similar accounts = ~$0.50m–$0.76m ARR** before storage, transfer, misses and support. Job-minute rounding and free allowances change actual cash savings.

**E — 1–2 week proof:** TypeScript controller/telemetry around existing native snapshot-runner results and one agreed CI workload; compare prepared image + cache volume, warm persistent runner and existing Firecracker snapshot product. Under this brief's no-accounts/no-deploy/no-Docker constraints, this remains a proposed partner experiment; it was not executed. A QuickJS/local-workerd demo can validate the job manifest and invalidation protocol, but cannot establish whole-CI speedups. Do not promise a new VM platform in two weeks.

**E — Demo/tweet:** split-screen one real job resumed on another executor versus cache-warm native start, reporting setup and useful work separately. “CI starts from yesterday's warm analysis state on a new machine; full bytes, cache hits and p95 included.” **I — Kill reply:** “BuildBuddy already ships this, including lazy snapshots; what advantage do you have?” There is no current general-purpose answer for this engine.

### E. Ship partially built state to idle machines or browsers

**F/I — Pain/alternatives:** distcc, Icecream, Bazel and Nix establish demand for using spare build capacity. They normally dispatch actions at dependency boundaries. BuildBuddy also covers moving warm runner state. The harder proposal is migration *during* expensive graph construction or compilation, where completed useful work might otherwise be lost.

**I — Why it occasionally wins:** host preemption or planned relocation with a small high-value live state and a compatible destination. Saving a half-computed checker is useful only if the checkpoint mechanism can stop there. The existing QuickJS safe point is after returning to the host; a long synchronous check has no automatic checkpoint halfway through it. Forking a compiler does not divide its remaining work automatically. Exporting artifacts/PCH/module caches or scheduling the next independent action usually has better granularity.

**E — Both sides/value:** a **100 MB** state moving in **8 s** over 100 Mbit/s to avoid **60 s** of rebuild work has a possible margin; avoiding **1.2 s** of native project load does not. Verification, queuing, codec and CPU differences consume the margin. If **10k preempted jobs/month** recover **60 s/job**, reference runner value is **$60/month**; paid placement/latency guarantees would need separate evidence. A **$100–$500/month** specialist integration and **20 customers = $24k–$120k ARR** are discovery hypotheses, not support for an open browser compute marketplace.

**E — 1–2 week proof:** bounded cooperative graph-building JS workload with genuine state, a host safe point between phases, one host forced to stop, and a second local host completing it. Compare restart, explicit serialized graph, journal replay and action-boundary dispatch. Add a browser destination only after local movement wins. Measure content-verification CPU and discard altered results. Browser compilation cannot be trusted as release verification merely because the incoming capsule hash was authentic.

**E — Demo/tweet:** unplug one executor after an expensive prefix and finish on the other, with resumed and fresh-build outputs matching. “This build phase survives losing its host; we publish when moving it beats restart.” **I — Kill reply:** “You engineered a safe point where a normal checkpoint/artifact would be smaller, and an untrusted browser cannot certify the output.” Often correct; count revalidation and reject the market if it erases savings.

## 6. Pricing, correctness, and the common acceptance bar

**F — Cash reference:** GitHub's checked pricing is **$0.006/minute** for standard Linux 2-core x64 runners, **$0.022/minute** for 8-core Linux, with job minutes rounded up. Public-repository standard runners and included private-repository allowances can make marginal cash savings zero. These rates are comparison anchors, not a prediction that QuickJS can replace equivalent machines. [Runner pricing](https://docs.github.com/en/billing/reference/actions-runner-pricing), [usage rules](https://docs.github.com/en/actions/concepts/billing-and-usage).

**I — Business size conclusion:** CPU-minute savings for small compiler/test initializations are surprisingly small. Repeated long initialization at platform scale, time-to-first-result, and branch isolation can be valuable; the payer is the CI/agent/preview platform or an engineering-productivity team. No sourced TAM or willingness-to-pay study was found. The per-candidate revenue scenarios above are deliberately bottom-up and are not additive: their buyers and budgets overlap. Integration, invalidation and support may cost more than the saved compute.

**I — Required cache identity:** exact compiler/runtime/module/ABI hashes, source/dependency tree, lockfile, config/flags, libraries, plugin versions, relevant environment, platform assumptions, seed fixture version and inherited journal position. A PR patch requires correct invalidation against the base; it is not authorization to use stale diagnostics. Hash the virtual filesystem and enumerate changed/deleted/added files. Configuration and dependency changes may invalidate the whole parent. Private sources and old freed bytes in snapshots remain confidential data.

**I — Required fork contract:** parent becomes immutable; branches get independent mutable memory, filesystem overlays, fixture state and effect identities. Rebind clocks/randomness, watcher handles, temp paths, ports and connections; retain operation receipts without inheriting permission to repeat writes. A database fork must match the app's captured view. For benchmark fixtures, disable real external writes. Use the [existing ownership/effects contract](03-contract.md) rather than inventing a second migration protocol. Build results returned by an untrusted device require independent validation.

**E — Common 10-working-day gate, no deployment required:** days 1–2 pin the workload and record fresh V8/native, persistent/reset and disk/explicit-state controls; days 3–5 implement one idle-boundary capture, restore and independent branch overlay; days 6–8 test 100 varied patches/mutations, invalidation and deliberate cross-branch contamination; days 9–10 measure end-to-end cold/warm/miss behavior with repeated trials. Use local Node/workerd; add a browser only if it resolves an actual placement need. Do not spend the whole window porting a large compiler.

**E — Record:** initialization executions and wall/CPU, useful suffix time, p50/p95 time to correct result, all-in capture/publication/restore, full/base/delta wire bytes, peak memory for parent plus concurrent children, invalidation/miss rate, cache population cost, and integration days. Include novel edits, not just unchanged repeated queries; compare outputs with clean runs and expose unsupported features.

**E — Proposed go/no-go thresholds:** zero mismatched results or state leakage in the finite test set; **≥2×** end-to-end improvement against the strongest correct baseline for the intended isolated-branch workflow, after amortizing parent creation over observed fanout; **≥30%** latency improvement when all transfer and miss costs are counted; and a specific buyer trace supporting the economics. These are decision thresholds, not achieved results. If persistent/reset or explicit serialized state is within **10%** and simpler to integrate, use it. If native/VM snapshots win, change backend instead of defending QuickJS.

## 7. Ranked top three

1. **I — Isolated warm test worlds for speculative coding-agent branches.** Clearest reason to need both rich live state and clean forks. Native/VM implementations are commercially credible; the portable pure-TS subset still needs the decisive reset/V8 comparison. Best experimental bet, not validated demand.
2. **I — Warm native CI/build environments across controlled executors.** Strongest evidence of existing value, and strongest incumbent competition. An integration into an existing runner system is more credible than a new QuickJS CI engine.
3. **I — Forkable semantic services for many related patches.** Rich state and relevant agent latency, but native TypeScript, incremental caches and persistent services sharply reduce the available margin. Portability may matter more than compute savings.

**I — The ONE bet:** build the two-week **warm isolated test-world fork** experiment, with a real portable pure-TS module, no external database claim, and V8 persistent/reset plus V8 startup images as the performance controls. If the practical buyer needs a Node+database stack, take the same product hypothesis to an existing Firecracker snapshot backend. Kill the QuickJS performance claim if its suffix penalty wins; retain browser portability only when a buyer actually needs it.

**Three next steps — E:** (1) obtain one agent trace separating environment setup, process starts, module loading, checking and useful tests, with actual branch fanout; (2) qualify the small test-world experiment against the named controls and report full costs/misses; (3) test willingness to pay with that measured result, or switch to an existing native snapshot integration if required by the workload. This report performs no outreach.

## Five-line TL;DR

1. **F/I:** Warm build heaps have real value; BuildBuddy already moves snapshotted Bazel runners across machines.
2. **F/I:** Historical TS project load was 9.6 s JS versus 1.2 s native; full compiler timings are not all initialization.
3. **F/I:** Persistent workers, current disk caches, V8 images, CRaC and Firecracker are mandatory, often superior baselines.
4. **I/E:** Clean isolated test branches are the best small experiment; large native tools should keep their native runtime.
5. **I:** Agent warmup share is unmeasured here; QuickJS's 5–11× glue penalty can erase every saved second.

**Verdict — GO-WITH-CHANGES for forked warm test environments; NO-GO for QuickJS-hosted `tsc` as a general speed play or generic “new snapshot CI” positioning.** **I:** prove useful isolation and complete-job latency on a small portable workload; use native snapshots where real applications demand them. No new compiler, snapshot, or agent-speedup measurement is claimed in this report.
