# Moving running programs: the recurring promise, the failures, and the 2026 opening

Research date: **2026-10-28**. Scope: the portable JavaScript/Wasm capsule described in [BRIEF.md](BRIEF.md), independent of the other Sofort projects. This report adds history and a bounded update to [the October 27 landscape](../v8/02-landscape.md), rather than repeating that inventory.

**Labels:** **F** = sourced fact, including an explicitly attributed project claim; **I** = inference or recommendation; **E** = estimate. **F-prior** identifies existing repository measurements, not measurements made here. No new execution benchmarks, demos, deployments, or security tests were run. Primary papers, specifications, author accounts, project source, and official documentation were inspected on **2026-10-28**. Publication dates below describe the documents, not search-engine crawl dates. A surviving manual establishes a mechanism, not continued commercial support; an author's demonstration claim is not independent replication.

## 1. The historical answer

**I — The promising 2026 product is a deliberately limited mobile computer, with explicit effects and ownership.** The history does not support “migration was impossible until Wasm.” It supports a more demanding proposition: migration works when someone controls a sufficiently complete execution boundary, compatible destinations, and the economic reason to move. The recurring failure was expecting that mechanism to create a universal market for visiting programs.

**I — Three questions must remain separate:** can a program's execution state move; will its dependencies and authority still work; and does moving it improve the user's outcome? An interpreter image can preserve execution without resolving dependencies or economics. Conversely, durable replay can satisfy the user's need to continue work without transporting a heap.

**I — Terminology used here:**

- **Code mobility / remote spawning:** send code, a closure, or inputs and start execution there.
- **Weak mobility:** move code and selected/object state, then enter a handler; the original active call stack is not preserved.
- **Strong mobility:** preserve a continuation, including where execution resumes. A cooperative suspension boundary still qualifies; arbitrary-instruction preemption is an additional capability.
- **Live migration:** transfer execution between hosts with a bounded final pause, often copying most state while the source still runs. A parked continuation transferred between awaits is a narrower form of execution handoff.
- **Durable execution:** recover progress after loss, through replay, snapshots, or explicit state. Durability and geographic mobility are independent properties.

## 2. Mobile agents: the 1990s version was remarkably close

### What the named systems actually promised

| System and dated primary evidence | F — Mechanism and promise | I — Lesson for this proposal |
|---|---|---|
| **General Magic Telescript, announced January 6, 1994.** [Original General Magic announcement, preserved by the Pen-Based Computing History Museum](https://www.penbasedcomputing.com/timeline/telescript-technologies-at-heart-of-next-generation-electronic-services/). | An electronic representative travels through networks to act for its owner: messaging, shopping, travel arrangements. AT&T announced PersonaLink as its deployment channel. Telescript's places, traveling agents, and supporting service infrastructure were described by Jim White at the [Dartmouth mobile-agent workshop, 1996](https://www.cs.dartmouth.edu/dfk/research/project/dagents/workshop/1996/summaries.html). | “An agent carries its task to the service” is an old product idea. The receiving places and useful services matter as much as the traveling program. |
| **IBM Aglets, 1996–1997.** [IBM-copyrighted Aglet API source, 1996–1998](https://www.ime.usp.br/~kon/MAC5759/aulas/AgletContext.html); [maintained project archive and manuals](https://aglets.sourceforge.net/). | Java mobile objects within an agent context, proxies, lifecycle events, messaging, dispatch/retraction, and persistence. The IBM-origin API models a host secured against visiting agents. Ordinary Java serialization gives object-state mobility rather than an arbitrary JVM thread image; see the platform authors' treatment of Aglets and Java limitations in [MOA, COOTS 1998](https://www.usenix.org/legacy/publications/library/proceedings/coots98/full_papers/milojicic/milojicic_html/milojicic.html). | Saving an agent object is not saving every local variable in the active Java stack. The distinction is central when comparing against a pending QuickJS promise. |
| **Agent Tcl / D'Agents, mid-1990s; retrospective evaluation May 2002.** [Gray, Cybenko, Kotz, Peterson, Rus, *D'Agents: Applications and Performance of a Mobile-Agent System*](https://www.cs.dartmouth.edu/dfk/research/gray-spe/index.html). | Tcl, Java, and Scheme support; the paper explicitly reports strong mobility for Tcl and Java. Information-retrieval agents sometimes outperformed client/server implementations, with performance depending strongly on application and environment. | This is direct prior art for moving a continuation to remote information. Its authors already rejected a universal performance win. |
| **ObjectSpace Voyager, 1997–1999.** [Vendor's *Voyager ORB 3.1 Developer Guide*, preserved copy](https://manualzz.com/doc/32736663/objectspace-voyager-orb-developer-guide). | Combined Java distributed objects/ORB facilities with mobility. `Mobility.of(object).moveTo(...)` moved serializable objects while client references remained usable; departure/arrival callbacks supported rebinding. | Transparent references can hide movement while creating routing and failure dependencies. Serializable objects do not establish arbitrary live-stack migration. |
| **JADE, late-1990s lineage; documented in the authors' 2007 book.** [Bellifemine, Caire, Greenwood, *Developing Multi-Agent Systems with JADE*, chapter 6](https://www.mit.bme.hu/system/files/oktatas/targyak/8671/Developing-Multi-Agent-Systems-with-JADE.pdf); [JADE Agent API, v4.5.0 documentation](https://jade-project.gitlab.io/API/jade/core/Agent.html). | Agent Mobility Service moves serialized agents between containers in one platform; inter-platform mobility requires the additional mechanism described in the book. `doMove()` requests asynchronous migration; `doClone()` requests a remote copy. Lifecycle hooks handle arrival/departure. This is weak mobility, not an active Java-stack image. | Mobile agents and cloning remain useful framework capabilities. Do not describe every framework as dead, or mistake framework-defined mobility for a universal capsule ABI. |

**F — Telescript really did preserve control flow.** General Magic's **October 1995 Language Reference** says the instruction after `go` executes at the destination; `send` constructs traveling clones. It also specifies capability/resource permits, their intersection, enforcement, and distinct region/place grants. This was already more than copying a script and its inputs. [Vendor language reference, introduction and predefined-class concepts](https://bitsavers.trailing-edge.com/pdf/generalMagic/Telescript_Language_Reference_Oct95.pdf). **I — Wasm improves the available substrate; it does not invent sandboxed execution or capability-limited mobile agents.**

**F — Telescript had a concrete distribution failure, not merely a security objection.** General Magic's **July 11, 1996** press release offered Internet mail and a Web browser to PersonaLink subscribers after AT&T's decision to discontinue PersonaLink on **August 30, 1996**. This is contemporaneous primary evidence of the Internet replacing its original service channel. It does not establish that every mobile-agent project failed for the same reason. [Original General Magic release](https://www.penbasedcomputing.com/timeline/general-magic-internet-access-software-to-be-offered-to-att-personalink-subscribers/).

**F — Standards were attempted.** OMG's **Mobile Agent Facility 1.0, January 2000**, following the 1998 MASIF work, standardized management/transfer concepts. Its interoperability section explicitly excludes language interoperability and distinguishes similar from dramatically different agent systems. The MASIF authors also deferred multi-hop security standardization and described language/serialization conversion as difficult. [Normative specification, §1.1](https://www.omg.org/spec/MOBFAC/1.0/PDF); [Milojičić et al., MASIF, 1998](https://citeseerx.ist.psu.edu/document?doi=aa0a75e4e8728ce8d03931adbfc19a528f3c93dc&repid=rep1&type=pdf).

**I — Thus “there were no standards” is misleading.** The unmet requirement was a deployable common execution, service, authority, and compatibility contract. Common transfer calls did not make one vendor's live agent executable inside every other vendor's engine. Wasm reduces the machine-code mismatch; it does not standardize the semantics of a tool called `purchase`, its permission model, or the fate of a request already in flight.

### Why the universal visiting-agent market did not emerge

**F — Security ran in both directions.** NIST's **October 1999 SP 800-19** distinguishes threats involving agents, platforms, and other entities. IBM researchers Karjoth and Posegga's **July 2000** operator-focused paper argued that contemporary security was insufficient for large commercial deployments inside public-network operators. Separately, Claessens, Preneel, and Vandewalle's **February 2003** transaction-security paper identified malicious hosts as a particularly difficult problem. [NIST report](https://www.nist.gov/publications/mobile-agent-security); [IBM authors' abstract](https://research.ibm.com/publications/mobile-agents-and-telcos-nightmares); [transaction-security paper](https://doi.org/10.1145/643477.643479).

**I — Protecting a host from visiting code and protecting the visiting computation from its host are different products.** The latter host can inspect secrets, falsify inputs, alter execution, or simply stop. A sandbox inside that host does not remove its control. An open market for strangers' idle machines needs a much stronger trust story than a runtime accepting customer code inside one cloud operator.

**F — The benefits were questioned contemporaneously, rather than disproved only afterward.** Harrison, Chess, and Kershenbaum's **March 28, 1995** IBM report compared mobile agents with alternatives and concluded that individual benefits were not overwhelming, while a pervasive framework could enable many services. [Author report](https://scispace.com/pdf/mobile-agents-are-they-a-good-idea-4ev3mskzkw.pdf).

**I — That exposes a coordination trap:** a useful marketplace needs many hosts and services; each host needs a reason to install, secure, meter, and support the runtime before the marketplace exists. HTTP services could expose useful operations independently. Sending a query or installing a server-side procedure often removed the same network chatter without accepting arbitrary visiting continuations. The Web winning is a credible ecosystem explanation, particularly for Telescript; it is not a sourced universal obituary for Aglets, Voyager, D'Agents, and JADE.

**I — Evidence limit:** the inspected primary records do not supply a defensible product-by-product ranking of causes or a closure date for every project. Research completion, commercial business failure, framework survival, and failure to become a universal Internet substrate must not be collapsed into “they all died because security.”

## 3. Process migration: working systems, expensive substrate

### Systems that already harvested idle computers

| System / primary date | F — What moved and why | I — Boundary exposed by the history |
|---|---|---|
| **V System, SOSP 1985.** [Theimer, Lantz, Cheriton, *Preemptable Remote Execution Facilities for the V-System*](https://pages.cs.wisc.edu/~bart/739/papers/vkernel.pdf). | Offloaded programs to idle workstations and moved them away when owners reclaimed the machines. Network transparency and avoiding residual dependencies on the source were explicit design goals. | “Move work to idle user devices” needs eviction, not just initial placement. That requirement is older than mobile agents. |
| **Charlotte, IEEE Computer, September 1989.** [Artsy and Finkel, *Designing a Process Migration Facility: The Charlotte Experience*](https://citeseerx.ist.psu.edu/document?doi=0e9a4988420f8204fcdc71c31171f95208b4dd2a&repid=rep1&type=pdf). | Detached a running process from its environment, transferred it, and reattached it while preserving communication; explicitly handled machine/communication failures during transfer. | The difficult part includes the handoff protocol and communicating peers. A valid state file alone does not establish a successful move. |
| **Sprite, in daily use by late 1988; paper August 1991.** [Douglis and Ousterhout, *Transparent Process Migration*](https://web.stanford.edu/~ouster/cgi-bin/papers/migration-spe.pdf). | Same-architecture process migration, idle-workstation offload, and eviction. Much migration occurred at `exec`, avoiding transfer of an existing address space. Reported compile speedups were 3–6×, with centralized file resources limiting gains. | Often the cheaper answer was to place a new task correctly. Moving a running heap must beat that baseline. |
| **MOSIX / openMosix.** [Project-era openMosix documentation](https://tldp.org/HOWTO/openMosix-HOWTO/x210.html); [project's official closure, February 29 / effective March 1, 2008](https://sourceforge.net/p/openmosix/news/2008/02/openmosix-project-ends/). | Transparent load balancing moved the user portion of a process while a deputy on its Unique Home Node handled many system calls. openMosix's announcement ended development and froze its source; this is a statement about openMosix, not the whole MOSIX lineage. | The home deputy simplifies compatibility but prevents a fully independent roaming process and can turn local syscalls into network traffic. |
| **Condor / HTCondor Standard Universe.** [Official 8.8 manual](https://htcondor.readthedocs.io/en/v8_8/users-manual/running-a-job-steps.html); [maintainer, January 9, 2020](https://www-auth.cs.wisc.edu/lists/htcondor-users/2020-January/msg00025.shtml). | Relinking with `condor_compile` enabled checkpointing, remote system calls, and restart elsewhere. Restrictions included process/thread and system-call limitations. The standard universe was subsequently removed; HTCondor retained application-level checkpoint workflows. | Batch resource harvesting succeeded; one transparent checkpoint implementation was not essential to that success. Explicit checkpoints can be the more maintainable contract. |

**F — openMosix's own July 15, 2007 end-of-life announcement** attributed its decision to increasingly available inexpensive multicore processors reducing the importance of single-system-image clustering, and developers moving toward virtualization and other projects. [Project announcement](https://sourceforge.net/p/openmosix/news/2007/07/openmosix-project-end-of-life-announcement/). **I — Treat that as the maintainers' stated rationale, not proof that clustering became unnecessary. It is a concrete example of a cheaper substitute and shifting developer investment undermining a functioning migration system.**

**F — Sprite's creator gives an unusually clear account of ecosystem cost.** Ousterhout's retrospective says distribution was difficult, the system ran at roughly ten sites, kernel maintenance grew harder, and the team could not keep up with commercial UNIX features and support teams. It decided in late 1991 to wind down major development. This is stronger evidence than attributing Sprite's fate to migration performance alone. [Ousterhout, *Sprite Retrospective*, covering 1984–1995](https://web.stanford.edu/~ouster/cgi-bin/spriteRetrospective.php).

**F — Residual dependencies were a conscious tradeoff.** Douglis's **1990 dissertation**, §4.4, explains that Sprite's home machine still participated in operations such as fork/exit, so migration could not protect a process from that machine's failure. Some dependencies, such as a physical device, were inherent without changing behavior. [Author dissertation](https://www2.eecs.berkeley.edu/Pubs/TechRpts/1990/CSD-90-598.pdf).

### Read the 2000 survey carefully

**F — Bibliography:** Milojičić, Douglis, Paindaveine, Wheeler, and Zhou, *Process Migration*, **ACM Computing Surveys 32(3), September 2000, pp. 241–299**, DOI **10.1145/367701.367728**. The full text inspected here is the authors' **HPL-1999-21, February 1999** prepublication report; its §7 separates misconceptions from adoption barriers. [Final publication](https://doi.org/10.1145/367701.367728); [author preprint, pp. 36–38](https://shiftleft.com/mirrors/www.hpl.hp.com/techreports/1999/HPL-1999-21.pdf).

**F — Their distinction:** complexity, unacceptable cost, insufficient transparency, and heterogeneity were frequently cited objections, but implementations had demonstrated solutions. The deeper barriers were too few compelling applications, inadequate distributed infrastructure, migration not being a user requirement because simpler alternatives sufficed, and users' resistance to sharing their own workstations. They also reported limited customer demand and missing vendor cooperation. Their outlook remained optimistic: useful applications and infrastructure might change adoption.

**I — The lesson is a demand test, not a prediction that another technical advance must finally make migration mainstream.** A 2026 version should identify which user loses work or money without *mid-execution* relocation. “We can use idle capacity” is insufficient when fresh-job placement, retry, batching, or a normal queue satisfies that user more cheaply.

## 4. Object mobility, images, and continuations: much of the mechanism already existed

### Languages that made execution state explicit

**F — Emerald, 1980s; TOCS February 1988:** Jul, Levy, Hutchinson, and Black implemented fine-grained mobility of objects ranging from data objects to process objects. `move`, location operations, and call-by-move/visit made placement part of the language/runtime. [*Fine-Grained Mobility in the Emerald System*](https://people.eecs.berkeley.edu/~prabal/resources/osprelim/JLH%2B88.pdf); [language guide](https://www.emeraldprogramminglanguage.org/guide.pdf).

**I — Emerald's relevance is stronger than “mobile code existed.”** It connected language semantics, identity, location, compiler/runtime support, and references. The catch for adoption is that the world must speak that language and runtime. A JS-in-Wasm capsule lowers that switching cost for guest authors, while still requiring all destinations to implement its host contract.

**F — Obliq, SRC report June 1994 / POPL January 1995:** Cardelli's distributed lexical scope allowed computations to travel while free identifiers retained their original bindings/sites. Objects were local by default; object migration could be expressed through cloning and aliasing. The expanded paper explicitly warns that flexibility can create undesirable network traffic and still requires placement planning. [POPL paper](https://www.classes.cs.uchicago.edu/archive/2007/spring/32102-1/papers/p286-cardelli.pdf); [expanded author paper, Computing Systems 8(1), 1995](https://www.usenix.org/publications/compsystems/1995/win_cardelli.pdf).

**I — A computation can move while its dependency graph does not.** Preserving references is not equivalent to making all accesses local; cutting references can change semantics. This is exactly the choice between carrying tool results, continuing to call an origin broker, and moving the relevant data/tool implementation.

**F — Kali Scheme, TOPLAS September 1995:** Cejtin, Jagannathan, and Kelsey's *Higher-Order Distributed Objects* integrated transmission of closures and continuations into distributed Scheme, enabling user-defined thread placement/migration and distributed linking. It was based on Scheme 48. [Project archive](https://conservatory.scheme.org/kali/); [paper record and links](https://research.scheme.org/concurrency/).

**F — Termite Scheme, Scheme Workshop 2006:** Germain, Feeley, and Monnier combined Erlang-inspired message passing with serializable Gambit continuations. Their paper demonstrates process migration, cloning, and dynamic code changes. The simple `migrate-task` captures a continuation, spawns it remotely, and terminates locally, leaving mailbox/links behind; a proxy variant addresses different semantics. [Author paper, §4.9](https://www.iro.umontreal.ca/~feeley/papers/GermainFeeleyMonnierSW06.pdf).

**I — Termite is especially direct prior art for “fork this running program.”** It also shows why a continuation is not the whole actor: mailbox, identity, links, and peer routing require an explicit decision. In the present proposal, the analogues are outstanding tool calls, stream positions, timers, approvals, and ownership of the next real effect.

**F — Erlang's successful distribution takes a different path.** Official Distributed Erlang documentation describes remote process creation and transparent message passing, links, and monitors. Official code-loading documentation describes current/old module versions and switching a running process to new code through fully qualified calls. [Distributed Erlang, current documentation](https://www.erlang.org/docs/27/system/distributed.html); [code replacement, OTP 26 reference](https://beta.erlang.org/docs/26/reference_manual/code_loading.html).

**I — Neither remote `spawn` nor hot code loading is an API for exporting an arbitrary active BEAM process stack and restoring it on another node.** Applications can transfer selected state and arrange handoff, but that is an application protocol. Erlang is evidence that location-aware actors, message passing, supervision, and code evolution can deliver much of the value without promising universal transparent process mobility.

### Images: a running world as a file predates Wasm

**F — Lisp machines:** Symbolics manuals describe saved Lisp worlds, world loading, incremental saves, and startup initialization. The **Genera 7 site-maintenance manual, November/December 1986**, describes loading a world, configuring machine/network identity, and starting the environment. [Vendor manual, “Boot.boot Files” and “Manipulating Worlds”](https://bitsavers.trailing-edge.com/pdf/symbolics/3600_series/Site_Maintenance_Genera_7_0_Dec86.pdf).

**I — A saved Lisp world is an ancestor of the image approach, not evidence of seamless arbitrary hardware migration.** The surrounding machine, devices, identity, and startup reconciliation still matter. Calling every “save world” a portable live-machine snapshot would overstate the historical contract.

**F — Smalltalk/Squeak:** the official Squeak distribution describes an image as a snapshot of all living objects and pairs it with a platform VM. Squeak's implementation documentation explains that execution resumes inside the snapshot method when an image starts. [Official distribution and image description, current page](https://squeak.org/downloads/); [snapshot implementation explanation, May 23, 2017](https://wiki.squeak.org/squeak/818).

**F — Browser execution is also older than 2026.** The **DLS October 2014 SqueakJS paper** describes a browser VM reading and writing the standard Squeak image format. SqueakJS runs unmodified Smalltalk images in a Web page and supports loading an image from a computer or server. [Author's paper](https://freudenbergs.de/bert/publications/Freudenberg-2014-SqueakJS.pdf); [SqueakJS site](https://squeak.js.org/). **I — This is a decisive qualification to browser-portability novelty claims:** a portable language world and a browser interpreter were already a workable combination. It does not establish automatic migration of native sockets, browser DOM objects, or arbitrary external processes.

### Continuation-based Web servers: suspend across user interactions

**F — PLT/Racket:** Graunke, Krishnamurthi, Van der Hoeven, and Felleisen's **ESOP 2001** server work provided high-level control abstractions for Web interactions. Today's Racket server distinguishes stateful servlets, whose continuations remain in server memory, from stateless servlets with serializable continuations stored on disk or sent to the client. [Author paper](https://cs.brown.edu/~sk/Publications/Papers/Published/gkvf-web-server-on-hlos/paper.pdf); [official server manual](https://docs.racket-lang.org/web-server/).

**F — Racket already documents the hard parts:** stateless servlet transformation makes control state serializable, but captured values must be serializable, untransformed library contexts need special treatment, and code changes can invalidate existing continuations. Storing a continuation in a browser is not running that Racket continuation in the browser. [Official stateless-servlet documentation, §3.2](https://docs.racket-lang.org/web-server/stateless.html).

**F — Seaside, research paper 2004 / IEEE Software September–October 2007:** Ducasse, Lienhard, and Renggli describe components with continuation-based control flow across pages and support for browser backtracking. A continuation may be invoked multiple times with different input. [Author paper, 2004](https://scg.unibe.ch/archive/papers/Duca04eSeaside.pdf); [2007 article](https://scg.unibe.ch/archive/papers/Duca07a-SeasideIEEE-SCG.pdf).

**F — Arc requires a narrower description.** Graham discussed continuation-style Web programming for Viaweb/Arc in **November 2001**, noting that carefully constructed closures could implement it. The public Arc-family Anarki server maps generated `fnid`s to functions in a server table and expires those entries; links/forms invoke the saved functions. [Graham's message](https://people.csail.mit.edu/gregs/ll1-discuss-archive-html/msg00681.html); [server implementation](https://github.com/arclanguage/anarki/blob/master/lib/srv.arc). **I — This is retained server-side interaction control, not evidence of a portable, durable full-stack image in Arc.**

**I — These frameworks did not fail to demonstrate useful continuations.** They made sequential interaction code practical. Their historical warning is that retained control state brings session memory, deployment/versioning, inspection, expiration, and repeated-invocation semantics. Backtracking a purchase flow cannot undo a purchase already committed elsewhere. The same issue returns when an agent forks a checkpoint for alternate futures.

### Unison: language-level distribution with current infrastructure

**F — Unison's March 7, 2023 description** shows `Remote` as an ability with `fork`/`await` and location-aware computations; ability handlers capture the continuation at an operation boundary. Its model separates the distributed program from the handler/backend. This substantially predates the current capsule proposal. [Unison authors, *Visualizing remote computations*](https://www.unison-lang.org/blog/visualizing-remote/).

**F — Its November 3, 2025 Volturno case study** describes shipped code, location-aware references/promises, transactional storage, and explicit failure/view-change protocols. Workers from an old view must stop before the next view processes their keys. [Unison author case study](https://www.unison-lang.org/blog/volturno-design/). **I — Sophisticated language mobility does not eliminate fencing or distributed failure handling.**

**F — Additional 2026 evidence beyond the landscape:** on **October 8, 2026**, Unison announced its Cloud implementation as **MIT licensed**, newly opening Nimbus workers, the API server/control plane, and the UI; the client was already open. It describes distributed batch fork/join, typed communication, storage, secrets, and long-running jobs. [Unison Cloud open-source announcement](https://www.unison-lang.org/blog/unison-cloud-open-source/).

**I — This changes availability and inspectability, not the birth date of code mobility.** It weakens a claim that distributed computation is necessarily locked inside a closed provider. The inspected sources do not establish arbitrary native-stack preemption, a browser execution backend, or interoperability with QuickJS capsules. Unison's language/ability contract remains different from exporting a JavaScript interpreter image.

## 5. Why VM live migration succeeded, and what CRIU actually contributes

**F — VMware's vMotion shipped in 2003.** Its engineers' **USENIX 2005** paper describes moving a running VM without modifying its guest OS or applications. The vendor's **July 9, 2019** engineering account describes active compute-state transfer between ESXi hosts. [Nelson et al., implementation paper](https://www.usenix.org/legacy/events/usenix05/tech/general/full_papers/short_papers/nelson/nelson_html/index.html); [vendor engineering account](https://blogs.vmware.com/cloud-foundation/2019/07/09/the-vmotion-process-under-the-hood/).

**F — Xen's Clark et al., NSDI May 2005,** explains why the VM boundary helped: application state, kernel state, and communication state moved together, avoiding process-migration dependencies on the old host. Its pre-copy approach transferred memory while execution continued, then used a final stop-and-copy interval. The evaluation included service downtime as low as **60 ms**, a paper result rather than a general SLO. [Author paper](https://www.usenix.org/legacy/publications/library/proceedings/nsdi05/tech/full_papers/clark/clark_html/index.html).

**I — VM migration aligned the boundary, buyer, and operating environment:**

1. The encapsulation boundary included the kernel that understood process resources.
2. The operator controlled both hosts, network routing, storage access, credentials, and admission.
3. The guest application did not need a new language or application rewrite.
4. Hardware maintenance and cluster rebalancing supplied recurring operational value.
5. A limited compatibility domain was acceptable; a universal heterogeneous Internet was unnecessary.

**I — This is not evidence that state transfer became free.** Dirty memory can resist pre-copy convergence; storage, device passthrough, network reachability, and CPU compatibility still constrain placement. The winning product could impose those constraints inside a managed fleet. A cross-provider/browser runtime must either reproduce that control or narrow its guest interface until those dependencies disappear.

**F — CRIU is process/container checkpoint-restore, not VM migration.** It works with Linux process state and kernel interfaces. Its TCP documentation describes `TCP_REPAIR`, connection sequence/queue restoration, packet locking during transfer, and the requirement that the original IP address be available at restore. Its external-resource documentation requires caller help for resources outside the dump boundary. [CRIU TCP documentation, including Linux 3.5 lineage](https://www.criu.org/TCP_connection); [external resources](https://criu.org/External_resources).

**I — CRIU is a successful engineering tool within a controlled Linux environment, but not a portable browser format.** It illustrates the persistent resource problem especially well: copying address-space bytes cannot by itself recreate a TCP connection or an externally mounted filesystem. Grouping CRIU with vMotion without this distinction hides the very boundary the proposal is trying to simplify.

## 6. Modern evidence: additions, not a second landscape

**F-prior — The October 27 landscape already covered** Golem replay/forks, Vercel quickjs-wasi and merged experimental Workflow memory snapshots, Cloudflare DOs/fibers/Code Mode/Containers, Wasmer/WASIX, Temporal/Restate, interpreter snapshots, VM sandboxes, and Wasm migration papers including Wharf/MVVM and Wanco. Those are baseline prior art, not discoveries of this report. [Existing landscape](../v8/02-landscape.md).

### New discovery: Weave moves an executing Wasm program into and out of browsers

**F — Weave (`dphilla/weave`) is a directly relevant omission.** GitHub metadata inspected today records creation on **July 3, 2026** and last push on **October 8, 2026**; the repository declares **Apache-2.0**. Dates establish public repository history, not the invention date of its mechanisms. [Repository](https://github.com/dphilla/weave); [repository metadata endpoint](https://api.github.com/repos/dphilla/weave).

**F — Author claims, not replicated here:** its README reports migration across Wasmtime, Node/V8, wazero, and WAMR; Chrome↔native and Chrome↔Chrome examples; checkpoint-to-file; and continued event sequences across migration. The compiler transforms supported Wasm so live locals/control state spill into linear memory at polls and can rebuild the call stack. It uses pre-copy followed by a final state transfer. It rejects shared-memory threads, `externref`, and several newer Wasm features. Host resources require compatible explicit services. [README](https://github.com/dphilla/weave/blob/main/README.md).

**F — Mechanism differs from the local QuickJS spike.** Weave rewrites module control flow, registerizes operand-stack values, and adds unwind/rewind machinery; poll boundaries occur at function entries and loop back-edges. This permits suspension within an instrumented computation instead of waiting for a JavaScript promise to park and the enclosing Wasm stack to empty. The design acknowledges code-size/speed costs. [Design document, §§1.1–1.4](https://github.com/dphilla/weave/blob/main/docs/DESIGN.md).

**F — Handoff semantics are unusually explicit.** The wire protocol stages a non-executing target and transfers ownership through prepare/commit. After the irreversible boundary, an uncertain commit cannot authorize source resumption; availability may be sacrificed. The document says durable failover across process/machine crashes still needs a coordinator or application fencing. Stateful-service restoration must not publish external effects while staging. [Protocol, phases and host services](https://github.com/dphilla/weave/blob/main/docs/PROTOCOL.md).

**F — The browser-sidecar example has a real-browser test harness in source.** Its documented scenario is Chrome→Wasmtime→Chrome, checking the next emitted counter value at both boundaries. Its authors explicitly limit that evidence to same-host ICE/Pion interoperability, without claiming a forced TURN or server-reflexive route test. [Demo and qualification instructions](https://github.com/dphilla/weave/blob/main/demos/browser-sidecar/README.md).

**I — Consequence:** do not claim that browser↔server live continuation movement is an unimplemented category in 2026. Weave documents a broader active-Wasm mechanism and browser transports; the landscape's interpreter projects already document narrower images. This research did not independently execute Weave or establish a production deployment, independent users, hostile-input resilience, general WASI compatibility, or a managed tool-authority service. Those are the appropriate remaining questions. Source-supported prototype capability and a supported commercial contract remain distinct.

## 7. Which old walls have moved in 2026?

The historical column refers to the primary evidence above. The 2026 judgments below are **I**, anchored to those mechanisms and the local evidence rather than claims of universally solved problems.

| Historical obstacle | What changes in 2026 | What still blocks a universal roaming program |
|---|---|---|
| **Host must accept someone else's code** | **I:** Wasm supplies a common validated execution format with explicit imports; browser and server runtimes already host it. A small interpreter can offer familiar JS inside that boundary. | **I:** quotas, termination, engine bugs, imports, output amplification, and snapshot-input handling remain host responsibilities. A trusted engine module does not make an arbitrary restored guest heap trustworthy. |
| **Agent must trust the host** | **I:** trusted cloud/enterprise fleets can use established operator relationships; capabilities and remote brokers can limit exposed secrets. | **I:** a browser controlled by a stranger can inspect or alter local state and fabricate results. Encryption in transit or a snapshot signature does not enforce honest execution. Confidential tasks and consequential writes cannot simply trust borrowed devices. |
| **Incompatible CPU, OS, and runtime state** | **I:** fixed wasm32 interpreter layouts remove much native ISA/pointer variation. Weave offers another route through instrumentation. | **I:** exact module/build identity, mutable globals/tables, import ABI, engine upgrades, unsupported Wasm features, and snapshot schema remain compatibility constraints. Wasm specifies execution, not one universal snapshot format. |
| **No installed destination substrate** | **I:** browsers and edge networks provide distribution that 1990s agent platforms had to build. Shipping a Wasm module is easier than installing a new OS. | **I:** hosts still need the right tools/data access. Edge availability does not mean arbitrary edge capacity, GPU placement, or permission to execute next to a database. A broker may remain the effective home node. |
| **Too little demand for migration itself** | **I:** generated programs can wait for model calls, approvals, and changing plans; saved state and branchable debugging may matter to harness builders. Agents can consume a constrained ABI without requiring a human to learn a new distributed language. | **I:** an agent can also generate explicit checkpoint state or ordinary workflow steps. A useful new consumer reduces authoring friction; it does not prove willingness to pay for heap mobility rather than replay. |
| **Transfer and execution overhead** | **I:** small interpreter heaps, compression, deltas, shared module caches, and object storage make some moves cheap. | **I:** large/high-entropy retained data, repeated moves, cold compilation, and an interpreter's CPU overhead can overwhelm savings. Cheap snapshot storage does not imply cheap active execution. |
| **Residual dependencies and locality** | **I:** a tool-only ABI can forbid accidental sockets/files/DOM and explicitly describe the few services needed. | **I:** moving a continuation closer to one service can move it farther from another. A reference to an origin tool remains remote. Database bandwidth, API limits, and GPU model state do not travel with a JS heap. |
| **Duplicate ownership and irreversible effects** | **I:** journals, stable operation IDs, leases/epochs, and workflow engines offer mature building blocks; Weave exposes uncertain handoff explicitly. | **I:** source and destination must not both issue the same next effect. Forks need separate authority rules. Crash-after-effect/before-receipt and partitioned owners still need cooperation from the effect service or reconciliation. |
| **Code evolution and operational support** | **I:** content-addressed modules, pinned deployments, conformance suites, and source-visible runtimes make compatibility auditable. | **I:** retaining vulnerable old engines is costly; changing them can invalidate images. Patching, debugging a remote continuation, inspection, cancellation, retention, and recovery support become the product. |
| **People own the allegedly idle machines** | **I:** opt-in browser Workers and cooperative checkpoints make participation and eviction easier to express. | **I:** users can close tabs, revoke consent, sleep devices, or need battery/thermal headroom. Browser throttling, connectivity, incentives, trust, and verification can cost more than the recovered CPU cycles. |

### The scarcity argument must name the scarce resource

**F-prior — Existing evidence already bounds the attractive story.** The October 25 spike parked a QuickJS continuation in Wasmtime and resumed it in Node/Chromium/local workerd/Dynamic Worker, including two divergent replies. Later roadblock measurements found **1.5–6.4 MB compressed** examples and roughly **5–11× V8 execution gaps on tested glue workloads**, with a larger gap on a numeric loop. These are workload-specific prior results, not universal ratios or fresh measurements. [Portability spike](../portability/02-wasm.md); [roadblock measurements, §§on snapshot growth and performance](../v8/03-roadblocks.md).

**I — Four different scarcity claims have different answers:**

1. **CPU glue capacity:** moving parsing, transformations, or local search to idle devices can recover actual CPU capacity. It must offset interpreter overhead, transfer, verification, and device churn. Starting the job on that device may be enough; migration earns its keep when placement changes after useful state accumulates.
2. **GPU/HBM inference capacity:** moving a JS orchestrator does not move weights, GPU kernels, or a model server's KV cache. If it still calls the same model API, it has not supplied another GPU or relieved that API's capacity. A model-provider scheduler integration is a separate project. [Existing compute analysis](../moonshots2/01-compute.md).
3. **Data/network/origin pressure:** moving a small program to authorized data can avoid exporting a large dataset and can combine repeated queries locally. This is the classic mobile-agent/locality case. It requires a host beside the data and useful local operations; a remote tool proxy alone does not deliver it. [Existing systems analysis](../moonshots2/05-systems.md).
4. **RAM occupied by waiting programs:** persisted images can free interpreter memory while waiting. Replay, application checkpoints, and provider VM suspension already substitute for this outcome. Compare total memory and recovery cost against them rather than against a permanently reserved server per agent.

**E — Illustrative network floor:** at an assumed **10 Mbit/s**, transferring **100 KiB** takes **81.9 ms** and **6 MiB** takes **5.03 s**, before latency, encryption, checkpoint capture, restore, or a missing engine module. At **100 Mbit/s**, **1 MiB** alone takes **83.9 ms**. These are `bytes × 8 / bits-per-second` calculations, not measured device/network performance. Compression size is not a bounded latency guarantee.

**I — A move should satisfy a workload-specific inequality:** saved queueing, avoided data transfer/round trips, avoided reconstruction, and cheaper useful execution must exceed capture + transfer + restore + coordination + slower execution + verification/recovery. Count only savings on the actual critical path. A “green” move additionally requires measured energy/carbon effects of transfer and destination execution; a cheaper region is not automatically greener.

## 8. Product implication: inherit the successful constraints

**I — Start with a compatible, trusted execution pool and opt-in browser participation for tasks whose state/results can be exposed or verified.** Make CPU glue, data-local operations, durable waits, and debugging branches separate use cases with separate baselines. Open participation can be a later expansion; it should not be the prerequisite for a useful product.

**I — Keep the guest boundary intentionally small:** JavaScript continuations at documented host-return safepoints; a versioned interpreter module; bounded memory/instructions/output; and a few explicit host operations. The pending operation belongs to a durable broker, identified by a stable ID. The capsule records what input has reached the guest; the broker records which real effects occurred and which owner may act next. A browser restore receives fresh, limited authority, not a copied secret wallet.

**I — Make a fork a policy operation as well as a memory operation.** Historical continuation systems already showed alternate futures. The valuable modern contract is which branches may perform real writes, what they may read, how they are canceled, and how an approval applies after policy/tool versions change. Simulation branches can share recorded inputs; committing one branch must fence stale owners and must not pretend external history has been rewound.

**I — The closest successful ancestor is the VM operator's controlled migration domain, combined with language-level continuation capture.** Wasm/browser reach makes that domain easier to extend, but the strongest differentiation would be an inspectable compatibility/effect contract and a useful handoff experience. Small snapshots and the ability to resume twice are prior-art mechanisms, including implementations public in 2026.

## Five-line TL;DR

1. **F/I:** Telescript, D'Agents, Emerald, Scheme continuations, and images already demonstrated the essential ideas; mechanisms were not the only obstacle.
2. **F/I:** The 2000 survey emphasized demand, infrastructure, adequate alternatives, and machine ownership; those remain adoption tests.
3. **F/I:** VM migration succeeded within controlled compatibility/network/storage domains with a recurring operational buyer.
4. **F/I:** Wasm, browsers, and agent harnesses improve reach; newly identified 2026 Weave source already documents live browser/native Wasm migration.
5. **I:** Trust, external effects, ownership, versioning, and actual compute economics still decide whether a roaming program is useful.

**Verdict — GO-WITH-CHANGES for the historical/product angle:** pursue a constrained, versioned continuation runtime with measured placement value and brokered effects. Do not base the thesis on technical novelty, automatic GPU relief, or a universal market for strangers' idle devices.

**The three next steps:**

1. **Qualify the new comparator locally:** pin Weave's source and run its browser↔native and failure-handoff scenarios in a bounded scratch environment; compare the instrumentation contract with an await-only interpreter image. Record real overhead, state size, unsupported features, and what the demos actually prove.
2. **Prove one economic use case against simpler alternatives:** compare migration with fresh placement, restart/replay, and explicit checkpoints for a workload whose intermediate state and best location actually change. Measure useful CPU, end-to-end latency, transferred bytes, total memory, and recovery under device loss; keep inference capacity separate.
3. **Specify compatibility and effect ownership before broader distribution:** module/ABI hashes, safe suspension rules, pending-operation IDs, journal cursor, ownership epoch, branch authority, version transitions, cancellation, and uncertain commits. Demonstrate that a stale source cannot issue a real write after handoff.
