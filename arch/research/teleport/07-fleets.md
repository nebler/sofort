# Agent fleets: cheap sleeping is solved; cheap continuation branching may still matter

Research date: **2026-10-28**. **F** = sourced fact or explicitly attributed vendor claim; **M-prior** = measurement in the existing repository, not performed for this report; **I** = inference; **E** = estimate or proposed experiment. Dollar amounts are USD, before tax. Mutable documentation and prices were inspected on this research date; publication dates are given where available. No cloud accounts, deployments, paid experiments, new runtime benchmarks, or outreach were used. Only this report was written.

Read before researching: [round-two brief](BRIEF-2.md), [original brief](BRIEF.md), and the TL;DRs and verdicts of [compute](01-compute.md), [history](02-history.md), [contract](03-contract.md), [spike](04-spike.md), and [product](05-product.md).

## Answer

**I — A movable program gives a fleet operator a portable unit of execution, rather than just a portable record of application state.** The operator can unload it, resume it on another compatible executor, and branch it without knowing how the application represents every closure, object graph, and pending continuation. This matters when the retained working state is small and rebuilding it is expensive. It matters much less when an agent is a conversation transcript, a few tool results, and a program counter that already fit an ordinary checkpoint.

**I — Do not sell “a million agents that cost nothing while idle” as the differentiator.** Durable Objects already remove idle compute billing; E2B already pauses live memory without charging stopped compute; Golem already unloads durable Wasm agents and recovers them through replay. Nor does “fork a running agent” distinguish the mechanism by itself: E2B memory snapshots can spawn many clones, Modal has memory clones, and LangGraph and Golem support branching. The credible opening is **small, portable continuations for generated or otherwise opaque JavaScript working state, combined with a correct fleet control plane**. Whether that opening is commercially meaningful remains unproved.

**I — Strongest initial application:** branch a paused, stateful tool-composition program into several read-only investigations or evaluations, choose a result, and continue under one fenced owner. The buyer is an agent-runtime or evaluation platform team. Generic support-agent hosting is a weak initial market: its best incumbent is often SQLite/JSON plus hibernation, and its dominant costs may be model and voice services rather than orchestration memory.

### Lifetime and idleness

**F — Long-lived identity is a documented use case.** Cloudflare describes agents persisting for days, weeks, or months, with waits ranging from seconds for model output to days for people and months for scheduled work. Its **99% dormant / 1% active** discussion is an illustrative economics example, not published utilization telemetry. [Long-running agents, updated 2026-10-27](https://developers.cloudflare.com/agents/concepts/agentic-patterns/long-running-agents/).

**F — Coding environments can outlive an individual turn.** Current Codex Cloud documentation says saved VM state is recoverable by default for up to **seven days after the last turn start or task resume**. Claude Code cloud sessions continue after the user leaves the page. These establish asynchronous persistence, not an always-running VM during the entire retention period. [Codex Cloud, accessed 2026-10-28](https://help.openai.com/en/articles/20001545-using-codex-cloud), [Claude Code cloud, accessed 2026-10-28](https://support.claude.com/en/articles/12618689-use-claude-code-in-the-cloud).

**F — Sandbox lifetime limits also need careful reading.** E2B documents one-hour Hobby and 24-hour Pro **continuous runs**, while paused sandboxes have unlimited retention and resuming resets the continuous-run limit. That does not mean the logical agent must die after 24 hours. [E2B billing and limits](https://docs.e2b.dev/billing).

**I — Four meanings of idle:** (1) no user event for days; (2) an unresolved human approval; (3) awaiting a model/tool for seconds; (4) CPU-idle but retaining a browser, TCP session, subprocess, or database transaction. Categories 1 and 2 are straightforward durable-event sleep. Category 3 can also become a callback-based durable wait. Category 4 may require a larger execution environment or reconnect logic. A small JS heap captures none of the remote browser's memory or model server's KV cache.

**I — Evidence limit:** I found no suitable primary measurement of the fraction of lifetime spent idle across the named production fleets. The one-million/99%-idle scenario below is explicitly an assumption. Do not turn Cloudflare's explanatory example into an industry statistic.

A comparison that reruns every historical LLM call is an unfair baseline.

## 3. One explicit fleet: 1 million agents, 99% idle

### Workload assumptions

**E — A deliberately auditable planning model, not a vendor benchmark:**

- 1,000,000 durable identities retained throughout 30 days: **2,592,000 seconds**.
- 1% active **wall time**, including model/tool waits that a given runtime keeps in memory: **10,000 concurrently active equivalents**, **7.2 million active instance-hours/month**. This is not 1% CPU utilization.
- One wake/agent/day: **30 million wakes/month**. Each averages 864 seconds active wall time, consistent with the assumed 1%. At equilibrium this is only 11.57 wakes/second; burst scenarios differ.
- For the lightweight application, explicit JSON state is **100 KB/agent**, archived live image **1 MB/agent**, restored guest linear memory **2 MiB/active agent**. These are different representations of the same proposed workload, not measured universal sizes.
- Native JSON/graph glue consumes **100 ms CPU/wake**; portable-interpreter execution including capture/restore consumes **600 ms/wake**. The 6× factor is a sensitivity assumption motivated by prior glue benchmarks, not a measured fleet multiplier.
- VM/sandbox examples use **1 vCPU equivalent and 1 GiB active memory**. They retain a hypothetical 1 GiB unique memory image per identity when comparing logical snapshot bytes. Actual sparse images, shared bases, compression, and disk changes may differ greatly.
- Keep **one current checkpoint per identity**. Logs, receipts, historical images, model context, repositories, browsers, tool sandboxes, replicas, and host overhead are excluded and must be added separately. Full Linux workloads cannot be replaced with this restricted JS guest.

**M-prior — The size premise is conditional.** The existing spike's 1-MiB guest payload occupied roughly **2 MiB raw**, with zstd snapshots around **97 KB for patterned bytes** and **1.15 MB for pseudorandom bytes**. A 50-MiB high-entropy payload produced about **52.53 MB**. Sparse hop deltas were around 19–23 KB in that specific workload; full memory scans and copy-on-write fork sharing remain unqualified. Warm small restores reached the next useful boundary around 0.4 ms in Chrome/Node, excluding network/durable control. [Existing spike](04-spike.md), [earlier limitations](../v8/03-roadblocks.md).

**E/I — Density upper bound, not a capacity claim:** 128 GiB of host RAM at 70% guest occupancy could hold about **45,875 × 2-MiB guests**, versus **89 × 1-GiB allocations**, a **512× guest-memory ratio**. Actual throughput, scheduling, per-instance overhead, GC, safety isolation, and network resources can be binding much sooner. Workers' per-isolate memory limits require sharding; a 128-GiB host is not one giant Cloudflare Worker. A compressed 100-KB checkpoint is not a 100-KB resident interpreter.

**I — The relevant win over a VM is scoped.** If the job needs native libraries, browser RAM, a shell, or a loaded compiler process, those resources still need somewhere to live. Moving the orchestrator's 1-MB heap while retaining its 1-GiB tool sandbox does not reduce fleet memory by 512×. Golem and stateless/actor runtimes also avoid a kernel per logical agent.

### Storage, churn, and burst sensitivity

**E — Pure storage is inexpensive at this scale.** One million 100-KB, 1-MB, or 3-MB current images are 100 GB, 1 TB, or 3 TB: approximately **$1.50, $15, or $45/month** in R2 byte rent. Thirty million writes/reads add about **$145.80 gross** regardless of these small sizes. Retaining 100 full 1-MB versions per identity grows image storage to 100 TB and $1,500/month; a broker journal and deltas can change that. JSON benefits from the same retention/delta techniques.

**E/I — Wake frequency can dominate archive rent.** At one wake/minute for every identity, there would be 43.2 billion wakes/month, with roughly $210,000 of gross R2 write/read operations at one write/read each, before compute. Such a fleet would have only 0.6 seconds active per wake if it still averaged 1% active wall time. Avoid polling; use durable events and coalesce checkpoints. “A million agents” alone is not enough to price anything.

**E — Cross-machine wire floors at a sustained 1 Gbit/s:** 100 KB takes 0.8 ms, 1 MB 8 ms, 3 MB 24 ms, and 1 GiB 8.59 s, excluding RTT, lookup, compression, ownership, and restore. VM providers use sparse/lazy loading and shared images; the 8.59-second full-transfer floor must not be presented as their measured resume latency. E2B's approximately one-second resume is the stronger documented comparison.

**E — A million-agent burst in 60 seconds is 16,667 starts/second.** Moving a unique 1-MB image for each requires about **16.7 GB/s aggregate payload throughput** and one TB overall. Average daily wakes need only about 11.6 MB/s at that image size. Schedulers, ownership storage, object fetches, and model quotas can bind before restore CPU does. Modal's million-sandbox demonstration shows that high creation throughput is already a competitive requirement, not a differentiator supplied automatically by Wasm.

## 4. What fleet operations actually gain from live movement

**I — Use three recovery classes:** explicit application checkpoints; journal replay plus periodic checkpoints; exact-build live images. Evaluate all three before deploying a VM image. Live images are an accelerator for the last two classes, not a replacement for a durable effect ledger.

| Operation | Specific gain from a live program | Strongest substitute / limiting condition |
| --- | --- | --- |
| Packing and rebalancing | **I:** unload a waiting guest; move its execution image to a less-loaded executor; preserve generated closures and pending control flow. | SQLite-backed actors already unload; fresh event placement and normal state loading usually suffice. Physical host placement on Cloudflare is provider-controlled. A user runtime can route capsules among its own logical executors, not command DO host migration. |
| Drain hosts for deploys | **I:** checkpoint at a host-return safepoint, fence the source, move bounded state, continue without rebuilding the prefix. Useful for long tasks that cannot cheaply restart. | Golem replay plus snapshots, durable Code Mode, and VM checkpoints already offer recovery paths. A drain that reaches a cheap application boundary needs no heap. A CPU-bound guest that never yields cannot be transparently drained by this prototype. |
| Move beside a user or data | **I:** continuation and cached derived state follow a changed best execution location, e.g. repeated read-only work inside a data boundary. | Request routing, query pushdown, initial placement, or shipping code + JSON. If tools still proxy to the original broker/database, moving the CPU may save no RTTs. |
| Burst scaling | **I:** a small prepared capsule avoids initializing the same complex runtime state for every branch. | E2B/Modal clones, prepared images, warm pools, ordinary startup snapshots, and cacheable initialization. Moving a guest does not create provider capacity or model tokens. |
| Fork N ways for search / A-B / eval | **I:** duplicate the exact paused JS working state before divergent future inputs; preserve hidden locals without a serializer. | LangGraph forks, journal forks, full-VM memory snapshots, or copying a transcript. Most best-of-N calls need only the prompt and sampling configuration. |
| Hibernate millions | **I:** persist complete guest state while releasing its RAM; no application-specific reconstruction routine. | DO/JSON, Golem unload/replay, E2B pause, and Sprites sleep already eliminate waiting compute. Heap storage may exceed explicit state. |
| Resume across a model/tool version change | **I:** keep past guest state and receipts exact while dispatching future calls through an explicitly selected version. Useful for paired evaluation from a fixed state. | A checkpointed transcript/state can do this too. The heap contains neither model weights nor KV cache; it cannot restore an old model service or incompatible tool contract. |
| Clone a “trained” agent | **I:** distribute a curated initialized working set: generated helper code, derived indexes, parsed policies, proven plans. | Exported configuration/memory, a prepared image, or an ordinary module plus JSON may be smaller and more inspectable. Cloning working state is not copying learned model weights. |

**F — Placement gap worth testing:** Cloudflare's current DO location documentation says existing objects do not change location; only the initial request respects a best-effort location hint, and dynamic relocation is planned. Jurisdictions constrain execution and storage. [DO data location, updated 2026-06-26](https://developers.cloudflare.com/durable-objects/reference/data-location/).

**E/I — Size the drain benefit honestly:** moving 10,000 active guests with 1-MB images moves 10 GB; at an assumed 1 GB/s aggregate effective drain rate, the payload takes 10 seconds. If a strong replay baseline needs 2 seconds of guest CPU per agent, it performs 20,000 CPU-seconds of rebuild work. With 100 cores at ideal utilization that alone is 200 seconds. But if an explicit checkpoint reconstructs in 5 ms, total rebuild work is only 50 CPU-seconds: transport/control can dominate and live images lose. These are scenarios to measure, not observed fleet behavior.

**I — Exact state and upgrades are different promises.** An exact interpreter/module hash can resume old byte state on a new host. Changing the guest program or interpreter can invalidate addresses, bytecode, object layout, and pending logic. Pin the old module to finish an execution or export/import a versioned application schema. A fleet still needs revocation and a policy for images tied to vulnerable old runtimes. Updating a model selector for the *next* request is easy; preserving identical future answers after the model changed is impossible to guarantee.

**I — “Merge results” must mean application data.** Return typed proposals, evidence, scores, or patches to a coordinator. Select a winning continuation or explicitly reduce those outputs. There is no general-purpose merge of divergent heaps, pending promises, third-party writes, or incompatible branch histories. For live A/B traffic, assign distinct users/sessions; copying one support case into two branches that both contact the real customer is not a valid experiment.

## 5. Is forking a running agent valuable in practice?

### Evidence for branching and parallel exploration

| Evidence | Sourced result | What it says about a live heap |
| --- | --- | --- |
| Language Agent Tree Search, ICML 2024 | **F:** LATS combines tree search, feedback, value estimation, and reflection; the published version reports **92.7% HumanEval pass@1 with GPT-4** and WebShop average score **75.9 with GPT-3.5**. [Published paper, 2024-07](https://proceedings.mlr.press/v235/zhou24r.html). | **I:** Search trees of agent states are useful. This is not an experiment comparing heap forks with checkpointed histories; the reported accuracy is not caused by memory-image transport. |
| Tree Search for Language Model Agents | **F:** Best-first environment search improved VisualWebArena success by **39.7% relative**, to **26.4%**, with a GPT-4o agent; WebArena improved **28.0% relative**. Submitted 2024-07-01; inspected revision 2026-02-08. [Authors' paper](https://arxiv.org/abs/2407.01476). | **I:** Branching can improve real interactive tasks. Resetting/cloning the browser or external environment is distinct from copying the agent's JS memory. |
| Anthropic production Research | **F:** Parallel subagents improved its internal research evaluation by **90.2%** over a single Opus 4 agent; multi-agent workloads used about **15× chat tokens** in its data. [Engineering, 2025-06-13](https://www.anthropic.com/research/multi-agent-research-system). | **I:** Parallel tool exploration has a buyer-visible use. Independent context windows, specialization, and extra tokens matter; blindly cloning identical context may reduce the intended separation. |
| Multiple-sample reasoning | **F:** OpenAI's o1 research compared single-sample answers with consensus over **64 samples**, 2024-09-12. [OpenAI research](https://openai.com/index/learning-to-reason-with-llms/). | **I:** Sampling alternatives is useful evidence, but ordinary prompt copying already supports it. This is weaker evidence for a *running-process* fork than environment/state branching. |
| Commercial developer workflow | **F:** Managed Devins run in independent VMs; the coordinator collects their work and resolves conflicts. Cognition explicitly emphasizes narrow tasks and clean contexts. [Cognition, 2026-03-19](https://cognition.com/blog/devin-can-now-manage-devins). | **I:** There is demand for parallel execution and managed lifecycle. It does not prove that children should inherit a full live heap rather than receive a task and repository baseline. |
| Support-agent evaluation | **F:** Decagon documents simulations, workflow versioning, and A/B testing. Sierra describes simulation and repeated load testing at substantial scale. [Decagon, 2026-03-19](https://decagon.ai/blog/introducing-duet), [Sierra, 2025-10-07](https://sierra.ai/blog/load-testing). | **I:** Forking a captured case into alternative policies/models is plausible workflow value. No inspected source measures incremental value of heap capture over their existing simulation state. |

**I — Conclusion from the evidence:** branching agent behavior is valuable; the evidence for a special benefit from **forking the live execution heap** is much narrower. It is strongest when a branch point includes expensive nontrivial derived working state or opaque generated control flow. It is weak for best-of-N from a prompt, independent clean-context subagents, or a graph already checkpointed at the desired node.

### Economics of a fork

**E — Compute-only example:** eight branches share a prefix that takes two seconds of guest computation to rebuild from recorded inputs. Seven extra rebuilds cost 14 CPU-seconds. Seven assumed 10-ms heap restores cost 0.07 CPU-seconds, saving 13.93 seconds of aggregate prefix work. At the Worker CPU tariff that is only about **$0.00028/task**, or **$279 per million such forks**, before checkpoint/transfer charges. Lower tail latency, avoiding restart bugs, or developer effort is likely a stronger purchase reason than those CPU dollars. Prefix model calls are **not** charged again in the journal baseline.

**I — Counterexample:** a LangGraph checkpoint already holds the prefix result in 100 KB. Cloning it is smaller than cloning the modeled 1-MB live image and may be faster. If the native suffix takes substantial CPU, the interpreter slowdown can exceed the prefix saving. Compare full quality-adjusted task cost, not just a fast memory-copy primitive.

**I — Safe speculative execution requires:** inherited past receipts; a new branch identity and future entropy domain; split rather than copied budgets; read-only or isolated effect sinks by default; cancellation; a single authorized commit path. A tool already in flight belongs to the durable broker, not to N copied network sockets. The selected branch must revalidate current policy and mutable external state before committing. [Existing contract analysis](03-contract.md).

**I — Evaluation has two modes:** recorded inputs after the branch give a controlled code/path comparison, while fresh model/tool inputs measure changed behavior. Label them separately. A live heap alone does not supply reproducible model sampling, a resettable website, unchanged customer data, or an oracle that picks the best answer.

## 6. Three candidate products, with proof and kill tests

### A. Preserve generated working state through waits and host drains

**F/I — Pain and current practice:** Cloudflare explicitly documents that local closures and running promises disappear on eviction; its fibers ask developers to choose recovery behavior, while durable Code Mode offers replay. Coding-agent platforms also retain whole cloud environments. The prospective buyer is a runtime/platform team integrating code execution, not a million individual support users. Public sources establish large fleets, but do not quantify how often their generated-state reconstruction is expensive.

**I — Specific value:** park an opaque generated JS program after substantial initialization, release its executor, and resume on a replacement host with its locals intact. Pack and drain these units without maintaining a bespoke serializer for each generated program. **Condition:** completed tool calls are already journaled, and the remaining local rebuild is material.

**E — Quantification / business:** the 10,000-guest drain example above ranges from a meaningful 20,000 CPU-second rebuild to a trivial 50 CPU-seconds depending on the baseline checkpoint. Raw holding costs are too small to support a large premium over JSON. Test a **$2,000–$5,000/month platform integration** only where recovery engineering, p95 disruption, or workload compatibility justifies it. Twenty such buyers imply **$0.48–$1.2 million ARR**; this is a sales hypothesis, not a sourced market count or validated willingness to pay.

**E — 1–2 week proof:** reuse the pinned QuickJS/Wasm spike and TypeScript broker skeleton; run two Node executors and local workerd without a paid deployment. Use 10,000 logical identities, no more than a bounded active batch, generated closures/cyclic structures, 40 recorded tool outcomes, human-approval waits, and forced executor kills. Compare **durable Code Mode-style recorded replay**, explicit JSON at safe boundaries, and full live images. Vary prefix CPU 5 ms / 500 ms / 5 s and snapshot entropy. Measure p50/p95 wake, CPU, RSS, image/history bytes, drain completion, and duplicate effects against a local idempotent sink. This is a narrow prototype, not production qualification of the contract.

**E — Pass / kill:** pass only if a real contributed workload shows **at least 5× lower p95 recovery versus recorded replay**, the explicit-checkpoint implementation cannot match the result with modest changes, and whole-task useful throughput still holds after interpreter overhead. Kill the commercial “cheap fleet” claim if JSON is within 10% on the relevant outcome or snapshot retention/control exceeds the saved cost.

**E — Demo:** a running generated support-ops script pauses for approval; the old executor exits; a new executor resumes its closure and emits one mocked effect. Show the replay and JSON timings beside it and label the local scope.

**E — One tweet:** “This support-ops program kept its closure through a host drain. We compare the live image with recorded replay and explicit checkpoints, including total wake time and bytes. The point is preserving costly working state; idle compute already costs zero on several platforms.”

**I — Expert reply that kills it:** “Your prefix replay is two milliseconds, and my normal checkpoint already stores everything I need. You added an interpreter, an effect broker, version pinning, and a larger state blob.”

### B. Branch exact paused working state for search and paired evaluation

**F/I — Pain and current practice:** the search papers, Anthropic Research, managed Devins, and support simulation products establish demand for exploration/evaluation. Existing solutions use transcript/graph branches or isolated environments. The buyer is an agent evaluation or runtime team whose investigations repeatedly branch *after* expensive state has accumulated.

**I — Specific value:** capture once before a hard decision; run 8–32 alternate future tool/model inputs without redoing the expensive local prefix or teaching a serializer about generated closure state. Collect evidence through a coordinator; promote one continuation. Paired model/tool comparisons can retain identical past inputs while changing only future dispatch. This is not automatic heap merge or a promise of identical new model output.

**E — Quantification / business:** the eight-way prefix example saves about $279/million tasks in Worker CPU, too little for a generic fork surcharge. Value must come from usable search depth within a deadline, reduced evaluation setup, or fewer expensive environment reconstructions. Test **$3,000–$10,000/month** with platforms running high-value evaluations. Ten buyers would be **$0.36–$1.2 million ARR**; again, a pricing experiment. Model tokens and evaluator quality must be included before promising ROI.

**E — 1–2 week proof:** create a bounded read-only search fixture with fixed local API datasets and 200 cases. At a documented await boundary, branch 8 ways with a shared token/tool budget and deterministic branch IDs. Implement **LangGraph-style state branching and journal forks** as primary baselines; use JSON+source as the cheap control. Use actual recorded model/tool traces or deterministic fixtures, clearly labeled, so the benchmark cannot gain by changing the task. Measure correct final answers per wall-time/budget, branch creation through useful work, context bytes, CPU, and avoided prefix work. Include a case where checkpointed JSON should win. Evaluate E2B/Modal feature parity from docs; cloud snapshot benchmarking requires a separate authorized experiment.

**E — Pass / kill:** pass only if the heap supports a useful intra-program branch that the baseline cannot cheaply express, and yields **at least 20% more correct completed investigations within the same end-to-end deadline and external-call budget**, or a verified reduction in integration work without a material performance regression. Kill if all useful branch points are already graph checkpoints or if extra tokens explain the entire gain.

**E — Demo:** one paused reconciliation/research program branches into eight read-only investigations, each continues the same existing helper closure, and the parent chooses a tested proposal. Display the one approved mocked write and seven canceled branches.

**E — One tweet:** “Eight futures from one paused JS investigation: same accumulated working state, different next inputs, one authorized commit. The comparison is graph checkpoints and recorded replay, not eight paid re-runs of the model history.”

**I — Expert reply that kills it:** “Useful search is real, but I can branch the transcript/checkpoint already. You have shown memory cloning, not an improvement in search quality, cost, or integration.”

### C. Relocate an established agent beside changing users or data

**F/I — Pain and current practice:** DO's initial placement can become wrong because existing objects do not currently relocate. Regional customer data and user geography can change, while normal routing, query pushdown, and recreated actors remain strong substitutes. The likely buyer is an enterprise agent platform with repeated, authorized data-local tool work, not an arbitrary marketplace of spare machines.

**I — Specific value:** move a small prepared execution state *after* the best location changes, preserving a difficult-to-rebuild working set. A broker can keep durable identity and external authority at home while executors change. Real locality requires useful computation beside data; tunneling every tool call home removes much of the benefit.

**E — Quantification / business:** assume 20 sequential interactions would each avoid 80 ms of remote RTT: **1.6 seconds** potentially saved. If capture, transfer, restore, and ownership take 50 ms, the optimistic net is 1.55 seconds, before slower execution. Initial correct placement plus JSON can achieve most of this too. Test a **$5,000–$15,000/month integration** only where a measured latency/data-boundary requirement exists; five buyers imply **$0.3–$0.9 million ARR**, not a forecast.

**E — 1–2 week proof:** two trusted local executors emulate region A/B using injected transport latency; workerd hosts the same guest contract. Move after the fifth data-dependent step. Compare **initial/fresh placement + JSON, recorded replay, and query pushdown** with live movement. Keep total source data/queries identical. Measure end-to-end latency, bytes crossing each boundary, reconstruction CPU, and effects. No cloud region or legal-compliance claims from this local test.

**E — Pass / kill:** require a material improvement over **fresh placement + explicit state**, not just over a badly located permanent VM. Reject the angle if all state is easy to copy as data, home-broker RTT remains on every critical operation, or privacy rules do not permit the image to move.

**E — Demo:** a previously prepared agent follows a data-local workload from executor A to B, with source shutdown and a visible ledger; show the fresh-actor/JSON alternative beside it.

**E — One tweet:** “This agent moved after its data location changed and kept its prepared JS working state. We measured against fresh placement plus JSON and query pushdown. The win must come from stateful relocation, not from choosing a slow baseline.”

**I — Expert reply that kills it:** “Route the request to the data and send a 20-KB checkpoint. Your 1-MB heap moved more information and still calls its broker across the ocean.”

### What about cloning a “trained” agent to every user?

**I — Treat this as a weaker subcase of prepared-state fan-out, not a fourth validated product.** The copy can include accumulated working memory, generated helpers, parsed policies, and derived indexes. It does not include remotely hosted model weights or the model's latent understanding. An external vector store, browser, filesystem, and cached inference prefix need separate sharing/copying semantics. Customer-specific context, secrets, approvals, and consumed budgets must not be blindly replicated.

**E — Cheap falsification:** initialize an anonymized policy helper once, then start 1,000 identities from (1) a live image, (2) source + serialized policy/index data, (3) an ordinary prepared runtime image. Measure total bytes, startup to useful work, identity isolation, and steady-state CPU. A template version is immutable; tenant credentials are injected by the broker afterward. At 1 MB/copy, 1,000 full copies are one GB of payload; shared immutable data may make the conventional baseline much smaller.

**I — No independent willingness-to-pay case yet.** A demo and tweet about “1,000 copies of a learned assistant” would invite the decisive reply: “You copied a cache and context, which I can export as data; no model learning was cloned.” Describe prepared execution state precisely, and promote this only if the three-way test finds a hidden-state initialization bottleneck.

## 7. The fleet control plane is part of the product

**I — Minimum operational contract:** stable identity to current-owner mapping; durable inbox/outbox and pending-operation receipts; monotonic owner epochs; module/ABI/image hashes; bounded image sizes and decompression; routing; schedules; per-branch budgets; cancellation; retention and garbage collection; current authorization at resume. Destination ownership must be accepted durably before the source can continue issuing effects. A resumed stale image must not reset a spending limit or reauthorize an old approval. [Contract report](03-contract.md).

**I — A broker per fleet is a bottleneck; a brokerless heap is unsafe.** Partition authority by tenant/agent and serialize only ownership and effect decisions that need it. The established million-object and million-sandbox systems are evidence that control-plane scaling matters at least as much as compact execution state. Reuse DOs or another durable store for identity/receipts rather than trying to encode authority inside copied memory.

**I — Cost and security must use the same boundary.** If untrusted browser execution produces a heap that a trusted privileged host cannot safely accept, the operator may need trusted reconstruction. That can erase reconstruction savings. Begin with compatible trusted executors. Immutable shared modules and encrypted storage help operations, but neither makes foreign-produced memory trustworthy nor restores a revoked tool API.

**I — Prospective business size:** the three candidate revenue sketches overlap and must not be added as independent markets. A bottom-up hypothesis of **50 qualified runtime/platform buyers × $60,000/year = $3 million ARR**, or **200 × $120,000 = $24 million ARR**, is conceivable as infrastructure software. The number of qualified buyers and their budgets are unvalidated. Millions of customer identities do not automatically produce millions of paying seats. Evidence of the broader agent market does not establish demand for this execution primitive.

## Ranked top three

1. **I — Fork exact, opaque working state for bounded read-only search and paired eval.** Strong evidence that branching is useful; conditional evidence that a live image improves it. Best wedge if the branch point lies inside generated code and prefix reconstruction is material. Primary opponent: graph/journal branching, plus E2B/Modal memory clones.
2. **I — Preserve generated programs across approval waits and host drains.** Real lifecycle need and a narrow engineering advantage. It earns a place only when Code Mode-style replay or explicit checkpoints are costly; idle-dollar savings alone fail. Primary opponent: durable Code Mode + DO and Golem snapshots/replay.
3. **I — Relocate prepared state after data/user locality changes.** Current DO location constraints leave a genuine feature gap, but routing and JSON often capture most value. Primary opponent: fresh placement + application state and query pushdown.

**The ONE bet — I:** build a **fork-and-resume adapter for generated JavaScript tool programs**, using the existing pinned interpreter and a brokered effect contract, and make the decisive demonstration a paired graph/journal-versus-heap experiment. Keep persistent identity, ordinary business memory, and large tool environments in their existing systems. Sell a proven reduction in recovery/evaluation friction, not “millions of idle agents for free.”

## Five-line TL;DR

1. **F/I:** Real platforms operate million-object or million-sandbox workloads; public user/conversation counts do not establish million-agent concurrency or a measured 99% idle fraction.
2. **F/I:** DO hibernation, E2B pause, Golem replay, and Sprites sleep already remove idle compute; current snapshot/branching competitors are substantial.
3. **E:** In the explicit 1M/99%-idle model, the small live-image executor is about $530/month in priced components, versus about $216 for JSON; VM-shaped alternatives price much higher but provide more capability.
4. **I:** Live state earns its keep when a small opaque continuation is expensive to reconstruct; tree search evidence supports branching, not a special heap-fork advantage by itself.
5. **I:** The buildable opportunity is brokered, version-pinned fork/resume with a fair checkpoint/replay comparison; a cheap-sleeping fleet business alone is a no-go.

**Verdict — GO-WITH-CHANGES for agent fleets.** Pursue the restricted continuation integration and validate it against strong actor/checkpoint/replay baselines. **NO-GO for a standalone “cheaper idle agents” thesis** without a customer trace showing costly reconstruction or a capability those baselines cannot cheaply provide.
