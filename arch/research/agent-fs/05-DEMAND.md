# Who would adopt an agent filesystem, for what, and how it gets in the door

Research cutoff: **2026-10-31**. Desk research only. No builds, benchmarks, Docker, VMs, installations, customer contact, or changes to existing files. This report is the only new file written.

**Evidence labels:** **V-L** = verified in local documents or raw transcript text; **V-P** = verified that a primary publication documents the feature, incident, or author-reported result; **V-A** = verified first-person anecdote, without independent validation; **I** = inference; **E** = proposed experiment, threshold, or price test. “Verified” does not mean this research reproduced a security exploit, benchmark, customer bill, or product guarantee. Transcript quotations are checked against captions, not audio; timestamps locate minute buckets. Vendor testimonials and repeated speakers are not independent samples.

## Verdict

- **I — There is demand for controlled execution; demand for Sofort's particular kernel is unproven.** The strongest initial prospect is a small agent-platform or multi-tenant SaaS team that owns its execution interface, has repeated short jobs, and can show either an expensive idle fleet or a blocked security requirement. Sell a measurable outcome, not “everything is a file.” Evidence: P01–P05, P09–P12 below.
- **V-L/I — The corpus contains unusually useful counterevidence.** Amp already buys E2B, wants cheaper Orbs, and nevertheless reports little pain to switch. A product that merely undercuts a price calculator faces a satisfied incumbent customer. [Transcript 51, 26:00–27:00](../corpus/transcripts/51-latent-space-orbs-shifting-coding-to-cloud-quinn-slack-amp-code.txt).
- **I — The best wedge is an execution adapter with durable workspace IDs, explicit effects and trustworthy receipts.** Candidate jobs: repeated agent evals, isolated support-bundle inspection, and scoped internal-agent scripts. Broad autonomous application development is a later compatibility test, not the first promise.
- **V-P/I — Active-compute billing is already offered.** Vercel excludes I/O and model-wait time from active CPU charges; Daytona stops CPU/RAM charges after pause/stop. Sofort must beat an optimized lifecycle and the whole invoice, including persistent state. [W01](https://vercel.com/docs/sandbox/pricing), [W03](https://www.daytona.io/docs/en/billing/).
- **V-L/I — Per-command reset does not remove malicious durable files.** A poisoned dependency, build configuration, hook or script can survive in the persistent workspace and execute again. Reset contains process state; write policies, provenance and explicit promotion govern persistent contamination. “No persistence of malicious repo code” is too strong.
- **I — Secret isolation and action authorization matter more than where the tool appears.** A file representing an MCP tool must still enforce tenant, object, recipient, operation and budget scope. An approved GitHub, telemetry or browser action can exfiltrate data without exposing an API key.
- **V-P/I — OpenCode is the cleanest public installation wedge.** Its documented custom-tool naming rules allow replacing built-in `bash`. Claude Code can remove built-ins and use MCP; Codex can disable command-execution tools and add MCP. These are distinct integrations, with other execution/read paths to constrain. [W14](https://opencode.ai/docs/custom-tools/), [W16](https://code.claude.com/docs/en/cli-reference), [W17](https://learn.chatgpt.com/docs/config-file/config-reference).
- **I — Sell SDK/API usage to builders; use an open-source CLI/MCP adapter for discovery.** A self-hosted binary is attractive to security-sensitive teams, but it transfers fleet operations and policy maintenance to them. Individual developers are useful champions and poor evidence of an infrastructure budget.
- **V-P/I — File-based tools, copy-on-write agent workspaces and credential brokers already exist.** Anthropic's MCP code-execution article, Turso AgentFS, Cloudflare Code Mode and NVIDIA OpenShell substantially overlap the story. Differentiation must survive comparison with their actual contracts. [W09](https://www.anthropic.com/research/code-execution-with-mcp), [W23](https://turso.tech/blog/agentfs-overlay), [W10](https://blog.cloudflare.com/code-mode-mcp/), [W24](https://github.com/NVIDIA/OpenShell/blob/main/docs/security/best-practices.mdx).
- **I/E — Demand gate:** obtain one paid, recurring design-partner workflow and a frozen command trace before broad OS work. Continue only if the partner routes real jobs through the adapter, keeps the boundary enabled, and renews at an explicit price. A benchmark can qualify the technology; it cannot substitute for this behavior.

### What the cost evidence does and does not establish

**V-P — Current contracts:** E2B bills running sandbox seconds; its displayed default is 2 vCPU/4 GiB, at $0.000028 + $0.000018 per second, with Pro $150/month before usage. [W02](https://e2b.dev/pricing). Vercel's default-region rates are $0.128/active-vCPU-hour and $0.0212/provisioned-GB-hour, with a one-minute memory minimum and $0.60/million creations. [W01](https://vercel.com/docs/sandbox/pricing). Daytona's stable billing docs distinguish reserved-resource runtime from paused/stopped disk retention; transitional states still charge compute. [W03](https://www.daytona.io/docs/en/billing/). These are tariffs, not measured production bills; regions, discounts, quotas and lifecycle versions matter.

**I — Illustrative arithmetic, not a benchmark:** 10,000 E2B-default runs each lasting 100 ms total $0.046 of CPU/RAM usage if billable duration summed to 1,000 seconds; this ignores lifecycle duration and billing granularity. Holding that default running for 10 hours instead costs $1.656 in usage. Neither model is a fair production forecast without a trace. A minimum charge, image transfer, retained memory, dependency work or remote I/O can erase a microsecond reset advantage. Vercel already removes model-wait CPU charges but still charges provisioned memory.

**I — Ask for three numbers:** sandbox spend as a share of total agent cost; avoidable cost after the incumbent's pause/right-sizing/caching options; and cost per successfully completed user task. Ten thousand tiny commands for cents may be feasible for some workloads, but this research verifies neither Sofort's hosted price nor that the target customer's useful work fits that workload. Buyers with subsidized model subscriptions/BYOK may feel infrastructure cost more sharply; others may be dominated by inference or engineer time.

**I — A qualified first prospect:** a team with an owner for `exec`, actual recurring traffic, a safe-to-share trace and a named budget/control problem; most useful jobs complete in seconds, and many workspaces wait between jobs. They do not require Docker, Chromium, GPU or opaque desktop state for the first workload. Example prospect categories are an independent eval service or a support-analysis SaaS. Arize, Amp, Every and Lark are evidence-bearing examples, **not contacted or committed design partners**.

**E — Price discovery:** offer one builder a $500 paid evaluation credited against future usage, and an explicit $1,000/month capped production offer only if verified monthly value exceeds that price materially. For self-hosting, test an annual support/security-maintenance agreement separately rather than assuming they will pay per command. Adjust or reject these offers based on their invoice and procurement process. A buyer declining paid migration despite a measured gain is stronger information than stars or a waitlist.

## Adoption path

### Enter through the execution boundary the buyer already owns

**I — Product sentence:** “Keep your agent and tools. Give every execution a disposable process environment, keep the workspace by ID, and enforce credentials and external actions through one inspectable policy.” File paths are the discoverability layer; the bought behavior is completion, containment, durable state and operational evidence.

| Surface | Where it gets in the door | Day-one scope and friction | Recommendation |
|---|---|---|---|
| **Open-source CLI plus MCP server** | A developer can try `exec`/`fork`/`diff` with an existing client; useful public demonstration and debugging surface | Signed/downloadable binary, supported-host check, explicit workspace import/export; familiar structured stdout/stderr/exit. MCP tool installation must not be confused with mandatory routing | **First distribution artifact**, exposing the same service contract as SDK. No claim that adding an MCP server intercepts arbitrary built-ins. |
| **TypeScript SDK; Python next when partner needs it** | Platform engineer replaces one execution adapter in a feature branch | Small stable API for workspace lifecycle, execution, cancellation, branches and receipts; stream output; preserve normal error semantics | **First paid integration.** Reuse the partner's model loop, evals and identity provider. Do not require migrating the whole harness. |
| **Hosted API** | SaaS wants isolation without becoming a hypervisor operator | Authenticated tenant/workspace IDs, quotas, accurate metering, cleanup, artifact URLs, predictable regions, service status and support | Best eventual revenue surface; offer only after fleet isolation and operations are qualified. Separate active execution from storage and retained-state charges. |
| **Self-hosted binary / BYOC** | Enterprise cannot send code/data out or already owns idle compute | Document exact CPU architecture, KVM/HVF and host-policy requirements, upgrades, limits and recovery. No kernel patches or live synthesis as an install step | Useful partner option. A downloadable binary is not automatically compatible with ordinary x86 Linux servers or locked-down CI hosts. |
| **Whole-agent remote workstation** | Customer wants a complete Linux development machine, browser, daemon and preview | Requires process persistence and broad tools; competes with bundled cloud agents and mature sandbox providers | Defer. It can be a separate tier, but it breaks the simple “every command forgets process state” contract unless boundaries are explicit. |

[W16](https://code.claude.com/docs/en/cli-reference), [W19](https://code.claude.com/docs/en/sandboxing). | **I:** launcher registers Sofort MCP, removes direct Bash and other relevant executors, and provides workspace-aware file operations. This is a configured replacement, not an automatic transparent Bash hook. Host hooks/provider configuration must be trusted or isolated at the harness level. |
| **Codex** | **V-P:** official config documents `features.shell_tool` to disable command-execution tools and MCP server configuration. [W17](https://learn.chatgpt.com/docs/config-file/config-reference), [W18](https://learn.chatgpt.com/docs/extend/mcp?surface=cli). | **I:** a pinned client profile disables native command execution and exposes Sofort MCP; test tool selection and file-edit consistency. This research did not verify a generic one-setting external replacement for every Codex execution path. OpenAI's self-hosted environment executor is another integration channel, but still needs a compatible resident executor. [W28](https://developers.openai.com/api/docs/guides/agents-api/environments/self-hosted). |
| **Cursor** | **V-P:** native terminal sandbox and run modes are documented; enterprise hooks can block/log shell actions. [W20](https://cursor.com/docs/agent/security/run-modes), [W26](https://cursor.com/blog/enterprise). | **I:** MCP can expose an alternate executor, but no complete native terminal-backend substitution was verified here. Treat reliable routing as an integration test or vendor partnership. Do not promise that a deny hook itself runs a replacement command with identical semantics. |

**I — Essential distinction:** choosing an execution tool is not enforcing it. Acceptance must enumerate hooks, plugin launches, native file tools, browser/network tools, subagents, background tasks and provider configuration. A launch-time host process can read a credential before the first Bash call. Put enforcement below all relevant code or limit the claim explicitly to jobs sent to the adapter. “Use Sofort” in a prompt is not an access control.

### Day-one contract and adoption gates

Every numerical target here is **E**, to negotiate and measure against a partner's current setup. These are not measured Sofort capabilities.

| Requirement | Necessary behavior / proposed acceptance gate |
|---|---|
| **Compatibility** | Advertise a bounded profile, then measure the share of real invocations **and complete tasks** it supports. Target ≥99% of invocations on the agreed trace and ≤2 percentage-point completion loss against baseline, with confidence/variance reported. No unsupported step may escape to the user's host. A niche read-only profile can be viable with a narrower declared promise; it is not a general Bash replacement. |
| **Shell semantics** | Define one isolation unit as one tool invocation, including its pipeline/subprocess tree. Support quoting, pipes, redirection, cwd, env, exit codes, signals and binary output for that unit. Carry cwd/env explicitly between invocations; never silently imply a persistent shell. Resetting each individual pipeline stage would require a different I/O design. |
| **Useful toolchain** | For general coding: actual Bash, Git, core utilities, `rg`, Python and unmodified Node/npm plus the chosen project's native dependencies. For the first narrow profile: list exact supported commands/versions. Count all rejected/unavailable operations. CLIs requiring authentication, package managers and dynamic loaders must be tested as workflows. |
| **Latency** | Suggested same-host adapter overhead p50 ≤10 ms / p99 ≤50 ms for a warm trivial supported job; hosted adapter overhead p50 ≤100 ms / p99 ≤250 ms in-region, separately reporting network and queue time. Keep total task-time regression below 5%. Publicly report cold import, first execution and concurrent saturation too. A microsecond reset timer is not an end-to-end tool-call timer. |
| **Persistent workspace** | Stable IDs; atomic branch creation at a defined filesystem version; correct permissions, links, rename and concurrent-write behavior within scope; explicit export/diff/cleanup. Fork storage only initially, meter changed bytes and garbage collection, and document that external service state is not forked. |
| **Process lifecycle** | Make foreground/background semantics explicit. Finite jobs reset; named service leases, if supported, have separate lifetime, credentials, ports, shutdown and cost. Never fake a surviving dev server or REPL when the VM has been reset. |
| **Security and effects** | No ambient host secrets or network; protect policy and tool metadata against repo writes; scope brokered actions and secrets per tenant/task. Policy decisions fail closed. Deadlines/cancellation are enforced independently of the agent; a cancellation receipt distinguishes effects already committed from actions merely requested. |
| **Ergonomics** | Install to first useful supported job in <10 minutes on a supported host. Stream logs, preserve terminal-independent output, give exact denial reasons and a safe way to request a policy change. Automatic retries cannot grant new authority. Routine permitted tasks require no repeated prompts. |
| **Audit consumer** | Export a host-owned event containing identity/tenant, workspace base and resulting version, command/input references, image/tool hashes, policy revision, decision, provider request/result ID, exit, resources and cancellation/effect outcome. Redact secrets. A real reviewer/SIEM/release gate must use it; a log file alone does not establish compliance. |
| **Economics** | Meter CPU, memory, retained filesystem, changed bytes, broker calls, transfer, queue/idle reserves and support/fallback costs. Publish $/successful task and $/10,000 executions at stated duration/memory/concurrency, plus bill reconciliation and hard limits. Buying capacity and billing active compute are different accounting layers. |

**V-L — Readiness boundary in this repository:** [jitk architecture](../../jitk/docs/ARCHITECTURE.md) documents prepared-start snapshots, short JavaScript bodies/static native programs, and trusted host tool policy. [MCP README](../../jitk/mcp/README.md) exposes `execute` and prepared-profile `run`; the latter accepts arguments and bounded read-only input files, not a host path or shell command. Current host selection includes arm64 macOS/HVF and Linux/KVM paths. This is a useful executor foundation, not evidence of the persistent general coding workstation proposed in the brief.

**V-L/I — Do not turn the scriptc score into an adoption claim:** the [phase-2 corpus report](../../jitk/docs/results/scriptc-corpus-phase2.md) records 3,198/3,947 comparable compiled programs matching Linux (81.0%), or 77.5% of all compiled programs; stock-layout parity is 73.2%. These are selected compiled-program output comparisons on an experimental kernel, not compatibility with 81% of shell commands, npm packages or customer repos. GrowOS's [controller](../../jitk/grow/README.md) is an offline development/qualification process. Ship pinned qualified images; do not have production tenants grow and immediately trust a missing syscall. scriptc should be an opt-in measured fast path after correctness, with compilation cost included.

## Kill risks

1. **I — Compatibility dominates the savings.** A single broken install, native addon, signal, watcher or browser can block a whole task. P01 shows the resulting behavior: users turn isolation off. Lark's purchase shows that full Docker/browser compatibility can be decisive. **Kill condition:** the agreed workflow repeatedly needs a broad Linux fallback or lowered isolation to finish; price/latency advantages disappear once fallback and support are counted. Keep a bounded product or stop the workstation claim.

2. **V-P/I — The bundled OS sandbox is good enough for the buyer's threat model.** Anthropic reported an internal 84% reduction in prompts after shipping its OS sandbox in October 2025. Codex currently documents Seatbelt on macOS and `bwrap` + seccomp by default on Linux; older Landlock descriptions are not the whole current implementation. [W22](https://www.anthropic.com/research/claude-code-sandboxing), [W29](https://learn.chatgpt.com/docs/agent-approvals-security). **Kill condition:** the same policy on a normal OS sandbox or warmed Linux VM satisfies required containment, speed and operating cost. Hardware isolation can be valuable, but only a buyer's explicit threat model makes it necessary.

3. **V-P/I — Incumbents bundle the entire workflow.** Claude Code already documents credential masking/proxy substitution as well as strict sandbox controls [W19](https://code.claude.com/docs/en/sandboxing). OpenAI provides an environment/executor integration and sandbox-provider guides [W28](https://developers.openai.com/api/docs/guides/agents-api/environments/self-hosted). Vercel's GA Sandbox offers snapshots and active-CPU pricing [W30](https://vercel.com/blog/vercel-sandbox-is-now-generally-available); its eve framework has replaceable sandbox adapters [W31](https://vercel.com/blog/introducing-eve). Cloudflare already supplies Code Mode [W10](https://blog.cloudflare.com/code-mode-mcp/). **Kill condition:** the buyer gets the required control, observability and acceptable economics through its current provider before it migrates. Being model-neutral can help distribution but is not a moat by itself.

4. **V-P/I — Other products already separate state, policy and execution.** Turso AgentFS documents CoW workspaces and `agentfs run`; NVIDIA OpenShell documents Landlock/seccomp, deny-default egress and endpoint-bound credential placeholders. [W23](https://turso.tech/blog/agentfs-overlay), [W24](https://github.com/NVIDIA/OpenShell/blob/main/docs/security/best-practices.mdx). Anthropic explicitly described filesystem-discoverable MCP tool APIs in 2025 [W09](https://www.anthropic.com/research/code-execution-with-mcp). **Kill condition:** the residual gain is only a different representation or packaging, without cheaper useful execution, a stronger required boundary or easier integration.

5. **I — Persistent storage defeats a careless security story.** An `npm install` can persist modified `node_modules`, config, scripts or build artifacts. A later pristine VM can execute them again; branches can carry the infection forward. Brokered tool calls and command outputs can also carry sensitive bytes. **Required correction:** treat every workspace version as potentially hostile, protect execution/policy metadata, quarantine shared caches, expose provenance and deliberate promotion. Do not promise absence of persistence or exfiltration solely from reset. VM reset also cannot undo an email, package publish or database write.

6. **I — Branching shifts the bottleneck elsewhere.** CoW avoids an eager full copy; it does not eliminate dirty-page/file storage, package caches, conflicts, test cost, merge review or external database state. P08 supports realistic experiment isolation; P07 supports independent attempts. Neither proves a need to fork live RAM. **Kill condition:** worktrees/snapshots already solve the buyer's branching problem and cheap forks merely accumulate unreviewed attempts. Test filesystem forks before engineering arbitrary process continuations.

7. **I — Few serious buyers need per-command teardown.** A session VM already separates tenants; a buyer may accept repo-controlled process persistence inside that session. Full reset may actively hurt browsers, REPLs, sockets, incremental compilers and dev servers. **Kill condition:** measured attacks and a stated threat model do not require the stronger boundary, while restart/rehydration costs worsen useful-job time. Offer finite-job isolation honestly or choose another segment.

8. **V-P/I — Supply-chain defenses improve above the kernel.** npm v12 docs now block dependency install scripts unless approved. [W27](https://docs.npmjs.com/cli/v12/commands/npm-install-scripts/). This is version/context-specific and does not prevent arbitrary test/config execution or abuse of an allowed operation. **Kill condition:** the target pain is adequately fixed by script approvals, scoped OIDC, cache isolation or trusted configuration, with no recurring need for Sofort.

9. **I — A new kernel adds a new trust and operations burden.** Differential agreement with Linux is valuable but not universal correctness, policy legitimacy or escape resistance. Buyers must trust host parsing, the broker, storage ownership, update/revocation and cancellation too. Enterprise security reviews may take longer than the saved engineering effort. **Kill condition:** independently reviewable deployment, patching and failure evidence cannot fit the buyer's requirements or budget.

10. **I — Receipts and lower compute spend are not automatically budget lines.** P13 shows that evidence may be generated without being consumed; P06 shows cheaper compute without urgency. **Kill condition:** no named person can say which approval, investigation or expense changes because of Sofort, or no budget owner will buy after seeing the result. Avoid using audit regulations as an assumed sales trigger; no legal compliance claim is made here.

## The fastest test of real demand

**I — Test adoption of the boundary before investing in broad Linux compatibility.** One recurring workflow, one owner and one comparison are enough to disprove the initial wedge. This research did not contact anyone, publish an adapter, execute a benchmark or schedule a test.

### A two-week demand experiment, contingent on a usable executor

1. **E — Days 1–2: recruit for evidence, not compliments.** Approach a short list of independent eval/platform or multi-tenant SaaS builders with a specific offer: route one existing short-job workflow through an alternative execution adapter. Require a named budget owner, a redacted recent bill, a representative command/task trace, actual lifecycle settings, and a clearly stated trust boundary. Ask them to rank cost, fewer prompts, branching, audit and isolation; do not let all five be the undifferentiated reason to buy. Request the paid evaluation above. No secrets or real customer data are necessary to establish the first baseline.

2. **E — Days 2–4: freeze a workload and an honest baseline.** Take at least 100 complete tasks with all commands, idle waits, files, external tools, failures and retries represented. Include concurrency and the whole long tail, not just the most frequent command names. Compare against their incumbent with reasonable pause/resume/right-sizing and a bundled OS sandbox where relevant. Define allowed effects, durable files and rejection cases before running candidates. If the partner needs a capability absent from today's jitk, record the gap instead of calling the integration ready.

3. **E — Days 4–7: build only the smallest integration in a later implementation task.** Publish a trusted OpenCode `bash` adapter plus the CLI/MCP contract, or implement the partner's SDK adapter directly if it owns the harness. A full-Linux backend can initially test the API, policy and workspace experience, clearly labeled; that tests product demand, **not** GrowOS economics. Today's prepared native/QuickJS executor can test an actually compatible narrow workload. Do not claim a mock, a Linux fallback or a translated subset proves a drop-in Sofort Bash replacement.

4. **E — Days 7–10: compare useful outcomes and attack boundaries.** Use the same tasks/models/seeds where possible, multiple trials for stochastic tasks, and publish sample sizes/variance. Record task completion, unsupported commands, denials, manual approvals, total time, cold/queue/p99 latency, bytes/CPU/RAM/storage, total invoice estimate and operator effort. Include benign canaries for: issue-induced install; poisoned registry config; a malicious persisted script across two commands; cross-workspace reads; a shared-cache write; allowed-host exfiltration; alternate host executor; timeout during a brokered mutation. Rejection of these finite fixtures is evidence on those cases, not a universal security proof.

5. **E — Days 10–14: force the purchase decision.** Ask the partner to keep real traffic on it for the next month at an agreed price and name who maintains policy. For example, route ≥20% of the qualified workflow for five working days without an engineer supervising every run, then accept the monthly paid offer. Record renewal, reversion, support hours and boundary-disable events. Do not count a founder's agreement to “try it,” stars, benchmark views or a free-credit-only install as paid demand.

### Decide in advance what the result means

| Proposed signal | Continue | Stop or narrow |
|---|---|---|
| **Commercial** | **E:** one independent partner pays for the evaluation and commits real recurring usage at an explicit production price after the result | Nobody supplies a real workflow/budget owner; or a prospect accepts free compute but rejects a paid offer despite the claimed benefit |
| **Behavior** | **E:** sustained routed work; policy remains enabled; buyer uses at least one receipt/fork feature to make an actual decision | Adapter installed but bypassed; every useful task requires host execution, manual rescue or broad grants |
| **Value** | **E:** choose one primary gate: ≥30% reduction in total execution cost per successful task **or** a previously blocked workflow approved because a specific required control now works | Benefit disappears against an optimized baseline; savings are immaterial to their overall budget; required control is available by simpler configuration |
| **Usability** | **E:** completion loss ≤2 percentage points; total-time regression <5%; setup <10 minutes; routine allowed work adds no prompts | Denials and compatibility work cause regular disabling, or support labor costs more than the measured saving |
| **Kernel-specific value** | **E:** after paid workflow demand, matched full-path tests show a material advantage from the Sofort backend itself | Demand exists for policy/workspace tooling but the same product on ordinary Linux/isolate infrastructure is sufficient; keep the useful layer and drop the kernel-led positioning |

**I — Public artifact:** publish the adapter, compatibility manifest, redacted task traces and reproducible benchmark method with cold/warm/concurrent results and failures. Include warmed full-Linux and OS-sandbox comparators with clearly different threat models. Use the [existing competition report](../growos-node/01-COMPETITION.md) to select matched alternatives, especially snapshot restore rather than naive cold boot. A benchmark earns a technical conversation; one partner voluntarily continuing paid use is the fastest credible evidence that the conversation becomes a business.
