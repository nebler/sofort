# GPU kernels and ML compilers: the economics flipped, and the obvious territory is occupied

Research date: **2026-10-28**. Lens: agents writing, tuning, porting, and maintaining accelerator kernels against an executable reference. Read the two flip briefs, the conclusions/bets/rejections of flip 01–06, and the compiler report in moonshots2. This report does not revisit compiling agent workflows or incremental agents.

**Labels:** **F** = sourced fact, including a clearly attributed author/vendor result; **M** = measured here; **I** = inference, proposed design, or judgment; **E** = estimate, scenario, or proposed experimental threshold. **No GPU experiments were performed. All performance results below are F, not M.** Sources were checked on the research date; linked dates identify the publication, revision, or explicitly undated live documentation.

## Finding

**I — The GrowOS pattern applies exceptionally well to kernels, but it is already an industry.** The agent proposes a replacement; a reference operator supplies numerical behavior; compilers, sanitizers, and hardware measurements reject bad candidates. ATLAS, FFTW, OSKI, Halide, and TVM anticipated much of this. What changed is the cost of extending their expert-written generators, schedules, and target-specific implementations. Search, measurement, and semantics were never optional.

**I — No candidate in this investigation clears round one's strongest “verified pain + proven old fix + no existing product” bar.** There are plausible paid projects and valuable research contributions. There is no defensible empty category called “AI kernel engineer,” “cross-vendor kernel agent,” “profile-driven kernel optimizer,” or even “verified AI kernels.” The ONE bet is therefore a conditional customer-specific maintenance experiment, not a recommendation to start a general kernel company.

**I — The best bounded experiment:** take one genuinely unsupported, performance-important operator family on a customer's second accelerator, grow its missing implementation against frozen semantics, and carry it through an unseen upstream change. Sell removal of a deployment blocker and maintained evidence. Use existing kernel agents and DSLs as components and competing baselines. If an ordinary agent with HIPIFY/Helion/Mojo and the customer's tests closes the same gap just as cheaply, stop.

## What fraction of GPU time is recoverable, and what is it worth?

**I — Answer to the literal fleet-wide question: unknown from the evidence located.** I did not find a representative public census of *time-weighted installed kernels* classified by distance from the appropriate hardware roofline across training, prefill, decode, recommenders, vision, and scientific workloads. A count of slow operators, model FLOP utilization, GPU-busy utilization, and an agent benchmark win rate measure different things. None supplies that missing percentage.

**F — The roofline is conditional on the work and memory traffic being modeled.** NVIDIA's guide distinguishes compute and memory ceilings and hierarchical memory roofs. AMD's guide explicitly notes omissions such as latency. [NVIDIA Nsight Compute profiling guide, live](https://docs.nvidia.com/nsight-compute/ProfilingGuide/), [AMD HIP performance guide, live](https://rocm.docs.amd.com/projects/HIP/en/latest/understand/performance_optimization.html). **I:** Low tensor-FLOP utilization can be correct for bandwidth-bound decode; high bandwidth utilization can still hide avoidable materialization. Fusion or a new algorithm changes the byte/FLOP budget, and therefore the roof against which the old implementation was judged.

**F — A useful, narrow empirical anchor:** [Agarwal, Garg, and Singhal, 2026-09-17, §§2 and 6–7](https://arxiv.org/html/2609.21058v1) profiles seven workloads on A100-80GB hardware at bf16. Its operator-family-based “addressable” share is 8.9–16.8% for the tested transformer cases, 41.9–58.2% for DLRM, and 46.1–55.3% for ResNet-50. It projects 1.32–2.49% transformer and 8.63% DLRM-inference runtime reductions using measured win rates/speedups; these are projections, not end-to-end deployment measurements. **I:** The paper labels cuBLAS/FlashAttention/cuDNN families already optimal rather than measuring every invocation's roofline gap. Its fraction is neither a hardware census nor a hard upper bound on what future agents can optimize. It does support selecting workloads before selling kernel savings.

**F/I — Amdahl is visible even in the best showcase.** The AlphaEvolve local-kernel and whole-training figures above differ by an order of magnitude. **E:** If “23% faster” means 1.23× throughput and the 1% saving comes entirely from that replacement, the affected region was approximately `0.01 / (1 − 1/1.23) = 5.35%` of original training time. This is a back-calculation under simplifying assumptions, not an additional Google measurement. The separate 0.7% worldwide-compute AlphaEvolve result concerns datacenter scheduling and must not be booked as kernel savings.

**I — What a customer audit must measure:**

1. Pin model, input/traffic distribution, serving phase, precision policy, library/compiler/driver versions, device, clocks/power state, and graph-capture mode. Report preprocessing, conversions, dispatch, and transfers as well as device execution.
2. For each important operator instance estimate `t_lower = max(required_FLOPs / applicable_compute_rate, required_bytes / applicable_bandwidth)` and compare with isolated measured execution. **E:** call `t_lower / t_measured < 0.5` “far” for an initial audit, with a sensitivity analysis. This threshold is a definition, not a natural constant. Include practical launch/occupancy/latency limits when setting an attainable target.
3. Compute a duration-weighted share over non-overlapping device work; show unknown/unmodeled work explicitly. Separately estimate critical-path application time. Overlapped kernel durations cannot simply be summed into wall-clock savings.
4. Give each candidate three independent fields: semantic/shape coverage, verified attainable acceleration, and exposed critical-path fraction. Re-profile the complete application after replacement. Weight multiple applications by actual device-hours, as opposed to averaging operator speedups.

**E — Economic scenarios, not a TAM or a claim about observed headroom.** For a fixed amount of useful work, a serial exposed fraction `f`, a fraction `q` of that work successfully replaced, and acceleration `s`, runtime saving is `r = f q (1 − 1/s)`. Speedup is `1/(1 − r)`; savings and throughput percentages are not interchangeable. Assume 1,024 continuously occupied GPUs and an all-in marginal-equivalent cost of **$2/GPU-hour** solely for illustration: `1,024 × 8,760 × $2 = $17.94m/year`.

| Exposed, successfully replaced fraction `f q` (E) | Acceleration (E) | Saved time/cost at fixed work (E) | Annual gross equivalent in that scenario (E) |
| --- | --- | --- | --- |
| 10% | 2× | 5% | $0.897m |
| 30% | 2× | 15% | $2.69m |
| 60% | 2× | 30% | $5.38m |
| 5% | 1.1× | 0.455% | $81.5k |

**I — Cash realization is a second gate.** Fixed reserved capacity may yield more throughput rather than a smaller bill. Savings disappear if another bottleneck takes over, the service's SLO cannot use the throughput, compilation disrupts launches, or workspace reduces batch capacity. Deduct search GPU-hours, model calls, expert review, retained variants, retuning, and regression costs. A vendor port has a different value equation: target hardware price/performance and availability minus migration and ongoing support cost. Compare equal quality, latency/SLO, memory capacity, and complete delivered workload, not equal advertised TFLOPs.

**E — Amortization matters for the long tail.** A search costing 10 GPU-hours saves 36,000 GPU-seconds only after enough reuse. At 10 microseconds saved per invocation that is **3.6 billion invocations** before paying back the device-time component; API and engineering expense add to the hurdle. A 10 ms saving needs only 3.6 million invocations. The number of distinct kernels is not the market size.

## The numerical oracle: strong locally, weaker than Linux compatibility in several ways

**I — Reference behavior must become an explicit contract.** Record supported shapes, symbolic ranges, layouts/strides, dtypes, accumulation policy, output types, alias/mutation behavior, NaN/Inf policy, RNG behavior, gradients, determinism requirements, and permitted approximation. Specialization to an advertised shape/dtype is legitimate. Specialization to public random values, hidden evaluator state, or the benchmark invocation count is not. Vendor-library dispatch is legitimate in a production optimizer if allowed, but must not be reported as a newly synthesized kernel.

**I — Distinguish four oracles:**

- **Function, strong within an envelope:** a frozen reference over held-out values, layouts, scalars, shape families, and execution contexts; exact comparisons where semantics demand exactness.
- **Numerics, moderate without extra structure:** floating-point reassociation makes bit equality too strict for many reductions, while loose absolute tolerance can accept an entirely omitted computation. Use operation-specific error budgets, adversarial distributions, and higher precision on bounded cases; there is no universally correct `atol/rtol` pair.
- **Safety, partial from dynamic checks:** memory/race/uninitialized-read/barrier tools, poisoned buffers, and mutation checks; passing them is not a universal proof. Formal checks strengthen only their modeled subset.
- **Performance, noisy and contextual:** trusted timing on the intended device and full workload; speedup on a single microbenchmark is not a correctness oracle or a business result.

**I — Additional attacks the design must anticipate:** changing global precision flags to slow the baseline; computing outside the timed region; using an untimed stream; caching by pointer or recognizing repeated buffers; preprocessing weights without charging changes; validating one path and timing another; writing only a sampled output subset; silently downcasting; dropping masks/clamps/dropout; modifying inputs to corrupt the reference; accepting stale result caches after a shape/driver update. Some can be ordinary bugs rather than intentional deception. The acceptance design should care about behavior, not the model's claimed intent.

### A concrete acceptance boundary

**I — Freeze semantics before the optimization loop.** A human/operator approves the supported envelope and error policy once; the optimization agent can edit implementation artifacts, not reference code, tolerances, hidden generators, or release rules. Test generators derived by a model must themselves be checked against the declared contract. Keep a separate final holdout to limit adaptive overfitting to repeated feedback.

**I — Reduce the executable surface.** Prefer a trusted wrapper/launcher and compiled device artifact with a narrow buffer ABI. Compile untrusted source separately. If arbitrary host/Python is necessary, execute it away from the reference and judge and measure it externally as well. Reference outputs never enter candidate-accessible device allocations or process memory. OS/process isolation does not make a malicious GPU program safe against all driver/device bugs; unsupported execution models remain outside the promise.

**I — Combine differential and structural checks.** Generate random and adversarial cases over the *supported* envelope: large/small magnitudes, cancellation, skew, empty segments, non-power-of-two tails, strides/offsets, masks, scalar boundaries, and repeated/changed inputs at reused addresses. Check output shape/dtype/device, aliases, forbidden mutation, launch errors, writes, and nonfinites. For softmax, compare distribution error and row mass; row mass alone can accept a wrong permutation. Near a true zero, relative error alone also fails: combine a justified absolute budget with scale-aware and operation-specific checks. High precision is an additional reference, not an automatic reason to reject the specified lower-precision semantics.

**I — Check the whole obligation.** Forward agreement does not establish gradients, stochastic semantics, recurrent state, or training stability. Use analytical/autodiff comparisons and finite differences where well-conditioned; specify whether an RNG sequence must match or only a distribution. For a training kernel, run a bounded end-to-end training regression with multiple seeds after local tests. A loss curve is an expensive weak semantic oracle, useful as an additional gate.

**I — Time accepted artifacts independently.** Validate and time the identical artifact hash. A trusted runner records hardware events in a controlled stream and uses complete synchronization or an equivalent dependency boundary for all allowed work; separately time the application path including setup/amortization. Rotate inputs/buffer addresses, test changed weights, and distinguish legitimately cached constants from hidden preprocessing. Randomize baseline/candidate order; control clocks, power, thermals, warmup, L2/cache policy, graph capture, and contention. Re-measure search finalists on fresh trials to reduce winner's-curse selection. Report distributions and uncertainty, not the minimum of thousands of attempts.

**I — Try to break the judge before accepting kernels.** Seed known wrong implementations: zero output, missing tail, dropped clamp/mask, unsafe downcast, input mutation, stale-output cache, incorrect gradient, uninitialized output, fake return type, and untimed work. A test set that accepts them fails the experiment. Sanitizer and formal-verifier modes supplement ordinary tests; unknown/timeouts remain unknown, not passes. Record the exact verifier semantics, instruction coverage, and trusted code. No finite suite establishes universal equivalence.

**F — The formal frontier is substantial but bounded.** [GPUVerify, OOPSLA 2012](https://nchong.github.io/papers/oopsla12.pdf) checks race and barrier-divergence freedom, not arbitrary operator equivalence. Gimlet's prototype reports 16 mathematically proved, two inequivalent, and eight unknown among 26 L1 Triton kernels, and explicitly models numbers as exact reals. Volta's paper likewise uses real-valued symbolic expressions and requires structured control/pointer behavior. [Browne, Lee, Salvi, 2026-10-17](https://arxiv.org/abs/2610.24548) adds agent-assisted floating-point proofs in Lean/Velvet and concurrency proofs in VerCors under stated assumptions; it says floating-point checks do not rely on compiled code. **I:** A source proof, a real-arithmetic proof, a memory-safety proof, and correctness of the shipped binary are distinct claims. Do not collapse them into a badge.

## Ten old ideas, evaluated with the required nine-part template

**I — Historical caution:** these ideas mostly succeeded within bounded domains. The evidence supports recurring expert labor, restricted languages/search spaces, integration burdens, and measurement cost; it does not support a story that autotuning or systolic arrays died and now need resurrection. Each experiment below is a proposed two-week proof, not work performed for this report. Device experiments require an existing sponsor's hardware/access; no rental or accounts were used here.

### 1. PHiPAC and ATLAS: agents extend the generator, while empirical search chooses

1. **Idea / origin — F/I.** Revive portable performance through generated variants and measured selection: [Bilmes et al., PHiPAC, ICS 1997; expanded distribution report October 1998](https://www2.eecs.berkeley.edu/Pubs/TechRpts/1998/5682.html), and [Whaley/Dongarra, ATLAS, SC 1998, project bibliography](https://math-atlas.sourceforge.net/faq.html). **I:** have an agent add missing epilogues/layouts/target primitives, rather than merely choose a tile size.
2. **Why bounded — F/I.** PHiPAC describes parameterized generators plus search scripts; these embody expert structure, not arbitrary program invention. [Whaley/Petitet/Dongarra, 2001](https://impact.ornl.gov/en/publications/automated-empirical-optimizations-of-software-and-the-atlas-proje/) frames ATLAS as keeping numerical software abreast of hardware change. **I:** the enduring cost is expanding that expert representation and maintaining it across architectures; the old method itself worked.
3. **What flipped — F/I.** Helion's 2026 LLM-search result demonstrates cheaper candidate selection; Inductor already provides empirical backend/configuration selection. **I:** stronger agents can also propose new generator branches, but real-device evaluation still costs money and ordinary search often wins inside a good fixed space.
4. **Oracle — I: strong for bounded functional/precision contracts; measured for speed.** Agent writes a generator extension; frozen reference tests and compiler legality checks validate generated instances. It can cheat by narrowing shapes, weakening precision, or preprocessing outside the timer; apply the acceptance boundary above.
5. **Superhuman-model test — I.** Better models expand the search space cheaply and amortize across more ops. Generic tile-prompting becomes commoditized; good libraries, device access, and reusable accepted extensions retain value.
6. **Prior art — F/I.** Inductor, Helion, TVM, NVIDIA agents, and GEAK in the map are direct implementations of large parts of this revival. **I:** reject another general autotuning agent.
7. **Value — I/E.** Kernel-library/platform teams pay for a missing family that repeats. A 2× improvement to 10% of exposed runtime gives 5% savings; charge against that realized gain, not total accelerator spend.
8. **Two-week proof — E.** Choose one unsupported fused epilogue over five shape families on an already available device; let the agent extend an existing generator. Compare equal search budgets with native autotuning and an ordinary coding agent; hold out a dtype/layout change.
9. **Demo / tweet / killer / kill — I/E.** Demo a failure becoming a checked generator branch and reusable dispatch. Tweet: “The agent added the missing implementation family; the compiler and independent measurements selected what ships.” Killer: “Max-autotune already finds that kernel.” Kill if the strongest existing generator matches the result or total setup/maintenance labor fails to fall by at least 50%.

### 2. FFTW's planner and genfft, plus SPIRAL: grow an algebraic codelet vocabulary

1. **Idea / origin — F/I.** [Frigo, genfft, PLDI May 1999](https://www.fftw.org/pldi99.pdf), [Frigo/Johnson, FFTW3, February 2005](https://fftw.org/fftw-paper-ieee.pdf), and [Püschel et al., SPIRAL, February 2005](https://www.spiral.net/doc/papers/IEEE_2005.pdf) separate mathematical decomposition, code generation, and empirical choice. **I:** agents add new codelets, algebraic decompositions, or target lowerings under independent checks.
2. **Why bounded — F/I.** FFTW already generated codelets because hand-writing and repeatedly rewriting them was impractical. Its planner measures compositions; `genfft` generates the leaves—these are distinct mechanisms. SPIRAL's explicit formula/rule/template vocabulary makes domain expertise reusable. **I:** neither died; extensions outside the encoded domain still require expertise.
3. **What flipped — F/I.** The labor shift is real but occupied even here: [Zhang et al., “Towards Semantics Lifting for Scientific Computing: A Case Study on FFT,” 2025-01-15](https://arxiv.org/abs/2501.09201) demonstrates lifting GPT-generated FFT code into SPIRAL's high-level specifications with symbolic/theorem-proving machinery. **I:** a model can explore unfamiliar leaves, but algebraic representation remains valuable for checking and reuse.
4. **Oracle — I: strong algebraically, moderate numerically.** Agent proposes a leaf or rewrite; exact symbolic checks where supported, a direct high-precision transform on small sizes, and full-size numerical tests judge it. It can get sign/normalization/stride conventions wrong, overfit real-only inputs, or substitute an unstable formula.
5. **Superhuman-model test — I.** Better proposals help; a deterministic planner remains cheap at deployment. If a model directly emits every needed fast transform, the custom generator loses differentiation, but accepted semantic facts can still be reused.
6. **Prior art — F/I.** FFTW/SPIRAL and the cited 2025 lifting work occupy the core; cuFFT/rocFFT are formidable practical baselines. **I:** no evidence found for a broad unsupplied FFT market; a private fused transform is the only plausible entrance.
7. **Value — I/E.** Scientific/signal-processing teams pay for a measured fused pipeline or unusual size/layout, not “AI FFT.” A useful 20% kernel win on a 5% region saves only 0.83% at 1.2× acceleration.
8. **Two-week proof — E.** One existing customer's transform-plus-windowing pipeline, three nontrivial sizes, independent sign/normalization/complex-data tests; agent generates one backend extension. Count generation, planning, temporary buffers, and repeated execution; compare the full pipeline with tuned vendor composition.
9. **Demo / tweet / killer / kill — I/E.** Tweet: “A new transform codelet joins the planner only after symbolic and numerical checks.” Killer: “You rediscovered an existing library plan and excluded planning/copies.” Kill below 10% full-pipeline improvement or if no actual unsupported workload is available.

### 3. OSKI: specialize irregular operators to structure, not just shape

1. **Idea / origin — F/I.** [Vuduc/Demmel/Yelick, OSKI, June 2005](https://bebop.cs.berkeley.edu/pubs/jop2005-SciDAC-OSKI.pdf) adapts sparse formats and transformations to the user's matrix and machine while exposing tuning cost. **I:** agents implement missing segmented, sparse, embedding, graph, and ragged kernels with guarded structural assumptions.
2. **Why bounded — F/I.** OSKI explains that the matrix may be unknown until runtime and tuning may be nontrivial. **I:** irregularity, format conversion, distribution-dependent behavior, and amortization prevent one universally best kernel. This is not a claim that OSKI died from one cause.
3. **What flipped — F/I.** Meta's production account explicitly identifies custom ranking operators as a scaling problem across model × hardware combinations. **I:** agents can absorb variant-writing and diagnosis; sparse IDs and degree distributions still control actual performance and numerical accumulation.
4. **Oracle — I: strong for supported integer/indexing semantics; moderate for reductions.** Agent selects or creates layouts and kernels; reference output, index/duplicate semantics, backward tests, and end-to-end performance decide. Cheat paths include assuming sorted/unique indices, omitting empty segments, and measuring lookup after excluding a per-batch sort/repack.
5. **Superhuman-model test — I.** Better models make more structures affordable, but input-dependent irregularity survives. A model cannot turn random memory accesses into a dense MXU workload without paying the required transformation costs.
6. **Prior art — F/I.** KernelEvolve and GEAK already cover important territory; [SparseTIR, 2022](https://arxiv.org/abs/2207.04606) supplies composable sparse-compilation abstractions. **I:** target an uncatered private op/structure, not embeddings in general.
7. **Value — I/E.** Recommender/graph owners pay for critical-path throughput and usable hardware choices. At `f = 0.4`, `s = 1.5`, and full successful coverage, saving is 13.3%; this is a scenario, not the paper's or Meta's measured result.
8. **Two-week proof — E.** Freeze one actual segmented gather/reduce or sparse gating op, including duplicates/unsorted IDs and a backward contract. Hold out degree/skew and shape families. Compare vendor sparse primitives, compilation, a coding agent, and the structured loop; time repacking and gradients.
9. **Demo / tweet / killer / kill — I/E.** Tweet: “The same private ragged op works on the second accelerator, including the ugly IDs and the backward pass.” Killer: “Your training distribution hid the slow/incorrect skew and the repack cost.” Kill if existing operators remove the blocker, if any accepted implementation corrupts holdout results, or if <5% full-workload improvement remains after costs.

### 4. Halide: let agents search schedules inside a semantic boundary

1. **Idea / origin — F/I.** [Ragan-Kelley et al., SIGGRAPH July 2012](https://people.csail.mit.edu/jrk/halide12/) separates algorithm from schedule; the [PLDI June 2013 work](https://people.csail.mit.edu/jrk/halide-pldi13.pdf) develops the language/compiler. **I:** an agent writes schedules or supported primitive extensions while a compiler preserves a declared computation.
2. **Why bounded — F.** [Mullapudi et al., July 2016](https://graphics.cs.cmu.edu/projects/halidesched/) describes schedule expertise as a burden; [Adams et al., July 2019](https://halide-lang.org/papers/autoscheduler2019.html) expands the space and uses learned costs/tree search, reporting gains over the earlier scheduler and expert schedules. Automatic scheduling already existed.
3. **What flipped — F/I.** Helion provides a contemporary high-level kernel language and LLM-guided tuning; its TPU backend is documented with Google collaboration [2026-07-23](https://pytorch.org/blog/helion-on-tpu-towards-hardware-heterogeneous-kernel-authoring/). **I:** cheap agents help create algorithms/extensions; the semantic split reduces the authority those agents need over correctness.
4. **Oracle — I: strong for legal schedules under compiler semantics, still needs target/numerical checks.** Agent changes scheduling decisions; legality, compilation, hidden reference tests, and hardware runs check them. Cheating includes modifying the algorithm instead, treating reduction reassociation as exact equivalence, and excluding layout conversion.
5. **Superhuman-model test — I.** Stronger models improve schedule/extension discovery; legal-by-construction representations retain value. If the DSL cannot express the best algorithm, schedule search alone hits a ceiling.
6. **Prior art — F/I.** Halide autoschedulers, Helion, Inductor, TVM, and agent-guided DSL search occupy it. **I:** build an upstream backend/primitive contribution; reject a new general Halide-plus-chat product.
7. **Value — I/E.** DSL/framework maintainers pay through development productivity and deployed performance. At least half the engineering time saved is a more plausible pilot metric than beating a library on a hand-picked shape.
8. **Two-week proof — E.** Start from a kernel whose existing DSL lowering fails on an unsupported layout or op; add one lowering with an agent, retain a frozen algorithm, and hold out five shape/layout families. Compare an expert using the existing autoscheduler and a normal coding agent.
9. **Demo / tweet / killer / kill — I/E.** Tweet: “One algorithm, independently checked schedules on two targets, and a new primitive carried through an update.” Killer: “This is already a Helion backend patch.” Kill a standalone product immediately if that is the whole differentiation; keep a useful upstream patch if it demonstrably reduces future maintenance.

### 5. Polyhedral compilation: agents make source analyzable; dependence analysis makes schedules legal

1. **Idea / origin — F/I.** [Bondhugula et al., PLuTo, April/June 2008](https://github.com/bondhugula/pluto), [Grosser et al., Polly, 2011](https://polly.llvm.org/publications/grosser-impact-2011.pdf), and [Vasilache et al., Tensor Comprehensions, 2018-02-13](https://arxiv.org/abs/1802.04730) automate affine transformations, parallelism, locality, fusion, and size specialization. **I:** agents extract/repair a suitable representation or implement missing target mappings.
2. **Why bounded — F/I.** Polly's paper explicitly identifies syntactic extraction restrictions and poor integration with internal/target-specific optimizers. TC combined a tensor language, polyhedral JIT, and autotuning. **I:** data-dependent indexing, aliasing, and hardware pipelines are not made affine merely by asking a better model.
3. **What flipped — I, anchored in F prior art.** Current agents can rewrite wrappers, expose dependencies, and propose guards. The revived component is expert extraction/backend labor, not the dependence mathematics. The existing TC system already supplied the reference tensor→specialized CUDA ambition.
4. **Oracle — I: strong within a valid extracted model; weak outside it.** Agent proposes a lift plus entry guards; source/reference differential tests check the lift, dependence analysis validates schedules. It can cheat by asserting no aliasing, deleting a data-dependent branch, or specializing a dynamic index to fixture values. Reject unsupported regions rather than invent legality.
5. **Superhuman-model test — I.** Better lifting helps more code enter the checked subset. If models write excellent raw kernels, generic source extraction becomes less commercially valuable; checking dependencies remains useful research infrastructure.
6. **Prior art — F/I.** PLuTo/Polly remain explicit infrastructure, [TC's implementation](https://github.com/facebookresearch/TensorComprehensions) exists, and contemporary tensor compilers use structured IRs. **I:** no unoccupied revival found for a universal affine kernel compiler.
7. **Value — I/E.** A compiler team may pay for a recurrent unsupported pattern; a one-off 5% microbenchmark improvement rarely funds a new compiler frontend/backend stack.
8. **Two-week proof — E.** Three regular private kernels rejected by current extraction; agent produces guarded analyzable variants, with adversarial alias/stride tests. Compare with direct compilation/DSL rewrite and measure total human setup plus full-workload performance.
9. **Demo / tweet / killer / kill — I/E.** Tweet: “The model exposes the loop; dependence analysis, not the model, authorizes parallelization.” Killer: “The guards silently excluded real production cases.” Kill if guarded coverage is too low, checks cannot validate lifting, or a direct ordinary-agent rewrite costs less.

### 6. STOKE: search instruction sequences under an independent checker

1. **Idea / origin — F/I.** [Schkufza/Sharma/Aiken, STOKE, ASPLOS March 2013](https://theory.stanford.edu/~aiken/publications/papers/asplos13.pdf) treats loop-free x86 superoptimization as stochastic search with correctness/performance costs. **I:** use an LLM as a high-quality proposal operator for PTX/assembly snippets or carefully bounded kernels.
2. **Why bounded — F/I.** The original task was loop-free binary optimization and explicitly sacrifices completeness. **I:** scaling to thousands of GPU threads, asynchronous instructions, floating-point behavior, and real performance adds substantial semantics and measurement work; this is not solved by replacing MCMC with prose reasoning.
3. **What flipped — F/I.** AlphaEvolve's selected low-level win and Costa et al.'s direct PTX lowering demonstrate productive proposals. **I:** models can jump beyond fixed rewrites, while old validation remains the acceptance authority.
4. **Oracle — I: strong for restricted exact regions; moderate/partial for whole floating-point GPU kernels.** Agent proposes an instruction sequence; symbolic equivalence, concurrency checks, numerical tests, and hardware timing decide. It can exploit missing instruction semantics, real-vs-float differences, unsafe synchronizations, or a verifier extension that assumes what it needs to prove.
5. **Superhuman-model test — I.** Better search increases checker demand, especially as proposals use newer instructions. Once models saturate performance, a proprietary proposal scaffold loses value; maintained trusted semantics are harder to replace.
6. **Prior art — F/I.** Standard Kernel's PTX work, AlphaEvolve, AI as a Compiler, and Volta directly occupy the revival. **I:** another general GPU superoptimizer is rejected; a verified unsupported instruction model might be a good research contribution.
7. **Value — I/E.** At a hyperscaler, sub-percent application savings can pay; at small deployment scale, search and semantic engineering can exceed the benefit. Use the Amdahl/cost calculations above.
8. **Two-week proof — E.** A small integer packing/indexing region with executable semantics; agent proposes replacements, a solver checks all bounded inputs, and a trusted runner benchmarks them inside a real kernel. Extend to one floating-point case only with an explicit approximation contract.
9. **Demo / tweet / killer / kill — I/E.** Tweet: “The agent's clever assembly was rejected by one counterexample; the accepted version is faster in the actual kernel.” Killer: “You verified real arithmetic or a sketch, not the executed instruction sequence.” Kill any unsupported proof claim; kill the product if integration erases the win or existing compiler passes capture it.

### 7. TVM, Ansor, MetaSchedule: agents grow reusable search rules

1. **Idea / origin — F/I.** [Chen et al., TVM, OSDI October 2018](https://www.usenix.org/conference/osdi18/presentation/chen), [Zheng et al., Ansor, OSDI November 2020](https://www.usenix.org/conference/osdi20/presentation/zheng), and [Shao et al., MetaSchedule, NeurIPS 2022](https://proceedings.neurips.cc/paper_files/paper/2022/hash/e894eafae43e68b4c8dfdacf742bcbf3-Abstract-Conference.html) automate tensor-program exploration. **I:** agents propose reusable schedule rules/intrinsics/cost features, accepted through independent semantics and held-out workloads.
2. **Why bounded — F.** Ansor explicitly addresses restricted search spaces and ineffective exploration. MetaSchedule explicitly targets the difficulty of letting experts expand those spaces, using a probabilistic schedule language. These papers already identify the proposed pain and contain solutions; “autotuning cannot generate its space” is too broad.
3. **What flipped — I, with F anchors in the prior-art map.** Agents can author modular search-space extensions instead of a human implementing every new hardware idiom. Contemporary open systems already learn/propose candidates; compare extension maintenance and reuse, not only first-run tuning latency.
4. **Oracle — I: strong for legal transformations, partial for new intrinsic/lowering implementations.** Compiler legality plus independent reference tests gate rules; hardware and held-out graphs judge cost. Cheating includes improving the training operator set while breaking another shape or biasing the cost model toward uncharged conversion work.
5. **Superhuman-model test — I.** A better model helps manufacture rules, but may obsolete elaborate hand-shaped proposal heuristics. A trusted compiler, measurements, and accepted reusable primitives can remain useful even with near-perfect proposals.
6. **Prior art — F/I.** TVM's lineage, Helion's hybrid search, and GEAK/AKA-style libraries of optimization knowledge leave no vacant generic agentic-autotuner category. **I:** work with an existing compiler on an actual missing target feature.
7. **Value — I/E.** Framework/chip vendors pay for faster bring-up and fewer regressions across many operators; amortization over an installed base matters more than a lone benchmark. Proposed pilot criterion: at least three unseen op/shape families benefit from the same extension.
8. **Two-week proof — E.** One missing intrinsic or schedule idiom, an existing compiler test corpus, agent-authored rule, held-out operators, and ordinary autotuning as equal-budget baseline. Count compile/search overhead, source complexity, and expert interventions.
9. **Demo / tweet / killer / kill — I/E.** Tweet: “One independently checked scheduling rule improves kernels the agent never saw.” Killer: “Your rule is a template keyed to the benchmark names.” Kill if gains fail on held-out families, if legality needs special pleading, or if an existing rule covers it.

### 8. Kung/Leiserson systolic arrays: map computation to existing accelerators, not a new chip per prompt

1. **Idea / origin — F/I.** [Kung/Leiserson, Systolic Arrays for VLSI, April 1978, revised December 1978](https://www.eecs.harvard.edu/htk/static/files/1978-cmu-cs-report-kung-leiserson.pdf) exploits regular local dataflow/reuse. **I:** agents generate tiling, pipelining, layout, and DMA schedules for existing matrix engines and their surrounding vector/scalar work.
2. **Why bounded — F/I.** Systolic arrays did not die: contemporary TPU kernels expose matrix units and explicit memory/pipeline concerns. [JAX Pallas TPU details, live](https://docs.jax.dev/en/latest/pallas/tpu/details.html) warns that unnatural patterns may require slow emulation and describes vector/scalar execution and asynchronous DMA/matrix work. **I:** unsupported or irregular mappings, not the absence of dense compute, are the software opportunity.
3. **What flipped — F/I.** The Helion/Google TPU backend already generates Pallas schedules, with a selected attention result of 838 TFLOPs and about 79% of one tensor core's peak on TPU v7 in its July 2026 post. **I:** agents reduce explicit pipeline-authoring labor; they cannot remove device memory capacity or data dependencies.
4. **Oracle — I: strong functional envelope; moderate performance portability.** Agent writes Pallas/layout/DMA schedules; reference JAX/PyTorch semantics, interpreter checks, device tests, and pipeline/resource checks decide. It can cheat by excluding transposes/DMA, using the wrong accumulation precision, or checking interpreter execution while timing a different lowered artifact.
5. **Superhuman-model test — I.** Better models make new device mappings easier, increasing accelerator substitutability. They do not make unsupported physical dataflow free. Building bespoke silicon remains capital- and hardware-constrained.
6. **Prior art — F/I.** Google/Pallas, AlphaEvolve, Helion, and target-specific compiler teams already work here. **I:** choose a missing operator, not “bring TPUs to PyTorch” as if no integration exists.
7. **Value — I/E.** Hardware owners and model teams pay when an actual model can use available capacity at an acceptable cost/SLO. An isolated TFLOP result does not determine cross-device economics.
8. **Two-week proof — E.** On already accessible TPU hardware, port one useful custom masked/block-sparse op with a frozen envelope and compiled JAX baseline; hold out a mask/shape regime, measure layout conversion and forward/backward memory.
9. **Demo / tweet / killer / kill — I/E.** Tweet: “A missing operator becomes a checked TPU implementation with the data movement included.” Killer: “XLA/Helion already lowers it, or your sparse workload was secretly dense.” Kill if no real blocker remains or complete target execution is no better than the existing supported stack.

### 9. TASO and Tensat: let models propose rules, not declare equalities

1. **Idea / origin — F/I.** [Jia et al., TASO, SOSP October 2019](https://www.cl.cam.ac.uk/~ey204/teaching/ACS/R244_2024_2025/papers/jia_SOSP_2019.pdf) generates/checks graph substitutions; [Yang et al., Tensat, MLSys 2021](https://proceedings.mlsys.org/paper_files/paper/2021/file/cc427d934a7f6c0663e5923f49eba531-Paper.pdf) uses equality saturation to reduce rewrite-order sensitivity. **I:** agents propose missing tensor rewrites or search-control strategies; checked semantics authorize them.
2. **Why bounded — F/I.** TASO reports exponential substitution-generation limits beyond its bounded graph sizes; Tensat addresses sequential search/phase ordering. **I:** e-graph explosion, trustworthy rules, realistic extraction cost, shared tensors, and finite-precision semantics remain separate costs.
3. **What flipped — F/I.** [LGuess, 2025-11-01](https://arxiv.org/abs/2511.00403) and [EggMind, 2026-04-19](https://arxiv.org/abs/2604.17364) already introduce LLM-guided equality-saturation machinery; the latter transfers strategies to an XLA-based tensor compiler. **I:** cheap domain-specific strategy writing is a real flip with direct competitors.
4. **Oracle — I: strong only for independently valid rules under the chosen semantics.** Agent suggests a rewrite/strategy; a proof/solver or trusted rule derivation checks equality, and measurements check extraction. It can cheat with real-number reassociation under IEEE arithmetic, lose a mask, assume no aliasing, or optimize a cost proxy rather than runtime. A statement in an e-graph is not proof its introducing rewrite was valid.
5. **Superhuman-model test — I.** Better models help propose larger algebraic moves and tame search, but can also replace handcrafted strategies. The semantics and extraction problem remain useful; a thin agent wrapper does not.
6. **Prior art — F.** [EqiForge, 2026-09-11](https://arxiv.org/abs/2609.12330) unifies tensor algebra and tiled execution in an equality-saturation optimizer, reporting fused attention-like implementations and improvements over selected strong baselines. Combined with LGuess/EggMind, this occupies both agent guidance and cross-level tensor search.
7. **Value — I/E.** Compiler teams pay for reliable extensions; graph-level elimination of materialization may beat optimizing a kernel already near its current roofline. Demand at least a 5% full-block improvement over a tuned compiler in a pilot.
8. **Two-week proof — E.** A small typed tensor IR or existing e-graph, three private operator blocks, agent-proposed rules with shape/precision side conditions, and unseen graph compositions. Exclude arbitrary user code; inspect extraction for recomputation and peak-memory costs.
9. **Demo / tweet / killer / kill — I/E.** Tweet: “The model proposes the fusion; a semantic checker rejects the attractive but invalid rewrite.” Killer: “Your equalities are over reals and your deployment is low precision.” Kill if accepted rules violate the deployed contract, extraction costs explode, or existing compiler fusion matches the whole-block result.

### 10. Maintained cross-vendor kernel compatibility: grow the missing behavior, not the syntax translation

1. **Idea / origin — F/I.** PHiPAC/ATLAS's 1990s portable-performance program is the old idea; [McKeeman's differential testing, 1998](https://www.cs.tufts.edu/comp/150FP/archive/bill-mckeeman/DifferentailTesting.pdf) supplies original-versus-replacement checking. Modern [HIPIFY documentation, live](https://rocmdocs.amd.com/projects/HIPIFY/en/latest/index.html) explicitly leaves unsupported libraries and performance rework to developers. **I:** an agent closes those remaining semantic/performance gaps for one named workload and maintains them through change.
2. **Why bounded — F/I.** HIPIFY documents that syntactic/API translation is incomplete and NVIDIA-tuned code can require AMD-specific rework. [HipKittens, November 2025; live implementation](https://github.com/HazyResearch/HipKittens) identifies differences in memory access, scheduling, and chiplet placement despite reusable tile interfaces. **I:** the labor is real; it includes multiple live toolchains, not simply converting `cuda` to `hip`.
3. **What flipped — F/I.** KernelEvolve and Modular explicitly automate heterogeneous implementations; Pallas, MLX, and high-level DSLs provide executable targets. **I:** agent labor makes the small private operator × target × version matrix less prohibitive, but data/device access and enough recurring volume must already exist.
4. **Oracle — I: strong within a frozen behavioral envelope; incomplete outside it.** Agent chooses a target-appropriate implementation instead of line-by-line imitation. Reference values and gradients, edge cases, alias/mutation/stream contracts, full-application tests, and per-target timings check it. It can cheat by narrowing the envelope, silently dispatching to CPU/source hardware, dropping backward support, or making the target's baseline artificially weak.
5. **Superhuman-model test — I.** Better models make ports cheap for everyone. Remaining value is recurring integration and acceptance of private operator changes, not a moat in translation prompts. If a standard model plus existing toolchains solves that too, the product disappears; the customer still benefits.
6. **Prior art — F/I.** HIPIFY, Helion, Triton, Mojo/MAX, Meta, AMD, and specialist startups are formidable. [Triton's live compatibility list](https://github.com/triton-lang/triton) supports NVIDIA/AMD; [Pallas](https://docs.jax.dev/en/latest/pallas/quickstart.html) addresses GPU/TPU; [MLX custom Metal kernels](https://ml-explore.github.io/mlx/build/html/dev/custom_metal_kernels.html) supplies an Apple target. **I:** these are different execution models, not universally interchangeable backends. The gap must be demonstrated on the customer's exact op; its existence cannot be inferred from “CUDA moat.”
7. **Value — I/E.** A model team or second-vendor hardware supplier pays to unblock a deployment and maintain it. **E:** offer a bounded $10k–25k follow-on pilot only after showing which real engineer-month, availability constraint, or recurring compute expense it replaces; this is a price hypothesis, not observed willingness to pay.
8. **Two-week proof — E.** One family, source NVIDIA and target AMD on already available hardware; ten actual workload cases, whole shape/structure families held out, an untouched upstream revision revealed in week two, and a full forward/backward deployment test. Build on existing agent/DSL tools, and compare with HIPIFY plus a normal coding agent under equal budgets. Apple/TPU become subsequent separate experiments, not promised day-14 deliverables.
9. **Demo / tweet / killer / kill — I/E.** Demo a real blocked workload, one adversarial rejection, a successful target run, then an unseen update repaired without editing the oracle. Tweet: “This model's missing second-vendor op now survives an upstream change, with independently replayed semantics and complete-workload timing.” Killer: “HIPIFY plus my existing agent and tests already does that; your remaining problem is drivers, deployment, and support.” Kill if no actual blocker, no repeated changes, unsafe holdout behavior, or <50% reduction in expert time including harness construction. **Disposition: conditional ONE bet; no claim of a vacant general market.**

## Porting details that determine whether idea 10 is real

**F/I — The target is an execution strategy, not just a language.** [ThunderKittens' live repository](https://github.com/HazyResearch/ThunderKittens) describes NVIDIA-focused tile primitives, TMA/WGMMA/tcgen05 use, and points to HipKittens and Apple-oriented ThunderMittens. [JAX TPU documentation](https://docs.jax.dev/en/latest/pallas/tpu/details.html) exposes memory spaces and explicit asynchronous operations; MLX exposes Metal kernel generation and custom VJPs. **I:** an accepted port may preserve the mathematical algorithm and replace almost every scheduling decision.

| Port (I design issues, informed by the linked platform documentation) | Agent's useful work | What the reference does not establish |
| --- | --- | --- |
| CUDA/CUTLASS/CuTe/TK → HIP/CK/HipKittens/FlyDSL/Triton | Replace inline PTX and vendor primitives; choose wave/tile layouts, LDS staging, synchronization, matrix instructions, and chiplet-aware launch policies. | Correctness on NVIDIA does not validate AMD memory behavior, runtime resource limits, or target performance. |
| CUDA/Triton → TPU Pallas/XLA | Reformulate data movement and layouts around vector/matrix units and explicit VMEM/DMA/pipelining; choose target-appropriate decompositions. | A source-kernel schedule and an interpreter run do not establish the lowered device pipeline or cost. |
| CUDA/Triton → Apple Metal/MLX or Mojo | Rework threadgroups/SIMD-group primitives, memory use, launch integration, and custom gradients. | Equal output on a Mac does not prove a competitive device path; unified-memory/preprocessing costs and available arithmetic formats matter. |
| Same kernel → new GPU/compiler/driver revision | Recompile, re-profile, repair invalid assumptions, and invalidate cached dispatch evidence. | An old artifact's evidence cannot automatically certify a changed binary or new shape envelope. |

**I — The maintenance artifact should be small and explicit:** frozen reference/version; operator contract and preconditions; implementation/compiler/device identity; accepted shape/structure envelope; numerical and safety evidence; complete benchmark recipe; dispatch guard and fallback; known exclusions. A fallback preserves availability only if it is a supported implementation on the deployed hardware and is reported honestly. It cannot reverse an incorrect in-place update after execution.

**I — Independent acceptance is essential but not a separate empty market.** Standard Kernel, robust-kbench, KernelBench-Verified, SOL-ExecBench, Gimlet, Volta, and the August contract-verifier study already cover large pieces. The residual hypothesis is that a customer will pay for an independently replayable *maintenance outcome* across a private compatibility matrix. No customer interviews or purchasing evidence were obtained here. A general verifier company would require an additional capability/distribution advantage, not just this failure taxonomy.

## The ONE bet

**I — Build a maintained, independently accepted port for one actual customer's missing operator family, starting CUDA→AMD, with a frozen original as oracle and an unseen upstream revision as the decisive test.** Prefer a private ragged/sparse/fused family with material runtime or deployment importance. Use an existing kernel agent and target DSL. The deliverable is a supported compatibility/performance envelope and a measured reduction in expert maintenance work.

**E — One engineer, two-week go/no-go:**

- **Days 1–2:** find one sponsor with a reproducible blocked deployment, source/target hardware already available, and a reference forward/backward op. Profile the full workload; verify that an existing library, compiler option, HIPIFY, Helion, Mojo, or ordinary agent does not already remove the blocker. If there is no real blocker or no device access, stop; a synthetic softmax leaderboard is a different experiment.
- **Days 3–4:** freeze contract, inputs/weight handling, precision, performance recipe, and three holdouts: whole shape/structure families, adversarial numerical cases, and a later upstream semantic change. Establish trusted evaluator authority and deliberately wrong candidate mutants. Capture source and target baselines, including conversions and graph/runtime integration.
- **Days 5–9:** compare budget-matched tracks: existing tools plus normal coding agent versus structured fault→propose→independent-check→accept. Charge harness setup, expert review, model calls, device time, and failure diagnosis. Keep each track's solutions from contaminating the other; use a crossover on a second small task if feasible.
- **Days 10–12:** reveal the upstream change, repair both tracks, and rerun held-out forward/backward, alias/state, numerical, stream, and workload checks. Re-time accepted immutable artifacts independently; report generated coverage, fallbacks, resource usage, failures, and manual intervention minutes.
- **Days 13–14:** reproduce on the sponsor's deployment path and review support obligations. **Continue only if** an actual deployment blocker is removed, zero accepted semantic failures occur in the untouched holdout, deliberate mutants are rejected, expert time including setup falls by at least 50%, and either a deployment unavailable before is now usable or measured complete-workload economics improve by at least 5%. These are proposed decision thresholds, not measured results or a proof of universal correctness.

**E — Commercial gate:** the sponsor agrees to a specific bounded follow-on scope and identifies the existing migration/support expense it replaces. A hypothetical $10k–25k pilot is testable; an inference-spend TAM multiplied by an assumed waste fraction is not evidence. If all benefit comes from publicly available toolchains and ordinary agent access, contribute the harness/patch and stop the special product claim.

## Rejected ideas and versions — one line each

- **I — General “AI CUDA engineer”:** public loops and commercial products already exist; KernelBench success is not product differentiation.
- **I — CUDA→ROCm syntax translator:** HIPIFY already handles much of that; remaining semantics, architecture-specific performance, and maintenance must be demonstrated.
- **I — Universal CUDA→AMD/TPU/Apple agent:** Meta/Modular and compiler ecosystems already pursue heterogeneity; one reference cannot validate every target's execution and economics.
- **I — LLM guesses tile sizes:** Helion already reports large tuning-cost reductions; compare with its hybrid search before building anything.
- **I — “Autotuning died, agents revive it”:** historically false; agents change expert extension costs and search quality, not the existence of empirical optimization.
- **I — New Halide/TVM with a chat interface:** current DSLs and agents already cover the proposal; an accepted missing primitive is a better contribution.
- **I — Polyhedral compiler for arbitrary irregular ML:** a model cannot make unsupported aliasing/data dependence affine without proving a valid transformation or restricting coverage.
- **I — STOKE for unrestricted GPU code:** concurrency, new instructions, and finite-precision semantics exceed the strong oracle of a small integer region; direct PTX agent work already exists.
- **I — LLM plus e-graph as an unexplored combination:** LGuess, EggMind, and EqiForge occupy related guidance and tensor-search directions; unchecked rewrites defeat the premise.

- **I — Private systolic ASIC per model:** the hardware idea succeeded; cheap schedule writing does not remove silicon capital, fabrication, deployment, or bandwidth limits.
