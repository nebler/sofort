# Models propose; old PL machinery checks

Research date: **2026-10-28**. Lens: compiler, synthesis and verification techniques whose search or human guidance can be supplied by an LLM. **F** = sourced fact; **M** = measured here; **I** = inference/judgment/proposal; **E** = estimate or experimental acceptance threshold. Published benchmark results are **F**, not **M**. No experiments were run for this report.

**F — Context read:** [round-two brief](BRIEF.md), [round-one method/template](../flip/BRIEF.md), the TL;DRs, ONE bets and rejected lists of round-one reports 01–06, and [the agent compiler report](../moonshots2/02-compilers.md). This report does not propose another agent JIT, trace compiler or incremental-agent runtime. The twelve entries below preserve the nine-question template; translation validation/superoptimization, invariants/termination, and attribute grammars/partial evaluation are paired to cover the full requested lens without pretending they are identical mechanisms.

**I — Verdict:** the economic flip is real, but the generic invention is occupied. By October 2026 there is direct work on LLM CEGIS, e-graph guidance, Alive2-guided optimization, Lean-checked LLVM validation, invariant and ranking-function synthesis, LiquidHaskell annotations, separation-logic specifications, recompilable decompilation, compiler mutator generation and repair. The best opportunities are narrow, maintained acceptance workflows around an existing customer program. This investigation does **not** establish an empty, venture-sized category comparable to round one's post-submit integration bet.

**I — Most important correction:** cheap proposal generation does not necessarily make checking cheap. A learned rewrite can be radically farther from the reference than a compiler peephole; an equivalent implementation can need an expensive relational proof. Better proposals sometimes enlarge the verification bottleneck. The more durable flip is often **LLM proposes the decomposition, invariant or proof**, while a small existing trusted checker validates each step.

## What counts as a checker

**I — Use these distinctions throughout.** A result is strong only relative to a frozen property, semantics and supported domain; it is not a guarantee that the property captures the customer's intent.

- **Strong:** a replayable proof or sound verification result for the entire stated domain, with relevant termination/effects included when claimed. Trust still includes the semantic model, frontend and checker implementation.
- **Bounded:** exhaustive checking only within an explicit bound. An SMT solver does not make bounded loop exploration an unbounded proof.
- **Weak:** compilation, tests, fuzzing, sanitizers, benchmark scores or agreement with an LLM judge. These can produce excellent counterexamples; lack of one does not establish equivalence.
- **None:** no independently specified acceptance criterion for the desired semantic claim. Readability and resemblance to likely source are examples.

**I — Shared anti-cheating boundary:** freeze the reference, public contract, allowed inputs, toolchain/flags, checker configuration and acceptance program outside the proposer's edit authority. Check the submitted artifact, not a different generated model of it. Reject extra assumptions, proof admissions, narrowed input domains, disabled checks and missing obligations. Keep `unknown` separate from success; measure coverage and refusal alongside correctness. A second LLM may help find problems but does not replace a mechanical checker.

**F — These are observed problems, not hypothetical reservations.** The Verus guide explicitly recommends a cheat checker and forbids changing existing specifications/executable code or using `assume`/`admit` in proof tasks. Meta's October 2026 typing survey reports respondents encountering overly broad types and suppression comments. [Verus guide, living documentation, accessed 2026-10-28](https://verus-lang.github.io/verus/guide/llmforverusproof.html); [Meta, 2026-10-27](https://engineering.fb.com/2026/10/27/developer-tools/python-typing-survey-2026-ai-tools-checker-landscape/).

## 1. CEGIS: replace expensive candidate search and human sketching

1. **Idea / origin — F.** Supply a partial program with holes; synthesize candidates, ask a validator for counterexamples, and accumulate them until a candidate meets the specification. Solar-Lezama's 2008 dissertation makes human algorithmic insight central: the sketch communicates structure while SAT-based induction fills details. CEGIS predates the dissertation; 2008 is the requested Sketch reference, not a claim about the date of invention. [Solar-Lezama, 2008-12-19](https://www2.eecs.berkeley.edu/Pubs/TechRpts/2008/EECS-2008-177.html).

2. **Why niche — F/I.** The thesis describes the difficulty of communicating insight without forcing programmers into unfamiliar formalisms. **I:** choosing the grammar, sketch and specification can cost more than implementing the function; solver search grows with the implementation space. This is a limitation of general application, not evidence that synthesis died.

3. **What flipped — I.** The agent can propose both the initial sketch and successive complete candidates, generalize counterexamples and try alternative decompositions. It can search across implementation strategies rather than just hole values. **F:** the AAAI 2025 LLM-CEGIS-Repair artifact already combines MaxSAT fault localization, sketches and LLM candidates. Its checking is against a test suite, a materially weaker oracle than universal verification. [Morvalho et al., AAAI 2025 artifact](https://github.com/pmorvalho/LLM-CEGIS-Repair).

4. **Oracle / cheating — strong, bounded or weak depending on validator, I.** An SMT proof in a supported finite/decidable DSL can be strong; bounded Alloy exploration is bounded; regression tests are weak. The model can satisfy safety by refusing all requests, hard-code seen counterexamples, weaken the generated formalization, or repeatedly forget previous cases. Keep the formalizer untrusted too; a correct solution of an incorrect encoding is not a correct implementation of the request.

5. **100× better model — I.** Makes the search cheaper and broadens feasible sketches. The checker still matters where acceptance is an engineering obligation, but a standalone CEGIS orchestration wrapper becomes easier to reproduce. Better models do not disambiguate an underdetermined specification without additional information.

6. **Who already does it — F.** Beyond the AAAI tool, Cunha's **Verified LLM-Driven Synthesis for Concept Design** uses a CEGIS-style loop for reaction rules. On three applications/twelve variants, invariant-only synthesis often produced implausible designs; scenarios improved intended-design recovery but did not eliminate missed behavior. This directly demonstrates that formal acceptance and product intent can diverge. [Cunha, preprint 2026-07-17](https://arxiv.org/abs/2607.15718). Refine4LLM also combines LLM generation with refinement calculus and verification. [Cai et al., POPL January 2025](https://doi.org/10.1145/3704905).

7. **Value / remaining gap — I/E.** No generic CEGIS startup gap established. A team with an existing formal DSL might pay for synthesizing and maintaining missing adapters, policies or arithmetic routines. **E:** a $10k–25k domain pilot is plausible only if it replaces days of specialist work; this is a price experiment, not market evidence. The missing asset is often the DSL's faithful semantics and discrimination of intended behaviors.

8. **Two-week proof — E.** Freeze twenty small reference-defined bit-vector or policy tasks, including conflicting/underspecified cases. A TS orchestrator retains all counterexamples; a solver checks candidates. Compare solver-only Sketch/SyGuS, ordinary agent-plus-tests and the hybrid under the same budget. Require useful contracts, explicit unknowns and fewer expert minutes, not merely more passing candidates.

9. **Demo / tweet / expert killer / kill — I/E.** Show a candidate that fits examples rejected by a new solver counterexample, then repaired without weakening the contract. Tweet: “The model supplies the sketch; an independent validator keeps finding the missing cases.” Killer: “You renamed a standard verifier feedback loop, and your spec does not express what users want.” Kill the generic product; retain a domain pilot only if the hybrid beats existing synthesis plus an ordinary agent after counting harness construction.

## 2. Equality saturation: model guesses checkpoints, schedules or new rewrite rules

1. **Idea / origin — F.** Retain equivalent expressions in an e-graph and extract one under a cost model instead of committing early to one rewrite order. `egg` made the approach practical and extensible. [Willsey et al., POPL January 2021](https://doi.org/10.1145/3434304). This was not a dead technique: the author's October 2026 retrospective describes substantial adoption and successors including egglog. [Willsey, 2026-10-01](https://blog.sigplan.org/2026/10/01/equality-saturation-an-incomplete-project/).

2. **Why niche — F.** Domain rewrite design and strategy selection remain manual; unrestricted expansion can exhaust memory. Guided Equality Saturation already asks humans for intermediate sketches/checkpoints to keep search tractable. [Koehler et al., POPL January 2024](https://steuwer.info/files/publications/2024/POPL-2024-2.pdf). **I:** this human-guided step is a particularly literal fit to the brief.

3. **What flipped — F/I.** LLMs can propose high-level waypoints and reusable search strategies. EggMind reports 45.1% lower final cost and 69.1% lower peak RAM than full EqSat on its vectorization benchmarks, with an XLA transfer study. These are author-reported comparisons, not universal speedups or product adoption. [Yin et al., preprint 2026-04-19](https://arxiv.org/abs/2604.17364). **I:** proposal cost falls, but extraction and e-graph growth remain real costs.

4. **Oracle / cheating — strong only through validated equalities, I.** E-graph membership proves derivability from the installed rules, not that those rules model the real language. If the model proposes a **new** rule, prove it in the DSL semantics, with its side conditions, before unioning classes. If it proposes only a strategy over fixed sound rules, correctness is much easier to preserve. Floating-point reassociation, integer overflow, binders, aliasing and effects are common gaps. A model can also game a symbolic cost model while making actual runtime worse.

5. **100× better model — I.** Helps choose smaller proof paths and better strategies; e-graphs still provide compact search and independently checkable derivations. For simple tasks direct generation plus verification may eliminate the need for saturation. Demand a comparison with that baseline.

6. **Who already does it — F.** **LGuess**, presented at EGRAPHS 2025 and posted November 1, asks LLMs for rewrite checkpoints and uses e-graphs for the intervening low-level chains; its demonstrated domain is multivariable polynomial factorization. **EggMind** synthesizes strategies, rather than simply trusting new LLM-written equations. **ChopChop** also uses e-graphs to constrain outputs to a rewrite-equivalent program space. [Peng/Ji/Xiong, 2025-11-01](https://arxiv.org/abs/2511.00403); [EggMind, 2026-04-19](https://arxiv.org/abs/2604.17364); [ChopChop, POPL 2026-01-08](https://doi.org/10.1145/3776708).

   **F — New-rule generation is occupied too:** **ASPEN**, MLCAD September 2025, proposes design-specific RTL rewrite rules together with Z3 proof scripts, admits rules after verification, and combines egglog saturation with synthesis/PPA feedback. This is closer to “LLM proposes new equalities” than LGuess's checkpoints. [Zhang et al., author paper, §III.B](https://www.csl.cornell.edu/~zhiruz/pdfs/aspen-mlcad2025.pdf). **I:** the generated proof script must encode the actual rule and fixed RTL semantics; executing a model-written Z3 query is insufficient if it proves a different equation. **F:** **CHOMPY**, FMCAD September 2026, is a non-LLM conditional-rule synthesizer that outperforms its LLM-only baseline on both evaluated rule benchmarks. The model is not automatically the best proposer. [Cheung/Nandi/Lerner, proceedings abstract](https://repositum.tuwien.at/handle/20.500.12708/230508?mode=full).

7. **Value / gap — I/E.** Domain compiler maintainers pay for useful optimization coverage under a memory/time budget. A remaining hypothesis is a maintained, proof-backed rewrite package for an underserved DSL, including side conditions and upgrade tests. It is not “LLM + egg.” **E:** $20k for one compiler integration is a consulting-scale beachhead; no source here establishes demand or an unserved vendor category.

8. **Two-week proof — E.** Pick one fixed integer DSL with executable semantics. Agent proposes twenty rules or strategies; prove rules with SMT, reject invalid side conditions, then compare full EqSat, guided EqSat, direct candidate checking and EggMind-style strategy search. Hold out expression families and benchmark actual target execution. Report memory, search time, proof failures and total savings.

9. **Demo / tweet / killer / kill — I/E.** Show a tempting invalid overflow rewrite rejected before entering the e-graph, and a valid strategy avoiding explosion. Tweet: “The model points at a useful equality path; every new equation earns admission.” Killer: “LGuess/EggMind already do the guidance, and your DSL has no paying users.” Kill absent a domain-specific integration advantage or if direct generation/checking is cheaper.

## 3. Translation validation and superoptimization: qualify individual rewrites, not the proposer

1. **Idea / origins — F.** Pnueli, Siegel and Singerman's translation validation checks each translation rather than proving the translator once. Massalin's superoptimizer searches instruction sequences for a cheaper equivalent program. [TACAS 1998](https://doi.org/10.1007/BFb0054170); [Massalin, ASPLOS October 1987](https://web.stanford.edu/class/cs343/resources/superoptimizer.pdf). **I:** pairing them lets an arbitrarily unreliable searcher submit candidates without becoming trusted.

2. **Why niche — F/I.** Instruction-sequence search is combinatorial; equivalence becomes harder with loops/memory. Alive2 bounds loops and explicitly excludes interprocedural transformations; its own paper says it can miss bugs beyond its bound. [Lopes et al., PLDI June 2021](https://web.ist.utl.pt/nuno.lopes/pubs/alive2-pldi21.pdf); [Alive2 README, accessed 2026-10-28](https://github.com/AliveToolkit/alive2). **I:** cross-language lowering, ABI and environment modeling can dominate the cheap-candidate story.

3. **What flipped — F/I.** **Iago** replaces Souper's enumerative proposer with an LLM: 7.4% fewer optimizations on its SPEC-derived sample, but 35.7% of its found optimizations were absent from Souper's results. This is complementarity, not domination. [Mukherjee, LLVM meeting October 2025](https://llvm.org/devmtg/2025-10/slides/technical_talks/mukherjee.pdf). **LLM-VeriOpt** uses Alive2 feedback in GRPO training of Qwen-3B and reports 90% verifiably correct outputs on its evaluation. Training accuracy does not remove the need to check every deployed rewrite. [Fang et al., CGO Jan 31–Feb 4, 2026](https://samainsworth.github.io/LLM-VeriOpt-CGO2026.pdf).

4. **Oracle / cheating — strong for supported loop-free refinements; bounded for ordinary Alive2 loop checks, I.** LLVM refinement is directional and preserves permitted behavior on source-defined inputs; it is not unrestricted source-language equivalence. Do not let the agent add `assume`, `noalias`, `nsw` or fast-math promises to the reference. Do not silently drop `undef`, overflow, exceptional behavior, memory effects or unsupported operations. Proving equality of two Lean ports does not prove either port matches the original native code. Performance is a separate noisy oracle; prevent benchmark detection, cached answers and shape-specific overfitting.

5. **100× better model — I.** Creates better candidates **and** better proof decompositions, increasing validator utility. It reduces the value of a proprietary prompt/search layer. A validator that cannot follow algorithmic changes can become the limiting factor even when generation is excellent. Economic value must survive amortized search and integration cost.

6. **Who already does it — F.** This subfield is especially occupied:

   - **Meta LLM Compiler**, June 27, 2024: models trained on 546B tokens of LLVM IR/assembly for optimization/disassembly; a proposal/model product, not a blanket semantic certificate. [Meta publication](https://ai.meta.com/research/publications/meta-large-language-model-compiler-foundation-models-of-compiler-optimization/).
   - **Wang/Xie**, January 30, 2024: Alive2 followed by learned predictions and selective fuzzing when formal validation fails. **I:** predicted soundness after a timeout must not be labeled proved. [Paper](https://arxiv.org/abs/2401.16797).
   - **Iago**, October 2025, and **LLM-VeriOpt**, CGO 2026, directly occupy neural superoptimization and verifier-guided optimizer training, as above.
   - **Verified Learning for Compiler Optimization**, September 23, 2026: LLM lazification rewrites with Alive2 in the acceptance loop. [Singh/Feng/Saha preprint](https://arxiv.org/abs/2609.27214).
   - **Trivet**, September 17, 2026: generates structured Lean scaffolds, delegates remaining proof obligations to LLMs, and kernel-checks results. It resolves 147/148 benchmark transformations, including restricted loops and symbolic widths; that is not arbitrary LLVM coverage. [Liao et al.](https://arxiv.org/abs/2609.19583).
   - **alive-next**, repository inspected October 28, 2026: agent-proposed decomposition and stepwise Alive2-certified proofs, replayable packages, and verified/refuted/unknown outcomes. Its README explicitly assumes removal of middle-end `undef`; this is a semantic restriction to audit, not a universal LLVM claim. Public repository evidence, not independently reproduced soundness/performance. [Repository](https://github.com/connglli/alive-next).
   - **Agentic Verified Optimization / Aqueduct**, October 20, 2026: checked optimization of Lean functions and repository ports. The 17 real applications are migrated into Lean and ports are validated by differential testing; subsequent proofs do not upgrade that migration boundary into a theorem. [Ye et al.](https://arxiv.org/abs/2610.30188).
   - **AlphaEvolve**, May 2025 onward: proposal/evaluator search already deployed inside Google; Google reports a 23% Gemini kernel improvement and 1% training-time reduction. A May 2026 update calls it a regular infrastructure tool, and Cloud documents an enterprise offering. Evaluator-driven search is not uniformly formal verification. [2025 announcement](https://deepmind.google/blog/alphaevolve-a-gemini-powered-coding-agent-for-designing-advanced-algorithms/), [2026-05-07 update](https://deepmind.google/blog/alphaevolve-impact/), [Cloud documentation, accessed 2026-10-28](https://docs.cloud.google.com/gemini/enterprise/docs/alphaevolve/developer-guide/overview).

7. **Value / gap — I/E.** The residual hypothesis is **qualification of real, source-native rewrite queues across updates**, using these validators rather than inventing another proposer. Integrate extraction, semantic restrictions, replay and performance qualification for one LLVM-using library team. Alive2/alive-next already cover major portions; this is a delivery/maintenance hypothesis, not an unoccupied method. **E:** a $2m/year compute workload with a genuine 3% end-to-end saving yields $60k/year gross headroom, before integration and verification costs. A $10k–20k pilot needs a named owner and blocked rewrite backlog.

8. **Two-week proof — E.** Freeze twenty real before/after pairs from one existing library; include integer/memory leaf functions and explicit exclusions. Use a TS queue with existing command-line validators. Compare ordinary agent+tests, direct Alive2, alive-next/Trivet where applicable, and the integrated workflow. No port-to-Lean shortcut unless the port itself is proved. Require at least three useful accepted native rewrites or verified rejection of real dangerous rewrites, one replay after a version change, zero accepted semantic mutants, and ≥50% less expert qualification time. Unknowns remain unshipped.

9. **Demo / tweet / killer / kill — I/E.** Replay the proof for the actual compiled artifact, show an overflow/memory counterexample, then invalidate the evidence after changing flags or source. Tweet: “A stronger optimizer can propose anything. This library accepts only rewrites whose exact semantic claim replays.” Killer: “Run alive-next plus a build script; your integration adds no customer value.” Kill unless a real team's backlog and review time establish an advantage beyond those tools. **Disposition: best conditional tool bet; not a proven company gap.**

## 4. Decompilation: recompilation is feedback, behavioral preservation is the goal

1. **Idea / origin — F/I.** Recover high-level programs from binaries using machine semantics, dataflow, types and control-flow structuring; use recompilation to constrain a guessed reconstruction. Cifuentes's thesis is a foundational modern reference, not the origin of all decompilation. [Reverse Compilation Techniques, July 1994](https://www.phatcode.net/res/228/files/decompilation_thesis.pdf). **I:** a model can supply the missing types, declarations and idiom reconstruction that previously demanded analyst effort.

2. **Why niche — F/I.** Decompilers did not die. Compilation destroys names/types/structure, and unknown calling conventions, indirect control flow and libraries remain difficult. **F:** DecLLM specifically documents the barrier that useful decompiler pseudocode is often not recompilable. [Wong et al., ISSTA July 2025](https://daoyuan14.github.io/papers/ISSTA25_DecLLM.pdf).

3. **What flipped — F.** DecLLM uses iterative LLM repair with compilation and dynamic runtime feedback and reports about 70% recompilation success for previously non-recompilable outputs in its evaluation. LLM4Decompile trains dedicated models for direct decompilation and refinement; its 2025 Decompile-Bench releases include two million training pairs and 70k evaluation pairs. [LLM4Decompile, EMNLP 2024](https://aclanthology.org/2024.emnlp-main.203/); [author dataset repository, release 2025-05-20](https://github.com/Pey121/llm4decompile/tree/main/decompile-bench).

4. **Oracle / cheating — compilation weak; binary behavioral comparison stronger but still finite, I.** Compiling `return 0` proves almost nothing. Byte-identical recompiled code is strong evidence for that code region under a fixed toolchain/relocation treatment, but is restrictive and not a general oracle for recovered behavior/types. Differential execution needs valid ABI-aware inputs, globals, heap state, external calls and error behavior. A model can invent a guard that removes a real vulnerability or fabricate a plausible callee. Preserve unknowns explicitly rather than quietly filling them with ordinary-looking C.

5. **100× better model — I.** Improves source recovery; does not recreate information that the binary never contained or validate an invented environment. Analysts still need provenance and semantic disagreement reports. A generic decompiler wrapper is rapidly commoditized.

6. **Who already does it — F.** LLM4Decompile and DecLLM are direct prior art; **RevEng.AI** exposes AI decompilation via product APIs/MCP. [Vendor documentation, accessed 2026-10-28](https://docs.reveng.ai/). **Decompile-Diverge** directly attacks the checking gap: it generates drivers, fuzzes from the reference and compares outputs. Among candidates passing shipped tests it reports 4.9% divergence overall, up to 13% for one system; on its real-library sample improved build rate coincided with worse behavioral agreement. [Liu/Raff/Micinski, preprint 2026-09-04](https://arxiv.org/abs/2609.05370). These are study-specific rates, not a population estimate.

7. **Value / gap — I/E.** Security and legacy-binary teams might pay for **ABI/state-aware qualification of one binary family**, including preservation of crash behavior and unresolved calls. Decompile-Diverge already occupies generic differential auditing. **E:** $10k per bounded legacy component is a hypothesis; evidence of recurring customer effort is required. No general “recompilation is the oracle” company survives this search.

8. **Two-week proof — E.** Choose fifty locally executable leaf functions from a permitted binary with known source withheld from generation. Generate drivers from ABI information; compare registers/return values and reachable memory, including boundary inputs and crash outcomes. Evaluate Ghidra, LLM refinement and Decompile-Diverge-style checking. Include a deliberately “sanitized” wrong reconstruction. Count driver mistakes and exclusions.

9. **Demo / tweet / killer / kill — I/E.** Show a beautiful compiling decompilation that erased a crash, then the divergence witness. Tweet: “Recompiled is not recovered: the original binary supplies the disagreement.” Killer: “Your driver invented the input contract; this is already Decompile-Diverge.” Kill without a valuable ABI/state integration that existing tools lack, or if valid drivers require analyst effort comparable to manual reconstruction.

## 5. Compiler fuzzing: make generators and mutators, not just individual test programs

1. **Idea / origin — F.** Generate defined programs, compile in multiple ways, and compare behavior to find wrong-code bugs. Csmith avoids undefined/unspecified behavior and reported over 325 previously unknown bugs over three years. [Yang et al., PLDI June 2011](https://www.flux.utah.edu/paper/yang-pldi11). YARPGen remains an actively available C/C++ generator; it is a baseline to reuse, not a dead predecessor. [Intel repository, accessed 2026-10-28](https://github.com/intel/yarpgen).

2. **Why bounded — F/I.** Building semantic-aware generators for new features/languages requires expertise. MetaMut's paper identifies invention and implementation of useful mutators as the labor bottleneck. **I:** naïvely replacing Csmith with a chat model can destroy validity and throughput, making the “revival” worse. [Ou et al., ASPLOS April–May 2024](https://connglli.github.io/pdfs/metamut_asplos24.pdf).

3. **What flipped — F/I.** MetaMut's paper reports 118 valid generated mutators at roughly $0.50/model invocation cost per mutator, after substantial prompt setup, and 131 bugs found. Its repository now describes over 200 mutators and over 130 reported bugs. Keep paper and live-repository counts separate. [Paper](https://connglli.github.io/pdfs/metamut_asplos24.pdf); [repository, accessed 2026-10-28](https://github.com/icsnju/MetaMut). **I:** an LLM can pay the language-expert cost once and leave a cheap conventional generator in the hot loop.

4. **Oracle / cheating — weak-to-strong evidence of individual failures, I.** A reproducible differential result on a **defined** program is powerful evidence; disagreement does not by itself identify which compiler is wrong. Sanitizers do not prove absence of all C UB, implementation-defined differences or unspecified evaluation order. Crashing a compiler and finding a miscompilation are different outcomes. The proposer can inflate novelty with invalid inputs, trivial duplicates, timeout floods or coverage in unimportant parsing paths. The reducer must preserve definedness as well as the failure.

5. **100× better model — I.** Improves generator synthesis, failure diagnosis and reduction. Conventional generation still wins on per-test cost/throughput; a better model does not make repeated inference necessary. Durable value is a maintained feature-validity oracle and useful actionable bugs, not generated-line counts.

6. **Who already does it — F.** **Fuzz4All** is an ICSE 2024 universal LLM fuzzer, **WhiteFox** an OOPSLA 2024 white-box optimization-directed fuzzer, and **MetaMut** an ASPLOS 2024 mutator synthesizer. [Fuzz4All artifact](https://github.com/fuzz4all/fuzz4all); [WhiteFox paper](https://arxiv.org/abs/2310.15991). **LegoFuzz**, OOPSLA 2025, interleaves offline LLM function generation with cheap composition and explicitly studies validity/throughput limits of online generation. [Ni/Li, 2025](https://doi.org/10.1145/3763079). **IssueMut**, MSR April 2026, learns mutators from bug histories and notes MetaMut's crash-oriented checking. [Author paper](https://damorim.github.io/publications/Liu_ETAL_MSR26.pdf). **GapForge**, July 2026, targets coverage gaps. [Preprint](https://arxiv.org/abs/2607.15762). An independent practitioner also documents MetaMut-style campaigns for Sui Move/Cairo, weakening the claim that smaller languages are untouched. [nowarp, 2026](https://nowarp.io/blog/compiler-testing-part-1/).

7. **Value / gap — I/E.** A small compiler vendor may buy **qualification for one new extension**, with definedness, reference interpretation, reduction and upstream-ready reports. The broad “LLM makes fuzzers” gap is closed. **E:** $15k–30k/extension campaign could fund a specialist service; no sourced budget or market count here. The strongest remaining work may belong upstream rather than in a new platform.

8. **Two-week proof — E.** Choose a CPU-executable DSL/IR extension with an independent interpreter. Agent writes a Rust generator; check generated programs in a restricted, explicitly defined subset. Compare ordinary property-based generation, templates and an LLM-assisted generator at equal CPU/model budgets. Seed known wrong-code mutants and freeze a holdout feature family. Require a real minimized divergence or materially better mutant discovery, with all invalid-input triage time charged.

9. **Demo / tweet / killer / kill — I/E.** A newly added vector operation produces a wrong-code witness, reduced to ten lines without losing definedness. Tweet: “The model writes the generator once; the reference interpreter judges millions of programs.” Killer: “MetaMut/LegoFuzz already did it, and your sanitizer is not a UB proof.” Kill without a named underserved extension or if hand templates find the same bugs for less effort. **Disposition: third-ranked conditional service/tool opportunity.**

## 6. Abstract interpretation, loop invariants and termination: synthesize proof ingredients

1. **Idea / origins — F.** Cousot and Cousot formalize sound approximation of program semantics via abstract domains and fixpoints; this is not merely guessing assertions. [POPL 1977, author's source](https://cs.nyu.edu/~pcousot/COUSOTpapers/POPL77.shtml). Ranking functions prove progress in a well-founded order; Podelski/Rybalchenko give a complete synthesis method for a particular linear-loop class, not arbitrary termination. [VMCAI January 2004](https://doi.org/10.1007/978-3-540-24622-0_20).

2. **Why niche — F/I.** Abstract interpretation succeeded in production analysis. The limitation is precision/domain design and proof ingredients for hard programs. **F:** LOOPY studies LLM-supplied invariants and ranking functions, noting the need for both inductive invariants and supporting facts for termination. **I:** nonlinear arithmetic, heap shape and relational properties push beyond fixed templates and require expert lemmas. [Kamath et al., FMCAD 2024](https://adharshkamath.github.io/papers/loopy_fmcad24.pdf).

3. **What flipped — I.** The model can supply predicates, disjunctions, auxiliary lemmas, lexicographic rankings and proof decompositions. The existing analyzer/VC generator must establish them. A particularly safe design lets the agent propose the **analysis result**, then checks a post-fixpoint; having it write an unchecked abstract transfer function instead changes the trusted analyzer.

4. **Oracle / cheating — strong with complete obligations, I.** Check initiation, preservation and sufficiency of invariants. For termination also check a well-founded measure, decrease and all supporting conditions under the real arithmetic/memory model. Checking only that the postcondition follows from an invariant permits `false`; checking only preservation permits an unreachable or useless invariant. Proving partial correctness does not prove termination, and termination does not imply a practical latency bound. The agent can invent loop bounds, assume overflow away, or exclude states by strengthening preconditions.

5. **100× better model — I.** Makes more useful facts available; independent checking remains valuable. It may obsolete much specialized invariant-search engineering, while increasing demand for interoperable semantics/VC interfaces. A standalone ranking-function chat UI has little moat.

6. **Who already does it — F.** **LEMUR**, ICLR 2024, formalizes a sound model/reasoner interaction with LLM-suggested subgoals. [Wu/Barrett/Narodytska](https://proceedings.iclr.cc/paper_files/paper/2024/hash/0c86142265c5e2c900613dd1d031cb90-Abstract-Conference.html). Microsoft's **LOOPY**, FMCAD 2024, combines candidates with Houdini and Frama-C; it covers termination as well as invariants. [Paper](https://adharshkamath.github.io/papers/loopy_fmcad24.pdf). **Quokka**, September 2025/revised August 2026, validates whether proposed invariants help prove assertions and evaluates 866 held-out instances. [Wei et al.](https://arxiv.org/abs/2509.21629). **LimICE**, July 30, 2026, integrates LLM lemma sequences with Incremental ICE and an ICE-DT fallback. [Author project, 2026](https://mast.stanford.edu/pubs/argus_agentic_gpu_optimization_guided_by_data_flow_invariants/).

7. **Value / gap — I/E.** Existing verified-code teams may pay for keeping fixed safety/termination obligations discharged across ordinary code changes, especially outside contest-sized arithmetic programs. General invariant synthesis is occupied. **E:** ten verification specialists saving one day/month at an assumed $1k/day yields $120k/year gross labor headroom; this estimates a customer situation, not product demand. Deployment context and unchanged contracts are essential.

Compare Frama-C alone, LOOPY/Quokka-style inference and a normal coding agent. Include nonterminating and invalid-invariant mutants. Measure expert minutes and verification time across revisions; distinguish safety, termination and resource bounds.

9. **Demo / tweet / killer / kill — I/E.** A changed loop invalidates the old invariant; the agent supplies a stronger inductive fact and the fixed assertion re-verifies. Tweet: “The model finds the lemma; the old verifier checks every transition.” Killer: “LOOPY already does this, and a generic agent now performs equally well.” Kill the proposer product unless maintenance on real revisions beats those baselines; keep the checker integration if useful.

## 7. Refinement types / LiquidHaskell: let models write the missing contracts

1. **Idea / origin — F.** Liquid Types combine conventional type inference with predicate abstraction and logical qualifiers to infer refinements expressive enough for safety properties. The original work already sought to reduce annotations, rather than requiring humans to write all dependent proofs. [Rondon/Kawaguchi/Jhala, PLDI June 2008](https://doi.org/10.1145/1375581.1375602).

2. **Why niche — F.** Modular expressiveness creates annotation choice: a contract can verify a function in isolation but be too weak for its callers. LHC's paper describes expert days-to-weeks annotation effort for the libraries it studies. [Sakkas et al., ICSE April 2025](https://ranjitjhala.github.io/static/icse25-neurosymbolic-refinement-inference.pdf). **I:** this is a particularly clean labor-cost flip, but a small-language ecosystem limits standalone market size.

3. **What flipped — F.** **LHC / Liquid Haskell Copilot** generates refinements across a call graph, combines neural bottom-up generation with symbolic assistance, and uses LiquidHaskell as oracle. On three packages it reports up to 94% of functions annotated automatically in hours using a 3B StarCoder model. This is package-specific coverage, not 94% of arbitrary Haskell correctness proved. [ICSE 2025 paper](https://ranjitjhala.github.io/static/icse25-neurosymbolic-refinement-inference.pdf).

4. **Oracle / cheating — strong for expressed properties within trusted assumptions, I.** Typechecking `Int -> Int` is not proof of a requested sorting or memory property. Weak result refinements, contradictory preconditions, trusted `assume` declarations and disabled termination can defeat the intended guarantee. Freeze exported contracts and prove internal contracts sufficient for all relevant clients. Reflected functions, axioms, FFI boundaries and the underlying compiler/checker remain part of the trust accounting. [LiquidHaskell specification reference, accessed 2026-10-28](https://ucsd-progsys.github.io/liquidhaskell/specifications/).

5. **100× better model — I.** Makes rich type/proof annotations cheaper and increases adoption potential. It also commoditizes LHC-like generation. The existing type checker is the durable component; workflow/maintenance value must be demonstrated.

6. **Who already does it — F/I.** LHC is an almost exact implementation of the proposed revival. Refinement-driven development remains an active research/tooling practice, including Tweag's IFL 2025 study/artifact. [Tweag artifact, 2025](https://github.com/tweag/ifl2025-liquidhaskell). **I:** this search found direct research/artifacts, not evidence that a universal commercial refinement-annotation service is deployed. Lack of a vendor is not proof of unmet demand.

7. **Value / gap — I/E.** A narrow gap is maintaining library interface guarantees across dependency/version changes, preserving public refinements and shrinking proof failures. Porting the idea to another language alone is not differentiation: existing verifiers already have agent integrations. **E:** $5k–15k for a proof-maintenance integration is a services hypothesis; generic Haskell annotation is unlikely to support a broad business.

8. **Two-week proof — E.** Reuse one LHC benchmark/library, freeze its public specification, and apply five realistic edits and ten wrong implementations. Compare LHC, an ordinary agent and manual annotations. Require all frozen client obligations to survive correct edits and all semantically relevant mutants to be rejected without contract weakening. Record verifier/configuration changes.

9. **Demo / tweet / killer / kill — I/E.** Show a package upgrade whose exported nonempty/bounds property still checks after automatic internal annotation repair. Tweet: “The agent updates the refinement plumbing; callers keep the same guarantee.” Killer: “LHC already does the hard part; there are too few users.” Reject generic inference as a new bet; continue only with a real maintenance customer and measurable saved work.

## 8. Gradual typing and type migration: optimize useful checking, not green builds

1. **Idea / origin — F.** Gradual typing supports programmer-controlled migration between dynamic and static portions, with formal interaction rules. [Siek/Taha, September 2006](https://web.stanford.edu/class/cs242/materials/old/siek06__gradual.pdf). **I:** distinguish this semantic discipline from adding optional Python/TypeScript annotations, whose checkers have different guarantees; they are not automatic implementations of a sound gradual calculus.

2. **Why bounded — F/I.** Type migration succeeded widely; package boundaries, dynamic frameworks and whole-repository consistency remain costly. **F:** TypyBench evaluates fifty Python repositories and finds that plausible type predictions still produce substantial consistency errors. [Dong et al., ICML 2025](https://www.cs.toronto.edu/~fanl/papers/typebench-icml25.pdf). **I:** the graveyard is labor-intensive precise migration, not typed languages themselves.

3. **What flipped — F.** Google's migration toolkit combines static targeting, Gemini edits and build/test repair. Its int32→int64 migration reported 80% AI-authored modifications and an engineer-estimated 50% time reduction; humans still targeted/reviewed changes, and some tests changed. This is a typed-code migration, not untyped→typed soundness evidence. [Google Research, 2024-07-18](https://research.google/blog/accelerating-code-migrations-with-ai/). Meta's 2026 survey reports 42.5% of respondents to the relevant question used AI to write hints; missing third-party type information was the leading reported difficulty at 65.1%. Survey responses are not population-random adoption measurements. [Meta, 2026-10-27](https://engineering.fb.com/2026/10/27/developer-tools/python-typing-survey-2026-ai-tools-checker-landscape/).

4. **Oracle / cheating — strong for selected static constraints, weak for runtime equivalence, I.** A passing type checker can be achieved with `Any`, `object`, casts, ignored errors, missing-import fallbacks or excluded files. A wrong stub can make every client appear safe. Freeze checking scope/configuration; measure precision and injected-bug detection in addition to error count. Preserve executable behavior and test public runtime interactions. Annotations can affect frameworks/introspection, so “types erase” is not a universal Python migration guarantee.

5. **100× better model — I.** Helps infer complex API shapes and fix cross-file inconsistencies; greatly weakens a generic annotation-agent business. Versioned third-party contracts and cross-checker conformance still need maintenance, but native inference may remove many cases without annotations.

6. **Who already does it — F.** **TypeT5**, ICLR 2023, already combines static context and iterative neural type predictions. **TypeWeaver/OpenTau**, documented in Yee's 2024 thesis, handle TypeScript migration/search rather than local type guesses alone. [TypeT5 artifact](https://github.com/utopia-group/TypeT5); [Yee, 2024 thesis](https://mhyee.com/publications/2024-phd-thesis.pdf). **TypyBench**, 2025, exposes repository consistency; **TypeCare**, ICSE April 2026, reranks/augments predictions from TypeT5/Tiger/TypeGen. [TypeCare author paper](https://prl.korea.ac.kr/papers/icse26typecare.pdf). Meta's survey explicitly describes AI tools invoking checkers and the Pyrefly team's work on agentic workflows. Google's toolkit demonstrates scaled internal migration. No claim that a new “AI type migrator” is unoccupied survives these sources.

7. **Value / gap — I/E.** The narrow hypothesis is **maintained third-party stubs for one dynamic framework**, with runtime examples, precision gates and tests of known invalid callers. This addresses documented pain and avoids arbitrary whole-codebase rewrites. It remains a weaker-oracle opportunity than formal translation validation and may belong with typeshed/framework maintainers. **E:** $10k pilot or $1k/month maintenance for one enterprise framework/version set; demand unverified.

8. **Two-week proof — E.** Select a package with real missing/incorrect stubs and ten client modules. Freeze runtime behavior, checker flags and scope. Agent proposes stubs/annotations; compare checker acceptance, valid-client compatibility, twenty deliberately invalid call sites and held-out runtime interactions. No new suppressions/dynamic escapes. Compare with ordinary agent+checker and framework-maintainer baseline; runtime agreement remains finite evidence.

9. **Demo / tweet / killer / kill — I/E.** Show a previously invisible invalid framework call rejected while valid dynamic cases continue to work. Tweet: “Fewer unknown types, more real mistakes caught, no added ignores.” Killer: “You sold annotations; my checker infers them and the framework's stubs are already improving.” Kill if mutation rejection does not improve, if valid clients are excluded, or if maintainers cannot justify recurring support. **Disposition: second-ranked conditional opportunity on pain evidence, not checker strength.**

## 9. Separation logic and Infer: distinguish proved contracts from absence of alarms

1. **Idea / origin — F.** Separation logic reasons locally about owned heap fragments; bi-abduction infers missing preconditions/frame information for compositional analysis. Reynolds's 2002 survey and Infer's foundations document this lineage. [Reynolds, LICS July 2002](https://doi.org/10.1109/LICS.2002.1029817); [Infer foundations, accessed 2026-10-28](https://fbinfer.com/docs/separation-logic-and-bi-abduction/).

2. **Why bounded — F.** Infer did not stall: Meta deploys it in CI across its main applications. What remains expensive is specifying custom heap abstractions and proving functional behavior with tools such as VeriFast/Iris. [Infer overview, accessed 2026-10-28](https://fbinfer.com/docs/about-Infer/). A 2026 study of 303 C functions reports only 31.4% verification success for generated VeriFast specifications despite much higher measured preservation of source/spec behavior. [Fan et al., 2026-06-25](https://arxiv.org/abs/2606.26490).

3. **What flipped — I.** Models can propose ownership predicates, unfold/fold sequences, frame facts, call summaries and proof scripts. The hard human step shifts from writing every assertion to choosing the externally required behavior and qualifying the abstraction boundary. Generating summaries for unknown libraries is useful only if their truth is independently checked.

4. **Oracle / cheating — strong for complete SL proofs; weak for “Infer has no report,” I.** Infer Pulse documents optimistic treatment of unknown functions and examples of false negatives/positives. Its silence is not a whole-program memory-safety proof. [Pulse documentation, accessed 2026-10-28](https://fbinfer.com/docs/checker-pulse/). The proposer can hide effects behind an unknown call, add a trusted lemma, weaken ownership requirements, suppress a finding, or prove memory safety while changing outputs. A checked SL contract proves what it says, not that it describes the API users depend on.

5. **100× better model — I.** Particularly helpful for intricate heap proofs and lemma selection. Does not eliminate the need to validate library summaries or semantic bridges. General-purpose coding agents with checker access are a strong, improving competitor to bespoke proof scaffolds.

6. **Who already does it — F.** **Spec-Agent**, May 26, 2026, synthesizes specifications across C++ repositories using static analysis, heap tracing and fuzz-based counterexample feedback; its reported 85% valid target coverage is empirical validation, not universal separation-logic proof. [Suresh/Korczynski/Vanegue](https://arxiv.org/abs/2605.27531). **SPLIT / SL-VC**, ICML July 2026, uses LLM-friendly tactics and spatial/pure decomposition on 289 SL verification conditions. [Wang/Wu/Cao](https://proceedings.mlr.press/v306/wang26iw.html). **Aria**, July 2026, reports broad proof completion with general code agents in a verification harness, including Iris/Rust-library lemmas. [Harnessing Code Agents for Automatic Software Verification](https://arxiv.org/abs/2607.06341). These differ from claiming that Meta Infer itself universally proves LLM patches; this search did not establish that claim.

7. **Value / gap — I/E.** Maintaining proved contracts for one custom C allocator/container or API boundary is a plausible specialist deliverable. The gap is not simply specification generation: Spec-Agent and the proof systems already exist. **E:** one team saving 20 specialist days/year at $1k/day supports at most $20k/year gross labor headroom before integration costs. A large cross-repository product is not established.

8. **Two-week proof — E.** Freeze one allocator or container implementation plus existing functional/ownership contracts. Let an agent repair auxiliary predicates/proofs after five implementation edits. Compare a generic agent, existing prover automation and specialized decomposition. Inject leak/UAF/output-change mutants, including one hidden behind an unmodeled helper. Require a complete checker result, not just a clean Infer report.

9. **Demo / tweet / killer / kill — I/E.** Show Infer silence on an unmodeled boundary, then a frozen ownership obligation rejecting the patch. Tweet: “The heap proof closes; the contract and unknown calls stay visible.” Killer: “Aria plus VeriFast already handles this; your chosen API has no maintained spec.” Kill absent recurring specialist work and a fixed meaningful contract.

## 10. Automatic parallelization: models choose transformations, dependence machinery decides legality

1. **Idea / origin — F.** Express loop instances/dependencies as affine sets/relations and derive legal schedules. Feautrier's 1992 scheduling work is a key lineage; it did not claim arbitrary sequential programs were easy to parallelize. [Author bibliography, papers October/December 1992](https://perso.ens-lyon.fr/paul.feautrier/Html/FEAUTRIER-P.html).

2. **Why bounded — F/I.** The affine/domain restrictions make legality tractable; unknown aliasing, indirect accesses, effects and synchronization limit coverage. **F:** AutoParLLM explicitly studies contextual parallelism discovery and directive generation against existing tools. **I:** expert algorithm restructuring and schedule tuning are expensive, but neither dependency constraints nor Amdahl's law disappear with cheap code. [Mahmud et al., NAACL April 2025](https://aclanthology.org/2025.naacl-long.593/).

3. **What flipped — I.** Agent proposes a parallelization plan, schedule, tiling, reduction or data representation; a dependence checker/prover accepts legal plans and a benchmark selects performance. The more the agent changes the algorithm, the less a conventional schedule checker alone can certify it. Keep this distinct from model inference being a parallel workload.

4. **Oracle / cheating — strong for supported dependence/plan properties; weak for general numerical/runtime behavior, I.** Race-free is not equivalent, and one successful threaded execution explores few schedules. Reductions can change floating-point results, alias promises can be false, asynchronous work can escape benchmark timing, and a missing barrier may only fail at certain sizes. Runtime alias/shape guards can support a narrow fast path if fallback and guard sufficiency are checked. A proof over real arithmetic does not prove bitwise floating-point equivalence.

5. **100× better model — I.** Better search makes legality filters more useful. A perfect schedule proposer still needs cost measurement and a correct distributed execution plan. For simple directives, the improved compiler/agent can erase a separate product's value.

6. **Who already does it — F.** **AutoParLLM**, 2025, and **ParaCoder**, PPoPP/FCPC 2025, directly generate parallel code. [AutoParLLM](https://aclanthology.org/2025.naacl-long.593/); [ParaCoder author record, 2025-05-02](https://scholars.hkbu.edu.hk/en/publications/paracoder-parallel-code-generation-with-large-language-model/). **CoV**, CGO 2026, combines static checks, Alive2 and runtime verification for an LLM vectorizer. [Kwon et al.](https://doi.org/10.1109/CGO68049.2026.11395240). **TrainVerify**, SOSP October 2025, already verifies distributed training-plan equivalence, including Llama3-405B/DeepSeek-V3-671B plans. It is a checker for parallelization, not evidence of LLM-generated plans, and its arithmetic/plan scope excludes kernel implementation and buffer-management correctness. [Microsoft Research](https://www.microsoft.com/en-us/research/publication/trainverify-equivalence-based-verification-for-distributed-llm-training/), [author slides](https://luyunchi.github.io/assets/pdf/trainverify-sosp25-slides.pdf). ARGUS and AlphaEvolve are additional direct adjacent competition, not unexplored kernel-agent territory.

7. **Value / gap — I/E.** A CPU library vendor might pay for guarded parallel fast paths with maintained legality proofs on a neglected irregular workload. General “AI parallelizes code” is crowded. **E:** a verified 10% saving on $500k/year compute leaves $50k/year gross headroom; require end-to-end savings under real thread/NUMA constraints. Distributed training is a separate, more expensive integration, outside a solo two-week build.

8. **Two-week proof — E.** Twenty CPU loops from one application, run on existing hardware; no GPU rental. Agent proposes schedules/guards in an existing restricted IR, with mechanical dependence checks. Compare Polly/compiler auto-vectorization, direct agent code and guarded accepted candidates. Hold out sizes and aliasing cases; time complete executions including synchronization. Label non-affine refusals.

9. **Demo / tweet / killer / kill — I/E.** Show the parallel fast path rejected for overlapping ranges and safely selected for disjoint ones. Tweet: “The model suggests the schedule; the dependency proof and guard decide where it runs.” Killer: “CoV already does this, and your benchmark omitted numerical or synchronization cost.” Kill if useful accepted coverage or whole-application improvement is negligible.

## 11. Attribute grammars and partial evaluation: manufacture language tooling around fixed semantics

1. **Ideas / origins — F.** Knuth's attribute grammars attach inherited/synthesized semantic information to syntax trees. Futamura specializes an interpreter with respect to a fixed program, producing a residual program; later projections concern specializing the specializer. These are two distinct ways to obtain machinery from structured semantic definitions. [Knuth, June 1968](https://www.ccs.neu.edu/home/chadwick/files/knuth.pdf); [Futamura, 1971/revised 1999 author archive](https://fi.ftmr.info/); [Jones/Gomard/Sestoft, 1993](https://raspi.itu.dk/people/sestoft/pebook/pebook.html).

2. **Why bounded — F/I.** Semantic equations/pruners require expert construction; partial evaluation needs suitable staging and can explode code or specialize the wrong boundary. **F:** weval addresses deriving compilers from interpreters with much less bespoke backend machinery. **I:** neither idea died solely from typing labor, and mature parser generators/JITs/staging systems are the baseline. [Fallin/Bernstein, PLDI June 2025](https://cfallin.org/pubs/pldi2025_weval.pdf).

3. **What flipped — I.** For a small existing DSL, an agent can propose attribute equations, type/effect rules, semantic pruners, binding-time annotations and specialization hints. Existing interpreters, proof obligations and differential executions check them. The model fills the labor-intensive language adapter; it must not become the unchecked authority defining which programs count as correct. This is tooling for ordinary programs, not the already-covered proposal to JIT agent traces.

4. **Oracle / cheating — strong only relative to a correct grammar/semantics/specializer, I.** A grammar guarantees syntax, not meaning. An attribute checker proves the encoded property, which can omit effects or allow trusted escapes. Specialization must preserve the interpreter's behavior for every remaining dynamic input; treating an environmental value as static or removing error paths invalidates it. Differential testing against the interpreter is weak evidence unless backed by a proof. Specializing a fixed prompt is not a license to replace an opaque LLM's future decisions with a deterministic rule.

5. **100× better model — I.** Makes DSL tooling cheap and improves specialization hints; fixed semantic definitions still support independent checks. A universal grammar/pruner generator is easily competed away, while an established domain language may gain valuable tooling. If a normal compiler already performs constant propagation, extra LLM staging may have no value.

6. **Who already does it — F.** **ChopChop**, POPL January 2026, constrains generation using AST program spaces and semantic pruning, demonstrated on rewrite equivalence and a TypeScript subset. **AGDecode**, posted **October 26, 2026**, is an even more direct attribute-grammar revival: partially constructed ASTs, relational constraints, SMT/CHC oracles and a Rocq-mechanized metatheory; uncertain solver results require conservative rejection or later resolution. It is a two-day-old preprint at this report date, not a mature product. [ChopChop](https://doi.org/10.1145/3776708); [Maghera et al., AGDecode](https://arxiv.org/abs/2610.36105). **weval**, 2024 preprint/PLDI 2025, is a real non-LLM partial evaluator; its reported SpiderMonkey/Lua speedups are 2.17×/1.84×, not evidence of an LLM-in-loop revival. [Author paper](https://cfallin.org/pubs/pldi2025_weval.pdf). **I:** this bounded search found no comparably concrete primary demonstration of an LLM producing and certifying a general partial evaluator or Futamura compiler generator; do not turn that search result into a novelty claim.

7. **Value / gap — I/E.** A maintained semantic frontend for one enterprise DSL might be useful; a new generic “semantic constrained decoding” method is occupied. LLM-assisted specialization of one interpreter is a research integration with unproven demand. **E:** $10k–25k/tooling integration is a customer-interview hypothesis. No broad platform valuation follows from the analogy.

8. **Two-week proof — E.** Use an existing arithmetic/query DSL interpreter. Track A: agent proposes attributes/pruners; independent examples and solver obligations check type/effect constraints, including malicious escapes. Track B, as an alternative experiment rather than a second platform: agent adds staging hints to an existing evaluator; compare residual execution against the interpreter on held-out inputs, and disclose whether correctness is proved or only tested. Choose one track for implementation; do not build both from scratch.

9. **Demo / tweet / killer / kill — I/E.** Show a well-formed but semantically invalid DSL program rejected, or a specialization bug exposed by changing a supposedly dynamic input. Tweet: “Cheap semantic tooling, checked against the language we already run.” Killer: “AGDecode/ChopChop already do the grammar work; weval already does the specialization.” Reject a generic method/product; keep a concrete DSL integration only if it removes paid maintenance work that these tools do not already handle.

## 12. Program repair / GenProg: proposal quality flipped, patch correctness did not

1. **Idea / origin — F.** GenProg uses genetic search over program edits, with tests encoding required behavior and the defect, then minimizes patches. It began before 2012; the 2012 TSE paper and ICSE systematic study are the requested landmark references. [Le Goues et al., TSE Jan–Feb 2012](https://web.eecs.umich.edu/~weimerw/p/weimer-tse2012-genprog.pdf); [ICSE June 2012](https://doi.org/10.1109/ICSE.2012.6227211).

2. **Why niche — F/I.** Search-space and representation choices were central; tests constrain only observed behavior. The project's own archive now discourages use of its 105-bug ICSE 2012 benchmark, pointing to corrected later benchmarks. [GenProg experiment archive, accessed 2026-10-28](https://squareslab.github.io/genprog-code/experiments/). **I:** a plausible patch is not necessarily a semantically correct one, and manual review/overfitting remain after search improves.

3. **What flipped — F/I.** LLMs provide a rich edit prior and debugging behavior rather than blind statement mutation. **F:** Google CodeMender reported 72 upstreamed security fixes over its initial six months, with static/dynamic analysis, differential testing, fuzzing and SMT-based tools; its October 2025 announcement said humans reviewed patches before submission. [Google DeepMind, 2025-10-06](https://deepmind.google/blog/introducing-codemender-an-ai-agent-for-code-security/). **I:** this is the revival, already being executed; raw patch generation is not the remaining scarce capability.

4. **Oracle / cheating — tests weak; fixed-spec proof strong for specified behavior, I.** Removing the crashing path, swallowing all errors, returning empty results or rejecting valid inputs can pass a crash regression. A repair cannot generally be equivalent to the buggy implementation on the defect; specify the allowed behavior change and preserve everything else that matters. Frozen contracts plus differential testing outside the defect envelope help. Agent-generated tests based on its own mistaken interpretation do not provide independent intent.

5. **100× better model — I.** Makes repair proposals cheaper and reduces syntax/localization scaffolding value. High-volume acceptance and independently grounded regression evidence become more important, but may be native features of general agents/CI. Verification demand survives where organizations must justify acceptance, not merely because current models are unreliable.

6. **Who already does it — F.** AAAI 2025 **LLM-CEGIS-Repair** combines formal localization with test feedback, already discussed in §1. **CodeMender** is direct operational prior art, and Google's 2026 announcement describes bringing foundational capabilities to enterprise customers; public 2025 review practice must not be mistaken for proof of today's exact deployment workflow. [Artifact](https://github.com/pmorvalho/LLM-CEGIS-Repair); [Google, 2026-07-21](https://deepmind.google/blog/introducing-gemini-3-5-flash-cyber/). **Meta AutoPatchBench**, April 29, 2025, evaluates fuzz-found C/C++ repairs with additional fuzzing and white-box differential testing against a known fixed version. Its publication explicitly discusses incomplete comparisons, nondeterminism filtering and timeout handling. This is a much better checker than “crash disappeared,” but not proof. [Meta publication](https://engineering.fb.com/2025/04/29/ai-research/autopatchbench-benchmark-ai-powered-security-fixes/). **Specification-guided Dafny arithmetic repair**, July 2025, also directly uses formal contracts as repair oracles. [Wu et al.](https://arxiv.org/abs/2507.03659).

7. **Value / gap — I/E.** No generic GenProg-with-LLMs gap remains. A bounded backport service for a legacy branch with a known reference fix, executable differential oracle and unchanged API may have value. Existing security repair vendors/labs are powerful competitors; the branch/support commitment must be the differentiation. **E:** $5k–20k per difficult qualified backport is a pricing hypothesis, not sourced willingness to pay.

8. **Two-week proof — E.** Pick five public historical bugs with a fixed version/reference and older branch, runnable without Docker. Withhold reference patch text from generation; freeze the defect's allowed change and independent holdout corpus. Compare normal agent repair with structured localization/validation. Include error-swallowing and input-rejection mutants. Count maintainer review minutes, wrong accepted patches, model spend and total verification cost, not only test-pass rate.

9. **Demo / tweet / killer / kill — I/E.** Show a crash-disabling fake fix rejected by valid-input replay and a compatible backport accepted. Tweet: “The patch survives the bug and keeps the old branch's behavior.” Killer: “CodeMender/AutoPatchBench already built the loop; your corpus has the ground-truth fix that live users lack.” Kill without a concrete unsupported-branch customer or if ordinary agent+existing validation performs equally well.

## Evidence limits and synthesis

**F — Evidence quality:** citations above point to primary papers, author artifacts, official documentation or the organization reporting its own deployment. Preprints are identified as such; repositories without a dated release are identified by inspection date. Numerical performance/adoption results are author/vendor reports, not reproduced measurements. The detailed Trivet implementation/limitations were inspected in its [full HTML, September 2026](https://arxiv.org/html/2609.19583v1); several other entries rely on primary abstracts plus artifacts rather than a full replication. Search included 2024 predecessors as well as 2025–2026 results; a 2023 preprint can have a 2024 venue publication.

**I — Why the remaining gaps are hard:** specification intent is external to the checker; semantic frontends can be wrong; independently accurate models of dependencies/FFI/hardware are costly; a solver's unknown region may cover the valuable workload. These are not all proposal-labor problems. A claim that the LLM writes a model and another tool verifies that model must expose the unproved link to the actual program.

**I — Three useful operating modes:** (a) model chooses among already legal transformations, as in scheduling over fixed rules; (b) model invents a candidate and a checker proves its obligation; (c) model invents proof ingredients to make a formerly expensive check feasible. Mode (c) is the deeper economic flip, but Trivet, alive-next, LEMUR and the proof-agent literature already occupy it. Select a workload and maintain its acceptance boundary rather than claiming the mode itself.

**I — No universal claim of checker invulnerability is warranted.** A trusted kernel can reject an invalid proof while accepting a proof of the wrong theorem. A correct bounded checker can miss an out-of-bound bug. A correct type checker can accept a uselessly dynamic annotation. A complete runtime comparison on a finite corpus can miss behavior outside that corpus. Report exactly which of these was obtained.

## Ranked top 3

1. **§3 — Qualify and maintain source-native rewrite queues with existing translation validators. I:** strongest semantic oracle and a natural old-program reference; stronger models help manufacture candidates and proof decompositions. **Gap status:** conditional integration opportunity, heavily contested by Alive2, alive-next, Trivet, Aqueduct and optimizer agents. No claim of an unoccupied method or established customer demand. A versioned, reproducible native acceptance workflow must save expert time beyond those tools.

2. **§8 — Maintain precise third-party type boundaries for one dynamic framework. I:** clearest directly sourced user pain, cheap iteration and a realistic small-tool surface. **Gap status:** conditional package/framework maintenance opportunity; TypeT5/OpenTau/TypeCare and checker teams already do much of the work. The oracle is materially weaker than §3, so sell measured improvement in bug detection/valid-client support rather than verified runtime equivalence.

3. **§5 — Qualify one underserved compiler extension using generated conventional fuzz machinery. I:** real compiler bugs, independent reference execution and an understandable specialist buyer. **Gap status:** conditional service/upstream tool; MetaMut/LegoFuzz/IssueMut and smaller-language campaigns occupy the generic architecture. The differentiator must be a feature's definedness/reference semantics and reduced triage effort.

**I — Ranking rationale:** oracle quality, evidence of remaining pain, ability to build a decisive solo experiment, survival against a much better model, and distance from direct prior art. These are not predicted market sizes. None currently clears every part of the round-one winner's bar.

## The ONE bet

**I — Run a customer-bound experiment for §3: maintained translation validation of agent rewrites in one existing native library.** Start from a real team's rejected or expensive-to-review rewrite backlog. Reuse Alive2 and, where semantic coverage permits, alive-next/Trivet. The agent proposes code and proof decompositions; acceptance is independently replayed for the exact input/output IR, original contract, flags and semantic profile. Supported cases are proved, bounded cases remain labeled bounded, tests remain labeled tests, and unknowns remain unaccepted.

**I — The ambition:** let a team accept a much larger stream of aggressive refactors/optimizations while retaining the existing program as specification and keeping expert qualification effort bounded. Better models increase the stream and can produce the proofs; they do not remove the need to bind evidence to the actual artifact and supported semantics. This is a narrow path to maintained compiler/verification infrastructure, not evidence for a new general optimizer company.

**E — One engineer, two weeks:**

- **Days 1–2:** obtain twenty real rewrite pairs and one later source revision from a willing team; freeze build/contract/environment semantics and exclusions. Stop the business experiment if no team has this problem; synthetic cases can test mechanics only.
- **Days 3–5:** extract actual IR pairs and integrate existing validators with typed proved/bounded/refuted/unknown outcomes. Freeze reference inputs and checker configuration outside agent writes; retain complete obligations and logs. No new semantic core.
- **Days 6–9:** let a normal agent and the structured proof workflow process budget-matched pairs. Reuse direct validators as controls. Record every human semantic intervention and all failed candidate/proof cost.
- **Days 10–12:** replay evidence, change source/flags/version, and check invalidation. Inject at least twenty relevant semantic mutants: overflow, aliasing, omitted effects, strengthened assumptions, wrong result, out-of-bound loop behavior and edited proof obligations. Explicitly refuse unsupported categories.
- **Days 13–14:** have the customer review the artifacts and compare saved specialist minutes, accepted useful coverage and measured whole-workload performance. Ask what existing expense a next paid pilot replaces.

**E — Continue only if** at least three useful real rewrites are qualified, no supported-domain semantic mutant is accepted as proved, an actual version change is handled without hidden assumptions, and expert qualification time falls ≥50% against existing validators plus an ordinary agent after including setup. For a performance sale, require a credible end-to-end saving with amortized search/verification/integration costs; proof count alone is insufficient. At least one customer must prefer a paid $10k–20k continuation to using the baseline tools themselves. A two-week mutant result is a qualification of the prototype, not a soundness theorem.

**I — The decisive expert objection:** “alive-next already supplies agents, decomposition and replayable certificates; Trivet already supplies proof scaffolds; your only addition is a queue.” If the experiment cannot show that source/build/version integration closes a real recurring acceptance gap, accept that objection and contribute the useful integration upstream. Do not retreat to selling the generic proposer/checker slogan.

## Five-line TL;DR

1. **F/I:** The revival is already happening: CEGIS, egg guidance, Alive2 optimization, invariant/ranking synthesis, LiquidHaskell, separation logic, decompilation, fuzzing and repair all have direct LLM prior art.
2. **I:** The deeper flip is letting models propose proof decompositions and invariants, but Trivet/alive-next/LEMUR already occupy that architecture; checking can still be the costly step.
3. **F/I:** Compilation, clean Infer output, green typing and passed fuzz tests are different from a semantic proof; modern primary sources document contract escape, decompiler divergence and weak-boundary failures.
4. **I:** Rank the remaining conditional opportunities as native rewrite qualification, precise framework type boundaries, and feature-specific compiler fuzzing; none is demonstrated market whitespace.
5. **I/E:** Bet one two-week customer experiment on maintaining native rewrite evidence across changes, and kill it unless it beats existing validators plus a normal agent in useful coverage and expert time.

## Rejected ideas — one-line reasons

- **I — Generic LLM CEGIS engine:** direct research/artifact coverage; semantics and intent are the scarce input.
- **I — Let LLM-written equations enter egg directly:** e-graphs preserve consequences of their rules and do not certify new rules' truth.
- **I — Another LLM-guided EqSat scheduler:** LGuess/EggMind occupy guidance and ASPEN proposes checked new rules; retain only a real DSL integration.
- **I — Generic LLM superoptimizer:** Iago, LLM-VeriOpt, Meta LLM Compiler and AlphaEvolve cover the obvious revival.
- **I — Generic agent-written translation proofs:** Trivet and alive-next are direct prior art, including structured decomposition and replay.
- **I — Claim proved native optimization after a test-validated Lean port:** the translation boundary stays empirical, even if subsequent Lean equivalence is proved.
- **I — Recompilation as a sufficient decompilation oracle:** compiling plausible code can erase behavior/vulnerabilities; DecLLM and Decompile-Diverge already map the gap.
- **I — Online LLM replacement for Csmith/YARPGen:** validity and per-test throughput can regress; generator/mutator synthesis already exists.
- **I — Generic invariant or termination copilot:** LOOPY, LEMUR, Quokka, LimICE and ACL2 work already implement it.
- **I — Generic refinement annotation agent:** LHC is a nearly exact prior implementation; maintained public-contract value needs a buyer.
- **I — Type migration measured by error count alone:** broad types, ignored errors and narrowed checking scope can make the result vacuous.
- **I — Infer silence as proof of patch safety:** Pulse explicitly documents unknown-call approximations and missed bugs.
- **I — Generic separation-logic specification generator:** Spec-Agent, VeriFast studies, SPLIT and Aria already cover generation/proof assistance.
- **I — Universal automatic parallelizer:** directive generation is occupied; aliasing, numerical semantics and concurrency still constrain the checker.
- **I — Generic semantic grammar decoder:** ChopChop and the October 26 AGDecode preprint directly occupy the mechanism.
- **I — Futamura-as-prompt-compilation product:** a fixed prompt is not a checked semantic program; agent JIT/incremental agents were already covered in the required prior report.
- **I — Another partial evaluator from scratch:** weval and existing staging machinery are concrete baselines; LLM labor savings alone do not establish demand.
- **I — Generic GenProg revived by LLMs:** CodeMender, Meta's repair evaluation and normal coding agents already execute the proposal/feedback loop.
- **I — A universal verification dashboard:** combining check marks does not close semantic gaps between their claims; no specific paid workflow was established.
