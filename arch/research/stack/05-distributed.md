# Round 10 · 05-distributed · 2026-10-28

**I — Recommendation:** run a two-day kill test for **Causal Command Diff**: replay captured Messages through an agent PR's pure update function, compare the Commands it proposes, and stop when the recorded future ceases to be causally valid. The useful demo is “this change would send a second receipt,” with the Message and command arguments that explain it. Foldkit already has capture-to-Story work, so the recommendation is an upstream causal-correlation/comparison contribution, not a separate new testing category.

**I — Research verdict:** of three examined finalists, only two retain a conditional contribution-sized scope. The Hydro proof candidate is rejected: an open PR already implements it. Foldkit also already has session-export work, so A is a contribution around causal correctness and comparison, not a claim to have invented capture-to-test. Generic schema generation, agentic protocol verification, TypeScript deterministic simulation, massively concurrent actors, and protocol optimization all have substantial direct prior art. The most interesting flip is making network behavior explicit and mechanically checkable in ordinary applications. The remaining work is connecting trustworthy checks to actual effects and implementation boundaries.

## 1. What changed at this layer

### Schemas are becoming ordinary infrastructure; temporal semantics are the hard part

**F —** MCP's **2026-07-28** release changed its core to stateless requests, introduced Multi Round-Trip Requests, and formalized extensions. Its maintainers reported nearly **half a billion monthly downloads** across Tier 1 SDKs, with TypeScript and Python each exceeding a billion cumulative downloads. These are package downloads, not unique agents, running services, or proof of AI authorship. The core is already designed to remove transport-session affinity; proposing “stateless MCP for agents” would be stale. [Release announcement, 2026-07-28](https://blog.modelcontextprotocol.io/posts/2026-07-28/).

**F —** The current OpenAPI document is **3.2.1, dated 2026-09-10**. AsyncAPI's current documentation includes **3.1.0**, operations, messages, correlation identifiers, and request/reply descriptions. Arazzo **1.1.0, dated 2026-05-17**, describes workflows and explicit dependencies for asynchronous operations. “OpenAPI describes individual shapes, therefore nobody describes API sequences” is an invalid premise. [OpenAPI 3.2.1](https://spec.openapis.org/oas/v3.2.1.html), [AsyncAPI 3.1.0](https://www.asyncapi.com/docs/reference/specification/v3.1.0), [Arazzo 1.1.0](https://spec.openapis.org/arazzo/v1.1.0.html).

**F —** Specmatic already combines schema-based tests, stubs, compatibility checks, stateful mocks, Arazzo, and an MCP interface for coding agents. Schemathesis already chains operations into stateful workflows. Buf already distinguishes generated-source compatibility from protobuf binary and JSON wire compatibility. These tools kill a generic “every agent-written service gets a schema and generated tests” project. [Specmatic agent workflow, 2025](https://specmatic.io/updates/specmatic-mcp-as-guardrails-for-coding-agents-api-spec-to-full-stack-implementation-in-minutes/), [Specmatic feature boundaries](https://docs.specmatic.io/references/open-source-vs-enterprise), [Schemathesis](https://schemathesis.io/), [Buf breaking checks](https://buf.build/docs/breaking/).

**I —** The economic change is the cost of authoring and maintaining the per-service descriptions, adapters, and fixtures. It does not make the intended contract available automatically. An agent can faithfully generate a schema for an incorrect implementation. There is no independently verified percentage of agent-authored distributed-service code in the sources inspected here; download growth should not be substituted for that number.

### Formal methods and deterministic simulation have already acquired agents

Its repository now documents persistent models and incremental CI verification. This is direct competition for the entire generic autonomous-formal-methods loop, not just a paper about prompting. [Agent testing and mutation work](https://antithesis.com/blog/2026/mutation-testing/), [JavaScript support](https://antithesis.com/docs/reference/sdk/javascript_sdk/).

**F —** There is also a published TypeScript/Node DST framework, **Chronos**. Its existence kills “FoundationDB testing, but for TypeScript” as an unoccupied idea; its marketing claims are not a measured guarantee for arbitrary Node programs. ## 2. Hydro and Infinity: what is actually checked

### Hydro is the strongest version of the rigor thesis in this lens

**F —** Hydro expresses distributed locations and communication in one Rust program. Its collection types carry ordering, delivery/retry, boundedness, and consistency information. Its dataflow substrate is now called **DFIR**; treating Hydroflow and the high-level Hydro API as interchangeable obscures the layers. The research lineage includes **Flo, POPL 2025**, and **Optimizing Distributed Protocols with Query Rewrites, SIGMOD 2024**. The latter reports manual rule-driven improvements of **5× for 2PC** and **3× for Paxos**, not an autonomous agent's general optimization result. [Repository](https://github.com/hydro-project/hydro), [research publications](https://hydro.run/research/).

**F —** The important limit is in the proof-obligation documentation. Machine-checked Verus obligations currently cover **commutativity**. **Idempotence, monotonicity, and order preservation accept manual written justifications.** The simulator does not trust these annotations and explores supported nondeterministic choices anyway. A green ordinary Rust build is therefore not a universal proof of distributed correctness. Verus verification is a separate invocation. [Proof obligations](https://hydro.run/docs/hydro/reference/correctness/proof-obligations/).

**F —** Source inspection confirms the distinction: at Hydro commit `116d5b2420a5fcd0ebdc84e40cd84106c72ab32c`, `VerusCommutativeProof` implements the commutativity mechanism, while `IdempotentProof` is implemented by `ManualProof`. The exported Verus macros cover fold, map, filter, and effect closure shapes. This is a gap on main, not evidence of an unoccupied project: open draft PR **#3214, opened 2026-10-04**, already implements actual-body Verus idempotence proofs, and open PR **#3236, opened 2026-10-16**, covers monotonicity and order preservation. C is rejected on that direct prior art. [Idempotence PR](https://github.com/hydro-project/hydro/pull/3214), [monotonicity/order-preservation PR](https://github.com/hydro-project/hydro/pull/3236). [Pinned implementation](https://github.com/hydro-project/hydro/blob/116d5b2420a5fcd0ebdc84e40cd84106c72ab32c/hydro_lang/src/properties/mod.rs).

**F —** Hydro already has simulation, explicit scheduling hooks, exhaustive and fuzzing modes, and merged **multi-version simulator support**. Its simulation documentation lists limitations, including unsupported `assume_retries::<ExactlyOnce>` observations. **Cress**, a **draft PR opened 2026-10-10**, goes further: delay a decision point and measure whether retry work amplifies. Its example raises sends from **250 to 746** for a three-attempt client; these are the PR author's test results. Cress is a draft Hydro checker; its stated timer and hook limitations matter. [Simulation support](https://hydro.run/docs/hydro/reference/simulation/), [multi-version PR #2945](https://github.com/hydro-project/hydro/pull/2945), [Cress draft #3222](https://github.com/hydro-project/hydro/pull/3222).

**I —** Consequently: use Hydro as prior art and a contribution destination. Do not pitch a new correct-by-construction agent language, a protocol optimizer, rolling-version simulation, or a retry-amplification visualizer as an empty space.

### Infinity changes the unit of scheduling, not the laws of effects

**F —** Infinity describes agents between turns as stored conversation data, with no live stack or connection. Its **75,000 agents on a Raspberry Pi** claim is about fitting waiting agents in memory. It does not show 75,000 simultaneous model completions, active tool operations, durable replicas, or production throughput. The inspected repository has **193 stars** and an Apache-2.0 license. [Infinity README](https://github.com/hydro-project/infinity).

**F —** Its architecture serializes slices within a conversation using FIFO message groups and runs different conversations concurrently. It records processed message IDs, flushes a tool call into history before dispatch, and receives tool results as subsequent messages. On AWS it uses SQS FIFO groups; embedded execution uses per-thread channels. These are specific runtime assumptions, not properties bestowed merely by being a Hydro project. [Infinity architecture](https://infinity.hydro.run/docs/infinity-runtime/architecture/).

**F —** RAP acknowledges invocations independently of asynchronous completion and delivers results to callback URLs. Transient delivery retries are recommended. Cancellation is advisory, may race with a result, may never arrive, and must not be relied on for correctness. Its subscription messages correlate to a subscription's `tool_call_id`; the listed required fields do not define a distinct mandatory occurrence ID. [Transport](https://infinity.hydro.run/docs/rap/spec/basic/transport/), [cancellation](https://infinity.hydro.run/docs/rap/spec/basic/tool-cancellation/), [subscription events](https://infinity.hydro.run/docs/rap/spec/server/subscription-events/).

**I —** A subscription ID cannot simultaneously serve as an identity for every distinct event and a deduplication key for delivery retries. A bridge needs a separate occurrence identity when its source offers one, or an explicit weaker guarantee. This is an integration requirement, not a reproduced Infinity defect.

**F —** RAP also already specifies session migration and an MCP compatibility proxy. The migration contract leaves the tool's state-transfer mechanism to its implementation. The compatibility guide describes both persistent local connections and fresh Lambda connections; its session-handshake discussion describes the older MCP lifecycle. It should not be used to claim that current MCP necessarily requires transport sessions or lacks asynchronous Tasks. [Migration](https://infinity.hydro.run/docs/rap/spec/basic/migration/), [MCP compatibility](https://infinity.hydro.run/docs/rap/about/mcp-compatibility/), [current MCP release](https://blog.modelcontextprotocol.io/posts/2026-07-28/).

### Where deterministic simulation's rigor stops

**F —** FoundationDB runs real cluster logic in a controlled single-threaded simulation, combined with live performance and hardware testing. TigerBeetle's **2026-08-20** discussion explains protocol-aware checks inside replicas, in addition to external safety and liveness observations. MadSim explicitly requires replacing I/O interfaces and eliminating uncontrolled uncertainty. These are architectural commitments, not an assertion that a fake clock makes any service deterministic. [FoundationDB](https://apple.github.io/foundationdb/testing.html), [TigerBeetle](https://tigerbeetle.com/blog/2026-08-20-protocol-aware-dst/), [MadSim](https://github.com/madsim-rs/madsim).

**F —** Edge runtimes have this work too. celld documents differential Workers/DO API tests against workerd, model-checked coordination, deterministic simulation, and fleet fault injection. A third-party “prove Durable Objects' runtime guarantees” package would compete with the runtime owner on its own oracle. [celld testing](https://github.com/denoland/celld/blob/main/docs/testing.md).

**I —** “DST for every agent-built service” becomes plausible when the agent builds against replaceable clock, entropy, transport, and storage boundaries from the outset. Retrofitting arbitrary dependency trees remains expensive. Passing simulated schedules proves neither the external service model nor behavior outside the declared fault model. Safety checks need a separate recovery/progress phase under stated fairness and availability assumptions.

## 3. What a million agents stresses

**I —** The old problems become frequent operational paths: ambiguous outcomes, event identity, retention, partial failure, and version overlap. No new consensus algorithm is required to explain them.

- **I — Transport completion versus effect completion.** A response can disappear after the effect commits. A canceled request need not mean canceled work. The application needs a state such as `unknown after dispatch`, separate from `not dispatched`, plus a documented recovery path.
- **I — Identity across layers.** Distinguish logical operation, transport attempt, event occurrence, delivery attempt, subscription, and conversation. Reusing one ID for these roles can either duplicate effects or suppress legitimate events. Hashing arguments cannot distinguish a retry from an intentional repetition.
- **I — Backpressure moves to the inbox.** Eliminating a waiting stack removes one concurrency limit. It does not bound callback bursts, durable queue length, model tokens, or children spawned per event. Admission limits, deadlines, and cancellation ownership must survive process death.
- **I — Retention becomes part of the protocol.** A dedup entry expiring before the oldest possible retry changes semantics. A cursor beyond retained history needs a gap/resynchronization result. An old callback arriving after an extension upgrade needs an explicit version interpretation.
- **E — Scale example, not an observed workload.** One million agents producing one event per 100 seconds yields **10,000 events/second**. One KiB of pending-operation metadata each consumes about **0.95 GiB**, before histories, indexes, replicas, and payloads. Zero idle compute is not zero system cost.
- **E — Fan-out example.** With independent 1% slow-call probability, 100 parallel calls have a **63.4%** chance that at least one is slow: `1 - 0.99^100`. Correlated faults can be worse; this is not a performance measurement.

**F —** A Durable Object's local storage/coordination does not remove these external boundaries. Alarms have at-least-once execution, with bounded automatic retries. Cloudflare documents interleaving around asynchronous work and explicit coordination controls. Cloudflare Computer's Cap'n Web lifecycle documentation distinguishes session death from durable filesystem reconciliation and prohibits treating arbitrary shell execution like a replayable synchronization batch. [DO alarms, updated 2026-04-21](https://developers.cloudflare.com/durable-objects/api/alarms/), [DO rules, updated 2026-10-18](https://developers.cloudflare.com/durable-objects/best-practices/rules-of-durable-objects/), [Computer lifecycle](https://github.com/cloudflare/computer/blob/main/docs/11_lifecycle.md).

**F —** Cap'n Proto has schemas and promise pipelining; Cap'n Web explicitly has **no schemas**, while integrating with TypeScript and providing pipelining. Their connections and capability lifetimes are separate from application persistence. “Add batching/pipelining to save agent RPC round trips” is already implemented. TypeScript type agreement is also not runtime input validation. [Cap'n Proto RPC](https://capnproto.org/rpc.html), [Cap'n Web](https://github.com/cloudflare/capnweb), [runtime validation guidance](https://github.com/cloudflare/capnweb/blob/main/packages/docs/src/content/docs/guides/validation.mdx).

**F —** The classic receiver-side solution is also old: RIFL couples request identity and completion records to the protected mutation, moves that metadata with the object, and manages its lifetime. That result does not automatically cover an unrelated external tool. [Lee et al., SOSP 2015](https://web.stanford.edu/~ouster/cgi-bin/papers/rifl.pdf).

## 5. Finalist A: Causal Command Diff

**I — One sentence:** show precisely how a PR changes the effect intents of a callback-heavy state machine, using captured real inputs and their causal connection to the requests that produced them.

**I — 30-second demo:** a captured checkout receives price and inventory replies in either order. The baseline proposes one receipt. An agent PR introduces a duplicate receipt after an inventory callback. The comparison shows two receipt Commands instead of one and points to the triggering Message. A harmless reordering of explicitly independent lookups passes. A second PR changes the price request from SKU A to B: replay stops there and marks the old price reply unavailable, instead of fabricating a completed checkout for B using A's price.

**F — Closest prior art:** Foldkit already records Message history with command names/arguments and supports replay. Its serializer exports `name`, `args`, and submodel path; it does not serialize the command implementation. Story tests can resolve a specific command instance using name and arguments. Its current `applyMessage` refuses a new Message while Commands remain unresolved, so production traces with interrupts or multiple outstanding requests cannot simply be pasted into the ordinary Story sequence. [Pinned serializer](https://github.com/foldkit/foldkit/blob/b702a5efbb74bebc056b798b414ddb923a82fbd5/packages/foldkit/src/devTools/serialize.ts), [pinned Story implementation](https://github.com/foldkit/foldkit/blob/b702a5efbb74bebc056b798b414ddb923a82fbd5/packages/foldkit/src/test/story.ts).

**F —** Temporal already rejects replay when generated Commands disagree with workflow history. Replay.io already rerecords a changed frontend with original interactions and captured network responses. Maple already groups and scrubs Foldkit command spans. Merely capturing commands, replaying inputs, or comparing old/new behavior is existing work. [Temporal](https://docs.temporal.io/references/workflow-task-errors), [Replay, 2024-11-26](https://replay.io/blog/rerecording), [Maple Foldkit instrumentation](https://maple.dev/docs/sdks/effect-foldkit/).

**F — Additional direct prior art:** Foldkit issue **#622, opened 2026-07-04**, requests exactly session capture to Story. Its author says they have a production app ready to use it; the API reports **three comments and one reaction**. Two comments explicitly disclose agent authorship at a user's request, so they are not independent customer confirmations. Open **PR #626**, also opened **2026-07-04**, implements the lowering half. Its stated strategy pairs the oldest pending command with the next Message; its description explicitly leaves concurrent correlation and live export to follow-up work. The diff inspected here agrees with that description. [Request](https://github.com/foldkit/foldkit/issues/622), [existing implementation PR](https://github.com/foldkit/foldkit/pull/626).

**I — Narrow gap:** causal correlation and an intent-comparison mode around the existing capture-to-Story work, potentially extracted into a local CI package that compares two pure update functions over versioned, causally linked Message/Command traces, without requiring the app to become a durable workflow. Its useful additions would be causal stopping, preserved multiplicity, and explicit comparison policy. Capture/export, command descriptors, and Story promotion are already requested or implemented in open work. No independent product gap is claimed for those pieces. General Effect programs are outside v1: an `Effect` value can contain arbitrary behavior, and is not automatically an inspectable command AST.

**F/I — Pain and beneficiary:** frontend/edge developers maintaining async state machines are the beneficiary. Issue #622 supplies one explicit production-user request for capture-to-test; issue **#720, opened 2026-07-13**, documents missing subscription lifecycle/provenance and the need to distinguish registration and execution generation. This supports the causal-capture prerequisite. Demand specifically for a cross-version production comparison gate remains unverified, and lost-response incidents do not prove an intent comparator would catch them. That keeps Value at 3. [Subscription provenance request](https://github.com/foldkit/foldkit/issues/720).

**I — The acceptance check:** freeze the capture, baseline build, schema versions, and comparator policy separately from the agent PR. Replay from an application-decoded initial Model; compare command type, resource/logical operation, and canonicalized arguments while retaining multiplicity. Match a result to a pending command instance and its request fingerprint, not its tag alone. Compare sequences by default; ignore relative order only inside independently justified groups. Include OutMessages and declared subscription start/stop intents when supported. An unpaired result, redacted value necessary for a decision, unknown message version, or changed prerequisite stops that branch with an explicit unsupported/diverged result. An expected intentional behavior change needs an explicit reviewed acceptance update.

**I — How an agent could game it:** retain the command's name/arguments while changing its interpreter; smuggle effects into `update`; change the comparison normalizer; label every command independent; or preserve a bug already present in production. Thus this check establishes **intent regression on captured valid prefixes**, not external effect equivalence or business correctness. Changed interpreters require boundary-level request/effect checks, such as B. Purity enforcement, isolated execution, and independently owned business invariants are prerequisites for stronger acceptance claims; repeatability alone does not prove purity. A green result must say what was actually compared.

**I — Better models:** stronger models can write more application variants and collector adapters, but cannot recover a response for a request never made. Captured customer behavior and the distinction between an intended and unintended effect change remain useful. No model is needed to replay or compare.

## 9. Self-extension and the rigor flip

**I —** The useful self-extension pattern is to grow a **versioned protocol fragment**, not install an arbitrary function and assume a schema makes it safe. Each proposed tool or callback handler must name its accepted inputs, emitted intents, owned resources, delivery/retry assumptions, and behavior for already-pending operations. The extension's acceptance check should be outside the proposing agent's edit authority.

**I —** A checks recorded valid prefixes against the new handler. B checks a finite corpus of handoff schedules against a real ledger. The existing Hydro work considered under C can discharge a narrow algebraic law for a reducer. None establishes that all possible future workflows remain valid. A finite state protocol model or session-type projection can add communication checks only under its explicit topology, fault, and participation assumptions. STScript predates agents; the 2026 dynamic/failure work shows that combining state evolution, exceptions, and liveness is an active problem, not a free consequence of generated code.

**I —** The statement “every service should ship a machine-checkable protocol spec” is most useful as a graduated engineering rule: schema and version compatibility for payloads; executable lifecycle and resource obligations for async work; captured behavioral regression checks; then simulation or proof where the service controls the necessary semantics. A proof of an agent-invented, weakened specification is a green result with little authority. The contract's owner, actual-body connection, coverage exclusions, and independent negative controls are part of the deliverable.

**I —** For the brief's ambiguous **“bb”**, I assume **babashka**, not a particular unidentified agent. **F:** babashka's executable is `bb`, it loads source libraries, and its pod protocol connects external binaries. **I:** the relevant historical pattern is a stable host with small replaceable extensions, much like Lisp/Emacs images; it supplies no automatic distributed recovery contract.
