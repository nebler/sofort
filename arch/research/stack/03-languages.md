## Verdict

Show the offending sequence and the scope of the observation. The interesting artifact is the small, human-owned contract and its connection to real execution. ## What changed at this layer in 2025–26

- **F — Code volume can outrun human review.** Anthropic reports growth from about 2,500 merged changes/day in May 2026 to over 30,000 in September, and says engineers increasingly review change intent. This is one unusually intensive agent user, not a population-wide productivity estimate. **I — That makes compact descriptions of allowed behavior more valuable than increasingly elaborate type puzzles.** [Anthropic, 2026-10-13, updated 2026-10-15](https://www.anthropic.com/research/redesigning-source-control).
- **F — Annotation labor really is becoming automatable on bounded tasks.** Faria et al. report correct annotation generation on 98.2% of 110 Dafny programs within eight repair iterations, using tests as specification oracles. **I — This supports cheaper proof assistance, not the disappearance of specification review.** It cannot be compared directly with DafnyBench's older 68% result: the datasets and tasks differ. [Faria et al., 2026-01-19](https://arxiv.org/abs/2601.12845), [DafnyBench, January 2025](https://popl25.sigplan.org/details/dafny-2025-papers/15/DafnyBench-A-Benchmark-for-Formal-Software-Verification).
- **F — Autonomous formal modeling is already an active implementation area.** Specula's authors report 249 bugs across 48 open-source systems using generated TLA+ models. P now advertises PeasyAI for model generation and PObserve for log monitoring. **I — “An agent writes TLA+/P” fails the gap test.** [Specula, submitted 2026-07-28, revised 2026-08-03](https://arxiv.org/abs/2607.25333), [P project, inspected 2026-10-28](https://p-org.github.io/P/).
- **F — Specification defects remain concrete.** MutDafny evaluates 40 mutation operators on 794 Dafny programs and identifies five weak real-world specifications in its manually analyzed subset. DafnyCOMP studies 300 composed programs and reports substantial degradation across function boundaries. **I — Cheap local annotations do not imply cheap, trustworthy whole-application specifications.** [MutDafny, 2025-11-19; revised 2026-04-12, ICSE 2026](https://arxiv.org/abs/2511.15403), [DafnyCOMP, 2025-09-27](https://arxiv.org/abs/2509.23061).
- **F — The usable application boundary has improved.** Foldkit makes `update` return a Model and Commands, with Story/Scene checking without executing Command Effects. Alchemy puts infrastructure and application Effects in one program. **I — These give agents more explicit structure to populate and reviewers more stable boundaries to inspect. They do not make arbitrary TypeScript pure or prove infrastructure behavior.** [Foldkit testing](https://github.com/foldkit/foldkit/blob/b702a5efbb74bebc056b798b414ddb923a82fbd5/packages/website/src/page/testing.md), [Alchemy](https://alchemy.run/what-is-alchemy/), inspected 2026-10-28.

**I — The rigor flip is partial.** Generating cases, types, schemas, annotations, and adapters gets cheaper. Choosing the right property, validating the abstraction, preserving compiler semantics, bounding the state space, and understanding a counterexample still cost effort. Models can help with that effort; their agreement is not an independent acceptance check.

## Which specification forms pass the cost / strength / readability test?

**I — Best default:** a closed vocabulary of observable operations, a few relational or frame conditions, and a small per-entity lifecycle. Keep arithmetic explicit, preferably bounded integer units. Generate readable tables and concrete examples from the same structured contract. Preserve an independently approved baseline when the agent changes implementation.

**E — Authoring budgets below are targets for small features, not measured model performance.** “Readable” means a domain owner can explain a permitted and a forbidden example without opening implementation code; that must be tested with people.

| Form | Cheap authoring unit / mechanical check | What a human can assess | Important boundary |
|---|---|---|---|
| **F/I: Effect errors and requirements** | Explicit `Effect<A, E, R>`, tagged error unions, service interfaces; ordinary TS checking. | Expected failures and services required at that boundary. | `E` excludes defects/interruption. `R` describes required services, not operations executed, multiplicity, or authority. Internally providing a service can remove it from outward `R`. |
| **I/E: Restricted refinements** | Roughly 5–20 predicates over bounded integers/enums; SMT implication or exhaustive finite checking. | `0 <= refund <= captured - refunded` is concrete. | JS numeric semantics and missing inputs matter. An arbitrary Schema/Zod predicate is executable JS, not automatically an SMT formula. |
| **I/E: Pre/postconditions plus frames** | Roughly 3–10 clauses over before/after snapshots; check every admitted patch or operation. | Which fields may change; required result; preserved data. | Checking only the result misses destructive overachievement. External writes must pass through the checking boundary. |
| **F/I: Session types / typestate tables** | A small graph plus correlation guards; deterministic monitor or a finite model. | “After cancellation, no new dispatch for this request”; allowed retry states. | Finite traces establish safety on observed executions. Eventual completion needs terminal obligations, time/fairness assumptions, or separate model analysis. |
| **F/I: Property specifications** | A few laws: roundtrip, conservation, idempotence, monotonicity; generators and shrinking. | A named law with a positive case and a violating case. | Sampling is not a proof. A property inferred from the buggy code can preserve the bug. Generic synthesis/testing is already occupied. |
| **F/I: TLA+ / Quint / P / Alloy** | Reuse an existing modeling language and checker; explicitly name finite scopes, environment, and fairness. | State transitions and counterexample traces, with coaching. | The checked model and real implementation must be connected. Alloy offers temporal analysis too; the choice is not “logic versus runtime.” |
| **F/I: Lean / Dafny / F* / Verus** | Suitable for a stable core: patch interpreter, accounting function, parser, monitor. | Small mathematical statements can be trusted after domain review. | Proof checks a statement under assumptions. The specification, foreign functions, extraction/compilation, and admissions remain part of the trust story. A whole-app proof remains a larger project. |
| **F/I: TS as an architecture checker** | Discriminated unions, exhaustive matches, mapped registries, `satisfies`, dependency rules. | Every Command has a declared handler/policy; prohibited imports stay absent. | TypeScript explicitly permits unsound behavior. Casts, inaccurate declarations, mutable aliases, and host APIs prevent treating it as a general proof kernel. |
| **I/E: Bounded macro definitions** | New names expand through a finite DAG into a fixed typed core; cap expansion and check frames/operation budgets. | Fully expanded behavior and its allowed write surface. | Macro hygiene/type preservation alone says nothing about effect authority. Arbitrary compile-time JS would enlarge the trusted execution surface. |

**F — Sources for these boundaries:** [Effect expected errors](https://effect.website/docs/v4/error-management/expected-errors), [TypeScript compatibility and soundness](https://www.typescriptlang.org/docs/handbook/type-compatibility), [P monitors](https://p-org.github.io/P/manual/monitors/), [Alloy documentation](https://alloytools.org/documentation.html), [F* tutorial](https://fstar-lang.org/tutorial/book/part1/part1_getting_off_the_ground.html), [Lean recursive definitions](https://lean-lang.org/doc/reference/latest/Definitions/Recursive-Definitions/), [Verus guide](https://verus-lang.github.io/verus/guide/), [Turnstile typed macros](https://docs.racket-lang.org/turnstile/The_Turnstile_Reference.html). Documentation inspected 2026-10-28. **F — Verus explicitly excludes verifying Rust/LLVM and the verifier itself from its current goals; formal verification should not silently inherit a stronger end-to-end claim.**

**I — Three separate checks are necessary.** A contract must be well formed and non-vacuous; implementation observations must conform to it; changes to the contract must receive their own review. None establishes that the original business requirement was correct. An agent may propose all three artifacts, but its permission to change the authoritative contract must differ from its permission to repair the implementation.

## Finalist A: Command-law gate for pure update functions

**I — One sentence:** turn a real Foldkit interaction into a review artifact that says exactly which Command requests an agent PR changed and which separately approved laws those requests violate.

**I — 30-second demo:** reproduce checkout, including a duplicated completion Message. Open a proposed change that updates the page correctly but requests a receipt twice. Run the gate. It shows the four Messages, the extra `SendReceipt(orderId)`, and the violated “at most one receipt request per completed order” law. A benign view refactor remains clean. Export the witness as a Story using existing exact Command assertions.

**F — Closest prior art:** Foldkit's `Command` has `name`, optional `args`, and an arbitrary `Effect`; Story exposes `expectExact`. Its DevTools integration records Command requests and result Messages. Issue #622 asks for a portable session and Story lowering; the basic workflow is already conceived upstream. FSL's effect dialect handles correlation, lifecycle ordering and duplicate irreversible completion. Quint's TS adapter generates traces, dispatches them into a driver, and can compare states. [Foldkit source](https://github.com/foldkit/foldkit/blob/b702a5efbb74bebc056b798b414ddb923a82fbd5/packages/foldkit/src/command/index.ts), [DevTools integration](https://github.com/foldkit/foldkit/blob/b702a5efbb74bebc056b798b414ddb923a82fbd5/packages/foldkit/src/runtime/devToolsIntegration.ts), [FSL effects](https://github.com/ymm-oss/fsl/blob/1844fa74a717ba9229e0b292d9421c0939016e5e/docs/design/DESIGN-effect.md), [Quint adapter](https://github.com/dearlordylord/quint-connect-ts), inspected 2026-10-28.

**I — Gap:** I did not find a complete Foldkit integration that imports an interaction, runs both reducer revisions, preserves Command multiplicity/payloads/correlation, checks a human-owned contract, and emits a concise PR artifact. That is a bounded search result. The implementation could be small precisely because the constituent machinery exists. “We record Commands” or “we generate Story tests” alone fails the gap test.

**F — Named beneficiary and pain:** Foldkit app maintainers. The author of #622 says a production app would use session export; a separate commenter on 2026-07-29 reports difficulty connecting e2e-discovered bugs back to Story/Scene and establishing trust in those tests. At inspection, #622 was open with **one reaction and three comments**. Two later comments explicitly identify themselves as agent-generated relays of suggestions; they are not independent adoption evidence. [Issue](https://github.com/foldkit/foldkit/issues/622), [independent e2e comment](https://github.com/foldkit/foldkit/issues/622#issuecomment-5123169529). **I — This supports a useful contribution; it does not establish a large user population.**

**I — Trustworthy check:** the gate owns immutable input histories, normalization rules, schemas, and the approved law file outside the implementation edit. It compares request descriptors, including duplicates, plus selected state projections. Contract changes are reviewed separately using existing semantic-diff machinery. Add permitted and forbidden examples so “reject everything” does not count as success. Each result must distinguish observed-trace conformance, bounded generated exploration, and any stronger proof.

**I — Example review contract, illustrative rather than an existing API:**

```text
entity: checkout(orderId)
observe: Submit, ApprovalResult, PaymentResult, Cancel
request: RequestApproval, Charge, SendReceipt
Charge requires approved(orderId)
Charge.amountCents equals approvedAmountCents(orderId)
SendReceipt requires paymentSucceeded(orderId)
SendReceipt count <= 1 per orderId
Cancel before dispatch forbids later Charge for that request generation
required example: Submit -> approved -> Charge -> paid -> SendReceipt
```

**I — How an agent could game it, and the exact scope limit:**

- Change the mapper to omit a Command, map every order to one ID, or remove a payload field. Freeze the mapper and schema; unknown tags and missing correlations are unresolved failures.
- Normalize away duplicates or sort away semantically important order. Preserve multiplicity and order unless the reviewed contract declares a specific pair independent. Foldkit's order-independent exact assertion is not itself a declaration that every Command commutes.
- Change the `Effect` body while preserving `name` and `args`. **A descriptor diff cannot detect that.** Bind approved handlers to source/build digests and mark changed handler bodies outside assurance coverage. Stronger runtime enforcement needs trusted handlers or observation at the real host-operation boundary; merely hashing code does not prove its meaning.
- Emit a matching completion without a matching outstanding request. Treat that as a correlation error; never invent a resolver link. Versioned Model changes without an approved migration make the trace unrelatable.
- Hide a network read in `update`, omit Subscriptions/Mounts, or drop inconvenient histories. Purity/source checks, explicit boundary coverage and retention counters expose some omissions; the tool must not claim complete behavior when those boundaries remain unobserved.

**I — Better models:** useful changes can intentionally alter behavior even when perfectly implemented. Maintainers still need to see the operational difference and decide whether it matches their intent. The value comes from stable historical inputs and separately owned contracts, rather than a model's inability to write a unit test.

**I — Owner response:** Foldkit should probably adopt the session/export/assertion pieces. An outside OSS contribution can supply the cross-revision runner, FSL/Quint adapter and reusable contract examples. Cloudflare or Vercel could add a framework integration; a proprietary platform moat is implausible and unnecessary for this side project.

**E — 2–3-week v1:** days 1–3, capture one real bounded session and prove unchanged replay fidelity; days 4–7, compare two revisions with stable schemas and descriptor multiplicity; days 8–11, connect three to five reviewed laws to an existing checker; days 12–15, produce Story fixtures and a CI Markdown artifact. Run in Node CI; show the app through a normal Vercel/Workers deployment later. Do not put a new theorem prover into a Worker. Real Effect-body changes remain explicitly outside the descriptor check.

**I — Expert reply that kills it:** “`Story.expectExact` plus Copy to Story and a dozen lines of CI already deliver the same signal; your extra spec doubles maintenance and still misses the actual Effect.”

**E — 1–2-day kill test:** use three real interaction histories from at least two app flows, including concurrent/repeated same-name Commands. Require unchanged replay to reproduce every supported descriptor; ten seeded changes should include duplicate dispatch, wrong ID, wrong amount, stale completion, benign refactor, and unchanged descriptor with changed handler body. Require at least five meaningful detections, zero accepted ambiguous correlations, no more than one false alert on five benign edits, and explicit out-of-coverage status for the changed-body case. Compare time and findings with plain Story assertions. Stop if setup needs over half a day per flow, the simple baseline catches everything at equal effort, or no maintainer wants the artifact.

## Finalist B: audit promises that disappear during DSL compilation

**I — One sentence:** make a small language extension show where each behavior-bearing clause is executed, checked, or explicitly rejected, then validate the claim with a distinguishing negative control.

**I — 30-second demo:** an agent adds `on_stale ... reject` to a workflow DSL. Parsing and type checking pass; the generated kernel omits the stale guard. The audit pairs the source clause with a late-completion trace and shows that removing the clause changes nothing in the generated behavior. Installing the compiler extension is blocked until the clause gets semantics or a located “unsupported” error.

**F — Named beneficiary and concrete pain:** maintainers of specification compilers and app-specific workflow DSLs. FSL #711, opened **2026-08-04**, describes `on_stale` being parsed and validated but omitted by both lowering paths. #723, opened **2026-08-05**, inventories additional accepted constructs lacking executable meaning. #779, opened **2026-08-08**, reports saga event emission failing to apply declared state evolution; the issue shows how unreachable states made a misleading property provable. All three issues were closed by inspection, with zero reactions. These are specific historical compiler defects, not open vulnerabilities or independent customer votes. [#711](https://github.com/ymm-oss/fsl/issues/711), [#723](https://github.com/ymm-oss/fsl/issues/723), [#779](https://github.com/ymm-oss/fsl/issues/779).

**F — Closest prior art:** Redex provides semantics testing and per-case coverage; FSL already has differential implementation checks, public kernel contracts, a coupled-change gate and documented rejection of unsupported constructs. **I — Those kill a generic “test your DSL compiler” proposal.** The narrower possible gap is a portable manifest and runner for *source promise → independently distinguishing behavior*, especially where two generated paths agree because both omit the same clause. [Redex](https://docs.racket-lang.org/redex/Testing.html), [FSL coupled-change checks](https://github.com/ymm-oss/fsl/blob/1844fa74a717ba9229e0b292d9421c0939016e5e/docs/design/DESIGN-coupled-change-metatest.md), [current domain design and historical omissions](https://github.com/ymm-oss/fsl/blob/1844fa74a717ba9229e0b292d9421c0939016e5e/docs/design/DESIGN-domain.md).

**I — Check and gaming:** inventory behavior-bearing AST fields, not just top-level variant names. Each field gets an explicit classification: executable, checked obligation, review-only metadata, or rejected. ## Finalist C: bounded macros for self-extending applications

**I — One sentence:** let an agent add reusable behaviors as typed macro data, while the host keeps one fixed interpreter, a bounded write frame, and the only implementations of external operations.

**F/I — What “bb” most plausibly means:** **get-bb/bb, the IDE that builds itself**, rather than babashka. Its primary site and plugin guide explicitly match the brief's self-extension context. Its configuration documentation says plugins execute as trusted server code; the SDK likewise describes content scripts as trusted same-origin code. Babashka's executable really is named `bb` and uses SCI, so it is a plausible alternate reading, but less consistent with this context. [bb](https://getbb.app/), [plugin guide](https://getbb.app/plugin-guide), [trust boundary](https://github.com/get-bb/bb/blob/main/docs/configuration.md), [SDK](https://github.com/get-bb/bb/blob/main/packages/plugin-sdk/README.md), [babashka](https://book.babashka.org/), inspected 2026-10-28. No claim about the builder's intended referent is stronger than this inference.

**I — 30-second demo:** a trusted bb task-board plugin owns a small JSON document. Ask it to grow a `triageSelected` behavior. The agent supplies a named macro that changes only selected cards' priority/labels. The review shows expansion, exact permitted paths and a maximum operation count. A second macro that changes an unselected card is refused. Reload a shared macro definition and show that an old installed behavior remains pinned to its earlier expansion.

**I — The specification form:** keep the grammar fixed. A macro is a typed, namespaced definition made from `sequence`, a restricted predicate, and existing host operation constructors. Macro calls form an acyclic dependency graph. Definitions may introduce names and compositions, never new primitive implementations. Bind each installed expansion to its dependency versions. Type-check parameters and output patches, bound expanded size, validate all writes against the frame, and validate postconditions before atomically committing the document.

**I — Example:** `triageSelected(ids)` may replace `/cards/<selected-id>/priority` and append an allowlisted label; it may not replace `/cards`, remove unrelated cards, invoke arbitrary JS, register a host callback, or add a network primitive. This deliberately supports a smaller class of extensions than a normal bb or Pi plugin. The demo must test whether that class is useful.

**F — Closest prior art:** Racket syntax-spec/Turnstile already supply extensible, typed language construction. CEL is an existing terminating, side-effect-free expression language under its defined function environment. json-render owns a component/action catalog; its Jev example validates finite-choice compositions, depth and cycles. Arkhe's reference runtime checks declared effects against a write surface. SES/Endo, SCI and Extism cover broader constrained execution patterns. **I — The remaining possible gap is jointly enforcing expansion provenance, per-invocation write frames and operation bounds in a concrete self-extension slot. A new macro system, policy language, sandbox, or genUI renderer is not the opportunity.** [syntax-spec](https://docs.racket-lang.org/syntax-spec-v1/Tutorial.html), [CEL definition](https://github.com/cel-expr/cel-spec/blob/master/doc/langdef.md), [Jev example](https://github.com/vercel-labs/json-render/blob/main/apps/web/lib/jev/README.md), [Arkhe guide](https://github.com/arkhelang/arkhelang/blob/main/docs/guides/architect-guide.md), [Endo](https://github.com/endojs/endo), [SCI](https://github.com/babashka/sci), [Extism](https://github.com/extism/js-pdk).

**F/I — Named beneficiary and pain:** bb/Pi extension authors and users who want narrow customizations without reviewing a whole general-purpose extension. Pi's security policy explicitly requires trustworthy extensions; bb documents its broader plugin trust boundary. These prove the current tradeoff, not demand for a restricted substitute. json-render #37 records user confusion where catalog documentation and generated prompts omitted information; it supports inspectable authoring surfaces, not the full macro product hypothesis. [Pi security](https://github.com/earendil-works/pi/security), [bb configuration](https://github.com/get-bb/bb/blob/main/docs/configuration.md), [json-render #37, 2026-01-21](https://github.com/vercel-labs/json-render/issues/37). **I — Value confidence is low until users bring useful extensions that fit the restricted core.**

**I — Check and gaming:** validate macro data without executing compiler callbacks; expand through pinned definitions; run the normal typed-core checker on the expansion; enforce expanded-operation and output-size caps; reject recursive calls and unknown constructors. Apply the frame to the *resulting document diff*, not merely the patch's textual path: replacing a parent object could otherwise erase unselected data. Use a snapshot revision and atomic compare-and-swap commit to prevent checking one document and applying to another. Input bindings and selected IDs come from the host. Host handlers remain trusted; general plugins running beside the slot keep their existing trust boundary.

**I — Limits that matter:** macro DAGs can expand exponentially, so acyclicity alone is insufficient. Runtime fuel is a resource guard, not a proof of useful completion. CEL extension functions and custom host handlers can invalidate assumptions about purity or cost. A read frame or data-flow policy would require additional work if confidentiality were in scope; a write frame does not supply it. Restrict v1 to local plugin-owned state and no network operations.

**I — Better models:** users will still disagree about which records an extension may modify; version pinning and host-enforced frames preserve that choice. Better models make more sophisticated compositions possible. Whether macro review is actually easier than reviewing a tiny generated TS function remains an empirical question.

**I — Owner response:** bb or Vercel could own this slot and absorb the feature. That is a serious gap-score penalty. A small portable checked-core package with a bb demonstration and an existing catalog-based web demonstration is a plausible OSS artifact; claiming a defensible independent platform is not.

**E — 2–3-week v1:** one trusted plugin, one document schema, four or five constructors, finite macro DAGs, host-selected frames, operation caps, dependency pinning, atomic state commit and an expansion viewer. Reuse schema validation and an existing predicate subset. Keep all generated material as data. A browser demo is Vercel-adjacent; pure validation/interpreting code can be portable to Workers, while bb's host adapter remains local.

**I — Expert reply that kills it:** “json-render plus a few trusted handlers already does this, and the restrictions remove every extension I actually need.”

**E — 1–2-day kill test:** collect ten actual requested customizations from bb/Pi users or their public extension repositories. Model them without adding primitives. Require at least six useful cases to fit and three users to understand the expansion/frame without reading the interpreter. Exercise recursive definitions, exponential expansion, parent replacement, unselected writes, stale revisions and edited dependencies. Stop if most cases need arbitrary JS/network access, an existing catalog API covers them with less code, or the owner does not want the slot.

## Small local experiment: why shape and final state are insufficient

**M — Executed 2026-10-28 with Python 3.15, standard library only.** A hand-written reducer had states `idle`, `pending`, `charging`, `done`, `cancelled` and four input Messages: `Submit`, `Approved`, `Completed`, `Cancel`. Its mutant additionally accepted `Completed` while already `done`, emitting another `SendReceipt`. Both returned the same final Model on the witness; the emitted Command lists differed. This was a toy model, not a Foldkit integration, TS compilation test, or historical-bug evaluation.

| Probe | Result measured |
|---|---|
| Enumerate every input history of lengths 0–5 | **M — 1,365 histories; 15 base/mutant differences.** |
| Shortest reducer witness | **M — `Submit, Approved, Completed, Completed`.** Base requests `RequestApproval, Charge, SendReceipt`; mutant adds another `SendReceipt`. Both finish `done`. |
| Compare finite protocol with a version allowing another charge | **M — shortest added trace: `request, approve, charge, charge`; five state pairs visited before the witness.** |
| Compare original protocol with an internal-state rename | **M — no trace difference in either direction; five reachable state pairs in each comparison.** |
| Test an implementation accepting no action | **M — its prefix language is included in the old contract; the reverse comparison fails at `request`.** |

**I — Implications:** assert Command multiplicity, not just final Model state; show concrete witnesses when weakening a finite contract; keep acceptance/productivity examples alongside safety. Internal state names need not define observable compatibility. A base-versus-PR trace diff and a normative law answer different questions.

**M — Reproduction specification:** the reducer transitions were `idle + Submit → pending / RequestApproval`, `pending + Approved → charging / Charge`, `charging + Completed → done / SendReceipt`, and `pending|charging + Cancel → cancelled / []`; other inputs preserved state with no Commands.
