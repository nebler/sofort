# 10 — Rigor flip: the historian and the critic

Research date: **2026-10-28**. Lens: **10-rigor-flip**. Scope: an open-source side project, independent of the excluded kernel work.

**Labels:** **F** = sourced fact or an author's reported result, not independently reproduced; **M** = measurement made during this research; **I** = inference, interpretation, design or recommendation; **E** = estimate or proposed threshold. There were no new model runs or benchmark reproductions in this report. Registry/API inspection is evidence of published artifacts, not a performance experiment. Undated documentation and repository state were accessed on 2026-10-28.

## Verdict

**I — The thesis is directionally useful and empirically overclaimed.** Agents reduce the expense of writing annotations, explicit transitions, adapters and tests. They do not remove the expense of deciding the requirement, reviewing a representation, maintaining its toolchain, exploring its state space or connecting a specification to running code. The winning property is an inexpensive, independently enforced acceptance boundary. Verbosity, functional style, diagrams and process ceremony are not substitutes for that boundary.

**F — A material correction to today's candidate:** Foldkit already has [issue #622, captured session → runnable Story](https://github.com/foldkit/foldkit/issues/622), opened **2026-07-04**, and [open PR #626](https://github.com/foldkit/foldkit/pull/626) implementing the lowering half. The PR explicitly excludes session export and acknowledges FIFO correlation limitations for concurrent Commands. The issue had **one positive reaction and three comments** when inspected. **I:** session export and Story generation are an upstream contribution opportunity, not an undiscovered project category. The remaining hypothesis is **cross-version Command comparison with explicit causal correlation and incomplete-trace detection**.

**I — ONE pick: Command Diff**, a small, upstream-friendly extension to the round-9 replay family. A captured checkout session runs through two versions of `update`, executes neither version's external effects, and shows exactly which Command intentions changed. It has the best demo and stack fit here, but only a **2/5 gap score**. If the existing Foldkit branch already supplies a satisfactory comparison, contribute there and stop the standalone project.

**I — The economic equation:** total cost remains `intent/specification + generation + checking + review + maintenance + failures`. Agents principally reduce generation and some maintenance. Cheap checking can make more explicit representations worthwhile; state explosion, solver timeouts and unclear intent remain. A method can become easier to use while still being a poor choice for a particular application.

## Apply the flip rule without changing it

**I:** The four gates from [the summary §12](../RESEARCH-SUMMARY.md#12-the-rules-we-learned) are conjunctive:

1. **A — Authoring:** the adoption barrier was manual work per case, rather than coordination, incentives, physical limits or an unsuitable abstraction.
2. **C — Check:** an independent mechanical check is substantially cheaper than that work. A second LLM's agreement does not qualify. Checking a model without checking the implementation-to-model relationship is incomplete.
3. **R — Runtime:** the accepted artifact works without calling the authoring model. A deterministic tool may be called by an agent later; its implementation need not contain inference.
4. **O — Ownership:** identify the owner of the authoritative check. An outsider has room where the check is public or distributed across application owners.

**I:** Verdicts below distinguish **genuine narrow flip**, **partial/conditional**, **no**, and **already alive**. A living technique can become more valuable without satisfying the historical-return claim. Historical causal explanations are explicitly interpretations unless a study directly supports them.

### Historical corrections before the sweep

**F:** Kemerer's [1992 CASE adoption study](https://sites.pitt.edu/~ckemerer/CK%20research%20papers/LearningCurveAffectsCASEAdoption_Kemerer92.pdf) documents abandoned or underused tools and learning-curve costs. **F:** Whittle, Hutchinson and Rouncefield's [2014 study](https://research.monash.edu/en/publications/the-state-of-practice-in-model-driven-engineering/) surveyed **450 practitioners** and interviewed **22**; MDE was more widespread than outsiders assumed, commonly applied to parts of systems. **I:** that contradicts a simple story in which the whole approach disappeared because humans disliked rigor.

**F:** The [1996 Cleanroom reference](https://www.sei.cmu.edu/library/cleanroom-software-engineering-reference/) specifies **14 processes and 20 work products**, combining mathematical development with statistical usage testing. [SDL Z.100's 2021 edition remains in force](https://www.itu.int/rec/T-REC-Z.100). **I:** neither should be described as a dead algorithm waiting for a chatbot. Adoption, specialist tooling and organizational practices are different problems.

## The post's nine techniques

**I:** In each row, “cost” compares human per-case work with the useful check. “Revival” distinguishes an authoring aid from merely using the technique to host an agent.

| Technique | What constrained adoption; human cost versus check cost | Strict flip assessment, including owner | Who is doing the agent version |
|---|---|---|---|
| **1. State machines** | **I:** not dead. Enumerating states, transitions and failure cases is tedious; executing a transition is cheap. Exhaustive exploration can be expensive. | **I:** **already alive; narrow A/C/R yes** for finite transition artifacts and fixed assertions; **O** belongs to the app's transition model and contracts. A graph alone does not verify guards or effects. | **F:** [Stately Agent](https://github.com/statelyai/agent) restricts a model to machine-legal events; this is runtime control, not proof of better authoring. Foldkit's [Machine API](https://foldkit.dev/core/machine) exposes explicit edges for analysis. |
| **2. Functional programming** | **I:** not dead. Human costs include unfamiliar composition, effects and error handling. Pure transitions are cheap to evaluate and replay; “functional” is not itself a checker. | **I:** **conditional**. A passes only for repetitive encoding; C needs an actual type/property/trace check; R passes; O is the compiler plus app owner. No automatic flip for FP taste. | **F:** [Foldkit](https://github.com/foldkit/foldkit) and the Maple migration use an explicit model/message/effect architecture with agents. **F:** [FPEval, October 2026](https://aclanthology.org/2026.findings-emnlp.710/) also documents substantial remaining FP generation difficulty. |
| **3. Declarative infrastructure** | **I:** already mainstream. Repetitive resource definitions and lifecycle wiring are costly; validating a plan is cheap relative to manually authoring it, but a valid plan may be undesirable. | **I:** **already alive; partial C**. Plans, policy and provider readback check narrower claims than service correctness. R passes; O is provider + operator policy. The framework owner has the distribution advantage. | **F:** [Alchemy](https://alchemy.run/what-is-alchemy/) puts infrastructure and application dependencies into typed Effect programs. **I:** another agent-generated IaC wrapper is owner territory. |
| **4. TDD** | **I:** not dead. Deriving meaningful examples and updating them costs human attention; running them is usually cheap. Red→green is useful only if the red assertion is legitimate. | **I:** **genuine narrow labor flip** when acceptance tests are fixed independently. A/C/R pass; O is the customer/test owner. Generating implementation and approval tests from the same misunderstanding fails C. | **F:** [TDFlow, 2025-10-27 / EACL 2026](https://arxiv.org/abs/2510.23761), [TDD-Bench Verified](https://arxiv.org/abs/2412.02883) and existing test-generation agents occupy the generic opportunity. |
| **5. DDD** | **I:** not dead. Translating domain conversations into models is manual; choosing bounded contexts also requires stakeholder agreement. There is no cheap complete test for the correct business vocabulary. | **I:** **no whole-method flip**: A partly, C fails for strategic design, R yes, O domain experts. Aggregate invariants can flip separately once supplied. | **F:** Microsoft's [DDD and agents cookbook](https://github.com/microsoft/AgenticCookBook/blob/main/docs/domain_driven_design.md) applies bounded contexts to agents; [Domain Modeling Meets Generative AI](https://github.com/mardenneubert/ddd-meets-genai) translates workshop artifacts into structured models, with code scaffolding described as future work. Neither establishes semantic correctness of domain discovery. |
| **6. Actor systems** | **I:** already alive. Mailbox protocols, persistence and supervision need explicit design; scheduler checks and bounded simulation are useful, but delivery semantics and interleavings remain hard. | **I:** **already alive; partial**. A can improve, C needs simulation/protocol contracts rather than “uses actors,” R yes, O runtime + application. | **F:** [Akka's Agent component, 2025-07-11](https://akka.io/blog/introducing-akkas-new-agent-component) uses its actor runtime. [Infinity](https://github.com/hydro-project/infinity) treats agent concurrency as event scheduling. **I:** these are primarily runtime adaptations, not comparative authoring evidence. |
| **7. Rigorous API schemas** | **I:** already mainstream. Writing and synchronizing schema/client/server artifacts is labor; parsing and compatibility checks are cheap. A schema cannot say whether a refund was deserved. | **I:** **narrow flip for the maintenance tail**: A/C/R yes where compatibility and behavior are independently specified; O API producer + consumer contracts. New schema generators face established owners. | **F:** [TypeSpec](https://typespec.io/docs/) supplies a compiler/emitter surface; [formal-agent-contracts](https://github.com/kotaroyamame/formal-agent-contracts) generates contracts/tests for agents. **I:** natural-language “spec” documents alone do not satisfy C. |
| **8. Type safety + formal verification** | **I:** two different strengths. Type annotation is repetitive; proving functional contracts needs invariants and lemmas. Type checking is often cheap; SMT search and proof maintenance are not uniformly cheap. | **I:** **genuine narrow flip** for fixed contracts and proof artifacts. A yes, C yes only for the claimed formal property and trusted assumptions, R yes, O kernel/compiler + spec owner. Formalization of intent remains outside that proof. | **F:** [dafny-annotator, 2025-06-21](https://dafny.org/blog/2025/06/21/dafny-annotator/), vericoding and [AgenticTyper, 2026-02](https://arxiv.org/abs/2602.21251) directly automate this labor. Generic proposer/verifier projects were already killed in rounds 6–7. |
| **9. Disciplined operations** | **I:** alive and necessary. Runbooks, dashboards, investigation and response are labor. An SLO evaluates observed service behavior, not a complete counterfactual diagnosis; responsibility and customer risk are not writing tasks. | **I:** **partial**. A passes for runbook execution, C only for independently measured outcomes within a declared window, R yes for deterministic remediations, O operator + telemetry. An agent saying “healthy” fails C. | **F:** [Azure SRE Agent](https://learn.microsoft.com/en-us/azure/sre-agent/overview) already collects operational context and proposes or executes configured mitigations. **I:** generic autonomous on-call is crowded; a specific acceptance or recovery check is more plausible. |

## The allegedly abandoned methods

**I:** This expands Z/B/VDM into separate entries because their tools and current evidence differ. A “yes” is always for a bounded artifact, not the entire surrounding methodology.

| Method | Historical barrier and useful check | Do agents pass A/C/R/O? | Direct revival evidence, or the honest absence of it |
|---|---|---|---|
| **CASE tools** | **F:** learning and adoption costs are documented by Kemerer (1992). **I:** maintaining multiple linked representations also imposed work; valid diagrams rarely established correct behavior. | **I:** **partial**: A yes for artifact upkeep; C no for generic diagram fidelity; R yes; O repository/metamodel vendor. Agent-authored executable subsets are plausible; a universal CASE suite fails. | **F:** [Mendix's 2026 roadmap](https://blogs.sw.siemens.com/news/mendix-roadmap-from-low-code-to-agentic-business-outcomes/) describes Maia and model APIs for external agents. **I:** the existing model-platform owner is doing the revival. |
| **MDE / UML round-tripping** | **F:** MDE survived selectively in the 2014 study. **I:** synchronization, transformation maintenance, tool lock-in and organizational fit matter more than drawing cost alone. Compilation can check well-formedness, not bidirectional semantic equivalence. | **I:** **conditional**: A partly, C only with executable semantics plus a validated transformation or behavioral baseline, R yes, O model/compiler owner. Regenerating both diagram and code is not an independent check. | **F:** [Text2UML / Calamo et al., 2025](https://github.com/IlKaiser/text2uml) publishes 45 conceptual-model scenarios; an [LLM-driven MDA pipeline, 2025-09-29](https://ieeexplore.ieee.org/abstract/document/11184520) generates UML and Python. **I:** model generation is demonstrated; robust arbitrary round-trip equivalence is not established by these sources. |
| **4GLs** | **I:** did not die: SQL, reporting and low-code survive. Escaping a domain-specific abstraction, portability and vendor control are not solved by cheaper typing. | **I:** **no generic resurrection**: A is not the sole barrier; C is domain-dependent; R yes; O domain runtime/vendor. Agents can lower authoring cost inside an existing 4GL. | **F:** [Mendix Maia](https://blogs.sw.siemens.com/news/mendix-roadmap-from-low-code-to-agentic-business-outcomes/) is a direct modern continuation. **I:** an outsider proposing “natural language to enterprise apps” competes with its owner. |
| **Cleanroom** | **F:** the SEI reference combines formal development, team process and statistical usage testing. **I:** proof/review work can shrink; obtaining a representative operational distribution and organizational adoption do not become free. | **I:** **partial**: A yes for proof obligations; C yes for fixed assertions and valid statistical tests, not arbitrary reliability claims; R yes; O customer workload + verifier. An entire methodology has not flipped merely because annotations are generated. | **I:** no convincing direct implementation of the complete classical process was verified in this sweep. **F:** dafny-annotator revives one component. “Clean-room reimplementation” repositories concern a different topic and were excluded. |
| **Z** | **I:** mathematical formulation, schema upkeep and refinement to code require specialist work. A theorem about an abstract state is not a proof of its generated implementation. | **I:** **conditional**: A yes; C fails without a checked refinement bridge; R yes; O spec author + formal tool. | **F:** Farchi's [online-banking case study, 2026-09-07](https://arxiv.org/abs/2609.07365) has AI-proposed Z interfaces. It explicitly states that its spec-level proofs do **not** establish generated-code refinement. A useful revival with an admitted missing gate. |
| **B / Event-B** | **I:** refinement and discharge of proof obligations are manual per model; automated provers/model checkers can discharge many fixed obligations. Domain modeling still requires judgment. | **I:** **genuine narrow flip**: A/C/R yes for fixed semantics and checked refinement; O public Rodin/ProB plus customer invariants. Solver limits and environment assumptions remain. | **F:** [Event-B Agent, FSE July 2026](https://hongshuw.github.io/files/Event_B_Agent%28FSE26%29.pdf) integrates model synthesis/repair with Rodin and ProB. **I:** this directly occupies “LLM writes Event-B, prover repairs it.” |
| **VDM** | **I:** writing invariants, operation contracts and proof obligations takes expertise; VDMJ can check syntax/types and generate obligations, which is weaker than proving them. | **I:** **narrow/conditional flip**: A yes, C only with obligations actually discharged and implementation checked, R yes, O public tools + application contract. | **F:** [kotaroyamame/formal-agent-contracts](https://github.com/kotaroyamame/formal-agent-contracts) uses VDM-SL, VDMJ and Z3 with TypeScript/Python outputs. Its evaluation needs the caveats below; existence of the pipeline is firmer than its quality claims. |
| **Design by Contract / Eiffel** | **I:** not dead; assertions spread into many languages. Human cost is articulating behavior and maintaining contracts. Runtime assertions cheaply check exercised executions; they do not cover all executions. | **I:** **genuine narrow flip** for independently fixed assertions: A/C/R yes; O library consumer/producer contract. Agent-inferred preconditions can exclude the failing inputs and hollow out the guarantee. | **F:** [jvelilla/eiffel_code_gen](https://github.com/jvelilla/eiffel_code_gen/blob/main/README.md) supplies contract-driven Eiffel rules/examples for LLMs. **I:** it is authoring guidance, not a demonstrated autonomous verification service. |
| **Literate programming** | **I:** prose, chunk organization, tangling and code/prose synchronization cost attention. Tangle equality cheaply checks extracted source; it cannot check whether the explanation is true or useful. | **I:** **no full flip**: A yes, C fails for the central human-understanding benefit, R yes, O reader. It may be pleasant documentation automation without satisfying the strict rule. | **F:** [tlehman/litprog-skill](https://github.com/tlehman/litprog-skill) provides agent-generated literate documents, tangling and reverse synchronization. **I:** round-6 “no revival” wording is too strong now; its “no independent prose oracle” objection survives. |
| **Hoare-style annotations** | **I:** loop invariants, framing and decreases clauses impose per-function specialist labor; proof checking is often much cheaper than inventing the annotation, though solver search can be costly. | **I:** **genuine narrow flip**: A/C/R yes with fixed program/spec and controlled assumptions; O verifier + spec owner. Editing code, adding assumptions or weakening postconditions changes the task. | **F:** [dafny-annotator](https://dafny.org/blog/2025/06/21/dafny-annotator/) is direct prior art; [DafnyPro, 2026-01-08](https://arxiv.org/abs/2601.05385) reports 86% correct proofs on DafnyBench for its configured system. |
| **Larch** | **F:** its [two-tier design](https://www.cs.ucf.edu/~leavens/larch-faq.html) separates mathematical vocabulary from language-specific behavioral interfaces. **I:** maintaining both tiers and language tooling was specialist work; checking consistency is not checking adequacy. | **I:** **conditional**, not evidenced as a standalone return: A plausible; C needs an extant sound toolchain/refinement link; R yes; O language ecosystem + contract owner. Porting the notation is insufficient. | **I:** no direct, convincing LSL/BISL agent revival was verified. **F:** searches return unrelated NASA and Character.AI products named Larch; those are not descendants of the specification system. Dafny/JML-style work revives related ideas, not that identity. |
| **N-version programming** | **F:** Knight–Leveson's [1985 report](https://libraopen.library.virginia.edu/entities/publication/4ac33eeb-79b4-46e4-aef9-f6ec56a62286) found correlated failures among 27 independently written versions on one million tests. **I:** cost was only one barrier. | **I:** **no strict reliability flip**: A improves, majority voting fails C because it is not an independent truth check, R yes, O must be an external oracle. Disagreement can locate ambiguity; agreement cannot certify correctness. | **F:** [Ron, Baudry and Monperrus, 2026-06-18](https://arxiv.org/abs/2606.20158) evaluate 48 agent-written versions. Triple voting reduces observed mean failures **387.44→130.99**, while common-mode errors persist around hard/ambiguous requirements. **I:** the summary's categorical dismissal needs this nuance, not a reversal into “voting is verification.” |
| **Executable specifications** | **I:** alive as parsers, interpreters, reference models and acceptance suites. The expensive part is maintaining a second behavior representation. Execution is cheap; a shared mistaken specification remains possible. | **I:** **genuine narrow flip** when the spec or reference is independently owned: A/C/R yes, O customer/public standard. “An LLM executes a prose spec” fails C. | **F:** Foldkit Story, TDFlow and formal-agent-contracts are concrete revivals. [GitHub Spec Kit](https://github.com/github/spec-kit) is adjacent spec-driven workflow prior art; **I:** prose files by themselves are not executable acceptance. |
| **Harel Statecharts** | **I:** not dead; hierarchy, parallel regions, history and event semantics reduce some complexity and introduce tooling/semantic choices. Path generation is cheap for small graphs; full dataful state exploration is not. | **I:** **already alive, narrow flip for authoring**: A yes, C only for explicit bounded assertions, R yes, O executable interpreter + app. | **F:** XState/Stately directly continues the tradition. [Maraev et al., September 2025](https://aclanthology.org/2025.clasp-main.3/) combine Harel Statecharts with LLM-supported dialogue while retaining deterministic dialogue control. |
| **Petri nets** | **I:** alive in workflow/process research and tools. Modeling concurrency is laborious; bounded reachability/liveness analysis is useful, but scale and the code-to-net relationship remain expensive. | **I:** **conditional**: A yes, C for bounded faithful models, R yes, O customer process + analysis tool. A beautiful net inferred from a log omits unobserved behavior. | **F:** [CIR+CVN, 2026-04-10](https://arxiv.org/abs/2604.09318) translates LLM-produced concurrency artifacts into Petri-net verification, evaluated on nine bounded patterns. **I:** Anthropic's tool named Petri is unrelated and was excluded. |
| **SDL** | **F:** Z.100 is still an in-force standard. **I:** specialist telecom tooling, integration and asynchronous-queue semantics mattered; generating diagrams does not eliminate unbounded queues or prove implementation correspondence. | **I:** **conditional, no demonstrated flip**: A partly, C only for a bounded executable subset with faithful implementation, R yes, O protocol/tool owner. | **I:** no direct well-evidenced agent revival of **ITU SDL** was found in the bounded search. GraphQL SDL, software-development-lifecycle acronyms and OpenZL SDDL are different things. Stately is an analogy, not evidence of an SDL revival. |
| **MISRA-style coding standards** | **I:** not abandoned. Rule interpretation, repetitive remediation and deviation records cost human effort. Many rules are mechanically checkable; others require judgment. Passing the checker alone is not functional equivalence. | **I:** **genuine narrow remediation flip**: A/C/R yes for mechanically checkable obligations plus behavior validation; O checker vendor + project deviation policy. No flip for uncheckable process obligations. | **F:** Toyota/Woven's MISRA Copilot is direct evidence, at proof-of-concept stage. **I:** an outsider lacks its internal examples and customer-specific deviation policy; a generic MISRA fixer is a poor solo opening. |

**I — Historian's result:** the strongest returning work is proof annotation, fixed-contract implementation and rule remediation. The weakest is semantic interpretation, stakeholder agreement and explanations. CASE/MDE failed partly at representation and organizational boundaries; N-version failed partly at independence; literate programming lacks a cheap explanation oracle. Cheaper authorship does not repair those central weaknesses.

## The critic: what the evidence actually says

### Evidence ledger

| Evidence, date and design | Reported observation | Assessment of the thesis |
|---|---|---|
| **F:** [Type-constrained code generation](https://arxiv.org/abs/2504.09246), April/May 2025; type-directed decoding versus existing generation on function-level benchmarks. | Compilation errors more than halved; functional correctness also improved. | **I — For, narrow causal claim.** This tests an actual mechanical constraint. It does not isolate library complexity, long-term maintenance or framework choice. |
| **F:** [llmlangbench release](https://github.com/vivshaw/llmlangbench/releases/tag/release-1), **2026-02-19**; six tasks × eight languages × three trials, Sonnet 4.5 and a 60-turn cap. | Published black-box **test-pass percentages**: TS **95.9%**, JS **95.8%**, Python **97.0%**, Rust **87.0%**, Haskell **82.0%**. Extended SQL trials: JS **83.2%**, TS **79.8%**. | **I — Against a blanket hierarchy.** These are test fractions, not all-or-nothing task success; samples are small and language/tooling/data effects are confounded. Still, the released numbers do not show a large automatic typing/rigor advantage. Ignore its separate LLM code-review grades as an independent correctness oracle. |
| **F:** [FPEval / FPBench](https://aclanthology.org/2026.findings-emnlp.710/), October 2026; **721 tasks**, seven models, Haskell/OCaml/Scala and Java baseline, executable tests and static analysis. | Higher error rates in Haskell/OCaml than Scala/Java; frequent imperative-looking FP code; static feedback and targeted instructions partly repair it. | **I — Against “humans were the only obstacle.”** Better discipline can help checkability while unfamiliar syntax/APIs and model priors still reduce success. This is not a controlled Effect/TS comparison either. |
| **F:** [Effect guidance benchmark](https://coey.dev/effect-first), **2026-02-23**; five tasks, four documentation contexts, GPT-5.2, one run per condition. | Uses deterministic **regex checks of idioms**. The author explicitly says a passing output might not compile. The “opensrc” condition prepends extracted signatures rather than evaluating a full retrieval workflow. | **I — Weak evidence of authoring support, no semantic framework victory.** Every arm writes Effect. This does not compare Effect with plain TS, execute behavior or demonstrate saved human review. |
| **F:** [TDFlow](https://arxiv.org/abs/2510.23761), January 2026 revision; agent workflow given human-written tests. | **88.8% SWE-bench Lite / 94.3% Verified** test resolution; seven test-hacking cases among 800 inspected runs counted as failures. | **I — For fixed acceptance, with a major condition.** Providing the target tests changes the information available, so these numbers must not be compared naively with standard issue-only leaderboard entries. Writing the correct reproducer remains the bottleneck. |
| **F:** [Vericoding](https://arxiv.org/abs/2509.22908), September 2025; fixed formal-specification synthesis and proof tasks. | High Dafny success and large improvement in proof completion, with materially lower success in the other collections. | **I — For mechanized proof labor.** No matched verified/unverified production-app treatment; no result about the truth of customer intent. Do not interpret proof completion as a business-acceptance rate. |
| **F:** [formal-agent-contracts evaluation](https://github.com/kotaroyamame/formal-agent-contracts/blob/master/eval/results/report.md), **2026-04-01**, 15 runs per arm over three tasks. | Reports **+42.8pp specification coverage**, but admits keyword heuristics, the same Claude instance producing both groups, and inability to execute the planned gold tests for its test-effectiveness metric. | **I — Promising artifact, weak outcome evidence.** A metric that rewards a formal spec for existing cannot independently show reduced drift. The report explicitly does not establish statistical significance. |
| **F:** Its [executed mutation follow-up](https://github.com/kotaroyamame/formal-agent-contracts/blob/master/eval/results/mutation-report.md), **2026-04-02**. | Control **21/21**, treatment **25/25** injected faults caught; only three mutation categories applied, about 1.5 mutants/run. | **I — No discriminating evidence either way.** The ceiling and shallow mutation set cannot confirm the headline quality advantage; equal scores also do not prove equivalence. This is evidence appraisal, not a new mutation-testing project pitch. |
| **F:** [TEBench](https://arxiv.org/abs/2605.06125), **2026-05-07**, 314 instances across ten Java projects, seven configurations. | Identification F1 **45.7–49.4%**; stale-test identification approximately **36%**. | **I — Against “discipline becomes free.”** Agents can repair red tests while missing assertions that pass but no longer express the relevant behavior. Applicability to current TS frontends needs separate validation. |
| **F:** [Z banking case study](https://arxiv.org/abs/2609.07365), September 2026. | Mathematical/spec-level reasoning with generated implementation; explicitly no established refinement proof from implementation to spec. | **I — Demonstrates the missing bridge.** Specification rigor cannot be credited to the code without a checked relationship. |
| **F:** [N-version agent experiment](https://arxiv.org/abs/2606.20158), June 2026. | Voting helps on the studied workload, but correlated failures cluster around difficult or ambiguous requirements. | **I — Both sides.** Authoring cost really falls; semantic correlation does not automatically disappear. An external reference, not agreement, establishes which version is right. |

**I — Direct answers:**

- **Typed versus untyped:** there is positive causal evidence for type-constrained generation and weak, mixed evidence for choosing a typed language as a whole. Cross-language rankings cannot isolate types from training distribution, libraries, scaffolding and task allocation.
- **Effect versus plain TS:** this sweep found a guidance benchmark, runnable examples and migration experience, but **no convincing controlled behavioral comparison** of these two treatments. That is a bounded search result, not proof of absence.
- **Elm versus React:** Foldkit's repository supplies comparable [Elm/React/Foldkit pixel-editor implementations](https://github.com/foldkit/foldkit/blob/main/comparisons/pixel-art-elm/README.md). **F:** these are functional comparison artifacts. **I:** they are not repeated agent trials, and Elm architecture, language, compiler messages and framework ecosystem are separate variables.
- **Verified versus unverified code:** proof completion is demonstrated for formal contracts; a matched study showing lower production defect rates for agent-generated verified web apps was not located here. A proved implementation is stronger for the proved property, but the specification and trusted assumptions still determine that property's relevance.

### Does rigor move the bug into the spec?

**I:** Yes, it can, but it also removes entire classes of implementation mistakes once the contract is independently fixed. The remaining chain is:

`customer intent → formal/executable contract → implementation → deployed environment → observed outcome`

**I:** A checker covering one arrow should not be advertised as covering the others. Six concrete failure modes follow:

1. **Vacuity:** an impossible precondition or unreachable transition makes an assertion trivially true.
2. **Weakening:** the agent broadens accepted outputs or excludes difficult inputs, then proves the easier claim.
3. **Shared misconception:** the same model generates code, expected outputs and review prose from one mistaken interpretation.
4. **Unverified translation:** a checked state machine is not the executing program, or code generation lacks validated refinement.
5. **Boundary escape:** an unchanged Command name/arguments conceal a changed effect implementation, or effects occur outside the declared boundary.
6. **Incomplete evidence:** an observed trace omits a rare path, truncated history, timing behavior or a subscription transition.

**F:** [TrojanSpec-Bench](https://github.com/m-zest/TrojanSpec-Bench-v1.0) publishes verifier-admitted examples where apparently faithful specifications admit incorrect implementations and includes a SpecGuard baseline. **I:** it is small-project primary evidence of the failure mechanism, not a mature deployment result; another generic “LLM proposes, spec checker critiques” product already has direct prior art.

**I — The corrected thesis:** optimize for **checkable behavior at boundaries that the author cannot redefine casually**. Favor a small explicit model when it makes a relevant check inexpensive. Prefer a simple implementation when extra machinery only adds representation drift. Even a much better model cannot infer missing customer intent or make one customer's policy authoritative for another.

## Self-extending software: what history contributes

**I:** Emacs/Lisp/Smalltalk images, HyperCard, spreadsheets and moldable development show that live extension is not new. The agent changes who can author an extension and how often it is attempted. They do not supply a general acceptance oracle. [Ink & Switch's malleable-software essay, June 2025](https://www.inkandswitch.com/essay/malleable-software/) frames the user-agency goal; it does not establish semantic safety for arbitrary generated extensions.

| Pattern | What can be checked independently | Residue / owner |
|---|---|---|
| **I:** extensions are data: schema-defined UI, formulas, finite transitions | Parser, schema, dependency-cycle checks, declared capability limits, bounded transition assertions. | The host owns the interpreter; the user owns whether the added feature is wanted. This is the strongest limited form. |
| **I:** extensions are code behind a stable host boundary | Compile, run fixed conformance traces, compare effect intentions, enforce host permissions. | Permissions constrain consequences, not correctness. A plugin must not silently rewrite its own acceptance boundary. |
| **I:** extensions modify a live persisted model | Decode old state, exercise migration against captured states and continue recorded events. | Successful decoding is weaker than behavior compatibility. Incompatible or uncorrelated evidence must be reported as unknown. |
| **I:** learned tools become a reusable library | Execute fixed examples and environment checks after generation; version the accepted code. | **F:** [Voyager, 2023](https://arxiv.org/abs/2305.16291) already stores executable skills and uses environmental feedback plus self-verification. **I:** its model judgment is not an independent oracle for arbitrary tasks. |

**F:** [Pi extensions](https://github.com/earendil-works/pi/blob/main/packages/coding-agent/docs/extensions.md) already expose TypeScript tools, commands, handlers and UI. **I:** an extension SDK or new universal self-growing agent host is occupied. The interesting addition is application-owned evidence for accepting one extension. The brief's ambiguous **“bb” is treated here as [babashka](https://github.com/babashka/babashka)**, the Clojure scripting runtime; this is an assumption, not identification of a named agent. A script can be generated and retained, but a successful load says nothing about its intended behavior.

**I:** For this lens, self-extension folds into Command Diff's candidate-module workflow and the benchmark's repeated change tasks. There is no proposed new language, agent runtime, workflow engine or snapshot system.

## Finalist 1 — Command Diff

**I — One sentence:** compare what two versions of an effects-as-values application would ask the outside world to do for the same recorded causal session.

**I — 30-second demo:** record a checkout with a retry and an out-of-order response; load an agent's PR; show `SendReceipt(order=42): 1 → 2` at the diverging Message, while the rendered order remains “complete” in both versions. A second edit changes only a local label and produces no Command diff. A third changes a Command implementation while retaining its descriptor; the report explicitly marks that body as outside descriptor-equivalence coverage.

**F — Closest art and actual gap:** Foldkit's current Story API can assert exact Commands and substitute results, and DevTools exposes Messages, Commands and model history. PR #626 already lowers captured artifacts into tests; it remains open and does not claim portable export or robust concurrent correlation. ReGrade already compares different software versions using network traffic. **I:** the remaining useful slice is a portable **base-versus-candidate intentions report** with one causal timeline, explicit evidence gaps and framework-neutral output. An exact Story test assembled from a recording may already cover most of the value. That is the central kill risk, not a footnote.

**F — Named pain:** #622's author **artile** says a production app would use session-to-test export; **sandias42** reports friction connecting browser-discovered bugs back to Story/Scene tests and says browser tests found many tricky failures. A maintainer comment records a request for “Copy to Story” and later bounded named recordings with a human description. **I:** this verifies a capture/reproducer need, not yet demand for PR Command comparison. Value is therefore **3/5**, not mass-market evidence. Do not count maintainer relays or AI-authored comments as independent customers.

**I — Check and gaming model:** preserve the baseline trace, normalizers and comparison policy outside candidate write access. Replay pure `update` without running returned Effects. Compare names, canonical arguments, multiplicity, interruption identity and declared causal dependencies. Pin source/dependency versions; record initial model and schema versions. **F:** Foldkit's Command type contains an `effect` as well as `name`, optional `args` and optional `key`; batch execution has no ordering guarantee. [Command source inspected at tree `b702a5ef…`](https://github.com/foldkit/foldkit/blob/b702a5efbb74bebc056b798b414ddb923a82fbd5/packages/foldkit/src/command/index.ts). **I:** serialize a descriptor, not arbitrary Effect closures. Attach invocation IDs and origin IDs to outcomes; FIFO is insufficient when effects finish out of order or user input arrives while work is pending.

**I:** stop following a candidate after an incompatible Command/result relationship; injecting a historical successful response for a request the candidate never emitted invents a world. **I — Strict flip:** A = manually turning a production failure into a deterministic replay; C = frozen trace plus deterministic comparison; R = replayed application/checker require no model; O = each application owner controls its history and intended differences. ## Finalist 2 — Post-merge recovery, with immutable acceptance evidence

**I — One sentence:** package the existing TAP/FACF/SafeRevert pattern for a GitHub repository: test trunk snapshots, distinguish flaky failures from regressions and prepare a validated recovery change.

**I — 30-second demo:** twenty pre-tested changes land while a slow integration suite runs. One breaks an interaction. A timeline shows the bad interval, repeated conflicting test outcomes, the candidate culprit, and a revert candidate that restores the failing invariant. A second failure is a flake and produces no revert recommendation.

**F — Prior art:** Google already has [TAP](https://research.google/pubs/taming-google-scale-continuous-testing/), [FACF](https://research.google/pubs/flake-aware-culprit-finding/) and [SafeRevert](https://research.google/pubs/saferevert-when-can-breaking-changes-be-automatically-reverted/); SafeRevert evaluates **34,000** real breakages. Chromium's LUCI supplies substantial open-source infrastructure. Anthropic already runs bisect/revert pipelines. **F:** [bisectrunk](https://github.com/nanxstats/bisectrunk) supports parallel, resumable, environment-aware bisection and artifact comparison. **I:** reuse an executor; the possible gap is GitHub-oriented orchestration, acceptance provenance and recovery decisions under flakes, not another bisection implementation.

**F — Search correction:** generic automatic rollback is already present in projects such as [OODA-loop](https://github.com/mataeil/OODA-loop), whose documented auto-merge path performs post-merge health checks and can revert. **I:** “no product does auto-revert” is false. The narrower combination of milestone testing, noisy culprit localization and validated recovery was not verified as a packaged general tool in this sweep. That remains an uncertain distribution gap.

**F — Named beneficiary/pain:** Anthropic's report gives direct large-scale pressure and says engineers still need to steer agents away from violating core system constraints. Google's SafeRevert abstract describes developers wasting time diagnosing failures introduced by others. **I:** beneficiaries are maintainers of agent-heavy repositories with expensive integration tests and a pre-existing revert culture. Typical small repositories may receive no value; this is the chief market-size uncertainty for an OSS side project.

**I — Check and gaming:** the checker consumes pinned commit trees, test definitions, runner images and raw results, separately from patch proposals. Validate the suspected culprit with repeat observations and a revert-then-test experiment at the current tip. Keep failure signatures separate; do not let one green suite erase a different failure. An agent can overfit the test, change dependencies, alter failure classification or propose a revert that passes while removing desired work. Immutable acceptance fixtures plus reviewer-visible removed behavior address some of this; they do not prove whole-system correctness.

**I — Flip fit:** this is primarily **needed-more-at-new-scale**, not a formerly dead methodology. A = repeated manual triage/recovery; C = independent CI results and counterfactual candidate testing; R = scheduler/localizer runs without a model; O = each repository's tests, policies and revert authority. Bayesian confidence is conditional on its noise model, not a proof. Multiple culprit interactions and non-monotonic histories require abstention or a broader search.

**I — Better models / owner:** CI observations, merge rate and current trunk are facts outside a model's weights. A better model can prepare repairs faster, but it cannot replace the independent run. GitHub/CI vendors could absorb this; the outsider rationale is an open runner-neutral implementation and customer-owned test policy. Evidence for a durable standalone gap is weaker than evidence for the need.

**E — Two-to-three-week v1:** offline simulator plus event log, Actions-result adapter, milestone selection, a bounded noisy localizer using an existing execution backend, then a read-only web view on Workers/R2. Produce a local revert patch and its test evidence; defer automatic merging and production remediation. A Durable Object may serialize orchestration, but does not run arbitrary repository builds. Existing CI executes them.

**I — Expert reply that kills it:** “Our merge queue's batching is sufficient; adopting a red-trunk interval is organizationally unacceptable, and your posterior assumes a flake model our tests violate.”

**E — One-to-two-day kill test:** replay at least three histories with real CI failures if publicly obtainable, plus declared synthetic interleaving/flake cases; compare ordinary bisection and the proposed policy at the same job budget. Record innocent-revert recommendations, diagnosis time, CI runs and abstentions. Require no silent confidence on interacting/multiple culprits. Do not claim calibrated 99% recovery confidence from a tiny sample. Stop if no accessible repository has both a throughput problem and a policy permitting post-merge recovery; return an executor contribution rather than another dashboard.

**I — Better models / owner:** absolute rankings will age; matched tasks with independent checks and escalating maintenance sequences can remain useful. **E — Two-to-three-week v1:** three small app domains, six to ten evolution tasks, deterministic service simulators, two framework arms, runner adapters, raw JSON and a static viewer. An Elm/React/Foldkit frontend arm is a later extension only after acceptance parity is demonstrated.
