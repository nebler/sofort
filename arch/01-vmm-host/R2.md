## 1. Cold builds

macOS 26.6.1 (25G76), M4 Pro, Rust 1.95.0, libkrun a1d8616.
`cold-bench.py`, n=100/build after 3 warmups and a separately recorded initial
launch. Full samples in r2/cold-results.json. Uptime start load
**18.93/18.71/18.15**, end **19.07/18.75/18.17**.
Numbers below are **p50 / p90 / p99 milliseconds**, fresh processes, cached
executable/signature/files. All five apply the same compatibility Seatbelt
profile before build. These include confinement setup, unlike some r1 hosts.

| Build | spawn→main | spawn→first guest instruction |
|---|---|---|
| Dynamic libkrun dylib | 6.187 / 10.128 / 13.962 | 14.613 / 24.044 / 33.600 |
| Supplied rlib, -O | 5.596 / 7.986 / 11.133 | 13.296 / 18.443 / 27.204 |
| Supplied rlib, -O, strip -x | **5.348 / 8.816 / 16.463** | **12.679 / 20.187 / 32.204** |
| Supplied rlib, -O, fat LTO | 5.415 / 8.493 / 12.446 | 12.999 / 20.620 / 32.560 |
| Minimal no-features rlib, LTO, strip | 5.495 / 9.368 / 12.348 | 13.468 / 20.192 / 32.262 |

Static stripped was the fastest observed median: main 0.839 ms faster than
using the dylib, first instruction 1.934 ms faster. LTO/minimal did not produce
an additional measured latency win; deltas among static builds are small
relative to loaded-host variation. Do not claim a significant LTO speedup.
The minimal binary is ~750 KiB versus ~1.1 MiB stripped supplied-rlib and ~1.4
MiB unstripped; dynamic launcher ~503 KiB plus 3.1 MiB library.
`otool -L` confirms static variants have no libkrun dylib dependency (system
Hypervisor/libSystem/libiconv remain). Build metadata retained separately.

**Fastest measured recommendation:** rlib + -O + strip. **Integration build
choice:** minimal-feature rlib + fat LTO + strip for its smaller deployed image
and no optional/FFI feature graph; measured latency was within 0.8 ms of the
fastest static median. No claim that it wins latency. The built CLI uses this
minimal native API path with the exact upstream runtime sources restored.
The minimal benchmark only added constructor diagnostics/optional GIC override;
those experiment hooks are absent from the delivered CLI.

The dynamic comparison uses a Rust C-ABI adapter, since the native Rust API
cannot directly import a cdylib. This does not confound spawn→main; it may add
small after-main differences. No C shim or dynamic adapter ships in the CLI.

First-instruction timing is literally the first `mrs cntvct_el0` at _start;
its value is later printed over console. On this HVF build CNTV offset is zero,
so guest counter and host mach_absolute_time share the same time domain.
Python monotonic_ns surrounds Popen; mach_timebase_info is 125/3 ns/tick.
All 500 accepted samples satisfy spawn ≤ main ≤ guest ≤ reaped.

## 3. Parking / D4 options A and B

Native GIC constructor succeeded on this OS. Native WFI recorded **zero**
vstate::wait_for_event entries while passing 1000/1000 exchanges: Apple handles
sleep/wake inside hv_vcpu_run. Native set_irq indeed never signals the userspace
WFE channel; the false premise was that this WFI was blocked on that channel.

| Variant | completed | idle CPU % core, 5s | echo p50/p90/p99 ms | start load |
|---|---|---|---|---|
| Native GIC + WFI | 1000/1000 | **0.000100** | 0.144 / 0.669 / 5.031 | 27.22/21.10/19.11 |
| Forced userspace GIC + WFI | 1000/1000 | **0.000225** | 0.057 / 0.117 / 0.702 | 25.71/20.98/19.09 |
| Native GIC + WFE | 1000/1000 | **3.190 (FAIL)** | 10.277 / 98.281 / 195.099 | 50.69/27.29/21.45 |
| Timer-only 1ms WFI | 1000/1000 | **0.494** | 2.014 / 16.195 / 106.948 | 101.87/44.64/28.17 |

Echo is one host byte → one guest byte, **not a JS result**. Host inserts 1ms
between exchanges, and verifies exact bytes. CPU = task user+system mach ticks
converted to ns / elapsed time. Native A wins on no patch/no polling; B is a
working fallback for timed waits, but its heavily contended latency is not a
fair ranking. The WFE choice fails the CPU gate even under contention.

Small reviewable **diagnostic** builder override + trace patch is in
r2/diagnostic-gic.patch. Forced userspace logged 1462 channel waits and passed.
Do not ship it: native WFI already passes. GIC setup/edge IRQ33/IAR+EOI and
check-before-sleep are in the tiny C/asm guest; detailed source trace and exact
runtime evidence are in r2/PARKING.md. All implicit device constraints remain
as settled: one console, plus GIC and PL031; no RTC toggle is invented.

## 4. Pre-spawned, not pre-booted / D4 option C

`go-bench.py`, **n=100 bare and n=100 r1 qjs**, randomized interleave.
Load start **18.91/18.61/18.15**, end **22.38/19.36/18.42**.
Blocking prepared worker idle CPU **0%** over **5.004s**; no VM/vCPU yet.

| workload | go→first guest instruction p50/p90/p99 ms | go→qjs READY p50/p90/p99 ms |
|---|---|---|
| Tiny bare image, 32 MiB | **1.295 / 5.473 / 10.855** | n/a |
| Private copy of 02 r1, 64 MiB | **2.035 / 5.797 / 11.560** | **10.668 / 26.547 / 52.807** |

Private r1 changes: capture first instruction and embed `print("READY")`.
Actual unmodified stripped static Bellard qjs runs at EL0. R1 physical mapping
needs 64 MiB; 32 MiB hangs before qjs, so no fabricated 32 MiB qjs result.
This is actual r1 initialization cost (including old ELF load/copy), not the
packed-r2/bootstrap/executor gate. C hides exec, scanning and sandbox setup,
but does not hide qjs boot. A's initialized WFI guest remains preferred when
02's complete guest path passes. Deadline/SIGKILL/reap stays external in A/B/C.
