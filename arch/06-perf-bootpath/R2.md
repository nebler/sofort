## Machine, provenance, and clock contract

Apple M4 Pro, 12 logical CPUs, 24 GiB; macOS 26.6.1 (25G76), HVF, Rust 1.95.0. One vCPU, **32 MiB** guest RAM, qjs 16 MiB allocation limit, one inout console; sandbox before build; panic=abort and external 10 s per-sample watchdog. Every process was exited/killed and reaped. Tests use a local host addition tool, not a remote API or the TS executor.

Final exact rows use byte-identical copies of 02's READY image and 01's final executable: kernel SHA256 `00040cfa7187a3cf25fb7cf8f01d973bf41f4f9179b4fc382dcb890b34d13edf`; VMM SHA256 `f514554ffaf4eba25d00137168219bf4cfcc5b6bf2f7191afab26e2eb37ecc3d`. All edits are private copies under this area or /tmp/jitk-06. The RAW image packs qjs at its final PA; no guest ELF parse/copy.

Integrated window uptime: `2:41  up  3:55, 2 users, load averages: 48.28 50.41 48.30` → `2:42  up  3:56, 2 users, load averages: 45.91 49.51 48.08`. All eight cases were randomly interleaved, 100 each. The one-minute load stayed severely elevated; intermediate readings are in r2-integrated.json. **These are loaded-host distributions, not idle estimates.**

Cold = fresh worker+VM, warm filesystem/code-signature caches, timing immediately before Popen/spawn. No build, image download, re-sign, or parent Python/Node startup in that boundary. FIRST and READY timestamps are buffered until shutdown. All tool results are asserted from JSON (`done.ok === 2`), not exit status.

Guest stamps: _start entry before BSS clearing; return from MMU init; immediately before EL0 eret; first syscall trap; the first JS statement's observable stdout syscall; READY JSON prefix; first ppoll observation of readable RX after READY. The first-statement boundary includes interpreter/stdio work and is not a JS instruction hook. The marker adds one short output before the bootstrap; exact rows use the untouched bootstrap with no marker. Guest intervals are elapsed wall time and include vCPU descheduling/MMIO exits.

Host marks: spawn boundary/return, main, sandbox begin/end, build entry/return, first hv_vcpu_run, READY receipt, submit, call receipt, response write, result receipt, _exit entry, wait/reap. build() starts the vCPU before returning, so build-return is not a serial boundary. Do not sum per-phase medians or percentiles.

Host RAW clock is also Node hrtime; mach_absolute_time has a different origin. libkrun hvf/src/lib.rs stores fresh vtimer_offset=0 and documents CNTVCT=mach_absolute_time-offset. Intersecting all 800 retained bracketed RAW/absolute pairs gives a constant origin offset 3399615646874 ns with **±2.541 µs** uncertainty. All guest-entry, READY and RX cross-clock orderings pass. No pause/suspend occurred; this mapping does not apply after snapshot pause/resume.

## Process exec, dyld controls, and code signing

Python directly calls os.posix_spawn or os.fork+os.execve with identical pipe endpoints; fork does not create another Python interpreter. Node uses asynchronous child_process.spawn from `/private/tmp/jitk-09/node-real`, not a PATH shim. Parent runtime startup is excluded. First exec after a changed signature has a **hundreds-of-ms** admission/cache/policy effect even in trivial C. This experiment does not identify how much is AMFI hashing, policy lookup, loader work, or scheduling: the **exact code-signature-validation CPU/time component is UNVERIFIED**. Do not call the whole delta dyld or validation alone. Build/sign once, validate ahead of serving, and retain the first-launch risk in rollout/refill planning. No system policy/cache was disabled or modified.

**Minimum achieved on this machine (observations, not guaranteed floors):** cached plain-C posix_spawn→main **1.602 ms**; framework control **2.860 ms**; dylib+framework control **3.644 ms**; static-minimal VMM **3.438 ms** (all from immediate-second signed pairs, n=100). The final-source VMM bench twin achieved **4.507 ms** in its n=100 posix_spawn window; Node final minimum **4.754 ms**. An idle-machine p50 or hardware minimum remains UNVERIFIED. Subtracting these minima does not produce an additive loader breakdown.

**REJECTED interpretation:** round-1 “9.4 ms exec+dyld” is not a fixed intrinsic dyld cost. It is a combined process/loader/runtime/scheduling span under a particular load. The controls, signature experiments, mixed static results, and newly separated sandbox cost explain why one fixed number is insufficient; no private OS subphase is fabricated.
