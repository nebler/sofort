## Nested harness limitation (not hidden by READY)

A repeat with **four outer Linux vCPUs** passed parking, then the outer Debian
kernel hard-locked during subsequent boot stress: watchdog CPU2 hard lockup at
36 s, RCU stall at 41 s, CPU1 hard lockup at 60 s. Raw evidence:
`out/nested-smp4-lockup.log`. SIGTERM did not stop that owned QEMU; SIGKILL did.
An earlier four-vCPU full run passed before parking was added
(`report-before-parking.json`). The final one-vCPU run passed every gate.
**Cause UNVERIFIED**: do not call this a guest SPI/edge-routing bug or a metal
failure. Defaulting the nested harness to one vCPU avoids the observed failure
in this run; it is not proof that the underlying nested-HVF SMP issue is fixed.
Another simultaneous harness start also got HV_NO_DEVICE creating its VGIC;
serializing/reducing our own harness usage resolved that resource failure.

These are retained raw; **precise guest versus host-user attribution is

The requested user/system counters and guest estimate are measured; a precise
additive profile needs better per-thread guest accounting on metal.
[Linux proc accounting](https://www.kernel.org/doc/html/v6.12/filesystems/proc.html)
and [guest-in-utime semantics](https://man7.org/linux/man-pages/man5/proc_pid_stat.5.html).

Top three measured cost buckets / proposed fixes (not claimed flamegraph sites):
1. **Host system CPU** dominates: c4 9.164 ms. Bare-VM system is 1.963 ms;
   setup-only is 0.778 ms. KVM/irqfd setup, MMIO exits, faults and thread creation
   are candidates, not individually profiled shares. Profile ioctl/exit counts
   on metal; test file-backed immutable image pages and fewer console threads.
2. **Guest execution** is approximately 3.7–4.8 ms in these counters: kernel
   MMU/GIC/virtio startup plus qjs/bootstrap. Bare guest estimate ~0.2 ms. Test
   fewer boot MMIO transactions/batched console setup; optimize qjs startup only
   after a metal guest profile. Parking hides latency, **does not save refill CPU**.
3. **Supervisor + clone wrapper**: c4 Python 0.684 + wrapper 0.196 = **0.880 ms**.
   Integrate CLONE_INTO_CGROUP in the persistent native supervisor rather than
   exec/wait a wrapper per VM; measure the real TS executor, not Python overhead.

What transfers: single-use lifecycle, copied image/device topology, syscall and
MMIO work, and the need to remove per-VM orchestration overhead. What does NOT:
HVF versus KVM setup cost, L0 nested exits, virtual CPU accounting/steal effects,
contention distributions, or any CPU-ms value. The 12.9 ms Mac figure and nested
12.919 ms coincidence do not validate a metal forecast. **The 5 CPU-ms kill line
is still unpassed/UNVERIFIED on metal**, not waived. No Linux exec/s/host claim.
