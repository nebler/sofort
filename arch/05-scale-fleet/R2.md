## Objection 2 — FIXED: the resource is HVF address spaces

`sysctl`: **kern.hv.max_address_spaces=128**, kern.hv.supported=1,
kern.maxproc=6000, kern.maxprocperuid=4000. Full kern.hv sysctls and process
inventory are in r2/results/host-environment.txt.

`hvf_slot.c` calls only `hv_vm_create(NULL)` and blocks on stdin; **no libkrun,
RAM mapping, vCPU or guest**. `hvf_limit.py` ran two saturation rounds, stopping
nothing else. Both created **117** live address spaces; the next **30/30**
creations returned **0xfae94005 = HV_NO_RESOURCES**, as defined by the local
Apple Hypervisor SDK's hv_error.h. Closing one owned slot immediately allowed
one new successful creation, **2/2** release/reacquire checks. All children
reaped; zero survivors. `r2/results/hvf-limit.json` has exact uptime, vm_stat,
process counts, attempts and codes.

Only **649/652 total system processes** preceded these tests, far below either
process ceiling even with another 117 children. The VM test has no guest RAM;
free-memory differences between rounds did not change its count. Therefore the
observed ceiling is **system-wide HVF address-space exhaustion**, not libkrun's
memory tier or a per-user process cap. 117 slots were available during R2,
versus 127 in R1: availability changes with other VMs. The configured total is
128; 127 is not a universal macOS jitk capacity.

Docker's Virtualization.framework VM remained present throughout. R1's one
unavailable slot is consistent with Docker; exact ownership of every occupied
address space cannot be enumerated through these public interfaces and is
**UNVERIFIED**. Do not claim a Docker-stop counterfactual was measured. No need
to stop Docker to identify the exhausted resource.
