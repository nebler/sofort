# Guest memory: the heap pool, mremap and the HVF dirty reset (2026-10-31)

`2026-10-31-capacity.md` left the guest allocator open: the Sofort guest's
heap high-water looked 2–10× what QuickJS needs, and T4 3 failed on every
class. This round measured the cause, fixed the kernel's memory paths, and
made the HVF reset copy only what a run wrote, so that a large class no
longer costs memory or reset time for small jobs.

## Summary

- **The 2–10× was mostly the reference.** The QuickJS-Wasm column counted
  blocks, not bytes (quickjs-emscripten's build has no
  `malloc_usable_size`, so QuickJS charges 8 bytes a block). On the guest's
  own QuickJS (2026-06-04, 64-bit, natively, exact requested bytes) the real
  programs need 0.6–13.1 MiB; the guest held up to 1.9× that before and
  1.06–1.54× after, for the programs whose replies arrive in sequence
  (`../tasks/README.md` "Working sets").
- **The fragmentation was real, and is gone.** mmap took the first free run
  of pages in a window linear in the physical address, and there was no
  `mremap`. Every heap page now comes from one pool at any free VA, and
  `mremap` moves descriptors. High-water fell 15–26% on most programs; T4 3,
  which no class completed, completes on glue-16m.
- **Fit matrix (HVF, S1, 100 runs):** glue-2m 0 → 8, glue-4m 56 → 68,
  glue-8m 92 → 92, glue-16m 96 → **100**. KVM (kvm-dev, one run of each
  program) completes the same programs per class.
- **HVF reset** copies only what a run wrote: `return 2` reset p50 is 34–40
  µs on every class (before 82–909 µs), and an idle slot's engine process is
  ~2.4 MiB on every class (before 3.1–17.4 MiB).
- **Default: glue-16m** (switched in `e287d79d`), the only class that
  completes every real task, now at glue-2m's idle cost and small-job reset
  on HVF (below).

## Cause, with evidence

`bench/v1/harness/heap-trace.ts` runs the programs on a diagnostic snapshot
whose kernel is built with `--features heap-trace` (`kernel/src/heap_trace.rs`):
every mmap, munmap, mremap, brk and madvise, the pages mapped after each,
and the window's page map at the first ENOMEM.

**The allocator.** The payload is Bellard QuickJS 2026-06-04 linked with
musl 1.2.5, whose malloc is mallocng (`kernel/payload/ring-rng/build.sh`).
QuickJS 2026 carves objects of up to 512 bytes from 4 KiB arenas it gets
from malloc; mallocng serves sizes up to ~128 KiB from groups it maps (8,
16, 17 and 32 pages are the common mappings), maps each larger block
alone, frees a group with munmap when its slots are free, grows its
metadata a page at a time with brk, and grows a large block with
`mremap(MREMAP_MAYMOVE)`, falling back to malloc, copy and free when that
fails.

**Before, on glue-16m:**

- T4 3 failed with 3,194 of the window's 3,634 pages mapped and 440 free in
  runs of 285, 135, 10, 4, 2, 2, 1 and 1, for a 307-page request (the join of
  its third 1.3 MB reply).
- Every `mremap` returned ENOSYS, so each growth of a large block (T4 3: 41 →
  61 → 92 → 137 → 205 → 308 → 461 pages, a join's buffer) held the old and the
  new block at once.
- The window's high-water ran 3–35% above the pages actually mapped (T4 4:
  4,000 against 2,976 KiB; T1 1: 1,048 against 872 KiB; T2 4: 10,484 against
  10,312 KiB).
- At the peak, 76 mappings of 32 pages (9.5 MiB of T4 3's 12.6 MiB) were
  mallocng groups, mostly holding objects the program keeps.

**The reference.** `bench/v1/harness/quickjs-ref.ts` runs each program on the
guest's QuickJS natively (`quickjs-ref/ws.c`), counting requested bytes.
QuickJS itself needs 13,464 KiB for T4 3 (it keeps 5,722 points, each with
two arrays) and 9,300 KiB for T2 4. No allocator fits them in glue-8m's
6 MiB heap.

**The transport.** The ring bootstrap joined a reply's 16 KiB fragments.
QuickJS's join grows its buffer 1.5× at a time, so a reply of n bytes held
about 2.5n at once (on the reference QuickJS, 1.31 MB of 16 KiB fragments
peaked at 3.27 MB joined and 2.68 MB as a rope).

## Fix and why

Options evaluated against the evidence:

- **(a) page-granular mapping: chosen.** It removes the failure outright:
  a request fails only when the pool has fewer free pages than it asks for.
- **(b) a real mremap: chosen.** It is cheap once pages are not tied to
  their address, and it removes the double hold on every large growth.
- **(c) best-fit with coalescing: rejected.** It still fails a request
  larger than the largest hole, and on these traces the holes were the
  problem.
- **(d) a different guest allocator: not needed.** mallocng's own overhead
  at the native peak is 1.5–5.6% (replaying the reference's allocation
  trace through its size classes), and changing it means rebuilding and
  re-proving the RNG-repaired payload.

Changes:

- **`kernel/src/heap.rs`** (ring profile only).
  - Every arena page between the user data copy and the stack is one pool,
    taken lowest first and zeroed when taken. That spans the former 64 KiB
    brk and the mmap window.
  - mmap, brk and the user L3 tables take single pages. Tables are
    allocated when a 2 MiB block of VA gets its first page and freed with
    its last.
  - mmap VA moves above the stack, `[0x2000000, 0xc000000)`, 10× or more
    any class's pool. Its first-fit search starts at the lowest free page.
  - `mremap` (flags 0 or `MREMAP_MAYMOVE`) shrinks in place, grows in
    place when the next pages are free, or moves the descriptors.
  - The static 64 KiB of user tables are gone, which gives that memory to
    the heap.
- **An emergency reserve.** Without holes, the request that runs out is
  often a small one. QuickJS then cannot allocate its out-of-memory error
  either and throws `null`, and Node classified that as a guest error, not
  LIMIT; mallocng also stops using brk after one failure.
  - Every request leaves 1/32 of the pool (24–40 pages) until one fails in
    the run. After that, requests of up to 32 pages may use it.
  - A small brk growth may always use it.
  - A request counts only the page tables its range lacks.
  - Result: every out-of-memory failure in the fit matrix is an
    InternalError again. It costs glue-2m a few runs at its edge (8 of 100
    complete, 20 without a reserve).
- **`kernel/ring-bootstrap.js.in`.** A reply's fragments form a rope (`+=`),
  which JSON.parse flattens into one exact-size string, instead of a join.
- **`HEAP_PEAK`** (STATS `heapPeakBytes`) is now the most pool pages in use
  at once (`shard/ABI-R7.md`). The ring ABI and layout record are
  unchanged: no ABI bump, new snapshots by kernel hash as always.
- **The console image is byte-identical** (5325be7f, as `kernel/.READY`):
  every change is behind the ring feature, so `.READY` needs no
  re-promotion.

## Security properties checked

- **W^X.** Heap pages are only ever mapped RW with UXN and PXN; `map_page`
  asserts it. mmap still refuses any protection but RW and `MAP_FIXED`. Page
  tables are never mapped to EL0. Covered by the kernel isolation tests
  (`make -C kernel test`: heap-exec, text-write, alias-write, fs-alias-write)
  and test-ring.
- **User/kernel separation.** A pool page is free, a user page, or a page
  table, never two at once. The bitmap asserts a page is in use when it is
  freed. A table is reachable only through the EL1 identity alias, whose
  descriptors have no EL0 access; a freed page's descriptor is cleared and
  the TLB flushed before EL0 runs.
- **Pointer validation** (`user.rs` `access`) walks the same tables page by
  page, within `USER_BASE..USER_END`. `USER_END` (ring) stays below the
  doorbell block.
- **All writable state stays in the arena.** The pool, its bitmap, the
  per-block counts, the reserve latch and every table are arena pages or
  kernel `.bss` in the arena, so a reset restores them. The arena is still
  the only writable memory a tenant can reach.
- **HVF dirty reset** (`shard/src/hvf.rs` `MemoryReset::Dirty`).
  - The arena is read-only at stage 2. A granule becomes writable only in
    the write-fault handler, which records it first, so an unrecorded
    granule is unchanged since it was restored.
  - Host writes into the arena record their granules. The transport is
    always copied.
  - The reset copies and cleans (DC CIVAC) every recorded granule, or
    remaps the arena from the file.
  - Verified byte for byte after every reset by the hostile cache-off,
    corpus, never-execute and leak-mix tests in that mode, plus
    `dirty_reset_restores_host_writes_and_reprotects`. `hvf confine`
    passes: a confined child still runs and resets a guest.

## Default class

**glue-16m, the default since `e287d79d`.**

- It is the only class that completes all 25 real programs.
- Its costs now track what a run uses, not the class:
  - **HVF:** with the dirty reset, an idle glue-16m slot is ~2.4 MiB, as
    glue-2m's is, and `return 2` resets in ~40 µs against 34 µs on glue-2m.
    A large job pays for what it wrote (below).
  - **Linux:** KVM already copied only dirtied pages.
- It still charges 16 MiB per START (`Engine.limits.memoryMB`) and accepts
  4 MiB replies.

The switch is `DEFAULT_SHARD_CLASS` in `executor/shard-backend.ts` and
`tslib/deps.ts` (then rebuild the deps tool). It also moves the parity
allowlist's `t-memory-over-arena` (twice glue-16m's arena passes the console
path's 16 MiB limit too), the HVF parking-gate receipt, and the published
glue-8m figures. The owner approved it on 2026-10-31; Mac CI and parity pass
on it (parity: 95 ok, `t-memory-over-arena` still allowlisted).

|---|---:|---:|---:|---:|---:|
| glue-2m | 82 → 34 µs | 122 → 72 µs | 83 (201) µs | 3.1 → 2.5 MiB | 11.0 → 11.0 MiB |
| glue-4m | 186 → 34 µs | 230 → 73 µs | 137 (221) µs | 4.6 → 2.4 MiB | 14.0 → 15.0 MiB |

How the dirty reset works:

- A guest write to a read-only arena granule (16 KiB) exits to the engine,
  which makes it writable and resumes the guest. Each such fault costs
  ~6 µs.
- A hot set of up to 128 recorded granules stays writable across resets,
  so a repeated small job takes no faults. It is re-protected every 16th
  reset.
- A larger set is not copied back: the reset remaps the arena from the
  file, read-only. That is cheaper, and it returns the run's pages to the
  kernel at once instead of at the 2 s idle trim. The child then calls
  `malloc_zone_pressure_relief` for the host heap the run's messages grew.

What stays after the bench tasks (11–15 MiB) is the engine child's own host
heap and the hot set. The zygote is separate (4.5 MiB idle; it grows with
the largest message it relayed, unchanged by this round).

**Linux** (kvm-dev, nested KVM, so times are not performance claims). One
slot. RSS is the shard process. Before = `2026-10-31-capacity.md`.

| class | KVM reset p50, `return 2` | shard RSS after `return 1` | after the bench tasks |
|---|---:|---:|---:|
| glue-2m | 182 → 106 µs | 11.6 → 9.5 MiB | 14.0 → 11.8 MiB |
| glue-4m | 188 → 108 µs | 15.0 → 14.5 MiB | 17.6 → 16.8 MiB |

dirties fewer distinct pages, and the KVM copy reset (pagemap) copies fewer.
The KVM idle trim (2 s) is unchanged.

## Risks

- **Write-fault cost on HVF.** A run that writes many new granules pays ~6
  µs each (a 900-granule T4 run: ~5 ms, against a 900 µs full copy before).
  The hot set hides this for repeated small jobs, not for a stream of
  different large ones.
- **The hot set.** Up to 128 granules (2 MiB) are copied at every reset
  until the 16th, and a slot's footprint keeps them until idle trim.
- **The reserve's sizing is empirical.** Below 24 pages it leaves the
  `null` failures; 40 pages cost glue-2m runs. A program that runs out
  through many small allocations after the latch opens can still exhaust
  it.
- **Semantics changes.**
  - mmap VA is now above the stack.
  - `munmap` and `mremap` accept mmap VA only, as before.
  - brk can grow to 1.5 MiB (the old cap was 64 KiB), backed by the pool.
- **The QuickJS-native reference** delivers replies at once and differs in
  GC timing, so it is a reference for QuickJS's need, not a lower bound on
  every guest run (T4 2, T4 5).
